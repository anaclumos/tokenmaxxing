# Self-update on the check tick

- The Bun global self-update runs `bun add -g tokenmaxxing@<version>` with no preceding `bun remove -g`. The `DependencyLoop` error recorded in `AGENTS.md` belongs to installing a local `.tgz` over an existing global, not to a registry version.
- The global root is detected from the running entry: the first of `BUN_INSTALL_GLOBAL_DIR`, `BUN_INSTALL/install/global`, `dirname(dirname(process.execPath))/install/global`, and `~/.bun/install/global` whose `node_modules/tokenmaxxing/src/main.ts` is the real path of `Bun.main`. The executable-derived candidate is what makes a timer unit without `BUN_INSTALL` in its environment still find a custom Bun root; `process.execPath` is the real binary path, never the invoked symlink. A `bunfig.toml` `install.globalDir` is not read, and a root set only through `BUN_INSTALL_GLOBAL_DIR` is invisible to a timer that does not carry it, so both read as unmanaged and never self-update.
- The self-update runs after the evaluation and the parked sampler, outside the pool lock and the Claude refresh lock, so a stalled registry request never delays a swap.
- The install child runs with `cwd` at the state directory and `BUN_INSTALL_GLOBAL_DIR` set to the detected root, because `bun add` reads `bunfig.toml` from its working directory and the environment variable wins over that file, and it is killed after 60 seconds (`Bun.spawn` `timeout` with `SIGKILL`), because launchd and systemd skip a firing while the previous check runs and an unbounded child would block every later tick. The stderr read starts before the exit wait and is raced against a one-second delay after the exit, because a descendant that inherited the pipe keeps the read pending after the direct child is killed.
- Only the Claude `init` installs the check timer. A Codex-only install has no tick and no self-update; that ceiling is documented, not engineered around.
