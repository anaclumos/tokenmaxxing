# Agent rules

Standing rules for anyone (human or agent) working in this repo. Follow them exactly.

## Code style

- Never use `typeof`. Use zod.
- Never use `interface` or standalone `type`. Model data as a zod schema and derive the type with `z.infer`.
- Always use es-toolkit instead of shipping hand-written utility code.
- Never use an em-dash. Use a regular hyphen, a colon, or parentheses.
- Do not cast to `any` to get around a type issue. Fix the type.

## Behavior

- Be humble.
- You will not know everything, and your knowledge cutoff may be aggressive. Assume you are behind.
- NEVER ASSUME ANYTHING. There is infinite exa, grep, and context7 quota. Always search the web / the codebase before acting.
- Always search the web whenever possible.
- Install things via the CLI (`bun add`, etc.) so you get the latest versions.

## State and compatibility

- This application has no external installed user base. Optimize for one canonical current-state implementation, not compatibility with historical local states.
- Do not preserve or introduce compatibility bridges, migration shims, fallback paths, compact adapters, or dual behavior for old local states unless the user explicitly asks.
- Prefer: one canonical current-state codepath, fail-fast diagnostics, explicit recovery steps.
- Over: automatic migration, compatibility glue, silent fallbacks, "temporary" second paths.
- Default stance: delete old-state compatibility code rather than carry it forward.
- If temporary migration or compatibility code is introduced for debugging or a narrowly scoped transition, call it out in the same diff with: why it exists, why the canonical path is insufficient, exact deletion criteria, and the task that tracks its removal.

## Editing hygiene

On every edit, delete:

- Extra comments a human wouldn't add, or that are inconsistent with the rest of the file.
- Extra defensive checks or try/catch blocks that are abnormal for that area of the codebase, especially when the caller is a trusted / validated codepath.
- Casts to `any`.
- Any other style inconsistent with the file.

## Project

tokenmaxxing (greenfield 2026-07-08) is Sunghyun's CLI for managing usage quota across the owner's own agent-CLI accounts: pool the owner's Claude Code (and eventually Codex) logins, swap to a fresher one when the active account nears its 5-hour or weekly limit, and keep sessions continuable across swaps. Every design decision serves that goal. Full design lives in `DESIGN.md` (auth/quota internals in its §2).

- Scope (2026-07-08, after the user twice narrowed it): v1 is Claude Code ONLY, macOS first. Linux support landed 2026-07-09 (commit bca7551). Codex is dropped for now; its verified mechanics are preserved below for v2.
- The npm name `tokenmaxxing` is owned by the user (anaclumos). v0.1.0 shipped 2026-07-09 (GitHub release + full acceptance: 32 unit tests, hermetic swap/concurrency/model-aware E2E, CLI init/doctor/uninstall through the compiled binary). Linux verified green in both a Docker ubuntu:24.04 arm64 container and on stella.
- All config and state live in `~/.config/tokenmaxxing/`. `CLAUDE_CONFIG_DIR` is used ONLY during `add` onboarding. There is NO `adopt` command: `tokenmaxxing init` auto-registers the existing login as account #1, and init's repair branch re-pins claudeBin and saves config.
- Bare `tokenmaxxing` / `xx` runs `status` (user ask 2026-07-09); `switch` stays explicit.
- The ideal install story the user wants: `bun i -g tokenmaxxing`.

## Architecture

- Supervised-respawn model: the user types `claude` as always, but PATH resolves to a thin supervisor shim (`~/.config/tokenmaxxing/bin/claude`) that runs the real claude with inherited stdio + saved `stty -g` termios (not a PTY copy) and watches for a respawn marker. The supervisor is process/PTY-only, NOT an API proxy.
- Swap mechanism: the statusLine shim tees `usage.json`; the Stop hook (once the decision engages, see switch policy) takes a `flock`, swaps the credential (harvest A, refresh B, write the refreshed blob to the `Claude Code-credentials` keychain item, atomically swap `oauthAccount` in `~/.claude.json` under claude's `~/.claude.lock`), writes a `respawn/<session_id>` marker, and `kill -TERM $PPID`; the supervisor sees the marker and relaunches `claude --resume <session-id>`. The kill happens ONLY at a salvageable state (post-Stop, turn committed to transcript, claude idle): that is WHY the thresholds sit below 100%, headroom to reach a clean boundary before the wall. Thresholds are split per window since 2026-07-16 (user decision) and are SCREENING bars only: `thresholds.session` 95 for the 5h window (a session reset is cheap to sit out), `thresholds.weekly` 98 for the 7-day aggregate AND per-model weekly caps (weekly quota is use-it-or-lose-it, drain it closer to the wall; the user re-confirmed 98 for the Fable cap when asked 2026-07-16). History: single `threshold` 95 at v0.1.0, raised to 98 on 2026-07-14, split + demoted to screening-only 2026-07-16; the old flat `threshold` config key is simply ignored (defaults apply), no migration shim. Works for N concurrent sessions: per-terminal supervisor, per-session id, each respawning independently under one shared swap.
- Since the 2026-07-10 hot-swap correction (see auth internals below), supervisor respawn is NOT needed for credential adoption on Claude Code; its remaining value is UX (depleted-pool countdown + auto `--resume`). A periodic timer-driven switch is architecturally sound on both platforms. Codex still requires a process restart to switch accounts.
- `init` auto-appends the supervisor PATH line to the shell rc (zsh via ZDOTDIR/.zshrc, bash via .bashrc; `TOKENMAXXING_SHELL_RC` test override; marker `# tokenmaxxing PATH`): user decision 2026-07-09. Reason: the `claude` shim must win PATH resolution, a package manager cannot guarantee that, and claude's auto-updater owns `~/.local/bin/claude`.
- Credential storage: `credstore.ts` is one facade over a `{kind: keychain|file}` target union. darwin = keychain via security(1) (`keychain.ts` is just that backend). linux = atomic 0600 files: live = `credDir()/.credentials.json` mirroring claude's exact resolution (incl. `CLAUDE_SECURESTORAGE_CONFIG_DIR` first); parked = `~/.config/tokenmaxxing/creds/<item>.json` in a 0700 dir; isolated = `<configDir>/.credentials.json` (no hash namespacing on Linux). `isolatedTarget(dir)` is first-class; add/sample use it.

## Stack and dependencies

- TS on Bun. Deps are exactly: zod, es-toolkit, ky. ky does the bounded Retry-After GET retries: do not hand-roll them. `flock(2)` via `bun:ffi` (`dlopen("libc.so.6")` works on Linux arm64 glibc; LOCK constants identical to darwin).
- Config is JSON at `config.json` (user dropped TOML/smol-toml 2026-07-09: "let's just use json").
- node:fs/path/os ARE Bun-native (Zig impls); Bun's docs point to node:fs beyond Bun.file/Bun.write, which are async-only, non-atomic, and have no create-mode, so they are unfit for the 0600 cred store and the flock fd (assessed 2026-07-09). The user probes for simplification regularly; keep this rationale handy.

## Claude Code auth and quota internals (verified)

Verified against Claude Code 2.1.204-2.1.207 and Codex CLI 0.143.0 (rust-v0.143.0 source). Both CLIs change monthly: re-verify before trusting in a later month.

- macOS: creds live in the Keychain, generic-password, service `Claude Code-credentials`, account `$USER`. There is no `~/.claude/.credentials.json` on macOS.
- Linux (binary-verified 2.1.205 native ELF + strace): the build is compile-time specialized; the credential-storage selector returns the plaintext-file store unconditionally and the keychain prefetch is a stub (no keyring/libsecret path). Creds file = `<credDir>/.credentials.json` (mkdir + write + chmod 0600), where credDir = `CLAUDE_SECURESTORAGE_CONFIG_DIR ?? CLAUDE_CONFIG_DIR ?? ~/.claude` (SECURESTORAGE checked FIRST, empty string falls through, `.normalize("NFC")` applied). No hash-namespacing on Linux: `CLAUDE_CONFIG_DIR` isolation is just the file inside that dir. `.claude.json` = `$CLAUDE_CONFIG_DIR/.claude.json` else `~/.claude.json` on both platforms.
- Setting `CLAUDE_CONFIG_DIR` on macOS namespaces the Keychain service to `Claude Code-credentials-<first 8 hex of sha256(NFC(raw env string))>`. The hash is over the RAW string, so the path must be byte-stable (trailing slash or `~` vs absolute yields a different entry). A missing namespaced keychain item does NOT fall back to the un-suffixed live item: it falls back to `<CLAUDE_CONFIG_DIR>/.credentials.json` then `{}` (binary-verified), so isolation is sound once the env is clean.
- Account identity sits in `.claude.json` `oauthAccount`; quota is metered server-side per `organizationUuid`.
- HOT-SWAP ADOPTION (corrected 2026-07-10 after the user's live observation exposed a wrong recorded verification; mechanism confirmed in 2.1.204/205/206 alike): a running claude session DOES adopt an externally swapped credential on both platforms, without restart. Every ensure-fresh call starts with a freshness poll: Linux mtime-stats `.credentials.json` and hard-flushes all token caches on change (no throttle); macOS clears the token memos and re-reads the keychain through a raw 30s cache, comparing accessToken. That poll runs at every inference-client creation (the query loop creates the client on the first attempt of EVERY request and recreates it on 401/407/connection-reset) and on every firstPartyApi call with refreshOAuth (including in-session `/usage`). Net adoption: the first request >= 30s after the last raw keychain read on macOS; the next request on Linux. Near-expiry refresh margin is 300s (not 120s), and the refresh path resolves races by adopting a mid-flight external write. A 401 (or 403 "OAuth token has been revoked") force-flushes the 30s cache and adopts immediately. A 429 never invalidates the token, but only the currently-retrying request keeps its snapshotted old token (429 retries reuse the same client); the session's next request adopts the swap. In-session `/usage` shares the exact token caches inference uses, so its account display flips with adoption, and within any 30s window `/usage` and inference necessarily hold the same token.
- Swaps must still run under claude's refresh lock, and a near-expiry session can refresh-write its own account's rotated token into the live store at any time, so harvest-by-true-owner stays mandatory.
- The default keychain item (`Claude Code-credentials`, unnamespaced) is shared by ALL default-profile sessions, so one swap migrates every session.
- There is NO `CLAUDE_CODE_DISABLE_HOOKS` env/flag. `--bare` disables hooks but also kills keychain reads; use `--settings '{"disableAllHooks":true}'` to disable hooks for a nested call.
- statusLine stdin carries `rate_limits`; Stop hook stdin does not. Feed usage via the statusLine shim writing a state file.
- Primary quota source (canonical, user-decided 2026-07-09): `claude -p '/usage'` (free, `num_turns:0`, 0 tokens), run in a throwaway `CLAUDE_CONFIG_DIR` for parked accounts. The direct `GET api.anthropic.com/api/oauth/usage` (Bearer, no beta header; response `limits[]` with `kind` in session|weekly_all|weekly_scoped, `percent`, ISO `resets_at`, per-model rows named by `scope.model.display_name`) was tried and REJECTED by the user: it 429s when the account being sampled is the token running the current session, and it is "the web one"; the user's steer is to fix the CLI method, not bypass it. `/usage` is just a renderer over that same endpoint (verified in the 2.1.205 bundle).
- Two real gotchas of the `/usage` CLI method: (1) it is fail-silent: when claude's internal usage fetch errors/429s, `/usage` prints only local session stats with NO percentage lines, so the ACTIVE/busy token yields nothing; sample the active account from the statusLine `usage.json` push, never by probing its own token. (2) Reset times are human-formatted (`resets Jul 13 at 11:59pm (Asia/Seoul)`); parse them to epoch via `parseResetClock` in usage.ts (month/day + h[:mm]am/pm + IANA tz, year inferred nearest-to-now, zoned-wall-to-epoch via Intl offset).
- `status --force` ping mechanics (built + live-verified 2026-07-16): `/usage` is free and starts NO window; one minimal metered request (`claude -p "Reply with exactly: ok" --model haiku`, ~27k input tokens of system prompt, `--tools ""` does not shrink it) opens the account's 5h session window at that instant - verified live, windows later showed `resets in 4h50m` anchored at the ping. GOTCHA: the server usage feed reflects a freshly opened window with a lag (somewhere between ~10s and a few minutes), so a `/usage` probe seconds after the ping still shows the dormant pre-ping session row; status renders a "usage feed lags" note instead of pretending the ping failed. ## Codex internals (v2 reference)

- Creds in `$CODEX_HOME/auth.json` (0600) by default; can be OS keyring (`config.toml` `cli_auth_credentials_store` = keyring/auto). `CODEX_HOME` must pre-exist as a dir.
- Hot-swap is impossible in a running process: `AuthManager` reloads are gated by `reload_if_account_id_matches`, so swapping auth.json to a different account mid-process is ignored; a restart is required to switch.
- Rate limits: `RateLimitSnapshot{primary(300min), secondary(10080min)}` on `TokenCount` rollout events (often null), or cleanly via `codex app-server` JSON-RPC `account/rateLimits/read`. Limit hit = HTTP 429 `usage_limit_reached`; `codex exec` exits 1 with stderr `You've hit your usage limit`.
- Headless login: `codex login --device-auth` (browser OAuth pinned to ports 1455/1457).
- Neither CLI has native multi-account as of these versions.

## Switch policy and per-model limits

- Switch targets the account FURTHEST BEHIND ITS OWN WEEKLY PACE (user decision 2026-07-13, superseding the 2026-07-10/12 soonest-expiry policy). The user asked for a pace ratio (actual used % over expected % for elapsed window time) and delegated improving the equation; the shipped metric is the forward-looking equivalent, `pacePressure` = remaining% / time-to-weekly-reset, highest first. Same use-it-or-lose-it rationale (weekly allowance is forfeited at a fixed per-account reset, support.claude.com article 11049741): the highest-pressure account is the one most quota is about to be wasted on. The raw backward ratio was rejected because it blows up right after a reset (expected ~0) and ignores how much quota is at risk; pressure strictly refines the old policy (equal remaining = soonest expiry first, equal expiry = most remaining first). Still NOT most-remaining-first in general.
- Bare `xx switch` is GREEDY and IDEMPOTENT: rank every account (current included) by pace pressure among those with every window under its screening bar (session 95 / weekly 98); if the current account already wins, do nothing. It can therefore run periodically and converge. It decides entirely off cached per-account windows: cached resetsAt values are absolute UTC epoch ms, weekly resets extrapolate forward in exact 7-day steps on the fixed anchor, and a session window past its cached reset counts as empty.
- The hooks/timer path (`evaluateAndMaybeSwap`) shares those greedy semantics since 2026-07-16 (user decision: "if there is a more greedily available underused account, we should switch often"). It ENGAGES once the active session window reaches `policy.greedySessionFloor` (default 50) or the active account crosses any screening bar. Engaged-but-under-every-bar = the greedy path: `currentWins` (picker.ts, shared with bare switch) keeps the seat on best-or-tie, otherwise `chooseAndSwap` onto the strictly better account; it NEVER depleted-waits or pre-parks (a usable current account must not be traded for a wait). Over a bar = the hard path, unchanged (swap away or depleted-wait). Below the floor the decision does not run at all: a fresh session rides its account.
- `pickBest` in `src/lib/picker.ts` filters usable accounts (no reauth, not exhausted) and sorts by `pacePressure` descending (a rolled-over cached week counts as fresh 100% remaining; never-sampled or no reset anchor = pressure 0, ranks last), tiebreak soonest `weeklyExpiry` then lowest 7-day usage. `ctx.currentAccountUuid: null` ranks everyone (bare `xx switch` and decide's `currentWins` seat check); non-null excludes the active account (`chooseAndSwap`), which MUST keep excluding it because a per-model-cap trigger leaves the active account aggregate-usable (in the greedy seat check the same protection comes from `currentWins` requiring the active account to pass `isExhausted`, whose gated families cover the burnt cap). Every PickCtx and trigger floor is built from `effectiveBars(cfg)` (thresholds minus projectionMargin): ONE bar per window for trigger and screening alike, otherwise a margin-triggered swap lands on an account inside the margin band and ping-pongs on the cooldown beat.
- Claude subscription quota has THREE limits (confirmed via `/usage` 2026-07-09): current session (5h rolling; statusLine `rate_limits.five_hour`), current week all models (7-day aggregate; `rate_limits.seven_day`), and current week per-model. The per-model cap is NOT in statusLine stdin; it comes only from `claude -p '/usage'`, polled TTL-cached when the active model is capacity-constrained. The hard path fires if session >= thresholds.session (95) OR week-all >= thresholds.weekly (98) OR week-(active model) >= thresholds.weekly; candidate screening (isExhausted/usableAt) applies the same per-window bars (both sides through `effectiveBars`), and the greedy path usually swaps long before any bar via `policy.greedySessionFloor`.
- Per-model weekly caps currently exist ONLY for Sonnet and Fable; there is NO Opus-only quota, and only Fable's cap matters for switching (user's claim 2026-07-12: "we only care about Fable"; "fable = need to switch, sonnet = ok"). `policy.switchModels` defaults to `["fable"]` (state.ts DEFAULT_CONFIG, changed 2026-07-12). The per-model cap bites well before the aggregate: this machine sat at 50% week-all while at 80% week-Fable.
- MODEL-NAME MATCHING TRAP: statusLine `model.display_name` is VERSIONED for Opus (`"Opus 4.8"`, id `claude-opus-4-8`) but BARE for Fable (`"Fable"`). Any exact-match gate on lowercased display names silently excludes Opus; that was the root cause of the 2026-07-09 stella depletion (Opus weekly drained to 100%, 14x "You've hit your weekly limit" over Jul 8-9, zero auto-switch, model-usage.json never created). Match by family substring/prefix, never exact display string.
- `/usage` per-model rows may not list Opus at all: every captured output shows only `Current week (Fable)`, even while an Opus weekly cap was the binding drained limit. All captured probes were of accounts at 0% Opus, so it is UNVERIFIED whether the Opus row appears once real Opus consumption exists; probe an account with known Opus usage before trusting `/usage` as an Opus-cap source.

## Decision-path invariants (v0.6.1, 2026-07-12)

Each guards a verified live failure. Preserve all of them.

- `loadFreshSnapshots` (decide.ts) is the ONLY snapshot loader for decisions: one `/usage` probe refreshes BOTH usage.json and model-usage.json when the tee is absent, org-drifted, or older than `usagePollTtlMs`. The original bug: cold-start discarded perModel and stamped model:null, so `needsPerModel` gated off and stella ignored Fable 95/95 for 9+ hours of checks.
- Unknown model (`model: null`) gates EVERY `switchModels` family; a known-unconstrained model gates none ("fable=switch, sonnet=ok" survives). Never "restore" the old matchedFamily-only gate.
- usage.json freshness = file MTIME, not the embedded ts: `writeUsage`'s write-on-change suppression bumps mtime (utimesSync) as the tee's liveness heartbeat. Judging by ts made a live Sonnet session look headless for up to 8.5 of every 10 minutes.
- Per-model caps of gated families count in `isExhausted`/`usableAt` (PickCtx.switchFamilies). Without this an all-Fable-burnt pool round-robin swaps; with it, live-verified: the cascade across the four accounts correctly skipped the fable-burnt one.
- 45s POST_SWAP_COOLDOWN in `evaluateAndMaybeSwap`: a model-blind evaluation right after a model-aware swap otherwise undoes it (A/B respawn loop).
- Depleted-path pre-parking (swapping onto a still-blocked soonest-recovering account) happens only when `anticipatory` (the supervised Stop hook with a session id, the only caller whose respawn marker pauses until reset). Timer/SessionStart stay put; the normal pick path adopts the target once its reset passes.
- The greedy path (engaged, under every bar) never reaches the depleted logic: `currentWins` keeps the seat, else swap onto the strictly better account, else `no-usable-target` and stay put. Only the hard path (a screening bar crossed) may depleted-wait; anything else trades a working session for a wait.
- The greedy path does NOT use `chooseAndSwap`: its dead-token fallback lands on the next usable candidate unconditionally, which is right when over a bar but wrong when the current account is healthy - a dead grant on the winner would bounce the session onto a pace-worse account and back (adversarial review catch, 2026-07-16). The greedy loop re-checks `currentWins` after every `InvalidGrantError` (performSwap persists needs-reauth before throwing, so each reload shrinks the candidate set and the loop terminates). E2E test 9 pins this.
- Unknown-reset blocked windows self-bound at sampledAt + window duration (5h/7d); no permanent bench, no waitUntil=now churn.

## Supervisor recursion guards (v0.6.2)

- Incident (2026-07-13 user report, on 0.6.1): unbounded wrapper recursion. A v0.4.0-era install had pinned a shim as config.json claudeBin; the supervisor spawned it, the shim resolved `claude` from PATH back onto the wrapper, forever (~1800 bun processes, ~10/sec). Reproduced on HEAD via a bounded shim harness. Most plausible poisoning: tokenmaxxing's own stale wrapper; `ensurePathInRc` marker-idempotency keeps an OLD binDir on PATH after a `TOKENMAXXING_HOME` relocation, and init's PATH scan (exact-string binDir skip) pinned that stale wrapper. `TOKENMAXXING_PROBE` never prevented spawning, only session management. The 60s probe killer was defeated because descendants inherit the stdout pipe and `new Response(p.stdout).text()` waits for ALL holders.
- Root lesson: every guard was existence-based; nothing validated that "the real claude" actually was claude, and no spawn path was depth-bounded.
- The 0.6.2 layered guards: (a) `TOKENMAXXING_WRAP_DEPTH` env sentinel, supervisor aborts at 5, both spawn arms tag depth+1; (b) `resolveRealClaude` rejects candidates whose realpath parent is realpath(binDir); (c) `probeUsage` presets depth to the cap (a probe must never re-enter the wrapper); (d) `verifyRealClaude` (`--version`, 15s timeout, must print /claude/i) gates init pinning (`resolveVerifiedClaude` walks ALL PATH candidates) and doctor; (e) probe pipe reads race child-exit + 2s grace.
- User aliases like `cc`/`cco` with plain-`claude` bodies are supervised via PATH and fine; doctor warns on `alias claude=` / `claude()` shadowing and absolute-path bypass aliases.
- When adding ANY new spawn of "the real claude": spawn `resolveRealClaude()` output, and preset the depth cap if that path must never re-enter the wrapper.

## Statusline

## Machine and environment gotchas

- On the user's Mac, `rm` is aliased to `rm -i` (zsh profile). In a non-TTY shell the confirmation prompt gets EOF, `rm` deletes nothing, and it still exits 0, so `rm file && echo ok` lies (this broke the claude-hud removal on 2026-07-11). Always pass `-f` (or use `command rm`) when deleting files in Bash tool calls on this machine, and verify the path is gone afterward.
- macOS has no `/bin/true` (only `/usr/bin/true`); use `/usr/bin/true` in tests (it exists on macOS and usr-merged Linux). Incident 2026-07-12: a swap e2e seeded `claudeBin: "/bin/true"`, `resolveRealClaude` fell through to its PATH scan (whose recursion guard only skipped the relocated test binDir), resolved the user's real installed wrapper, and spawned a forever-hung `/usage` probe that wedged the e2e for 15+ minutes. Fixes: `resolveRealClaude` now throws on a configured-but-missing claudeBin instead of PATH-scanning, and `probeUsageOnce` kills the child after 60s (PROBE_KILL_MS). Caveat learned 2026-07-13: the 60s kill alone was NOT sufficient (descendants inherit the stdout pipe and the read blocked past the kill); see the v0.6.2 recursion guards above.
- Piping macOS tar into a Linux container creates AppleDouble `._*.test.ts` files that `bun test` executes; use `COPYFILE_DISABLE=1`.
- macOS 26 recurring TCC dialogs "bun would like to access data from other apps" (first reported 2026-07-12) come from the tokenmaxxing periodic check: the `com.tokenmaxxing.check` launchd agent fires every 180s and runs the check via the dev shim, whose root executable is plain `bun`, so macOS attributes every TCC request from the job (including children) to "bun". The check spawns `claude -p /usage --output-format json` nearly every run (`usagePollTtlMs` 90s < 180s interval), and the claude CLI is known upstream to touch other apps' protected data (anthropics/claude-code issues #63130, #36832, #36675: unstable per-version binary identity, no app bundle). The system TCC db has bun listed in Full Disk Access but toggled OFF, so App Data prompts keep re-firing (the user-level `kTCCServiceSystemPolicyAppData` row, auth_value 5, does not stop them). Fix: toggle `bun` ON in System Settings > Privacy & Security > Full Disk Access. Scoped alternative: install a compiled tokenmaxxing binary signed with a stable (non-ad-hoc) identity + Info.plist and grant that FDA instead. Clicking Allow on the dialog does not durably persist for path-identified CLI clients.

## Mistakes I have made

When the user is unhappy with a mistake, record it here in this same bullet style so it is not repeated.

- Re-ran a live interactive PTY test after the user had already declined it. Respect a rejection the first time.
- `installSupervisor` copied the running binary onto itself (`copyFileSync(self, target)` with `self === target`), truncating and destroying the installed binary. Guard self-referential file operations.
- `init` re-imported the "current account" from `~/.claude.json` `oauthAccount` and parked the live credential under it, assuming `oauthAccount` matches the live keychain credential. After swaps they diverge, so this clobbered a parked backup. Do not assume identity files agree with credential stores; make destructive commands idempotent and fail-fast on drift.
- Shipped the keychain write over `security -i` without verifying its line-buffer limit, then a real 4.3KB blob truncated silently. Verify external tool limits with a real-sized payload before relying on them.
- Installed the compiled binary by `copyFileSync` alone. macOS AMFI SIGKILLs (exit 137) a copied ad-hoc-signed Mach-O because the copy gets a `com.apple.provenance` xattr and the signature stops validating. After copying a Mach-O on macOS, `xattr -c` + `codesign --force --sign -` it. A byte-identical copy is not a runnable copy on macOS.
- Declared "no contamination" after seeing distinct parked-credential hashes and ~1-minute-different `/usage` reset clocks. Distinct blobs do not prove distinct accounts: two rotations of the SAME account's token differ byte-for-byte. Verify a credential's true owner via the roles endpoint (`fetchTokenOrg`), never by comparing blobs.
- `performSwap` harvested the live credential into whatever account `accounts.json` labeled active. Labels drift from the live blob (kill mid-swap before `saveAccounts`, manual `/login`), and one drifted harvest overwrote another account's backup, destroying its only credential. Park a credential under its token's API-reported identity, and commit the active label inside the same critical section as the credential writes.

- Told the user "a running macOS claude does NOT hot-swap on a credential swap" from a recorded verification that was wrong (the per-request ensure-fresh poll existed in every version checked). The user's live observation contradicted it and the user was right.
