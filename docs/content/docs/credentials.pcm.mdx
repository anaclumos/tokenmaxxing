---
title: Credential storage and safety model
description: "Wia credentials dey live per platform and the rules every swap dey enforce"
---

All state dey live for `~/.config/tokenmaxxing/`. Credential I/O dey pass through one single platform-selected store facade; call sites no dey branch on platform.

**macOS**: credentials dey live for the login keychain as generic-password items, e match wia Claude Code imself dey keep dem. The live item na the one claude dey read; each pooled account im backup dey parked as im own `tokenmaxxing-cred-<uuid8>` keychain item. Nothing dey plaintext for disk. Reads dey use `security find-generic-password -w` (the secret dey only ever appear on stdout); writes dey pipe one `add-generic-password` line go inside `security -i` over stdin so the secret no dey ever appear for any process im argv. The interactive mode get roughly 4 KB line buffer, so oversized blobs dey fall back to argv write - one reason parked items dey store only the minimal OAuth object.

**Linux**: Claude Code dey store credentials as one 0600 plaintext file, and tokenmaxxing dey follow the same model: the live file na claude im own `.credentials.json`, and parked backups na atomic 0600 files under `~/.config/tokenmaxxing/creds/` inside one 0700 directory. Atomic for here mean write-to-temp, fsync, then rename: one concurrent reader dey always see one whole old or one whole new file, never a partial one.

The safety rules wey the swap dey enforce:

- **Harvest by true owner.** Before a swap, dem dey resolve the live credential im actual owner by asking the API which account the token belong to (`fetchTokenIdentity` against the OAuth profile endpoint, matched for account UUID) - never by organization, because every seat for one Team plan dey share one organization, and never by trusting the stored active label, wey fit drift. One drifted label one time cause say one account im harvest overwrite another account im only backup. If the live credential belong to one account outside the pool, the swap go refuse outright rather than clobber am.
- **One critical section.** The harvest, the install of the new credential, the backup of im rotated token, the `~/.claude.json` account swap, and the active-label commit all dey happen inside the same locked section.
- **Interlock with claude im own refresh.** One near-expiry session fit rotate im own token any moment, so credential writes dey also take Claude Code im refresh lock (best-effort, with stale-lock reclaim and bounded timeout).
- **Dead grants dey degrade cleanly.** One refresh wey come back `invalid_grant` dey flag dat account as needs-reauth and dey persist the flag before the error propagate, so retry loops dey shrink the candidate set and terminate. One credential wey Claude Code imself clear after one failed refresh (empty access and refresh tokens) dey recognized as dead without spending any request. Before dem spend one parked refresh token, dem dey resolve im owner through the profile endpoint; one parked credential wey resolve to one different account dey flagged instead of refreshed, because refreshing one copy of another account im live grant dey revoke dat account im sessions. Any other token endpoint rejection (one HTTP 4xx wey no be `invalid_grant`) dey skip dat candidate for the rest of the evaluation and e no dey flag anything. `tokenmaxxing auth` dey fix one flagged account for the same place, and e dey refuse a login wey land for one different account from the one wey dem dey repair.
- **No token logging.** Tokens no dey ever appear for logs, errors, or output. Error bodies from token and usage endpoints no dey ever surface raw; only one allowlisted set of fields dey survive, because one token endpoint im failure body fit echo request material.
- **Probe hygiene.** Any spawned `claude` probe dey scrub the eight environment variables wey claude dey honor before im keychain lookup (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, and so on), so a probe no fit ever get attributed to the wrong account.
