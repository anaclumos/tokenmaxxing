tokenmaxxing - это CLI для автоматического переключения аккаунтов Claude Code. Он объединяет несколько принадлежащих вам подписочных аккаунтов (Pro/Max) и на лету переключает активные учётные данные на более свежий аккаунт, когда используемый приближается к лимиту использования. Вы запускаете `claude` ровно так же, как и всегда; переключение происходит на безопасной границе хода, и ваша текущая сессия продолжает тот же диалог на новом аккаунте без перезапуска. Это работает сразу для множества параллельных сессий.

Единственное заметное поведение - это худший случай: когда весь пул достиг лимита, сессия приостанавливается с обратным отсчётом и автоматически возобновляется на аккаунте, который сбросится следующим (Ctrl-C возобновляет немедленно).

<Callout>
Область применения: Claude Code на macOS и Linux, а также Codex CLI от OpenAI в качестве второго, параллельного пула. Он объединяет подписочные аккаунты, а не API-ключи. Это инструмент для личного использования, предназначенный для объединения принадлежащих вам аккаунтов в сессиях и агентах, которые вы запускаете сами - см. [Личное использование и условия обслуживания](#personal-use-and-terms-of-service).
</Callout>

## Проблема

Подписка Claude одновременно учитывает три лимита (все подтверждены через `/usage`):

- **Текущая сессия**: скользящее 5-часовое окно.
- **Текущая неделя (все модели)**: 7-дневный агрегат.
- **Текущая неделя, по каждой модели**: отдельные недельные лимиты для отдельных семейств моделей. Сейчас они существуют только для Sonnet и Fable, и только лимит Fable достаточно жёсткий, чтобы иметь значение - он срабатывает задолго до агрегата. Машина может находиться на 50% недельного лимита по всем моделям, уже будучи на 80% недельного лимита по Fable.

Недельная квота работает по принципу «используй или потеряешь»: всё, что аккаунт не израсходовал к моменту своего фиксированного недельного сброса, сгорает. Если у вас несколько аккаунтов, рациональная стратегия - продолжать расходовать квоту на том аккаунте, который сильнее всех отстаёт от своего недельного темпа, и переключаться до того, как какой-либо отдельный лимит упрётся в стену посреди сессии.

Делать это вручную означает выйти из аккаунта, войти в другой и потерять свой диалог. tokenmaxxing автоматизирует это: работающий `claude` перепроверяет своё хранилище учётных данных между запросами, поэтому подменённые под ним учётные данные принимаются на месте (примерно за 30 секунд на macOS, на следующем запросе в Linux). Обычное переключение никогда не перезапускает вашу сессию. Единственный случай, который по-прежнему требует управления процессом, - это полностью исчерпанный пул (сессия не может приостановить себя сама), и именно для этого существует тонкий супервизор.

Всё остальное в `claude` остаётся без изменений: все флаги, серверы MCP, хуки и навыки (skills) передаются как есть.

## Быстрый старт

Требуется [Bun](https://bun.sh) и Claude Code, на macOS или Linux.

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` делает пять вещей:

1. Импортирует аккаунт, под которым вы уже вошли, как аккаунт #1 (отдельной команды `adopt` нет).
2. Устанавливает shim-супервизор `claude`.
3. Добавляет три записи в `settings.json` для Claude Code: statusLine, хук Stop и хук SessionStart (плюс запись subagentStatusLine).
4. Добавляет каталог bin супервизора в PATH в rc-файле вашей оболочки (идемпотентно, помечается комментарием `# tokenmaxxing PATH`). Он должен стоять в PATH раньше настоящего `claude`, чтобы перехватывать его.
5. Устанавливает таймер периодической проверки (агент launchd на macOS, пользовательский таймер systemd в Linux), который запускает `tokenmaxxing check` каждые 180 секунд.

Перезапустите оболочку, затем добавьте больше аккаунтов и приступайте:

```sh
tokenmaxxing add        # входит ещё в один аккаунт в изоляции и добавляет его в пул
claude                  # используйте claude как обычно
```

`tokenmaxxing` также доступен под псевдонимом `xx`. Просто `tokenmaxxing` (или `xx`) запускает `status`; `switch` остаётся явной командой.

## Команды

| Команда | Что делает |
|---|---|
| `tokenmaxxing init` | Импортирует текущий аккаунт, устанавливает супервизор, хуки и statusline |
| `tokenmaxxing init --codex` | То же для Codex: импортирует вход, устанавливает супервизор codex и хук Stop |
| `tokenmaxxing add` | Регистрирует дополнительный аккаунт (изолированный вход, собирается в пул) |
| `tokenmaxxing add --codex` | Регистрирует дополнительный аккаунт Codex (изолированный вход) |
| `tokenmaxxing auth [sel \| --all]` | Повторно аутентифицирует аккаунт пула на месте. Без аргументов выводит пул и спрашивает, какой; селектор указывает на один аккаунт и сообщает, под каким email входить; `--all` проходит по каждому аккаунту, требующему повторной аутентификации, по очереди |
| `tokenmaxxing switch [sel]` | Переключается на лучший аккаунт (жадно, идемпотентно) или принудительно на конкретный |
| `tokenmaxxing switch --codex [sel]` | Переключает пул Codex (вступает в силу при следующем запуске codex) |
| `tokenmaxxing ls` | Выводит список аккаунтов в пуле |
| `tokenmaxxing status` | Аккаунты с индикаторами использования за 5ч / неделю / по моделям, активные и исчерпанные до сброса |
| `tokenmaxxing status --force` | Дополнительно пингует каждый аккаунт (по одному крошечному запросу к haiku), чтобы все 5-часовые таймеры сессий стартовали прямо сейчас, затем берёт свежую выборку |
| `tokenmaxxing watch [seconds]` | Статус в реальном времени, перерисовывается каждые N секунд (по умолчанию 120, минимум 30; никогда не пингует) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | Действующая конфигурация с источниками; редактирование ключей через точку; `tidy` удаляет неизвестные ключи |
| `tokenmaxxing check` | Один раз вычисляет решение о переключении (именно это запускает периодический таймер) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Демон-мост для Slack (Socket Mode, без публичного URL) |
| `tokenmaxxing doctor` | Проверяет, что супервизор и записи в настройках сохранились |
| `tokenmaxxing rename [--codex] <sel> <label>` | Переименовывает аккаунт в пуле |
| `tokenmaxxing rm <sel>` | Удаляет аккаунт из пула |
| `tokenmaxxing uninstall` | Удаляет супервизор и записи в настройках (аккаунты и учётные данные сохраняются) |

## Архитектура

tokenmaxxing - это единая точка входа с множественным вызовом (`src/main.ts`), которая ведёт себя как супервизор `claude`, когда вызывается под этим именем, обслуживает shim-ы хуков и statusline через внутренние подкоманды, а в остальных случаях диспетчеризует CLI. Он работает напрямую под Bun; npm-пакет поставляется как исходный код на TypeScript, а не как сборка.

Движущиеся части:

### Shim-супервизор

`init` записывает shell-shim из 2 строк с именем `claude` в `~/.config/tokenmaxxing/bin/` и ставит этот каталог первым в PATH. Когда вы вводите `claude`, shim запускает супервизор, который порождает настоящий бинарник claude с унаследованным stdio и сохранённым снимком терминала `stty -g`. Это только менеджер процессов и терминала: он никогда не проксирует трафик API и никогда не трогает токены в процессе передачи.

Вызовы в режиме печати (`claude -p`, `--version`, `--help`), неинтерактивные подкоманды (`claude mcp`, `claude config` и так далее) и собственные проверки tokenmaxxing проходят напрямую без управления сессией. Для интерактивной сессии супервизор фиксирует id сессии (генерируя новый или переиспользуя тот, что вы передали через `--session-id` / `-r` / `-c`), сохраняет ваши флаги запуска, чтобы более поздний перезапуск мог их воспроизвести, а затем следит за файлом-маркером перезапуска, привязанным к этой сессии.

### Ответвление statusline

Claude Code передаёт данные о лимитах (`rate_limits.five_hour` и `rate_limits.seven_day`) в stdin statusline на каждом ходу. tokenmaxxing владеет слотом statusline, поэтому его отрисовщик заодно служит бесплатным push-каналом данных об использовании: на каждом такте он ответвляет агрегированные окна плюс активную модель в `usage.json`. Лимиты по каждой модели не приходят в stdin statusline; они поступают только из `claude -p '/usage'` (бесплатно, ноль токенов), который опрашивается с TTL и кэшируется в `model-usage.json`, когда активная модель ограничена по ёмкости.

Ответвление работает по принципу записи при изменении: когда показатели не меняются, оно лишь обновляет mtime файла, что служит сигналом жизнеспособности канала. Свежесть всегда определяется по mtime, а не по встроенной временной метке.

### Хук Stop и переключение

На каждой границе хода хук Stop выполняет решение о переключении (см. [Как принимается решение о переключении](#how-switching-decides)). Когда переключение оправдано, оно происходит под эксклюзивной блокировкой `flock(2)` (взятой через `bun:ffi`, поскольку в macOS нет бинарника `flock(1)`), а запись учётных данных дополнительно взаимоблокируется с собственной блокировкой обновления Claude Code. Внутри критической секции одно переключение:

1. Собирает текущие активные учётные данные в припаркованную резервную копию их истинного владельца.
2. Устанавливает свежеобновлённые учётные данные целевого аккаунта в качестве активных, сливая их с существующим активным blob-ом, чтобы сопутствующее состояние (например, OAuth-токены для каждого сервера MCP) сохранилось.
3. Сохраняет ротированный токен цели в её собственную резервную копию.
4. Атомарно перезаписывает поле `oauthAccount` в `~/.claude.json`.
5. Фиксирует новую активную метку и очищает устаревшие снимки использования - всё это до снятия блокировки, так что сбой никогда не сможет оставить установленные учётные данные и активную метку указывающими на разные аккаунты.

Поскольку все сессии профиля по умолчанию используют одни активные учётные данные, единственное переключение мигрирует все сессии сразу, а flock плюс повторная проверка под блокировкой не дают конкурирующим хукам сжечь два аккаунта.

### Принятие на месте

Работающая сессия claude опрашивает своё хранилище учётных данных между запросами: на macOS она перечитывает keychain через короткий кэш и сравнивает access-токены; в Linux она проверяет mtime файла учётных данных и сбрасывает свои кэши токенов при изменении. В итоге подменённые учётные данные принимаются каждой работающей сессией примерно за 30 секунд на macOS и уже на следующем запросе в Linux, без всякого перезапуска. Именно поэтому обычное переключение не записывает маркер и не вызывает повторного порождения процесса - сессия просто продолжается на новом аккаунте. Внутрисессионный `/usage` использует те же кэши токенов, поэтому отображаемый им аккаунт меняется вместе с принятием.

### Ожидание при исчерпанном пуле и автовозобновление

Только когда каждый аккаунт в пуле превысил свои пороги, хук Stop записывает маркер перезапуска (схема маркера требует временную метку `waitUntil`; обычное переключение никогда не может её создать). Супервизор видит маркер, посылает SIGTERM своему дочернему процессу на уже зафиксированной границе хода (хук Stop выполняется после того, как транскрипт записан на диск и claude бездействует, поэтому ничего не теряется), восстанавливает терминал, показывает обратный отсчёт до ближайшего сброса, а затем перезапускает `claude --resume <session-id>` на восстановленном аккаунте. Ctrl-C во время обратного отсчёта возобновляет немедленно. Автоожидание ограничено `policy.maxWaitMs` (по умолчанию 1 час); сверх этого решение сообщает о пуле как об исчерпанном вместо ожидания.

### Таймер периодической проверки

Хуки срабатывают только на границах ходов, а один длинный агентский ход может сжечь окно от здорового до исчерпанного без единой границы. Поэтому `init` также устанавливает периодический таймер - агент launchd на macOS, пользовательский таймер systemd в Linux - который запускает `tokenmaxxing check` каждые 180 секунд независимо от активности ходов.

### Хук SessionStart

Запускает ту же оценку, когда сессия начинается или возобновляется, чтобы новая сессия стартовала на нужном аккаунте. Пауза после переключения делает его корректным no-op сразу после повторного порождения процесса.

## Как принимается решение о переключении [#how-switching-decides]

Решение состоит из двух слоёв: вентиль вовлечения, а затем жадный или жёсткий путь.

### Вовлечение

Ниже `policy.greedySessionFloor` (по умолчанию 50, в процентах от 5-часового окна сессии) решение вообще не выполняется - новая сессия остаётся на своём аккаунте. Как только активное окно сессии израсходовано на 50% или пересечён любой жёсткий порог, решение вовлекается.

### Пороги отсева

Пороги - это барьеры отсева, а не триггер для паники:

- `thresholds.session`: 95. Пятичасовой сброс дёшево переждать, поэтому окно сессии переключается раньше.
- `thresholds.weekly`: 98. Этот единственный порог покрывает и 7-дневный агрегат, и каждый недельный лимит по модели. Недельная квота работает по принципу «используй или потеряешь», поэтому она вырабатывается почти до предела.

Оба намеренно ниже 100: этот запас - бюджет на то, чтобы дойти до чистой границы хода (плюс до одного хода задержки принятия на macOS), прежде чем аккаунт действительно достигнет своего лимита. Те же пороги отсеивают кандидатов на переключение: аккаунт, превысивший любой из своих порогов, не является допустимой целью. Триггер и отсев всегда используют одни и те же действующие пороги (пороги минус `policy.projectionMargin`), потому что отсев мягче триггера привёл бы к переключениям на аккаунты, которые триггер тут же снова отметит, гоняя пул туда-сюда.

### Цель: давление темпа

Среди пригодных аккаунтов целью становится тот, который сильнее всех отстаёт от своего недельного темпа: наибольшее **давление темпа**, определяемое как оставшийся недельный процент, делённый на время до недельного сброса этого аккаунта. Выигрывает аккаунт, у которого вот-вот сгорит больше всего квоты. При равенстве побеждает ближайший недельный срок истечения, затем наименьшее использование за 7 дней.

Всё работает на основе кэшированных окон, хранящихся как абсолютные UTC-эпохи, поэтому устаревший снимок всё равно разрешается корректно: прошедший недельный сброс экстраполируется вперёд точными 7-дневными шагами, а любое окно за пределами своего кэшированного сброса считается только что опустошённым (никогда не повод для переключения и никогда не повод держать аккаунт на скамейке).

### Жадный путь против жёсткого

- **Жадный путь** (вовлечён, но под всеми порогами): ранжирует каждый аккаунт, включая текущий. Если текущий аккаунт уже выигрывает или на равных, не делать ничего. Иначе переключиться на строго лучший аккаунт. Он никогда не ждёт и никогда не паркует заранее - пригодный текущий аккаунт не обменивается на ожидание. Поскольку текущий аккаунт тоже ранжируется, и автоматический путь, и просто `tokenmaxxing switch` идемпотентны: периодическая оценка сходится к нужному аккаунту и затем остаётся на нём.
- **Жёсткий путь** (порог пересечён): переключиться на лучшего пригодного кандидата. Если refresh-токен кандидата оказывается мёртвым, он помечается как требующий повторной аутентификации и пробуется следующий кандидат. Если ничего не пригодно, выполняется логика ожидания при исчерпании; только вызывающая сторона, которая действительно может приостановить сессию (контролируемый хук Stop), имеет право заранее парковаться на всё ещё заблокированный, но восстанавливающийся раньше всех аккаунт.

### Лимиты по каждой модели

`policy.switchModels` (по умолчанию `["fable"]`) задаёт семейства моделей, чей недельный лимит по модели может вызвать переключение. Сопоставление идёт по токену семейства, а не по точной отображаемой строке: отображаемые имена моделей меняются («Fable» стало «Fable 5»), и однажды проверка по точной строке молча полностью отключила переключение по моделям. Два связанных правила безопасности:

- Неизвестная активная модель блокирует каждое настроенное семейство. Сразу после того, как переключение очистило снимки, безголовая машина может работать вслепую по модели; трактовка неизвестного как неограниченного однажды позволила аккаунту незамеченным часами находиться на своём лимите Fable.
- Отсев кандидатов также учитывает заблокированные лимиты по моделям, поэтому пул, где каждый аккаунт сжёг свой лимит Fable, не переключается по кругу.

### Пауза

45-секундная пауза после переключения блокирует автоматический путь. Ответвление statusline подавляется на те же 45 секунд после переключения (принятие занимает до 30 секунд на macOS), поэтому более ранняя оценка выполнялась бы на данных, которые само переключение сделало недействительными - именно этот сценарий однажды породил цикл повторного порождения A-в-B-и-обратно. Ручная команда `tokenmaxxing switch` не подвержена паузе.

## Конфигурация

Конфигурация - это JSON в `~/.config/tokenmaxxing/config.json`. Каждое поле необязательно; значения по умолчанию применяются к каждому полю.

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: барьеры отсева, описанные выше.
- `policy.projectionMargin`: вычитается из обоих порогов для формирования действующих порогов.
- `policy.greedySessionFloor`: процент использования сессии, при котором вовлекается жадное схождение.
- `policy.switchModels`: семейства моделей, чей недельный лимит по модели блокирует переключение (записи приводятся к нижнему регистру при загрузке).
- `policy.usagePollTtlMs`: как долго остаётся свежим опрос `/usage` по моделям.
- `policy.maxWaitMs`: граница автоожидания при исчерпанном пуле.

`tokenmaxxing config` показывает действующую конфигурацию с источниками; `config set`/`unset` редактируют ключи через точку; `config tidy` удаляет неизвестные ключи.

## Структура каталога состояния

Всё находится в `~/.config/tokenmaxxing/` (переопределяется через `TOKENMAXXING_HOME`; у каждого внешне наблюдаемого пути есть переопределение через переменную окружения, так что весь инструмент может герметично работать в тестах).

| Путь | Что содержит |
|---|---|
| `config.json` | Ваша конфигурация (разреженная; значения по умолчанию применяются к каждому полю) |
| `accounts.json` | Несекретный индекс объединённых аккаунтов Claude: метки, id, кэшированные окна использования. Никогда токены |
| `usage.json` | Снимок агрегированных окон от ответвления statusline; его mtime - сигнал жизнеспособности канала |
| `model-usage.json` | Недельные лимиты по моделям из `/usage`, кэшированные с TTL |
| `lastswap.json` | Метка времени в эпохах последнего переключения; управляет 45-секундной паузой |
| `lock` | Файл `flock`, сериализующий переключения |
| `tokenmaxxing.log` | Журнал событий только для добавления |
| `bin/` | Shim-ы PATH: `claude`, `codex` и точки входа `tokenmaxxing` / `xx` |
| `respawn/<session-id>` | Маркеры перезапуска для ожидания при исчерпании, за которыми следит супервизор |
| `creds/` | Только Linux: файлы припаркованных учётных данных, 0600 в каталоге 0700 (на macOS учётные данные паркуются как элементы keychain для каждого аккаунта) |
| `onboard/`, `sample/` | Одноразовые изолированные конфигурационные домашние каталоги для входов `add`/`auth` и проверок `/usage` припаркованных аккаунтов; домашние каталоги онбординга, содержащие учётные данные в открытом виде, удаляются после сбора |
| `slack.json` | Токены и привязки каналов `xx serve` (0600) |
| `slack-threads/` | Записи сессий для каждого треда для `xx serve` |
| `codex-*` | Параллельный пул Codex: `codex-accounts.json`, `codex-lastswap.json`, `codex-lock`, `codex-creds/`, `codex-onboard/`, `codex-respawn/` и `codex-live/` (по одному PID-проверенному файлу присутствия на каждую работающую контролируемую сессию codex, так что живой аккаунт никогда не становится целью переключения) |

Вне своего собственного каталога tokenmaxxing затрагивает ровно: `~/.claude.json` (замена `oauthAccount`), `settings.json` Claude Code (записи хука и statusline), активное хранилище учётных данных (элемент keychain `Claude Code-credentials` на macOS, `.credentials.json` в Linux), `~/.claude.lock` (блокировка обновления claude, берётся во время переключений), `auth.json` и `hooks.json` codex, а также юнит периодической проверки в launchd или systemd.

## Хранение учётных данных и модель безопасности

Всё состояние хранится в `~/.config/tokenmaxxing/`. Ввод-вывод учётных данных идёт через единый фасад хранилища, выбираемый по платформе; места вызова никогда не ветвятся по платформе.

**macOS**: учётные данные хранятся в login keychain как элементы generic-password, там же, где их держит сам Claude Code. Активный элемент - тот, что читает claude; резервная копия каждого аккаунта в пуле паркуется как отдельный элемент keychain `tokenmaxxing-cred-<uuid8>`. Ничего не хранится на диске в открытом виде. Чтение использует `security find-generic-password -w` (секрет появляется только в stdout); запись направляет строку `add-generic-password` в `security -i` через stdin, поэтому секрет никогда не появляется в argv какого-либо процесса. У интерактивного режима буфер строки примерно 4 КБ, поэтому слишком большие blob-ы откатываются к записи через argv - одна из причин, по которой припаркованные элементы хранят только минимальный OAuth-объект.

**Linux**: Claude Code хранит учётные данные как plaintext-файл с правами 0600, и tokenmaxxing следует той же модели: активный файл - это собственный `.credentials.json` claude, а припаркованные резервные копии - атомарные файлы 0600 в `~/.config/tokenmaxxing/creds/` внутри каталога 0700. Атомарно здесь означает запись во временный файл, fsync, затем переименование: конкурирующий читатель всегда видит либо целый старый, либо целый новый файл, никогда не частичный.

Правила безопасности, которые обеспечивает переключение:

- **Сбор по истинному владельцу.** Перед переключением реальный владелец активных учётных данных определяется через запрос к API, какой организации принадлежит токен (`fetchTokenOrg` к OAuth-эндпоинту roles) - никогда через доверие к сохранённой активной метке, которая может сместиться. Сместившаяся метка однажды привела к тому, что сбор одного аккаунта перезаписал единственную резервную копию другого. Если активные учётные данные принадлежат аккаунту вне пула, переключение прямо отказывается вместо того, чтобы затереть их.
- **Одна критическая секция.** Сбор, установка новых учётных данных, резервное копирование их ротированного токена, замена аккаунта в `~/.claude.json` и фиксация активной метки - всё происходит внутри одной заблокированной секции.
- **Взаимоблокировка с собственным обновлением claude.** Сессия у грани истечения может ротировать свой токен в любой момент, поэтому запись учётных данных также берёт блокировку обновления Claude Code (по мере возможности, с перехватом устаревшей блокировки и ограниченным тайм-аутом).
- **Мёртвые гранты деградируют аккуратно.** Обновление, вернувшее `invalid_grant`, помечает этот аккаунт как требующий повторной аутентификации и сохраняет флаг до того, как ошибка распространится, поэтому циклы повтора сужают набор кандидатов и завершаются. `tokenmaxxing auth` чинит помеченный аккаунт на месте и отказывает во входе, который приводит к аккаунту, отличному от восстанавливаемого.
- **Никакого логирования токенов.** Токены никогда не появляются в логах, ошибках или выводе. Тела ошибок от эндпоинтов токенов и использования никогда не выводятся в сыром виде; сохраняется только разрешённый список полей, потому что тело ошибки эндпоинта токена может отразить материал запроса.
- **Гигиена проверок.** Любая порождённая проверка `claude` вычищает восемь переменных окружения, которые claude учитывает до обращения к keychain (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR` и так далее), поэтому проверка никогда не может быть отнесена к неверному аккаунту.

## Замечания по платформам: macOS против Linux

| | macOS | Linux |
|---|---|---|
| Активные учётные данные | Элемент generic-password в login keychain | Файл `.credentials.json` с правами 0600 |
| Припаркованные учётные данные | Элементы keychain для каждого аккаунта | Файлы 0600 в каталоге 0700 |
| Принятие после переключения | В течение ~30 секунд (кэш чтения keychain) | Следующий запрос (опрос mtime файла) |
| Периодическая проверка | Агент launchd, каждые 180с | Пользовательский таймер systemd, каждые 180с |
| Хранилище изолированного входа | Служба keychain с хешированным пространством имён для каждого каталога конфигурации | Файл внутри изолированного каталога конфигурации |

Две специфичные для Linux детали, которые стоит знать: claude определяет свой каталог учётных данных сначала из `CLAUDE_SECURESTORAGE_CONFIG_DIR` (затем `CLAUDE_CONFIG_DIR`, затем `~/.claude`), и tokenmaxxing в точности повторяет это разрешение, чтобы они никогда не рассинхронизировались. И две сборки одной и той же версии claude под разные ОС форматируют время сброса в `/usage` по-разному (одна использует связку " at ", другая - запятую); парсер tokenmaxxing принимает ровно эти две формы и логирует, а не угадывает, при любой третьей.

На macOS есть одно честное ограничение: `init` и `add` намеренно обращаются к keychain интерактивно, чтобы первый доступ `security` не был холодным внутри безголового хука.

## Statusline

tokenmaxxing отрисовывает statusline Claude Code нативно (одновременно ответвляя канал данных об использовании). Принцип дизайна: квота передаётся цветом, а не числами. Одна строка, например:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- Каждый токен окна - это его время до сброса, окрашенное по непрерывному градиенту от зелёного через жёлтый к красному по проценту использования (truecolor, когда терминал это поддерживает, иначе с шагом по 256-цветному кубу). Градиент закрепляется на чистом зелёном для 0, жёлтом на 75 и красном на 95 и выше, поэтому старые полосы серьёзности сохраняются как опорные точки градиента.
- Имя модели окрашивается по заполнению контекстного окна на том же градиенте.
- Зелёный `◆` возглавляет окна активного аккаунта; каждый припаркованный аккаунт получает свой голубой `◇` (красный `✗`, если требуется повторная аутентификация). Аккаунты сортируются по ближайшему предстоящему сбросу.
- Показатель по модели идёт первым в каждом блоке как одиночная окрашенная буква: Fable отображается как `𝒇`; другие семейства используют свою первую букву в верхнем регистре, всегда с сопоставлением по семейству.
- Нетронутый припаркованный аккаунт отображается зелёным `full`. Измеренное использование с неизвестным сбросом отображается окрашенным `?`, а неизмеренный лимит по модели на заблокированной модели отображается неокрашенным `𝒇?` - неизмеренное никогда не должно выглядеть безопасным.
- Обратный отсчёт до сброса показывает только наибольшую единицу, никогда «now» или «0m»; окно без предстоящего сброса отображается зелёным `0` (снова пустое).
- Имя связанного git-worktree возглавляет строку; основной checkout там ничего не отображает. Определение читает из файловой системы файл `.git` и никогда не порождает подпроцесс git.
- При установленном `NO_COLOR` строка откатывается к склеенному числовому формату (`2h5` означает сброс через 2 часа, 5% использовано; `ctx 42` для заполнения контекста) - без цвета исчерпанное окно не должно выглядеть свежим.

Задачи субагентов получают свои строки на панели через surface subagentStatusLine claude: по одной строке на активную задачу, имя семейства окрашивается по заполнению контекста этой задачи.

## Поддержка Codex

То же объединение работает для Codex CLI от OpenAI, с вашими собственными аккаунтами подписки ChatGPT:

```sh
tokenmaxxing init --codex   # импортирует ваш текущий вход codex + устанавливает супервизор codex и хук Stop
tokenmaxxing add --codex    # входит в другой аккаунт в изоляции - ваш основной вход не затрагивается
codex                       # используйте codex как обычно
```

Пул Codex - это полностью параллельное состояние: собственный индекс аккаунтов, собственные файлы припаркованных учётных данных (файлы 0600 на обеих платформах, поскольку собственное хранилище codex - это plaintext-файл), собственная блокировка, собственная метка времени последнего переключения. С пулом Claude не разделяется ничего, кроме кода политики принятия решений.

### Почему горячая замена невозможна в Codex

Работающий процесс codex держит один менеджер аутентификации в памяти и явно отказывается перезагружать `auth.json`, когда тот теперь называет другой аккаунт. Нет ни наблюдателя за файлами, ни опроса учётных данных на каждый запрос, поэтому учётные данные, подменённые под работающим codex, просто никогда не вступают в силу для инференса. Перезапуск и есть переключение: `codex resume <session-id>` продолжает локальный транскрипт на том аккаунте, который теперь содержит `auth.json`.

tokenmaxxing справляется с этим через shim-супервизор codex: хук Stop выполняет то же жадное решение по давлению темпа на каждой границе хода, и когда он переключается, он записывает маркер, который заставляет супервизор послать SIGTERM сессии на зафиксированной границе и перезапустить `codex resume <session-id>` на свежем аккаунте с сохранённым транскриптом. Поскольку каждое переключение codex - это видимый перезапуск, жадный путь codex несёт запас улучшения 1.2x: претендент должен превзойти давление темпа текущего аккаунта на 20%, а не на волосок. Жёсткий путь (пересечённый порог) игнорирует этот запас. Для codex также нет обратного отсчёта при исчерпании пула - ничто не может приостановить сессию codex - поэтому полностью исчерпанный пул codex остаётся на месте.

Другие механизмы, специфичные для codex:

- Данные об использовании читаются из бесплатного аутентифицированного GET к собственному эндпоинту лимитов codex (тот же вызов, что делает `/status` в CLI): проценты плюс абсолютные времена сброса в эпохах, как агрегированные окна, так и лимиты по моделям. Классификация окон определяется длительностью, а не позицией, потому что у текущих планов может вообще не быть 5-часового окна, и недельное окно находится в основном слоте.
- Refresh-токены codex ротируются, и повторное использование замещённого убивает всё семейство грантов. Каждая ротация сохраняется в тот же миг, как возвращается, активный аккаунт всегда выбирается только через активный blob (никогда через устаревшую припаркованную копию), а файлы присутствия для каждой сессии гарантируют, что аккаунт, работающий в живой родственной сессии, никогда не станет целью переключения и его припаркованный токен никогда не будет обновлён.
- Codex требует файлового хранилища учётных данных: `init --codex` быстро завершается с ошибкой, если закреплено хранилище keyring, а `add --codex` записывает настройку файлового режима в изолированный домашний каталог онбординга, чтобы вход оказался пригодным для сбора.
- Один ручной шаг: codex пропускает хуки, которым не сказано доверять. После `init --codex` откройте codex один раз и доверьте хуку Stop tokenmaxxing через `/hooks`, иначе автопереключение молча останется неактивным. `init --codex` печатает это напоминание.

## Мост в Slack: xx serve

`tokenmaxxing serve` запускает локальный демон Slack через Socket Mode - публичный URL не требуется. Настройка:

```sh
tokenmaxxing serve setup                    # печатает манифест приложения, запрашивает два токена
tokenmaxxing serve link <channel-id> <repo> # привязывает канал к checkout репозитория
tokenmaxxing serve                          # запускает демон
```

Упомяните бота в привязанном канале, и он откроет сессию Claude Code для этого треда в checkout привязанного репозитория. Каждое сообщение в треде запускает один `query()` из Agent SDK с `resume` - никогда постоянный потоковый запрос - поэтому `ensureBestAccount()` заново оценивает пул на каждом отдельном ходу, и демон может перезапускаться, не теряя треды (записи тредов долговечны; демон повторно подписывается на них при запуске).

Заметное поведение:

- **Потоковая передача**: ответы транслируются в Slack нативно, с карточками задач для размышлений и запусков инструментов, с кодом в ограждённых блоках, отрисованным с подсветкой, с завершающей карточкой «Turn», содержащей стоимость и длительность, и с новым сообщением Slack, открываемым каждый раз, когда запуск инструмента прерывает потоковый текст, так что ход читается как отдельные сообщения вокруг запусков инструментов. Вызовы TodoWrite обновляют одну стабильную карточку-чеклист на месте.
- **Разрешения**: `permissionMode` для каждой привязки по умолчанию равен `acceptEdits`; `--yolo` (псевдоним `--dangerous`) переводит привязку в `bypassPermissions`. Интерактивные диалоги запрещены в ретранслируемых ходах - никто не может ответить на них через Slack - поэтому модель спрашивает прозой, и ваш ответ в треде становится следующим ходом. Встроенный навык плагина учит её отмечать запросившего и завершать ход, когда нужно решение.
- **Slash-команды**: сообщение в треде, чей очищенный текст начинается с `/`, выполняется как slash-команда claude. Редактор Slack проглатывает сообщения, начинающиеся с `/`, поэтому используйте форму с упоминанием в начале (`@bot /usage`) или ведущий пробел.
- **Плавное завершение**: SIGTERM/SIGINT выполняет слив - новые ходы громко отбрасываются, выполняющимся ходам даётся до 5 минут, а дочерний процесс claude запускается отсоединённым в собственной группе процессов, чтобы Ctrl-C в терминале не мог убить его до того, как слив сохранит ход.
- **Очистка треда**: когда вы сообщаете, что работа завершена, модель вызывает внутрипроцессный инструмент `finish_thread`; после того как ход полностью завершается, демон удаляет запись треда, отписывается и публикует одно подтверждение. Новое упоминание запускает новую сессию.
- **Гигиена ошибок**: ошибки хода публикуют только обрезанный текст сообщения, никогда сырые тела ошибок.

## Интерфейс Agent SDK

Программная точка входа пакета (`exports["."]` указывает на `src/sdk.ts`) связывает tokenmaxxing с Claude Agent SDK для агентов, которых вы строите на основе собственных объединённых аккаунтов. Ваше приложение должно работать под Bun (tokenmaxxing поставляется как исходный код на TypeScript и использует `bun:ffi`).

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK порождает подпроцесс claude на каждый `query()` и читает учётные данные один раз при порождении - никакого statusline, никакой горячей замены посреди запроса - поэтому интеграция управляется границами:

- `ensureBestAccount()` - это точно то же решение, что выполняют хуки и таймер CLI (пороги, давление темпа, пауза, весь код общий), никогда не упреждающее: сессия SDK никогда не может быть приостановлена для обратного отсчёта при исчерпании.
- `pooledOptions()` закрепляет `pathToClaudeCodeExecutable` за настоящим бинарником claude (никогда за оболочкой-супервизором) и предоставляет полную замену `env` с вычищенными всеми внешними переопределениями учётных данных. Он быстро завершается с ошибкой, если `CLAUDE_CONFIG_DIR` или `CLAUDE_SECURESTORAGE_CONFIG_DIR` установлены в окружении вашего приложения: в Linux переключение записало бы активные учётные данные туда, куда указывают эти переменные, тогда как вычищенный подпроцесс читает хранилище по умолчанию - тихая рассинхронизация с неверным аккаунтом.
- `stopHookCheck` заново выполняет решение на границах ходов; переключение, которое он совершает, вступает в силу при следующем порождении. Он ловит свои собственные ошибки (записывая в stderr и в лог), а не пробрасывает их дальше, потому что необработанное исключение хука может прервать агента, а прерывание хода из-за сломанной проверки переключения обходится дороже, чем продолжить на текущем аккаунте.

`sdk.ts` ничего не импортирует из самого Agent SDK; его значения структурно распределяются в опции SDK.

## Сборка и распространение

npm-пакет поставляется как исходный код на TypeScript, а не как сборка: бинарник `tokenmaxxing` указывает прямо на `src/main.ts` с shebang-ом Bun, и Bun 1.2.6 или новее запускает его как есть. Именно поэтому Bun - жёсткое требование. Скомпилированных бинарников нет по замыслу: ранний релиз поставил единственный бинарник macOS на 61 МБ на все платформы и упал в Linux с `exec format error`, а скомпилированные пакеты для каждой платформы потребовали бы собственного конвейера релиза, поэтому моделью распространения стал запуск исходного кода через Bun.

Карта `exports` пакета предоставляет `src/sdk.ts` в качестве программной точки входа, описанной выше. Релизы помечаются тегом `v<version>` на GitHub; CI публикует в npm через доверенную публикацию (OIDC, с provenance), и вентиль публикации сначала запускает проверку типов и полный набор тестов.

## Личное использование и условия обслуживания [#personal-use-and-terms-of-service]

tokenmaxxing объединяет аккаунты, которыми вы владеете, в сессиях и агентах, которые вы запускаете сами. Эта формулировка намеренна: Anthropic не разрешает сторонним продуктам предлагать вход claude.ai или лимиты claude.ai, и это включает агентов, построенных на Agent SDK. Не поставляйте объединённый интерфейс SDK, или что-либо построенное на нём, третьим сторонам. tokenmaxxing также намеренно остаётся на опосредованном через CLI пути `/usage` для данных о квоте, вместо того чтобы переизобретать OAuth или проксировать трафик API: это не прокси, и единственные OAuth-эндпоинты, которых он касается, - это стандартный грант обновления, используемый во время переключения, и проверка идентичности только на чтение (эндпоинт roles), которая подтверждает, какому аккаунту на самом деле принадлежит токен.

## Честные ограничения

- **Один холодный ход.** Кэш промптов ограничен организацией, поэтому первый ход на новом аккаунте один раз заново загружает контекст.
- **Заминка при паузе из-за исчерпания.** Только полностью исчерпанный пул останавливает сессию на обратный отсчёт; всё, что напечатано в это мгновение, теряется.
- **Задержка принятия.** На macOS первый ход в пределах ~30 секунд после переключения всё ещё может учитываться на старый аккаунт; запас порогов это поглощает.
- **Общий радиус поражения.** Все сессии профиля по умолчанию используют одни активные учётные данные, поэтому переключение перемещает их все вместе (каждая принимает на месте).
- **Учётные данные в открытом виде на Linux.** Сам Claude Code хранит учётные данные Linux как plaintext-файл с правами 0600; припаркованные копии tokenmaxxing следуют той же модели.

## Устранение неполадок и FAQ

**Похоже, `claude` не находится под супервизором.**
Запустите `tokenmaxxing doctor`. Shim должен выигрывать в разрешении PATH; проверьте, что строка `# tokenmaxxing PATH` в rc-файле вашей оболочки указывает на текущий каталог bin и стоит впереди настоящего claude. `doctor` также предупреждает о `alias claude=...` или shell-функции `claude()`, затеняющей оболочку, и о псевдонимах, запускающих бинарник claude по абсолютному пути (они полностью обходят супервизор).

**Автопереключение никогда не срабатывает в Codex.**
Codex пропускает хуки, которым не сказано доверять. Откройте codex, выполните `/hooks` и доверьте хуку Stop tokenmaxxing. Доверие записывается против хеша хука, поэтому его нужно выдать заново, если хук когда-либо будет отредактирован.

**Аккаунт показывает красный `✗` в statusline.**
Его refresh-токен мёртв (отозван или ротирован из-под его резервной копии). Запустите `tokenmaxxing auth <sel>`, чтобы повторно аутентифицировать его на месте; команда сообщает, под каким email входить, и отказывает во входе, который приводит к другому аккаунту.

**Почему он не переключается на аккаунт с наибольшим остатком квоты?**
Потому что это не тот аккаунт, который сильнее всего рискует потерять квоту. Целью является аккаунт, сильнее всех отстающий от своего недельного темпа: оставшийся процент, делённый на время до его недельного сброса. При равном остатке это сводится к самому раннему истечению в первую очередь, а при равном истечении - к наибольшему остатку в первую очередь.

**Только что произошло переключение, а statusline всё ещё показывает старый аккаунт.**
Это ожидаемо в течение примерно 30 секунд на macOS: работающая сессия принимает подменённые учётные данные при следующем обновлении кэша учётных данных. Ответвление данных об использовании подавляется на 45 секунд после переключения именно по этой причине.

**Стоит ли что-нибудь `status --force`?**
Да, намеренно: он отправляет по одному минимальному тарифицируемому запросу к haiku на каждый аккаунт, чтобы каждое 5-часовое окно сессии стартовало в этот момент, а не лежало бездействующим, затем берёт свежую выборку. Обычные `status` и `watch` никогда не пингуют; чтения `/usage` бесплатны. Учтите, что серверный канал данных об использовании может отставать от только что открытого окна на секунды или минуты, поэтому проверка сразу после пинга может всё ещё показывать состояние до пинга - `status` отображает примечание вместо того, чтобы делать вид, что пинг провалился.

**Проверка `/usage` ничего не вернула для активного аккаунта.**
Это известное поведение claude: когда его внутренний запрос данных об использовании завершается неудачей или ограничивается по частоте, `/usage` печатает только локальную статистику сессии без строк с процентами. tokenmaxxing выбирает данные активного аккаунта из push statusline и проверяет только припаркованные аккаунты, именно чтобы этого избежать.

**Фоновые сессии claude.**
Фоновый демон claude порождает настоящий версионированный бинарник по абсолютному пути, обходя shim-ы PATH, поэтому фоновые сессии не находятся под супервизором. Хуки всё ещё срабатывают через `settings.json`, а принятие учётных данных плюс периодический таймер обеспечивают переключение, но для них нет перезапуска, управляемого маркером.

**Однажды что-то породило множество процессов. Возможно ли это до сих пор?**
Супервизор несёт многослойные защиты от рекурсии против именно этого исторического сбоя (устаревшая оболочка, закреплённая как «настоящий» claude): сторож глубины в окружении, прерывающий на 5 уровнях, ограничитель частоты порождения на диске, проверки идентичности по realpath, отклоняющие любого кандидата, разрешающегося обратно в собственный каталог bin tokenmaxxing, и жёсткий сбой (никогда не молчаливое сканирование PATH), когда настроенный путь к claude больше не существует. `init` и `doctor` проверяют, что кандидат действительно является claude, запуская `--version` перед его закреплением.

**Удаление.**
`tokenmaxxing uninstall` удаляет shim-ы супервизора, записи в настройках и периодический таймер, оставляя ваши аккаунты и припаркованные учётные данные нетронутыми. Он удаляет только записи statusline, которые распознаёт как свои.
