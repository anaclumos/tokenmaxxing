tokenmaxxing అనేది ఆటోమేటిక్ Claude Code ఖాతా మార్పిడి కోసం ఒక CLI. ఇది మీకు స్వంతమైన అనేక సబ్‌స్క్రిప్షన్ (Pro/Max) ఖాతాలను పూల్ చేస్తుంది మరియు వాడుకలో ఉన్న ఖాతా వినియోగ పరిమితికి చేరుకున్నప్పుడు క్రియాశీల క్రెడెన్షియల్‌ను మరింత తాజా ఖాతాకు హాట్-స్వాప్ చేస్తుంది. మీరు ఎప్పటిలాగే `claude`ను నడుపుతారు; మార్పిడి ఒక సురక్షితమైన టర్న్ సరిహద్దు వద్ద జరుగుతుంది మరియు మీ నడుస్తున్న సెషన్ పునఃప్రారంభం లేకుండా అదే సంభాషణను కొత్త ఖాతాలో కొనసాగిస్తుంది. ఇది ఒకేసారి అనేక సమాంతర సెషన్‌లలో పనిచేస్తుంది.

కనిపించే ఏకైక ప్రవర్తన చెత్త పరిస్థితి మాత్రమే: మొత్తం పూల్ దాని పరిమితికి చేరినప్పుడు, సెషన్ ఒక కౌంట్‌డౌన్‌తో నిలిచిపోతుంది మరియు రీసెట్ అయ్యే తదుపరి ఖాతాపై స్వయంచాలకంగా కొనసాగుతుంది (Ctrl-C వెంటనే కొనసాగిస్తుంది).

## సమస్య

ఒక Claude సబ్‌స్క్రిప్షన్ ఒకేసారి మూడు పరిమితులను కొలుస్తుంది (అన్నీ `/usage` ద్వారా ధృవీకరించబడ్డాయి):

- **ప్రస్తుత సెషన్**: రోలింగ్ 5-గంటల విండో.
- **ప్రస్తుత వారం (అన్ని మోడల్‌లు)**: 7-రోజుల మొత్తం.
- **ప్రస్తుత వారం, ప్రతి మోడల్‌కు**: వ్యక్తిగత మోడల్ కుటుంబాల కోసం వేర్వేరు వారపు పరిమితులు. ఇవి ప్రస్తుతం Sonnet మరియు Fable కోసం మాత్రమే ఉన్నాయి, మరియు Fable పరిమితి మాత్రమే పట్టించుకోదగినంత గట్టిగా ఉంది - ఇది మొత్తం పరిమితి కంటే చాలా ముందుగానే బంధిస్తుంది. ఒక యంత్రం ఇప్పటికే 80% week-Fable వద్ద ఉన్నప్పుడు 50% week-all వద్ద ఉండవచ్చు.

వారపు కోటా వాడుకో-లేదా-కోల్పో విధానంలో ఉంటుంది: ఒక ఖాతా తన నిర్ధారిత వారపు రీసెట్ నాటికి వినియోగించని దానంతా కోల్పోతుంది. మీకు అనేక ఖాతాలు ఉంటే, తన స్వంత వారపు వేగం కంటే అత్యంత వెనుకబడి ఉన్న ఖాతాపై కోటాను ఖర్చు చేస్తూ ఉండటం, మరియు సెషన్ మధ్యలో ఏదైనా ఒక పరిమితి గోడకు తగిలే ముందు మారడం హేతుబద్ధమైన వ్యూహం.

దీన్ని చేతితో చేయడం అంటే లాగ్ అవుట్ చేయడం, లాగిన్ చేయడం, మరియు మీ సంభాషణను కోల్పోవడం. tokenmaxxing దీన్ని స్వయంచాలకం చేస్తుంది: నడుస్తున్న `claude` అభ్యర్థనల మధ్య తన క్రెడెన్షియల్ స్టోర్‌ను తిరిగి తనిఖీ చేస్తుంది, కాబట్టి దాని కింద మార్చబడిన క్రెడెన్షియల్ యథాస్థానంలో స్వీకరించబడుతుంది (macOS పై సుమారు 30 సెకన్లలో, Linux పై తదుపరి అభ్యర్థనలో). ఒక సాధారణ మార్పిడి మీ సెషన్‌ను ఎప్పుడూ పునఃప్రారంభించదు. ఇప్పటికీ ప్రాసెస్ నిర్వహణ అవసరమయ్యే ఒకే సందర్భం పూర్తిగా ఖాళీ అయిన పూల్ - ఒక సెషన్ తనను తాను నిలిపివేయలేదు - మరియు అందుకే సన్నని సూపర్‌వైజర్ ఉంది.

`claude` గురించి మిగతా అంతా మారదు: అన్ని ఫ్లాగ్‌లు, MCP సర్వర్‌లు, హుక్‌లు, మరియు స్కిల్‌లు యథాతథంగా వెళ్తాయి.

## త్వరిత ప్రారంభం

macOS లేదా Linux పై [Bun](https://bun.sh) మరియు Claude Code అవసరం.

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` ఐదు పనులు చేస్తుంది:

1. మీరు ఇప్పటికే లాగిన్ అయి ఉన్న ఖాతాను ఖాతా #1గా దిగుమతి చేస్తుంది (ప్రత్యేక `adopt` కమాండ్ లేదు).
2. `claude` సూపర్‌వైజర్ షిమ్‌ను ఇన్‌స్టాల్ చేస్తుంది.
3. Claude Code యొక్క `settings.json`లో మూడు ఎంట్రీలను ఇన్‌స్టాల్ చేస్తుంది: ఒక statusLine, ఒక Stop హుక్, మరియు ఒక SessionStart హుక్ (అదనంగా ఒక subagentStatusLine ఎంట్రీ).
4. సూపర్‌వైజర్ యొక్క bin డైరెక్టరీని మీ షెల్ rc యొక్క PATHకు జోడిస్తుంది (ఇడెంపొటెంట్, `# tokenmaxxing PATH` వ్యాఖ్యతో గుర్తించబడింది). దాన్ని అడ్డగించడానికి అది PATHలో అసలైన `claude` కంటే ముందు ఉండాలి.
5. ప్రతి 180 సెకన్లకు `tokenmaxxing check`ను నడిపే ఆవర్తన తనిఖీ టైమర్‌ను (macOS పై launchd ఏజెంట్, Linux పై systemd యూజర్ టైమర్) ఇన్‌స్టాల్ చేస్తుంది.

మీ షెల్‌ను పునఃప్రారంభించండి, తర్వాత మరిన్ని ఖాతాలను జోడించి ప్రారంభించండి:

```sh
tokenmaxxing add        # మరో ఖాతాను వేరుచేసి లాగిన్ చేసి పూల్ చేస్తుంది
claude                  # ఎప్పటిలాగే claude వాడండి
```

`tokenmaxxing`కు `xx` అనే మారుపేరు కూడా ఉంది. ఒట్టి `tokenmaxxing` (లేదా `xx`) `status`ను నడుపుతుంది; `switch` స్పష్టంగానే ఉంటుంది.

## కమాండ్‌లు

| కమాండ్ | ఇది ఏమి చేస్తుంది |
|---|---|
| `tokenmaxxing init` | ప్రస్తుత ఖాతాను దిగుమతి చేయండి, సూపర్‌వైజర్, హుక్‌లు, మరియు statuslineను ఇన్‌స్టాల్ చేయండి |
| `tokenmaxxing init --codex` | Codex కోసం అదే: లాగిన్‌ను దిగుమతి చేయండి, codex సూపర్‌వైజర్ మరియు Stop హుక్‌ను ఇన్‌స్టాల్ చేయండి |
| `tokenmaxxing add` | అదనపు ఖాతాను నమోదు చేయండి (వేరుచేసిన లాగిన్, పూల్‌లోకి సేకరించబడుతుంది) |
| `tokenmaxxing add --codex` | అదనపు Codex ఖాతాను నమోదు చేయండి (వేరుచేసిన లాగిన్) |
| `tokenmaxxing auth [sel \| --all]` | పూల్ చేసిన ఖాతాను యథాస్థానంలో తిరిగి ప్రామాణీకరించండి. ఒట్టిది పూల్‌ను జాబితా చేసి ఏది అని అడుగుతుంది; ఒక సెలెక్టర్ ఒక ఖాతాను లక్ష్యంగా చేసుకుని ఏ ఇమెయిల్‌తో సైన్ ఇన్ చేయాలో చెబుతుంది; `--all` తిరిగి-ప్రామాణీకరణ అవసరమైన ప్రతి ఖాతాను ఒక్కొక్కటిగా నడుస్తుంది |
| `tokenmaxxing switch [sel]` | ఉత్తమ ఖాతాకు మారండి (అత్యాశ, ఇడెంపొటెంట్) లేదా నిర్దిష్ట ఖాతాను బలవంతం చేయండి |
| `tokenmaxxing switch --codex [sel]` | Codex పూల్‌ను మార్చండి (తదుపరి codex ప్రారంభంలో అమలులోకి వస్తుంది) |
| `tokenmaxxing ls` | పూల్ చేసిన ఖాతాలను జాబితా చేయండి |
| `tokenmaxxing status` | 5గం / వారపు / ప్రతి-మోడల్ వినియోగ బార్‌లతో ఖాతాలు, క్రియాశీలం మరియు రీసెట్-వరకు-ఖాళీ |
| `tokenmaxxing status --force` | అదనంగా ప్రతి ఖాతాను పింగ్ చేయండి (ఒక్కొక్కదానికి ఒక చిన్న haiku అభ్యర్థన) తద్వారా అన్ని 5గం సెషన్ టైమర్‌లు ఇప్పుడు ప్రారంభమవుతాయి, తర్వాత తాజాగా నమూనా చేయండి |
| `tokenmaxxing watch [seconds]` | ప్రత్యక్ష స్థితి, ప్రతి N సెకన్లకు తిరిగి రెండర్ చేయబడుతుంది (డిఫాల్ట్ 120, కనిష్ఠం 30; ఎప్పుడూ పింగ్ చేయదు) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | మూలాలతో అమలులో ఉన్న కాన్ఫిగ్; డాట్ చేసిన కీలను సవరించండి; `tidy` తెలియని కీలను తొలగిస్తుంది |
| `tokenmaxxing check` | మార్పిడి నిర్ణయాన్ని ఒకసారి మూల్యాంకనం చేయండి (ఆవర్తన టైమర్ నడిపేది ఇదే) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack బ్రిడ్జ్ డెమన్ (Socket Mode, పబ్లిక్ URL లేదు) |
| `tokenmaxxing doctor` | సూపర్‌వైజర్ మరియు సెట్టింగ్‌ల ఎంట్రీలు నిలిచి ఉన్నాయని ధృవీకరించండి |
| `tokenmaxxing rename [--codex] <sel> <label>` | పూల్ చేసిన ఖాతాకు తిరిగి లేబుల్ ఇవ్వండి |
| `tokenmaxxing rm <sel>` | పూల్ నుండి ఒక ఖాతాను తొలగించండి |
| `tokenmaxxing uninstall` | సూపర్‌వైజర్ మరియు సెట్టింగ్‌ల ఎంట్రీలను తొలగించండి (ఖాతాలు మరియు క్రెడెన్షియల్‌లు ఉంచబడతాయి) |

## ఆర్కిటెక్చర్

tokenmaxxing అనేది ఒకే మల్టీ-కాల్ ఎంట్రీ పాయింట్ (`src/main.ts`), అది ఆ పేరుతో పిలిచినప్పుడు `claude` సూపర్‌వైజర్‌గా ప్రవర్తిస్తుంది, అంతర్గత సబ్‌కమాండ్‌ల ద్వారా హుక్ మరియు statusline షిమ్‌లను అందిస్తుంది, మరియు లేకపోతే CLIని పంపిణీ చేస్తుంది. ఇది నేరుగా Bun కింద నడుస్తుంది; npm ప్యాకేజ్ ఒక బిల్డ్ కాదు, TypeScript సోర్స్‌ను రవాణా చేస్తుంది.

కదిలే భాగాలు:

### సూపర్‌వైజర్ షిమ్

`init` `claude` అనే 2-లైన్ల షెల్ షిమ్‌ను `~/.config/tokenmaxxing/bin/`లోకి రాస్తుంది మరియు ఆ డైరెక్టరీని PATHలో మొదటిగా ఉంచుతుంది. మీరు `claude` టైప్ చేసినప్పుడు, షిమ్ సూపర్‌వైజర్‌ను నడుపుతుంది, అది వారసత్వంగా వచ్చిన stdio మరియు సేవ్ చేసిన `stty -g` టెర్మినల్ స్నాప్‌షాట్‌తో అసలైన claude బైనరీని స్పాన్ చేస్తుంది. ఇది కేవలం ప్రాసెస్ మరియు టెర్మినల్ మేనేజర్ మాత్రమే: ఇది API ట్రాఫిక్‌ను ఎప్పుడూ ప్రాక్సీ చేయదు మరియు ప్రయాణంలో ఉన్న టోకెన్‌లను ఎప్పుడూ తాకదు.

ప్రింట్-మోడ్ ఇన్వొకేషన్‌లు (`claude -p`, `--version`, `--help`), నాన్-ఇంటరాక్టివ్ సబ్‌కమాండ్‌లు (`claude mcp`, `claude config`, మొదలైనవి), మరియు tokenmaxxing యొక్క స్వంత ప్రోబ్‌లు ఎటువంటి సెషన్ నిర్వహణ లేకుండా నేరుగా వెళ్తాయి. ఇంటరాక్టివ్ సెషన్ కోసం, సూపర్‌వైజర్ ఒక సెషన్ idని పిన్ చేస్తుంది (ఒకదాన్ని ఉత్పత్తి చేస్తూ, లేదా మీరు `--session-id` / `-r` / `-c` ద్వారా అందించిన దాన్ని తిరిగి ఉపయోగిస్తూ), తర్వాత పునఃప్రారంభం వాటిని రీప్లే చేయగలిగేలా మీ లాంచ్ ఫ్లాగ్‌లను నిల్వ చేస్తుంది, ఆపై ఆ సెషన్‌కు కీ చేసిన రీస్పాన్ మార్కర్ ఫైల్ కోసం గమనిస్తుంది.

### statusline టీ

Claude Code ప్రతి టర్న్‌లో రేట్-లిమిట్ డేటాను (`rate_limits.five_hour` మరియు `rate_limits.seven_day`) statusline యొక్క stdinలోకి పంపుతుంది. statusline స్లాట్ tokenmaxxing స్వంతం, కాబట్టి దాని రెండరర్ ఒక ఉచిత, పుష్-ఆధారిత వినియోగ ఫీడ్‌గా కూడా పనిచేస్తుంది: ప్రతి టిక్‌కు అది మొత్తం విండోలను, అలాగే క్రియాశీల మోడల్‌ను `usage.json`లోకి టీ చేస్తుంది. ప్రతి-మోడల్ పరిమితులు statusline stdinలో ఉండవు; అవి `claude -p '/usage'` (ఉచితం, సున్నా టోకెన్‌లు) నుండి మాత్రమే వస్తాయి, ఇది TTLతో పోల్ చేయబడి, క్రియాశీల మోడల్ సామర్థ్య-పరిమితం అయినప్పుడు `model-usage.json`లోకి కాష్ చేయబడుతుంది.

టీ మార్పు-పైన-రాయడం విధానంలో ఉంటుంది: సంఖ్యలు మారనప్పుడు అది కేవలం ఫైల్ యొక్క mtimeను పెంచుతుంది, ఇది ఫీడ్ యొక్క సజీవత్వ హృదయస్పందనగా పనిచేస్తుంది. తాజాతనం ఎల్లప్పుడూ mtime ద్వారా అంచనా వేయబడుతుంది, ఎంబెడ్ చేసిన టైమ్‌స్టాంప్ ద్వారా ఎప్పుడూ కాదు.

### Stop హుక్ మరియు మార్పిడి

ప్రతి టర్న్ సరిహద్దు వద్ద, Stop హుక్ మార్పిడి నిర్ణయాన్ని నడుపుతుంది ([మార్పిడి ఎలా నిర్ణయిస్తుంది](#how-switching-decides) చూడండి). మార్పిడి సమర్థనీయమైనప్పుడు, ఇది `flock(2)` ప్రత్యేక లాక్ కింద జరుగుతుంది (`bun:ffi` ద్వారా తీసుకోబడుతుంది, ఎందుకంటే macOS ఏ `flock(1)` బైనరీని రవాణా చేయదు), మరియు క్రెడెన్షియల్ రైట్‌లు అదనంగా Claude Code యొక్క స్వంత రిఫ్రెష్ లాక్‌తో ఇంటర్‌లాక్ అవుతాయి. క్రిటికల్ సెక్షన్ లోపల, ఒక మార్పిడి:

1. ప్రస్తుత లైవ్ క్రెడెన్షియల్‌ను దాని నిజమైన యజమాని పార్క్ చేసిన బ్యాకప్‌లోకి సేకరిస్తుంది.
2. లక్ష్య ఖాతా యొక్క తాజాగా రిఫ్రెష్ చేసిన క్రెడెన్షియల్‌ను లైవ్‌గా ఇన్‌స్టాల్ చేస్తుంది, ఇప్పటికే ఉన్న లైవ్ బ్లాబ్‌లోకి విలీనం చేస్తుంది తద్వారా సోదర స్థితి (ప్రతి-MCP-సర్వర్ OAuth టోకెన్‌ల వంటివి) నిలిచి ఉంటుంది.
3. లక్ష్యం యొక్క తిప్పబడిన టోకెన్‌ను దాని స్వంత బ్యాకప్‌కు నిల్వ చేస్తుంది.
4. `~/.claude.json`లోని `oauthAccount` ఫీల్డ్‌ను ఆటమిక్‌గా తిరిగి రాస్తుంది.
5. కొత్త క్రియాశీల లేబుల్‌ను కమిట్ చేస్తుంది మరియు పాత వినియోగ స్నాప్‌షాట్‌లను తొలగిస్తుంది, ఇవన్నీ లాక్ విడుదల కావడానికి ముందు, తద్వారా ఒక క్రాష్ ఇన్‌స్టాల్ చేసిన క్రెడెన్షియల్ మరియు క్రియాశీల లేబుల్‌ను వేర్వేరు ఖాతాల వైపు చూపిస్తూ ఎప్పుడూ వదిలిపెట్టదు.

అన్ని డిఫాల్ట్-ప్రొఫైల్ సెషన్‌లు ఒకే లైవ్ క్రెడెన్షియల్‌ను పంచుకుంటాయి కాబట్టి, ఒకే మార్పిడి ప్రతి సెషన్‌ను ఒకేసారి మారుస్తుంది, మరియు flock, అలాగే లాక్ కింద తిరిగి-తనిఖీ, పోటీపడే హుక్‌లు రెండు ఖాతాలను ఖర్చు చేయకుండా నిరోధిస్తాయి.

### యథాస్థాన స్వీకరణ

నడుస్తున్న claude సెషన్ అభ్యర్థనల మధ్య తన క్రెడెన్షియల్ స్టోర్‌ను పోల్ చేస్తుంది: macOS పై ఇది ఒక చిన్న కాష్ ద్వారా కీచైన్‌ను తిరిగి చదివి యాక్సెస్ టోకెన్‌లను పోల్చుతుంది; Linux పై ఇది క్రెడెన్షియల్‌ల ఫైల్ యొక్క mtimeను స్టాట్ చేసి, మార్పు జరిగినప్పుడు తన టోకెన్ కాష్‌లను ఫ్లష్ చేస్తుంది. మొత్తం ప్రభావం ఏమిటంటే, మార్చబడిన క్రెడెన్షియల్ ప్రతి నడుస్తున్న సెషన్ చేత macOS పై సుమారు 30 సెకన్లలో మరియు Linux పై తదుపరి అభ్యర్థనలోనే, ఎటువంటి పునఃప్రారంభం లేకుండా స్వీకరించబడుతుంది. అందుకే ఒక సాధారణ మార్పిడి ఏ మార్కర్‌ను రాయదు మరియు ఏ రీస్పాన్‌ను ప్రేరేపించదు - సెషన్ కేవలం కొత్త ఖాతాపై కొనసాగుతుంది. సెషన్-లోని `/usage` అదే టోకెన్ కాష్‌లను పంచుకుంటుంది, కాబట్టి దాని ఖాతా ప్రదర్శన స్వీకరణతో పాటు మారుతుంది.

### ఖాళీ-పూల్ నిరీక్షణ మరియు స్వయంచాలక పునఃప్రారంభం

పూల్‌లోని ప్రతి ఖాతా తన బార్‌లను దాటినప్పుడు మాత్రమే Stop హుక్ ఒక రీస్పాన్ మార్కర్‌ను రాస్తుంది (మార్కర్ స్కీమాకు `waitUntil` టైమ్‌స్టాంప్ అవసరం; ఒక సాధారణ మార్పిడి ఎప్పుడూ ఒకదాన్ని ఉత్పత్తి చేయలేదు). సూపర్‌వైజర్ మార్కర్‌ను చూసి, ఇప్పటికే కమిట్ చేసిన టర్న్ సరిహద్దు వద్ద తన చైల్డ్‌కు SIGTERM పంపుతుంది (ట్రాన్‌స్క్రిప్ట్ డిస్క్‌పై ఉన్న తర్వాత మరియు claude నిష్క్రియంగా ఉన్నప్పుడు Stop హుక్ నడుస్తుంది, కాబట్టి ఏదీ కోల్పోదు), టెర్మినల్‌ను పునరుద్ధరిస్తుంది, త్వరగా వచ్చే రీసెట్‌కు ఒక కౌంట్‌డౌన్‌ను చూపుతుంది, ఆపై కోలుకున్న ఖాతాపై `claude --resume <session-id>`ను తిరిగి ప్రారంభిస్తుంది. కౌంట్‌డౌన్ సమయంలో Ctrl-C వెంటనే కొనసాగిస్తుంది. స్వయంచాలక-నిరీక్షణ `policy.maxWaitMs` (డిఫాల్ట్ 1 గంట) ద్వారా పరిమితం చేయబడింది; దాన్ని దాటితే నిర్ణయం నిరీక్షించే బదులు పూల్‌ను ఖాళీగా నివేదిస్తుంది.

### ఆవర్తన తనిఖీ టైమర్

హుక్‌లు కేవలం టర్న్ సరిహద్దుల వద్ద మాత్రమే ప్రేరేపించబడతాయి, మరియు ఒక పొడవైన ఏజెంటిక్ టర్న్ ఒక్క సరిహద్దు లేకుండా ఒక విండోను ఆరోగ్యకరమైన స్థితి నుండి ఖాళీ స్థితికి ఖర్చు చేయగలదు. అందువల్ల `init` ఒక ఆవర్తన టైమర్‌ను కూడా ఇన్‌స్టాల్ చేస్తుంది - macOS పై launchd ఏజెంట్, Linux పై systemd యూజర్ టైమర్ - అది టర్న్ కార్యకలాపంతో సంబంధం లేకుండా ప్రతి 180 సెకన్లకు `tokenmaxxing check`ను నడుపుతుంది.

### ఒక SessionStart హుక్

సెషన్ ప్రారంభమైనప్పుడు లేదా కొనసాగినప్పుడు అదే మూల్యాంకనాన్ని నడుపుతుంది, తద్వారా కొత్త సెషన్ సరైన ఖాతాపై ప్రారంభమవుతుంది. మార్పిడి-తర్వాత కూల్‌డౌన్ దీన్ని రీస్పాన్ తర్వాత వెంటనే సరైన నో-ఆప్‌గా చేస్తుంది.

## మార్పిడి ఎలా నిర్ణయిస్తుంది [#how-switching-decides]

నిర్ణయానికి రెండు పొరలు ఉన్నాయి: ఒక ఎంగేజ్‌మెంట్ గేట్, ఆపై ఒక అత్యాశ లేదా కఠిన మార్గం.

### ఎంగేజ్‌మెంట్

`policy.greedySessionFloor` (డిఫాల్ట్ 50, 5-గంటల సెషన్ విండోలో శాతంగా) కంటే తక్కువగా ఉంటే, నిర్ణయం అస్సలు నడవదు - కొత్త సెషన్ తన ఖాతాపై కొనసాగుతుంది. క్రియాశీల సెషన్ విండో 50% వాడబడిన తర్వాత, లేదా ఏదైనా కఠిన బార్ దాటిన తర్వాత, నిర్ణయం ఎంగేజ్ అవుతుంది.

### స్క్రీనింగ్ బార్‌లు

థ్రెషోల్డ్‌లు స్క్రీనింగ్ బార్‌లు, భయాందోళనకు ట్రిగర్ కాదు:

- `thresholds.session`: 95. 5-గంటల రీసెట్ కోసం వేచి ఉండటం చౌక, కాబట్టి సెషన్ విండో ముందుగానే మారిపోతుంది.
- `thresholds.weekly`: 98. ఈ ఒక్క బార్ 7-రోజుల మొత్తం మరియు ప్రతి-మోడల్ వారపు పరిమితి రెండింటినీ కవర్ చేస్తుంది. వారపు కోటా వాడుకో-లేదా-కోల్పో విధానంలో ఉంటుంది, కాబట్టి ఇది గోడకు దగ్గరగా ఖాళీ అవుతుంది.

రెండూ ఉద్దేశపూర్వకంగా 100 కంటే తక్కువగా ఉన్నాయి: ఖాతా నిజంగా తన పరిమితిని తాకే ముందు ఒక శుభ్రమైన టర్న్ సరిహద్దును (అదనంగా macOS పై ఒక టర్న్ వరకు స్వీకరణ ఆలస్యం) చేరుకోవడానికి ఆ వెసులుబాటే బడ్జెట్. అదే బార్‌లు మార్పిడి అభ్యర్థులను స్క్రీన్ చేస్తాయి: తన బార్‌లలో ఏదైనా దాటిన ఖాతా చెల్లుబాటు అయ్యే లక్ష్యం కాదు. ట్రిగర్ మరియు స్క్రీనింగ్ ఎల్లప్పుడూ అదే అమలు బార్‌లను (థ్రెషోల్డ్‌లు మైనస్ `policy.projectionMargin`) ఉపయోగిస్తాయి, ఎందుకంటే ట్రిగర్ కంటే వదులైన స్క్రీన్ ట్రిగర్ వెంటనే తిరిగి-ఫ్లాగ్ చేసే ఖాతాలపై మార్పిడులను దింపి, పూల్‌ను ముందుకూ వెనుకకూ కొట్టేస్తుంది.

### లక్ష్యం: వేగ ఒత్తిడి

వాడదగిన ఖాతాలలో, లక్ష్యం తన స్వంత వారపు వేగం కంటే అత్యంత వెనుకబడి ఉన్నది: అత్యధిక **వేగ ఒత్తిడి**, ఇది మిగిలిన వారపు శాతాన్ని ఆ ఖాతా వారపు రీసెట్ వరకు ఉన్న సమయంతో భాగించగా వచ్చినట్లు నిర్వచించబడింది. కోల్పోబోతున్న అత్యధిక కోటా ఉన్న ఖాతా గెలుస్తుంది. సమానత్వాలు త్వరగా వచ్చే వారపు గడువుకు, ఆపై అత్యల్ప 7-రోజుల వినియోగానికి తీర్చబడతాయి.

అంతా సంపూర్ణ UTC ఎపోక్‌లుగా నిల్వ చేయబడిన కాష్ చేసిన విండోలపై నడుస్తుంది, కాబట్టి పాత స్నాప్‌షాట్ కూడా సరిగ్గా పరిష్కరించబడుతుంది: గడిచిపోయిన వారపు రీసెట్ ఖచ్చితమైన 7-రోజుల దశలలో ముందుకు లెక్కించబడుతుంది, మరియు తన కాష్ చేసిన రీసెట్‌ను దాటిన ఏ విండో అయినా తాజాగా ఖాళీగా లెక్కించబడుతుంది (మారడానికి ఎప్పుడూ కారణం కాదు, ఖాతాను బెంచ్‌లో ఉంచడానికి ఎప్పుడూ కారణం కాదు).

### అత్యాశ మార్గం vs కఠిన మార్గం

- **అత్యాశ మార్గం** (ఎంగేజ్ అయినది, కానీ ప్రతి బార్ కింద): ప్రస్తుత ఖాతాతో సహా ప్రతి ఖాతాకు ర్యాంక్ ఇవ్వండి. ప్రస్తుత ఖాతా ఇప్పటికే గెలిచినా లేదా సమానంగా ఉన్నా, ఏమీ చేయవద్దు. లేకపోతే ఖచ్చితంగా మెరుగైన ఖాతాకు మారండి. ఇది ఎప్పుడూ నిరీక్షించదు మరియు ఎప్పుడూ ముందుగా-పార్క్ చేయదు - వాడదగిన ప్రస్తుత ఖాతా నిరీక్షణ కోసం మార్చుకోబడదు. ప్రస్తుత ఖాతాకు కూడా ర్యాంక్ ఇవ్వబడుతుంది కాబట్టి, స్వయంచాలక మార్గం మరియు ఒట్టి `tokenmaxxing switch` రెండూ ఇడెంపొటెంట్: ఆవర్తనంగా మూల్యాంకనం చేయడం సరైన ఖాతాపై కేంద్రీకృతమై, ఆపై అక్కడే ఉంటుంది.
- **కఠిన మార్గం** (ఒక బార్ దాటబడింది): ఉత్తమ వాడదగిన అభ్యర్థికి మారండి. ఒక అభ్యర్థి రిఫ్రెష్ టోకెన్ చనిపోయినట్లు తేలితే, అది తిరిగి-ప్రామాణీకరణ అవసరమని ఫ్లాగ్ చేయబడి, తదుపరి అభ్యర్థి ప్రయత్నించబడుతుంది. ఏదీ వాడదగినది కాకపోతే, ఖాళీ-నిరీక్షణ లాజిక్ నడుస్తుంది; సెషన్‌ను నిజంగా నిలిపివేయగల కాలర్ (పర్యవేక్షించబడిన Stop హుక్) మాత్రమే ఇంకా-నిరోధించబడిన కానీ త్వరగా-కోలుకునే ఖాతాపై ముందుగా-పార్క్ చేయడానికి అనుమతించబడుతుంది.

### ప్రతి-మోడల్ పరిమితులు

`policy.switchModels` (డిఫాల్ట్ `["fable"]`) ప్రతి-మోడల్ వారపు పరిమితి మార్పిడిని ట్రిగర్ చేయగల మోడల్ కుటుంబాలను పేర్కొంటుంది. సరిపోల్చడం కుటుంబ టోకెన్ ద్వారా జరుగుతుంది, ఖచ్చితమైన ప్రదర్శన స్ట్రింగ్ ద్వారా ఎప్పుడూ కాదు: మోడల్ ప్రదర్శన పేర్లు మారుతూ ఉంటాయి ("Fable" "Fable 5" అయ్యింది), మరియు ఒక ఖచ్చితమైన-స్ట్రింగ్ గేట్ ఒకసారి ప్రతి-మోడల్ మార్పిడిని పూర్తిగా నిశ్శబ్దంగా నిలిపివేసింది. రెండు సంబంధిత భద్రతా నియమాలు:

- తెలియని క్రియాశీల మోడల్ ప్రతి కాన్ఫిగర్ చేసిన కుటుంబాన్ని గేట్ చేస్తుంది. మార్పిడి స్నాప్‌షాట్‌లను తొలగించిన వెంటనే, ఒక హెడ్‌లెస్ యంత్రం మోడల్-గుడ్డిగా నడవవచ్చు; తెలియని దాన్ని పరిమితి లేనిదిగా పరిగణించడం ఒకసారి ఒక ఖాతాను గంటల తరబడి గమనించకుండా దాని Fable పరిమితి వద్ద ఉండనిచ్చింది.
- అభ్యర్థి స్క్రీనింగ్ గేట్ చేసిన ప్రతి-మోడల్ పరిమితులను కూడా లెక్కిస్తుంది, కాబట్టి ప్రతి ఖాతా తన Fable పరిమితిని ఖర్చు చేసిన పూల్ రౌండ్-రాబిన్ చేయదు.

### కూల్‌డౌన్

45-సెకన్ల మార్పిడి-తర్వాత కూల్‌డౌన్ స్వయంచాలక మార్గాన్ని గేట్ చేస్తుంది. మార్పిడి తర్వాత అదే 45 సెకన్ల పాటు statusline టీ అణచివేయబడుతుంది (macOS పై స్వీకరణకు 30 సెకన్ల వరకు పడుతుంది), కాబట్టి ముందటి మూల్యాంకనం మార్పిడి తానే చెల్లనిదిగా చేసిన డేటాపై నడుస్తుంది - ఆ ఖచ్చితమైన పరిస్థితి ఒకసారి A-నుండి-B-మరియు-తిరిగి రీస్పాన్ లూప్‌ను ఉత్పత్తి చేసింది. మాన్యువల్ `tokenmaxxing switch` కూల్‌డౌన్ చేత ప్రభావితం కాదు.

## కాన్ఫిగరేషన్

కాన్ఫిగ్ `~/.config/tokenmaxxing/config.json` వద్ద JSON. ప్రతి ఫీల్డ్ ఐచ్ఛికం; డిఫాల్ట్‌లు ప్రతి-ఫీల్డ్‌కు వర్తిస్తాయి.

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: పైన వివరించిన స్క్రీనింగ్ బార్‌లు.
- `policy.projectionMargin`: అమలు బార్‌లను ఏర్పరచడానికి రెండు బార్‌ల నుండి తీసివేయబడుతుంది.
- `policy.greedySessionFloor`: అత్యాశ కేంద్రీకరణ ఎంగేజ్ అయ్యే సెషన్-వాడిన శాతం.
- `policy.switchModels`: ప్రతి-మోడల్ వారపు పరిమితి మార్పిడిని గేట్ చేసే మోడల్ కుటుంబాలు (లోడ్ అయ్యేటప్పుడు ఎంట్రీలు చిన్న అక్షరాలుగా మార్చబడతాయి).
- `policy.usagePollTtlMs`: `/usage` ప్రతి-మోడల్ పోల్ ఎంతసేపు తాజాగా ఉంటుంది.
- `policy.maxWaitMs`: ఖాళీ-పూల్ స్వయంచాలక-నిరీక్షణ పరిమితి.

`tokenmaxxing config` మూలాలతో అమలు కాన్ఫిగ్‌ను చూపుతుంది; `config set`/`unset` డాట్ చేసిన కీలను సవరిస్తాయి; `config tidy` తెలియని కీలను తొలగిస్తుంది.

## స్థితి డైరెక్టరీ లేఅవుట్

మొత్తం `~/.config/tokenmaxxing/` కింద ఉంటుంది (`TOKENMAXXING_HOME`తో అధిగమించవచ్చు; బాహ్యంగా గమనించగల ప్రతి పాత్‌కు ఒక env ఓవర్‌రైడ్ ఉంది, తద్వారా మొత్తం సాధనం పరీక్షలలో హెర్మెటిక్‌గా నడవగలదు).

| పాత్ | ఇది ఏమి కలిగి ఉంటుంది |
|---|---|
| `config.json` | మీ కాన్ఫిగరేషన్ (విరళం; డిఫాల్ట్‌లు ప్రతి ఫీల్డ్‌కు వర్తిస్తాయి) |
| `accounts.json` | పూల్ చేసిన Claude ఖాతాల రహస్యం-కాని సూచిక: లేబుల్‌లు, ids, కాష్ చేసిన వినియోగ విండోలు. టోకెన్‌లు ఎప్పుడూ కాదు |
| `usage.json` | statusline టీ యొక్క సమగ్ర విండో స్నాప్‌షాట్; దాని mtime ఫీడ్ యొక్క సజీవత హార్ట్‌బీట్ |
| `model-usage.json` | `/usage` నుండి TTL-కాష్ చేసిన ప్రతి-మోడల్ వారపు పరిమితులు |
| `lastswap.json` | చివరి మార్పిడి యొక్క ఎపోక్ టైమ్‌స్టాంప్; 45-సెకన్ల కూల్‌డౌన్‌ను నడిపిస్తుంది |
| `lock` | మార్పిడులను క్రమీకరించే `flock` ఫైల్ |
| `tokenmaxxing.log` | జోడించడం-మాత్రమే ఈవెంట్ లాగ్ |
| `bin/` | PATH షిమ్‌లు: `claude`, `codex`, మరియు `tokenmaxxing` / `xx` ఎంట్రీ పాయింట్‌లు |
| `respawn/<session-id>` | సూపర్‌వైజర్ గమనించే ఖాళీ-నిరీక్షణ రీస్పాన్ మార్కర్‌లు |
| `creds/` | Linux మాత్రమే: పార్క్ చేసిన క్రెడెన్షియల్ ఫైల్‌లు, 0700 డైరెక్టరీలో 0600 (macOS బదులుగా క్రెడెన్షియల్‌లను ప్రతి-ఖాతా కీచైన్ అంశాలుగా పార్క్ చేస్తుంది) |
| `onboard/`, `sample/` | `add`/`auth` లాగిన్‌ల కోసం మరియు పార్క్ చేసిన-ఖాతా `/usage` ప్రోబ్‌ల కోసం విసిరివేయదగిన వేరుచేసిన కాన్ఫిగ్ హోమ్‌లు; ప్లెయిన్‌టెక్స్ట్ క్రెడెన్షియల్‌లను కలిగి ఉన్న onboard హోమ్‌లు సేకరణ తర్వాత తొలగించబడతాయి |
| `slack.json` | `xx serve` టోకెన్‌లు మరియు ఛానెల్ లింక్‌లు (0600) |
| `slack-threads/` | `xx serve` కోసం ప్రతి-థ్రెడ్ సెషన్ రికార్డులు |
| `codex-*` | సమాంతర Codex పూల్: `codex-accounts.json`, `codex-lastswap.json`, `codex-lock`, `codex-creds/`, `codex-onboard/`, `codex-respawn/`, మరియు `codex-live/` (ప్రతి నడుస్తున్న సూపర్‌వైజ్డ్ codex సెషన్‌కు ఒక PID-ధృవీకరించిన ఉనికి ఫైల్, తద్వారా లైవ్ ఖాతా ఎప్పుడూ మార్పిడి లక్ష్యం కాదు) |

తన స్వంత డైరెక్టరీ వెలుపల, tokenmaxxing సరిగ్గా వీటిని మాత్రమే తాకుతుంది: `~/.claude.json` (`oauthAccount` మార్పిడి), Claude Code యొక్క `settings.json` (హుక్ మరియు statusline ఎంట్రీలు), లైవ్ క్రెడెన్షియల్ స్టోర్ (macOS పై `Claude Code-credentials` కీచైన్ అంశం, Linux పై `.credentials.json`), `~/.claude.lock` (claude యొక్క రిఫ్రెష్ లాక్, మార్పిడుల సమయంలో తీసుకోబడుతుంది), codex యొక్క `auth.json` మరియు `hooks.json`, మరియు launchd లేదా systemdలో ఆవర్తన-తనిఖీ యూనిట్.

## క్రెడెన్షియల్ నిల్వ మరియు భద్రతా నమూనా

మొత్తం స్థితి `~/.config/tokenmaxxing/`లో ఉంటుంది. క్రెడెన్షియల్ I/O ఒకే ప్లాట్‌ఫారమ్-ఎంపిక చేసిన స్టోర్ ఫసాడ్ ద్వారా వెళ్తుంది; కాల్ సైట్‌లు ప్లాట్‌ఫారమ్‌పై ఎప్పుడూ శాఖలు చేయవు.

**macOS**: క్రెడెన్షియల్‌లు జెనరిక్-పాస్‌వర్డ్ అంశాలుగా లాగిన్ కీచైన్‌లో ఉంటాయి, Claude Code స్వయంగా వాటిని ఉంచే చోటుతో సరిపోతూ. లైవ్ అంశం claude చదివేది; ప్రతి పూల్ చేసిన ఖాతా బ్యాకప్ దాని స్వంత `tokenmaxxing-cred-<uuid8>` కీచైన్ అంశంగా పార్క్ చేయబడుతుంది. డిస్క్‌పై ఏదీ ప్లెయిన్‌టెక్స్ట్ కాదు. చదవడాలు `security find-generic-password -w` ఉపయోగిస్తాయి (రహస్యం కేవలం stdoutపై మాత్రమే కనిపిస్తుంది); రాయడాలు stdin ద్వారా `add-generic-password` లైన్‌ను `security -i`లోకి పైప్ చేస్తాయి, తద్వారా రహస్యం ఏ ప్రాసెస్ argvలో ఎప్పుడూ కనిపించదు. ఇంటరాక్టివ్ మోడ్‌కు సుమారు 4 KB లైన్ బఫర్ ఉంది, కాబట్టి పెద్ద పరిమాణపు బ్లాబ్‌లు argv రైట్‌కు తిరిగివస్తాయి - పార్క్ చేసిన అంశాలు కేవలం కనీస OAuth ఆబ్జెక్ట్‌ను మాత్రమే నిల్వ చేయడానికి ఒక కారణం.

**Linux**: Claude Code క్రెడెన్షియల్‌లను 0600 ప్లెయిన్‌టెక్స్ట్ ఫైల్‌గా నిల్వ చేస్తుంది, మరియు tokenmaxxing అదే నమూనాను అనుసరిస్తుంది: లైవ్ ఫైల్ claude యొక్క స్వంత `.credentials.json`, మరియు పార్క్ చేసిన బ్యాకప్‌లు 0700 డైరెక్టరీలోని `~/.config/tokenmaxxing/creds/` కింద ఆటమిక్ 0600 ఫైల్‌లు. ఇక్కడ ఆటమిక్ అంటే తాత్కాలికంలోకి-రాయడం, fsync, ఆపై పేరుమార్చడం: ఏకకాల రీడర్ ఎల్లప్పుడూ పూర్తి పాత లేదా పూర్తి కొత్త ఫైల్‌ను చూస్తుంది, పాక్షికంగా ఎప్పుడూ కాదు.

మార్పిడి అమలు చేసే భద్రతా నియమాలు:

- **నిజమైన యజమాని ద్వారా సేకరణ.** మార్పిడికి ముందు, టోకెన్ ఏ సంస్థకు చెందుతుందో API నుండి అడగడం ద్వారా (OAuth roles ఎండ్‌పాయింట్‌పై `fetchTokenOrg`) లైవ్ క్రెడెన్షియల్ వాస్తవ యజమాని పరిష్కరించబడతాడు - మారగలిగే నిల్వ చేసిన క్రియాశీల లేబుల్‌ను నమ్మడం ద్వారా ఎప్పుడూ కాదు. మారిపోయిన లేబుల్ ఒకసారి ఒక ఖాతా సేకరణ మరో ఖాతా ఏకైక బ్యాకప్‌ను దిద్దివేసేలా చేసింది. లైవ్ క్రెడెన్షియల్ పూల్ వెలుపలి ఖాతాకు చెందితే, మార్పిడి దాన్ని దిద్దివేయడం కంటే పూర్తిగా తిరస్కరిస్తుంది.
- **ఒక క్రిటికల్ సెక్షన్.** సేకరణ, కొత్త క్రెడెన్షియల్ ఇన్‌స్టాల్, దాని తిప్పబడిన టోకెన్ బ్యాకప్, `~/.claude.json` ఖాతా మార్పిడి, మరియు క్రియాశీల-లేబుల్ కమిట్ అన్నీ ఒకే లాక్ చేసిన సెక్షన్ లోపల జరుగుతాయి.
- **claude యొక్క స్వంత రిఫ్రెష్‌తో ఇంటర్‌లాక్.** గడువు-సమీపంలో ఉన్న సెషన్ ఏ క్షణంలోనైనా తన స్వంత టోకెన్‌ను తిప్పగలదు, కాబట్టి క్రెడెన్షియల్ రైట్‌లు Claude Code యొక్క రిఫ్రెష్ లాక్‌ను కూడా తీసుకుంటాయి (బెస్ట్-ఎఫర్ట్, పాత-లాక్ తిరిగి పొందడం మరియు పరిమిత టైమ్‌అవుట్‌తో).
- **చనిపోయిన గ్రాంట్‌లు శుభ్రంగా తగ్గుతాయి.** `invalid_grant`గా తిరిగివచ్చే రిఫ్రెష్ ఆ ఖాతాను తిరిగి-ప్రామాణీకరణ అవసరమని ఫ్లాగ్ చేసి, లోపం వ్యాప్తి చెందే ముందు ఫ్లాగ్‌ను నిల్వ చేస్తుంది, తద్వారా పునఃప్రయత్న లూప్‌లు అభ్యర్థి సమూహాన్ని కుదించి ముగుస్తాయి. `tokenmaxxing auth` ఫ్లాగ్ చేసిన ఖాతాను యథాస్థానంలో సరిచేస్తుంది, మరియు రిపేర్ చేయబడుతున్న ఖాతా కంటే వేరే ఖాతాపై దిగే లాగిన్‌ను తిరస్కరిస్తుంది.
- **టోకెన్ లాగింగ్ లేదు.** టోకెన్‌లు లాగ్‌లు, లోపాలు, లేదా అవుట్‌పుట్‌లో ఎప్పుడూ కనిపించవు. టోకెన్ మరియు వినియోగ ఎండ్‌పాయింట్‌ల నుండి వచ్చే లోప బాడీలు ఎప్పుడూ ముడి రూపంలో బయటపెట్టబడవు; కేవలం అనుమతించబడిన ఫీల్డ్‌ల సమూహం మాత్రమే నిలుస్తుంది, ఎందుకంటే ఒక టోకెన్ ఎండ్‌పాయింట్ యొక్క వైఫల్య బాడీ అభ్యర్థన పదార్థాన్ని ప్రతిధ్వనించగలదు.
- **ప్రోబ్ పరిశుభ్రత.** స్పాన్ చేయబడిన ఏ `claude` ప్రోబ్ అయినా claude తన కీచైన్ లుకప్‌కు ముందు గౌరవించే ఎనిమిది ఎన్విరాన్‌మెంట్ వేరియబుల్‌లను (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, మొదలైనవి) శుభ్రం చేస్తుంది, తద్వారా ఒక ప్రోబ్ తప్పు ఖాతాకు ఎప్పుడూ ఆపాదించబడదు.

## ప్లాట్‌ఫారమ్ గమనికలు: macOS vs Linux

| | macOS | Linux |
|---|---|---|
| లైవ్ క్రెడెన్షియల్ | లాగిన్ కీచైన్ జెనరిక్-పాస్‌వర్డ్ అంశం | 0600 `.credentials.json` ఫైల్ |
| పార్క్ చేసిన క్రెడెన్షియల్‌లు | ప్రతి-ఖాతా కీచైన్ అంశాలు | 0700 డైరెక్టరీలో 0600 ఫైల్‌లు |
| మార్పిడి తర్వాత స్వీకరణ | ~30 సెకన్లలో (కీచైన్ రీడ్ కాష్) | తదుపరి అభ్యర్థన (ఫైల్ mtime పోల్) |
| ఆవర్తన తనిఖీ | launchd ఏజెంట్, ప్రతి 180సె | systemd యూజర్ టైమర్, ప్రతి 180సె |
| వేరుచేసిన-లాగిన్ స్టోర్ | కాన్ఫిగ్ డైర్‌కు హాష్-నేమ్‌స్పేస్ చేసిన కీచైన్ సేవ | వేరుచేసిన కాన్ఫిగ్ డైర్ లోపల ఒక ఫైల్ |

తెలుసుకోదగిన రెండు Linux-నిర్దిష్ట వివరాలు: claude తన క్రెడెన్షియల్ డైరెక్టరీని మొదట `CLAUDE_SECURESTORAGE_CONFIG_DIR` నుండి (ఆపై `CLAUDE_CONFIG_DIR`, ఆపై `~/.claude`) పరిష్కరిస్తుంది, మరియు tokenmaxxing ఆ పరిష్కారాన్ని సరిగ్గా ప్రతిబింబిస్తుంది, తద్వారా ఆ రెండూ ఎప్పుడూ డీసింక్ కావు. మరియు అదే claude వెర్షన్ యొక్క రెండు OS బిల్డ్‌లు `/usage` రీసెట్ గడియారాలను వేర్వేరుగా ఫార్మాట్ చేస్తాయి (ఒకటి " at " గ్లూను ఉపయోగిస్తుంది, మరొకటి కామాను); tokenmaxxing యొక్క పార్సర్ సరిగ్గా ఆ రెండు రూపాలను స్వీకరిస్తుంది మరియు ఏదైనా మూడవదానిపై ఊహించే బదులు లాగ్ చేస్తుంది.

macOS పై, ఒక నిజాయితీ పరిమితి: `init` మరియు `add` ఉద్దేశపూర్వకంగా కీచైన్‌ను ఇంటరాక్టివ్‌గా తాకుతాయి, తద్వారా మొదటి `security` యాక్సెస్ ఒక హెడ్‌లెస్ హుక్ లోపల చల్లగా ఉండదు.

## statusline

tokenmaxxing Claude Code యొక్క statuslineను స్థానికంగా రెండర్ చేస్తుంది (వినియోగ ఫీడ్‌ను టీ చేస్తూనే). రూపకల్పన సూత్రం: కోటా సంఖ్యలలో కాదు, రంగులో మోయబడుతుంది. ఉదాహరణకు, ఒక లైన్:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- ప్రతి విండో టోకెన్ దాని రీసెట్-వరకు-సమయం, వాడిన శాతం ద్వారా నిరంతర ఆకుపచ్చ-నుండి-పసుపు-నుండి-ఎరుపు ర్యాంప్‌పై చిత్రించబడుతుంది (టెర్మినల్ మద్దతిస్తే ట్రూకలర్, లేకపోతే 256-రంగుల క్యూబ్‌పైకి మెట్లుగా). ర్యాంప్ 0కి స్వచ్ఛమైన ఆకుపచ్చ వద్ద, 75 వద్ద పసుపు, మరియు 95 మరియు అంతకంటే ఎక్కువ వద్ద ఎరుపు వద్ద ఆంకర్ అవుతుంది, కాబట్టి పాత తీవ్రత బ్యాండ్‌లు ర్యాంప్ ఆంకర్‌లుగా నిలుస్తాయి.
- మోడల్ పేరు అదే ర్యాంప్‌పై కాంటెక్స్ట్-విండో ఫిల్ ద్వారా చిత్రించబడుతుంది.
- ఆకుపచ్చ `◆` క్రియాశీల ఖాతా విండోలకు ముందుంటుంది; ప్రతి పార్క్ చేసిన ఖాతాకు దాని స్వంత సియాన్ `◇` వస్తుంది (తిరిగి-ప్రామాణీకరణ అవసరమైతే ఎరుపు `✗`). ఖాతాలు త్వరగా రాబోయే రీసెట్ ప్రకారం క్రమబద్ధీకరించబడతాయి.
- ప్రతి బ్లాక్‌లో ప్రతి-మోడల్ ఒక ఒట్టి చిత్రించిన మొదటి అక్షరంగా ముందుగా వస్తుంది: Fable `𝒇`గా రెండర్ అవుతుంది; ఇతర కుటుంబాలు తమ పెద్ద-అక్షర మొదటి అక్షరాన్ని ఉపయోగిస్తాయి, ఎల్లప్పుడూ కుటుంబ-సరిపోల్చబడతాయి.
- తాకని పార్క్ చేసిన ఖాతా ఆకుపచ్చ `full`గా రెండర్ అవుతుంది. తెలియని రీసెట్‌తో కొలిచిన వినియోగం ఒక చిత్రించిన `?`గా రెండర్ అవుతుంది, మరియు గేట్ చేసిన మోడల్‌పై కొలవని ప్రతి-మోడల్ పరిమితి ఒక చిత్రించని `𝒇?`గా రెండర్ అవుతుంది - కొలవనిది ఎప్పుడూ సురక్షితంగా కనిపించకూడదు.
- రీసెట్ కౌంట్‌డౌన్‌లు అతిపెద్ద యూనిట్‌ను మాత్రమే చూపుతాయి, ఎప్పుడూ "now" లేదా "0m" కాదు; రాబోయే రీసెట్ లేని విండో ఆకుపచ్చ `0`గా రెండర్ అవుతుంది (మళ్ళీ ఖాళీ).
- లింక్ చేసిన git worktree యొక్క బేస్‌నేమ్ లైన్‌కు ముందుంటుంది; ప్రధాన చెక్‌అవుట్ అక్కడ ఏదీ రెండర్ చేయదు. గుర్తింపు `.git` ఫైల్ కోసం ఫైల్‌సిస్టమ్‌ను చదువుతుంది మరియు ఏ git సబ్‌ప్రాసెస్‌ను ఎప్పుడూ స్పాన్ చేయదు.
- `NO_COLOR` సెట్ చేసినప్పుడు, లైన్ ఒక అతికించిన సంఖ్యా ఫార్మాట్‌కు తిరిగివస్తుంది (`2h5` అంటే 2 గంటల్లో రీసెట్ అవుతుంది, 5% వాడబడింది; కాంటెక్స్ట్ ఫిల్ కోసం `ctx 42`) - రంగు లేకుండా, ఖాళీ అయిన విండో తాజాగా కనిపించకూడదు.

సబ్‌ఏజెంట్ టాస్క్‌లు claude యొక్క subagentStatusLine ఉపరితలం ద్వారా తమ స్వంత ప్యానెల్ వరుసలను పొందుతాయి: ప్రతి క్రియాశీల టాస్క్‌కు ఒక వరుస, ఆ టాస్క్ యొక్క కాంటెక్స్ట్ ఫిల్ ద్వారా చిత్రించిన కుటుంబ పేరు.

## Codex మద్దతు

అదే పూలింగ్ OpenAI యొక్క Codex CLI కోసం, మీ స్వంత ChatGPT-సబ్‌స్క్రిప్షన్ ఖాతాలపై పనిచేస్తుంది:

```sh
tokenmaxxing init --codex   # మీ ప్రస్తుత codex లాగిన్‌ను దిగుమతి చేయండి + codex సూపర్‌వైజర్ & Stop హుక్‌ను ఇన్‌స్టాల్ చేయండి
tokenmaxxing add --codex    # మరో ఖాతాను వేరుచేసి లాగిన్ చేయండి - మీ ప్రాథమిక లాగిన్ తాకబడదు
codex                       # ఎప్పటిలాగే codex వాడండి
```

Codex పూల్ పూర్తిగా సమాంతర స్థితి: దాని స్వంత ఖాతాల ఇండెక్స్, దాని స్వంత పార్క్ చేసిన క్రెడెన్షియల్ ఫైల్‌లు (రెండు ప్లాట్‌ఫారమ్‌లపై 0600 ఫైల్‌లు, ఎందుకంటే codex యొక్క స్వంత స్టోర్ ఒక ప్లెయిన్‌టెక్స్ట్ ఫైల్), దాని స్వంత లాక్, దాని స్వంత చివరి-మార్పిడి టైమ్‌స్టాంప్. నిర్ణయ-విధాన కోడ్ తప్ప Claude పూల్‌తో ఏదీ పంచుకోబడదు.

### Codex పై హాట్-స్వాప్ ఎందుకు అసాధ్యం

నడుస్తున్న codex ప్రాసెస్ ఒక ఇన్-మెమరీ auth మేనేజర్‌ను కలిగి ఉంటుంది మరియు `auth.json` ఇప్పుడు వేరే ఖాతాను పేర్కొన్నప్పుడు దాన్ని తిరిగి లోడ్ చేయడాన్ని స్పష్టంగా తిరస్కరిస్తుంది. ఏ ఫైల్ వాచర్ లేదు మరియు ప్రతి-అభ్యర్థన క్రెడెన్షియల్ పోల్ లేదు, కాబట్టి నడుస్తున్న codex కింద మార్చబడిన క్రెడెన్షియల్ ఇన్ఫరెన్స్ కోసం ఎప్పుడూ అమలులోకి రాదు. పునఃప్రారంభమే మార్పిడి: `codex resume <session-id>` `auth.json` ఇప్పుడు కలిగి ఉన్న ఏ ఖాతాపైనైనా స్థానిక ట్రాన్‌స్క్రిప్ట్‌ను కొనసాగిస్తుంది.

tokenmaxxing దీన్ని ఒక codex సూపర్‌వైజర్ షిమ్‌తో నిర్వహిస్తుంది: Stop హుక్ ప్రతి టర్న్ సరిహద్దు వద్ద అదే అత్యాశ వేగ-ఒత్తిడి నిర్ణయాన్ని నడుపుతుంది, మరియు అది మారినప్పుడు, సూపర్‌వైజర్‌ను కమిట్ చేసిన సరిహద్దు వద్ద సెషన్‌కు SIGTERM పంపి, ట్రాన్‌స్క్రిప్ట్ చెక్కుచెదరకుండా తాజా ఖాతాపై `codex resume <session-id>`ను తిరిగి ప్రారంభించేలా చేసే ఒక మార్కర్‌ను రాస్తుంది. ప్రతి codex మార్పిడి కనిపించే పునఃప్రారంభం కాబట్టి, codex అత్యాశ మార్గం 1.2x మెరుగుదల మార్జిన్‌ను కలిగి ఉంటుంది: ఒక సవాలుదారు ప్రస్తుత ఖాతా వేగ ఒత్తిడిని 20% మించాలి, ఏ కొంచెంతోనూ కాదు. కఠిన మార్గం (దాటిన బార్) మార్జిన్‌ను విస్మరిస్తుంది. codex కోసం ఖాళీ-పూల్ కౌంట్‌డౌన్ కూడా లేదు - codex సెషన్‌ను ఏదీ నిలిపివేయలేదు - కాబట్టి పూర్తిగా ఖాళీ అయిన codex పూల్ అక్కడే ఉంటుంది.

ఇతర codex-నిర్దిష్ట యంత్రాంగాలు:

- వినియోగం codex యొక్క స్వంత రేట్-లిమిట్ ఎండ్‌పాయింట్‌పై ఒక ఉచిత ప్రామాణీకరించిన GET నుండి చదవబడుతుంది (CLI యొక్క `/status` చేసే అదే కాల్): శాతాలు అలాగే సంపూర్ణ ఎపోక్ రీసెట్ సమయాలు, మొత్తం విండోలు మరియు ప్రతి-మోడల్ పరిమితులు ఒకేలా. విండో వర్గీకరణ వ్యవధి-ఆధారితం, స్థానం-ఆధారితం ఎప్పుడూ కాదు, ఎందుకంటే ప్రస్తుత ప్లాన్‌లకు అస్సలు 5-గంటల విండో ఉండకపోవచ్చు మరియు వారపు విండో ప్రాథమిక స్లాట్‌లో ఉంటుంది.
- Codex రిఫ్రెష్ టోకెన్‌లు తిరుగుతాయి, మరియు భర్తీ చేయబడిన దాన్ని తిరిగి ఉపయోగించడం మొత్తం గ్రాంట్ కుటుంబాన్ని చంపుతుంది. ప్రతి తిప్పుడు తిరిగివచ్చిన క్షణంలోనే నిల్వ చేయబడుతుంది, క్రియాశీల ఖాతా ఎల్లప్పుడూ లైవ్ బ్లాబ్ ద్వారా మాత్రమే నమూనా చేయబడుతుంది (పాత పార్క్ చేసిన కాపీ ఎప్పుడూ కాదు), మరియు ప్రతి-సెషన్ ప్రెజెన్స్ ఫైల్‌లు లైవ్ సోదర సెషన్‌లో నడుస్తున్న ఖాతా ఎప్పుడూ మార్పిడి లక్ష్యం కాదని మరియు దాని పార్క్ చేసిన టోకెన్ ఎప్పుడూ రిఫ్రెష్ కాదని నిర్ధారిస్తాయి.
- Codexకు ఫైల్ క్రెడెన్షియల్ స్టోర్ అవసరం: కీరింగ్ స్టోర్ పిన్ చేయబడి ఉంటే `init --codex` వేగంగా విఫలమవుతుంది, మరియు `add --codex` వేరుచేసిన ఆన్‌బోర్డింగ్ హోమ్‌లోకి ఫైల్-మోడ్ సెట్టింగ్‌ను రాస్తుంది, తద్వారా లాగిన్ సేకరించదగినదిగా దిగుతుంది.
- ఒక మాన్యువల్ దశ: codex తనకు నమ్మమని చెప్పని హుక్‌లను దాటవేస్తుంది. `init --codex` తర్వాత, codexను ఒకసారి తెరిచి `/hooks` ద్వారా tokenmaxxing Stop హుక్‌ను నమ్మండి, లేకపోతే స్వయంచాలక-మార్పిడి నిశ్శబ్దంగా నిష్క్రియంగా ఉంటుంది. `init --codex` ఈ రిమైండర్‌ను ముద్రిస్తుంది.

```sh
tokenmaxxing serve                          # డెమన్‌ను నడుపుతుంది
```

లింక్ చేసిన ఛానెల్‌లో బాట్‌ను మెన్షన్ చేయండి, అది ఆ థ్రెడ్ కోసం, లింక్ చేసిన రెపో చెక్‌అవుట్‌లో ఒక Claude Code సెషన్‌ను తెరుస్తుంది. ప్రతి థ్రెడ్ సందేశం `resume`తో ఒక Agent SDK `query()`ను నడుపుతుంది - నిరంతర స్ట్రీమింగ్ క్వెరీ ఎప్పుడూ కాదు - కాబట్టి `ensureBestAccount()` ప్రతి ఒక్క టర్న్‌లో పూల్‌ను తిరిగి మూల్యాంకనం చేస్తుంది మరియు డెమన్ థ్రెడ్‌లను కోల్పోకుండా పునఃప్రారంభించగలదు (థ్రెడ్ రికార్డ్‌లు మన్నికైనవి; డెమన్ ప్రారంభంలో వాటిని తిరిగి సబ్‌స్క్రైబ్ చేస్తుంది).

గమనార్హమైన ప్రవర్తన:

- **స్ట్రీమింగ్**: జవాబులు Slackలోకి స్థానికంగా స్ట్రీమ్ అవుతాయి, ఆలోచన మరియు టూల్ రన్‌ల కోసం టాస్క్ కార్డ్‌లతో, హైలైటింగ్‌తో రెండర్ చేయబడిన ఫెన్స్ కోడ్‌తో, ఖర్చు మరియు వ్యవధితో ముగింపు "Turn" కార్డ్‌తో, మరియు ఒక టూల్ రన్ స్ట్రీమ్ చేసిన టెక్స్ట్‌ను అడ్డగించినప్పుడల్లా కొత్త Slack సందేశం తెరవబడుతుంది, తద్వారా ఒక టర్న్ టూల్ రన్‌ల చుట్టూ వేర్వేరు సందేశాలుగా చదవబడుతుంది. TodoWrite కాల్‌లు ఒక స్థిరమైన చెక్‌లిస్ట్ కార్డ్‌ను యథాస్థానంలో అప్‌డేట్ చేస్తాయి.
- **అనుమతులు**: ప్రతి-లింక్ `permissionMode` డిఫాల్ట్‌గా `acceptEdits`; `--yolo` (మారుపేరు `--dangerous`) ఒక లింక్‌ను `bypassPermissions`లోకి ఎంచుకుంటుంది. రిలే చేసిన టర్న్‌లలో ఇంటరాక్టివ్ డైలాగ్‌లు అనుమతించబడవు - Slack ద్వారా ఎవరూ దానికి సమాధానం ఇవ్వలేరు - కాబట్టి మోడల్ గద్యంలో అడుగుతుంది మరియు మీ థ్రెడ్ జవాబు తదుపరి టర్న్ అవుతుంది. ఒక బండిల్ చేసిన ప్లగిన్ స్కిల్ దానికి నిర్ణయం అవసరమైనప్పుడు అభ్యర్థించినవారిని ట్యాగ్ చేసి టర్న్‌ను ముగించమని నేర్పుతుంది.
- **స్లాష్ కమాండ్‌లు**: తొలగించిన టెక్స్ట్ `/`తో ప్రారంభమయ్యే థ్రెడ్ సందేశం ఒక claude స్లాష్ కమాండ్‌గా నడుస్తుంది. Slack యొక్క కంపోజర్ `/`తో ప్రారంభమయ్యే సందేశాలను తినేస్తుంది, కాబట్టి మెన్షన్-మొదట రూపాన్ని (`@bot /usage`) లేదా ముందు ఒక ఖాళీని ఉపయోగించండి.
- **సున్నితమైన షట్‌డౌన్**: SIGTERM/SIGINT డ్రెయిన్ చేస్తుంది - కొత్త టర్న్‌లు గట్టిగా వదిలివేయబడతాయి, ప్రయాణంలో ఉన్న టర్న్‌లకు 5 నిమిషాల వరకు సమయం లభిస్తుంది, మరియు claude చైల్డ్ దాని స్వంత ప్రాసెస్ గ్రూప్‌లో విడిగా నడుస్తుంది, తద్వారా డ్రెయిన్ టర్న్‌ను భద్రపరిచే ముందు టెర్మినల్ Ctrl-C దాన్ని చంపలేదు.
- **థ్రెడ్ శుభ్రపరచడం**: పని పూర్తయిందని మీరు చెప్పినప్పుడు, మోడల్ ఒక ఇన్-ప్రాసెస్ `finish_thread` టూల్‌ను పిలుస్తుంది; టర్న్ పూర్తిగా ముగిసిన తర్వాత, డెమన్ థ్రెడ్ రికార్డ్‌ను తొలగించి, అన్‌సబ్‌స్క్రైబ్ చేసి, ఒక నిర్ధారణను పోస్ట్ చేస్తుంది. కొత్త మెన్షన్ కొత్త సెషన్‌ను ప్రారంభిస్తుంది.
- **లోప పరిశుభ్రత**: టర్న్ లోపాలు కత్తిరించిన సందేశ-మాత్రమే టెక్స్ట్‌ను పోస్ట్ చేస్తాయి, ముడి లోప బాడీలను ఎప్పుడూ కాదు.

## Agent SDK ఉపరితలం

ప్యాకేజ్ యొక్క ప్రోగ్రామాటిక్ ఎంట్రీ (`exports["."]` `src/sdk.ts` వద్ద చూపుతుంది) మీ స్వంత పూల్ చేసిన ఖాతాలపై మీరు నిర్మించే ఏజెంట్‌ల కోసం tokenmaxxingను Claude Agent SDKతో జతచేస్తుంది. మీ యాప్ Bun కింద నడవాలి (tokenmaxxing TypeScript సోర్స్‌ను రవాణా చేస్తుంది మరియు `bun:ffi`ను ఉపయోగిస్తుంది).

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK ప్రతి `query()`కు ఒక claude సబ్‌ప్రాసెస్‌ను స్పాన్ చేస్తుంది మరియు స్పాన్ వద్ద ఒకసారి క్రెడెన్షియల్‌లను చదువుతుంది - statusline లేదు, క్వెరీ-మధ్య హాట్-స్వాప్ లేదు - కాబట్టి ఏకీకరణ సరిహద్దు-ఆధారితం:

- `ensureBestAccount()` CLI హుక్‌లు మరియు టైమర్ నడిపే ఖచ్చితమైన నిర్ణయం (బార్‌లు, వేగ ఒత్తిడి, కూల్‌డౌన్, అన్నీ షేర్ చేసిన కోడ్), ఎప్పుడూ ముందస్తుగా కాదు: ఒక SDK సెషన్‌ను ఖాళీ కౌంట్‌డౌన్ కోసం ఎప్పుడూ నిలిపివేయలేము.
- `pooledOptions()` `pathToClaudeCodeExecutable`ను అసలైన claude బైనరీకి పిన్ చేస్తుంది (సూపర్‌వైజర్ ర్యాపర్‌కు ఎప్పుడూ కాదు) మరియు ప్రతి పరిసర క్రెడెన్షియల్ ఓవర్‌రైడ్ శుభ్రం చేయబడిన పూర్తి భర్తీ `env`ను అందిస్తుంది. మీ యాప్ ఎన్విరాన్‌మెంట్‌లో `CLAUDE_CONFIG_DIR` లేదా `CLAUDE_SECURESTORAGE_CONFIG_DIR` సెట్ చేయబడితే అది వేగంగా విఫలమవుతుంది: Linux పై ఒక మార్పిడి అవి చూపే చోట లైవ్ క్రెడెన్షియల్‌ను రాస్తుంది, అదే సమయంలో శుభ్రం చేసిన సబ్‌ప్రాసెస్ డిఫాల్ట్ స్టోర్‌ను చదువుతుంది, ఒక నిశ్శబ్ద తప్పు-ఖాతా డీసింక్.
- `stopHookCheck` టర్న్ సరిహద్దుల వద్ద నిర్ణయాన్ని తిరిగి నడుపుతుంది; అది దింపే మార్పిడి తదుపరి స్పాన్‌లో అమలులోకి వస్తుంది. ఇది తిరిగి విసిరే బదులు తన స్వంత లోపాలను పట్టుకుంటుంది (stderr మరియు లాగ్‌కు లాగింగ్ చేస్తూ), ఎందుకంటే నిర్వహించని హుక్ మినహాయింపు ఏజెంట్‌ను అడ్డగించగలదు, మరియు విరిగిన మార్పిడి తనిఖీ కారణంగా ఒక టర్న్‌ను రద్దు చేయడం ప్రస్తుత ఖాతాను కొనసాగించడం కంటే ఎక్కువ ఖర్చవుతుంది.

`sdk.ts` Agent SDK నుండి ఏదీ దిగుమతి చేయదు; దాని విలువలు SDK యొక్క ఆప్షన్‌లలోకి నిర్మాణాత్మకంగా విస్తరిస్తాయి.

## బిల్డ్ మరియు పంపిణీ

npm ప్యాకేజీ TypeScript సోర్స్‌ను పంపుతుంది, బిల్డ్‌ను కాదు: `tokenmaxxing` బిన్ నేరుగా Bun షెబ్యాంగ్‌తో `src/main.ts`ను సూచిస్తుంది, మరియు Bun 1.2.6 లేదా అంతకంటే కొత్తది దాన్ని ఉన్నదున్నట్లే నడుపుతుంది. అందుకే Bun ఒక కఠినమైన అవసరం. రూపకల్పన ప్రకారం సంకలనం చేయబడిన బైనరీలు ఏవీ లేవు: ఒక ప్రారంభ విడుదల ప్రతి ప్లాట్‌ఫారమ్‌కు ఒకే 61 MB macOS బైనరీని పంపింది మరియు Linux పై `exec format error`తో విఫలమైంది, మరియు ప్రతి-ప్లాట్‌ఫారమ్ సంకలనం చేయబడిన ప్యాకేజీలకు ప్రతిదానికీ దాని స్వంత విడుదల పైప్‌లైన్ అవసరమవుతుంది, కాబట్టి సోర్స్-Bun-చే-నడపబడేది పంపిణీ నమూనాగా మారింది.

ప్యాకేజీ యొక్క `exports` మ్యాప్ పైన వివరించిన ప్రోగ్రామాటిక్ ఎంట్రీగా `src/sdk.ts`ను బహిర్గతం చేస్తుంది. విడుదలలు GitHub పై `v<version>`గా ట్యాగ్ చేయబడతాయి; CI ట్రస్టెడ్ పబ్లిషింగ్ (OIDC, ప్రొవెనెన్స్‌తో) ద్వారా npmకి ప్రచురిస్తుంది, మరియు ప్రచురణ గేట్ మొదట టైప్‌చెక్ మరియు పూర్తి పరీక్షా సూట్‌ను నడుపుతుంది.

## వ్యక్తిగత వినియోగం మరియు సేవా నిబంధనలు [#personal-use-and-terms-of-service]

tokenmaxxing మీకు స్వంతమైన ఖాతాలను, మీరే నడిపే సెషన్‌లు మరియు ఏజెంట్‌లలో పూల్ చేస్తుంది. ఆ పదజాలం ఉద్దేశపూర్వకమైనది: మూడవ-పక్ష ఉత్పత్తులు claude.ai లాగిన్ లేదా claude.ai రేట్ పరిమితులను అందించడానికి Anthropic అనుమతించదు, మరియు అందులో Agent SDKపై నిర్మించిన ఏజెంట్‌లు కూడా ఉన్నాయి. పూల్ చేసిన SDK ఉపరితలాన్ని, లేదా దానిపై నిర్మించిన దేనినైనా మూడవ పక్షాలకు రవాణా చేయవద్దు. tokenmaxxing OAuthను తిరిగి అమలు చేయడం లేదా API ట్రాఫిక్‌ను ప్రాక్సీ చేయడం కంటే కోటా డేటా కోసం CLI-మధ్యవర్తిత్వ `/usage` మార్గంపైనే ఉద్దేశపూర్వకంగా ఉంటుంది: ఇది ప్రాక్సీ కాదు, మరియు ఇది తాకే ఏకైక OAuth ఎండ్‌పాయింట్‌లు మార్పిడి సమయంలో ఉపయోగించే ప్రామాణిక రిఫ్రెష్ గ్రాంట్ మరియు ఒక టోకెన్ నిజంగా ఏ ఖాతాకు చెందుతుందో ధృవీకరించే చదవడం-మాత్రమే గుర్తింపు తనిఖీ (roles ఎండ్‌పాయింట్).

## నిజాయితీ పరిమితులు

- **ఒక చల్లని టర్న్.** ప్రాంప్ట్ కాష్ సంస్థ-పరిధిలో ఉంటుంది, కాబట్టి కొత్త ఖాతాపై మొదటి టర్న్ కాంటెక్స్ట్‌ను ఒకసారి తిరిగి అప్‌లోడ్ చేస్తుంది.
- **ఖాళీ-విరామ ఇబ్బంది.** పూర్తిగా ఖాళీ అయిన పూల్ మాత్రమే కౌంట్‌డౌన్ కోసం సెషన్‌ను ఆపుతుంది; ఆ క్షణంలో టైప్ చేసినదంతా కోల్పోతుంది.
- **స్వీకరణ ఆలస్యం.** macOS పై మార్పిడి జరిగిన ~30 సెకన్లలోని మొదటి టర్న్ ఇప్పటికీ పాత ఖాతాను కొలవవచ్చు; బార్‌ల వెసులుబాటు దాన్ని గ్రహిస్తుంది.
- **భాగస్వామ్య పేలుడు వ్యాసార్థం.** అన్ని డిఫాల్ట్-ప్రొఫైల్ సెషన్‌లు ఒకే లైవ్ క్రెడెన్షియల్‌ను పంచుకుంటాయి, కాబట్టి ఒక మార్పిడి వాటన్నింటినీ కలిపి కదిలిస్తుంది (ప్రతి ఒక్కటి యథాస్థానంలో స్వీకరిస్తుంది).
- **Linux పై ప్లెయిన్‌టెక్స్ట్ క్రెడెన్షియల్‌లు.** Claude Code స్వయంగా Linux క్రెడెన్షియల్‌లను 0600 ప్లెయిన్‌టెక్స్ట్ ఫైల్‌గా నిల్వ చేస్తుంది; tokenmaxxing యొక్క పార్క్ చేసిన కాపీలు అదే నమూనాను అనుసరిస్తాయి.

## సమస్య పరిష్కారం మరియు తరచుగా అడిగే ప్రశ్నలు

**`claude` పర్యవేక్షించబడుతున్నట్లు కనిపించడం లేదు.**
`tokenmaxxing doctor` నడపండి. షిమ్ PATH పరిష్కారాన్ని గెలవాలి; మీ షెల్ rcలోని `# tokenmaxxing PATH` లైన్ ప్రస్తుత bin డైరెక్టరీని చూపుతుందని మరియు అసలైన claude కంటే ముందు ఉందని తనిఖీ చేయండి. `doctor` `alias claude=...` లేదా ర్యాపర్‌ను నీడ చేసే `claude()` షెల్ ఫంక్షన్ గురించి, మరియు claude బైనరీని సంపూర్ణ మార్గం ద్వారా ప్రారంభించే మారుపేర్ల గురించి (అవి సూపర్‌వైజర్‌ను పూర్తిగా దాటవేస్తాయి) కూడా హెచ్చరిస్తుంది.

**Codex పై స్వయంచాలక-మార్పిడి ఎప్పుడూ జరగదు.**
Codex తనకు నమ్మమని చెప్పని హుక్‌లను దాటవేస్తుంది. codexను తెరిచి, `/hooks` నడిపి, tokenmaxxing Stop హుక్‌ను నమ్మండి. నమ్మకం హుక్ యొక్క హాష్‌పై రికార్డ్ చేయబడుతుంది, కాబట్టి హుక్ ఎప్పుడైనా సవరించబడితే అది తిరిగి మంజూరు చేయాలి.

**ఖాతా statuslineలో ఎరుపు `✗` చూపుతుంది.**
దాని రిఫ్రెష్ టోకెన్ చనిపోయింది (రద్దు చేయబడింది లేదా దాని బ్యాకప్ కింద నుండి తిప్పబడింది). దాన్ని యథాస్థానంలో తిరిగి ప్రామాణీకరించడానికి `tokenmaxxing auth <sel>` నడపండి; కమాండ్ మీకు ఏ ఇమెయిల్‌తో సైన్ ఇన్ చేయాలో చెబుతుంది మరియు వేరే ఖాతాపై దిగే లాగిన్‌ను తిరస్కరిస్తుంది.

**ఇది అత్యధిక మిగిలిన కోటా ఉన్న ఖాతాకు ఎందుకు మారదు?**
ఎందుకంటే అది కోటాను కోల్పోయే అత్యధిక ప్రమాదంలో ఉన్న ఖాతా కాదు. లక్ష్యం తన స్వంత వారపు వేగం కంటే అత్యంత వెనుకబడి ఉన్న ఖాతా: మిగిలిన శాతాన్ని దాని వారపు రీసెట్ వరకు ఉన్న సమయంతో భాగించగా వచ్చినది. సమాన మొత్తాలు మిగిలి ఉంటే అది త్వరగా వచ్చే గడువును మొదట, మరియు సమాన గడువుతో అత్యధిక మిగిలిన దాన్ని మొదట తీసుకోవడానికి కుదించబడుతుంది.

**ఇది ఇప్పుడే మారింది మరియు statusline ఇంకా పాత ఖాతాను చూపుతోంది.**
macOS పై ~30 సెకన్ల వరకు ఇది ఊహించదగినది: నడుస్తున్న సెషన్ తన తదుపరి క్రెడెన్షియల్-కాష్ రిఫ్రెష్‌లో మార్చబడిన క్రెడెన్షియల్‌ను స్వీకరిస్తుంది. సరిగ్గా ఈ కారణంగానే మార్పిడి తర్వాత 45 సెకన్ల పాటు వినియోగ టీ అణచివేయబడుతుంది.

**`status --force` దేనికైనా ఖర్చవుతుందా?**
అవును, ఉద్దేశపూర్వకంగా: ఇది ప్రతి ఖాతాకు ఒక కనీస కొలిచిన haiku అభ్యర్థనను పంపుతుంది, తద్వారా ప్రతి 5-గంటల సెషన్ విండో నిద్రాణంగా ఉండే బదులు ఆ క్షణంలో ప్రారంభమవుతుంది, తర్వాత తాజాగా నమూనా చేస్తుంది. ఒట్టి `status` మరియు `watch` ఎప్పుడూ పింగ్ చేయవు; `/usage` చదవడాలు ఉచితం. సర్వర్ వినియోగ ఫీడ్ తాజాగా తెరిచిన విండోను సెకన్ల నుండి నిమిషాల వరకు ఆలస్యం చేయగలదని గమనించండి, కాబట్టి పింగ్ తర్వాత వెంటనే చేసిన ప్రోబ్ ఇప్పటికీ పింగ్-ముందు స్థితిని చూపవచ్చు - `status` పింగ్ విఫలమైనట్లు నటించే బదులు ఒక గమనికను రెండర్ చేస్తుంది.

**`/usage` ప్రోబ్ క్రియాశీల ఖాతా కోసం ఏదీ తిరిగి ఇవ్వలేదు.**
అది తెలిసిన claude ప్రవర్తన: దాని అంతర్గత వినియోగ ఫెచ్ విఫలమైనప్పుడు లేదా రేట్-పరిమితం అయినప్పుడు, `/usage` శాతం లైన్‌లు లేకుండా కేవలం స్థానిక సెషన్ గణాంకాలను మాత్రమే ముద్రిస్తుంది. దీన్ని ఖచ్చితంగా నివారించడానికి tokenmaxxing క్రియాశీల ఖాతాను statusline పుష్ నుండి నమూనా చేస్తుంది మరియు పార్క్ చేసిన ఖాతాలను మాత్రమే ప్రోబ్ చేస్తుంది.

**నేపథ్య claude సెషన్‌లు.**
Claude యొక్క నేపథ్య డెమన్ అసలైన వెర్షన్ చేసిన బైనరీని సంపూర్ణ మార్గం ద్వారా స్పాన్ చేస్తుంది, PATH షిమ్‌లను దాటవేస్తూ, కాబట్టి నేపథ్య సెషన్‌లు పర్యవేక్షించబడవు. హుక్‌లు ఇంకా `settings.json` ద్వారా ప్రేరేపించబడతాయి, మరియు క్రెడెన్షియల్ స్వీకరణ, అలాగే ఆవర్తన టైమర్ మార్పిడిని కవర్ చేస్తాయి, కానీ వాటికి మార్కర్-ఆధారిత రీస్పాన్ లేదు.

**ఒకసారి ఏదో చాలా ప్రాసెస్‌లను స్పాన్ చేసింది. అది ఇప్పటికీ సాధ్యమేనా?**
సూపర్‌వైజర్ సరిగ్గా ఆ చారిత్రక వైఫల్యానికి వ్యతిరేకంగా (ఒక పాత ర్యాపర్ "అసలైన" claudeగా పిన్ చేయబడటం) పొరలుగా ఉన్న రికర్షన్ గార్డ్‌లను కలిగి ఉంది: 5 స్థాయిల వద్ద రద్దు చేసే ఎన్విరాన్‌మెంట్‌లోని ఒక లోతు సెంటినల్, డిస్క్‌పై ఒక స్పాన్-రేట్ లిమిటర్, tokenmaxxing యొక్క స్వంత bin డైరెక్టరీలోకి తిరిగి పరిష్కారమయ్యే ఏ అభ్యర్థినైనా తిరస్కరించే రియల్‌పాత్ గుర్తింపు తనిఖీలు, మరియు కాన్ఫిగర్ చేసిన claude మార్గం ఇక ఉనికిలో లేనప్పుడు ఒక కఠిన వైఫల్యం (నిశ్శబ్ద PATH స్కాన్ ఎప్పుడూ కాదు). `init` మరియు `doctor` దాన్ని పిన్ చేసే ముందు `--version` నడపడం ద్వారా ఒక అభ్యర్థి నిజంగా claude అని ధృవీకరిస్తాయి.

**అన్‌ఇన్‌స్టాల్ చేయడం.**
`tokenmaxxing uninstall` సూపర్‌వైజర్ షిమ్‌లను, సెట్టింగ్‌ల ఎంట్రీలను, మరియు ఆవర్తన టైమర్‌ను తొలగిస్తుంది, మరియు మీ ఖాతాలను, పార్క్ చేసిన క్రెడెన్షియల్‌లను చెక్కుచెదరకుండా ఉంచుతుంది. ఇది తనవిగా గుర్తించే statusline ఎంట్రీలను మాత్రమే తొలగిస్తుంది.
