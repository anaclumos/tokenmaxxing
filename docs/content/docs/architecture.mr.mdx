tokenmaxxing हा एकच मल्टी-कॉल एंट्री पॉइंट (`src/main.ts`) आहे जो त्या नावाने बोलावल्यावर `claude` पर्यवेक्षक म्हणून वागतो, अंतर्गत सबकमांड्सद्वारे हुक आणि statusline शिम्स सेवतो, आणि अन्यथा CLI डिस्पॅच करतो. तो थेट Bun अंतर्गत चालतो; npm पॅकेज TypeScript स्रोत पाठवते, बिल्ड नव्हे.

चलणारे भाग:

## पर्यवेक्षक शिम

`init` हा `claude` नावाचा २-ओळींचा शेल शिम `~/.config/tokenmaxxing/bin/` मध्ये लिहितो आणि ती डिरेक्टरी PATH वर प्रथम ठेवतो. जेव्हा तुम्ही `claude` टाइप करता, तेव्हा शिम पर्यवेक्षक चालवतो, जो खरी claude बायनरी वारसाहक्काने मिळालेल्या stdio आणि जतन केलेल्या `stty -g` टर्मिनल स्नॅपशॉटसह स्पॉन करतो. तो केवळ एक प्रक्रिया आणि टर्मिनल व्यवस्थापक आहे: तो कधीही API ट्रॅफिक प्रॉक्सी करत नाही आणि उड्डाणातील टोकन्सना कधीही स्पर्श करत नाही.

प्रिंट-मोड आवाहने (`claude -p`, `--version`, `--help`), नॉन-इंटरॲक्टिव्ह सबकमांड्स (`claude mcp`, `claude config`, वगैरे), आणि tokenmaxxing च्या स्वतःच्या प्रोब्स कोणत्याही सत्र व्यवस्थापनाशिवाय थेट पास होतात. इंटरॲक्टिव्ह सत्रासाठी, पर्यवेक्षक एक session id पिन करतो (एक तयार करतो, किंवा तुम्ही `--session-id` / `-r` / `-c` द्वारे दिलेला पुन्हा वापरतो), तुमचे लॉन्च फ्लॅग्ज टिकवतो जेणेकरून नंतरचे पुन्हा-लॉन्च ते पुन्हा चालवू शकेल, आणि नंतर त्या सत्राशी संबंधित respawn मार्कर फाइलवर लक्ष ठेवतो.

## statusline टी

Claude Code प्रत्येक टर्नला statusline च्या stdin मध्ये दर-मर्यादा डेटा (`rate_limits.five_hour` आणि `rate_limits.seven_day`) पाठवते. tokenmaxxing statusline स्लॉटचे मालक आहे, त्यामुळे त्याचे रेंडरर एक मुक्त, पुश-आधारित वापर फीड म्हणून दुहेरी काम करते: प्रत्येक टिकला ते एकत्रित विंडोज तसेच सक्रिय मॉडेल `usage.json` मध्ये टी करते. प्रति-मॉडेल मर्यादा statusline stdin मध्ये नसतात; त्या फक्त `claude -p '/usage'` (मुक्त, शून्य टोकन्स) कडून येतात, जे TTL सह पोल केले जाते आणि सक्रिय मॉडेल क्षमता-मर्यादित असताना `model-usage.json` मध्ये कॅश केले जाते.

टी बदल-झाल्यावर-लिहिणारी आहे: जेव्हा आकडे अपरिवर्तित असतात तेव्हा ती फक्त फाइलचा mtime वाढवते, जो फीडचा जिवंतपणा दर्शवणारा ठोका म्हणून काम करतो. ताजेपणा नेहमी mtime द्वारे ठरवला जातो, अंतर्भूत टाइमस्टॅम्पद्वारे कधीही नाही.

## Stop हुक आणि बदल

प्रत्येक टर्न सीमेवर, Stop हुक बदल निर्णय चालवतो (पहा [बदल कसा ठरवला जातो](/mr/switching)). जेव्हा बदल आवश्यक असतो, तेव्हा तो `flock(2)` अनन्य लॉकखाली होतो (`bun:ffi` द्वारे घेतलेला, कारण macOS कोणतीही `flock(1)` बायनरी पाठवत नाही), आणि क्रेडेन्शियल लेखन Claude Code च्या स्वतःच्या रीफ्रेश लॉकशी अतिरिक्तपणे इंटरलॉक करते. क्रिटिकल सेक्शनच्या आत, एक बदल:

1. सध्याचे थेट क्रेडेन्शियल त्याच्या खऱ्या मालकाच्या पार्क केलेल्या बॅकअपमध्ये संकलित करतो.
2. लक्ष्य खात्याचे ताजे रीफ्रेश केलेले क्रेडेन्शियल थेट म्हणून स्थापित करतो, विद्यमान थेट ब्लॉबमध्ये विलीन करतो जेणेकरून सहचर स्थिती (जसे की प्रति-MCP-सर्व्हर OAuth टोकन्स) टिकून राहील. (लक्ष्याचे फिरवलेले रीफ्रेश टोकन रीफ्रेश परत आल्याच्या क्षणीच त्याच्या स्वतःच्या बॅकअपमध्ये आधीच टिकवले गेले होते, flock खाली पण या रीफ्रेश-लॉक क्रिटिकल सेक्शनच्या आधी.)
3. `~/.claude.json` मधील `oauthAccount` फील्ड अणुरूपपणे पुन्हा लिहितो.
4. लॉक सुटण्याआधी नवीन सक्रिय लेबल कमिट करतो आणि जुने वापर स्नॅपशॉट्स साफ करतो. या फाइल्स एकत्रितपणे क्रॅश-अणुरूप असू शकत नाहीत, त्यामुळे एखादा क्रॅश मधली स्थिती मागे ठेवू शकतो; पुढचा बदल थेट क्रेडेन्शियलचा खरा मालक लेबलपासून स्वतंत्रपणे सोडवतो आणि आढळलेली कोणतीही तफावत लॉग करतो.

कारण सर्व डीफॉल्ट-प्रोफाइल सत्रे ते एकच थेट क्रेडेन्शियल सामायिक करतात, एकच बदल एकाच वेळी प्रत्येक सत्र स्थलांतरित करतो, आणि flock तसेच लॉकखाली पुन्हा-तपासणी शर्यत करणाऱ्या हुक्सना दोन खाती जाळण्यापासून रोखते.

## जागच्या जागी स्वीकार

चालू claude सत्र विनंत्यांदरम्यान त्याचे क्रेडेन्शियल स्टोअर पोल करते: macOS वर ते एका छोट्या कॅशद्वारे कीचेन पुन्हा वाचते आणि अॅक्सेस टोकन्सची तुलना करते; Linux वर ते क्रेडेन्शियल्स फाइलचा mtime स्टॅट करते आणि बदलावर त्याचे टोकन कॅश फ्लश करते. निव्वळ परिणाम असा की बदललेले क्रेडेन्शियल प्रत्येक चालू सत्राद्वारे macOS वर सुमारे ३० सेकंदांत आणि Linux वर अगदी पुढील विनंतीवर, कोणत्याही पुन्हा सुरू न करता स्वीकारले जाते. यामुळेच साधा बदल कोणताही मार्कर लिहीत नाही आणि कोणताही respawn ट्रिगर करत नाही - सत्र फक्त नवीन खात्यावर सुरू राहते. सत्रांतर्गत `/usage` तेच टोकन कॅश सामायिक करते, त्यामुळे त्याचे खाते प्रदर्शन स्वीकारासोबत बदलते.

## संपलेल्या पूलची प्रतीक्षा आणि स्वयं-पुन्हा-सुरू

फक्त जेव्हा पूलमधील प्रत्येक खाते त्याच्या बारांवर असते तेव्हाच Stop हुक respawn मार्कर लिहितो (मार्कर स्कीमाला `waitUntil` टाइमस्टॅम्प आवश्यक असतो; साधा बदल कधीही एक तयार करू शकत नाही). पर्यवेक्षक मार्कर पाहतो, आधीच-कमिट-केलेल्या टर्न सीमेवर त्याच्या मुलाला SIGTERM करतो (Stop हुक ट्रान्सक्रिप्ट डिस्कवर आल्यानंतर आणि claude निष्क्रिय असताना चालतो, त्यामुळे काहीही गमावले जात नाही), टर्मिनल पुनर्संचयित करतो, सर्वात लवकर रीसेटपर्यंत काउंटडाउन दाखवतो, आणि नंतर पुनर्प्राप्त खात्यावर `claude --resume <session-id>` पुन्हा-लॉन्च करतो. काउंटडाउनदरम्यान Ctrl-C लगेच पुन्हा सुरू करते. स्वयं-प्रतीक्षा `policy.maxWaitMs` (डीफॉल्ट १ तास) ने बांधलेली असते; त्यापलीकडे निर्णय प्रतीक्षा करण्याऐवजी पूल संपलेला असल्याचे नोंदवतो.

## नियतकालिक तपासणी टायमर

हुक्स फक्त टर्न सीमांवर फायर होतात, आणि एक लांब एजंटिक टर्न एकाही सीमेशिवाय एका विंडोला निरोगीपासून संपलेल्यापर्यंत जाळू शकतो. म्हणून `init` एक नियतकालिक टायमर देखील स्थापित करते - macOS वर launchd एजंट, Linux वर systemd यूजर टायमर - जो टर्न क्रियाकलापाकडे दुर्लक्ष करून दर ६० सेकंदांनी `tokenmaxxing check --if-due` चालवतो. तपासणी थेट खात्याच्या मोकळिकेवरून स्वतःची गती ठरवते: प्रत्येक बारापर्यंत भरपूर जागा असताना ती दर पाच मिनिटांनी मूल्यांकन करते, आणि एखाद्या बाराजवळ असताना प्रत्येक टिकला (पहा [बदल कसा ठरवला जातो](/mr/switching)).

## एक SessionStart हुक

जेव्हा सत्र सुरू होते किंवा पुन्हा सुरू होते तेव्हा तेच मूल्यांकन चालवते, जेणेकरून ताजे सत्र योग्य खात्यावर सुरू होईल. बदल-नंतरचा कूलडाउन respawn नंतर लगेच याला एक योग्य नो-ऑप बनवतो.
