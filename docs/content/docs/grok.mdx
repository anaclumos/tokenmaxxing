---
title: grok support
description: Pooling grok logins, placing each session on the freshest one, and resuming it on another near quota
---

tokenmaxxing pools grok subscription logins the way it pools Muse Code logins: each `grok` session starts on the pooled account with the most headroom, and an interactive session that nears its account's limit resumes on a fresher account.

```sh
tokenmaxxing init --grok          # pool the first grok login, install the grok supervisor
tokenmaxxing add --grok           # pool another one through an isolated login
grok                              # use grok as always
```

`init`, `add`, `auth`, `emails`, `rm`, and `rename` take `--grok`; every other command refuses the flag with exit code 2. `init --grok` verifies the real `grok` and pins its path (`grokBin` in `config.json`, overridden by `TOKENMAXXING_GROK_BIN`), writes the `grok` wrapper into the state directory's `bin/`, and puts that directory ahead of the real `grok` on `PATH` the way `init` does for `claude`.

## Accounts

An account is a grok CLI login. `init --grok` imports the first entry of `~/.grok/auth.json` (`GROK_HOME` is honored when it names no store) and points at `add --grok` for the rest; with no live login it runs `grok login` in a throwaway `GROK_HOME` under the state directory. `add --grok` and `auth --grok` always use the isolated login. Identity is the entry's user id (or `principal_id`, else the map key), the label defaults to the email in the entry, and the harvested entry is written verbatim to `grok-stores/<uuid8>/auth.json` at mode 0600. A store is usable when that entry holds a `refresh_token`.

## The seat

grok reads its login from `$GROK_HOME/auth.json` (`~/.grok` when `GROK_HOME` is unset), so a seat is a `GROK_HOME`: the account's store directory. `XAI_API_KEY` is not used, because it overrides the account login. Every tool a seated session runs inherits that `GROK_HOME`, so the store mirrors the real grok home (`GROK_HOME` when it is set and names no store, else `~/.grok`; a seated child also carries the real home in `TOKENMAXXING_GROK_HOME`, so a launch from inside a seat mirrors the same one, and a launch that gets no seat restores it as `GROK_HOME`): before each launch it gets a symlink to every entry of the real home except `auth.json` and `auth.json*` lock files. Sessions, plugins, and the rest stay shared, so `-c` and `-r` work across stores. An entry a seated tool creates under `GROK_HOME` when the real home has none of that name lands in the store. Several sessions can share one account: grok takes `auth.json.lock` in the store.

## Placement

The wrapper sorts each launch into one of three modes.

| Launch | Mode |
| --- | --- |
| `grok`, `grok <prompt>`, `grok -c`, `grok -r ...` on a terminal | Supervised: seated, watched, and moved near quota |
| The same without a terminal, or with `-p` / `--single` / `--prompt-file` / `--prompt-json` | Seated for its whole life, never moved |
| `grok agent ...`, `grok dashboard` | Seated for its whole life, never moved |
| Any launch whose parent already runs on a pooled seat (a `grok` a seated session starts) | Keeps that seat and records its own presence, never moved |
| `--help`, `--version`, any other subcommand (`login`, `logout`, `usage`, `sessions`, ...), `XAI_API_KEY` set, or `TOKENMAXXING_UNMANAGED` set | Passthrough on the ambient login |

A seated launch first reads the usage of every usable account whose sample is older than `policy.usagePollTtlMs`, then picks the account with the most headroom under the bars, counting the sessions already on each account so equal accounts share the load; when every account is at its bars it picks the one that frees up first. grok reports only the weekly subscription credit window, so its accounts rank as weekly-only in [the ranking](/switching#session-window-first). With accounts pooled but none usable, the launch says so on stderr and runs on the ambient login. It writes a presence file to `grok-live/`, keyed to the child's pid, so `status` counts the session and `rm` refuses the account.

## Moves

A supervised session's seat is checked every 10 seconds. The check reads the seat's usage once the stored sample is older than `policy.usagePollTtlMs` (60 seconds after an unmeasured read), and when the seat is at its bars, or its login was rejected, it re-reads every other account's stale usage and runs the same decision as a Muse Code move. Placement, the child's spawn, and its presence file share one hold of the pool lock, so `rm --grok` never removes an account a launch is taking. A new interactive session is started with `-s <uuid>` so the supervisor already knows the session id. With a fresher account available, it stops the child with SIGTERM (SIGKILL after 30 seconds) and starts `grok -r <session id>` on the new account with the first launch's root flags, minus the prompt, `-p` / `--single`, `--prompt-file`, `--prompt-json`, `--cwd`, `--session-id`, and the worktree flags. `grok -c` and a bare `grok -r` resume the newest session for the working directory, found by `summary.json` mtime under `~/.grok/sessions/<urlencoded-cwd>/`. A turn that was running when the move landed stops; send it again. When the session id is still unknown, the move is skipped and logged as `groksupervisor.session_unresolved`. With every account at its bars, the session stays where it is. `grok agent` (including ACP `grok agent stdio`) keeps the account it started on: a mid-session JSON-RPC replay is out of scope.

`check` and the periodic timer do not sample the pool: a seated launch and the supervisor read the usage they need. `doctor` checks the pinned `grok`, its place on `PATH`, and that each store holds a login of its account. `uninstall` removes `bin/grok` and keeps the stores.

## Usage

Usage is the weekly subscription credit window from `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` (`creditUsagePercent`, classified by the period's duration). The endpoint leaves `creditUsagePercent` out while the period's use is 0, so a credits body without it reads as 0%. `TOKENMAXXING_GROK_USAGE_URL` overrides that URL for hermetic runs. The dollar billing body (`GET /v1/billing` without `format=credits`) is not quota: subscription accounts report `monthlyLimit` 0 there while credits remain, and a parser that treats that body as usage reports the account depleted. tokenmaxxing does not refresh grok tokens; a stored access token that has expired is retried against the live `GROK_HOME` login when that login is the same account. A 401 flags the account for `auth --grok`. A failed read does not write the dollar body: an account with no stored window stays unmeasured, and one with a stored credits window keeps that figure as stale as it was.

## What status shows

The grok pool renders after Codex, headed `grok  (N accounts)` and skipped when empty, and `status --json` always carries it under `grok`. Each account renders the buffered weekly credit bar once a sample has landed, `usage.week` carries that window, `sessions` counts the seated sessions, and `exhausted` follows the same bars as the other pools; an unmeasured account has `usage` null and `exhausted` `false`. `status` shows `sampling grok usage...` on a terminal while the check runs, erases it, then reports `live sample failed` when the read fails (run `auth --grok` when the store has no usable credential); `status --cached` skips the check and notes `never sampled` when nothing is stored.

## State

| Path | What it holds |
|---|---|
| `grok-accounts.json` | The pool index, the same schema as `accounts.json`; it names no active account |
| `grok-lock` | The `flock` file that serializes the pool's commands and launches |
| `grok-stores/<uuid8>/` | The account's seat: the `GROK_HOME` of the sessions on it, with the mirror links |
| `grok-stores/<uuid8>/auth.json` | The account's 0600 login |
| `grok-live/<id>` | One presence file per seated session |
| `bin/grok` | The wrapper that runs `tokenmaxxing __supervise-grok` |
| `onboard/grok-<pid>-<random>/` | The throwaway `GROK_HOME` of one isolated login, deleted after it |
