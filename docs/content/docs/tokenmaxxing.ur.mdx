tokenmaxxing خودکار Claude Code اکاؤنٹ سوئچنگ کے لیے ایک CLI ہے۔ یہ آپ کے متعدد ذاتی سبسکرپشن (Pro/Max) اکاؤنٹس کو پول کرتا ہے اور جب زیرِ استعمال اکاؤنٹ کسی استعمال کی حد کے قریب پہنچتا ہے تو فعال کریڈنشل کو ایک تازہ اکاؤنٹ پر ہاٹ سوئپ کر دیتا ہے۔ آپ `claude` کو بالکل اسی طرح چلاتے ہیں جیسے ہمیشہ چلاتے ہیں؛ سوئپ ایک محفوظ ٹرن باؤنڈری پر ہوتا ہے اور آپ کا رواں سیشن دوبارہ شروع ہوئے بغیر نئے اکاؤنٹ پر وہی گفتگو جاری رکھتا ہے۔ یہ بیک وقت کئی متوازی سیشنز پر کام کرتا ہے۔

واحد نظر آنے والا رویہ بدترین صورت ہے: جب پورا پول اپنی حد پر ہوتا ہے، تو سیشن ایک کاؤنٹ ڈاؤن کے ساتھ رک جاتا ہے اور اگلے ری سیٹ ہونے والے اکاؤنٹ پر خودکار طور پر دوبارہ شروع ہو جاتا ہے (Ctrl-C فوراً دوبارہ شروع کر دیتا ہے)۔

<Callout>
دائرہ کار: macOS اور Linux پر Claude Code، نیز OpenAI کا Codex CLI ایک دوسرے، متوازی پول کے طور پر۔ یہ سبسکرپشن اکاؤنٹس کو پول کرتا ہے، API کیز کو نہیں۔ یہ ایک ذاتی استعمال کا ٹول ہے جو آپ کے اپنے اکاؤنٹس کو ان سیشنز اور ایجنٹس میں پول کرنے کے لیے ہے جنہیں آپ خود چلاتے ہیں - دیکھیں [ذاتی استعمال اور سروس کی شرائط](#personal-use-and-terms-of-service)۔
</Callout>

## مسئلہ

ایک Claude سبسکرپشن بیک وقت تین حدوں کی پیمائش کرتی ہے (سب کی تصدیق `/usage` کے ذریعے ہوئی):

- **موجودہ سیشن**: ایک رولنگ 5 گھنٹے کی ونڈو۔
- **موجودہ ہفتہ (تمام ماڈلز)**: ایک 7 دن کا مجموعہ۔
- **موجودہ ہفتہ، فی ماڈل**: انفرادی ماڈل فیملیز کے لیے الگ ہفتہ وار حدیں۔ یہ فی الحال صرف Sonnet اور Fable کے لیے موجود ہیں، اور صرف Fable کی حد اتنی تنگ ہے کہ اہمیت رکھے - یہ مجموعے سے کہیں پہلے پابند ہو جاتی ہے۔ ایک مشین 50% ہفتہ-مجموعی پر بیٹھی رہ سکتی ہے جبکہ پہلے ہی 80% ہفتہ-Fable پر ہو۔

ہفتہ وار کوٹا "استعمال کرو ورنہ کھو دو" کی نوعیت کا ہے: کوئی اکاؤنٹ اپنے مقررہ ہفتہ وار ری سیٹ تک جو کچھ استعمال نہ کرے وہ ضائع ہو جاتا ہے۔ اگر آپ کے پاس کئی اکاؤنٹس ہیں، تو معقول حکمتِ عملی یہ ہے کہ اس اکاؤنٹ پر کوٹا خرچ کرتے رہیں جو اپنی ہفتہ وار رفتار سے سب سے زیادہ پیچھے ہو، اور کسی بھی واحد حد کے سیشن کے دوران دیوار سے ٹکرانے سے پہلے دوسرے اکاؤنٹ پر منتقل ہو جائیں۔

یہ کام ہاتھ سے کرنے کا مطلب ہے لاگ آؤٹ کرنا، لاگ اِن کرنا، اور اپنی گفتگو کھو دینا۔ tokenmaxxing اسے خودکار بناتا ہے: ایک رواں `claude` درخواستوں کے درمیان اپنے کریڈنشل اسٹور کو دوبارہ چیک کرتا ہے، لہٰذا اس کے نیچے سوئپ کیا گیا کریڈنشل اپنی جگہ اپنا لیا جاتا ہے (macOS پر تقریباً 30 سیکنڈ کے اندر، Linux پر اگلی درخواست پر)۔ ایک سادہ سوئپ کبھی آپ کا سیشن دوبارہ شروع نہیں کرتا۔ واحد صورت جس میں اب بھی پروسیس مینجمنٹ درکار ہوتی ہے وہ مکمل طور پر ختم ہو چکا پول ہے - ایک سیشن خود کو روک نہیں سکتا - اور یہی وہ کام ہے جس کے لیے پتلا سپروائزر موجود ہے۔

`claude` کے بارے میں باقی سب کچھ بدلا نہیں ہے: تمام فلیگز، MCP سرورز، ہکس، اور اسکلز بغیر کسی رکاوٹ کے گزر جاتے ہیں۔

## فوری آغاز

macOS یا Linux پر [Bun](https://bun.sh) اور Claude Code درکار ہیں۔

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` پانچ کام کرتا ہے:

1. جس اکاؤنٹ سے آپ پہلے ہی لاگ اِن ہیں اسے اکاؤنٹ #1 کے طور پر امپورٹ کرتا ہے (کوئی الگ `adopt` کمانڈ نہیں ہے)۔
2. `claude` سپروائزر شِم انسٹال کرتا ہے۔
3. Claude Code کی `settings.json` میں تین اندراجات انسٹال کرتا ہے: ایک statusLine، ایک Stop ہک، اور ایک SessionStart ہک (نیز ایک subagentStatusLine اندراج)۔
4. سپروائزر کی bin ڈائرکٹری کو آپ کے شیل rc کے PATH میں شامل کرتا ہے (idempotent، ایک `# tokenmaxxing PATH` تبصرے سے نشان زد)۔ اسے اصل `claude` سے پہلے PATH پر بیٹھنا پڑتا ہے تاکہ اسے روک سکے۔
5. ایک وقفہ وار چیک ٹائمر انسٹال کرتا ہے (macOS پر ایک launchd ایجنٹ، Linux پر ایک systemd یوزر ٹائمر) جو ہر 180 سیکنڈ میں `tokenmaxxing check` چلاتا ہے۔

اپنے شیل کو دوبارہ شروع کریں، پھر مزید اکاؤنٹس شامل کریں اور آگے بڑھیں:

```sh
tokenmaxxing add        # ایک اور اکاؤنٹ کو الگ تھلگ حالت میں لاگ اِن کر کے پول میں شامل کرتا ہے
claude                  # claude کو ہمیشہ کی طرح استعمال کریں
```

`tokenmaxxing` کا عرف `xx` بھی ہے۔ خالی `tokenmaxxing` (یا `xx`) `status` چلاتا ہے؛ `switch` واضح طور پر لکھنا لازم رہتا ہے۔

| کمانڈ | یہ کیا کرتی ہے |
|---|---|
| `tokenmaxxing init` | موجودہ اکاؤنٹ امپورٹ کریں، سپروائزر، ہکس، اور statusline انسٹال کریں |
| `tokenmaxxing init --codex` | Codex کے لیے وہی: لاگ اِن امپورٹ کریں، codex سپروائزر اور Stop ہک انسٹال کریں |
| `tokenmaxxing add` | ایک اضافی اکاؤنٹ رجسٹر کریں (الگ تھلگ لاگ اِن، پول میں سمیٹا گیا) |
| `tokenmaxxing add --codex` | ایک اضافی Codex اکاؤنٹ رجسٹر کریں (الگ تھلگ لاگ اِن) |
| `tokenmaxxing auth [sel \| --all]` | کسی پول شدہ اکاؤنٹ کی اپنی جگہ دوبارہ تصدیق کریں۔ خالی کمانڈ پول کی فہرست دیتی ہے اور پوچھتی ہے کہ کون سا؛ ایک سلیکٹر ایک اکاؤنٹ کو نشانہ بناتا ہے اور بتاتا ہے کہ کس ای میل سے سائن اِن کرنا ہے؛ `--all` ہر ری آتھ درکار اکاؤنٹ کو یکے بعد دیگرے چلاتا ہے |
| `tokenmaxxing switch [sel]` | بہترین اکاؤنٹ پر سوئچ کریں (لالچی، idempotent) یا کسی مخصوص اکاؤنٹ پر مجبور کریں |
| `tokenmaxxing switch --codex [sel]` | Codex پول کو سوئچ کریں (اگلے codex آغاز پر مؤثر ہوتا ہے) |
| `tokenmaxxing ls` | پول شدہ اکاؤنٹس کی فہرست بنائیں |
| `tokenmaxxing status` | 5h / ہفتہ وار / فی ماڈل استعمال بارز کے ساتھ اکاؤنٹس، فعال اور ری سیٹ تک ختم شدہ |
| `tokenmaxxing status --force` | اضافی طور پر ہر اکاؤنٹ کو پنگ کریں (ہر ایک پر ایک چھوٹی سی haiku درخواست) تاکہ تمام 5h سیشن ٹائمرز ابھی شروع ہو جائیں، پھر تازہ نمونہ لیں |
| `tokenmaxxing watch [seconds]` | لائیو اسٹیٹس، ہر N سیکنڈ میں دوبارہ رینڈر (پہلے سے طے شدہ 120، کم از کم 30؛ کبھی پنگ نہیں کرتا) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | ذرائع کے ساتھ مؤثر config؛ ڈوٹڈ کیز میں ترمیم کریں؛ `tidy` نامعلوم کیز کو صاف کرتا ہے |
| `tokenmaxxing check` | سوئچ فیصلے کا ایک بار جائزہ لیں (وقفہ وار ٹائمر یہی چلاتا ہے) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack برج ڈیمن (Socket Mode، کوئی عوامی URL نہیں) |
| `tokenmaxxing doctor` | تصدیق کریں کہ سپروائزر اور settings کے اندراجات باقی رہے |
| `tokenmaxxing rename [--codex] <sel> <label>` | کسی پول شدہ اکاؤنٹ کا لیبل دوبارہ لگائیں |
| `tokenmaxxing rm <sel>` | پول سے ایک اکاؤنٹ ہٹائیں |
| `tokenmaxxing uninstall` | سپروائزر اور settings کے اندراجات ہٹائیں (اکاؤنٹس اور کریڈنشلز محفوظ رہتے ہیں) |

## آرکیٹیکچر

tokenmaxxing ایک ہی ملٹی کال انٹری پوائنٹ (`src/main.ts`) ہے جو اس نام کے تحت پکارے جانے پر `claude` سپروائزر کے طور پر کام کرتا ہے، اندرونی سب کمانڈز کے ذریعے ہک اور statusline شِمز فراہم کرتا ہے، اور دیگر صورتوں میں CLI کو ڈسپیچ کرتا ہے۔ یہ براہ راست Bun کے تحت چلتا ہے؛ npm پیکج TypeScript سورس بھیجتا ہے، کوئی بلڈ نہیں۔

متحرک اجزاء:

### سپروائزر شِم

`init` ایک 2 لائن شیل شِم لکھتا ہے جس کا نام `claude` ہے، `~/.config/tokenmaxxing/bin/` میں، اور اس ڈائرکٹری کو PATH پر سب سے پہلے رکھتا ہے۔ جب آپ `claude` ٹائپ کرتے ہیں، تو شِم سپروائزر کو چلاتا ہے، جو اصل claude بائنری کو وراثتی stdio اور محفوظ کردہ `stty -g` ٹرمینل سنیپ شاٹ کے ساتھ اسپان کرتا ہے۔ یہ صرف ایک پروسیس اور ٹرمینل مینیجر ہے: یہ کبھی API ٹریفک پراکسی نہیں کرتا اور کبھی رواں ٹوکنز کو نہیں چھوتا۔

پرنٹ موڈ کالز (`claude -p`، `--version`، `--help`)، غیر انٹرایکٹو سب کمانڈز (`claude mcp`، `claude config`، وغیرہ)، اور tokenmaxxing کی اپنی پروبز بغیر کسی سیشن مینجمنٹ کے سیدھی گزر جاتی ہیں۔ ایک انٹرایکٹو سیشن کے لیے، سپروائزر ایک سیشن id پن کرتا ہے (ایک تیار کرتے ہوئے، یا وہ استعمال کرتے ہوئے جو آپ نے `--session-id` / `-r` / `-c` کے ذریعے پاس کیا)، آپ کے لانچ فلیگز کو محفوظ کرتا ہے تاکہ بعد میں دوبارہ لانچ انہیں دہرا سکے، اور پھر اس سیشن سے منسلک ایک ری اسپان مارکر فائل پر نظر رکھتا ہے۔

### statusline ٹی

Claude Code ہر ٹرن پر ریٹ لمٹ ڈیٹا (`rate_limits.five_hour` اور `rate_limits.seven_day`) statusline کے stdin میں پش کرتا ہے۔ tokenmaxxing statusline سلاٹ کا مالک ہے، لہٰذا اس کا رینڈرر ایک مفت، پش پر مبنی استعمال فیڈ کے طور پر بھی کام کرتا ہے: ہر ٹِک پر یہ مجموعی ونڈوز کے ساتھ ساتھ فعال ماڈل کو `usage.json` میں ٹی کرتا ہے۔ فی ماڈل حدیں statusline کے stdin میں نہیں ہیں؛ وہ صرف `claude -p '/usage'` سے آتی ہیں (مفت، صفر ٹوکنز)، جسے ایک TTL کے ساتھ پول کیا جاتا ہے اور جب فعال ماڈل صلاحیت کے لحاظ سے محدود ہو تو `model-usage.json` میں کیش کیا جاتا ہے۔

ٹی write-on-change ہے: جب اعداد بدلے نہ ہوں تو یہ صرف فائل کے mtime کو بمپ کرتا ہے، جو فیڈ کے liveness heartbeat کے طور پر کام کرتا ہے۔ تازگی ہمیشہ mtime سے پرکھی جاتی ہے، کبھی سرایت شدہ ٹائم اسٹیمپ سے نہیں۔

### Stop ہک اور سوئپ

ہر ٹرن باؤنڈری پر، Stop ہک سوئچ فیصلہ چلاتا ہے (دیکھیں [سوئچنگ کیسے فیصلہ کرتی ہے](#how-switching-decides))۔ جب کوئی سوئپ جواز رکھتا ہو، تو یہ ایک `flock(2)` خصوصی لاک کے تحت ہوتا ہے (جو `bun:ffi` کے ذریعے لیا جاتا ہے، کیونکہ macOS کوئی `flock(1)` بائنری نہیں بھیجتا)، اور کریڈنشل رائٹس اضافی طور پر Claude Code کے اپنے ری فریش لاک کے ساتھ انٹرلاک ہوتی ہیں۔ کریٹیکل سیکشن کے اندر، ایک سوئپ:

1. موجودہ لائیو کریڈنشل کو اس کے حقیقی مالک کے پارک شدہ بیک اپ میں سمیٹتا ہے۔
2. ہدف اکاؤنٹ کے تازہ ری فریش شدہ کریڈنشل کو لائیو کے طور پر انسٹال کرتا ہے، موجودہ لائیو بلاب میں ضم کرتے ہوئے تاکہ سبلنگ اسٹیٹ (جیسے فی MCP سرور OAuth ٹوکنز) باقی رہے۔
3. ہدف کے روٹیٹ شدہ ٹوکن کو اس کے اپنے بیک اپ میں محفوظ کرتا ہے۔
4. `~/.claude.json` میں `oauthAccount` فیلڈ کو ایٹمی طور پر دوبارہ لکھتا ہے۔
5. نئے فعال لیبل کو کمِٹ کرتا ہے اور باسی استعمال کے سنیپ شاٹس صاف کرتا ہے، یہ سب لاک کے چھوٹنے سے پہلے، تاکہ کوئی کریش کبھی انسٹال شدہ کریڈنشل اور فعال لیبل کو مختلف اکاؤنٹس کی طرف اشارہ کرتا نہ چھوڑ سکے۔

چونکہ تمام ڈیفالٹ پروفائل سیشنز ایک ہی لائیو کریڈنشل کا اشتراک کرتے ہیں، ایک واحد سوئپ بیک وقت ہر سیشن کو منتقل کر دیتا ہے، اور flock کے ساتھ لاک کے تحت دوبارہ چیک ریسنگ ہکس کو دو اکاؤنٹس جلانے سے روکتا ہے۔

### اپنی جگہ اپنانا

ایک رواں claude سیشن درخواستوں کے درمیان اپنے کریڈنشل اسٹور کو پول کرتا ہے: macOS پر یہ ایک مختصر کیش کے ذریعے کی چین کو دوبارہ پڑھتا ہے اور رسائی ٹوکنز کا موازنہ کرتا ہے؛ Linux پر یہ کریڈنشلز فائل کے mtime کو اسٹیٹ کرتا ہے اور تبدیلی پر اپنے ٹوکن کیشز کو فلش کرتا ہے۔ خالص اثر یہ ہے کہ ایک سوئپ شدہ کریڈنشل ہر رواں سیشن macOS پر تقریباً 30 سیکنڈ کے اندر اور Linux پر بالکل اگلی درخواست پر، بغیر کسی دوبارہ آغاز کے اپنا لیتا ہے۔ یہی وجہ ہے کہ ایک سادہ سوئپ کوئی مارکر نہیں لکھتا اور کوئی ری اسپان نہیں چلاتا - سیشن بس نئے اکاؤنٹ پر جاری رہتا ہے۔ سیشن کے اندر `/usage` وہی ٹوکن کیشز شیئر کرتا ہے، لہٰذا اس کا اکاؤنٹ ڈسپلے اپنانے کے ساتھ ہی بدل جاتا ہے۔

### ختم شدہ پول کا انتظار اور خودکار دوبارہ آغاز

صرف اسی وقت جب پول کا ہر اکاؤنٹ اپنی بارز سے تجاوز کر جائے تو Stop ہک ایک ری اسپان مارکر لکھتا ہے (مارکر اسکیما کو ایک `waitUntil` ٹائم اسٹیمپ درکار ہوتی ہے؛ ایک سادہ سوئپ کبھی ایسا پیدا نہیں کر سکتا)۔ سپروائزر مارکر دیکھتا ہے، اپنے چائلڈ کو پہلے سے کمِٹ شدہ ٹرن باؤنڈری پر SIGTERM کرتا ہے (Stop ہک اس وقت چلتا ہے جب ٹرانسکرپٹ ڈسک پر ہو اور claude فارغ ہو، لہٰذا کچھ ضائع نہیں ہوتا)، ٹرمینل بحال کرتا ہے، سب سے قریبی ری سیٹ تک کاؤنٹ ڈاؤن دکھاتا ہے، اور پھر بحال ہونے والے اکاؤنٹ پر `claude --resume <session-id>` دوبارہ لانچ کرتا ہے۔ کاؤنٹ ڈاؤن کے دوران Ctrl-C فوراً دوبارہ شروع کر دیتا ہے۔ خودکار انتظار `policy.maxWaitMs` (پہلے سے طے شدہ 1 گھنٹہ) سے محدود ہے؛ اس سے آگے فیصلہ پول کو انتظار کرنے کے بجائے ختم شدہ کے طور پر رپورٹ کرتا ہے۔

### وقفہ وار چیک ٹائمر

ہکس صرف ٹرن باؤنڈریز پر چلتی ہیں، اور ایک لمبا ایجنٹک ٹرن ایک ونڈو کو صحت مند سے ختم شدہ تک ایک بھی باؤنڈری کے بغیر جلا سکتا ہے۔ اس لیے `init` ایک وقفہ وار ٹائمر بھی انسٹال کرتا ہے - macOS پر ایک launchd ایجنٹ، Linux پر ایک systemd یوزر ٹائمر - جو ٹرن سرگرمی سے قطع نظر ہر 180 سیکنڈ میں `tokenmaxxing check` چلاتا ہے۔

### ایک SessionStart ہک

جب کوئی سیشن شروع ہوتا ہے یا دوبارہ شروع ہوتا ہے تو وہی جائزہ چلاتا ہے، تاکہ ایک تازہ سیشن درست اکاؤنٹ پر شروع ہو۔ سوئپ کے بعد کولڈاؤن اسے ری اسپان کے فوراً بعد ایک درست no-op بنا دیتا ہے۔

## سوئچنگ کیسے فیصلہ کرتی ہے [#how-switching-decides]

فیصلے کی دو تہیں ہیں: ایک اینگیجمنٹ گیٹ، اور پھر ایک لالچی یا سخت راستہ۔

### اینگیجمنٹ

`policy.greedySessionFloor` (پہلے سے طے شدہ 50، 5 گھنٹے کی سیشن ونڈو کے فیصد میں) سے نیچے، فیصلہ بالکل نہیں چلتا - ایک تازہ سیشن اپنے اکاؤنٹ پر سوار رہتا ہے۔ جیسے ہی فعال سیشن ونڈو 50% استعمال ہو جائے، یا کوئی سخت بار عبور ہو جائے، فیصلہ مصروف ہو جاتا ہے۔

### اسکریننگ بارز

تھریشولڈز اسکریننگ بارز ہیں، گھبراہٹ کا محرک نہیں:

- `thresholds.session`: 95۔ ایک 5 گھنٹے کا ری سیٹ چھوڑ دینا سستا ہے، لہٰذا سیشن ونڈو پہلے ہی دوسری طرف سوئپ ہو جاتی ہے۔
- `thresholds.weekly`: 98۔ یہ ایک بار 7 دن کے مجموعے اور ہر فی ماڈل ہفتہ وار حد دونوں کا احاطہ کرتا ہے۔ ہفتہ وار کوٹا "استعمال کرو ورنہ کھو دو" ہے، لہٰذا یہ دیوار کے قریب تک نکلتا ہے۔

دونوں جان بوجھ کر 100 سے نیچے ہیں: گنجائش وہ بجٹ ہے جو ایک صاف ٹرن باؤنڈری تک پہنچنے کے لیے ہے (macOS پر اپنانے کی زیادہ سے زیادہ ایک ٹرن تاخیر سمیت) اکاؤنٹ کے حقیقتاً اپنی حد سے ٹکرانے سے پہلے۔ وہی بارز سوئپ امیدواروں کو اسکرین کرتی ہیں: کوئی اکاؤنٹ جو اپنی کسی بار سے تجاوز کر چکا ہو ایک درست ہدف نہیں ہے۔ محرک اور اسکریننگ ہمیشہ وہی مؤثر بارز استعمال کرتی ہیں (تھریشولڈز مائنس `policy.projectionMargin`)، کیونکہ محرک سے زیادہ نرم اسکرین سوئپس کو ان اکاؤنٹس پر پہنچائے گی جنہیں محرک فوراً دوبارہ فلیگ کر دیتا ہے، پول کو پنگ پونگ کراتے ہوئے۔

### ہدف: رفتار دباؤ

قابلِ استعمال اکاؤنٹس میں، ہدف وہ ہے جو اپنی ہفتہ وار رفتار سے سب سے زیادہ پیچھے ہو: سب سے زیادہ **رفتار دباؤ**، جس کی تعریف باقی ماندہ ہفتہ وار فیصد کو اس اکاؤنٹ کے ہفتہ وار ری سیٹ تک باقی وقت پر تقسیم کرنے سے ہوتی ہے۔ وہ اکاؤنٹ جیت جاتا ہے جس کا سب سے زیادہ کوٹا ضائع ہونے والا ہو۔ برابری کی صورت میں فیصلہ سب سے قریبی ہفتہ وار میعاد ختم ہونے، پھر سب سے کم 7 دن کے استعمال پر جاتا ہے۔

سب کچھ کیش شدہ ونڈوز پر چلتا ہے جو مطلق UTC epoch کے طور پر محفوظ ہوتی ہیں، لہٰذا ایک باسی سنیپ شاٹ بھی درست طور پر حل ہو جاتا ہے: ایک ہفتہ وار ری سیٹ جو گزر چکا ہو وہ عین 7 دن کے قدموں میں آگے بڑھایا جاتا ہے، اور کوئی بھی ونڈو جو اپنے کیش شدہ ری سیٹ سے آگے ہو اسے تازہ خالی شمار کیا جاتا ہے (کبھی سوئچ کرنے کی وجہ نہیں، کبھی کسی اکاؤنٹ کو بینچ پر رکھنے کی وجہ نہیں)۔

### لالچی بمقابلہ سخت راستہ

- **لالچی راستہ** (مصروف، مگر ہر بار سے نیچے): ہر اکاؤنٹ کی درجہ بندی کریں، موجودہ سمیت۔ اگر موجودہ اکاؤنٹ پہلے ہی جیتتا ہے یا برابر ہے، تو کچھ نہ کریں۔ ورنہ سختی سے بہتر اکاؤنٹ پر سوئپ کریں۔ یہ کبھی انتظار نہیں کرتا اور کبھی پہلے سے پارک نہیں کرتا - ایک قابلِ استعمال موجودہ اکاؤنٹ کو انتظار کے بدلے نہیں دیا جاتا۔ چونکہ موجودہ اکاؤنٹ کی بھی درجہ بندی ہوتی ہے، خودکار راستہ اور خالی `tokenmaxxing switch` دونوں idempotent ہیں: وقفہ وار جائزہ درست اکاؤنٹ پر یکجا ہو جاتا ہے اور پھر وہیں رہتا ہے۔
- **سخت راستہ** (ایک بار عبور ہوئی): بہترین قابلِ استعمال امیدوار پر سوئپ ہو جائیں۔ اگر کسی امیدوار کا ری فریش ٹوکن مردہ نکلے، تو اسے ری آتھ درکار فلیگ کیا جاتا ہے اور اگلا امیدوار آزمایا جاتا ہے۔ اگر کچھ بھی قابلِ استعمال نہ ہو، تو ختم شدہ انتظار کی منطق چلتی ہے؛ صرف وہ کالر جو حقیقتاً سیشن کو روک سکے (زیرِ نگرانی Stop ہک) کو ایک اب بھی رکاوٹ زدہ مگر سب سے جلد بحال ہونے والے اکاؤنٹ پر پہلے سے پارک کرنے کی اجازت ہے۔

### فی ماڈل حدیں

`policy.switchModels` (پہلے سے طے شدہ `["fable"]`) ان ماڈل فیملیز کے نام دیتا ہے جن کی فی ماڈل ہفتہ وار حد ایک سوئچ کو محرک کر سکتی ہے۔ ملاپ فیملی ٹوکن سے ہوتا ہے، کبھی عین ڈسپلے اسٹرنگ سے نہیں: ماڈل ڈسپلے نام بدلتے رہتے ہیں ("Fable" بن گیا "Fable 5")، اور ایک عین اسٹرنگ گیٹ نے ایک بار خاموشی سے فی ماڈل سوئچنگ کو مکمل طور پر غیر فعال کر دیا تھا۔ دو متعلقہ حفاظتی قواعد:

- ایک نامعلوم فعال ماڈل ہر تشکیل شدہ فیملی کو گیٹ کرتا ہے۔ ایک سوئپ کے سنیپ شاٹس صاف کرنے کے فوراً بعد، ایک ہیڈ لیس مشین ماڈل کے بارے میں اندھی چل سکتی ہے؛ نامعلوم کو غیر محدود سمجھنے نے ایک بار ایک اکاؤنٹ کو اس کی Fable حد پر گھنٹوں غیر محسوس بیٹھے رہنے دیا۔
- امیدوار اسکریننگ گیٹ شدہ فی ماڈل حدوں کو بھی شمار کرتی ہے، لہٰذا ایک ایسا پول جہاں ہر اکاؤنٹ نے اپنی Fable حد جلا دی ہو راؤنڈ رابن نہیں کرتا۔

### کولڈاؤن

ایک 45 سیکنڈ کا سوئپ کے بعد کولڈاؤن خودکار راستے کو گیٹ کرتا ہے۔ statusline ٹی کو سوئپ کے بعد وہی 45 سیکنڈ کے لیے دبا دیا جاتا ہے (macOS پر اپنانے میں 30 سیکنڈ تک لگتے ہیں)، لہٰذا ایک پہلے کا جائزہ اس ڈیٹا پر چلے گا جسے سوئپ نے خود باطل کر دیا - یہی درست منظرنامہ ایک بار ایک A-سے-B-اور-واپس ری اسپان لوپ پیدا کر چکا ہے۔ دستی `tokenmaxxing switch` کولڈاؤن سے متاثر نہیں ہوتا۔

## کنفیگریشن

Config ایک JSON ہے `~/.config/tokenmaxxing/config.json` پر۔ ہر فیلڈ اختیاری ہے؛ ڈیفالٹس فی فیلڈ لاگو ہوتے ہیں۔

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: اوپر بیان کردہ اسکریننگ بارز۔
- `policy.projectionMargin`: مؤثر بارز بنانے کے لیے دونوں بارز سے تفریق کیا جاتا ہے۔
- `policy.greedySessionFloor`: سیشن-استعمال فیصد جس پر لالچی یکجائی مصروف ہوتی ہے۔
- `policy.switchModels`: ماڈل فیملیز جن کی فی ماڈل ہفتہ وار حد ایک سوئچ کو گیٹ کرتی ہے (لوڈ ہونے پر اندراجات لوئر کیس کر دیے جاتے ہیں)۔
- `policy.usagePollTtlMs`: ایک `/usage` فی ماڈل پول کتنی دیر تازہ رہتا ہے۔
- `policy.maxWaitMs`: ختم شدہ پول کا خودکار انتظار حد۔

`tokenmaxxing config` ذرائع کے ساتھ مؤثر config دکھاتا ہے؛ `config set`/`unset` ڈوٹڈ کیز میں ترمیم کرتے ہیں؛ `config tidy` نامعلوم کیز کو صاف کرتا ہے۔

## کریڈنشل اسٹوریج اور حفاظتی ماڈل

تمام اسٹیٹ `~/.config/tokenmaxxing/` میں رہتی ہے۔ کریڈنشل I/O ایک واحد پلیٹ فارم-منتخب اسٹور فسیڈ سے گزرتی ہے؛ کال سائٹس کبھی پلیٹ فارم پر شاخ نہیں بناتیں۔

**macOS**: کریڈنشلز لاگ اِن کی چین میں generic-password آئٹمز کے طور پر رہتی ہیں، اسی جگہ سے مماثل جہاں Claude Code خود انہیں رکھتا ہے۔ لائیو آئٹم وہی ہے جسے claude پڑھتا ہے؛ ہر پول شدہ اکاؤنٹ کا بیک اپ اپنے `tokenmaxxing-cred-<uuid8>` کی چین آئٹم کے طور پر پارک ہوتا ہے۔ ڈسک پر کچھ بھی پلین ٹیکسٹ نہیں ہے۔ ریڈز `security find-generic-password -w` استعمال کرتی ہیں (راز صرف کبھی stdout پر ظاہر ہوتا ہے)؛ رائٹس ایک `add-generic-password` لائن کو stdin کے ذریعے `security -i` میں پائپ کرتی ہیں تاکہ راز کسی بھی پروسیس کے argv میں کبھی ظاہر نہ ہو۔ انٹرایکٹو موڈ کا لائن بفر تقریباً 4 KB کا ہے، لہٰذا حد سے بڑے بلابز ایک argv رائٹ پر واپس آتے ہیں - ایک وجہ کہ پارک شدہ آئٹمز صرف کم از کم OAuth آبجیکٹ ذخیرہ کرتے ہیں۔

**Linux**: Claude Code کریڈنشلز کو ایک 0600 پلین ٹیکسٹ فائل کے طور پر ذخیرہ کرتا ہے، اور tokenmaxxing وہی ماڈل اپناتا ہے: لائیو فائل claude کی اپنی `.credentials.json` ہے، اور پارک شدہ بیک اپس ایک 0700 ڈائرکٹری میں `~/.config/tokenmaxxing/creds/` کے تحت ایٹمی 0600 فائلیں ہیں۔ یہاں ایٹمی کا مطلب ہے temp پر لکھنا، fsync، پھر rename: ایک متوازی ریڈر ہمیشہ ایک مکمل پرانی یا مکمل نئی فائل دیکھتا ہے، کبھی نامکمل نہیں۔

سوئپ جو حفاظتی قواعد نافذ کرتا ہے:

- **حقیقی مالک کے ذریعے سمیٹنا۔** سوئپ سے پہلے، لائیو کریڈنشل کا اصل مالک API سے یہ پوچھ کر حل کیا جاتا ہے کہ ٹوکن کس تنظیم سے تعلق رکھتا ہے (`fetchTokenOrg` OAuth roles اینڈ پوائنٹ کے خلاف) - کبھی محفوظ کردہ فعال لیبل پر بھروسہ کر کے نہیں، جو بدل سکتا ہے۔ ایک بدلے ہوئے لیبل نے ایک بار ایک اکاؤنٹ کے سمیٹے کو دوسرے اکاؤنٹ کے واحد بیک اپ کو مٹانے کا سبب بنایا۔ اگر لائیو کریڈنشل پول سے باہر کسی اکاؤنٹ سے تعلق رکھتا ہو، تو سوئپ اسے مٹانے کے بجائے سرے سے انکار کر دیتا ہے۔
- **ایک کریٹیکل سیکشن۔** سمیٹنا، نئے کریڈنشل کی انسٹالیشن، اس کے روٹیٹ شدہ ٹوکن کا بیک اپ، `~/.claude.json` اکاؤنٹ سوئپ، اور فعال-لیبل کمِٹ سب ایک ہی لاک شدہ سیکشن کے اندر ہوتے ہیں۔
- **claude کے اپنے ری فریش کے ساتھ انٹرلاک۔** ایک قریب المیعاد سیشن کسی بھی لمحے اپنا ٹوکن روٹیٹ کر سکتا ہے، لہٰذا کریڈنشل رائٹس Claude Code کا ری فریش لاک بھی لیتی ہیں (بہترین کوشش کے ساتھ، ایک باسی-لاک دوبارہ حاصل کرنے اور ایک محدود ٹائم آؤٹ کے ساتھ)۔
- **مردہ گرانٹس صاف طور پر تنزل کرتے ہیں۔** ایک ری فریش جو `invalid_grant` واپس کرے اس اکاؤنٹ کو ری آتھ درکار فلیگ کرتا ہے اور خرابی کے پھیلنے سے پہلے فلیگ کو محفوظ کرتا ہے، لہٰذا ری ٹرائی لوپس امیدوار سیٹ کو سکیڑتے ہیں اور ختم ہو جاتے ہیں۔ `tokenmaxxing auth` ایک فلیگ شدہ اکاؤنٹ کو اپنی جگہ ٹھیک کرتا ہے، اور یہ ایک ایسے لاگ اِن سے انکار کرتا ہے جو مرمت کیے جانے والے اکاؤنٹ سے مختلف اکاؤنٹ پر جائے۔
- **کوئی ٹوکن لاگنگ نہیں۔** ٹوکنز کبھی لاگز، خرابیوں، یا آؤٹ پٹ میں ظاہر نہیں ہوتے۔ ٹوکن اور استعمال اینڈ پوائنٹس سے خرابی کے باڈیز کبھی خام طور پر ظاہر نہیں کیے جاتے؛ صرف ایک اجازت شدہ فیلڈز کا سیٹ باقی رہتا ہے، کیونکہ ایک ٹوکن اینڈ پوائنٹ کی ناکامی کی باڈی درخواستی مواد کی گونج دے سکتی ہے۔
- **پروب حفظانِ صحت۔** کوئی بھی اسپان شدہ `claude` پروب ان آٹھ ماحولیاتی متغیرات کو صاف کرتا ہے جنہیں claude اپنی کی چین تلاش سے پہلے مانتا ہے (`ANTHROPIC_API_KEY`، `CLAUDE_CODE_OAUTH_TOKEN`، `CLAUDE_SECURESTORAGE_CONFIG_DIR`، وغیرہ)، لہٰذا ایک پروب کبھی غلط اکاؤنٹ سے منسوب نہیں ہو سکتا۔

## پلیٹ فارم نوٹس: macOS بمقابلہ Linux

| | macOS | Linux |
|---|---|---|
| لائیو کریڈنشل | لاگ اِن کی چین generic-password آئٹم | 0600 `.credentials.json` فائل |
| پارک شدہ کریڈنشلز | فی اکاؤنٹ کی چین آئٹمز | ایک 0700 ڈائرکٹری میں 0600 فائلیں |
| سوئپ کے بعد اپنانا | تقریباً 30 سیکنڈ کے اندر (کی چین ریڈ کیش) | اگلی درخواست (فائل mtime پول) |
| وقفہ وار چیک | launchd ایجنٹ، ہر 180s | systemd یوزر ٹائمر، ہر 180s |
| الگ تھلگ-لاگ اِن اسٹور | فی config ڈائرکٹری ہیش-نیم اسپیسڈ کی چین سروس | الگ تھلگ config ڈائرکٹری کے اندر ایک فائل |

دو Linux-مخصوص تفصیلات جاننے کے قابل ہیں: claude اپنی کریڈنشل ڈائرکٹری کو پہلے `CLAUDE_SECURESTORAGE_CONFIG_DIR` سے حل کرتا ہے (پھر `CLAUDE_CONFIG_DIR`، پھر `~/.claude`)، اور tokenmaxxing اس حل کو بالکل ویسے ہی نقل کرتا ہے تاکہ دونوں کبھی غیر ہم آہنگ نہ ہوں۔ اور ایک ہی claude ورژن کے دو OS بلڈز `/usage` ری سیٹ کلاکس کو مختلف طریقے سے فارمیٹ کرتے ہیں (ایک " at " گلو استعمال کرتا ہے، دوسرا ایک کاما)؛ tokenmaxxing کا پارسر بالکل انہی دو صورتوں کو قبول کرتا ہے اور کسی تیسری پر اندازہ لگانے کے بجائے لاگ کرتا ہے۔

macOS پر، ایک ایماندارانہ محدودیت: `init` اور `add` جان بوجھ کر کی چین کو انٹرایکٹو طور پر چھوتے ہیں، تاکہ پہلی `security` رسائی ایک ہیڈ لیس ہک کے اندر ٹھنڈی نہ ہو۔

## statusline

tokenmaxxing Claude Code کی statusline کو نیٹو طور پر رینڈر کرتا ہے (جبکہ استعمال فیڈ کو ٹی کرتے ہوئے)۔ ڈیزائن کا اصول: کوٹا رنگ میں لے جایا جاتا ہے، نمبروں میں نہیں۔ ایک لائن، مثال کے طور پر:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- ہر ونڈو ٹوکن اس کا ری سیٹ تک وقت ہے، استعمال فیصد کے حساب سے ایک مسلسل سبز-سے-پیلا-سے-سرخ ریمپ پر پینٹ کیا گیا (جب ٹرمینل سپورٹ کرے تو truecolor، ورنہ 256 رنگ کیوب پر مرحلہ وار)۔ ریمپ 0 کے لیے خالص سبز، 75 پر پیلا، اور 95 اور اس سے اوپر پر سرخ پر لنگر انداز ہوتا ہے، لہٰذا پرانی شدت کی پٹیاں ریمپ لنگروں کے طور پر باقی رہتی ہیں۔
- ماڈل کا نام اسی ریمپ پر کانٹیکسٹ ونڈو فِل سے پینٹ کیا جاتا ہے۔
- ایک سبز `◆` فعال اکاؤنٹ کی ونڈوز کی قیادت کرتا ہے؛ ہر پارک شدہ اکاؤنٹ کو اپنا خود کا سیان `◇` ملتا ہے (اگر اسے ری آتھ درکار ہو تو سرخ `✗`)۔ اکاؤنٹس سب سے قریبی آنے والے ری سیٹ کے حساب سے ترتیب پاتے ہیں۔
- فی ماڈل ہر بلاک میں پہلے ایک خالی پینٹ شدہ ابتدائی حرف کے طور پر آتا ہے: Fable `𝒇` رینڈر کرتا ہے؛ دیگر فیملیز اپنا بڑا کیا گیا پہلا حرف استعمال کرتی ہیں، ہمیشہ فیملی-مماثل۔
- ایک اچھوتا پارک شدہ اکاؤنٹ ایک سبز `full` رینڈر کرتا ہے۔ ایک نامعلوم ری سیٹ کے ساتھ ماپا گیا استعمال ایک پینٹ شدہ `?` رینڈر کرتا ہے، اور ایک گیٹ شدہ ماڈل پر ایک بغیر ماپے فی ماڈل حد ایک بغیر پینٹ شدہ `𝒇?` رینڈر کرتی ہے - بغیر ماپے کو کبھی محفوظ نہیں دکھنا چاہیے۔
- ری سیٹ کاؤنٹ ڈاؤنز صرف سب سے بڑی اکائی دکھاتے ہیں، کبھی "now" یا "0m" نہیں؛ کوئی آنے والے ری سیٹ کے بغیر ونڈو ایک سبز `0` رینڈر کرتی ہے (دوبارہ خالی)۔
- ایک منسلک git ورک ٹری کا بیس نیم لائن کی قیادت کرتا ہے؛ ایک مین چیک آؤٹ وہاں کچھ رینڈر نہیں کرتا۔ شناخت فائل سسٹم کو ایک `.git` فائل کے لیے پڑھتی ہے اور کبھی git سب پروسیس اسپان نہیں کرتی۔
- `NO_COLOR` سیٹ ہونے کے ساتھ، لائن ایک جوڑے گئے عددی فارمیٹ پر واپس آتی ہے (`2h5` کا مطلب 2 گھنٹے میں ری سیٹ، 5% استعمال؛ کانٹیکسٹ فِل کے لیے `ctx 42`) - رنگ کے بغیر، ایک نکلی ہوئی ونڈو کو تازہ نہیں دکھنا چاہیے۔

سب ایجنٹ ٹاسکس claude کی subagentStatusLine سطح کے ذریعے اپنی خود کی پینل قطاریں پاتے ہیں: ہر فعال ٹاسک پر ایک قطار، فیملی نام اس ٹاسک کے کانٹیکسٹ فِل سے پینٹ کیا گیا۔

## Codex سپورٹ

وہی پولنگ OpenAI کے Codex CLI کے لیے کام کرتی ہے، آپ کے اپنے ChatGPT-سبسکرپشن اکاؤنٹس کے خلاف:

```sh
tokenmaxxing init --codex   # اپنا موجودہ codex لاگ اِن امپورٹ کریں + codex سپروائزر اور Stop ہک انسٹال کریں
tokenmaxxing add --codex    # ایک اور اکاؤنٹ الگ تھلگ لاگ اِن کریں - آپ کا بنیادی لاگ اِن اچھوتا رہتا ہے
codex                       # codex کو ہمیشہ کی طرح استعمال کریں
```

Codex پول مکمل طور پر متوازی اسٹیٹ ہے: اپنا خود کا اکاؤنٹس انڈیکس، اپنی خود کی پارک شدہ کریڈنشل فائلیں (دونوں پلیٹ فارمز پر 0600 فائلیں، کیونکہ codex کا اپنا اسٹور ایک پلین ٹیکسٹ فائل ہے)، اپنا خود کا لاک، اپنا خود کا آخری-سوئپ ٹائم اسٹیمپ۔ فیصلہ-پالیسی کوڈ کے علاوہ Claude پول کے ساتھ کچھ بھی شیئر نہیں ہوتا۔

### Codex پر ہاٹ سوئپ کیوں ناممکن ہے

ایک رواں codex پروسیس ایک ہی اِن میموری آتھ مینیجر رکھتا ہے اور واضح طور پر `auth.json` کو دوبارہ لوڈ کرنے سے انکار کرتا ہے جب وہ اب کسی مختلف اکاؤنٹ کا نام دیتا ہے۔ کوئی فائل واچر اور کوئی فی درخواست کریڈنشل پول نہیں ہے، لہٰذا ایک رواں codex کے نیچے سوئپ کیا گیا کریڈنشل انفرنس کے لیے بس کبھی مؤثر نہیں ہوتا۔ دوبارہ آغاز ہی سوئچ ہے: `codex resume <session-id>` مقامی ٹرانسکرپٹ کو اس اکاؤنٹ پر جاری رکھتا ہے جو `auth.json` اب رکھتا ہے۔

tokenmaxxing اسے ایک codex سپروائزر شِم کے ساتھ سنبھالتا ہے: Stop ہک ہر ٹرن باؤنڈری پر وہی لالچی رفتار-دباؤ فیصلہ چلاتا ہے، اور جب یہ سوئپ کرتا ہے، تو یہ ایک مارکر لکھتا ہے جو سپروائزر کو سیشن کو کمِٹ شدہ باؤنڈری پر SIGTERM کرنے اور تازہ اکاؤنٹ پر `codex resume <session-id>` دوبارہ لانچ کرنے پر مجبور کرتا ہے، ٹرانسکرپٹ برقرار رکھتے ہوئے۔ چونکہ ہر codex سوئچ ایک نظر آنے والا دوبارہ آغاز ہے، codex لالچی راستہ ایک 1.2x بہتری مارجن رکھتا ہے: ایک چیلنجر کو موجودہ اکاؤنٹ کے رفتار دباؤ کو 20% سے مات دینا ہوگی، بال برابر سے نہیں۔ سخت راستہ (ایک عبور شدہ بار) مارجن کو نظر انداز کرتا ہے۔ codex کے لیے کوئی ختم شدہ پول کاؤنٹ ڈاؤن بھی نہیں ہے - کچھ بھی codex سیشن کو روک نہیں سکتا - لہٰذا ایک مکمل طور پر ختم شدہ codex پول وہیں رہتا ہے۔

دیگر codex-مخصوص میکانکس:

- استعمال codex کے اپنے ریٹ لمٹ اینڈ پوائنٹ کے خلاف ایک مفت تصدیق شدہ GET سے پڑھا جاتا ہے (وہی کال جو CLI کا `/status` کرتا ہے): فیصد کے ساتھ ساتھ مطلق epoch ری سیٹ اوقات، مجموعی ونڈوز اور فی ماڈل حدیں یکساں۔ ونڈو درجہ بندی دورانیہ-محرک ہے، کبھی پوزیشن-محرک نہیں، کیونکہ موجودہ پلانز میں سرے سے کوئی 5 گھنٹے کی ونڈو نہ ہو اور ہفتہ وار ونڈو بنیادی سلاٹ میں بیٹھی ہو۔
- Codex ری فریش ٹوکنز روٹیٹ ہوتے ہیں، اور ایک متروک ٹوکن کا دوبارہ استعمال پوری گرانٹ فیملی کو ختم کر دیتا ہے۔ ہر روٹیشن کو واپس آتے ہی محفوظ کیا جاتا ہے، فعال اکاؤنٹ کا نمونہ ہمیشہ لائیو بلاب کے ذریعے لیا جاتا ہے (کبھی ایک باسی پارک شدہ کاپی سے نہیں)، اور فی سیشن موجودگی فائلیں یقینی بناتی ہیں کہ ایک لائیو سبلنگ سیشن میں چلنے والا اکاؤنٹ کبھی سوئپ ہدف نہ ہو اور کبھی اپنا پارک شدہ ٹوکن ری فریش نہ کروائے۔
- Codex کو فائل کریڈنشل اسٹور درکار ہے: `init --codex` تیزی سے ناکام ہو جاتا ہے اگر کی رِنگ اسٹور پن کیا گیا ہو، اور `add --codex` فائل-موڈ ترتیب کو الگ تھلگ آن بورڈنگ ہوم میں لکھتا ہے تاکہ لاگ اِن قابلِ سمیٹ اترے۔
- ایک دستی مرحلہ: codex ان ہکس کو چھوڑ دیتا ہے جن پر بھروسہ کرنے کو نہیں کہا گیا۔ `init --codex` کے بعد، codex کو ایک بار کھولیں اور `/hooks` کے ذریعے tokenmaxxing Stop ہک پر بھروسہ کریں، ورنہ خودکار سوئچنگ خاموشی سے بے اثر رہتی ہے۔ `init --codex` یہ یاد دہانی پرنٹ کرتا ہے۔

## Slack برج: xx serve

`tokenmaxxing serve` Socket Mode پر ایک مقامی Slack ڈیمن چلاتا ہے - کوئی عوامی URL درکار نہیں۔ سیٹ اپ:

```sh
tokenmaxxing serve setup                    # ایپ مینی فیسٹ پرنٹ کرتا ہے، دو ٹوکنز مانگتا ہے
tokenmaxxing serve link <channel-id> <repo> # ایک چینل کو ایک ریپو چیک آؤٹ سے باندھتا ہے
tokenmaxxing serve                          # ڈیمن چلاتا ہے
```

ایک منسلک چینل میں بوٹ کو مینشن کریں اور یہ اس تھریڈ کے لیے، منسلک ریپو چیک آؤٹ میں ایک Claude Code سیشن کھولتا ہے۔ ہر تھریڈ پیغام ایک Agent SDK `query()` کو `resume` کے ساتھ چلاتا ہے - کبھی ایک مستقل اسٹریمنگ کوئری نہیں - لہٰذا `ensureBestAccount()` ہر ایک ٹرن پر پول کا دوبارہ جائزہ لیتا ہے اور ڈیمن تھریڈز کھوئے بغیر دوبارہ شروع ہو سکتا ہے (تھریڈ ریکارڈز پائیدار ہیں؛ ڈیمن آغاز پر انہیں دوبارہ سبسکرائب کرتا ہے)۔

قابلِ ذکر رویہ:

- **اسٹریمنگ**: جوابات نیٹو طور پر Slack میں اسٹریم ہوتے ہیں، سوچ اور ٹول رنز کے لیے ٹاسک کارڈز کے ساتھ، ہائی لائٹنگ کے ساتھ رینڈر شدہ فینسڈ کوڈ، لاگت اور دورانیے کے ساتھ ایک اختتامی "Turn" کارڈ، اور جب بھی کوئی ٹول رن اسٹریم شدہ متن میں خلل ڈالے تو ایک نیا Slack پیغام کھولا جاتا ہے، تاکہ ایک ٹرن ٹول رنز کے گرد الگ الگ پیغامات کے طور پر پڑھا جائے۔ TodoWrite کالز ایک مستحکم چیک لسٹ کارڈ کو اپنی جگہ اپ ڈیٹ کرتی ہیں۔
- **اجازتیں**: فی لنک `permissionMode` بطور ڈیفالٹ `acceptEdits` ہے؛ `--yolo` (عرف `--dangerous`) ایک لنک کو `bypassPermissions` میں شامل کرتا ہے۔ ریلے شدہ ٹرنز میں انٹرایکٹو ڈائیلاگز کی اجازت نہیں ہے - کوئی بھی Slack کے ذریعے ان کا جواب نہیں دے سکتا - لہٰذا ماڈل نثر میں پوچھتا ہے اور آپ کا تھریڈ جواب اگلا ٹرن ہوتا ہے۔ ایک بنڈل شدہ پلگ اِن اسکل اسے سکھاتی ہے کہ درخواست کنندہ کو ٹیگ کرے اور جب اسے کوئی فیصلہ درکار ہو تو ٹرن ختم کر دے۔
- **سلیش کمانڈز**: ایک تھریڈ پیغام جس کا صاف کیا گیا متن `/` سے شروع ہو ایک claude سلیش کمانڈ کے طور پر چلتا ہے۔ Slack کا کمپوزر `/` سے شروع ہونے والے پیغامات کھا جاتا ہے، لہٰذا مینشن-پہلے فارم (`@bot /usage`) یا ایک ابتدائی خالی جگہ استعمال کریں۔
- **خوش اسلوبی سے بند ہونا**: SIGTERM/SIGINT خالی کرتا ہے - نئے ٹرنز کو بلند آواز سے گرا دیا جاتا ہے، جاری ٹرنز کو 5 منٹ تک ملتے ہیں، اور claude چائلڈ اپنے خود کے پروسیس گروپ میں الگ چلتا ہے تاکہ ایک ٹرمینل Ctrl-C ڈرین کے ٹرن محفوظ کرنے سے پہلے اسے ختم نہ کر سکے۔
- **تھریڈ صفائی**: جب آپ اسے بتاتے ہیں کہ کام مکمل ہو گیا، تو ماڈل ایک اِن پروسیس `finish_thread` ٹول کال کرتا ہے؛ ٹرن مکمل ختم ہونے کے بعد، ڈیمن تھریڈ ریکارڈ گرا دیتا ہے، ان سبسکرائب کرتا ہے، اور ایک تصدیق پوسٹ کرتا ہے۔ ایک تازہ مینشن ایک نیا سیشن شروع کرتا ہے۔
- **خرابی حفظانِ صحت**: ٹرن خرابیاں صرف چھانٹے گئے پیغام-متن پوسٹ کرتی ہیں، کبھی خام خرابی باڈیز نہیں۔

## Agent SDK سطح

پیکج کا پروگرامی انٹری پوائنٹ (`exports["."]` `src/sdk.ts` کی طرف اشارہ کرتا ہے) tokenmaxxing کو Claude Agent SDK کے ساتھ ان ایجنٹس کے لیے جوڑتا ہے جو آپ اپنے ذاتی پول شدہ اکاؤنٹس کے خلاف بناتے ہیں۔ آپ کی ایپ کو Bun کے تحت چلنا چاہیے (tokenmaxxing TypeScript سورس بھیجتا ہے اور `bun:ffi` استعمال کرتا ہے)۔

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK ہر `query()` پر ایک claude سب پروسیس اسپان کرتا ہے اور اسپان پر ایک بار کریڈنشلز پڑھتا ہے - کوئی statusline نہیں، کوئی کوئری کے دوران ہاٹ سوئپ نہیں - لہٰذا انضمام باؤنڈری-محرک ہے:

- `ensureBestAccount()` بالکل وہی فیصلہ ہے جو CLI ہکس اور ٹائمر چلاتے ہیں (بارز، رفتار دباؤ، کولڈاؤن، سب مشترکہ کوڈ)، کبھی توقعاتی نہیں: ایک SDK سیشن کو کبھی ختم شدہ کاؤنٹ ڈاؤن کے لیے روکا نہیں جا سکتا۔
- `pooledOptions()` `pathToClaudeCodeExecutable` کو اصل claude بائنری پر پن کرتا ہے (کبھی سپروائزر ریپر پر نہیں) اور ہر محیطی کریڈنشل اووررائیڈ کو صاف کر کے ایک مکمل متبادل `env` فراہم کرتا ہے۔ یہ تیزی سے ناکام ہو جاتا ہے اگر آپ کی ایپ کے ماحول میں `CLAUDE_CONFIG_DIR` یا `CLAUDE_SECURESTORAGE_CONFIG_DIR` سیٹ ہو: Linux پر ایک سوئپ لائیو کریڈنشل کو وہاں لکھے گا جہاں وہ اشارہ کرتے ہیں جبکہ صاف کیا گیا سب پروسیس ڈیفالٹ اسٹور پڑھتا ہے، ایک خاموش غلط-اکاؤنٹ غیر ہم آہنگی۔
- `stopHookCheck` فیصلے کو ٹرن باؤنڈریز پر دوبارہ چلاتا ہے؛ ایک سوئپ جو یہ اتارے وہ اگلے اسپان پر مؤثر ہوتا ہے۔ یہ اپنی خرابیاں خود پکڑتا ہے (stderr اور لاگ میں لاگ کرتے ہوئے) بجائے دوبارہ اچھالنے کے، کیونکہ ایک غیر سنبھالی ہک استثنا ایجنٹ میں خلل ڈال سکتی ہے، اور ایک ٹوٹے سوئچ چیک پر ایک ٹرن منسوخ کرنا موجودہ اکاؤنٹ پر سوار رہنے سے زیادہ مہنگا پڑتا ہے۔

`sdk.ts` خود Agent SDK سے کچھ بھی امپورٹ نہیں کرتا؛ اس کی اقدار ساختی طور پر SDK کے آپشنز میں پھیلتی ہیں۔

## ذاتی استعمال اور سروس کی شرائط [#personal-use-and-terms-of-service]

tokenmaxxing ان اکاؤنٹس کو پول کرتا ہے جن کے آپ مالک ہیں، ان سیشنز اور ایجنٹس میں جنہیں آپ خود چلاتے ہیں۔ یہ الفاظ جان بوجھ کر ہیں: Anthropic تیسرے فریق کی مصنوعات کو claude.ai لاگ اِن یا claude.ai ریٹ لمٹس پیش کرنے کی اجازت نہیں دیتا، اور اس میں Agent SDK پر بنائے گئے ایجنٹس شامل ہیں۔ پول شدہ SDK سطح، یا اس پر بنی کوئی بھی چیز، تیسرے فریق کو نہ بھیجیں۔ tokenmaxxing کوٹا ڈیٹا کے لیے OAuth کو دوبارہ نافذ کرنے یا API ٹریفک پراکسی کرنے کے بجائے جان بوجھ کر CLI-ثالثی `/usage` راستے پر رہتا ہے: یہ ایک پراکسی نہیں ہے، اور واحد OAuth اینڈ پوائنٹس جنہیں یہ چھوتا ہے وہ ایک سوئپ کے دوران استعمال ہونے والا معیاری ری فریش گرانٹ اور ایک صرف پڑھنے کے قابل شناختی چیک (roles اینڈ پوائنٹ) ہیں جو تصدیق کرتا ہے کہ ایک ٹوکن حقیقتاً کس اکاؤنٹ سے تعلق رکھتا ہے۔

## ایماندارانہ محدودیتیں

- **ایک ٹھنڈا ٹرن۔** پرامپٹ کیش تنظیم-محدود ہے، لہٰذا ایک نئے اکاؤنٹ پر پہلا ٹرن کانٹیکسٹ کو ایک بار دوبارہ اپ لوڈ کرتا ہے۔
- **ختم شدہ-وقفے کی رکاوٹ۔** صرف ایک مکمل طور پر ختم شدہ پول سیشن کو کاؤنٹ ڈاؤن کے لیے روکتا ہے؛ اس لمحے میں ٹائپ کی گئی کوئی بھی چیز ضائع ہو جاتی ہے۔
- **اپنانے کی تاخیر۔** macOS پر ایک سوئپ کے تقریباً 30 سیکنڈ کے اندر پہلا ٹرن اب بھی پرانے اکاؤنٹ کی پیمائش کر سکتا ہے؛ بارز کی گنجائش اسے جذب کر لیتی ہے۔
- **مشترکہ اثر کا دائرہ۔** تمام ڈیفالٹ پروفائل سیشنز ایک لائیو کریڈنشل شیئر کرتے ہیں، لہٰذا ایک سوئپ انہیں سب کو ایک ساتھ منتقل کرتا ہے (ہر ایک اپنی جگہ اپناتا ہے)۔
- **Linux پر پلین ٹیکسٹ کریڈنشلز۔** Claude Code خود Linux کریڈنشلز کو ایک 0600 پلین ٹیکسٹ فائل کے طور پر ذخیرہ کرتا ہے؛ tokenmaxxing کی پارک شدہ کاپیاں وہی ماڈل اپناتی ہیں۔

## مسائل کا حل اور اکثر پوچھے گئے سوالات

**`claude` زیرِ نگرانی نہیں لگتا۔**
`tokenmaxxing doctor` چلائیں۔ شِم کو PATH حل جیتنا چاہیے؛ چیک کریں کہ آپ کے شیل rc میں `# tokenmaxxing PATH` لائن موجودہ bin ڈائرکٹری کی طرف اشارہ کرتی ہے اور اصل claude سے آگے بیٹھی ہے۔ `doctor` `alias claude=...` یا ایک `claude()` شیل فنکشن کے ریپر کو چھپانے، اور ان عرفوں کے بارے میں بھی خبردار کرتا ہے جو ایک claude بائنری کو مطلق پاتھ سے لانچ کرتے ہیں (وہ سپروائزر کو مکمل طور پر نظر انداز کر دیتے ہیں)۔

**Codex پر خودکار سوئچنگ کبھی نہیں چلتی۔**
Codex ان ہکس کو چھوڑ دیتا ہے جن پر بھروسہ کرنے کو نہیں کہا گیا۔ codex کھولیں، `/hooks` چلائیں، اور tokenmaxxing Stop ہک پر بھروسہ کریں۔ بھروسہ ہک کے ہیش کے خلاف ریکارڈ ہوتا ہے، لہٰذا اگر ہک کبھی ترمیم شدہ ہو تو اسے دوبارہ دینا ہوگا۔

**ایک اکاؤنٹ statusline میں ایک سرخ `✗` دکھاتا ہے۔**
اس کا ری فریش ٹوکن مردہ ہے (منسوخ یا اس کے بیک اپ کے نیچے سے روٹیٹ ہو چکا)۔ اسے اپنی جگہ دوبارہ تصدیق کرنے کے لیے `tokenmaxxing auth <sel>` چلائیں؛ کمانڈ آپ کو بتاتی ہے کہ کس ای میل سے سائن اِن کرنا ہے اور ایک ایسے لاگ اِن سے انکار کرتی ہے جو کسی مختلف اکاؤنٹ پر جائے۔

**یہ سب سے زیادہ باقی ماندہ کوٹے والے اکاؤنٹ پر کیوں سوئچ نہیں کرتا؟**
کیونکہ وہ سب سے زیادہ کوٹا ضائع کرنے کے خطرے والا اکاؤنٹ نہیں ہے۔ ہدف وہ اکاؤنٹ ہے جو اپنی ہفتہ وار رفتار سے سب سے زیادہ پیچھے ہو: باقی ماندہ فیصد کو اس کے ہفتہ وار ری سیٹ تک وقت پر تقسیم کیا گیا۔ برابر باقی ماندہ مقدار کے ساتھ یہ سب سے قریبی میعاد ختم ہونے پر سمٹ آتا ہے، اور برابر میعاد ختم ہونے کے ساتھ سب سے زیادہ باقی ماندہ پر۔

**یہ ابھی سوئچ ہوا اور statusline اب بھی پرانا اکاؤنٹ دکھاتا ہے۔**
macOS پر تقریباً 30 سیکنڈ تک متوقع: رواں سیشن سوئپ شدہ کریڈنشل کو اپنے اگلے کریڈنشل-کیش ری فریش پر اپناتا ہے۔ استعمال ٹی کو بالکل اسی وجہ سے سوئپ کے بعد 45 سیکنڈ کے لیے دبا دیا جاتا ہے۔

**کیا `status --force` کی کوئی لاگت ہے؟**
جی ہاں، جان بوجھ کر: یہ فی اکاؤنٹ ایک کم از کم میٹرڈ haiku درخواست بھیجتا ہے تاکہ ہر 5 گھنٹے کی سیشن ونڈو اسی لمحے شروع ہو جائے بجائے سست پڑی رہنے کے، پھر تازہ نمونہ لیتا ہے۔ سادہ `status` اور `watch` کبھی پنگ نہیں کرتے؛ `/usage` ریڈز مفت ہیں۔ نوٹ کریں کہ سرور استعمال فیڈ ایک تازہ کھلی ونڈو کو سیکنڈوں سے منٹوں تک پیچھے کر سکتا ہے، لہٰذا پنگ کے فوراً بعد ایک پروب اب بھی پنگ سے پہلے کی حالت دکھا سکتا ہے - `status` پنگ کے ناکام ہونے کا بہانہ کرنے کے بجائے ایک نوٹ رینڈر کرتا ہے۔

**فعال اکاؤنٹ کے لیے `/usage` پروب نے کچھ واپس نہیں کیا۔**
یہ ایک معلوم claude رویہ ہے: جب اس کی اندرونی استعمال فیچ ناکام ہو یا ریٹ محدود ہو، تو `/usage` صرف مقامی سیشن اعدادوشمار پرنٹ کرتا ہے بغیر فیصد لائنوں کے۔ tokenmaxxing فعال اکاؤنٹ کا نمونہ statusline پش سے لیتا ہے اور صرف پارک شدہ اکاؤنٹس کی پروب کرتا ہے، ٹھیک اسی سے بچنے کے لیے۔

**پس منظر کے claude سیشنز۔**
Claude کا پس منظر ڈیمن اصل ورژن شدہ بائنری کو مطلق پاتھ سے اسپان کرتا ہے، PATH شِمز کو نظر انداز کرتے ہوئے، لہٰذا پس منظر کے سیشنز زیرِ نگرانی نہیں ہوتے۔ ہکس اب بھی `settings.json` کے ذریعے چلتی ہیں، اور کریڈنشل اپنانا نیز وقفہ وار ٹائمر سوئچنگ کا احاطہ کرتے ہیں، مگر ان کے لیے کوئی مارکر-محرک ری اسپان نہیں ہے۔

**کسی چیز نے ایک بار بہت سے پروسیسز اسپان کیے۔ کیا یہ اب بھی ممکن ہے؟**
سپروائزر ٹھیک اسی تاریخی ناکامی کے خلاف تہ دار ری کرشن گارڈز رکھتا ہے (ایک باسی ریپر جو "اصل" claude کے طور پر پن کیا گیا): ماحول میں ایک ڈیپتھ سینٹینل جو 5 سطحوں پر رک جاتا ہے، ایک آن ڈسک اسپان-ریٹ لمٹر، realpath شناختی چیکس جو کسی بھی امیدوار کو مسترد کرتے ہیں جو tokenmaxxing کی اپنی bin ڈائرکٹری میں واپس حل ہو، اور ایک سخت ناکامی (کبھی ایک خاموش PATH اسکین نہیں) جب ایک تشکیل شدہ claude پاتھ اب موجود نہ ہو۔ `init` اور `doctor` کسی امیدوار کو پن کرنے سے پہلے `--version` چلا کر تصدیق کرتے ہیں کہ وہ حقیقتاً claude ہے۔

`tokenmaxxing uninstall` سپروائزر شِمز، settings کے اندراجات، اور وقفہ وار ٹائمر ہٹاتا ہے، اور آپ کے اکاؤنٹس اور پارک شدہ کریڈنشلز کو برقرار رکھتا ہے۔ یہ صرف ان statusline اندراجات کو ہٹاتا ہے جنہیں یہ اپنے کے طور پر پہچانتا ہے۔
