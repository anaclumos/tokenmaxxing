tokenmaxxing은 자동 Claude Code 계정 전환을 위한 CLI입니다. 직접 보유한 여러 구독(Pro/Max) 계정을 모아 관리하고, 사용 중인 계정이 사용 한도에 가까워지면 활성 자격 증명을 더 여유로운 계정으로 즉시 교체합니다. `claude`는 늘 하던 그대로 실행하면 됩니다. 교체는 안전한 턴 경계에서 이뤄지며, 실행 중인 세션은 재시작 없이 새 계정에서 동일한 대화를 계속 이어갑니다. 동시에 실행되는 여러 세션에서도 함께 작동합니다.

겉으로 드러나는 유일한 동작은 최악의 경우입니다. 풀 전체가 한도에 도달하면 세션은 카운트다운과 함께 일시 정지했다가 가장 먼저 초기화되는 계정에서 자동으로 재개됩니다(Ctrl-C를 누르면 즉시 재개됩니다).

<Callout>
범위: macOS와 Linux의 Claude Code, 그리고 두 번째 병렬 풀로서의 OpenAI Codex CLI. API 키가 아니라 구독 계정을 모아 관리합니다. 이는 직접 보유한 계정을, 직접 실행하는 세션과 에이전트에서 모아 쓰기 위한 개인용 도구입니다. [개인적 사용과 이용약관](#personal-use-and-terms-of-service)을 참고하세요.
</Callout>

## 문제

Claude 구독은 세 가지 한도를 동시에 측정합니다(모두 `/usage`로 확인됨):

- **현재 세션**: 5시간 롤링 윈도우.
- **현재 주간(전체 모델)**: 7일 합산.
- **현재 주간, 모델별**: 개별 모델 계열마다 별도의 주간 상한. 현재 이 상한은 Sonnet과 Fable에만 존재하며, 그중 Fable 상한만이 유의미할 만큼 빡빡합니다. 이 상한은 합산 한도보다 훨씬 먼저 걸립니다. 어떤 머신은 주간 전체가 50%인데도 주간 Fable은 이미 80%에 도달해 있을 수 있습니다.

주간 할당량은 쓰지 않으면 사라집니다(use-it-or-lose-it). 계정이 고정된 주간 초기화 시점까지 소비하지 않은 분량은 모두 소멸됩니다. 여러 계정을 보유하고 있다면, 합리적인 전략은 자기 주간 진행률에서 가장 뒤처진 계정에 계속 할당량을 소진하고, 어떤 한도든 세션 도중 벽에 부딪히기 전에 다른 계정으로 전환하는 것입니다.

이 작업을 손으로 하려면 로그아웃하고, 로그인하고, 대화를 잃어야 합니다. tokenmaxxing은 이를 자동화합니다. 실행 중인 `claude`는 요청 사이에 자격 증명 저장소를 다시 확인하므로, 그 아래에서 교체된 자격 증명은 그 자리에서 곧바로 채택됩니다(macOS에서는 약 30초 이내, Linux에서는 다음 요청 시). 단순 교체는 세션을 결코 재시작하지 않습니다. 여전히 프로세스 관리가 필요한 유일한 경우는 풀이 완전히 소진된 상황입니다. 세션은 스스로를 일시 정지할 수 없기 때문입니다. 얇은 supervisor가 존재하는 이유가 바로 이것입니다.

`claude`의 나머지 모든 것은 그대로입니다. 모든 플래그, MCP 서버, 훅, 스킬이 그대로 통과됩니다.

## 빠른 시작

macOS 또는 Linux에서 [Bun](https://bun.sh)과 Claude Code가 필요합니다.

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init`은 다섯 가지 일을 합니다:

1. 이미 로그인되어 있는 계정을 계정 #1로 가져옵니다(별도의 `adopt` 명령은 없습니다).
2. `claude` supervisor shim을 설치합니다.
3. Claude Code의 `settings.json`에 세 개의 항목을 설치합니다: statusLine, Stop 훅, SessionStart 훅(그리고 subagentStatusLine 항목).
4. supervisor의 bin 디렉터리를 셸 rc의 PATH에 추가합니다(멱등적이며, `# tokenmaxxing PATH` 주석으로 표시됩니다). 실제 `claude`를 가로채려면 PATH에서 그보다 앞에 있어야 합니다.
5. 180초마다 `tokenmaxxing check`를 실행하는 주기적 확인 타이머(macOS에서는 launchd 에이전트, Linux에서는 systemd 사용자 타이머)를 설치합니다.

셸을 재시작한 다음, 계정을 더 추가하고 시작하세요:

```sh
tokenmaxxing add        # 계정을 하나 더 격리된 상태로 로그인해 풀에 추가합니다
claude                  # 늘 하던 대로 claude를 사용합니다
```

`tokenmaxxing`은 `xx`로도 별칭이 설정되어 있습니다. 아무 인자 없이 `tokenmaxxing`(또는 `xx`)을 실행하면 `status`가 실행됩니다. `switch`는 명시적으로만 실행됩니다.

## 명령어

| 명령어 | 기능 |
|---|---|
| `tokenmaxxing init` | 현재 계정을 가져오고, supervisor, 훅, statusline을 설치합니다 |
| `tokenmaxxing init --codex` | Codex에 대해 동일하게 수행합니다: 로그인을 가져오고 codex supervisor와 Stop 훅을 설치합니다 |
| `tokenmaxxing add` | 추가 계정을 등록합니다(격리된 로그인, 풀로 수확됨) |
| `tokenmaxxing add --codex` | 추가 Codex 계정을 등록합니다(격리된 로그인) |
| `tokenmaxxing auth [sel \| --all]` | 풀에 등록된 계정을 그 자리에서 재인증합니다. 인자 없이 실행하면 풀 목록을 보여주고 어느 계정인지 묻습니다. 선택자를 주면 한 계정을 대상으로 하고 어느 이메일로 로그인해야 하는지 알려줍니다. `--all`은 재인증이 필요한 모든 계정을 하나씩 순회합니다 |
| `tokenmaxxing switch [sel]` | 최적 계정으로 전환하거나(그리디, 멱등적) 특정 계정을 강제 지정합니다 |
| `tokenmaxxing switch --codex [sel]` | Codex 풀을 전환합니다(다음 codex 시작 시 적용됨) |
| `tokenmaxxing ls` | 풀에 등록된 계정을 나열합니다 |
| `tokenmaxxing status` | 5시간 / 주간 / 모델별 사용량 막대, 활성 상태, 초기화까지 소진된 상태를 포함한 계정 목록 |
| `tokenmaxxing status --force` | 추가로 모든 계정을 핑합니다(계정마다 아주 작은 haiku 요청 하나씩). 그러면 모든 5시간 세션 타이머가 지금 시작되고, 이후 새로 샘플링합니다 |
| `tokenmaxxing watch [seconds]` | N초마다 다시 렌더링되는 실시간 상태(기본 120, 최소 30, 핑은 절대 하지 않음) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | 출처와 함께 유효 설정을 표시하고, 점 표기 키를 편집하며, `tidy`는 알 수 없는 키를 정리합니다 |
| `tokenmaxxing check` | 전환 결정을 한 번 평가합니다(주기적 타이머가 실행하는 것이 이것입니다) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack 브리지 데몬(Socket Mode, 공개 URL 불필요) |
| `tokenmaxxing doctor` | supervisor와 설정 항목이 살아남았는지 확인합니다 |
| `tokenmaxxing rename [--codex] <sel> <label>` | 풀에 등록된 계정의 라벨을 변경합니다 |
| `tokenmaxxing rm <sel>` | 풀에서 계정을 제거합니다 |
| `tokenmaxxing uninstall` | supervisor와 설정 항목을 제거합니다(계정과 자격 증명은 유지됩니다) |

## 아키텍처

tokenmaxxing은 하나의 다중 호출 진입점(`src/main.ts`)으로, 그 이름으로 호출되면 `claude` supervisor로 동작하고, 내부 서브커맨드를 통해 훅과 statusline shim을 제공하며, 그 외에는 CLI를 디스패치합니다. Bun 위에서 직접 실행됩니다. npm 패키지는 빌드 산출물이 아니라 TypeScript 소스를 배포합니다.

구성 요소는 다음과 같습니다:

### supervisor shim

`init`은 `claude`라는 이름의 두 줄짜리 셸 shim을 `~/.config/tokenmaxxing/bin/`에 작성하고 그 디렉터리를 PATH 맨 앞에 둡니다. `claude`를 입력하면 shim이 supervisor를 실행하고, supervisor는 상속된 stdio와 저장된 `stty -g` 터미널 스냅샷으로 실제 claude 바이너리를 생성합니다. 이는 오로지 프로세스 및 터미널 관리자입니다. API 트래픽을 프록시하지 않으며, 전송 중인 토큰을 절대 건드리지 않습니다.

프린트 모드 호출(`claude -p`, `--version`, `--help`), 비대화형 서브커맨드(`claude mcp`, `claude config` 등), 그리고 tokenmaxxing 자체의 프로브는 세션 관리 없이 그대로 통과합니다. 대화형 세션의 경우, supervisor는 세션 id를 고정하고(새로 생성하거나, `--session-id` / `-r` / `-c`로 전달한 값을 재사용), 나중에 재실행 시 재현할 수 있도록 실행 플래그를 저장한 다음, 그 세션에 연결된 respawn 마커 파일을 감시합니다.

### statusline tee

Claude Code는 매 턴마다 rate-limit 데이터(`rate_limits.five_hour`와 `rate_limits.seven_day`)를 statusline의 stdin으로 밀어 넣습니다. tokenmaxxing이 statusline 슬롯을 소유하므로, 그 렌더러는 무료 푸시 기반 사용량 피드 역할을 겸합니다. 매 틱마다 합산 윈도우와 활성 모델을 `usage.json`으로 tee합니다. 모델별 상한은 statusline stdin에 없습니다. 이는 오직 `claude -p '/usage'`(무료, 토큰 0개)에서만 얻을 수 있으며, TTL로 폴링되어 활성 모델이 용량 제약을 받을 때 `model-usage.json`에 캐시됩니다.

tee는 변경 시에만 기록합니다(write-on-change). 수치가 바뀌지 않으면 파일의 mtime만 갱신하며, 이는 피드의 활성 상태를 알리는 하트비트 역할을 합니다. 최신성은 항상 mtime으로 판단하며, 내장된 타임스탬프로는 절대 판단하지 않습니다.

### Stop 훅과 교체

매 턴 경계마다 Stop 훅은 전환 결정을 실행합니다([전환 결정 방식](#how-switching-decides) 참고). 교체가 필요할 때는 `flock(2)` 배타 잠금 아래에서 이뤄지며(macOS에는 `flock(1)` 바이너리가 없으므로 `bun:ffi`를 통해 획득), 자격 증명 쓰기는 추가로 Claude Code 자체의 갱신 잠금과 맞물립니다. 임계 구역 안에서, 한 번의 교체는:

1. 현재 라이브 자격 증명을 그 실제 소유자의 보관 백업으로 수확합니다.
2. 대상 계정의 새로 갱신된 자격 증명을 라이브로 설치하며, 기존 라이브 blob에 병합하여 형제 상태(예: MCP 서버별 OAuth 토큰)가 유지되도록 합니다.
3. 대상의 회전된 토큰을 그 자체 백업에 저장합니다.
4. `~/.claude.json`의 `oauthAccount` 필드를 원자적으로 다시 씁니다.
5. 잠금이 해제되기 전에 새 활성 라벨을 커밋하고 오래된 사용량 스냅샷을 지웁니다. 따라서 크래시가 발생하더라도 설치된 자격 증명과 활성 라벨이 서로 다른 계정을 가리키는 일은 결코 생기지 않습니다.

모든 기본 프로필 세션이 하나의 라이브 자격 증명을 공유하므로, 단 한 번의 교체로 모든 세션이 한꺼번에 이전되며, flock과 잠금 아래의 재확인이 경쟁하는 훅들이 두 계정을 소진하는 것을 막아줍니다.

### 그 자리에서의 채택

실행 중인 claude 세션은 요청 사이에 자격 증명 저장소를 폴링합니다. macOS에서는 짧은 캐시를 통해 키체인을 다시 읽고 액세스 토큰을 비교하며, Linux에서는 자격 증명 파일의 mtime을 확인하고 변경 시 토큰 캐시를 비웁니다. 최종 효과는, 교체된 자격 증명이 재시작 없이 macOS에서는 약 30초 이내에, Linux에서는 바로 다음 요청에 모든 실행 중인 세션에 채택된다는 것입니다. 이것이 단순 교체가 마커를 쓰지 않고 respawn을 유발하지 않는 이유입니다. 세션은 그저 새 계정에서 계속됩니다. 세션 내 `/usage`도 동일한 토큰 캐시를 공유하므로, 그 계정 표시도 채택과 함께 바뀝니다.

### 풀 소진 시 대기와 자동 재개

풀의 모든 계정이 각자의 기준선을 넘었을 때에만 Stop 훅이 respawn 마커를 기록합니다(마커 스키마는 `waitUntil` 타임스탬프를 요구합니다. 단순 교체는 결코 이를 생성할 수 없습니다). supervisor는 마커를 감지하면 이미 커밋된 턴 경계에서 자식 프로세스에 SIGTERM을 보내고(Stop 훅은 트랜스크립트가 디스크에 기록되고 claude가 유휴 상태가 된 뒤에 실행되므로 손실되는 것이 없습니다), 터미널을 복원하고, 가장 빠른 초기화까지의 카운트다운을 표시한 다음, 복구된 계정에서 `claude --resume <session-id>`를 다시 실행합니다. 카운트다운 도중 Ctrl-C를 누르면 즉시 재개됩니다. 자동 대기는 `policy.maxWaitMs`(기본 1시간)로 제한됩니다. 그 이상이면 결정은 대기하는 대신 풀이 소진되었다고 보고합니다.

### 주기적 확인 타이머

훅은 턴 경계에서만 발동하는데, 하나의 긴 에이전트 턴은 경계가 단 한 번도 없이 윈도우를 건강한 상태에서 소진 상태까지 태워버릴 수 있습니다. 그래서 `init`은 턴 활동과 무관하게 180초마다 `tokenmaxxing check`를 실행하는 주기적 타이머(macOS에서는 launchd 에이전트, Linux에서는 systemd 사용자 타이머)도 설치합니다.

### SessionStart 훅

세션이 시작되거나 재개될 때 동일한 평가를 실행하여, 새 세션이 올바른 계정에서 시작되도록 합니다. 교체 후 쿨다운 덕분에 respawn 직후에는 올바르게 아무 동작도 하지 않습니다.

## 전환 결정 방식 [#how-switching-decides]

결정은 두 계층으로 이뤄집니다: 관여 게이트, 그다음 그리디 경로 또는 하드 경로.

### 관여

`policy.greedySessionFloor`(기본 50, 5시간 세션 윈도우의 백분율) 미만에서는 결정이 아예 실행되지 않습니다. 새 세션은 자기 계정을 그대로 탑니다. 활성 세션 윈도우가 50% 사용되거나 어떤 하드 기준선이든 넘어서면 결정이 관여합니다.

### 선별 기준선

이 임계값들은 선별 기준선이지, 비상 발동 트리거가 아닙니다:

- `thresholds.session`: 95. 5시간 초기화는 그냥 기다리는 비용이 낮으므로, 세션 윈도우는 더 일찍 다른 계정으로 교체합니다.
- `thresholds.weekly`: 98. 이 하나의 기준선이 7일 합산과 모든 모델별 주간 상한을 함께 다룹니다. 주간 할당량은 쓰지 않으면 사라지므로, 벽에 가깝게까지 소진합니다.

둘 다 의도적으로 100 미만입니다. 이 여유분은 계정이 실제로 한도에 도달하기 전에 깔끔한 턴 경계에 도달하기 위한(그리고 macOS에서는 최대 한 턴의 채택 지연까지 감안한) 예산입니다. 같은 기준선이 교체 후보를 선별합니다. 어떤 기준선이든 넘어선 계정은 유효한 대상이 아닙니다. 트리거와 선별은 항상 동일한 유효 기준선(임계값에서 `policy.projectionMargin`을 뺀 값)을 사용합니다. 선별이 트리거보다 느슨하면 트리거가 즉시 다시 표시할 계정으로 교체가 이뤄져 풀이 핑퐁하게 되기 때문입니다.

### 대상: 진행 압력

사용 가능한 계정 중에서 대상은 자기 주간 진행률에서 가장 뒤처진 계정입니다. 즉 **진행 압력(pace pressure)**이 가장 높은 계정으로, 이는 남은 주간 백분율을 그 계정의 주간 초기화까지 남은 시간으로 나눈 값으로 정의됩니다. 소멸될 할당량이 가장 많은 계정이 선택됩니다. 동점일 경우 주간 만료가 가장 빠른 계정, 그다음으로 7일 사용량이 가장 낮은 계정 순으로 갈립니다.

모든 것은 절대 UTC epoch로 저장된 캐시 윈도우를 기반으로 동작하므로, 오래된 스냅샷도 여전히 올바르게 해석됩니다. 이미 지난 주간 초기화는 정확히 7일 단위로 앞으로 외삽되고, 캐시된 초기화 시점을 지난 윈도우는 모두 갓 비워진 것으로 간주됩니다(전환의 이유도, 계정을 벤치에 앉혀 둘 이유도 결코 되지 않습니다).

### 그리디 경로 대 하드 경로

- **그리디 경로**(관여했지만 모든 기준선 아래): 현재 계정을 포함해 모든 계정의 순위를 매깁니다. 현재 계정이 이미 이기거나 동점이면 아무것도 하지 않습니다. 그렇지 않으면 확실히 더 나은 계정으로 교체합니다. 절대 대기하거나 미리 park하지 않습니다. 사용 가능한 현재 계정을 대기와 맞바꾸지 않습니다. 현재 계정도 순위에 포함되므로, 자동 경로와 인자 없는 `tokenmaxxing switch` 모두 멱등적입니다. 주기적으로 평가하면 올바른 계정으로 수렴한 다음 그대로 머무릅니다.
- **하드 경로**(기준선을 넘음): 사용 가능한 최적 후보로 교체합니다. 후보의 갱신 토큰이 죽은 것으로 드러나면 재인증 필요로 표시하고 다음 후보를 시도합니다. 사용 가능한 것이 없으면 소진 대기 로직이 실행됩니다. 실제로 세션을 일시 정지할 수 있는 호출자(supervisor가 감독하는 Stop 훅)만이 아직 차단되어 있지만 가장 빨리 회복될 계정으로 미리 park하는 것이 허용됩니다.

### 모델별 상한

`policy.switchModels`(기본 `["fable"]`)는 모델별 주간 상한이 전환을 유발할 수 있는 모델 계열을 지정합니다. 매칭은 계열 토큰 기준이며, 정확한 표시 문자열 기준이 결코 아닙니다. 모델 표시 이름은 변합니다("Fable"이 "Fable 5"가 되었습니다). 정확한 문자열 게이트는 한때 모델별 전환을 통째로 조용히 비활성화한 적이 있습니다. 관련된 두 가지 안전 규칙:

- 알 수 없는 활성 모델은 설정된 모든 계열을 게이트합니다. 교체가 스냅샷을 지운 직후, 헤드리스 머신은 모델을 알 수 없는 상태로 실행될 수 있습니다. 알 수 없음을 제약 없음으로 취급했다가 한 계정이 몇 시간 동안 눈치채이지 않은 채 Fable 상한에 머문 적이 있습니다.
- 후보 선별은 게이트된 모델별 상한도 반영하므로, 모든 계정이 Fable 상한을 소진한 풀은 라운드로빈하지 않습니다.

### 쿨다운

45초의 교체 후 쿨다운이 자동 경로를 게이트합니다. statusline tee는 교체 후 동일한 45초 동안 억제됩니다(채택은 macOS에서 최대 30초가 걸립니다). 그렇지 않으면 이른 평가가 교체 자체로 무효화된 데이터로 실행됩니다. 바로 그 시나리오가 한때 A에서 B로 갔다가 되돌아오는 respawn 루프를 만들어냈습니다. 수동 `tokenmaxxing switch`는 쿨다운의 영향을 받지 않습니다.

## 설정

설정은 `~/.config/tokenmaxxing/config.json`에 있는 JSON입니다. 모든 필드는 선택 사항이며, 기본값이 필드별로 적용됩니다.

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: 위에서 설명한 선별 기준선.
- `policy.projectionMargin`: 유효 기준선을 만들기 위해 두 기준선에서 빼는 값.
- `policy.greedySessionFloor`: 그리디 수렴이 관여하는 세션 사용 백분율.
- `policy.switchModels`: 모델별 주간 상한이 전환을 게이트하는 모델 계열(항목은 로드 시 소문자로 변환됩니다).
- `policy.usagePollTtlMs`: `/usage` 모델별 폴링이 최신 상태로 유지되는 시간.
- `policy.maxWaitMs`: 풀 소진 시 자동 대기의 상한.

`tokenmaxxing config`는 출처와 함께 유효 설정을 보여줍니다. `config set`/`unset`은 점 표기 키를 편집합니다. `config tidy`는 알 수 없는 키를 정리합니다.

## 상태 디렉터리 구조

모든 것은 `~/.config/tokenmaxxing/` 아래에 있습니다(`TOKENMAXXING_HOME`으로 재정의 가능. 외부에서 관찰 가능한 모든 경로에 환경 변수 재정의가 있어, 도구 전체가 테스트에서 격리된 상태로 실행될 수 있습니다).

| 경로 | 담는 내용 |
|---|---|
| `config.json` | 당신의 설정(희소하며, 기본값이 필드별로 적용됩니다) |
| `accounts.json` | 풀에 등록된 Claude 계정의 비밀이 아닌 인덱스: 라벨, id, 캐시된 사용량 윈도우. 토큰은 결코 담지 않습니다 |
| `usage.json` | statusline tee의 합산 윈도우 스냅샷. 그 mtime이 피드의 활성 상태 하트비트입니다 |
| `model-usage.json` | `/usage`에서 얻은 TTL 캐시된 모델별 주간 상한 |
| `lastswap.json` | 마지막 교체의 epoch 타임스탬프. 45초 쿨다운을 구동합니다 |
| `lock` | 교체를 직렬화하는 `flock` 파일 |
| `tokenmaxxing.log` | 추가 전용 이벤트 로그 |
| `bin/` | PATH shim: `claude`, `codex`, 그리고 `tokenmaxxing` / `xx` 진입점 |
| `respawn/<session-id>` | supervisor가 감시하는 소진 대기 respawn 마커 |
| `creds/` | Linux 전용: 보관된 자격 증명 파일, 0700 디렉터리 안의 0600(macOS는 대신 자격 증명을 계정별 키체인 항목으로 보관합니다) |
| `onboard/`, `sample/` | `add`/`auth` 로그인과 보관 계정 `/usage` 프로브를 위한 일회용 격리 설정 홈. 평문 자격 증명을 담은 onboard 홈은 수확 후 삭제됩니다 |
| `slack.json` | `xx serve` 토큰과 채널 링크(0600) |
| `slack-threads/` | `xx serve`의 스레드별 세션 기록 |
| `codex-*` | 병렬 Codex 풀: `codex-accounts.json`, `codex-lastswap.json`, `codex-lock`, `codex-creds/`, `codex-onboard/`, `codex-respawn/`, 그리고 `codex-live/`(실행 중인 감독 대상 codex 세션마다 하나씩 PID로 검증되는 존재 파일. 그래서 라이브 계정은 결코 교체 대상이 되지 않습니다) |

자기 디렉터리 밖에서 tokenmaxxing이 건드리는 것은 정확히 다음뿐입니다: `~/.claude.json`(`oauthAccount` 교체), Claude Code의 `settings.json`(훅과 statusline 항목), 라이브 자격 증명 저장소(macOS에서는 `Claude Code-credentials` 키체인 항목, Linux에서는 `.credentials.json`), `~/.claude.lock`(교체 중에 획득하는 claude의 갱신 잠금), codex의 `auth.json`과 `hooks.json`, 그리고 launchd 또는 systemd의 주기적 확인 유닛.

## 자격 증명 저장과 안전성 모델

모든 상태는 `~/.config/tokenmaxxing/`에 있습니다. 자격 증명 I/O는 플랫폼별로 선택된 단일 저장소 파사드를 거칩니다. 호출 지점은 플랫폼에 따라 분기하지 않습니다.

**macOS**: 자격 증명은 로그인 키체인에 generic-password 항목으로 저장되며, 이는 Claude Code 자체가 저장하는 위치와 동일합니다. 라이브 항목은 claude가 읽는 항목입니다. 풀에 등록된 각 계정의 백업은 자체 `tokenmaxxing-cred-<uuid8>` 키체인 항목으로 보관됩니다. 디스크에 평문으로 저장되는 것은 없습니다. 읽기는 `security find-generic-password -w`를 사용하며(비밀 값은 오직 stdout에만 나타납니다), 쓰기는 `add-generic-password` 줄을 stdin을 통해 `security -i`로 파이프하므로 비밀 값이 어떤 프로세스의 argv에도 나타나지 않습니다. 대화형 모드에는 대략 4 KB의 줄 버퍼가 있어, 지나치게 큰 blob은 argv 쓰기로 대체됩니다. 이것이 보관 항목이 최소한의 OAuth 객체만 저장하는 한 가지 이유입니다.

**Linux**: Claude Code는 자격 증명을 0600 평문 파일로 저장하며, tokenmaxxing도 같은 방식을 따릅니다. 라이브 파일은 claude 자체의 `.credentials.json`이고, 보관 백업은 0700 디렉터리 안의 `~/.config/tokenmaxxing/creds/` 아래에 있는 원자적 0600 파일입니다. 여기서 원자적이라는 것은 임시 파일에 쓰고, fsync한 다음, 이름을 바꾼다는 뜻입니다. 동시 읽기는 항상 온전한 이전 파일이나 온전한 새 파일을 보며, 부분적인 파일은 결코 보지 않습니다.

교체가 강제하는 안전 규칙:

- **실제 소유자 기준 수확.** 교체 전에 라이브 자격 증명의 실제 소유자는 토큰이 어느 조직에 속하는지 API에 물어(OAuth roles 엔드포인트에 대한 `fetchTokenOrg`) 결정합니다. 저장된 활성 라벨을 신뢰하는 방식은 결코 아닙니다. 이 라벨은 어긋날 수 있기 때문입니다. 어긋난 라벨이 한때 한 계정의 수확이 다른 계정의 유일한 백업을 덮어쓰게 만든 적이 있습니다. 라이브 자격 증명이 풀 밖의 계정에 속한다면, 교체는 그것을 덮어쓰는 대신 아예 거부합니다.
- **하나의 임계 구역.** 수확, 새 자격 증명의 설치, 회전된 토큰의 백업, `~/.claude.json` 계정 교체, 활성 라벨 커밋이 모두 동일한 잠금 구역 안에서 일어납니다.
- **claude 자체 갱신과의 맞물림.** 만료가 임박한 세션은 언제든 자기 토큰을 회전할 수 있으므로, 자격 증명 쓰기는 Claude Code의 갱신 잠금도 획득합니다(최선 노력 방식이며, 오래된 잠금 회수와 제한된 타임아웃을 포함합니다).
- **죽은 grant는 깔끔하게 격하됩니다.** `invalid_grant`으로 돌아온 갱신은 해당 계정을 재인증 필요로 표시하고 오류가 전파되기 전에 그 표시를 저장하므로, 재시도 루프가 후보 집합을 줄이고 종료됩니다. `tokenmaxxing auth`는 표시된 계정을 그 자리에서 고치며, 복구 대상과 다른 계정으로 로그인되는 것을 거부합니다.
- **토큰 로깅 없음.** 토큰은 로그, 오류, 출력에 결코 나타나지 않습니다. 토큰 및 사용량 엔드포인트의 오류 본문은 결코 원본 그대로 노출되지 않습니다. 허용 목록에 있는 필드 집합만 살아남습니다. 토큰 엔드포인트의 실패 본문이 요청 자료를 되비출 수 있기 때문입니다.
- **프로브 위생.** 생성된 모든 `claude` 프로브는 claude가 키체인 조회 전에 존중하는 여덟 개의 환경 변수(`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR` 등)를 제거하므로, 프로브가 잘못된 계정에 귀속되는 일은 결코 없습니다.

## 플랫폼 참고 사항: macOS 대 Linux

| | macOS | Linux |
|---|---|---|
| 라이브 자격 증명 | 로그인 키체인 generic-password 항목 | 0600 `.credentials.json` 파일 |
| 보관 자격 증명 | 계정별 키체인 항목 | 0700 디렉터리 안의 0600 파일 |
| 교체 후 채택 | 약 30초 이내(키체인 읽기 캐시) | 다음 요청(파일 mtime 폴링) |
| 주기적 확인 | launchd 에이전트, 180초마다 | systemd 사용자 타이머, 180초마다 |
| 격리 로그인 저장소 | 설정 디렉터리별 해시 네임스페이스 키체인 서비스 | 격리된 설정 디렉터리 안의 파일 |

알아둘 만한 Linux 특유의 두 가지 세부 사항: claude는 자격 증명 디렉터리를 `CLAUDE_SECURESTORAGE_CONFIG_DIR`에서 먼저 해석하고(그다음 `CLAUDE_CONFIG_DIR`, 그다음 `~/.claude`), tokenmaxxing은 그 해석을 정확히 그대로 따라 하므로 둘이 어긋나는 일이 없습니다. 그리고 같은 claude 버전의 두 OS 빌드는 `/usage` 초기화 시각을 서로 다르게 포맷합니다(하나는 " at " 연결자를, 다른 하나는 쉼표를 사용합니다). tokenmaxxing의 파서는 정확히 그 두 형식만 받아들이며, 제3의 형식에 대해서는 추측하는 대신 로그를 남깁니다.

macOS에서 한 가지 솔직한 제약: `init`과 `add`는 의도적으로 키체인을 대화형으로 건드립니다. 그래야 첫 `security` 접근이 헤드리스 훅 안에서 콜드 상태가 아니게 됩니다.

## statusline

tokenmaxxing은 Claude Code의 statusline을 네이티브로 렌더링합니다(사용량 피드를 tee하면서). 설계 원칙: 할당량은 숫자가 아니라 색으로 전달됩니다. 한 줄이며, 예를 들면:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- 각 윈도우 토큰은 초기화까지 남은 시간이며, 사용 백분율에 따라 연속적인 초록에서 노랑, 빨강으로 이어지는 그러데이션(ramp)으로 채색됩니다(터미널이 지원하면 트루컬러, 아니면 256색 큐브에 단계적으로 매핑). 그러데이션은 0에서 순수 초록, 75에서 노랑, 95 이상에서 빨강으로 고정되므로, 기존의 심각도 구간이 그러데이션 앵커로 유지됩니다.
- 모델 이름은 같은 그러데이션 위에서 컨텍스트 윈도우 채움 정도로 채색됩니다.
- 초록 `◆`가 활성 계정의 윈도우들 앞에 옵니다. 보관된 각 계정은 자체 시안색 `◇`를 받습니다(재인증이 필요하면 빨간 `✗`). 계정은 가장 가까운 예정 초기화 순으로 정렬됩니다.
- 각 블록에서 모델별 정보가 채색된 이니셜 하나로 맨 앞에 옵니다. Fable은 `𝒇`로 렌더링되고, 다른 계열은 대문자화한 첫 글자를 사용하며, 항상 계열로 매칭됩니다.
- 손대지 않은 보관 계정은 초록 `full`로 렌더링됩니다. 초기화 시각을 알 수 없는 측정된 사용량은 채색된 `?`로, 게이트된 모델의 측정되지 않은 모델별 상한은 채색되지 않은 `𝒇?`로 렌더링됩니다. 측정되지 않은 것이 안전해 보여서는 결코 안 됩니다.
- 초기화 카운트다운은 가장 큰 단위 하나만 표시하며, "now"나 "0m"은 결코 표시하지 않습니다. 예정된 초기화가 없는 윈도우는 초록 `0`으로 렌더링됩니다(다시 비었음).
- 연결된 git worktree의 basename이 줄 맨 앞에 옵니다. 메인 체크아웃은 그 자리에 아무것도 렌더링하지 않습니다. 감지는 파일 시스템에서 `.git` 파일을 읽으며, git 서브프로세스를 결코 생성하지 않습니다.
- `NO_COLOR`가 설정되면 줄은 붙여 쓴 숫자 형식으로 대체됩니다(`2h5`는 2시간 후 초기화, 5% 사용을 뜻하고, `ctx 42`는 컨텍스트 채움을 뜻합니다). 색이 없으면 소진된 윈도우가 신선해 보여서는 안 됩니다.

서브에이전트 작업은 claude의 subagentStatusLine 표면을 통해 자체 패널 행을 받습니다. 활성 작업마다 한 행씩이며, 계열 이름은 그 작업의 컨텍스트 채움으로 채색됩니다.

## Codex 지원

동일한 풀링이 OpenAI의 Codex CLI에 대해서도, 직접 보유한 ChatGPT 구독 계정을 상대로 작동합니다:

```sh
tokenmaxxing init --codex   # 현재 codex 로그인을 가져오고 codex supervisor와 Stop 훅을 설치합니다
tokenmaxxing add --codex    # 다른 계정을 격리된 상태로 로그인합니다. 기본 로그인은 그대로 유지됩니다
codex                       # 늘 하던 대로 codex를 사용합니다
```

Codex 풀은 완전히 병렬 상태입니다. 자체 계정 인덱스, 자체 보관 자격 증명 파일(codex 자체 저장소가 평문 파일이므로 두 플랫폼 모두 0600 파일), 자체 잠금, 자체 마지막 교체 타임스탬프를 갖습니다. 결정 정책 코드를 제외하면 Claude 풀과 공유하는 것은 없습니다.

### Codex에서 hot-swap이 불가능한 이유

실행 중인 codex 프로세스는 하나의 인메모리 인증 관리자를 보유하며, `auth.json`이 이제 다른 계정을 가리키면 그것을 다시 로드하기를 명시적으로 거부합니다. 파일 워처도, 요청별 자격 증명 폴링도 없으므로, 실행 중인 codex 아래에서 교체된 자격 증명은 추론에 대해 그저 결코 적용되지 않습니다. 재시작이 곧 전환입니다. `codex resume <session-id>`는 `auth.json`이 이제 보유한 계정에서 로컬 트랜스크립트를 계속합니다.

tokenmaxxing은 이를 codex supervisor shim으로 처리합니다. Stop 훅은 매 턴 경계마다 동일한 그리디 진행 압력 결정을 실행하고, 교체할 때는 supervisor가 커밋된 경계에서 세션에 SIGTERM을 보내고 트랜스크립트를 그대로 둔 채 새 계정에서 `codex resume <session-id>`를 다시 실행하도록 만드는 마커를 기록합니다. 모든 codex 전환은 눈에 보이는 재시작이므로, codex 그리디 경로는 1.2배의 개선 여유를 둡니다. 도전 계정은 현재 계정의 진행 압력을 아슬아슬하게가 아니라 20% 앞서야 합니다. 하드 경로(기준선을 넘음)는 이 여유를 무시합니다. 또한 codex에는 풀 소진 카운트다운이 없습니다. codex 세션은 그 무엇도 일시 정지할 수 없기 때문입니다. 그래서 완전히 소진된 codex 풀은 그대로 머무릅니다.

그 밖의 codex 특유의 동작:

- 사용량은 codex 자체 rate-limit 엔드포인트에 대한 무료 인증 GET(CLI의 `/status`가 하는 것과 동일한 호출)에서 읽습니다. 백분율과 절대 epoch 초기화 시각, 합산 윈도우와 모델별 상한 모두를 얻습니다. 윈도우 분류는 위치 기반이 결코 아니라 기간 기반입니다. 현재 요금제에는 5시간 윈도우가 아예 없을 수 있고 주간 윈도우가 기본 슬롯에 놓이기 때문입니다.
- Codex 갱신 토큰은 회전하며, 대체된 토큰을 재사용하면 grant 계열 전체가 죽습니다. 모든 회전은 반환되는 즉시 저장되고, 활성 계정은 오직 라이브 blob을 통해서만 샘플링되며(오래된 보관 사본은 결코 사용하지 않음), 세션별 존재 파일은 라이브 형제 세션에서 실행 중인 계정이 결코 교체 대상이 되지 않고 그 보관 토큰이 결코 갱신되지 않도록 보장합니다.
- Codex는 파일 자격 증명 저장소를 요구합니다. keyring 저장소가 고정되어 있으면 `init --codex`는 즉시 실패하고, `add --codex`는 격리된 온보딩 홈에 파일 모드 설정을 기록하여 로그인이 수확 가능한 상태로 안착하도록 합니다.
- 수동 단계 하나: codex는 신뢰하라고 알려주지 않은 훅을 건너뜁니다. `init --codex` 이후 codex를 한 번 열어 `/hooks`를 통해 tokenmaxxing Stop 훅을 신뢰하세요. 그러지 않으면 자동 전환이 조용히 작동하지 않은 채로 남습니다. `init --codex`는 이 안내를 출력합니다.

## Slack 브리지: xx serve

`tokenmaxxing serve`는 Socket Mode를 통해 로컬 Slack 데몬을 실행합니다. 공개 URL이 필요하지 않습니다. 설정:

```sh
tokenmaxxing serve setup                    # 앱 매니페스트를 출력하고 두 개의 토큰을 입력받습니다
tokenmaxxing serve link <channel-id> <repo> # 채널을 저장소 체크아웃에 연결합니다
tokenmaxxing serve                          # 데몬을 실행합니다
```

연결된 채널에서 봇을 멘션하면 그 스레드를 위한 Claude Code 세션이 연결된 저장소 체크아웃에서 열립니다. 모든 스레드 메시지는 `resume`을 사용한 하나의 Agent SDK `query()`를 실행합니다(지속적인 스트리밍 쿼리는 결코 아닙니다). 그래서 `ensureBestAccount()`가 매 턴마다 풀을 다시 평가하며, 데몬은 스레드를 잃지 않고 재시작할 수 있습니다(스레드 기록은 영속적이며, 데몬은 시작 시 그것들을 다시 구독합니다).

주목할 만한 동작:

- **스트리밍**: 응답은 Slack으로 네이티브 스트리밍되며, 사고 과정과 도구 실행에 대한 작업 카드, 하이라이팅이 적용된 펜스 코드, 비용과 소요 시간이 담긴 마무리 "Turn" 카드, 그리고 도구 실행이 스트리밍된 텍스트를 끊을 때마다 새로 열리는 Slack 메시지를 포함합니다. 그래서 한 턴이 도구 실행을 중심으로 별개의 메시지로 읽힙니다. TodoWrite 호출은 하나의 안정적인 체크리스트 카드를 그 자리에서 갱신합니다.
- **권한**: 링크별 `permissionMode`는 기본값이 `acceptEdits`입니다. `--yolo`(별칭 `--dangerous`)는 링크를 `bypassPermissions`로 설정합니다. 중계된 턴에서는 대화형 대화 상자가 허용되지 않습니다. 아무도 Slack을 통해 대화 상자에 답할 수 없기 때문입니다. 그래서 모델은 산문으로 묻고, 당신의 스레드 답장이 다음 턴이 됩니다. 번들된 플러그인 스킬이 결정이 필요할 때 요청자를 태그하고 턴을 끝내도록 가르칩니다.
- **슬래시 명령**: 정리된 텍스트가 `/`로 시작하는 스레드 메시지는 claude 슬래시 명령으로 실행됩니다. Slack의 작성기는 `/`로 시작하는 메시지를 삼키므로, 멘션 우선 형식(`@bot /usage`)이나 앞에 공백을 붙여 사용하세요.
- **우아한 종료**: SIGTERM/SIGINT는 드레인을 수행합니다. 새 턴은 소리 내어 버려지고, 진행 중인 턴은 최대 5분을 얻으며, claude 자식은 자체 프로세스 그룹에서 분리되어 실행되므로 터미널 Ctrl-C가 드레인이 턴을 보존하기 전에 그것을 죽일 수 없습니다.
- **스레드 정리**: 작업이 끝났다고 알리면 모델은 인프로세스 `finish_thread` 도구를 호출합니다. 턴이 완전히 끝난 뒤 데몬은 스레드 기록을 삭제하고, 구독을 해제하며, 확인 메시지 하나를 게시합니다. 새 멘션은 새 세션을 시작합니다.
- **오류 위생**: 턴 오류는 다듬어진 메시지 텍스트만 게시하며, 원본 오류 본문은 결코 게시하지 않습니다.

## Agent SDK 표면

패키지의 프로그래밍 진입점(`exports["."]`이 `src/sdk.ts`를 가리킴)은 직접 보유한 풀 계정을 상대로 만드는 에이전트를 위해 tokenmaxxing을 Claude Agent SDK와 짝지웁니다. 당신의 앱은 Bun 위에서 실행되어야 합니다(tokenmaxxing은 TypeScript 소스를 배포하고 `bun:ffi`를 사용합니다).

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK는 `query()`마다 claude 서브프로세스를 생성하고 생성 시점에 자격 증명을 한 번 읽습니다. statusline도, 쿼리 도중 hot-swap도 없습니다. 그래서 이 통합은 경계 기반입니다:

- `ensureBestAccount()`는 CLI 훅과 타이머가 실행하는 바로 그 결정입니다(기준선, 진행 압력, 쿨다운, 모두 공유 코드). 결코 선제적이지 않습니다. SDK 세션은 소진 카운트다운을 위해 일시 정지될 수 없습니다.
- `pooledOptions()`는 `pathToClaudeCodeExecutable`를 실제 claude 바이너리로 고정하고(supervisor 래퍼가 결코 아님) 주변의 모든 자격 증명 재정의를 제거한 완전한 대체 `env`를 제공합니다. 당신의 앱 환경에 `CLAUDE_CONFIG_DIR`나 `CLAUDE_SECURESTORAGE_CONFIG_DIR`가 설정되어 있으면 즉시 실패합니다. Linux에서는 교체가 라이브 자격 증명을 그 변수들이 가리키는 곳에 쓰는 반면 제거된 서브프로세스는 기본 저장소를 읽어, 조용한 잘못된 계정 불일치가 생기기 때문입니다.
- `stopHookCheck`는 턴 경계에서 결정을 다시 실행합니다. 그것이 성사시킨 교체는 다음 생성 시 적용됩니다. 이것은 다시 던지는 대신 자체 오류를 잡습니다(stderr와 로그에 기록). 처리되지 않은 훅 예외가 에이전트를 중단시킬 수 있고, 망가진 전환 확인 때문에 턴을 중단하는 것이 현재 계정을 계속 쓰는 것보다 비용이 더 크기 때문입니다.

`sdk.ts`는 Agent SDK 자체에서 아무것도 임포트하지 않습니다. 그 값들은 SDK의 옵션으로 구조적으로 펼쳐집니다.

## 빌드와 배포

npm 패키지는 빌드 산출물이 아니라 TypeScript 소스를 배포합니다. `tokenmaxxing` bin은 Bun 셔뱅과 함께 곧바로 `src/main.ts`를 가리키며, Bun 1.2.6 이상이 그것을 그대로 실행합니다. 이것이 Bun이 필수 요건인 이유입니다. 컴파일된 바이너리는 설계상 없습니다. 초기 릴리스는 61 MB짜리 단일 macOS 바이너리를 모든 플랫폼에 배포했다가 Linux에서 `exec format error`로 실패했고, 플랫폼별 컴파일 패키지는 저마다 자체 릴리스 파이프라인이 필요했기에, Bun이 소스를 실행하는 방식이 배포 모델이 되었습니다.

패키지의 `exports` 맵은 위에서 설명한 프로그래밍 진입점으로 `src/sdk.ts`를 노출합니다. 릴리스는 GitHub에서 `v<version>`으로 태그됩니다. CI는 신뢰할 수 있는 게시(trusted publishing, OIDC 및 provenance 포함)를 통해 npm에 게시하며, 게시 게이트는 먼저 타입 체크와 전체 테스트 스위트를 실행합니다.

## 개인적 사용과 이용약관 [#personal-use-and-terms-of-service]

tokenmaxxing은 직접 보유한 계정을, 직접 실행하는 세션과 에이전트에서 모아 씁니다. 그 표현은 의도적입니다. Anthropic은 제3자 제품이 claude.ai 로그인이나 claude.ai 사용 한도를 제공하는 것을 허용하지 않으며, 여기에는 Agent SDK 위에 구축된 에이전트도 포함됩니다. 풀 SDK 표면이나 그 위에 구축된 어떤 것도 제3자에게 배포하지 마세요. 또한 tokenmaxxing은 OAuth를 다시 구현하거나 API 트래픽을 프록시하는 대신 할당량 데이터를 위해 CLI를 매개로 한 `/usage` 경로에 의도적으로 머무릅니다. 이것은 프록시가 아니며, 이것이 건드리는 유일한 OAuth 엔드포인트는 교체 중에 사용되는 표준 갱신 grant와 토큰이 실제로 어느 계정에 속하는지 확인하는 읽기 전용 신원 확인(roles 엔드포인트)뿐입니다.

## 솔직한 제약

- **한 번의 콜드 턴.** 프롬프트 캐시는 조직 범위이므로, 새 계정에서의 첫 턴은 컨텍스트를 한 번 다시 업로드합니다.
- **소진 일시 정지의 작은 문제.** 오직 완전히 소진된 풀만이 카운트다운을 위해 세션을 멈춥니다. 그 찰나에 입력한 것은 무엇이든 사라집니다.
- **채택 지연.** macOS에서는 교체 후 약 30초 이내의 첫 턴이 여전히 이전 계정에 집계될 수 있습니다. 기준선의 여유분이 이를 흡수합니다.
- **공유되는 영향 범위.** 모든 기본 프로필 세션이 하나의 라이브 자격 증명을 공유하므로, 교체는 그것들을 모두 함께 옮깁니다(각자 그 자리에서 채택합니다).
- **Linux의 평문 자격 증명.** Claude Code 자체가 Linux 자격 증명을 0600 평문 파일로 저장합니다. tokenmaxxing의 보관 사본도 같은 방식을 따릅니다.

## 문제 해결과 FAQ

**`claude`가 supervisor의 관리를 받지 않는 것 같습니다.**
`tokenmaxxing doctor`를 실행하세요. shim이 PATH 해석에서 이겨야 합니다. 셸 rc의 `# tokenmaxxing PATH` 줄이 현재 bin 디렉터리를 가리키고 실제 claude보다 앞에 있는지 확인하세요. `doctor`는 또한 래퍼를 가리는 `alias claude=...`나 `claude()` 셸 함수에 대해, 그리고 claude 바이너리를 절대 경로로 실행하는 별칭에 대해 경고합니다(그런 별칭은 supervisor를 완전히 우회합니다).

**Codex에서 자동 전환이 전혀 발동하지 않습니다.**
Codex는 신뢰하라고 알려주지 않은 훅을 건너뜁니다. codex를 열어 `/hooks`를 실행하고 tokenmaxxing Stop 훅을 신뢰하세요. 신뢰는 훅의 해시를 기준으로 기록되므로, 훅이 편집되면 다시 부여해야 합니다.

**한 계정이 statusline에 빨간 `✗`를 표시합니다.**
그 계정의 갱신 토큰이 죽었습니다(취소되었거나 백업 아래에서 회전되어 빠졌습니다). `tokenmaxxing auth <sel>`을 실행해 그 자리에서 재인증하세요. 이 명령은 어느 이메일로 로그인해야 하는지 알려주고, 다른 계정으로 로그인되는 것을 거부합니다.

**왜 남은 할당량이 가장 많은 계정으로 전환하지 않나요?**
그 계정이 할당량을 소멸할 위험이 가장 큰 계정은 아니기 때문입니다. 대상은 자기 주간 진행률에서 가장 뒤처진 계정입니다. 남은 백분율을 주간 초기화까지 남은 시간으로 나눈 값이죠. 남은 양이 같으면 이는 만료가 가장 빠른 계정 우선으로 귀결되고, 만료가 같으면 남은 양이 가장 많은 계정 우선으로 귀결됩니다.

**방금 전환했는데 statusline이 여전히 이전 계정을 표시합니다.**
macOS에서는 최대 약 30초까지 예상되는 현상입니다. 실행 중인 세션은 다음 자격 증명 캐시 갱신 시 교체된 자격 증명을 채택합니다. 사용량 tee가 교체 후 45초 동안 억제되는 것이 바로 이 이유 때문입니다.

**`status --force`는 비용이 드나요?**
네, 의도적으로 듭니다. 계정마다 아주 작은 과금 haiku 요청을 하나씩 보내, 모든 5시간 세션 윈도우가 잠들어 있는 대신 그 순간에 시작되도록 한 다음 새로 샘플링합니다. 일반 `status`와 `watch`는 결코 핑하지 않으며, `/usage` 읽기는 무료입니다. 서버 사용량 피드는 갓 열린 윈도우를 수 초에서 수 분까지 지연 반영할 수 있으므로, 핑 직후의 프로브가 여전히 핑 이전 상태를 보여줄 수 있음에 유의하세요. `status`는 핑이 실패한 척하는 대신 안내 메시지를 렌더링합니다.

**`/usage` 프로브가 활성 계정에 대해 아무것도 반환하지 않았습니다.**
그것은 알려진 claude 동작입니다. 내부 사용량 조회가 실패하거나 속도 제한에 걸리면, `/usage`는 백분율 줄 없이 로컬 세션 통계만 출력합니다. tokenmaxxing은 바로 이를 피하기 위해 활성 계정은 statusline 푸시에서 샘플링하고 보관 계정만 프로브합니다.

**백그라운드 claude 세션.**
Claude의 백그라운드 데몬은 실제 버전이 지정된 바이너리를 절대 경로로 생성하여 PATH shim을 우회하므로, 백그라운드 세션은 관리되지 않습니다. 훅은 여전히 `settings.json`을 통해 발동하고, 자격 증명 채택과 주기적 타이머가 전환을 담당하지만, 그것들에 대한 마커 기반 respawn은 없습니다.

**한 번은 무언가가 많은 프로세스를 생성했습니다. 여전히 가능한가요?**
supervisor는 바로 그 과거의 실패(오래된 래퍼가 "실제" claude로 고정된 경우)에 대비한 계층적 재귀 가드를 갖추고 있습니다. 5단계에서 중단하는 환경 내 깊이 센티널, 디스크 기반 생성 속도 제한기, tokenmaxxing 자체 bin 디렉터리로 되돌아 해석되는 후보를 거부하는 realpath 신원 확인, 그리고 설정된 claude 경로가 더 이상 존재하지 않을 때의 하드 실패(조용한 PATH 스캔이 결코 아님)입니다. `init`과 `doctor`는 후보를 고정하기 전에 `--version`을 실행해 그것이 실제로 claude인지 확인합니다.

**제거하기.**
`tokenmaxxing uninstall`은 supervisor shim, 설정 항목, 주기적 타이머를 제거하며, 당신의 계정과 보관 자격 증명은 그대로 둡니다. 자신의 것으로 인식하는 statusline 항목만 제거합니다.
