कॉन्फिग `~/.config/tokenmaxxing/config.json` येथे JSON आहे. प्रत्येक फील्ड ऐच्छिक आहे; डीफॉल्ट्स प्रति-फील्ड लागू होतात.

```json
{
  "thresholds": { "session": [90], "weekly": 98 },
  "hardThresholds": { "session": 100, "weekly": 100 },
  "claudeBin": "/path/to/real/claude",
  "codexBin": "/path/to/real/codex",
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 80,
    "greedySwapMargin": 0.15,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000,
    "checkIntervalMs": 60000
  }
}
```

- `thresholds.session`: ५-तासांची शिडी, म्हणजे चढत्या क्रमाने लावलेल्या स्क्रीनिंग पायऱ्यांची यादी. प्रत्येक मूल्यांकन एकच सक्रिय पायरी ठरवते, ती म्हणजे सर्वात खालची अशी पायरी जी पूलमधले एखादे तरी खाते अजून पार करते, आणि तीच पायरी ट्रिगर आणि उमेदवारांची तपासणी दोन्ही असते. Codex फक्त सर्वात वरची पायरी वाचतो. पहा [स्विचिंग कसे ठरते](/mr/switching).
- `thresholds.weekly`: साप्ताहिक स्क्रीनिंग बार, जो ७-दिवसांची एकत्रित बेरीज आणि प्रत्येक प्रति-मॉडेल साप्ताहिक मर्यादा व्यापतो.
- `hardThresholds.session` / `hardThresholds.weekly`: भिंत बार (डीफॉल्ट १००, प्रत्येक खात्याची खरी सर्व्हर मर्यादा). `hardThresholds.session` हा सत्राच्या सर्वात वरच्या पायरीइतका किंवा त्याहून वर असलाच पाहिजे. जेव्हा प्रत्येक खाते त्याच्या स्क्रीनिंग बाराच्या वर असते, तेव्हा स्वयंचलित Claude निर्णय पार्क करण्याआधी प्रत्येकाला त्याच्या भिंतीपर्यंत पिळून काढतो - पहा [भिंत](/mr/switching). बंद करण्यासाठी तो सर्वात वरच्या पायरीच्या आणि साप्ताहिक बाराच्या बरोबरीने सेट करा; Codex हे सेटिंग दुर्लक्षित करतो.
- `claudeBin` / `codexBin`: पर्यवेक्षक जे खरे बायनरीज स्पॉन करतात त्यांना पिन करते (`init` / `init --codex` द्वारे लिहिले जाते; रिकर्शन-गार्ड निदान सांगते की `claudeBin` इथे खऱ्या Claude बायनरीकडे निर्देश करेनासे झाल्यावर ते इथे दुरुस्त करा).
- `policy.projectionMargin`: प्रभावी बार तयार करण्यासाठी प्रत्येक सत्र पायरीतून, साप्ताहिक बारातून आणि भिंत बारांतून वजा केला जातो.
- `policy.greedySessionFloor`: सत्र-वापर टक्केवारी ज्यावर हावरट एकवटणे सहभागी होते.
- `policy.greedySwapMargin`: हावरट मार्गावरील विद्यमान खात्याची हिस्टेरेसिस, 0 ते 1 दरम्यानचा अपूर्णांक (डीफॉल्ट 0.15). पार्क केलेल्या खात्याचा गती दबाव सध्याच्या खात्याच्या दबावाला या अपूर्णांकाहून अधिकने ओलांडत नाही तोपर्यंत सध्याचे खाते आपली जागा धरून ठेवते, त्यामुळे जवळपास बरोबरीत असलेली खाती जागेची अदलाबदल करत राहणे आणि प्रति-संस्था प्रॉम्प्ट कॅश उद्ध्वस्त करणे थांबते. जुन्या नेहमी-सर्वोत्तम-घ्या वर्तनासाठी 0 सेट करा. तो ओलांडलेल्या बाराला किंवा भिंतीला कधीही सैल करत नाही - फक्त अशा खात्यांमधले पार्श्व बदल जी सर्व बारांच्या खाली आहेत. मॅन्युअल `tokenmaxxing switch` त्याकडे दुर्लक्ष करतो आणि नेहमी सर्वोत्तम खात्यावर एकवटतो.
- `policy.switchModels`: मॉडेल कुटुंबे ज्यांची प्रति-मॉडेल साप्ताहिक मर्यादा बदल गेट करते (नोंदी लोड होताना लोअरकेस केल्या जातात).
- `policy.usagePollTtlMs`: एक `/usage` प्रति-मॉडेल पोल किती काळ ताजा राहतो.
- `policy.maxWaitMs`: संपलेल्या-पूलची स्वयं-प्रतीक्षा मर्यादा.
- `policy.checkIntervalMs`: नियतकालिक तपासणीचा टिक (डीफॉल्ट 60000, किमान 10000, कारण launchd डीफॉल्टने दर १० सेकंदांतून एकापेक्षा जास्त वेळा जॉब स्पॉन करत नाही). `init` तो पूर्ण सेकंदांपर्यंत वर गोल करून टायमरचा अंतराल म्हणून लिहिते (Linux वर systemd चा `AccuracySec` त्याचा बारावा भाग असतो, किमान एक सेकंद), आणि मोकळिकेचा प्रत्येक पट्टा त्याचा गुणाकार असतो: बाराजवळ एक टिक, भरपूर मोकळीक असताना जास्तीत जास्त पाच टिक (पहा [तपासणीची लय](/mr/switching)). संपलेल्या पूलची प्रतीक्षा आणि बदल-नंतरचा कूलडाउन याऐवजी त्यांच्या स्वतःच्या अंतिम वेळांपर्यंत झोपतात. वेळापत्रक पुढच्या तपासणीला नवीन मूल्य वाचते, पण स्थापित टायमर तुम्ही पुन्हा `tokenmaxxing init` चालवेपर्यंत त्याचा जुना टिक ठेवतो, आणि देय वेळेची सूट कॉन्फिगर केलेल्या टिकाच्या निम्मी असते, त्यामुळे बदललेला टिक त्या पुन्हा-चालवण्यानंतरच पूर्णपणे पाळला जातो. Nix-व्यवस्थापित टायमरसह, `checkTimer.intervalSeconds` तेच मूल्य सेट करा; त्या पर्यायाला तीच १०-सेकंदांची किमान मर्यादा आहे.

`tokenmaxxing config` स्रोतांसह प्रभावी कॉन्फिग दाखवते; `config set`/`unset` डॉट-केलेल्या कीज संपादित करतात; `config tidy` अज्ञात कीज काढून टाकते.
