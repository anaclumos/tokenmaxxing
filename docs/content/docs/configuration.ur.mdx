---
title: کنفیگریشن
description: "config.json اسکیما، تھریشولڈز، اور پالیسی نوبز"
---

Config ایک JSON ہے `~/.config/tokenmaxxing/config.json` پر۔ ہر فیلڈ اختیاری ہے؛ ڈیفالٹس فی فیلڈ لاگو ہوتے ہیں۔

```json
{
  "thresholds": { "session": [90], "weekly": 98 },
  "hardThresholds": { "session": 100, "weekly": 100 },
  "claudeBin": "/path/to/real/claude",
  "codexBin": "/path/to/real/codex",
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 80,
    "greedySwapMargin": 0.15,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000,
    "checkIntervalMs": 60000
  }
}
```

- `thresholds.session`: 5 گھنٹے کی سیڑھی، یعنی اسکریننگ زینوں کی ایک چڑھتی ہوئی فہرست۔ ہر جائزہ ایک فعال زینہ طے کرتا ہے، وہ سب سے نچلا زینہ جس سے نیچے پول کا کوئی اکاؤنٹ اب بھی موجود ہے، اور یہی زینہ محرک بھی ہے اور امیدواروں کی اسکرین بھی۔ Codex صرف سب سے اوپر والا زینہ پڑھتا ہے۔ دیکھیں [سوئچنگ کیسے فیصلہ کرتی ہے](/ur/switching)۔
- `thresholds.weekly`: ہفتہ وار اسکریننگ بار، جو 7 دن کے مجموعے اور ہر فی ماڈل ہفتہ وار حد دونوں کا احاطہ کرتی ہے۔
- `hardThresholds.session` / `hardThresholds.weekly`: دیوار بارز (پہلے سے طے شدہ 100، ہر اکاؤنٹ کی حقیقی سرور حد)۔ `hardThresholds.session` کا سب سے اوپر والے سیشن زینے پر یا اس سے اوپر ہونا لازم ہے۔ جب ہر اکاؤنٹ اپنی اسکریننگ بار سے تجاوز کر جائے، تو خودکار Claude فیصلہ پارک کرنے سے پہلے ہر ایک کو اس کی دیوار تک نچوڑتا ہے - دیکھیں [دیوار](/ur/switching)۔ اسے غیر فعال کرنے کے لیے سب سے اوپر والے زینے اور ہفتہ وار بار کے برابر سیٹ کریں؛ Codex اس ترتیب کو نظر انداز کرتا ہے۔
- `claudeBin` / `codexBin`: ان اصل بائنریز پر پن کرتا ہے جنہیں سپروائزرز اسپان کرتے ہیں (`init` / `init --codex` کے ذریعے لکھا جاتا ہے؛ ری کرژن-گارڈ تشخیص آپ کو یہاں `claudeBin` ٹھیک کرنے کو کہتی ہے جب یہ اصل Claude بائنری کی طرف اشارہ کرنا چھوڑ دے)۔
- `policy.projectionMargin`: مؤثر بارز بنانے کے لیے ہر سیشن زینے، ہفتہ وار بار، اور دیوار بارز سے تفریق کیا جاتا ہے۔
- `policy.greedySessionFloor`: سیشن-استعمال فیصد جس پر لالچی یکجائی مصروف ہوتی ہے۔
- `policy.greedySwapMargin`: لالچی راستے پر موجودہ اکاؤنٹ کے حق میں hysteresis، 0 سے 1 کے درمیان ایک کسر (پہلے سے طے شدہ 0.15)۔ موجودہ اکاؤنٹ اپنی نشست پکڑے رکھتا ہے، سوائے اس کے کہ کسی پارک شدہ اکاؤنٹ کا رفتار دباؤ اس سے اِس کسر سے زیادہ آگے نکل جائے، تاکہ تقریباً برابر اکاؤنٹس نشست کو بار بار آگے پیچھے کرنا اور فی تنظیم پرامپٹ کیش توڑنا چھوڑ دیں۔ پرانے ہمیشہ-بہترین-لے-لو رویے کے لیے اسے 0 پر سیٹ کریں۔ یہ کبھی کسی عبور شدہ بار یا دیوار کو نرم نہیں کرتا، صرف ان اکاؤنٹس کے درمیان پہلو بہ پہلو سوئپس کو جو سب بارز سے نیچے ہوں۔ دستی `tokenmaxxing switch` اسے نظرانداز کرتا ہے اور ہمیشہ بہترین اکاؤنٹ پر یکجا ہوتا ہے۔
- `policy.switchModels`: ماڈل فیملیز جن کی فی ماڈل ہفتہ وار حد ایک سوئچ کو گیٹ کرتی ہے (لوڈ ہونے پر اندراجات لوئر کیس کر دیے جاتے ہیں)۔
- `policy.usagePollTtlMs`: ایک `/usage` فی ماڈل پول کتنی دیر تازہ رہتا ہے۔
- `policy.maxWaitMs`: ختم شدہ پول کا خودکار انتظار حد۔
- `policy.checkIntervalMs`: وقفہ وار چیک کا ٹِک (پہلے سے طے شدہ 60000، کم از کم 10000 کیونکہ launchd پہلے سے طے شدہ حالت میں کسی جاب کو ہر 10 سیکنڈ میں ایک بار سے زیادہ اسپان نہیں کرتا)۔ `init` اسے، پورے سیکنڈوں تک اوپر گول کر کے، ٹائمر کے وقفے کے طور پر لکھتا ہے (Linux پر systemd کا `AccuracySec` اس کا بارہواں حصہ ہوتا ہے، کم از کم ایک سیکنڈ)، اور گنجائش کا ہر بینڈ اسی کا مضاعف ہوتا ہے: کسی بار کے قریب ایک ٹِک، اور کھلی گنجائش کے ساتھ زیادہ سے زیادہ پانچ ٹِک (دیکھیں [چیک کی رفتار](/ur/switching))۔ ختم شدہ پول کا انتظار اور سوئپ کے بعد کولڈاؤن اس کے بجائے اپنی اپنی مہلت تک سوتے ہیں۔ شیڈول اگلی چیک پر نئی قدر پڑھ لیتا ہے، مگر انسٹال شدہ ٹائمر اپنا پرانا ٹِک اُس وقت تک رکھتا ہے جب تک آپ `tokenmaxxing init` دوبارہ نہ چلائیں، اور مقررہ وقت کی رعایت تشکیل شدہ ٹِک کا نصف ہے، لہٰذا بدلا ہوا ٹِک اُس دوبارہ چلانے کے بعد ہی پوری طرح نافذ ہوتا ہے۔ Nix کے زیرِ انتظام ٹائمر کے ساتھ، `checkTimer.intervalSeconds` کو اسی قدر پر سیٹ کریں؛ اُس آپشن کی بھی وہی 10 سیکنڈ کی کمترین حد ہے۔

`tokenmaxxing config` ذرائع کے ساتھ مؤثر config دکھاتا ہے؛ `config set`/`unset` ڈوٹڈ کیز میں ترمیم کرتے ہیں؛ `config tidy` نامعلوم کیز کو صاف کرتا ہے۔
