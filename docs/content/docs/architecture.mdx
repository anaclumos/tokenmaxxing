title: Architecture
description: The supervisor shim, per-account credential stores, the statusline tee, and moves by respawn
---

tokenmaxxing is one multi-call entry point (`src/main.ts`) that behaves as the `claude` supervisor when invoked under that name (and as the `codex` supervisor under that one), serves the hook and statusline shims via internal subcommands, and otherwise dispatches the CLI. It runs directly under Bun; the npm package ships TypeScript source, not a build.

One switching engine serves both switching pools. The account model, the picker, the decision, and the account commands take a provider (`src/lib/provider.ts`): the Claude provider (`src/lib/claude.ts`) wires the per-account credential stores, session presence, the OAuth profile endpoint, the statusline tee, and the `/usage` probe; the Codex provider (`src/lib/codex.ts`) wires its per-account stores (`codex-stores/<uuid8>/` with `auth.json`, everything else symlinked to the shared `~/.codex`), its identity, the usage GET and the refresh it needs, presence, and the store check before a move (see [Codex support](/codex)). The provider's `seats` capability names the difference: Claude seats are `shared` (several sessions can run on one account's store, and a session moves only by respawn), Codex seats are `live` (at most one session runs on an account, because codex has no cross-process refresh lock, and an account running in another session is never a target). Two more providers, grok (`src/lib/grok.ts`) and opencode-go (`src/lib/opencodego.ts`), are `statusOnly`: they get the same stores and account commands and no supervisor, hooks, usage source, or switching (see [Status-only pools](/status-only-pools)). Everything below describes the Claude provider unless it says otherwise.

## One credential store per account

Each pooled account owns one Claude Code credential store under the state directory: `stores/<uuid8>/`. On Linux that is the `.credentials.json` file inside it; on macOS Claude Code keys the keychain item by the store path (`Claude Code-credentials-<sha256(path)[0:8]>`). A session runs on an account because the supervisor sets `CLAUDE_SECURESTORAGE_CONFIG_DIR` to that account's store before it spawns claude. Only the credential is namespaced: `~/.claude` (settings, transcripts, plugins) and `~/.claude.json` stay shared, so `--resume` works across stores.

tokenmaxxing writes a store once, when `init`, `add`, or `auth` harvests an isolated login into it. After that the only writer is Claude Code's own token refresh, which runs inside each session under the refresh lock rooted at the store, so sessions that share an account coordinate the way two windows of one login always did. A credential is never copied between stores: a refresh rotation revokes the previous access token of that grant, so two stores holding one grant would break each other.

## The supervisor shim

`init` writes a 2-line shell shim named `claude` into `~/.config/tokenmaxxing/bin/`, beside the `tokenmaxxing` and `xx` entry points, and puts that directory ahead of the real binary on PATH. When you type `claude`, the shim runs the supervisor, which picks an account, spawns the real claude binary with inherited stdio (stdin through a relay pipe when the session runs with `--input-format stream-json`) and a saved `stty -g` terminal snapshot, and records the session's presence. It is a process and terminal manager only: it never proxies API traffic and never touches tokens. When the supervisor itself receives SIGTERM (the Claude Agent SDK stops a session that way, and harnesses such as T3 Code drive claude through the SDK), it forwards the signal to the real claude process and exits after it, so a harness stop or restart never leaves an orphaned session running on the old seat.

The `tokenmaxxing` entry point starts Bun with `--no-env-file`, so the supervisor does not import `.env` files from the working directory, and the session it spawns does not inherit their values from it. This covers every path that runs through that entry point: the `claude` and `codex` shims, the hooks, the statusline, and the check timer. The claude binary is a Bun executable that reads those files on its own, which the shim cannot change.

Print-mode invocations (`claude -p`, `--version`, `--help`), non-interactive subcommands (`claude mcp`, `claude config`, and so on), the interactive resume picker (`claude -r` with no session id), an invalid `--session-id`, `--fork-session` with a resume, and tokenmaxxing's own probes pass straight through with no store and no session management; they use whatever login the environment already names, by default Claude Code's own store. For an interactive session, the supervisor pins a session id (generating one, or reusing the one you passed via `--session-id`, `-r <id>`, or `-c`), persists your launch flags so a later relaunch can replay them, takes the pool lock, picks the seat (see [How switching decides](/switching)), spawns claude with `CLAUDE_SECURESTORAGE_CONFIG_DIR` set to that account's store, and writes `live/<session-id>` with the account id, the child's pid, and its start time. The lock covers the pick and the presence write, so two launches at once see each other and land on different accounts. The presence file is validated against the process start time whenever it is read, so a dead session never counts. When every account is at or over a bar, a new session is placed on the account whose block clears soonest. With no pooled account, or with every account needing re-auth, the session launches with no store, on whatever login the environment names, still under the supervisor's marker watch.

## The statusline tee

Claude Code pushes rate-limit data (`rate_limits.five_hour` and `rate_limits.seven_day`) into the statusline's stdin every turn. tokenmaxxing owns the statusline slot, so its renderer doubles as a free, push-based usage feed: each tick it tees the aggregate windows plus the active model into `usage/<uuid8>.json` for the account whose store the session runs under (read from the inherited `CLAUDE_SECURESTORAGE_CONFIG_DIR`). A session with no pooled store writes no tee. Per-model caps are not in statusline stdin; they come from a sample: the direct no-spend usage read (its `limits[]` rows), or `claude -p '/usage'` (free, zero tokens) when the token is near expiry or the read fails. Inside a hook decision the seat is sampled once when its tee is older than `policy.usagePollTtlMs` or when the tee's active model is a gated family, so a Fable session keeps its Fable cap fresh; the interval doubles after each failed sample, up to 30 minutes, and resets on success. The rows are stored on the account record in `accounts.json` next to the aggregate windows, so the tee never carries them.

The tee is written on change. An unchanged push within 30 seconds of the last write only bumps the file's mtime, which acts as the feed's liveness heartbeat; a later unchanged push rewrites the file with a fresh sample time. Freshness is judged by mtime; ordering against the stored record is judged by the sample time inside the file.

## The Stop hook and the move

At every turn boundary, the Stop hook runs the switch decision for its own seat, the account whose store the session runs under (see [How switching decides](/switching)). When a move is warranted, the decision runs under a `flock(2)` exclusive lock (taken via `bun:ffi`, since macOS ships no `flock(1)` binary): it folds every account's tee into `accounts.json`, ranks the usable accounts, verifies that the target's store holds a usable credential, and returns the target. The hook then writes `respawn/<session-id>`: the target account, the session to resume, a `waitUntil`, a compact flag (set by the Stop and SessionStart hooks, cleared by StopFailure), and the launch time of the process it was written for, so a marker left by an earlier launch of the same session is discarded. The supervisor sees the marker, SIGTERMs its child at the already-committed turn boundary (the Stop hook runs after the transcript is on disk and claude is idle, so nothing is lost), restores the terminal, compacts the conversation when the marker asks for it (`claude -p --resume <session-id> /compact` under the old seat's store, bounded at 5 minutes; a failure prints why and the move goes on with the full context), and relaunches `claude --resume <session-id>` with `CLAUDE_SECURESTORAGE_CONFIG_DIR` set to the target's store. The resumed process reads the target's store cold and continues the same conversation on the new account. The relaunch also submits a first prompt that says the session was resumed on an account with headroom (and compacted, when it was) and asks Claude to continue the task, or to restate what it needs when the previous turn ended waiting on you, so the conversation goes on without a keystroke. In a terminal session that prompt is the positional argument after the session id. A harness session that drives claude with `--input-format stream-json` ignores a positional prompt, so there the supervisor owns stdin, relays the harness's JSON lines to the child through a pipe, and writes the prompt as the first `user` line of each relaunched process; the supervisor's own notices (the compaction, the move, the depleted-pool wait with its resume time, the resume) go to that stdout as `system` lines of subtype `informational` and level `warning`, the shape Claude Code uses for its own print-mode notices, so a harness such as T3 Code shows them in the conversation and the stream stays parseable. In a terminal session the same notices go to stderr. A session whose transcript file is missing gets neither the compaction nor the prompt. The move writes no credential. Other sessions are not affected: each session moves on its own seat's figures.

The supervisor does not depend on a hook firing. Every ten seconds while the child runs it reads its own seat's cached figures (the account record plus the seat's tee) against the same bars, and at or over a bar it runs the same decision the hooks run and writes the same marker itself. That is what moves a session when no turn boundary comes: a harness session whose main turn has ended while a background workflow or background agents keep burning the window (a harness session has no statusline tee, and its next Stop hook waits for the next prompt), or a subagent whose refusal stamped the wall while the parent turn was still running. A turn in flight is cut at the bar; the transcript holds every completed step, and the resume prompt continues from there. A Ctrl-C override of a depleted-pool wait suppresses the watch for as long as the override runs.

A hook in a session started outside the supervisor has no session to respawn, so the decision only records enforced limits there and moves nothing; the session runs on whatever login it has until that login is refused, and the StopFailure hook then prints the shim command that resumes the session under the supervisor (see [Honest limitations](/limitations)). A failure inside a subagent of a supervised session stamps the limit and writes no marker, because the parent turn is still running; the supervisor's seat watch reads the stamp within ten seconds and moves.

## Depleted-pool wait and auto-resume

When every account in the pool is over its bars, the Stop hook writes the marker with a `waitUntil` timestamp instead: the account with the soonest reset, or the session's own account when it recovers first. The supervisor terminates the child at the turn boundary, restores the terminal, compacts when the marker asks for it, shows a countdown to that reset (in a harness session, one line naming the account and the resume time), and then relaunches `claude --resume <session-id>` under the target's store. Ctrl-C during the countdown resumes immediately, and the supervisor then ignores any later marker whose `waitUntil` falls at or before the wait it skipped, so the next Stop hook does not park the session again. The auto-wait is bounded by `policy.maxWaitMs` (default 1 hour); beyond that the decision reports the pool as depleted instead of waiting. A marker the supervisor cannot parse is never treated as absent: the supervisor terminates the child at that same boundary, restores the terminal, and exits naming the marker path, so a mismatched marker schema never skips the wait silently.

## The periodic check timer

`init` installs a periodic timer, a launchd agent on macOS and a systemd user timer on Linux, that runs `tokenmaxxing check` once per tick (`policy.checkIntervalMs`, 60 seconds by default). A tick has no session, so it moves nothing; it folds fresh tees into `accounts.json` and samples up to three accounts per tick, accounts with a live session first and then the ones whose last sample attempt is oldest: the direct no-spend usage read first, and a `/usage` probe under the account's store for a near-expiry token or a failed read (see [How switching decides](/switching)). On a Bun global install the tick also checks npm for a newer version once a day (see [Build and distribution](/distribution)). A seat's figure is the one that changes and the supervisor's seat watch reads it, so a long agentic turn or a background workflow that burns through a window is moved by that watch when the sampled figure crosses the bar, and by the StopFailure hook when the server's refusal comes first.

## The SessionStart hook

Runs the same decision on every session start, whatever its source (startup, resume, clear, compact), and, when the session is supervised, writes the same respawn marker the Stop hook would, compaction included. A session placed on a seat that is already over its bar, or resumed into a depleted pool, is moved or paused before its first turn instead of after it. The supervisor's marker watch polls every 150 ms, so a prompt sent inside that window can still start on the old seat; its refusal is then handled by the StopFailure hook.
