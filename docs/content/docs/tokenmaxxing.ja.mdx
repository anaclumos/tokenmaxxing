tokenmaxxing は Claude Code アカウントを自動で切り替える CLI です。自分が保有する複数のサブスクリプション (Pro/Max) アカウントをプールし、使用中のアカウントが使用量制限に近づくと、アクティブな認証情報をより余裕のあるアカウントへホットスワップします。`claude` はこれまでどおりそのまま実行します。切り替えは安全なターン境界で発生し、実行中のセッションは再起動せずに新しいアカウント上で同じ会話を継続します。多数の同時セッションにも同時に対応します。

唯一目に見える挙動は最悪ケースです。プール全体が制限に達したときは、セッションがカウントダウンとともに一時停止し、次にリセットされるアカウントで自動再開します (Ctrl-C で即時再開)。

<Callout>
対象範囲: macOS と Linux 上の Claude Code に加えて、OpenAI の Codex CLI を2つ目の並列プールとして扱います。プールするのはサブスクリプションアカウントであり、API キーではありません。これは自分が保有するアカウントを、自分自身が実行するセッションやエージェントの中でプールするための個人利用ツールです。[個人利用と利用規約](#personal-use-and-terms-of-service)を参照してください。
</Callout>

## 課題

Claude のサブスクリプションは、3つの制限を同時に計測します (いずれも `/usage` で確認済み)。

- **現在のセッション**: 5時間のローリングウィンドウ。
- **今週 (全モデル)**: 7日間の集計。
- **今週 (モデルごと)**: 個別のモデルファミリーに対する週次上限。現状これは Sonnet と Fable にのみ存在し、切り替えに関係するほど厳しいのは Fable の上限だけです。これは集計上限よりもかなり早く効いてきます。あるマシンでは週全体が50%のまま、すでに週次 Fable が80%に達していることがあります。

週次クォータは使い切らなければ失われる方式です。固定の週次リセットまでにアカウントが消費しなかった分は失効します。複数のアカウントを保有しているなら、合理的な戦略は、自分自身の週次ペースから最も遅れているアカウントでクォータを消費し続け、セッション途中でいずれかの制限が上限に達する前に切り替えておくことです。

これを手作業で行うと、ログアウトし、ログインし、会話を失うことになります。tokenmaxxing はこれを自動化します。実行中の `claude` はリクエストの合間に認証情報ストアを再確認するため、その裏で入れ替えられた認証情報はその場で採用されます (macOS では約30秒以内、Linux では次のリクエストで)。通常の切り替えでセッションが再起動することはありません。プロセス管理が依然として必要になる唯一のケースは、プールが完全に枯渇したときです。セッションは自分自身を一時停止できないため、この目的のために軽量なスーパーバイザーが存在します。

`claude` に関するその他すべては変わりません。すべてのフラグ、MCP サーバー、フック、スキルはそのまま透過します。

## クイックスタート

macOS または Linux 上で [Bun](https://bun.sh) と Claude Code が必要です。

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` は5つのことを行います。

1. すでにログイン済みのアカウントをアカウント #1 としてインポートします (別途 `adopt` コマンドはありません)。
2. `claude` スーパーバイザーのシムをインストールします。
3. Claude Code の `settings.json` に3つのエントリをインストールします。statusLine、Stop フック、SessionStart フック (加えて subagentStatusLine エントリ)。
4. スーパーバイザーの bin ディレクトリをシェル rc の PATH に追記します (冪等で、`# tokenmaxxing PATH` コメントで印を付けます)。本物の `claude` より前に PATH 上に置いてインターセプトする必要があります。
5. `tokenmaxxing check` を180秒ごとに実行する定期チェックタイマーをインストールします (macOS では launchd エージェント、Linux では systemd ユーザータイマー)。

シェルを再起動し、それからアカウントを追加して開始します。

```sh
tokenmaxxing add        # もう1つのアカウントを分離環境でログインしてプールに追加する
claude                  # これまでどおり claude を使う
```

`tokenmaxxing` には `xx` というエイリアスもあります。引数なしの `tokenmaxxing` (または `xx`) は `status` を実行します。`switch` は明示的に指定する必要があります。

## コマンド

| コマンド | 動作 |
|---|---|
| `tokenmaxxing init` | 現在のアカウントをインポートし、スーパーバイザー、フック、statusline をインストールする |
| `tokenmaxxing init --codex` | Codex 向けに同じ処理を行う。ログインをインポートし、codex スーパーバイザーと Stop フックをインストールする |
| `tokenmaxxing add` | 追加のアカウントを登録する (分離ログインでプールに取り込む) |
| `tokenmaxxing add --codex` | 追加の Codex アカウントを登録する (分離ログイン) |
| `tokenmaxxing auth [sel \| --all]` | プール内のアカウントをその場で再認証する。引数なしはプールを一覧表示してどれかを尋ね、セレクタは1つのアカウントを対象にしてどのメールでサインインするか伝え、`--all` は再認証が必要なアカウントを1つずつたどる |
| `tokenmaxxing switch [sel]` | 最良のアカウントに切り替える (グリーディかつ冪等) か、特定のアカウントを強制する |
| `tokenmaxxing switch --codex [sel]` | Codex プールを切り替える (次の codex 起動時に反映される) |
| `tokenmaxxing ls` | プール内のアカウントを一覧表示する |
| `tokenmaxxing status` | 5h / 週次 / モデルごとの使用量バー、アクティブ状態、リセットまで枯渇のアカウント一覧 |
| `tokenmaxxing status --force` | さらに各アカウントに ping を送り (それぞれ小さな haiku リクエスト1回)、すべての5hセッションタイマーを今開始させてから新しくサンプリングする |
| `tokenmaxxing watch [seconds]` | ライブステータスを N 秒ごとに再描画する (デフォルト120、下限30、ping は決して送らない) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | 有効な設定とそのソースを表示する。ドット区切りキーを編集する。`tidy` は不明なキーを削除する |
| `tokenmaxxing check` | 切り替えの判断を1回評価する (定期タイマーが実行するのはこれ) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack ブリッジデーモン (Socket Mode、公開 URL 不要) |
| `tokenmaxxing doctor` | スーパーバイザーと設定エントリが残っているか検証する |
| `tokenmaxxing rename [--codex] <sel> <label>` | プール内のアカウントのラベルを付け替える |
| `tokenmaxxing rm <sel>` | プールからアカウントを削除する |
| `tokenmaxxing uninstall` | スーパーバイザーと設定エントリを削除する (アカウントと認証情報は保持される) |

## アーキテクチャ

tokenmaxxing は単一のマルチコールエントリポイント (`src/main.ts`) であり、その名前で呼び出されると `claude` スーパーバイザーとして振る舞い、内部サブコマンドを通じてフックと statusline のシムを提供し、それ以外の場合は CLI をディスパッチします。Bun 上で直接動作します。npm パッケージはビルド成果物ではなく TypeScript ソースを配布します。

可動部分は次のとおりです。

### スーパーバイザーシム

`init` は `claude` という名前の2行のシェルシムを `~/.config/tokenmaxxing/bin/` に書き込み、そのディレクトリを PATH の先頭に置きます。`claude` と入力すると、シムがスーパーバイザーを実行し、スーパーバイザーは継承した stdio と保存済みの `stty -g` 端末スナップショットとともに本物の claude バイナリを起動します。これはプロセスと端末のマネージャーにすぎません。API トラフィックをプロキシすることはなく、送信中のトークンに触れることもありません。

print モードの呼び出し (`claude -p`、`--version`、`--help`)、非対話型サブコマンド (`claude mcp`、`claude config` など)、および tokenmaxxing 自身のプローブは、セッション管理なしでそのまま通過します。対話型セッションの場合、スーパーバイザーはセッション ID を固定し (新規に生成するか、`--session-id` / `-r` / `-c` で渡されたものを再利用する)、後で再起動したときにリプレイできるよう起動フラグを保存し、そのセッションに紐づいた再起動マーカーファイルを監視します。

### statusline の tee

Claude Code はレート制限データ (`rate_limits.five_hour` と `rate_limits.seven_day`) を毎ターン statusline の stdin に送り込みます。tokenmaxxing は statusline スロットを所有しているため、そのレンダラーは無料でプッシュベースの使用量フィードを兼ねます。各ティックで集計ウィンドウとアクティブモデルを `usage.json` に tee します。モデルごとの上限は statusline の stdin にはありません。これらは `claude -p '/usage'` (無料、トークン消費ゼロ) からのみ得られ、TTL 付きでポーリングされ、アクティブモデルが容量制約を受けているときに `model-usage.json` にキャッシュされます。

tee は変更時書き込み方式です。数値が変わらないときはファイルの mtime を更新するだけで、これがフィードの生存ハートビートとして機能します。鮮度は常に mtime で判断し、埋め込まれたタイムスタンプでは判断しません。

### Stop フックと切り替え

毎ターン境界で、Stop フックが切り替えの判断を実行します ([切り替えの判断方法](#how-switching-decides)を参照)。切り替えが妥当なときは `flock(2)` の排他ロックの下で行われ (macOS には `flock(1)` バイナリが同梱されていないため `bun:ffi` 経由で取得します)、認証情報の書き込みはさらに Claude Code 自身のリフレッシュロックともインターロックします。クリティカルセクション内で、1回の切り替えは次を行います。

1. 現在のライブ認証情報を、その真の所有者の待機バックアップに取り込みます。
2. ターゲットアカウントの新しくリフレッシュした認証情報をライブとしてインストールし、既存のライブ blob にマージすることで兄弟状態 (MCP サーバーごとの OAuth トークンなど) を残します。
3. ターゲットのローテートされたトークンを自身のバックアップに保存します。
4. `~/.claude.json` の `oauthAccount` フィールドをアトミックに書き換えます。
5. 新しいアクティブラベルをコミットし、古い使用量スナップショットをクリアします。これらはすべてロック解放前に行われるため、クラッシュがインストール済みの認証情報とアクティブラベルを別々のアカウントに向けたまま残すことは決してありません。

デフォルトプロファイルのすべてのセッションが唯一のライブ認証情報を共有するため、1回の切り替えですべてのセッションが一斉に移行します。flock とロック下での再確認により、競合するフックが2つのアカウントを浪費することを防ぎます。

### その場での採用

実行中の claude セッションはリクエストの合間に認証情報ストアをポーリングします。macOS では短いキャッシュを通じてキーチェーンを再読み込みしてアクセストークンを比較し、Linux では認証情報ファイルの mtime を stat して変更時にトークンキャッシュをフラッシュします。正味の効果として、入れ替えられた認証情報は、macOS では約30秒以内、Linux ではまさに次のリクエストで、再起動なしにすべての実行中セッションに採用されます。これが、通常の切り替えでマーカーを書き込まず再起動もトリガーしない理由です。セッションは新しいアカウント上でそのまま継続します。セッション内の `/usage` は同じトークンキャッシュを共有するため、そのアカウント表示も採用に合わせて切り替わります。

### プール枯渇時の待機と自動再開

プール内のすべてのアカウントがバーを超えたときにのみ、Stop フックは再起動マーカーを書き込みます (マーカースキーマは `waitUntil` タイムスタンプを必須とし、通常の切り替えでは決して生成されません)。スーパーバイザーはマーカーを見つけると、すでにコミット済みのターン境界で子プロセスに SIGTERM を送り (Stop フックはトランスクリプトがディスクに書かれ claude がアイドルになった後に実行されるため、何も失われません)、端末を復元し、最も早いリセットまでのカウントダウンを表示し、それから回復したアカウント上で `claude --resume <session-id>` を再起動します。カウントダウン中に Ctrl-C を押すと即座に再開します。自動待機は `policy.maxWaitMs` (デフォルト1時間) で上限が設けられており、それを超えると判断は待機する代わりにプールを枯渇として報告します。

### 定期チェックタイマー

フックはターン境界でしか発火せず、1回の長いエージェント的なターンが境界を1つも挟まずにウィンドウを健全な状態から枯渇まで消費し尽くすことがあります。そのため `init` は定期タイマー (macOS では launchd エージェント、Linux では systemd ユーザータイマー) もインストールし、ターンの活動に関係なく180秒ごとに `tokenmaxxing check` を実行します。

### SessionStart フック

セッションが開始または再開したときに同じ評価を実行し、新しいセッションが正しいアカウントで始まるようにします。切り替え後のクールダウンにより、再起動直後は正しく no-op になります。

## 切り替えの判断方法 [#how-switching-decides]

判断は2つの層を持ちます。エンゲージメントゲートと、それに続くグリーディパスまたはハードパスです。

### エンゲージメント

`policy.greedySessionFloor` (デフォルト50、5時間セッションウィンドウの使用パーセント) を下回っている間、判断はまったく実行されません。新しいセッションはそのアカウントに乗り続けます。アクティブなセッションウィンドウが50%使用されるか、いずれかのハードバーを超えると、判断がエンゲージします。

### スクリーニングバー

しきい値はスクリーニングバーであり、パニックのトリガーではありません。

- `thresholds.session`: 95。5時間リセットは待つコストが低いため、セッションウィンドウはより早く切り替えます。
- `thresholds.weekly`: 98。この1つのバーが7日間の集計とすべてのモデルごとの週次上限の両方をカバーします。週次クォータは使い切らなければ失われるため、上限に近いところまで消費します。

どちらも意図的に100未満です。この余裕は、アカウントが実際に制限に達する前に、きれいなターン境界へ (加えて macOS では最大1ターンの採用ラグを見込んで) 到達するための予算です。同じバーが切り替え候補もスクリーニングします。いずれかのバーを超えたアカウントは有効なターゲットではありません。トリガーとスクリーニングは常に同じ有効バー (しきい値から `policy.projectionMargin` を引いたもの) を使います。スクリーニングがトリガーより緩いと、トリガーが即座に再フラグするアカウントに切り替えが着地し、プールが行ったり来たりしてしまうためです。

### ターゲット: ペースプレッシャー

使用可能なアカウントの中で、ターゲットは自分自身の週次ペースから最も遅れているアカウントです。すなわち**ペースプレッシャー**が最も高いもので、これは残りの週次パーセントをそのアカウントの週次リセットまでの時間で割った値と定義されます。最も多くのクォータを失効させかけているアカウントが勝ちます。同点の場合は週次期限が最も早いもの、次に7日間使用量が最も低いものへとタイブレークします。

すべては絶対 UTC エポックとして保存されたキャッシュ済みウィンドウで動作するため、古いスナップショットでも正しく解決されます。すでに過ぎた週次リセットは正確な7日刻みで先へ外挿され、キャッシュ済みリセットを過ぎたウィンドウは新しく空とみなされます (切り替える理由にも、アカウントをベンチに置き続ける理由にもなりません)。

### グリーディパスとハードパス

- **グリーディパス** (エンゲージ済みだが、すべてのバー未満): 現在のアカウントを含むすべてのアカウントをランク付けします。現在のアカウントがすでに勝っているか同点なら、何もしません。そうでなければ厳密により良いアカウントへ切り替えます。決して待機せず、事前パークもしません。使用可能な現在のアカウントを待機と引き換えにすることはありません。現在のアカウントもランク付けされるため、自動パスと引数なしの `tokenmaxxing switch` はどちらも冪等です。定期的に評価すると正しいアカウントに収束し、その後はそのまま留まります。
- **ハードパス** (バーを超えた): 最良の使用可能な候補へ切り替えます。候補のリフレッシュトークンが失効していると判明したら、そのアカウントは再認証が必要としてフラグされ、次の候補が試されます。何も使用可能でなければ枯渇待機ロジックが動きます。実際にセッションを一時停止できる呼び出し元 (スーパーバイズされた Stop フック) だけが、まだブロックされているが最も早く回復するアカウントへの事前パークを許可されます。

### モデルごとの上限

`policy.switchModels` (デフォルト `["fable"]`) は、モデルごとの週次上限が切り替えをトリガーできるモデルファミリーを指定します。マッチングはファミリートークンによって行われ、正確な表示文字列では決して行われません。モデルの表示名は変動し (「Fable」は「Fable 5」になりました)、正確な文字列によるゲートはかつてモデルごとの切り替えを丸ごと無効にしてしまったことがあります。関連する2つの安全ルールがあります。

- 不明なアクティブモデルは、設定されたすべてのファミリーをゲートします。切り替えがスナップショットをクリアした直後、ヘッドレスなマシンはモデル不明で動作することがあります。不明を無制約として扱っていたために、あるアカウントが Fable 上限のまま何時間も気付かれずに留まったことがありました。
- 候補スクリーニングはゲートされたモデルごとの上限も数えるため、すべてのアカウントが Fable 上限を使い切ったプールはラウンドロビンしません。

### クールダウン

45秒の切り替え後クールダウンが自動パスをゲートします。statusline の tee も切り替え後の同じ45秒間は抑制されます (採用には macOS で最大30秒かかります)。そうしないと、より早い評価が切り替え自身によって無効化されたデータ上で走ってしまいます。まさにこのシナリオが、かつて A から B へ、そして戻る再起動ループを生み出しました。手動の `tokenmaxxing switch` はクールダウンの影響を受けません。

## 設定

設定は `~/.config/tokenmaxxing/config.json` の JSON です。すべてのフィールドは任意で、デフォルトはフィールドごとに適用されます。

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: 上で説明したスクリーニングバー。
- `policy.projectionMargin`: 有効バーを形成するために両方のバーから引かれる値。
- `policy.greedySessionFloor`: グリーディ収束がエンゲージするセッション使用パーセント。
- `policy.switchModels`: モデルごとの週次上限が切り替えをゲートするモデルファミリー (エントリは読み込み時に小文字化されます)。
- `policy.usagePollTtlMs`: `/usage` のモデルごとポーリングが新鮮なまま保たれる期間。
- `policy.maxWaitMs`: プール枯渇時の自動待機の上限。

`tokenmaxxing config` は有効な設定とそのソースを表示します。`config set` / `unset` はドット区切りキーを編集します。`config tidy` は不明なキーを削除します。

## 状態ディレクトリのレイアウト

すべては `~/.config/tokenmaxxing/` の下に存在します (`TOKENMAXXING_HOME` で上書き可能。外部から観測可能なパスにはそれぞれ env オーバーライドがあるため、ツール全体をテストで密閉的に実行できます)。

| パス | 保持内容 |
|---|---|
| `config.json` | あなたの設定 (疎で、デフォルトはフィールドごとに適用される) |
| `accounts.json` | プールされた Claude アカウントの非機密インデックス。ラベル、ID、キャッシュ済み使用量ウィンドウ。トークンは決して含まない |
| `usage.json` | statusline の tee による集計ウィンドウのスナップショット。その mtime がフィードの生存ハートビート |
| `model-usage.json` | `/usage` からの TTL キャッシュ済みのモデルごとの週次上限 |
| `lastswap.json` | 直近の切り替えのエポックタイムスタンプ。45秒のクールダウンを駆動する |
| `lock` | 切り替えを直列化する `flock` ファイル |
| `tokenmaxxing.log` | 追記のみのイベントログ |
| `bin/` | PATH シム。`claude`、`codex`、および `tokenmaxxing` / `xx` のエントリポイント |
| `respawn/<session-id>` | スーパーバイザーが監視する枯渇待機の再起動マーカー |
| `creds/` | Linux のみ。0700ディレクトリ内の0600のパーク済み認証情報ファイル (macOS は代わりにアカウントごとのキーチェーンアイテムとして認証情報をパークする) |
| `onboard/`, `sample/` | `add` / `auth` のログインとパーク済みアカウントの `/usage` プローブのための使い捨ての分離設定ホーム。平文の認証情報を保持する onboard ホームは取り込み後に削除される |
| `slack.json` | `xx serve` のトークンとチャンネルリンク (0600) |
| `slack-threads/` | `xx serve` のスレッドごとのセッションレコード |
| `codex-*` | 並列した Codex プール。`codex-accounts.json`、`codex-lastswap.json`、`codex-lock`、`codex-creds/`、`codex-onboard/`、`codex-respawn/`、および `codex-live/` (実行中のスーパーバイズされた codex セッションごとに1つの PID 検証済みプレゼンスファイル。そのためライブアカウントが切り替えターゲットになることは決してない) |

自身のディレクトリの外で、tokenmaxxing が触れるのは正確に次のものだけです。`~/.claude.json` (`oauthAccount` の切り替え)、Claude Code の `settings.json` (フックと statusline のエントリ)、ライブ認証情報ストア (macOS では `Claude Code-credentials` キーチェーンアイテム、Linux では `.credentials.json`)、`~/.claude.lock` (切り替え中に取得する claude のリフレッシュロック)、codex の `auth.json` と `hooks.json`、そして launchd または systemd の定期チェックユニット。

## 認証情報の保管と安全性モデル

すべての状態は `~/.config/tokenmaxxing/` に存在します。認証情報の I/O は単一のプラットフォーム選択済みストアファサードを通ります。呼び出し側がプラットフォームで分岐することはありません。

**macOS**: 認証情報は Claude Code 自身が保管するのと同じ場所である、ログインキーチェーンの generic-password アイテムに存在します。ライブアイテムは claude が読むもので、プール内の各アカウントのバックアップは自身の `tokenmaxxing-cred-<uuid8>` キーチェーンアイテムとしてパークされます。ディスク上に平文のものはありません。読み取りは `security find-generic-password -w` を使い (秘密は stdout にしか現れません)、書き込みは `add-generic-password` の行を stdin 経由で `security -i` にパイプするため、秘密がどのプロセスの argv にも現れません。対話モードには約4 KB の行バッファがあるため、大きすぎる blob は argv 書き込みにフォールバックします。これがパークアイテムが最小限の OAuth オブジェクトだけを保存する理由の1つです。

**Linux**: Claude Code は認証情報を0600の平文ファイルとして保存し、tokenmaxxing も同じモデルに従います。ライブファイルは claude 自身の `.credentials.json` であり、パークバックアップは0700ディレクトリ内の `~/.config/tokenmaxxing/creds/` 下のアトミックな0600ファイルです。ここでのアトミックとは、一時ファイルへの書き込み、fsync、そしてリネームを意味します。同時実行の読み手は常に古いファイル全体か新しいファイル全体を見て、部分的なものは決して見ません。

切り替えが強制する安全ルールは次のとおりです。

- **真の所有者による取り込み。** 切り替え前に、ライブ認証情報の実際の所有者は、そのトークンがどの組織に属するかを API に問い合わせて解決されます (OAuth roles エンドポイントに対する `fetchTokenOrg`)。変動しうる保存済みのアクティブラベルを信頼することは決してありません。変動したラベルがかつて、あるアカウントの取り込みが別のアカウントの唯一のバックアップを上書きする原因になりました。ライブ認証情報がプール外のアカウントに属している場合、切り替えはそれを潰す代わりに完全に拒否します。
- **単一のクリティカルセクション。** 取り込み、新しい認証情報のインストール、そのローテートされたトークンのバックアップ、`~/.claude.json` のアカウント切り替え、アクティブラベルのコミットは、すべて同じロックされたセクション内で行われます。
- **claude 自身のリフレッシュとのインターロック。** 期限が近いセッションはいつでも自分のトークンをローテートしうるため、認証情報の書き込みは Claude Code のリフレッシュロックも取得します (ベストエフォートで、古いロックの再取得と上限付きタイムアウトを伴います)。
- **失効したグラントは正常に劣化する。** `invalid_grant` が返ってきたリフレッシュは、そのアカウントを再認証が必要としてフラグし、エラーが伝播する前にフラグを保存するため、リトライループは候補集合を縮小して終了します。`tokenmaxxing auth` はフラグされたアカウントをその場で修正し、修正対象とは別のアカウントに着地するログインを拒否します。
- **トークンのロギングなし。** トークンはログ、エラー、出力に決して現れません。トークンおよび使用量エンドポイントからのエラー本文は生のまま表に出ることはなく、許可リストに載ったフィールドのみが残ります。トークンエンドポイントの失敗本文はリクエスト内容をそのまま返すことがあるためです。
- **プローブの衛生。** 起動されるあらゆる `claude` プローブは、claude がキーチェーン参照の前に尊重する8つの環境変数 (`ANTHROPIC_API_KEY`、`CLAUDE_CODE_OAUTH_TOKEN`、`CLAUDE_SECURESTORAGE_CONFIG_DIR` など) を消去するため、プローブが誤ったアカウントに帰属されることは決してありません。

## プラットフォームメモ: macOS と Linux

| | macOS | Linux |
|---|---|---|
| ライブ認証情報 | ログインキーチェーンの generic-password アイテム | 0600 `.credentials.json` ファイル |
| パーク済み認証情報 | アカウントごとのキーチェーンアイテム | 0700ディレクトリ内の0600ファイル |
| 切り替え後の採用 | 約30秒以内 (キーチェーン読み取りキャッシュ) | 次のリクエスト (ファイル mtime ポーリング) |
| 定期チェック | launchd エージェント、180秒ごと | systemd ユーザータイマー、180秒ごと |
| 分離ログインストア | 設定ディレクトリごとにハッシュ名前空間化されたキーチェーンサービス | 分離設定ディレクトリ内のファイル |

知っておく価値のある Linux 固有の詳細が2つあります。claude は認証情報ディレクトリをまず `CLAUDE_SECURESTORAGE_CONFIG_DIR` から解決し (次に `CLAUDE_CONFIG_DIR`、次に `~/.claude`)、tokenmaxxing はその解決を正確にミラーするため、2つが乖離することはありません。そして同じ claude バージョンの2つの OS ビルドは、`/usage` のリセット時計を異なる形式でフォーマットします (一方は " at " の接着、もう一方はカンマを使う)。tokenmaxxing のパーサーはまさにその2つの形式を受け入れ、3つ目に対しては推測せずログを出します。

macOS では、正直な制限が1つあります。`init` と `add` は意図的にキーチェーンに対話的に触れるため、最初の `security` アクセスがヘッドレスフック内でコールドにならないようにしています。

## statusline

tokenmaxxing は Claude Code の statusline をネイティブに描画します (使用量フィードを tee しながら)。設計原則は、クォータは数字ではなく色で表す、というものです。1行の例を示します。

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- 各ウィンドウのトークンはリセットまでの時間を表し、使用パーセントに応じて緑から黄、赤への連続ランプで着色されます (端末が対応していれば truecolor、そうでなければ256色キューブへ段階化されます)。ランプは0で純緑、75で黄、95以上で赤にアンカーされるため、以前の重大度バンドがランプアンカーとして残ります。
- モデル名は同じランプ上でコンテキストウィンドウの充填によって着色されます。
- 緑の `◆` がアクティブアカウントのウィンドウを先導します。パーク済みの各アカウントは自身のシアンの `◇` を得ます (再認証が必要なら赤の `✗`)。アカウントは次に来るリセットが最も早い順にソートされます。
- モデルごとの情報は各ブロックの先頭に、着色された頭文字だけで現れます。Fable は `𝒇` を描画します。他のファミリーは大文字化した頭文字を使い、常にファミリーでマッチされます。
- 手つかずのパーク済みアカウントは緑の `full` を描画します。リセットが不明な計測済み使用量は着色された `?` を描画し、ゲートされたモデルの未計測のモデルごと上限は着色されない `𝒇?` を描画します。未計測は決して安全に見えてはなりません。
- リセットカウントダウンは最大の単位のみを表示し、"now" や "0m" は決して表示しません。次に来るリセットがないウィンドウは緑の `0` を描画します (再び空)。
- リンクされた git ワークツリーのベース名が行を先導します。メインチェックアウトではそこに何も描画しません。この検出はファイルシステムから `.git` ファイルを読み取り、git サブプロセスを決して起動しません。
- `NO_COLOR` が設定されている場合、行は接着された数値形式にフォールバックします (`2h5` は2時間後にリセット、5%使用を意味し、`ctx 42` はコンテキスト充填を表す)。色がなければ、消費済みのウィンドウが新鮮に見えてはなりません。

サブエージェントのタスクは、claude の subagentStatusLine サーフェスを通じて独自のパネル行を得ます。アクティブなタスクごとに1行で、ファミリー名はそのタスクのコンテキスト充填によって着色されます。

## Codex サポート

同じプーリングが OpenAI の Codex CLI に対しても、自分自身の ChatGPT サブスクリプションアカウントに対して機能します。

```sh
tokenmaxxing init --codex   # 現在の codex ログインをインポートし codex スーパーバイザーと Stop フックをインストールする
tokenmaxxing add --codex    # 別のアカウントを分離してログインする。主要ログインには触れない
codex                       # これまでどおり codex を使う
```

Codex プールは完全に並列した状態です。独自のアカウントインデックス、独自のパーク済み認証情報ファイル (codex 自身のストアが平文ファイルであるため、両プラットフォームで0600ファイル)、独自のロック、独自の直近切り替えタイムスタンプを持ちます。判断ポリシーのコードを除いて、Claude プールと共有されるものは何もありません。

### なぜ Codex ではホットスワップが不可能なのか

実行中の codex プロセスは1つのインメモリ認証マネージャーを保持し、`auth.json` が別のアカウントを指すようになると明示的にリロードを拒否します。ファイルウォッチャーもリクエストごとの認証情報ポーリングもないため、実行中の codex の裏で入れ替えられた認証情報は推論には決して反映されません。再起動が切り替えです。`codex resume <session-id>` は、`auth.json` が今保持しているアカウント上でローカルのトランスクリプトを継続します。

tokenmaxxing はこれを codex スーパーバイザーシムで処理します。Stop フックが各ターン境界で同じグリーディなペースプレッシャー判断を実行し、切り替えるときはマーカーを書き込みます。それによりスーパーバイザーはコミット済みの境界でセッションに SIGTERM を送り、新しいアカウント上でトランスクリプトを保ったまま `codex resume <session-id>` を再起動します。すべての codex 切り替えは目に見える再起動であるため、codex のグリーディパスは1.2倍の改善マージンを持ちます。挑戦者は現在のアカウントのペースプレッシャーをわずかにではなく20%上回らなければなりません。ハードパス (バーを超えた) はマージンを無視します。codex には枯渇プールのカウントダウンもありません。codex セッションを一時停止できるものは何もないため、完全に枯渇した codex プールはそのまま留まります。

その他の codex 固有の仕組み:

- 使用量は、codex 自身のレート制限エンドポイントに対する無料の認証済み GET から読み取られます (CLI の `/status` が行うのと同じ呼び出し)。パーセンテージに加えて絶対エポックのリセット時刻、集計ウィンドウとモデルごとの上限の両方です。ウィンドウ分類は位置ではなく期間で決まります。現在のプランには5時間ウィンドウがまったくない場合があり、週次ウィンドウが主要スロットに座っているためです。
- Codex のリフレッシュトークンはローテートし、置き換えられたものを再利用するとグラントファミリー全体が失効します。すべてのローテーションは返ってきた瞬間に保存され、アクティブアカウントは常にライブ blob を通じてのみサンプリングされ (古いパークコピーを通じては決して行われません)、セッションごとのプレゼンスファイルにより、ライブの兄弟セッションで動作しているアカウントが切り替えターゲットになることも、そのパークトークンがリフレッシュされることもないようにします。
- Codex はファイル認証情報ストアを必要とします。`init --codex` はキーリングストアが固定されている場合は速やかに失敗し、`add --codex` は分離オンボーディングホームにファイルモード設定を書き込むため、ログインが取り込み可能な形で着地します。
- 手動ステップが1つあります。codex は信頼するよう指示されていないフックをスキップします。`init --codex` の後、codex を1度開いて `/hooks` から tokenmaxxing の Stop フックを信頼してください。さもないと自動切り替えは静かに不活性のままです。`init --codex` はこのリマインダーを表示します。

## Slack ブリッジ: xx serve

`tokenmaxxing serve` は Socket Mode 上でローカルの Slack デーモンを実行します。公開 URL は不要です。セットアップ:

```sh
tokenmaxxing serve setup                    # アプリマニフェストを表示し、2つのトークンの入力を求める
tokenmaxxing serve link <channel-id> <repo> # チャンネルをリポジトリのチェックアウトに紐づける
tokenmaxxing serve                          # デーモンを実行する
```

リンクされたチャンネルでボットにメンションすると、そのスレッド用に、リンクされたリポジトリのチェックアウト内で Claude Code セッションを開きます。すべてのスレッドメッセージは `resume` 付きの1回の Agent SDK `query()` を実行し (持続的なストリーミングクエリではありません)、そのため `ensureBestAccount()` が毎ターンごとにプールを再評価し、デーモンはスレッドを失うことなく再起動できます (スレッドレコードは永続的で、デーモンは起動時にそれらを再購読します)。

注目すべき挙動:

- **ストリーミング**: 返信は思考とツール実行のためのタスクカード、ハイライト付きで描画されるフェンス付きコード、コストと所要時間を含む締めの「Turn」カードとともに Slack へネイティブにストリームされ、ツール実行がストリームされたテキストを中断するたびに新しい Slack メッセージが開かれるため、1つのターンがツール実行の周りで別々のメッセージとして読めます。TodoWrite の呼び出しは1つの安定したチェックリストカードをその場で更新します。
- **権限**: リンクごとの `permissionMode` はデフォルトで `acceptEdits` です。`--yolo` (エイリアス `--dangerous`) はリンクを `bypassPermissions` にオプトインします。対話ダイアログはリレーされたターンでは許可されません。Slack を通じて誰も答えられないためです。そのためモデルは散文で尋ね、あなたのスレッド返信が次のターンになります。同梱のプラグインスキルが、判断が必要なときにリクエスト元をタグ付けしてターンを終える方法を教えます。
- **スラッシュコマンド**: メンションを除いたテキストが `/` で始まるスレッドメッセージは、claude のスラッシュコマンドとして実行されます。Slack のコンポーザーは `/` で始まるメッセージを飲み込むため、メンション優先の形式 (`@bot /usage`) または先頭スペースを使ってください。
- **グレースフルシャットダウン**: SIGTERM/SIGINT はドレインします。新しいターンは声高にドロップされ、進行中のターンには最大5分が与えられ、claude の子プロセスは独自のプロセスグループで detached で動作するため、端末の Ctrl-C がドレインによってターンが保全される前に子プロセスを殺すことはできません。
- **スレッドのクリーンアップ**: 作業が完了したと伝えると、モデルはインプロセスの `finish_thread` ツールを呼びます。ターンが完全に終わった後、デーモンはスレッドレコードを削除し、購読を解除し、確認を1つ投稿します。新しいメンションが新しいセッションを開始します。
- **エラーの衛生**: ターンエラーは、生のエラー本文ではなく、切り詰めたメッセージのみのテキストを投稿します。

## Agent SDK サーフェス

パッケージのプログラム的エントリ (`exports["."]` は `src/sdk.ts` を指します) は、自分自身のプールされたアカウントに対して構築するエージェントのために、tokenmaxxing を Claude Agent SDK と組み合わせます。アプリは Bun 上で動作する必要があります (tokenmaxxing は TypeScript ソースを配布し `bun:ffi` を使うためです)。

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK は `query()` ごとに claude サブプロセスを起動し、認証情報を起動時に1度だけ読みます (statusline なし、クエリ途中のホットスワップなし)。そのため統合は境界駆動です。

- `ensureBestAccount()` は CLI のフックとタイマーが実行するのとまったく同じ判断であり (バー、ペースプレッシャー、クールダウン、すべて共有コード)、決して先読み的ではありません。SDK セッションは枯渇カウントダウンのために一時停止されることは決してありません。
- `pooledOptions()` は `pathToClaudeCodeExecutable` を本物の claude バイナリ (スーパーバイザーラッパーではない) に固定し、あらゆる周辺の認証情報オーバーライドを消去した完全な置き換え `env` を供給します。アプリの環境に `CLAUDE_CONFIG_DIR` または `CLAUDE_SECURESTORAGE_CONFIG_DIR` が設定されている場合は速やかに失敗します。Linux では、切り替えがそれらの指す先にライブ認証情報を書き込む一方で、消去されたサブプロセスはデフォルトのストアを読むという、静かな誤アカウントの乖離になるためです。
- `stopHookCheck` はターン境界で判断を再実行します。それが着地させた切り替えは次の起動時に反映されます。自身のエラーを (stderr とログに記録して) キャッチし、再スローしません。未処理のフック例外はエージェントを中断しうるため、そして壊れた切り替えチェックのためにターンを中断するコストは、現在のアカウントに乗り続けるコストより大きいためです。

`sdk.ts` は Agent SDK 自体からは何もインポートしません。その値は SDK のオプションに構造的にスプレッドされます。

## ビルドと配布

npm パッケージはビルド成果物ではなく TypeScript ソースを配布します。`tokenmaxxing` の bin は Bun のシバンとともに `src/main.ts` を直接指し、Bun 1.2.6 以降はそれをそのまま実行します。これが Bun が必須要件である理由です。コンパイル済みバイナリは設計上存在しません。初期のリリースは単一の61 MB の macOS バイナリをすべてのプラットフォームに配布し、Linux では `exec format error` で失敗しました。プラットフォームごとのコンパイル済みパッケージはそれぞれ独自のリリースパイプラインを必要とするため、Bun によるソース実行が配布モデルになりました。

パッケージの `exports` マップは、上で説明したプログラム的エントリとして `src/sdk.ts` を公開します。リリースは GitHub 上で `v<version>` としてタグ付けされます。CI は trusted publishing (OIDC、来歴付き) を通じて npm に公開し、公開ゲートはまず型チェックとフルのテストスイートを実行します。

## 個人利用と利用規約 [#personal-use-and-terms-of-service]

tokenmaxxing は、自分が保有するアカウントを、自分自身が実行するセッションやエージェントの中でプールします。この文言は意図的なものです。Anthropic はサードパーティ製品が claude.ai のログインや claude.ai のレート制限を提供することを許可しておらず、それには Agent SDK 上に構築されたエージェントも含まれます。プールされた SDK サーフェス、またはそれの上に構築されたものを、サードパーティに提供しないでください。tokenmaxxing はまた、OAuth を再実装したり API トラフィックをプロキシしたりする代わりに、クォータデータについては意図的に CLI 経由の `/usage` パスに留まります。これはプロキシではなく、触れる唯一の OAuth エンドポイントは、切り替え中に使われる標準のリフレッシュグラントと、トークンが実際にどのアカウントに属するかを検証する読み取り専用の識別チェック (roles エンドポイント) だけです。

## 正直な制限

- **1回のコールドターン。** プロンプトキャッシュは組織スコープであるため、新しいアカウントでの最初のターンは1度だけコンテキストを再アップロードします。
- **枯渇一時停止のしゃっくり。** 完全に枯渇したプールだけがカウントダウンのためにセッションを止めます。その一瞬にタイプされたものは失われます。
- **採用ラグ。** macOS では切り替えから約30秒以内の最初のターンが依然として古いアカウントを計測することがあります。バーの余裕がそれを吸収します。
- **共有の爆発半径。** デフォルトプロファイルのすべてのセッションが1つのライブ認証情報を共有するため、切り替えはそれらすべてを一緒に移動させます (各セッションがその場で採用します)。
- **Linux での平文認証情報。** Claude Code 自身が Linux の認証情報を0600の平文ファイルとして保存します。tokenmaxxing のパークコピーも同じモデルに従います。

## トラブルシューティングと FAQ

**`claude` がスーパーバイズされていないようです。**
`tokenmaxxing doctor` を実行してください。シムは PATH 解決で勝たなければなりません。シェル rc の `# tokenmaxxing PATH` 行が現在の bin ディレクトリを指し、本物の claude より前に位置していることを確認してください。`doctor` はまた、ラッパーを覆い隠す `alias claude=...` や `claude()` シェル関数について、そして claude バイナリを絶対パスで起動するエイリアス (それらはスーパーバイザーを完全にバイパスします) について警告します。

**Codex で自動切り替えがまったく発火しません。**
codex は信頼するよう指示されていないフックをスキップします。codex を開き、`/hooks` を実行し、tokenmaxxing の Stop フックを信頼してください。信頼はフックのハッシュに対して記録されるため、フックが編集されたら再付与が必要です。

**statusline であるアカウントが赤い `✗` を示します。**
そのリフレッシュトークンが失効しています (取り消されたか、バックアップの裏でローテートされた)。`tokenmaxxing auth <sel>` を実行してその場で再認証してください。コマンドはどのメールでサインインするか伝え、別のアカウントに着地するログインを拒否します。

**なぜ最も残りクォータの多いアカウントに切り替えないのですか。**
それがクォータを失効させるリスクが最も高いアカウントではないからです。ターゲットは自分自身の週次ペースから最も遅れているアカウントです。すなわち残りパーセントを週次リセットまでの時間で割ったものです。残りが等しい場合はこれが期限の早い順に、期限が等しい場合は残りの多い順に帰着します。

**今切り替えたのに statusline がまだ古いアカウントを示しています。**
macOS では最大約30秒間、これは想定内です。実行中のセッションは次の認証情報キャッシュのリフレッシュで、入れ替えられた認証情報を採用します。使用量 tee はまさにこの理由で切り替え後45秒間抑制されます。

**`status --force` はコストがかかりますか。**
はい、意図的にです。各アカウントに最小限の計測 haiku リクエストを1回送り、すべての5時間セッションウィンドウが休眠したままにならずその瞬間に開始されるようにしてから、新しくサンプリングします。通常の `status` と `watch` は決して ping しません。`/usage` の読み取りは無料です。サーバーの使用量フィードは新しく開いたウィンドウを数秒から数分遅延させることがあるため、ping 直後のプローブはまだ ping 前の状態を示すことがあります。`status` は ping が失敗したふりをする代わりにメモを描画します。

**`/usage` プローブがアクティブアカウントに対して何も返しませんでした。**
それは既知の claude の挙動です。内部の使用量フェッチが失敗またはレート制限されると、`/usage` はローカルのセッション統計のみをパーセンテージ行なしで表示します。tokenmaxxing はまさにこれを避けるために、アクティブアカウントを statusline のプッシュからサンプリングし、パーク済みのアカウントのみをプローブします。

**バックグラウンドの claude セッション。**
claude のバックグラウンドデーモンは、本物のバージョン付きバイナリを絶対パスで起動し、PATH シムをバイパスするため、バックグラウンドセッションはスーパーバイズされません。フックは依然として `settings.json` を通じて発火し、認証情報の採用と定期タイマーが切り替えをカバーしますが、それらにはマーカー駆動の再起動はありません。

**かつて何かが大量のプロセスを起動しました。それはまだ起こりうるのですか。**
スーパーバイザーはまさにその過去の障害 (古いラッパーが「本物の」claude として固定される) に対して、多層の再帰ガードを備えています。5レベルで中止する環境内の深さセンチネル、ディスク上の起動レート制限、tokenmaxxing 自身の bin ディレクトリに解決し直すあらゆる候補を拒否する realpath の識別チェック、そして設定された claude パスが存在しなくなったときの (静かな PATH スキャンではなく) ハード失敗です。`init` と `doctor` は、固定する前に `--version` を実行して候補が実際に claude であることを検証します。

**アンインストール。**
`tokenmaxxing uninstall` はスーパーバイザーシム、設定エントリ、定期タイマーを削除し、あなたのアカウントとパーク済みの認証情報はそのまま残します。自身のものと認識する statusline エントリのみを削除します。
