相同嘅集合方式適用於 OpenAI 嘅 Codex CLI，對住你自己嘅 ChatGPT 訂閱帳戶：

```sh
tokenmaxxing init --codex   # 匯入你當前嘅 codex 登入 + 安裝 codex 監督者同 Stop hook
tokenmaxxing add --codex    # 用隔離方式登入另一個帳戶 - 你嘅主要登入唔會被掂
codex                       # 照舊咁用 codex
```

Codex 帳戶池係完全並行嘅狀態：佢自己嘅帳戶索引、佢自己嘅泊存憑證檔案（兩個平台上面都係 0600 檔案，因為 codex 自己嘅儲存係一個明文檔案）、佢自己嘅鎖、佢自己嘅上次切換時間戳。除咗決策策略嘅程式碼之外,無嘢同 Claude 帳戶池共用。

## 點解 Codex 上面熱切換係不可能

一個正在運行嘅 codex 進程持有一個記憶體內嘅 auth manager，並且喺 `auth.json` 而家指向一個唔同帳戶嗰時明確拒絕重新載入佢。無檔案監視者亦都無每請求嘅憑證輪詢，所以喺一個正在運行嘅 codex 下面換咗嘅憑證對推理嚟講根本唔會生效。重新啟動就係切換：`codex resume <session-id>` 會喺 `auth.json` 而家持有嘅任何帳戶上面繼續本地嘅轉錄稿。

tokenmaxxing 用一個 codex 監督者 shim 處理呢個：Stop hook 喺每個回合邊界行相同嘅貪婪步伐壓力決定，而當佢切換時，佢會寫一個標記令監督者喺已提交嘅邊界 SIGTERM 個 session，並喺新鮮帳戶上面重新啟動 `codex resume <session-id>`，轉錄稿完好無缺。因為每次 codex 切換都係一次睇得到嘅重新啟動，所以 codex 貪婪路徑帶有一個 1.2 倍嘅改善邊際：一個挑戰者必須將當前帳戶嘅步伐壓力勝過 20%，唔可以係差一啲啲。強硬路徑（一條被跨越嘅界線）忽略嗰個邊際。codex 亦都無帳戶池耗盡倒數 - 無嘢可以暫停一個 codex session - 所以一個完全耗盡嘅 codex 帳戶池會留喺度。

其他 codex 專屬機制：

- 用量係由一個對住 codex 自己嘅速率限制端點嘅免費已認證 GET 讀取（同 CLI 嘅 `/status` 所做嘅同一個呼叫）：百分比加上絕對 epoch 重設時間，總量窗口同每模型上限都一樣。窗口分類係按持續時間，永遠唔係按位置，因為當前計劃可能根本無 5 小時窗口，而每週窗口坐喺主要位置。
- Codex 刷新 token 會輪換,而重用一個已被取代嘅就會殺死成個授權系列。每次輪換都會喺佢返嚟嗰一刻保存，活躍帳戶永遠只會透過活躍 blob 採樣（永遠唔會係一個過時嘅泊存副本），而每 session 嘅存在檔案確保一個喺活躍兄弟 session 運行嘅帳戶永遠唔會係一個切換目標亦都永遠唔會令佢嘅泊存 token 被刷新。
- Codex 需要檔案憑證儲存：如果 keyring 儲存被固定，`init --codex` 會快速失敗，而 `add --codex` 會將檔案模式設定寫入隔離嘅入職 home 令個登入落喺可收集嘅狀態。
- 一個手動步驟：codex 會跳過佢未被告知去信任嘅 hook。喺 `init --codex` 之後,開一次 codex 並透過 `/hooks` 信任 tokenmaxxing Stop hook，否則自動切換會靜靜哋保持無效。`init --codex` 會列印呢個提醒。
