tokenmaxxing स्वचालित Claude Code खाता स्विचिंग के लिए एक CLI है। यह आपके स्वामित्व वाले कई सब्सक्रिप्शन (Pro/Max) खातों को पूल करता है और जब उपयोग में मौजूद खाता किसी उपयोग सीमा के करीब पहुंचता है, तो सक्रिय क्रेडेंशियल को एक ताज़ा खाते पर हॉट-स्वैप कर देता है। आप `claude` को ठीक वैसे ही चलाते हैं जैसे हमेशा चलाते हैं; स्वैप एक सुरक्षित टर्न सीमा पर होता है और आपका चालू सेशन बिना पुनः आरंभ किए नए खाते पर उसी बातचीत को जारी रखता है। यह एक साथ कई समवर्ती सेशन में काम करता है।

एकमात्र दिखाई देने वाला व्यवहार सबसे खराब स्थिति है: जब पूरा पूल अपनी सीमा पर होता है, तो सेशन एक काउंटडाउन के साथ रुक जाता है और रीसेट होने वाले अगले खाते पर स्वतः फिर से शुरू हो जाता है (Ctrl-C तुरंत फिर से शुरू कर देता है)।

<Callout>
दायरा: macOS और Linux पर Claude Code, साथ ही एक दूसरे, समानांतर पूल के रूप में OpenAI का Codex CLI। यह सब्सक्रिप्शन खातों को पूल करता है, API कुंजियों को नहीं। यह आपके स्वामित्व वाले खातों को, उन सेशन और एजेंट में जिन्हें आप स्वयं चलाते हैं, पूल करने के लिए एक व्यक्तिगत-उपयोग टूल है - देखें [व्यक्तिगत उपयोग और सेवा की शर्तें](#personal-use-and-terms-of-service)।
</Callout>

## समस्या

एक Claude सब्सक्रिप्शन एक साथ तीन सीमाओं को मापता है (सभी `/usage` के माध्यम से पुष्टि की गई):

- **वर्तमान सेशन**: एक रोलिंग 5-घंटे की विंडो।
- **वर्तमान सप्ताह (सभी मॉडल)**: एक 7-दिन का समुच्चय।
- **वर्तमान सप्ताह, प्रति मॉडल**: अलग-अलग मॉडल परिवारों के लिए अलग साप्ताहिक सीमाएं। ये वर्तमान में केवल Sonnet और Fable के लिए मौजूद हैं, और केवल Fable की सीमा इतनी सख्त है कि मायने रखे - यह समुच्चय से काफी पहले लागू होती है। एक मशीन week-all पर 50% पर हो सकती है जबकि week-Fable पर पहले से ही 80% पर हो।

साप्ताहिक कोटा उपयोग-करें-या-खो-दें है: किसी खाते ने अपने निश्चित साप्ताहिक रीसेट तक जो भी उपभोग नहीं किया है वह ज़ब्त हो जाता है। यदि आपके पास कई खाते हैं, तो तर्कसंगत रणनीति यह है कि जो भी खाता अपनी साप्ताहिक गति से सबसे अधिक पीछे है उस पर कोटा खर्च करते रहें, और किसी भी एकल सीमा के सेशन के बीच में दीवार से टकराने से पहले स्विच कर जाएं।

इसे हाथ से करने का मतलब है लॉग आउट करना, लॉग इन करना, और अपनी बातचीत खो देना। tokenmaxxing इसे स्वचालित करता है: एक चालू `claude` अनुरोधों के बीच अपने क्रेडेंशियल स्टोर की फिर से जांच करता है, इसलिए उसके नीचे स्वैप किया गया क्रेडेंशियल अपनी जगह पर अपना लिया जाता है (macOS पर लगभग 30 सेकंड के भीतर, Linux पर अगले अनुरोध पर)। एक सामान्य स्वैप आपके सेशन को कभी पुनः आरंभ नहीं करता। एकमात्र स्थिति जिसमें अभी भी प्रोसेस प्रबंधन की आवश्यकता होती है वह है पूरी तरह से समाप्त पूल - एक सेशन खुद को रोक नहीं सकता - और इसी के लिए पतला सुपरवाइज़र मौजूद है।

`claude` के बारे में बाकी सब कुछ अपरिवर्तित है: सभी फ्लैग, MCP सर्वर, हुक, और स्किल पास-थ्रू होते हैं।

## त्वरित आरंभ

macOS या Linux पर [Bun](https://bun.sh) और Claude Code की आवश्यकता होती है।

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` पांच काम करता है:

1. उस खाते को आयात करता है जिसमें आप पहले से लॉग इन हैं, खाता #1 के रूप में (कोई अलग `adopt` कमांड नहीं है)।
2. `claude` सुपरवाइज़र शिम इंस्टॉल करता है।
3. Claude Code के `settings.json` में तीन प्रविष्टियां इंस्टॉल करता है: एक statusLine, एक Stop हुक, और एक SessionStart हुक (साथ ही एक subagentStatusLine प्रविष्टि)।
4. सुपरवाइज़र की bin डायरेक्टरी को आपके शेल rc के PATH में जोड़ता है (idempotent, `# tokenmaxxing PATH` टिप्पणी के साथ चिह्नित)। इसे रोकने के लिए इसे PATH पर असली `claude` से आगे रहना होता है।
5. एक आवधिक जांच टाइमर इंस्टॉल करता है (macOS पर एक launchd एजेंट, Linux पर एक systemd उपयोगकर्ता टाइमर) जो हर 180 सेकंड में `tokenmaxxing check` चलाता है।

अपना शेल पुनः आरंभ करें, फिर और खाते जोड़ें और आगे बढ़ें:

```sh
tokenmaxxing add        # एक और खाते को अलगाव में लॉग इन करता है और उसे पूल करता है
claude                  # हमेशा की तरह claude का उपयोग करें
```

`tokenmaxxing` को `xx` के रूप में भी उपनामित किया गया है। सादा `tokenmaxxing` (या `xx`) `status` चलाता है; `switch` स्पष्ट रहता है।

## कमांड

| कमांड | यह क्या करता है |
|---|---|
| `tokenmaxxing init` | वर्तमान खाता आयात करें, सुपरवाइज़र, हुक, और statusline इंस्टॉल करें |
| `tokenmaxxing init --codex` | Codex के लिए वही: लॉगिन आयात करें, codex सुपरवाइज़र और Stop हुक इंस्टॉल करें |
| `tokenmaxxing add` | एक अतिरिक्त खाता पंजीकृत करें (पृथक लॉगिन, पूल में हार्वेस्ट किया गया) |
| `tokenmaxxing add --codex` | एक अतिरिक्त Codex खाता पंजीकृत करें (पृथक लॉगिन) |
| `tokenmaxxing auth [sel \| --all]` | किसी पूल किए गए खाते को उसकी जगह पर पुनः प्रमाणित करें। सादा पूल की सूची देता है और पूछता है कि कौन सा; एक चयनकर्ता एक खाते को लक्षित करता है और आपको बताता है कि किस ईमेल से साइन इन करना है; `--all` हर एक needs-reauth खाते को एक-एक करके देखता है |
| `tokenmaxxing switch [sel]` | सर्वश्रेष्ठ खाते पर स्विच करें (लोभी, idempotent) या किसी विशिष्ट खाते को बाध्य करें |
| `tokenmaxxing switch --codex [sel]` | Codex पूल को स्विच करें (अगले codex आरंभ पर प्रभावी होता है) |
| `tokenmaxxing ls` | पूल किए गए खातों की सूची दें |
| `tokenmaxxing status` | 5h / साप्ताहिक / प्रति-मॉडल उपयोग बार वाले खाते, सक्रिय और रीसेट-तक-समाप्त |
| `tokenmaxxing status --force` | अतिरिक्त रूप से हर खाते को पिंग करें (प्रत्येक को एक छोटा सा haiku अनुरोध) ताकि सभी 5h सेशन टाइमर अभी शुरू हो जाएं, फिर नए सिरे से नमूना लें |
| `tokenmaxxing watch [seconds]` | लाइव स्थिति, हर N सेकंड में फिर से रेंडर की गई (डिफ़ॉल्ट 120, न्यूनतम 30; कभी पिंग नहीं करती) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | स्रोतों के साथ प्रभावी config; डॉटेड कुंजियां संपादित करें; `tidy` अज्ञात कुंजियों को छांटता है |
| `tokenmaxxing check` | स्विच निर्णय का एक बार मूल्यांकन करें (यही आवधिक टाइमर चलाता है) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack ब्रिज डेमन (Socket Mode, कोई सार्वजनिक URL नहीं) |
| `tokenmaxxing doctor` | सत्यापित करें कि सुपरवाइज़र और सेटिंग्स प्रविष्टियां बची रहीं |
| `tokenmaxxing rename [--codex] <sel> <label>` | किसी पूल किए गए खाते को फिर से लेबल करें |
| `tokenmaxxing rm <sel>` | पूल से एक खाता हटाएं |
| `tokenmaxxing uninstall` | सुपरवाइज़र और सेटिंग्स प्रविष्टियां हटाएं (खाते और क्रेडेंशियल रखे जाते हैं) |

## आर्किटेक्चर

tokenmaxxing एक बहु-कॉल प्रवेश बिंदु (`src/main.ts`) है जो उस नाम के तहत आह्वान किए जाने पर `claude` सुपरवाइज़र के रूप में व्यवहार करता है, आंतरिक सबकमांड के माध्यम से हुक और statusline शिम प्रदान करता है, और अन्यथा CLI को डिस्पैच करता है। यह सीधे Bun के तहत चलता है; npm पैकेज एक बिल्ड नहीं, बल्कि TypeScript सोर्स भेजता है।

गतिशील भाग:

### सुपरवाइज़र शिम

`init` `~/.config/tokenmaxxing/bin/` में `claude` नामक एक 2-लाइन शेल शिम लिखता है और उस डायरेक्टरी को PATH पर पहले रखता है। जब आप `claude` टाइप करते हैं, तो शिम सुपरवाइज़र चलाता है, जो असली claude बाइनरी को विरासत में मिले stdio और सहेजे गए `stty -g` टर्मिनल स्नैपशॉट के साथ स्पॉन करता है। यह केवल एक प्रोसेस और टर्मिनल प्रबंधक है: यह कभी API ट्रैफ़िक को प्रॉक्सी नहीं करता और कभी उड़ान में टोकन को नहीं छूता।

प्रिंट-मोड आह्वान (`claude -p`, `--version`, `--help`), गैर-इंटरैक्टिव सबकमांड (`claude mcp`, `claude config`, इत्यादि), और tokenmaxxing के अपने प्रोब बिना किसी सेशन प्रबंधन के सीधे पास हो जाते हैं। एक इंटरैक्टिव सेशन के लिए, सुपरवाइज़र एक सेशन id पिन करता है (एक उत्पन्न करके, या आपके द्वारा `--session-id` / `-r` / `-c` के माध्यम से पास की गई id का पुन: उपयोग करके), आपके लॉन्च फ्लैग को बनाए रखता है ताकि बाद का पुनः लॉन्च उन्हें फिर से चला सके, और फिर उस सेशन से जुड़ी एक respawn मार्कर फ़ाइल पर नज़र रखता है।

### statusline टी

Claude Code हर टर्न में statusline के stdin में रेट-लिमिट डेटा (`rate_limits.five_hour` और `rate_limits.seven_day`) पुश करता है। tokenmaxxing statusline स्लॉट का स्वामी है, इसलिए इसका रेंडरर एक मुफ़्त, पुश-आधारित उपयोग फ़ीड के रूप में भी काम करता है: प्रत्येक टिक पर यह समुच्चय विंडो और सक्रिय मॉडल को `usage.json` में टी कर देता है। प्रति-मॉडल सीमाएं statusline stdin में नहीं होतीं; वे केवल `claude -p '/usage'` (मुफ़्त, शून्य टोकन) से आती हैं, जिसे एक TTL के साथ पोल किया जाता है और सक्रिय मॉडल के क्षमता-सीमित होने पर `model-usage.json` में कैश किया जाता है।

टी परिवर्तन-पर-लिखता-है है: जब आंकड़े अपरिवर्तित होते हैं तो यह केवल फ़ाइल के mtime को बढ़ाता है, जो फ़ीड के जीवंतता हार्टबीट के रूप में कार्य करता है। ताज़गी का निर्णय हमेशा mtime द्वारा होता है, कभी अंतर्निहित टाइमस्टैम्प द्वारा नहीं।

### Stop हुक और स्वैप

हर टर्न सीमा पर, Stop हुक स्विच निर्णय चलाता है (देखें [स्विचिंग का निर्णय कैसे होता है](#how-switching-decides))। जब कोई स्वैप उचित होता है, तो यह एक `flock(2)` अनन्य लॉक के तहत होता है (`bun:ffi` के माध्यम से लिया गया, क्योंकि macOS कोई `flock(1)` बाइनरी नहीं भेजता), और क्रेडेंशियल लेखन अतिरिक्त रूप से Claude Code के अपने रिफ्रेश लॉक के साथ इंटरलॉक करते हैं। महत्वपूर्ण खंड के अंदर, एक स्वैप:

1. वर्तमान लाइव क्रेडेंशियल को उसके असली स्वामी के पार्क किए गए बैकअप में हार्वेस्ट करता है।
2. लक्षित खाते के ताज़ा रिफ्रेश किए गए क्रेडेंशियल को लाइव के रूप में इंस्टॉल करता है, मौजूदा लाइव ब्लॉब में मर्ज करते हुए ताकि सहोदर स्थिति (जैसे प्रति-MCP-सर्वर OAuth टोकन) बची रहे।
3. लक्ष्य के घुमाए गए टोकन को उसके अपने बैकअप में बनाए रखता है।
4. `~/.claude.json` में `oauthAccount` फ़ील्ड को परमाणु रूप से फिर से लिखता है।
5. नए सक्रिय लेबल को कमिट करता है और बासी उपयोग स्नैपशॉट को साफ़ करता है, यह सब लॉक जारी होने से पहले, ताकि एक क्रैश कभी भी इंस्टॉल किए गए क्रेडेंशियल और सक्रिय लेबल को अलग-अलग खातों की ओर इशारा करते हुए न छोड़े।

क्योंकि सभी डिफ़ॉल्ट-प्रोफ़ाइल सेशन एक ही लाइव क्रेडेंशियल साझा करते हैं, एक अकेला स्वैप हर सेशन को एक साथ माइग्रेट कर देता है, और flock तथा लॉक के तहत एक पुनः-जांच रेसिंग हुक को दो खातों को खर्च करने से रोकती है।

### जगह-पर अपनाना

एक चालू claude सेशन अनुरोधों के बीच अपने क्रेडेंशियल स्टोर को पोल करता है: macOS पर यह एक छोटे कैश के माध्यम से keychain को फिर से पढ़ता है और एक्सेस टोकन की तुलना करता है; Linux पर यह क्रेडेंशियल फ़ाइल के mtime को स्टैट करता है और परिवर्तन पर अपने टोकन कैश को फ्लश करता है। शुद्ध प्रभाव यह है कि एक स्वैप किया गया क्रेडेंशियल macOS पर लगभग 30 सेकंड के भीतर और Linux पर बिल्कुल अगले अनुरोध पर, बिना किसी पुनः आरंभ के, हर चालू सेशन द्वारा अपना लिया जाता है। यही कारण है कि एक सामान्य स्वैप कोई मार्कर नहीं लिखता और कोई respawn ट्रिगर नहीं करता - सेशन बस नए खाते पर जारी रहता है। इन-सेशन `/usage` उन्हीं टोकन कैश को साझा करता है, इसलिए इसका खाता प्रदर्शन अपनाने के साथ ही बदल जाता है।

### समाप्त-पूल प्रतीक्षा और स्वतः-पुनरारंभ

केवल तभी जब पूल का हर खाता अपने बार से ऊपर हो, Stop हुक एक respawn मार्कर लिखता है (मार्कर स्कीमा को एक `waitUntil` टाइमस्टैम्प की आवश्यकता होती है; एक सामान्य स्वैप कभी एक नहीं बना सकता)। सुपरवाइज़र मार्कर को देखता है, पहले से ही कमिट की गई टर्न सीमा पर अपने चाइल्ड को SIGTERM करता है (Stop हुक ट्रांसक्रिप्ट के डिस्क पर आने और claude के निष्क्रिय होने के बाद चलता है, इसलिए कुछ भी नहीं खोता), टर्मिनल को बहाल करता है, सबसे जल्दी रीसेट तक एक काउंटडाउन दिखाता है, और फिर पुनर्प्राप्त खाते पर `claude --resume <session-id>` को फिर से लॉन्च करता है। काउंटडाउन के दौरान Ctrl-C तुरंत फिर से शुरू कर देता है। स्वतः-प्रतीक्षा `policy.maxWaitMs` (डिफ़ॉल्ट 1 घंटा) द्वारा सीमित है; उससे आगे निर्णय प्रतीक्षा करने के बजाय पूल को समाप्त के रूप में रिपोर्ट करता है।

### आवधिक जांच टाइमर

हुक केवल टर्न सीमाओं पर सक्रिय होते हैं, और एक लंबा एजेंटिक टर्न बिना किसी एकल सीमा के एक विंडो को स्वस्थ से समाप्त तक खर्च कर सकता है। इसलिए `init` एक आवधिक टाइमर भी इंस्टॉल करता है - macOS पर एक launchd एजेंट, Linux पर एक systemd उपयोगकर्ता टाइमर - जो टर्न गतिविधि की परवाह किए बिना हर 180 सेकंड में `tokenmaxxing check` चलाता है।

### एक SessionStart हुक

जब कोई सेशन शुरू या फिर से शुरू होता है तो वही मूल्यांकन चलाता है, ताकि एक नया सेशन सही खाते पर शुरू हो। स्वैप-के-बाद का कूलडाउन इसे respawn के तुरंत बाद एक सही no-op बना देता है।

## स्विचिंग का निर्णय कैसे होता है [#how-switching-decides]

निर्णय के दो स्तर हैं: एक संलग्नता द्वार, और फिर एक लोभी या कठोर पथ।

### संलग्नता

`policy.greedySessionFloor` (डिफ़ॉल्ट 50, 5-घंटे की सेशन विंडो के प्रतिशत में) से नीचे, निर्णय बिल्कुल नहीं चलता - एक नया सेशन अपने खाते पर सवार रहता है। एक बार सक्रिय सेशन विंडो 50% उपयोग हो जाने पर, या कोई कठोर बार पार हो जाने पर, निर्णय संलग्न हो जाता है।

### स्क्रीनिंग बार

थ्रेशोल्ड स्क्रीनिंग बार हैं, घबराहट के लिए ट्रिगर नहीं:

- `thresholds.session`: 95. एक 5-घंटे का रीसेट प्रतीक्षा करने के लिए सस्ता है, इसलिए सेशन विंडो पहले ही स्वैप कर जाती है।
- `thresholds.weekly`: 98. यह एक बार 7-दिन के समुच्चय और हर प्रति-मॉडल साप्ताहिक सीमा दोनों को कवर करता है। साप्ताहिक कोटा उपयोग-करें-या-खो-दें है, इसलिए यह दीवार के करीब तक खर्च होता है।

दोनों जानबूझकर 100 से नीचे हैं: हेडरूम वह बजट है जिससे खाता वास्तव में अपनी सीमा तक पहुंचने से पहले एक स्वच्छ टर्न सीमा तक (साथ ही macOS पर एक टर्न तक अपनाने की देरी) पहुंचा जा सके। वही बार स्वैप उम्मीदवारों की स्क्रीनिंग करते हैं: अपने किसी भी बार से ऊपर का खाता एक वैध लक्ष्य नहीं है। ट्रिगर और स्क्रीनिंग हमेशा एक ही प्रभावी बार (थ्रेशोल्ड घटा `policy.projectionMargin`) का उपयोग करते हैं, क्योंकि ट्रिगर से ढीली एक स्क्रीन उन खातों पर स्वैप लाती जिन्हें ट्रिगर तुरंत फिर से फ्लैग कर देता, पूल को पिंग-पॉन्ग करते हुए।

### लक्ष्य: गति दबाव

उपयोग योग्य खातों में, लक्ष्य वह है जो अपनी साप्ताहिक गति से सबसे अधिक पीछे है: उच्चतम **गति दबाव**, जिसे शेष साप्ताहिक प्रतिशत को उस खाते के साप्ताहिक रीसेट तक के समय से विभाजित करके परिभाषित किया गया है। जिस खाते का सबसे अधिक कोटा ज़ब्त होने वाला है वह जीतता है। बराबरी सबसे जल्दी साप्ताहिक समाप्ति की ओर, फिर सबसे कम 7-दिन के उपयोग की ओर टूटती है।

सब कुछ पूर्ण UTC epoch के रूप में संग्रहीत कैश की गई विंडो से चलता है, इसलिए एक बासी स्नैपशॉट भी सही ढंग से हल होता है: एक साप्ताहिक रीसेट जो बीत चुका है वह ठीक 7-दिन के चरणों में आगे की ओर एक्सट्रापोलेट होता है, और अपने कैश किए गए रीसेट से आगे की कोई भी विंडो नए सिरे से खाली गिनी जाती है (कभी स्विच करने का कारण नहीं, कभी किसी खाते को बेंच पर रखने का कारण नहीं)।

### लोभी बनाम कठोर पथ

- **लोभी पथ** (संलग्न, लेकिन हर बार से नीचे): हर खाते को रैंक करें, वर्तमान सहित। यदि वर्तमान खाता पहले से जीतता है या बराबरी करता है, तो कुछ न करें। अन्यथा सख्ती से बेहतर खाते पर स्वैप करें। यह कभी प्रतीक्षा नहीं करता और कभी पूर्व-पार्क नहीं करता - एक उपयोग योग्य वर्तमान खाते को प्रतीक्षा के बदले नहीं दिया जाता। क्योंकि वर्तमान खाता भी रैंक किया जाता है, स्वचालित पथ और सादा `tokenmaxxing switch` दोनों idempotent हैं: आवधिक रूप से मूल्यांकन करना सही खाते पर अभिसरित होता है और फिर वहीं टिका रहता है।
- **कठोर पथ** (एक बार पार): सर्वश्रेष्ठ उपयोग योग्य उम्मीदवार पर स्वैप कर जाएं। यदि किसी उम्मीदवार का रिफ्रेश टोकन मृत निकलता है, तो उसे needs-reauth फ्लैग किया जाता है और अगले उम्मीदवार को आज़माया जाता है। यदि कुछ भी उपयोग योग्य नहीं है, तो समाप्त-प्रतीक्षा तर्क चलता है; केवल एक कॉलर जो वास्तव में सेशन को रोक सकता है (पर्यवेक्षित Stop हुक) को अभी भी अवरुद्ध लेकिन सबसे जल्दी पुनर्प्राप्त होने वाले खाते पर पूर्व-पार्क करने की अनुमति है।

### प्रति-मॉडल सीमाएं

`policy.switchModels` (डिफ़ॉल्ट `["fable"]`) उन मॉडल परिवारों का नाम देता है जिनकी प्रति-मॉडल साप्ताहिक सीमा एक स्विच ट्रिगर कर सकती है। मिलान परिवार टोकन द्वारा होता है, कभी सटीक प्रदर्शन स्ट्रिंग द्वारा नहीं: मॉडल प्रदर्शन नाम बदलते रहते हैं ("Fable" "Fable 5" बन गया), और एक सटीक-स्ट्रिंग गेट ने एक बार चुपचाप प्रति-मॉडल स्विचिंग को पूरी तरह अक्षम कर दिया था। दो संबंधित सुरक्षा नियम:

- एक अज्ञात सक्रिय मॉडल हर कॉन्फ़िगर किए गए परिवार को गेट करता है। एक स्वैप द्वारा स्नैपशॉट साफ़ करने के तुरंत बाद, एक हेडलेस मशीन मॉडल-अंधी चल सकती है; अज्ञात को अप्रतिबंधित मानने ने एक बार एक खाते को घंटों तक बिना ध्यान दिए अपनी Fable सीमा पर बैठे रहने दिया।
- उम्मीदवार स्क्रीनिंग गेट की गई प्रति-मॉडल सीमाओं को भी गिनती है, इसलिए एक पूल जहां हर खाते ने अपनी Fable सीमा जला दी है वह राउंड-रॉबिन नहीं करता।

### कूलडाउन

एक 45-सेकंड का स्वैप-के-बाद कूलडाउन स्वचालित पथ को गेट करता है। स्वैप के बाद उन्हीं 45 सेकंड के लिए statusline टी को दबा दिया जाता है (macOS पर अपनाने में 30 सेकंड तक लगते हैं), इसलिए एक पूर्ववर्ती मूल्यांकन उस डेटा पर चलता जिसे स्वैप ने स्वयं अमान्य कर दिया था - उसी सटीक परिदृश्य ने एक बार A-से-B-और-वापस respawn लूप उत्पन्न किया। मैनुअल `tokenmaxxing switch` कूलडाउन से अप्रभावित रहता है।

## कॉन्फ़िगरेशन

Config `~/.config/tokenmaxxing/config.json` पर JSON है। हर फ़ील्ड वैकल्पिक है; डिफ़ॉल्ट प्रति-फ़ील्ड लागू होते हैं।

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: ऊपर वर्णित स्क्रीनिंग बार।
- `policy.projectionMargin`: प्रभावी बार बनाने के लिए दोनों बार से घटाया गया।
- `policy.greedySessionFloor`: सेशन-उपयोग प्रतिशत जिस पर लोभी अभिसरण संलग्न होता है।
- `policy.switchModels`: मॉडल परिवार जिनकी प्रति-मॉडल साप्ताहिक सीमा एक स्विच को गेट करती है (लोड पर प्रविष्टियां लोअरकेस की जाती हैं)।
- `policy.usagePollTtlMs`: एक `/usage` प्रति-मॉडल पोल कितनी देर ताज़ा रहता है।
- `policy.maxWaitMs`: समाप्त-पूल स्वतः-प्रतीक्षा सीमा।

`tokenmaxxing config` स्रोतों के साथ प्रभावी config दिखाता है; `config set`/`unset` डॉटेड कुंजियां संपादित करते हैं; `config tidy` अज्ञात कुंजियों को छांटता है।

## क्रेडेंशियल भंडारण और सुरक्षा मॉडल

सभी स्थिति `~/.config/tokenmaxxing/` में रहती है। क्रेडेंशियल I/O एक अकेले प्लेटफ़ॉर्म-चयनित स्टोर मुखौटे से होकर गुजरता है; कॉल साइट कभी प्लेटफ़ॉर्म पर शाखा नहीं बनातीं।

**macOS**: क्रेडेंशियल लॉगिन keychain में generic-password आइटम के रूप में रहते हैं, वहीं जहां Claude Code स्वयं उन्हें रखता है। लाइव आइटम वही है जिसे claude पढ़ता है; प्रत्येक पूल किए गए खाते का बैकअप उसके अपने `tokenmaxxing-cred-<uuid8>` keychain आइटम के रूप में पार्क किया जाता है। डिस्क पर कुछ भी प्लेनटेक्स्ट नहीं है। पढ़ने के लिए `security find-generic-password -w` का उपयोग होता है (रहस्य केवल कभी stdout पर दिखाई देता है); लेखन एक `add-generic-password` लाइन को stdin के माध्यम से `security -i` में पाइप करता है ताकि रहस्य किसी भी प्रोसेस के argv में कभी दिखाई न दे। इंटरैक्टिव मोड में लगभग 4 KB का लाइन बफ़र होता है, इसलिए अत्यधिक बड़े ब्लॉब एक argv लेखन पर वापस आ जाते हैं - एक कारण कि पार्क किए गए आइटम केवल न्यूनतम OAuth ऑब्जेक्ट संग्रहीत करते हैं।

**Linux**: Claude Code क्रेडेंशियल को एक 0600 प्लेनटेक्स्ट फ़ाइल के रूप में संग्रहीत करता है, और tokenmaxxing उसी मॉडल का पालन करता है: लाइव फ़ाइल claude की अपनी `.credentials.json` है, और पार्क किए गए बैकअप एक 0700 डायरेक्टरी में `~/.config/tokenmaxxing/creds/` के तहत परमाणु 0600 फ़ाइलें हैं। यहां परमाणु का मतलब है टेम्प-में-लिखना, fsync, फिर नाम बदलना: एक समवर्ती पाठक हमेशा एक पूरी पुरानी या पूरी नई फ़ाइल देखता है, कभी आंशिक नहीं।

स्वैप जो सुरक्षा नियम लागू करता है:

- **असली स्वामी द्वारा हार्वेस्ट।** स्वैप से पहले, लाइव क्रेडेंशियल का वास्तविक स्वामी API से यह पूछकर हल किया जाता है कि टोकन किस संगठन का है (`fetchTokenOrg`, OAuth roles एंडपॉइंट के विरुद्ध) - कभी संग्रहीत सक्रिय लेबल पर भरोसा करके नहीं, जो भटक सकता है। एक भटके हुए लेबल ने एक बार एक खाते के हार्वेस्ट को दूसरे खाते के एकमात्र बैकअप को अधिलेखित करने का कारण बना। यदि लाइव क्रेडेंशियल पूल के बाहर के किसी खाते का है, तो स्वैप उसे अधिलेखित करने के बजाय सीधे मना कर देता है।
- **एक महत्वपूर्ण खंड।** हार्वेस्ट, नए क्रेडेंशियल का इंस्टॉल, उसके घुमाए गए टोकन का बैकअप, `~/.claude.json` खाता स्वैप, और सक्रिय-लेबल कमिट सभी एक ही लॉक किए गए खंड के अंदर होते हैं।
- **claude के अपने रिफ्रेश के साथ इंटरलॉक।** एक समाप्ति के करीब सेशन किसी भी क्षण अपना टोकन घुमा सकता है, इसलिए क्रेडेंशियल लेखन Claude Code का रिफ्रेश लॉक भी लेते हैं (best-effort, एक बासी-लॉक पुनर्प्राप्ति और एक सीमित टाइमआउट के साथ)।
- **मृत अनुदान साफ़-सुथरे ढंग से गिरावट करते हैं।** एक रिफ्रेश जो `invalid_grant` लौटाता है उस खाते को needs-reauth फ्लैग करता है और त्रुटि के प्रसार से पहले फ्लैग को बनाए रखता है, इसलिए पुनः प्रयास लूप उम्मीदवार सेट को छोटा करते हैं और समाप्त हो जाते हैं। `tokenmaxxing auth` एक फ्लैग किए गए खाते को उसकी जगह ठीक करता है, और यह एक ऐसे लॉगिन को अस्वीकार करता है जो मरम्मत किए जा रहे खाते से भिन्न खाते पर उतरता है।
- **कोई टोकन लॉगिंग नहीं।** टोकन कभी लॉग, त्रुटियों, या आउटपुट में दिखाई नहीं देते। टोकन और उपयोग एंडपॉइंट से त्रुटि बॉडी कभी कच्चे रूप में सामने नहीं आतीं; केवल फ़ील्ड का एक अनुमत-सूची सेट बचता है, क्योंकि एक टोकन एंडपॉइंट की विफलता बॉडी अनुरोध सामग्री को प्रतिध्वनित कर सकती है।
- **प्रोब स्वच्छता।** कोई भी स्पॉन किया गया `claude` प्रोब उन आठ पर्यावरण चरों को साफ़ करता है जिन्हें claude अपनी keychain खोज से पहले मानता है (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, इत्यादि), ताकि एक प्रोब को कभी गलत खाते के लिए जिम्मेदार न ठहराया जा सके।

## प्लेटफ़ॉर्म नोट्स: macOS बनाम Linux

| | macOS | Linux |
|---|---|---|
| लाइव क्रेडेंशियल | लॉगिन keychain generic-password आइटम | 0600 `.credentials.json` फ़ाइल |
| पार्क किए गए क्रेडेंशियल | प्रति-खाता keychain आइटम | 0700 डायरेक्टरी में 0600 फ़ाइलें |
| स्वैप के बाद अपनाना | ~30 सेकंड के भीतर (keychain रीड कैश) | अगला अनुरोध (फ़ाइल mtime पोल) |
| आवधिक जांच | launchd एजेंट, हर 180s | systemd उपयोगकर्ता टाइमर, हर 180s |
| पृथक-लॉगिन स्टोर | प्रति config dir हैश-नेमस्पेस्ड keychain सेवा | पृथक config dir के अंदर एक फ़ाइल |

जानने योग्य दो Linux-विशिष्ट विवरण: claude अपनी क्रेडेंशियल डायरेक्टरी को पहले `CLAUDE_SECURESTORAGE_CONFIG_DIR` से हल करता है (फिर `CLAUDE_CONFIG_DIR`, फिर `~/.claude`), और tokenmaxxing उस समाधान को बिल्कुल प्रतिबिंबित करता है ताकि दोनों कभी desync न हों। और एक ही claude संस्करण के दो OS बिल्ड `/usage` रीसेट घड़ियों को अलग-अलग स्वरूपित करते हैं (एक " at " ग्लू का उपयोग करता है, दूसरा एक कॉमा); tokenmaxxing का पार्सर ठीक उन्हीं दो रूपों को स्वीकार करता है और किसी तीसरे पर अनुमान लगाने के बजाय लॉग करता है।

macOS पर, एक ईमानदार सीमा: `init` और `add` जानबूझकर keychain को इंटरैक्टिव रूप से छूते हैं, ताकि पहली `security` एक्सेस एक हेडलेस हुक के अंदर ठंडी न हो।

## statusline

tokenmaxxing Claude Code के statusline को मूल रूप से रेंडर करता है (जबकि उपयोग फ़ीड को टी करता है)। डिज़ाइन सिद्धांत: कोटा रंग में ले जाया जाता है, संख्याओं में नहीं। एक लाइन, उदाहरण के लिए:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- प्रत्येक विंडो टोकन उसका रीसेट-तक-समय है, जिसे उपयोग किए गए प्रतिशत द्वारा एक सतत हरे-से-पीले-से-लाल रैंप पर रंगा जाता है (जब टर्मिनल समर्थन करता है तो truecolor, अन्यथा 256-रंग क्यूब पर स्टेप किया गया)। रैंप 0 के लिए शुद्ध हरे, 75 पर पीले, और 95 और उससे ऊपर पर लाल पर एंकर करता है, इसलिए पुराने गंभीरता बैंड रैंप एंकर के रूप में बचे रहते हैं।
- मॉडल नाम को उसी रैंप पर संदर्भ-विंडो भराव द्वारा रंगा जाता है।
- एक हरा `◆` सक्रिय खाते की विंडो का नेतृत्व करता है; प्रत्येक पार्क किए गए खाते को उसका अपना सियान `◇` मिलता है (यदि इसे reauth की आवश्यकता हो तो लाल `✗`)। खाते सबसे जल्दी आने वाले रीसेट के अनुसार क्रमबद्ध होते हैं।
- प्रत्येक ब्लॉक में प्रति-मॉडल एक नंगे रंगे आद्याक्षर के रूप में पहले आता है: Fable `𝒇` रेंडर करता है; अन्य परिवार अपने अपरकेस पहले अक्षर का उपयोग करते हैं, हमेशा परिवार-मिलान किया गया।
- एक अछूता पार्क किया गया खाता एक हरा `full` रेंडर करता है। अज्ञात रीसेट के साथ मापा गया उपयोग एक रंगा `?` रेंडर करता है, और एक गेट किए गए मॉडल पर एक बिना-मापी प्रति-मॉडल सीमा एक बिना-रंगा `𝒇?` रेंडर करती है - बिना-मापा कभी सुरक्षित नहीं दिखना चाहिए।
- रीसेट काउंटडाउन केवल सबसे बड़ी इकाई दिखाते हैं, कभी "now" या "0m" नहीं; बिना किसी आने वाले रीसेट वाली एक विंडो एक हरा `0` रेंडर करती है (फिर से खाली)।
- एक लिंक किए गए git worktree का बेसनेम लाइन का नेतृत्व करता है; एक मुख्य checkout वहां कुछ भी रेंडर नहीं करता। पहचान एक `.git` फ़ाइल के लिए फ़ाइल सिस्टम को पढ़ती है और कभी git सबप्रोसेस स्पॉन नहीं करती।
- `NO_COLOR` सेट होने पर, लाइन एक चिपके हुए संख्यात्मक स्वरूप पर वापस आ जाती है (`2h5` का मतलब है 2 घंटे में रीसेट होता है, 5% उपयोग किया गया; संदर्भ भराव के लिए `ctx 42`) - रंग के बिना, एक खाली विंडो ताज़ा नहीं दिखनी चाहिए।

उप-एजेंट कार्यों को claude के subagentStatusLine सतह के माध्यम से अपनी पैनल पंक्तियां मिलती हैं: प्रति सक्रिय कार्य एक पंक्ति, परिवार नाम उस कार्य के संदर्भ भराव द्वारा रंगा गया।

## Codex समर्थन

वही पूलिंग OpenAI के Codex CLI के लिए, आपके अपने ChatGPT-सब्सक्रिप्शन खातों के विरुद्ध काम करती है:

```sh
tokenmaxxing init --codex   # अपना वर्तमान codex लॉगिन आयात करें + codex सुपरवाइज़र और Stop हुक इंस्टॉल करें
tokenmaxxing add --codex    # एक और खाते में लॉग इन करें, पृथक - आपका प्राथमिक लॉगिन अछूता रहता है
codex                       # हमेशा की तरह codex का उपयोग करें
```

Codex पूल पूरी तरह से समानांतर स्थिति है: इसका अपना खाता सूचकांक, इसकी अपनी पार्क की गई क्रेडेंशियल फ़ाइलें (दोनों प्लेटफ़ॉर्म पर 0600 फ़ाइलें, क्योंकि codex का अपना स्टोर एक प्लेनटेक्स्ट फ़ाइल है), इसका अपना लॉक, इसका अपना अंतिम-स्वैप टाइमस्टैम्प। निर्णय-नीति कोड को छोड़कर Claude पूल के साथ कुछ भी साझा नहीं है।

### Codex पर हॉट-स्वैप क्यों असंभव है

एक चालू codex प्रोसेस एक इन-मेमोरी auth प्रबंधक रखता है और जब `auth.json` अब एक भिन्न खाते का नाम देता है तो उसे फिर से लोड करने से स्पष्ट रूप से मना कर देता है। कोई फ़ाइल वॉचर और कोई प्रति-अनुरोध क्रेडेंशियल पोल नहीं है, इसलिए एक चालू codex के नीचे स्वैप किया गया क्रेडेंशियल इनफेरेंस के लिए बस कभी प्रभावी नहीं होता। पुनः आरंभ ही स्विच है: `codex resume <session-id>` स्थानीय ट्रांसक्रिप्ट को उस खाते पर जारी रखता है जो `auth.json` अब रखता है।

tokenmaxxing इसे एक codex सुपरवाइज़र शिम के साथ संभालता है: Stop हुक हर टर्न सीमा पर वही लोभी गति-दबाव निर्णय चलाता है, और जब यह स्वैप करता है, तो यह एक मार्कर लिखता है जो सुपरवाइज़र को कमिट की गई सीमा पर सेशन को SIGTERM करने और ताज़ा खाते पर `codex resume <session-id>` को फिर से लॉन्च करने के लिए बनाता है, ट्रांसक्रिप्ट बरकरार। क्योंकि हर codex स्विच एक दृश्यमान पुनः आरंभ है, codex लोभी पथ एक 1.2x सुधार मार्जिन रखता है: एक चुनौतीकर्ता को वर्तमान खाते के गति दबाव को 20% से हराना होगा, बाल-बराबर से नहीं। कठोर पथ (एक पार किया गया बार) मार्जिन को अनदेखा करता है। codex के लिए कोई समाप्त-पूल काउंटडाउन भी नहीं है - कुछ भी codex सेशन को रोक नहीं सकता - इसलिए एक पूरी तरह से समाप्त codex पूल वहीं टिका रहता है।

अन्य codex-विशिष्ट यांत्रिकी:

- उपयोग codex के अपने रेट-लिमिट एंडपॉइंट के विरुद्ध एक मुफ़्त प्रमाणित GET से पढ़ा जाता है (वही कॉल जो CLI का `/status` करता है): प्रतिशत के साथ पूर्ण epoch रीसेट समय, समुच्चय विंडो और प्रति-मॉडल सीमाएं समान रूप से। विंडो वर्गीकरण अवधि-चालित है, कभी स्थिति-चालित नहीं, क्योंकि वर्तमान योजनाओं में बिल्कुल भी 5-घंटे की विंडो नहीं हो सकती और साप्ताहिक विंडो प्राथमिक स्लॉट में बैठती है।
- Codex रिफ्रेश टोकन घूमते हैं, और एक अधिक्रमित टोकन का पुन: उपयोग पूरे अनुदान परिवार को मार देता है। हर घुमाव उसके लौटते ही तुरंत बनाए रखा जाता है, सक्रिय खाते का नमूना केवल कभी लाइव ब्लॉब के माध्यम से लिया जाता है (कभी बासी पार्क की गई प्रति नहीं), और प्रति-सेशन उपस्थिति फ़ाइलें सुनिश्चित करती हैं कि एक लाइव सहोदर सेशन में चल रहा खाता कभी स्वैप लक्ष्य न हो और कभी अपने पार्क किए गए टोकन को रिफ्रेश न कराए।
- Codex को फ़ाइल क्रेडेंशियल स्टोर की आवश्यकता होती है: यदि keyring स्टोर पिन किया गया है तो `init --codex` तेज़ी से विफल हो जाता है, और `add --codex` पृथक ऑनबोर्डिंग होम में फ़ाइल-मोड सेटिंग लिखता है ताकि लॉगिन हार्वेस्ट-योग्य रूप में उतरे।
- एक मैनुअल चरण: codex उन हुक को छोड़ देता है जिन पर भरोसा करने के लिए उसे नहीं कहा गया है। `init --codex` के बाद, codex को एक बार खोलें और `/hooks` के माध्यम से tokenmaxxing Stop हुक पर भरोसा करें, अन्यथा स्वतः-स्विचिंग चुपचाप निष्क्रिय रहती है। `init --codex` यह अनुस्मारक प्रिंट करता है।

```sh
tokenmaxxing serve setup                    # ऐप मेनिफ़ेस्ट प्रिंट करता है, दो टोकन के लिए संकेत देता है
tokenmaxxing serve link <channel-id> <repo> # एक चैनल को एक repo checkout से बांधें
tokenmaxxing serve                          # डेमन चलाएं
```

एक लिंक किए गए चैनल में बॉट का उल्लेख करें और यह उस थ्रेड के लिए, लिंक किए गए repo checkout में, एक Claude Code सेशन खोल देता है। हर थ्रेड संदेश `resume` के साथ एक Agent SDK `query()` चलाता है - कभी एक स्थायी स्ट्रीमिंग क्वेरी नहीं - इसलिए `ensureBestAccount()` हर एक टर्न पर पूल का पुनर्मूल्यांकन करता है और डेमन थ्रेड खोए बिना पुनः आरंभ हो सकता है (थ्रेड रिकॉर्ड टिकाऊ हैं; डेमन उन्हें स्टार्टअप पर फिर से सब्सक्राइब करता है)।

उल्लेखनीय व्यवहार:

- **स्ट्रीमिंग**: उत्तर मूल रूप से Slack में स्ट्रीम होते हैं, सोच और टूल रन के लिए कार्य कार्ड, हाइलाइटिंग के साथ रेंडर किया गया फेंस्ड कोड, लागत और अवधि के साथ एक समापन "Turn" कार्ड, और जब भी कोई टूल रन स्ट्रीम किए गए टेक्स्ट को बाधित करता है तो एक नया Slack संदेश खुलता है, ताकि एक टर्न टूल रन के आसपास अलग-अलग संदेशों के रूप में पढ़ा जाए। TodoWrite कॉल एक स्थिर चेकलिस्ट कार्ड को उसकी जगह अपडेट करते हैं।
- **अनुमतियां**: प्रति-लिंक `permissionMode` डिफ़ॉल्ट रूप से `acceptEdits` होता है; `--yolo` (उपनाम `--dangerous`) एक लिंक को `bypassPermissions` में शामिल करता है। रिले किए गए टर्न में इंटरैक्टिव डायलॉग की अनुमति नहीं है - कोई भी Slack के माध्यम से किसी का उत्तर नहीं दे सकता - इसलिए मॉडल गद्य में पूछता है और आपका थ्रेड उत्तर अगला टर्न होता है। एक बंडल किया गया प्लगइन स्किल इसे सिखाता है कि जब उसे कोई निर्णय चाहिए तो अनुरोधकर्ता को टैग करे और टर्न समाप्त कर दे।
- **स्लैश कमांड**: एक थ्रेड संदेश जिसका छांटा गया टेक्स्ट `/` से शुरू होता है, एक claude स्लैश कमांड के रूप में चलता है। Slack का कंपोज़र `/` से शुरू होने वाले संदेशों को खा जाता है, इसलिए mention-पहले रूप (`@bot /usage`) या एक अग्रणी स्थान का उपयोग करें।
- **सुंदर शटडाउन**: SIGTERM/SIGINT ड्रेन करता है - नए टर्न जोर से गिराए जाते हैं, उड़ान में चल रहे टर्न को 5 मिनट तक मिलते हैं, और claude चाइल्ड अपने स्वयं के प्रोसेस समूह में अलग होकर चलता है ताकि एक टर्मिनल Ctrl-C इसे ड्रेन द्वारा टर्न को संरक्षित करने से पहले न मार सके।
- **थ्रेड सफाई**: जब आप इसे बताते हैं कि काम हो गया, तो मॉडल एक इन-प्रोसेस `finish_thread` टूल कॉल करता है; टर्न पूरी तरह समाप्त होने के बाद, डेमन थ्रेड रिकॉर्ड गिरा देता है, सब्सक्राइब रद्द करता है, और एक पुष्टि पोस्ट करता है। एक नया उल्लेख एक नया सेशन शुरू करता है।
- **त्रुटि स्वच्छता**: टर्न त्रुटियां छांटे गए केवल-संदेश टेक्स्ट पोस्ट करती हैं, कभी कच्ची त्रुटि बॉडी नहीं।

## Agent SDK सतह

पैकेज का प्रोग्रामेटिक प्रवेश (`exports["."]` `src/sdk.ts` की ओर इशारा करता है) उन एजेंट के लिए tokenmaxxing को Claude Agent SDK के साथ जोड़ता है जिन्हें आप अपने स्वयं के पूल किए गए खातों के विरुद्ध बनाते हैं। आपके ऐप को Bun के तहत चलना होगा (tokenmaxxing TypeScript सोर्स भेजता है और `bun:ffi` का उपयोग करता है)।

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK प्रति `query()` एक claude सबप्रोसेस स्पॉन करता है और स्पॉन पर एक बार क्रेडेंशियल पढ़ता है - कोई statusline नहीं, कोई मध्य-क्वेरी हॉट-स्वैप नहीं - इसलिए एकीकरण सीमा-चालित है:

- `ensureBestAccount()` वही सटीक निर्णय है जो CLI हुक और टाइमर चलाते हैं (बार, गति दबाव, कूलडाउन, सभी साझा कोड), कभी पूर्वानुमानित नहीं: एक SDK सेशन को कभी एक समाप्त काउंटडाउन के लिए रोका नहीं जा सकता।
- `pooledOptions()` `pathToClaudeCodeExecutable` को असली claude बाइनरी पर पिन करता है (कभी सुपरवाइज़र रैपर नहीं) और हर परिवेशी क्रेडेंशियल ओवरराइड को साफ़ किए गए एक पूर्ण प्रतिस्थापन `env` की आपूर्ति करता है। यदि आपके ऐप के पर्यावरण में `CLAUDE_CONFIG_DIR` या `CLAUDE_SECURESTORAGE_CONFIG_DIR` सेट है तो यह तेज़ी से विफल हो जाता है: Linux पर एक स्वैप लाइव क्रेडेंशियल को वहां लिखता जहां वे इशारा करते हैं जबकि साफ़ किया गया सबप्रोसेस डिफ़ॉल्ट स्टोर पढ़ता है, एक मौन गलत-खाता desync।
- `stopHookCheck` टर्न सीमाओं पर निर्णय फिर से चलाता है; यह जो स्वैप उतारता है वह अगले स्पॉन पर प्रभावी होता है। यह पुनः फेंकने के बजाय अपनी स्वयं की त्रुटियों को पकड़ता है (stderr और लॉग में लॉगिंग), क्योंकि एक अनहैंडल्ड हुक अपवाद एजेंट को बाधित कर सकता है, और एक टूटी हुई स्विच जांच पर एक टर्न को रद्द करना वर्तमान खाते पर टिके रहने से अधिक महंगा पड़ता है।

`sdk.ts` Agent SDK से स्वयं कुछ भी आयात नहीं करता; इसके मान संरचनात्मक रूप से SDK के विकल्पों में फैल जाते हैं।

## व्यक्तिगत उपयोग और सेवा की शर्तें [#personal-use-and-terms-of-service]

tokenmaxxing आपके स्वामित्व वाले खातों को, उन सेशन और एजेंट में जिन्हें आप स्वयं चलाते हैं, पूल करता है। वह शब्दावली जानबूझकर है: Anthropic तृतीय-पक्ष उत्पादों को claude.ai लॉगिन या claude.ai रेट सीमाएं प्रदान करने की अनुमति नहीं देता, और इसमें Agent SDK पर निर्मित एजेंट शामिल हैं। पूल की गई SDK सतह, या उस पर निर्मित किसी भी चीज़ को, तृतीय पक्षों को न भेजें। tokenmaxxing OAuth को फिर से लागू करने या API ट्रैफ़िक को प्रॉक्सी करने के बजाय कोटा डेटा के लिए जानबूझकर CLI-मध्यस्थ `/usage` पथ पर बना रहता है: यह एक प्रॉक्सी नहीं है, और यह केवल जिन OAuth एंडपॉइंट को छूता है वे हैं स्वैप के दौरान उपयोग किया जाने वाला मानक रिफ्रेश अनुदान और एक केवल-पढ़ने के लिए पहचान जांच (roles एंडपॉइंट) जो सत्यापित करती है कि एक टोकन वास्तव में किस खाते का है।

- **साझा विस्फोट त्रिज्या।** सभी डिफ़ॉल्ट-प्रोफ़ाइल सेशन एक लाइव क्रेडेंशियल साझा करते हैं, इसलिए एक स्वैप उन सभी को एक साथ स्थानांतरित करता है (प्रत्येक अपनी जगह अपना लेता है)।
- **Linux पर प्लेनटेक्स्ट क्रेडेंशियल।** Claude Code स्वयं Linux क्रेडेंशियल को एक 0600 प्लेनटेक्स्ट फ़ाइल के रूप में संग्रहीत करता है; tokenmaxxing की पार्क की गई प्रतियां उसी मॉडल का पालन करती हैं।

## समस्या निवारण और अक्सर पूछे जाने वाले प्रश्न

**`claude` पर्यवेक्षित नहीं लगता।**
`tokenmaxxing doctor` चलाएं। शिम को PATH समाधान जीतना होगा; जांचें कि आपके शेल rc में `# tokenmaxxing PATH` लाइन वर्तमान bin डायरेक्टरी की ओर इशारा करती है और असली claude से आगे बैठती है। `doctor` `alias claude=...` या एक `claude()` शेल फ़ंक्शन के रैपर को छाया देने के बारे में भी चेतावनी देता है, और उन उपनामों के बारे में जो पूर्ण पथ से एक claude बाइनरी लॉन्च करते हैं (वे सुपरवाइज़र को पूरी तरह से बायपास करते हैं)।

**Codex पर स्वतः-स्विचिंग कभी सक्रिय नहीं होती।**
Codex उन हुक को छोड़ देता है जिन पर भरोसा करने के लिए उसे नहीं कहा गया है। codex खोलें, `/hooks` चलाएं, और tokenmaxxing Stop हुक पर भरोसा करें। भरोसा हुक के हैश के विरुद्ध दर्ज किया जाता है, इसलिए यदि हुक कभी संपादित किया जाता है तो इसे फिर से देना होगा।

**statusline में एक खाता लाल `✗` दिखाता है।**
इसका रिफ्रेश टोकन मृत है (निरस्त या इसके बैकअप के नीचे से घुमा दिया गया)। इसे उसकी जगह पर पुनः प्रमाणित करने के लिए `tokenmaxxing auth <sel>` चलाएं; कमांड आपको बताता है कि किस ईमेल से साइन इन करना है और एक ऐसे लॉगिन को अस्वीकार करता है जो एक भिन्न खाते पर उतरता है।

**यह सबसे अधिक शेष कोटा वाले खाते पर स्विच क्यों नहीं करता?**
क्योंकि वह कोटा ज़ब्त करने के सबसे अधिक जोखिम वाला खाता नहीं है। लक्ष्य वह खाता है जो अपनी साप्ताहिक गति से सबसे अधिक पीछे है: शेष प्रतिशत को उसके साप्ताहिक रीसेट तक के समय से विभाजित किया गया। समान मात्रा शेष होने पर यह सबसे जल्दी समाप्ति पहले तक सिमट जाता है, और समान समाप्ति पर सबसे अधिक शेष पहले तक।

**यह अभी स्विच हुआ और statusline अभी भी पुराना खाता दिखाता है।**
macOS पर ~30 सेकंड तक अपेक्षित: चालू सेशन अपने अगले क्रेडेंशियल-कैश रिफ्रेश पर स्वैप किए गए क्रेडेंशियल को अपना लेता है। ठीक इसी कारण से उपयोग टी को स्वैप के बाद 45 सेकंड के लिए दबा दिया जाता है।

**क्या `status --force` की कोई लागत है?**
हां, जानबूझकर: यह प्रति खाता एक न्यूनतम मीटर किया गया haiku अनुरोध भेजता है ताकि हर 5-घंटे की सेशन विंडो निष्क्रिय पड़े रहने के बजाय उसी क्षण शुरू हो जाए, फिर नए सिरे से नमूना लेता है। सादा `status` और `watch` कभी पिंग नहीं करते; `/usage` पढ़ना मुफ़्त है। ध्यान दें कि सर्वर उपयोग फ़ीड एक ताज़ा खुली विंडो में सेकंड से मिनट तक की देरी कर सकता है, इसलिए पिंग के तुरंत बाद एक प्रोब अभी भी पिंग-पूर्व स्थिति दिखा सकता है - `status` पिंग विफल होने का दिखावा करने के बजाय एक नोट रेंडर करता है।

**`/usage` प्रोब ने सक्रिय खाते के लिए कुछ नहीं लौटाया।**
यह एक ज्ञात claude व्यवहार है: जब इसका आंतरिक उपयोग फ़ेच विफल होता है या रेट-सीमित होता है, तो `/usage` केवल स्थानीय सेशन आंकड़े बिना किसी प्रतिशत लाइन के प्रिंट करता है। tokenmaxxing सक्रिय खाते का नमूना statusline पुश से लेता है और केवल पार्क किए गए खातों को प्रोब करता है, ठीक इसी से बचने के लिए।

**पृष्ठभूमि claude सेशन।**
Claude का पृष्ठभूमि डेमन पूर्ण पथ द्वारा असली संस्करणित बाइनरी को स्पॉन करता है, PATH शिम को बायपास करते हुए, इसलिए पृष्ठभूमि सेशन पर्यवेक्षित नहीं होते। हुक अभी भी `settings.json` के माध्यम से सक्रिय होते हैं, और क्रेडेंशियल अपनाना तथा आवधिक टाइमर स्विचिंग को कवर करते हैं, लेकिन उनके लिए कोई मार्कर-चालित respawn नहीं है।

**किसी चीज़ ने एक बार बहुत सारी प्रक्रियाएं स्पॉन कीं। क्या यह अभी भी संभव है?**
सुपरवाइज़र ठीक उसी ऐतिहासिक विफलता के विरुद्ध स्तरित पुनरावर्तन रक्षक रखता है (एक बासी रैपर जो "असली" claude के रूप में पिन किया गया): पर्यावरण में एक गहराई प्रहरी जो 5 स्तरों पर रुक जाता है, एक ऑन-डिस्क स्पॉन-दर सीमक, realpath पहचान जांच जो किसी भी उम्मीदवार को अस्वीकार करती है जो tokenmaxxing की अपनी bin डायरेक्टरी में वापस हल होता है, और एक कठोर विफलता (कभी एक मौन PATH स्कैन नहीं) जब एक कॉन्फ़िगर किया गया claude पथ अब मौजूद नहीं रहता। `init` और `doctor` किसी उम्मीदवार को पिन करने से पहले `--version` चलाकर सत्यापित करते हैं कि वह वास्तव में claude है।

**अनइंस्टॉल करना।**
`tokenmaxxing uninstall` सुपरवाइज़र शिम, सेटिंग्स प्रविष्टियां, और आवधिक टाइमर हटाता है, और आपके खातों तथा पार्क किए गए क्रेडेंशियल को बरकरार छोड़ देता है। यह केवल उन statusline प्रविष्टियों को हटाता है जिन्हें यह अपनी स्वयं की के रूप में पहचानता है।
