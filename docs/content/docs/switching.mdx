---
title: How switching decides
description: One bar per window, pace pressure, and the depleted wait
---

The automatic decision runs at every turn boundary (the Stop hook), on session start, and on the periodic check. It has one rule: while the live account is under its bars, hold; once it is at or over any bar, move to the usable account with the highest pace pressure; when no account is usable, wait for the soonest reset.

## The bars

- `thresholds.session`: 90, in percent of the 5-hour session window.
- `thresholds.weekly`: 98. This one bar covers both the 7-day aggregate and every gated per-model weekly cap. Weekly quota is use-it-or-lose-it, so it drains close to the limit.

`policy.projectionMargin` is subtracted from both, so the effective bars are `thresholds - projectionMargin`. Both sit below 100 because the headroom is the budget to reach a clean turn boundary (plus up to one turn of adoption lag on macOS) before the account hits its real limit. Codex reads the same two bars.

The same bars gate the trigger and screen the candidates: the decision engages when the live account's measured usage is at or over a bar, and a candidate is usable when none of its cached windows (session, weekly aggregate, gated per-model caps, and any server-pinned enforcement) is at or over one. A screen laxer than the trigger would land swaps on accounts the trigger immediately re-flags, so there is exactly one bar per window. Unmeasured usage never reads as safe: an account with no sample ranks last, and a live account with no fresh tee or probe does not trigger.

Older versions carried a session ladder, an engagement floor, organization affinity, incumbent hysteresis, and wall bars. Their config keys are gone: an array `thresholds.session` fails config loading with a zod message naming the field, and `hardThresholds`, `policy.greedySessionFloor`, and `policy.greedySwapMargin` are ignored by the loader.

## The target: pace pressure

**Pace pressure** is remaining weekly percent divided by time until that account's weekly reset. The usable candidate with the highest pace pressure wins; ties break by soonest weekly reset, then lowest weekly usage. Organization membership is not a ranking input. Manual `tokenmaxxing switch` uses the same ranking and reports the live account as already best when it ties the winner.

Everything runs off cached windows stored as absolute UTC epochs, so a stale snapshot still resolves correctly: a weekly reset that has passed extrapolates forward in exact 7-day steps, and any window past its cached reset counts as freshly empty (never a reason to switch, never a reason to keep an account benched).

The decision reads the cached figures only; it never probes a candidate before a handoff. Parked figures stay fresh through the [periodic check](#periodic-check), which samples one parked account per tick.

- An account requiring reauthentication is excluded for the evaluation.
- A dead refresh grant is marked for reauthentication and the next candidate is tried.

## When nothing is usable

When every account is at or over a bar, the decision picks the soonest recovery: the live account's own reset, or another account's earliest reset when that comes first. If that reset lands within `policy.maxWaitMs` (default 1 hour), the supervised session pauses until it (see [Architecture](/architecture)); only the supervised Stop hook may pre-park the pool onto the other account while pausing, so the resumed session starts there. Further out, the decision reports the pool as depleted and the session stays put, keeps running into its real limit, and the enforced-limit path below takes over. The pause happens at the bar, not at 100: the unspent headroom is the same budget that set the bar. Codex has no pause; it rides its account until the server refuses it.

## Per-model caps

`policy.switchModels` (default `["fable"]`) names the model families whose per-model weekly cap can trigger a switch. Matching is by family token, never by exact display string: model display names drift ("Fable" became "Fable 5"), and an exact-string gate once silently disabled per-model switching entirely. Two related safety rules:

- An unknown active model gates every configured family. Right after a swap clears snapshots, a headless machine can run model-blind; treating unknown as unconstrained once let an account sit at its Fable cap for hours unnoticed.
- Candidate screening counts gated per-model caps too, so a pool where every account has burnt its Fable cap does not round-robin.

## Cooldown

A 45-second post-swap cooldown gates the automatic path. The statusline tee is suppressed for the same 45 seconds after a swap (adoption takes up to 30 seconds on macOS), so an earlier evaluation would run on data the swap itself invalidated - that exact scenario once produced an A-to-B-and-back respawn loop. Manual `tokenmaxxing switch` is unaffected by the cooldown.

## Enforced limits

The cached figures can lag reality: the live account's per-model cap comes only from a `/usage` probe of the busy live token, which often prints nothing under session load. When the server actually refuses a turn, Claude Code ends it on an API error and fires its `StopFailure` hook instead of `Stop`. tokenmaxxing installs that hook with a `rate_limit` matcher, and it reads the transcript's structured error row (the same row Claude Code marks `isApiErrorMessage`): a `quotaLimits` block names the window (`five_hour`, `seven_day`, or a per-model type) with the server's reset, and the Fable cap failure, which carries no `quotaLimits`, is recognized from the client's own error rendering plus the 429 body. Model prose is never read.

The hook hands the classified refusal to the decision, which blocks the account until the reset inside the same critical section that picks the target: it writes `enforcedUntil` on the account record, using the server's reset when the row carries one, else the account's own cached reset for that window, else now plus the window length, and a later wall already on the account is never shortened. That one field is what the trigger and the candidate screen read, so an account with no usage sample yet cannot be picked straight back, a Fable refusal parks the account until its weekly reset, and a seat still walled after a failed swap keeps triggering on every later tick, screening candidates on every configured family because the wall does not record which one tripped. The decision treats the enforcement as a fact stronger than any cached window (it skips the live probe, gates candidates by the tripped family, and never holds the seat) and swaps away. A subagent's five-hour or weekly failure screens every configured family, because the tee reports the main session's model and not the subagent's, and so does a failure that lands while an earlier wall is still active, whichever deadline is later, because that wall does not record which family tripped; the stamp and the selection share one lock, so two hooks that fail back to back cannot lose that screening, and a hook whose account was swapped away after it classified the failure still stamps that account, ignores the post-swap cooldown, and swaps again if the new seat is exhausted for the refusal's family, or for any configured family when the refusal is blind. In a supervised session whose main turn failed, it also drops a respawn marker: the supervisor relaunches `--resume` on the fresh account, and the next prompt you send continues the conversation there. A failure inside a subagent swaps but never respawns (the parent turn is still running), and an unsupervised session gets the swap and adopts it on its next request.

A failure inside the 45-second post-swap cooldown is ignored, because a request that started on the old credential can end on the new seat during adoption; a fresh seat that is walled too fails its next turn after the cooldown and is blocked then. The hook decides that by reading the swap clock before it captures the live account and again after it has read its input: an unchanged recent clock means the swap completed before the capture and the failure is dropped; a changed clock means a swap completed after the capture, however many swaps ran and wherever the seat sits now, and the failure reaches the decision, which walls the captured account.

## Periodic check

The timer runs `tokenmaxxing check` once per tick (`policy.checkIntervalMs`, 60 seconds by default) and every tick evaluates. Under both bars the evaluation reads the tee and returns in milliseconds, so a tick costs nothing worth skipping. The live `/usage` probe is bounded by `policy.usagePollTtlMs` regardless of tick rate: an attempt, successful or not, is recorded on the account record (`lastProbeAt`), no second probe runs inside the TTL, and no probe runs at all while the live account is walled by an enforced limit, because the wall already decides. A tick that lands inside the post-swap cooldown returns at once, and a tick during a depleted wait replays the recorded wait. launchd and systemd both skip a firing while the previous check is still running, so evaluations never overlap.

After the evaluation, the same tick samples one parked account: the one whose last `/usage` attempt is oldest, skipping any attempted within `policy.usagePollTtlMs`. A failed attempt counts as an attempt, so a broken account moves to the back of the line instead of blocking the others. With `n` pooled accounts every parked account is attempted about once per `n` ticks, or once per `policy.usagePollTtlMs` plus a tick when that is longer, so a parked figure is as fresh as its last successful attempt and an account whose probes keep failing stays as stale as the decision last saw it (see [Honest limitations](/limitations)). No sample runs inside the 45-second post-swap cooldown, because a refresh of the just-parked credential would revoke the token sessions still hold during adoption. The tick holds the pool lock only to reserve the target and to store the result; the `/usage` child runs outside it, so an enforced-limit swap never waits on a slow probe. Reserving the target includes the credential checks that must stay serialized (the owner lookups and, for an expiring parked token, one refresh), and the owner lookups and the refresh request share one 20-second deadline, with the refresh-lock wait bounded by its own five short attempts, so a stalled endpoint cannot hold the pool lock past that. A parked slot whose pair carries the live login's own refresh token is never rotated from the tick (a rotation there would supersede the live store), it is skipped until `switch` reconciles it. A reservation is stamped with the time it is made, not the time the tick started, so a long evaluation ahead of it cannot leave the stamp stale. The child gets one attempt, bounded by the 60-second kill deadline, because the round-robin is its retry loop; a `check` therefore never outlives the next tick by more than that one deadline. The tick's child runs in its own isolated config home, separate from the one `status` uses, so the two can sample the same account at once, and the tick hands a credential the child rotated back to the parked slot only while that slot still holds the pair the child was given; a swap that rotates the pair mid-probe wins and the child's copy is discarded. A result is stored only when it is newer than the sample already on record.
