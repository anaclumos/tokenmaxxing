tokenmaxxing は単一のマルチコールエントリポイント (`src/main.ts`) であり、その名前で呼び出されると `claude` スーパーバイザーとして振る舞い、内部サブコマンドでフックと statusline のシムを提供し、それ以外の場合は CLI をディスパッチします。Bun 上で直接動作します。npm パッケージはビルド成果物ではなく TypeScript ソースを配布します。

可動部分は次のとおりです。

## スーパーバイザーシム

`init` は `claude` という名前の2行のシェルシムを `~/.config/tokenmaxxing/bin/` に書き込み、そのディレクトリを PATH の先頭に置きます。`claude` と入力すると、シムがスーパーバイザーを実行し、スーパーバイザーは継承した stdio と保存済みの `stty -g` 端末スナップショットとともに本物の claude バイナリを起動します。これはプロセスと端末のマネージャーにすぎません。API トラフィックをプロキシすることはなく、送信中のトークンに触れることもありません。

print モードの呼び出し (`claude -p`、`--version`、`--help`)、非対話型サブコマンド (`claude mcp`、`claude config` など)、および tokenmaxxing 自身のプローブは、セッション管理なしでそのまま通過します。対話型セッションの場合、スーパーバイザーはセッション ID を固定し (新規に生成するか、`--session-id` / `-r` / `-c` で渡されたものを再利用する)、後で再起動したときにリプレイできるよう起動フラグを保存し、そのセッションに紐づいた再起動マーカーファイルを監視します。

## statusline の tee

Claude Code はレート制限データ (`rate_limits.five_hour` と `rate_limits.seven_day`) を毎ターン statusline の stdin に送り込みます。tokenmaxxing は statusline スロットを所有しているため、そのレンダラーは無料でプッシュベースの使用量フィードを兼ねます。各ティックで集計ウィンドウとアクティブモデルを `usage.json` に tee します。モデルごとの上限は statusline の stdin には含まれず、`claude -p '/usage'` (無料、トークン消費ゼロ) からのみ得られます。これを TTL 付きでポーリングし、アクティブモデルが容量制約を受けているときに `model-usage.json` にキャッシュします。

tee は変更時書き込み方式です。数値が変わらないときはファイルの mtime を更新するだけで、これがフィードの生存ハートビートとして機能します。鮮度は常に mtime で判断し、埋め込まれたタイムスタンプでは判断しません。

## Stop フックと切り替え

毎ターン境界で Stop フックが切り替えの判断を実行します ([切り替えの判断方法](/ja/switching)を参照)。切り替えが妥当なときは `flock(2)` の排他ロックの下で行われ (macOS には `flock(1)` バイナリが同梱されていないため `bun:ffi` 経由で取得します)、認証情報の書き込みはさらに Claude Code 自身のリフレッシュロックともインターロックします。クリティカルセクション内で、1回の切り替えは次の手順を実行します。

1. 現在のライブ認証情報をその真の所有者の待機バックアップに取り込みます。
2. ターゲットアカウントのリフレッシュしたばかりの認証情報をライブとしてインストールし、既存のライブ blob にマージすることで兄弟状態 (MCP サーバーごとの OAuth トークンなど) を残します。
3. ターゲットのローテートされたトークンを自身のバックアップに保存します。
4. `~/.claude.json` の `oauthAccount` フィールドをアトミックに書き換えます。
5. 新しいアクティブラベルをコミットし、古い使用量スナップショットをクリアします。いずれもロック解放前に行われるため、クラッシュしても、インストール済みの認証情報とアクティブラベルが別々のアカウントを指したまま残ることは決してありません。

デフォルトプロファイルのすべてのセッションが唯一のライブ認証情報を共有するため、1回の切り替えですべてのセッションが一斉に移行します。flock とロック下での再確認により、競合するフックが2つのアカウントを浪費することを防ぎます。

## その場での採用

実行中の claude セッションはリクエストの合間に認証情報ストアをポーリングします。macOS では短いキャッシュ越しにキーチェーンを再読み込みしてアクセストークンを比較し、Linux では認証情報ファイルの mtime を stat して変更時にトークンキャッシュをフラッシュします。その結果、入れ替えられた認証情報は、macOS では約30秒以内、Linux では次のリクエストで、再起動なしにすべての実行中セッションに採用されます。これが通常の切り替えでマーカーを書き込まず再起動もトリガーしない理由です。セッションは新しいアカウント上でそのまま継続します。セッション内の `/usage` は同じトークンキャッシュを共有するため、そのアカウント表示も採用に合わせて切り替わります。

## プール枯渇時の待機と自動再開

プール内のすべてのアカウントがバーを超えたときにのみ、Stop フックは再起動マーカーを書き込みます (マーカースキーマは `waitUntil` タイムスタンプを必須とし、通常の切り替えでは決して生成されません)。スーパーバイザーはマーカーを見つけると、すでにコミット済みのターン境界で子プロセスに SIGTERM を送り (Stop フックはトランスクリプトがディスクに書かれ claude がアイドルになった後に実行されるため、何も失われません)、端末を復元し、最も早いリセットまでのカウントダウンを表示し、それから回復したアカウント上で `claude --resume <session-id>` を再起動します。カウントダウン中に Ctrl-C を押すと即座に再開します。自動待機は `policy.maxWaitMs` (デフォルト1時間) で上限が設けられており、それを超えると判断は待機する代わりにプールを枯渇として報告します。

## 定期チェックタイマー

フックはターン境界でしか発火せず、1回の長いエージェント的なターンが境界を1つも挟まずにウィンドウを健全な状態から枯渇まで消費し尽くすことがあります。そのため `init` は定期タイマー (macOS では launchd エージェント、Linux では systemd ユーザータイマー) もインストールし、ターンの活動に関係なく180秒ごとに `tokenmaxxing check` を実行します。

## SessionStart フック

セッションが開始または再開したときに同じ評価を実行し、新しいセッションが正しいアカウントで始まるようにします。切り替え後のクールダウンにより、再起動直後は正しく no-op になります。
