---
title: Pag-iimbak ng credential at modelo ng kaligtasan
description: "Kung saan nakatira ang mga credential kada platform at ang mga tuntuning ipinapatupad ng bawat pagpapalit"
---

Ang lahat ng state ay nasa `~/.config/tokenmaxxing/`. Ang credential I/O ay dumadaan sa isang platform-selected na store facade; hindi kailanman nagsasanga ang mga call site ayon sa platform.

**macOS**: ang mga credential ay nasa login keychain bilang mga generic-password na item, na tumutugma kung saan pinananatili ng Claude Code mismo ang mga ito. Ang live na item ang binabasa ng claude; ang backup ng bawat naka-pool na account ay naka-park bilang sarili nitong `tokenmaxxing-cred-<uuid8>` na keychain item. Walang plaintext sa disk. Gumagamit ang mga pagbasa ng `security find-generic-password -w` (ang secret ay lumalabas lamang sa stdout); ang mga pagsulat ay nagpi-pipe ng isang `add-generic-password` na linya papunta sa `security -i` sa pamamagitan ng stdin upang hindi kailanman lumitaw ang secret sa argv ng anumang proseso. Ang interactive mode ay may humigit-kumulang 4 KB na line buffer, kaya't ang mga labis na malaking blob ay bumabalik sa isang argv write - isang dahilan kung bakit ang mga naka-park na item ay nag-iimbak lamang ng minimal na OAuth object.

**Linux**: nag-iimbak ang Claude Code ng mga credential bilang isang 0600 plaintext file, at sinusunod ng tokenmaxxing ang parehong modelo: ang live file ay ang sariling `.credentials.json` ng claude, at ang mga naka-park na backup ay atomic na 0600 file sa ilalim ng `~/.config/tokenmaxxing/creds/` sa isang 0700 directory. Ang atomic dito ay nangangahulugang write-to-temp, fsync, pagkatapos ay rename: ang isang concurrent na reader ay palaging nakakakita ng isang buong luma o buong bagong file, hindi kailanman ng bahagyang isa.

Ang mga safety rule na ipinapatupad ng pagpapalit:

- **Pag-ani ayon sa tunay na may-ari.** Bago ang isang pagpapalit, ang aktwal na may-ari ng live credential ay tinutukoy sa pamamagitan ng pagtatanong sa API kung aling account ang pag-aari ng token (`fetchTokenIdentity` laban sa OAuth profile endpoint, itinutugma ayon sa UUID ng account) - hindi kailanman ayon sa organisasyon, dahil iisang organisasyon ang ibinabahagi ng bawat seat sa isang Team plan, at hindi kailanman sa pamamagitan ng pagtitiwala sa nakaimbak na aktibong label, na maaaring gumalaw. Isang gumalaw na label ang minsang naging sanhi upang ma-overwrite ng pag-ani ng isang account ang tanging backup ng ibang account. Kung ang live credential ay pag-aari ng isang account sa labas ng pool, tumatanggi ang pagpapalit nang tuwiran sa halip na sirain ito.
- **Isang critical section.** Ang pag-ani, ang pag-install ng bagong credential, ang backup ng na-rotate nitong token, ang pagpapalit ng account sa `~/.claude.json`, at ang pag-commit ng aktibong label ay lahat nangyayari sa loob ng parehong naka-lock na section.
- **Interlock sa sariling refresh ng claude.** Ang isang malapit-nang-mag-expire na session ay maaaring mag-rotate ng sarili nitong token anumang sandali, kaya't kinukuha rin ng mga credential write ang refresh lock ng Claude Code (best-effort, na may stale-lock reclaim at isang bounded na timeout).
- **Malinis na bumababa ang mga patay na grant.** Ang isang refresh na bumalik nang `invalid_grant` ay nagfla-flag sa account na iyon bilang needs-reauth at pinananatili ang flag bago kumalat ang error, kaya't pinaliliit ng mga retry loop ang candidate set at natatapos. Ang isang credential na nilinis mismo ng Claude Code matapos ang isang nabigong refresh (walang laman na access at refresh token) ay kinikilala bilang patay nang hindi gumagasta ng isang request. Bago magasta ang isang naka-park na refresh token, ang may-ari nito ay tinutukoy sa pamamagitan ng profile endpoint; ang isang naka-park na credential na natutukoy bilang pag-aari ng ibang account ay fina-flag sa halip na i-refresh, dahil ang pag-refresh ng isang kopya ng live grant ng ibang account ay nagpapawalang-bisa sa mga session ng account na iyon. Ang anumang ibang pagtanggi ng token endpoint (isang HTTP 4xx na hindi `invalid_grant`) ay linalaktawan ang candidate na iyon para sa natitirang bahagi ng ebalwasyon at walang fina-flag. Inaayos ng `tokenmaxxing auth` ang isang naka-flag na account nang nasa lugar, at tumatanggi ito sa isang login na napupunta sa ibang account kaysa sa isinasaayos.
- **Walang pag-log ng token.** Hindi kailanman lumilitaw ang mga token sa mga log, error, o output. Ang mga error body mula sa token at usage endpoint ay hindi kailanman inilalabas nang hilaw; tanging ang isang allowlisted na set ng mga field ang nananatili, dahil ang failure body ng isang token endpoint ay maaaring mag-echo ng request material.
- **Kalinisan ng probe.** Nililinis ng anumang na-spawn na `claude` probe ang walong environment variable na iginagalang ng claude bago ang keychain lookup nito (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, at iba pa), kaya't hindi kailanman maaaring maiugnay ang isang probe sa maling account.
