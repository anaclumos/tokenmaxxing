---
title: "Slack ブリッジ: xx serve"
description: "xx serve は Socket Mode 上で Slack のスレッドから Claude Code セッションを実行する"
---

`tokenmaxxing serve` は Socket Mode 上でローカルの Slack デーモンを実行します。公開 URL は不要です。セットアップ:

```sh
tokenmaxxing serve setup                    # アプリマニフェストを表示し、2つのトークンの入力を求める
tokenmaxxing serve link <channel-id> <repo> # チャンネルをリポジトリのチェックアウトに紐づける
tokenmaxxing serve                          # デーモンを実行する
```

リンクされたチャンネルでボットにメンションすると、リンク先リポジトリのチェックアウト内に、そのスレッド用の Claude Code セッションを開きます。スレッドへのメッセージはどれも `resume` 付きの Agent SDK `query()` を1回だけ実行し (持続的なストリーミングクエリではありません)、ターンごとに `ensureBestAccount()` がプールを再評価するので、デーモンはスレッドを失うことなく再起動できます (スレッドレコードは永続的で、デーモンは起動時に再購読します)。

注目すべき挙動:

- **ストリーミング**: 返信は思考とツール実行のためのタスクカード、ハイライト付きで描画されるフェンス付きコード、コストと所要時間を含む締めの「Turn」カードとともに Slack へネイティブにストリームされ、1つのターンのカードはすべて展開可能な1つのプランブロックに折りたたまれるため、ターンは通常、返信とそのアクティビティのドロップダウン1つからなる単一のメッセージとして読めます (ターン中盤のリトライや追記の拒否があると、後続のメッセージが開きます)。TodoWrite の呼び出しは、同じチェックリストカードをその場で更新し続けます。Slack はネイティブのストリームを、およそ30秒の無音または5分の生存時間でサーバー側から期限切れにし、そのメッセージを「Something went wrong」のピルとして凍結させてしまうため、デーモンはどちらのタイマーにも達する前にアイドル状態や長寿命のメッセージをきれいに閉じ、新しいメッセージで続きを流します。
- **権限**: リンクごとの `permissionMode` はデフォルトで `acceptEdits` です。`--yolo` (エイリアス `--dangerous`) はリンクを `bypassPermissions` にオプトインします。対話ダイアログはリレーされたターンでは許可されません。Slack では誰も答えられないためです。代わりにモデルは文章で尋ね、スレッドへの返信が次のターンになります。同梱のプラグインスキルが、判断が必要なときにリクエスト元をタグ付けしてターンを終える方法を教えます。
- **ステータスリアクション**: ターンのトリガーとなったメッセージには、その状態が絵文字リアクションとして付きます。ターンの実行中は砂時計、その後はチェックマーク (完了)、バツ (失敗)、またはクエスチョンマーク (モデルがあなたの判断を必要としている) になります。現行マニフェストの `reactions:write` スコープが必要です。既存のアプリはマニフェストを貼り直して再インストールしてください。
- **アテンションとナッジ**: モデルがあなたに判断を求めるとき、インプロセスの `need_attention` ツールを呼ぶため、デーモンはそのスレッドがあなたを待っていることを把握します。10分間反応がないと、スレッド内で1回だけタグ付けします。スレッドが待機中の間、質問へのリアクションはあなたの回答としてリレーされます (サムズアップは推奨オプションを選びます)。それ以外に追跡中のスレッドで付けたリアクションは、コンテキストとして次のターンに畳み込まれます。`reactions:read` と `reaction_added` イベントが必要です。
- **スラッシュコマンド**: メンションを除いたテキストが `/` で始まるスレッドメッセージは、claude のスラッシュコマンドとして実行されます。Slack のコンポーザーは `/` で始まるメッセージを飲み込むため、メンションを先頭に置いた形式 (`@bot /usage`) を使うか、先頭にスペースを付けてください。
- **使用量上限の自動再開**: プール内のすべてのアカウントが上限に達した場合、短時間の障害であればメッセージをその場に保留してリトライし、長時間の障害であれば保留通知を投稿したうえでプールが回復し次第ターンを自動的に再開します。これはデーモンの再起動をまたいでも維持されます。回復時刻が不明な上限の場合のみ、再送信を求めます。
- **失敗時のリトライ**: 完了しないまま失敗したターン (claude の子プロセスのクラッシュ、API エラー) は、黙って最大2回まで追加でリトライされます。同じセッションを再開するので、終わった作業がやり直されることはありません。そのうえでなお失敗した場合にだけ、スレッドに本当のエラーが届きます。回答が完了したターンがリトライされることはなく、プールの枯渇だと判明した失敗は、上記の使用量上限の仕組みに引き継がれます。
- **障害の隔離**: あるスレッドの失敗が他のスレッドを巻き添えにすることはありません。キューに入った各タスクは自身のエラーを自分で引き受け (クラッシュしたハンドラは自分のスレッドに診断情報を投稿し、デーモンはそのまま動き続けます)、さらにデーモンは最後の砦としてリジェクションのガードを持ちます。これがないと、ランタイムはたった1つの野良リジェクションでプロセス全体を、つまり同時に走っているすべてのスレッドのターンを殺してしまうからです。
- **グレースフルシャットダウン**: SIGTERM/SIGINT はドレインします。新しいターンは明示的にドロップされ、進行中のターンには最大5分が与えられます。claude の子プロセスは独自のプロセスグループで detached として動作するため、端末で Ctrl-C を押しても、ドレインがターンを保全する前に子プロセスが殺されることはありません。
- **スレッドのクリーンアップ**: 作業が完了したと伝えると、モデルはインプロセスの `finish_thread` ツールを呼びます。ターンが完全に終わった後、デーモンはスレッドレコードを削除し、購読を解除し、確認のメッセージを1つ投稿します。改めてメンションすれば、新しいセッションが始まります。
- **エラーの衛生**: ターンのエラーは、生のエラー本文ではなく、切り詰めたメッセージ部分だけを投稿します。
