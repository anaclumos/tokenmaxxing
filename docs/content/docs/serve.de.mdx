---
title: "Die Slack-Bridge: xx serve"
description: "xx serve führt Claude-Code-Sitzungen aus Slack-Threads über Socket Mode aus"
---

`tokenmaxxing serve` betreibt einen lokalen Slack-Daemon über Socket Mode - keine öffentliche URL erforderlich. Einrichtung:

```sh
tokenmaxxing serve setup                    # gibt das App-Manifest aus, fragt nach den beiden Tokens
tokenmaxxing serve link <channel-id> <repo> # bindet einen Kanal an einen Repo-Checkout
tokenmaxxing serve                          # startet den Daemon
```

Erwähnen Sie den Bot in einem verlinkten Kanal, und er öffnet eine Claude-Code-Sitzung für diesen Thread, im verlinkten Repo-Checkout. Jede Thread-Nachricht führt weiterhin ein einzelnes Agent-SDK-`query()` mit `resume` aus - sodass `ensureBestAccount()` den Pool bei jedem einzelnen Zug neu auswertet und der Daemon neu starten kann, ohne Threads zu verlieren (Thread-Datensätze sind dauerhaft; der Daemon abonniert sie beim Start erneut) - aber jede Abfrage nimmt Streaming-Eingaben entgegen, und genau das erlaubt es einer Antwort, den bereits laufenden Zug zu steuern.

Bemerkenswertes Verhalten:

- **Steuerung**: Eine Antwort, die eintrifft, während der Zug des Threads noch läuft, wird in diesen Zug eingefaltet - dieselbe Injektion mitten im Zug, die Claude Code auch interaktiv nutzt - sodass das Modell sie an der nächsten Werkzeuggrenze des Zugs sieht und den Kurs korrigiert, statt zuerst das Falsche zu Ende zu bringen. Eine Antwort, die nach dem letzten Werkzeugaufruf des Zugs eintrifft, läuft direkt danach als eigener Zug; in beiden Fällen geht nichts verloren. Gesteuerte Nachrichten tragen die Sanduhr als Reaktion und schließen mit dem Zug ab, und ihr Text reitet auf dem dauerhaften Marker des Zugs, sodass Neustarts und Wiederaufnahmen bei Nutzungslimits sie erneut abspielen. Nur eine Nachricht, die hinter einer anderen wartenden Nachricht in der Warteschlange steht, überspringt das Einfalten (die Reihenfolge bleibt erhalten), und ein drainierender Daemon verwirft weiterhin lautstark, statt zu steuern.
- **Streaming**: Antworten streamen nativ in Slack, mit Aufgabenkarten für Denken und Werkzeugläufe, in Blöcken eingefasstem Code mit Syntaxhervorhebung und einer abschließenden "Turn"-Karte mit Kosten und Dauer; alle Karten eines Zugs klappen zu einem ausklappbaren Plan-Block zusammen, sodass ein Zug sich normalerweise als eine einzige Nachricht liest: die Antwort plus ein Dropdown seiner Aktivität (ein Wiederholungsversuch mitten im Zug oder ein abgelehntes Anhängen öffnet eine Folgenachricht). TodoWrite-Aufrufe aktualisieren eine stabile Checklisten-Karte an Ort und Stelle.
- **Berechtigungen**: Der `permissionMode` pro Link ist standardmäßig `acceptEdits`; `--yolo` (Alias `--dangerous`) meldet einen Link für `bypassPermissions` an. Interaktive Dialoge sind in relaisierten Zügen unzulässig - niemand kann einen davon über Slack beantworten - sodass das Modell in Prosa fragt und Ihre Thread-Antwort der nächste Zug ist. Ein mitgeliefertes Plugin-Skill bringt ihm bei, den Anforderer zu markieren und den Zug zu beenden, wenn es eine Entscheidung braucht.
- **Status-Reaktionen**: Die Nachricht, die einen Zug ausgelöst hat, trägt seinen Zustand als Emoji-Reaktion: eine Sanduhr, während der Zug läuft, dann ein Häkchen (erledigt), ein X (fehlgeschlagen) oder ein Fragezeichen (das Modell braucht Ihre Entscheidung). Erfordert den `reactions:write`-Scope aus dem aktuellen Manifest; bestehende Apps müssen das Manifest erneut einfügen und neu installieren.
- **Aufmerksamkeit und Anstupser**: Wenn das Modell Sie um eine Entscheidung bittet, ruft es ein prozessinternes `need_attention`-Werkzeug auf, sodass der Daemon weiß, dass der Thread auf Sie wartet. Wenn Sie 10 Minuten lang still bleiben, markiert er Sie einmal im Thread. Während ein Thread wartet, wird eine Reaktion auf die Frage als Ihre Antwort weitergeleitet (ein Daumen hoch wählt die empfohlene Option); jede andere Reaktion, die Sie in einem verfolgten Thread hinzufügen, wird als Kontext in den nächsten Zug eingefaltet. Erfordert `reactions:read` und das `reaction_added`-Ereignis.
- **Slash-Befehle**: Eine Thread-Nachricht, deren bereinigter Text mit `/` beginnt, läuft als claude-Slash-Befehl. Slacks Composer schluckt Nachrichten, die mit `/` beginnen, daher verwenden Sie die Mention-zuerst-Form (`@bot /usage`) oder ein führendes Leerzeichen.
- **Automatische Wiederaufnahme bei Nutzungslimits**: Wenn jedes gepoolte Konto am Limit ist, parkt ein kurzer Ausfall die Nachricht und versucht es an Ort und Stelle erneut; ein längerer postet einen Zwischenbescheid und nimmt den Zug automatisch wieder auf, sobald sich der Pool erholt, und übersteht dabei Daemon-Neustarts. Nur ein Limit ohne bekannte Erholungszeit bittet Sie, die Nachricht erneut zu senden.
- **Ordentliches Herunterfahren**: SIGTERM/SIGINT drainiert - neue Züge werden lautstark verworfen, laufende Züge erhalten bis zu 5 Minuten, und das claude-Kind läuft losgelöst in seiner eigenen Prozessgruppe, sodass ein Terminal-Ctrl-C es nicht töten kann, bevor die Drainierung den Zug bewahrt.
- **Thread-Aufräumen**: Wenn Sie ihm sagen, dass die Arbeit erledigt ist, ruft das Modell ein prozessinternes `finish_thread`-Werkzeug auf; nachdem der Zug vollständig endet, verwirft der Daemon den Thread-Datensatz, meldet sich ab und postet eine Bestätigung. Eine frische Erwähnung startet eine neue Sitzung.
- **Fehler-Hygiene**: Zugfehler posten gekürzten, reinen Nachrichtentext, nie rohe Fehlerkörper.
