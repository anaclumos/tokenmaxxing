---
title: การจัดเก็บ credential และโมเดลความปลอดภัย
description: "credential อยู่ที่ไหนในแต่ละแพลตฟอร์ม และกฎที่การสลับทุกครั้งบังคับใช้"
---

สถานะทั้งหมดอยู่ใน `~/.config/tokenmaxxing/` การอ่านเขียน credential (I/O) ผ่าน facade ของที่เก็บที่เลือกตามแพลตฟอร์มเพียงตัวเดียว จุดที่เรียกใช้จะไม่แยกสาขาตามแพลตฟอร์มเลย

**macOS**: credential อยู่ใน login keychain ในรูปแบบรายการ generic-password ซึ่งตรงกับที่ Claude Code เองเก็บไว้ รายการสด (live item) คือรายการที่ claude อ่าน ไฟล์สำรองของแต่ละบัญชีในพูลจะถูก park เป็นรายการ keychain `tokenmaxxing-cred-<uuid8>` ของตัวเอง ไม่มีอะไรเป็นข้อความธรรมดา (plaintext) อยู่บนดิสก์ การอ่านใช้ `security find-generic-password -w` (ความลับจะปรากฏบน stdout เท่านั้น) การเขียนจะ pipe บรรทัด `add-generic-password` เข้าไปยัง `security -i` ผ่าน stdin เพื่อไม่ให้ความลับปรากฏใน argv ของโปรเซสใดๆ โหมดโต้ตอบมีบัฟเฟอร์บรรทัดประมาณ 4 KB ดังนั้น blob ที่ใหญ่เกินไปจะย้อนกลับไปใช้การเขียนแบบ argv ซึ่งเป็นเหตุผลหนึ่งที่รายการที่ park เก็บเพียงอ็อบเจกต์ OAuth ขั้นต่ำเท่านั้น

**Linux**: Claude Code เก็บ credential เป็นไฟล์ข้อความธรรมดาสิทธิ์ 0600 และ tokenmaxxing ใช้โมเดลเดียวกัน คือไฟล์สดคือ `.credentials.json` ของ claude เอง และไฟล์สำรองที่ park ไว้เป็นไฟล์สิทธิ์ 0600 แบบอะตอมมิกภายใต้ `~/.config/tokenmaxxing/creds/` ในไดเรกทอรีสิทธิ์ 0700 คำว่าอะตอมมิกในที่นี้หมายถึงการเขียนลงไฟล์ชั่วคราว fsync แล้วจึงเปลี่ยนชื่อ (rename) ตัวอ่านที่ทำงานพร้อมกันจะเห็นไฟล์เก่าทั้งไฟล์หรือไฟล์ใหม่ทั้งไฟล์เสมอ ไม่มีทางเห็นไฟล์ที่ไม่สมบูรณ์

กฎความปลอดภัยที่การสลับบังคับใช้:

- **เก็บเกี่ยวตามเจ้าของที่แท้จริง** ก่อนการสลับ เจ้าของที่แท้จริงของ credential สดจะถูกระบุด้วยการถาม API ว่า token เป็นของบัญชีใด (`fetchTokenIdentity` กับ OAuth profile endpoint จับคู่ด้วย UUID ของบัญชี) ไม่ใช่ด้วยองค์กร เพราะทุกที่นั่งของแผน Team ใช้องค์กรเดียวกัน และไม่ใช่ด้วยการเชื่อป้ายบัญชีที่ใช้งานอยู่ซึ่งเก็บไว้ เพราะมันเลื่อนคลาดได้ ป้ายที่เลื่อนคลาดครั้งหนึ่งเคยทำให้การเก็บเกี่ยวของบัญชีหนึ่งไปเขียนทับไฟล์สำรองเพียงไฟล์เดียวของอีกบัญชี ถ้า credential สดเป็นของบัญชีที่อยู่นอกพูล การสลับจะปฏิเสธทันทีแทนที่จะเขียนทับมัน
- **ส่วนวิกฤตเดียว** การเก็บเกี่ยว การติดตั้ง credential ใหม่ การสำรอง token ที่หมุนเวียนของมัน การสลับบัญชีใน `~/.claude.json` และการยืนยันป้ายบัญชีที่ใช้งานอยู่ ทั้งหมดเกิดขึ้นภายในส่วนที่ล็อกไว้เดียวกัน
- **ประสานล็อกกับการรีเฟรชของ claude เอง** เซสชันที่ใกล้หมดอายุสามารถหมุนเวียน token ของตัวเองได้ทุกเมื่อ ดังนั้นการเขียน credential จึงจับ refresh lock ของ Claude Code ด้วย (แบบพยายามให้ดีที่สุด พร้อมการเรียกคืนล็อกค้าง และการหมดเวลาที่มีขอบเขต)
- **grant ที่ตายแล้วเสื่อมลงอย่างเรียบร้อย** การรีเฟรชที่ตอบกลับมาเป็น `invalid_grant` จะติดธงบัญชีนั้นว่าต้องยืนยันตัวตนใหม่ และบันทึกธงก่อนที่ข้อผิดพลาดจะแพร่กระจาย ดังนั้นลูปการลองใหม่จะทำให้ชุดตัวเลือกเล็กลงและสิ้นสุด credential ที่ Claude Code เองล้างค่าหลังจากการรีเฟรชล้มเหลว (access และ refresh token ว่างเปล่า) จะถูกระบุว่าตายแล้วโดยไม่ต้องส่งคำขอ ก่อนที่ refresh token ที่ park ไว้จะถูกใช้ เจ้าของของมันจะถูกระบุผ่าน profile endpoint; credential ที่ park ไว้ซึ่งระบุว่าเป็นของบัญชีอื่นจะถูกติดธงแทนที่จะถูกรีเฟรช เพราะการรีเฟรชสำเนา grant สดของบัญชีอื่นจะเพิกถอนเซสชันของบัญชีนั้น การถูกปฏิเสธจาก token endpoint แบบอื่นใด (HTTP 4xx ที่ไม่ใช่ `invalid_grant`) จะข้ามตัวเลือกนั้นสำหรับส่วนที่เหลือของการประเมิน และไม่ติดธงใดๆ `tokenmaxxing auth` ซ่อมบัญชีที่ติดธง ณ ที่เดิม และจะปฏิเสธการเข้าสู่ระบบที่ไปลงคนละบัญชีกับบัญชีที่กำลังซ่อม
- **ไม่บันทึก token** token ไม่เคยปรากฏในบันทึก (log) ข้อผิดพลาด หรือเอาต์พุต เนื้อหาข้อผิดพลาด (error body) จาก token และ usage endpoint ไม่เคยถูกแสดงแบบดิบ มีเพียงชุดฟิลด์ที่อยู่ในรายการอนุญาต (allowlist) เท่านั้นที่ผ่านออกมา เพราะเนื้อหาความล้มเหลวของ token endpoint อาจสะท้อนเนื้อหาของคำขอกลับมาได้
- **สุขอนามัยของการ probe** การ probe `claude` ที่ถูก spawn ทุกครั้งจะล้างตัวแปรสภาพแวดล้อมแปดตัวที่ claude ให้ความสำคัญก่อนการค้นหา keychain (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR` และอื่นๆ) เพื่อไม่ให้การ probe ถูกระบุว่าเป็นของบัญชีที่ผิดได้
