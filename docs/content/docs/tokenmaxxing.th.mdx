tokenmaxxing เป็น CLI สำหรับการสลับบัญชี Claude Code แบบอัตโนมัติ โดยจะรวมบัญชีแบบ subscription (Pro/Max) หลายบัญชีที่คุณเป็นเจ้าของ และ hot-swap credential ที่ใช้งานอยู่ไปยังบัญชีที่สดกว่าเมื่อบัญชีที่กำลังใช้อยู่ใกล้ถึงลิมิตการใช้งาน คุณยังคงรัน `claude` ได้เหมือนเดิมทุกอย่าง การสลับจะเกิดขึ้นที่ขอบเขตของเทิร์นที่ปลอดภัย และเซสชันที่กำลังทำงานอยู่ของคุณจะดำเนินบทสนทนาเดิมต่อไปบนบัญชีใหม่โดยไม่ต้องรีสตาร์ท ระบบนี้ทำงานได้กับหลายเซสชันที่ทำงานพร้อมกันในคราวเดียว

พฤติกรรมเดียวที่คุณจะเห็นคือกรณีที่แย่ที่สุด นั่นคือเมื่อทั้งพูล (pool) ถึงลิมิตหมดแล้ว เซสชันจะหยุดชั่วคราวพร้อมกับนับถอยหลัง และกลับมาทำงานต่อโดยอัตโนมัติบนบัญชีถัดไปที่รีเซ็ต (กด Ctrl-C เพื่อกลับมาทำงานต่อทันที)

<Callout>
ขอบเขต: Claude Code บน macOS และ Linux รวมถึง Codex CLI ของ OpenAI ในฐานะพูลที่สองที่ทำงานคู่ขนานกัน เครื่องมือนี้รวมบัญชีแบบ subscription ไม่ใช่ API key นี่เป็นเครื่องมือสำหรับการใช้งานส่วนตัวเพื่อรวมบัญชีที่คุณเป็นเจ้าของ ในเซสชันและ agent ที่คุณรันเอง ดู [การใช้งานส่วนตัวและข้อกำหนดในการให้บริการ](#personal-use-and-terms-of-service)
</Callout>

## ปัญหา

subscription ของ Claude มีการวัดลิมิตสามอย่างพร้อมกัน (ทั้งหมดยืนยันผ่าน `/usage`):

- **เซสชันปัจจุบัน**: หน้าต่างเวลาแบบเลื่อน (rolling) 5 ชั่วโมง
- **สัปดาห์ปัจจุบัน (ทุกโมเดล)**: ยอดรวม 7 วัน
- **สัปดาห์ปัจจุบัน แยกตามโมเดล**: ลิมิตรายสัปดาห์แยกต่างหากสำหรับแต่ละตระกูลโมเดล ปัจจุบันมีเฉพาะ Sonnet และ Fable เท่านั้น และมีเพียงลิมิตของ Fable ที่แน่นพอที่จะมีผลจริง โดยจะถึงลิมิตก่อนยอดรวมมาก เครื่องอาจอยู่ที่ 50% ของ week-all ในขณะที่อยู่ที่ 80% ของ week-Fable แล้ว

โควตารายสัปดาห์เป็นแบบใช้หรือเสีย (use-it-or-lose-it) นั่นคือส่วนที่บัญชียังไม่ได้ใช้เมื่อถึงเวลารีเซ็ตรายสัปดาห์แบบตายตัวจะถูกริบไป ถ้าคุณเป็นเจ้าของบัญชีหลายบัญชี กลยุทธ์ที่สมเหตุสมผลคือใช้โควตาต่อไปบนบัญชีที่ล้าหลังจังหวะรายสัปดาห์ของตัวเองมากที่สุด และสลับออกไปก่อนที่ลิมิตใดลิมิตหนึ่งจะชนกำแพงกลางเซสชัน

การทำสิ่งนั้นด้วยมือหมายถึงต้องออกจากระบบ เข้าสู่ระบบใหม่ และสูญเสียบทสนทนาของคุณ tokenmaxxing ทำสิ่งนี้ให้อัตโนมัติ กล่าวคือ `claude` ที่กำลังทำงานอยู่จะตรวจสอบที่เก็บ credential ของมันอีกครั้งระหว่างคำขอต่างๆ ดังนั้น credential ที่ถูกสลับอยู่ข้างใต้จึงถูกนำมาใช้แทนที่ได้ทันที (ภายในประมาณ 30 วินาทีบน macOS และในคำขอถัดไปบน Linux) การสลับแบบธรรมดาจะไม่รีสตาร์ทเซสชันของคุณเลย กรณีเดียวที่ยังต้องมีการจัดการโปรเซสคือเมื่อพูลหมดเกลี้ยงทั้งพูล เพราะเซสชันไม่สามารถหยุดตัวเองได้ และนั่นคือเหตุผลที่ตัว supervisor แบบบางเบามีอยู่

ทุกอย่างที่เหลือเกี่ยวกับ `claude` ยังคงเหมือนเดิม ไม่ว่าจะเป็นแฟล็กทั้งหมด เซิร์ฟเวอร์ MCP ฮุก และสกิล ล้วนส่งผ่านไปได้ตามปกติ

## เริ่มต้นอย่างรวดเร็ว

ต้องใช้ [Bun](https://bun.sh) และ Claude Code บน macOS หรือ Linux

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` ทำห้าอย่าง:

1. นำเข้าบัญชีที่คุณเข้าสู่ระบบอยู่แล้วเป็นบัญชี #1 (ไม่มีคำสั่ง `adopt` แยกต่างหาก)
2. ติดตั้ง shim ของ supervisor สำหรับ `claude`
3. ติดตั้งสามรายการใน `settings.json` ของ Claude Code ได้แก่ statusLine, Stop hook และ SessionStart hook (พร้อมกับรายการ subagentStatusLine)
4. เพิ่มไดเรกทอรี bin ของ supervisor เข้าไปใน PATH ของไฟล์ rc ของเชลล์คุณ (ทำซ้ำได้โดยไม่เปลี่ยนผล มีคอมเมนต์ `# tokenmaxxing PATH` กำกับไว้) มันต้องอยู่ก่อน `claude` ตัวจริงใน PATH เพื่อดักจับ
5. ติดตั้งตัวจับเวลาตรวจสอบเป็นระยะ (launchd agent บน macOS และ systemd user timer บน Linux) ที่รัน `tokenmaxxing check` ทุก 180 วินาที

รีสตาร์ทเชลล์ของคุณ จากนั้นเพิ่มบัญชีและเริ่มใช้งานได้เลย:

```sh
tokenmaxxing add        # เข้าสู่ระบบอีกหนึ่งบัญชีแบบแยกส่วน แล้วรวมเข้าพูล
claude                  # ใช้ claude ได้เหมือนเดิม
```

`tokenmaxxing` มี alias เป็น `xx` ด้วย การพิมพ์ `tokenmaxxing` (หรือ `xx`) เปล่าๆ จะรัน `status` ส่วน `switch` ต้องระบุอย่างชัดเจนเสมอ

## คำสั่ง

| คำสั่ง | ทำอะไร |
|---|---|
| `tokenmaxxing init` | นำเข้าบัญชีปัจจุบัน ติดตั้ง supervisor, ฮุก และ statusline |
| `tokenmaxxing init --codex` | เหมือนกันสำหรับ Codex คือนำเข้าล็อกอิน ติดตั้ง codex supervisor และ Stop hook |
| `tokenmaxxing add` | ลงทะเบียนบัญชีเพิ่มเติม (ล็อกอินแบบแยกส่วน แล้วเก็บเข้าพูล) |
| `tokenmaxxing add --codex` | ลงทะเบียนบัญชี Codex เพิ่มเติม (ล็อกอินแบบแยกส่วน) |
| `tokenmaxxing auth [sel \| --all]` | ยืนยันตัวตนใหม่ให้บัญชีในพูล ณ ที่เดิม คำสั่งเปล่าจะแสดงรายการพูลและถามว่าจะเลือกบัญชีไหน ตัวเลือก (selector) จะเจาะจงหนึ่งบัญชีและบอกว่าต้องเข้าสู่ระบบด้วยอีเมลใด `--all` จะไล่ทีละบัญชีที่ต้องยืนยันตัวตนใหม่ |
| `tokenmaxxing switch [sel]` | สลับไปยังบัญชีที่ดีที่สุด (แบบ greedy และ idempotent) หรือบังคับเลือกบัญชีที่เจาะจง |
| `tokenmaxxing switch --codex [sel]` | สลับพูลของ Codex (มีผลเมื่อเริ่ม codex ครั้งถัดไป) |
| `tokenmaxxing ls` | แสดงรายการบัญชีในพูล |
| `tokenmaxxing status` | บัญชีพร้อมแถบการใช้งาน 5 ชม. / รายสัปดาห์ / แยกตามโมเดล ทั้งที่ใช้งานอยู่และที่หมดโควตาจนกว่าจะรีเซ็ต |
| `tokenmaxxing status --force` | เพิ่มเติมคือ ping ทุกบัญชี (คำขอ haiku เล็กๆ บัญชีละหนึ่งครั้ง) เพื่อให้ตัวจับเวลาเซสชัน 5 ชม. ทั้งหมดเริ่มนับตอนนี้ แล้วเก็บตัวอย่างข้อมูลใหม่ |
| `tokenmaxxing watch [seconds]` | สถานะแบบเรียลไทม์ เรนเดอร์ใหม่ทุก N วินาที (ค่าเริ่มต้น 120 ต่ำสุด 30 ไม่มีการ ping) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | config ที่มีผลจริงพร้อมแหล่งที่มา แก้ไขคีย์แบบจุด (dotted keys) `tidy` จะตัดคีย์ที่ไม่รู้จักออก |
| `tokenmaxxing check` | ประเมินการตัดสินใจสลับหนึ่งครั้ง (นี่คือสิ่งที่ตัวจับเวลาเป็นระยะรัน) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | เดมอนสะพานเชื่อม Slack (Socket Mode ไม่ต้องมี URL สาธารณะ) |
| `tokenmaxxing doctor` | ตรวจสอบว่า supervisor และรายการการตั้งค่ายังอยู่ครบ |
| `tokenmaxxing rename [--codex] <sel> <label>` | เปลี่ยนป้ายชื่อบัญชีในพูล |
| `tokenmaxxing rm <sel>` | ลบบัญชีออกจากพูล |
| `tokenmaxxing uninstall` | ลบ supervisor และรายการการตั้งค่า (บัญชีและ credential จะถูกเก็บไว้) |

## สถาปัตยกรรม

tokenmaxxing เป็นจุดเข้า (entry point) แบบเรียกได้หลายชื่อเพียงจุดเดียว (`src/main.ts`) ที่ทำหน้าที่เป็น supervisor ของ `claude` เมื่อถูกเรียกด้วยชื่อนั้น ให้บริการ shim ของฮุกและ statusline ผ่านคำสั่งย่อยภายใน และในกรณีอื่นก็ส่งต่อไปยัง CLI มันรันโดยตรงบน Bun แพ็กเกจ npm ส่งมาเป็นซอร์สโค้ด TypeScript ไม่ใช่ไฟล์ที่ผ่านการ build

ส่วนประกอบที่ทำงานอยู่:

### shim ของ supervisor

`init` เขียน shim ของเชลล์ 2 บรรทัดชื่อ `claude` ลงใน `~/.config/tokenmaxxing/bin/` และวางไดเรกทอรีนั้นไว้เป็นอันดับแรกใน PATH เมื่อคุณพิมพ์ `claude` shim จะรัน supervisor ซึ่งจะ spawn ไบนารี claude ตัวจริงโดยสืบทอด stdio และสแนปช็อตของเทอร์มินัลที่บันทึกด้วย `stty -g` มันเป็นเพียงตัวจัดการโปรเซสและเทอร์มินัลเท่านั้น ไม่เคยทำหน้าที่เป็นพร็อกซีให้ทราฟฟิก API และไม่เคยแตะต้อง token ที่กำลังส่งอยู่

การเรียกใช้ในโหมด print (`claude -p`, `--version`, `--help`) คำสั่งย่อยที่ไม่โต้ตอบ (`claude mcp`, `claude config` และอื่นๆ) และการ probe ของ tokenmaxxing เองจะส่งผ่านตรงๆ โดยไม่มีการจัดการเซสชัน สำหรับเซสชันแบบโต้ตอบ supervisor จะปักหมุด session id (โดยสร้างขึ้นใหม่ หรือใช้ตัวที่คุณส่งมาผ่าน `--session-id` / `-r` / `-c` ซ้ำ) เก็บแฟล็กการเปิดใช้งานของคุณไว้เพื่อให้การเปิดใหม่ในภายหลังสามารถเล่นซ้ำได้ จากนั้นจึงเฝ้าดูไฟล์ marker สำหรับ respawn ที่ผูกกับเซสชันนั้น

### การ tee ของ statusline

Claude Code จะส่งข้อมูลลิมิตอัตรา (`rate_limits.five_hour` และ `rate_limits.seven_day`) เข้าไปยัง stdin ของ statusline ในทุกเทิร์น tokenmaxxing เป็นเจ้าของช่อง statusline ดังนั้นตัวเรนเดอร์ของมันจึงทำหน้าที่เป็นฟีดการใช้งานแบบ push ที่ฟรีไปในตัว โดยในแต่ละจังหวะ (tick) มันจะ tee หน้าต่างยอดรวมพร้อมกับโมเดลที่ใช้งานอยู่ลงใน `usage.json` ลิมิตแยกตามโมเดลไม่ได้อยู่ใน stdin ของ statusline แต่มาจาก `claude -p '/usage'` เท่านั้น (ฟรี ไม่ใช้ token) ซึ่งจะถูก poll พร้อม TTL และแคชลงใน `model-usage.json` เมื่อโมเดลที่ใช้งานอยู่ถูกจำกัดความจุ

การ tee เป็นแบบเขียนเมื่อมีการเปลี่ยนแปลง (write-on-change) เมื่อตัวเลขไม่เปลี่ยนแปลง มันจะเพียงอัปเดต mtime ของไฟล์ ซึ่งทำหน้าที่เป็นสัญญาณชีพ (heartbeat) ของฟีด ความสดใหม่จะถูกตัดสินจาก mtime เสมอ ไม่ใช่จาก timestamp ที่ฝังอยู่ในไฟล์

### Stop hook และการสลับ

ที่ขอบเขตของทุกเทิร์น Stop hook จะรันการตัดสินใจสลับ (ดู [การตัดสินใจสลับทำงานอย่างไร](#how-switching-decides)) เมื่อการสลับมีความจำเป็น มันจะเกิดขึ้นภายใต้ล็อกแบบเอ็กซ์คลูซีฟ `flock(2)` (ทำผ่าน `bun:ffi` เนื่องจาก macOS ไม่มีไบนารี `flock(1)` มาให้) และการเขียน credential ยังประสานล็อก (interlock) กับ refresh lock ของ Claude Code เองด้วย ภายในส่วนวิกฤต (critical section) การสลับหนึ่งครั้งจะ:

1. เก็บเกี่ยว credential สดปัจจุบันไปยังไฟล์สำรอง (parked backup) ของเจ้าของที่แท้จริง
2. ติดตั้ง credential ที่รีเฟรชใหม่ของบัญชีเป้าหมายเป็นตัวสด โดยรวมเข้ากับ blob สดที่มีอยู่เดิม เพื่อให้สถานะข้างเคียง (เช่น token OAuth ต่อเซิร์ฟเวอร์ MCP) ยังคงอยู่
3. บันทึก token ที่หมุนเวียนแล้วของบัญชีเป้าหมายลงในไฟล์สำรองของตัวเอง
4. เขียนฟิลด์ `oauthAccount` ใน `~/.claude.json` ใหม่แบบอะตอมมิก
5. ยืนยันป้ายบัญชีที่ใช้งานอยู่อันใหม่และล้างสแนปช็อตการใช้งานที่เก่าค้าง ทั้งหมดก่อนที่ล็อกจะถูกปล่อย เพื่อให้การล่มของโปรแกรมไม่มีทางทำให้ credential ที่ติดตั้งไว้กับป้ายบัญชีที่ใช้งานอยู่ชี้ไปคนละบัญชีกัน

เนื่องจากทุกเซสชันในโปรไฟล์เริ่มต้นใช้ credential สดตัวเดียวกัน การสลับเพียงครั้งเดียวจึงย้ายทุกเซสชันพร้อมกัน และ flock พร้อมกับการตรวจสอบซ้ำภายใต้ล็อกช่วยป้องกันไม่ให้ฮุกที่แข่งกัน (racing hooks) เผาผลาญสองบัญชี

### การนำมาใช้ ณ ที่เดิม

เซสชัน claude ที่กำลังทำงานจะ poll ที่เก็บ credential ระหว่างคำขอ บน macOS มันจะอ่าน keychain ใหม่ผ่านแคชระยะสั้นและเปรียบเทียบ access token ส่วนบน Linux มันจะ stat ค่า mtime ของไฟล์ credential และล้างแคช token เมื่อมีการเปลี่ยนแปลง ผลลัพธ์สุทธิคือ credential ที่ถูกสลับจะถูกนำมาใช้โดยทุกเซสชันที่กำลังทำงานภายในประมาณ 30 วินาทีบน macOS และในคำขอถัดไปทันทีบน Linux โดยไม่ต้องรีสตาร์ทใดๆ นี่คือเหตุผลที่การสลับแบบธรรมดาไม่เขียน marker และไม่กระตุ้นให้เกิด respawn เซสชันเพียงแค่ดำเนินต่อบนบัญชีใหม่ `/usage` ภายในเซสชันใช้แคช token ชุดเดียวกัน ดังนั้นการแสดงบัญชีของมันจึงเปลี่ยนไปพร้อมกับการนำมาใช้

### การรอเมื่อพูลหมดและการกลับมาทำงานอัตโนมัติ

เฉพาะเมื่อทุกบัญชีในพูลเกินแถบ (bars) ของตัวเองแล้วเท่านั้น Stop hook จึงจะเขียน respawn marker (สคีมาของ marker กำหนดให้ต้องมี timestamp `waitUntil` การสลับแบบธรรมดาไม่มีทางสร้างมันได้) supervisor เห็น marker จึงส่ง SIGTERM ให้โปรเซสลูกที่ขอบเขตเทิร์นที่ยืนยันไปแล้ว (Stop hook รันหลังจากทรานสคริปต์อยู่บนดิสก์และ claude ว่างอยู่ ดังนั้นจึงไม่มีอะไรสูญหาย) คืนค่าเทอร์มินัล แสดงการนับถอยหลังไปยังการรีเซ็ตที่เร็วที่สุด แล้วจึงเปิด `claude --resume <session-id>` ใหม่บนบัญชีที่ฟื้นแล้ว การกด Ctrl-C ระหว่างนับถอยหลังจะกลับมาทำงานต่อทันที การรออัตโนมัติถูกจำกัดด้วย `policy.maxWaitMs` (ค่าเริ่มต้น 1 ชั่วโมง) หากเกินกว่านั้น การตัดสินใจจะรายงานว่าพูลหมดแทนที่จะรอต่อ

### ตัวจับเวลาตรวจสอบเป็นระยะ

ฮุกจะทำงานเฉพาะที่ขอบเขตเทิร์นเท่านั้น และเทิร์นแบบ agentic ที่ยาวเพียงเทิร์นเดียวสามารถเผาผลาญหน้าต่างจากสภาพดีจนหมดได้โดยไม่มีขอบเขตเลยแม้แต่ครั้งเดียว ดังนั้น `init` จึงติดตั้งตัวจับเวลาเป็นระยะด้วย (launchd agent บน macOS และ systemd user timer บน Linux) ที่รัน `tokenmaxxing check` ทุก 180 วินาทีโดยไม่ขึ้นกับกิจกรรมของเทิร์น

### SessionStart hook

รันการประเมินแบบเดียวกันเมื่อเซสชันเริ่มหรือกลับมาทำงานต่อ เพื่อให้เซสชันใหม่เริ่มต้นบนบัญชีที่ถูกต้อง ช่วงพัก (cooldown) หลังการสลับทำให้มันเป็น no-op ที่ถูกต้องทันทีหลัง respawn

## การตัดสินใจสลับทำงานอย่างไร [#how-switching-decides]

การตัดสินใจมีสองชั้น ได้แก่ ประตูการเข้าทำงาน (engagement gate) แล้วจึงเป็นเส้นทางแบบ greedy หรือแบบ hard

### การเข้าทำงาน

เมื่อต่ำกว่า `policy.greedySessionFloor` (ค่าเริ่มต้น 50 คิดเป็นเปอร์เซ็นต์ของหน้าต่างเซสชัน 5 ชั่วโมง) การตัดสินใจจะไม่ทำงานเลย เซสชันใหม่จะใช้บัญชีของมันต่อไป เมื่อหน้าต่างเซสชันที่ใช้งานอยู่ถูกใช้ไป 50% หรือมีแถบ hard ใดถูกข้าม การตัดสินใจจึงจะเข้าทำงาน

### แถบคัดกรอง

ค่าเกณฑ์ (thresholds) คือแถบคัดกรอง ไม่ใช่ตัวกระตุ้นให้แตกตื่น:

- `thresholds.session`: 95 การรอให้รีเซ็ต 5 ชั่วโมงมีต้นทุนต่ำ ดังนั้นหน้าต่างเซสชันจึงสลับออกไปเร็วกว่า
- `thresholds.weekly`: 98 แถบเดียวนี้ครอบคลุมทั้งยอดรวม 7 วันและลิมิตรายสัปดาห์แยกตามโมเดลทุกตัว โควตารายสัปดาห์เป็นแบบใช้หรือเสีย ดังนั้นจึงใช้จนใกล้ชนกำแพง

ทั้งสองค่าถูกตั้งไว้ต่ำกว่า 100 โดยเจตนา พื้นที่เหลือคืองบประมาณสำหรับไปให้ถึงขอบเขตเทิร์นที่สะอาด (บวกกับความหน่วงในการนำมาใช้ได้ถึงหนึ่งเทิร์นบน macOS) ก่อนที่บัญชีจะชนลิมิตจริงๆ แถบเดียวกันนี้ใช้คัดกรองบัญชีที่จะเป็นตัวเลือกในการสลับ บัญชีที่เกินแถบใดแถบหนึ่งของตัวเองจะไม่ใช่เป้าหมายที่ถูกต้อง ทั้งตัวกระตุ้นและการคัดกรองใช้แถบที่มีผลจริง (effective bars) ชุดเดียวกันเสมอ (thresholds ลบด้วย `policy.projectionMargin`) เพราะการคัดกรองที่หลวมกว่าตัวกระตุ้นจะทำให้การสลับไปลงบนบัญชีที่ตัวกระตุ้นจะติดธงซ้ำทันที ทำให้พูลกระเด้งไปมา

### เป้าหมาย: แรงกดดันจังหวะ (pace pressure)

ในบรรดาบัญชีที่ใช้งานได้ เป้าหมายคือบัญชีที่ล้าหลังจังหวะรายสัปดาห์ของตัวเองมากที่สุด นั่นคือมี **pace pressure** สูงสุด ซึ่งนิยามว่าเป็นเปอร์เซ็นต์รายสัปดาห์ที่เหลือหารด้วยเวลาจนกว่าบัญชีนั้นจะรีเซ็ตรายสัปดาห์ บัญชีที่กำลังจะถูกริบโควตามากที่สุดเป็นผู้ชนะ กรณีเสมอกันจะตัดสินด้วยวันหมดอายุรายสัปดาห์ที่เร็วที่สุดก่อน จากนั้นจึงเป็นการใช้งาน 7 วันที่ต่ำที่สุด

ทุกอย่างทำงานจากหน้าต่างที่แคชไว้ ซึ่งเก็บเป็นค่า UTC epoch แบบสัมบูรณ์ ดังนั้นสแนปช็อตที่เก่าค้างก็ยังคำนวณได้ถูกต้อง กล่าวคือการรีเซ็ตรายสัปดาห์ที่ผ่านไปแล้วจะถูกคาดการณ์ไปข้างหน้าเป็นขั้นละ 7 วันพอดี และหน้าต่างใดที่เลยการรีเซ็ตที่แคชไว้จะถูกนับว่าว่างเปล่าใหม่ (ไม่เป็นเหตุผลให้สลับ และไม่เป็นเหตุผลให้พักบัญชีไว้)

### เส้นทาง greedy กับ hard

- **เส้นทาง greedy** (เข้าทำงานแล้ว แต่ยังต่ำกว่าทุกแถบ): จัดอันดับทุกบัญชี รวมถึงบัญชีปัจจุบันด้วย ถ้าบัญชีปัจจุบันชนะหรือเสมออยู่แล้ว ก็ไม่ทำอะไร มิฉะนั้นจึงสลับไปยังบัญชีที่ดีกว่าอย่างชัดเจน มันไม่เคยรอและไม่เคย pre-park บัญชีปัจจุบันที่ใช้งานได้จะไม่ถูกแลกกับการรอ เนื่องจากบัญชีปัจจุบันก็ถูกจัดอันดับด้วย ทั้งเส้นทางอัตโนมัติและ `tokenmaxxing switch` เปล่าๆ จึงเป็น idempotent การประเมินเป็นระยะจะลู่เข้าสู่บัญชีที่ถูกต้องแล้วอยู่นิ่ง
- **เส้นทาง hard** (มีแถบถูกข้าม): สลับออกไปยังตัวเลือกที่ใช้งานได้ดีที่สุด ถ้าปรากฏว่า refresh token ของตัวเลือกใดตายแล้ว มันจะถูกติดธงว่าต้องยืนยันตัวตนใหม่ (needs-reauth) และลองตัวเลือกถัดไป ถ้าไม่มีตัวเลือกใดใช้งานได้ ตรรกะการรอเมื่อหมดโควตาจะทำงาน มีเพียงผู้เรียก (caller) ที่สามารถหยุดเซสชันได้จริง (Stop hook ที่ถูกควบคุมโดย supervisor) เท่านั้นที่ได้รับอนุญาตให้ pre-park ไปยังบัญชีที่ยังถูกบล็อกอยู่แต่จะฟื้นตัวเร็วที่สุด

### ลิมิตแยกตามโมเดล

`policy.switchModels` (ค่าเริ่มต้น `["fable"]`) ระบุตระกูลโมเดลที่ลิมิตรายสัปดาห์แยกตามโมเดลสามารถกระตุ้นการสลับได้ การจับคู่ทำโดยใช้ family token ไม่ใช่สตริงที่แสดงผลแบบตรงเป๊ะ เพราะชื่อที่แสดงของโมเดลเปลี่ยนไปเรื่อยๆ ("Fable" กลายเป็น "Fable 5") และครั้งหนึ่งประตูที่ใช้สตริงตรงเป๊ะเคยปิดการสลับแยกตามโมเดลทั้งหมดอย่างเงียบๆ มีกฎความปลอดภัยที่เกี่ยวข้องสองข้อ:

- โมเดลที่ใช้งานอยู่ซึ่งไม่ทราบชนิดจะเปิดประตู (gate) ให้ทุกตระกูลที่ตั้งค่าไว้ ทันทีหลังจากการสลับล้างสแนปช็อต เครื่องแบบ headless อาจทำงานโดยไม่เห็นข้อมูลโมเดล การปฏิบัติต่อโมเดลที่ไม่ทราบว่าไม่มีข้อจำกัดครั้งหนึ่งเคยทำให้บัญชีค้างอยู่ที่ลิมิต Fable ของมันหลายชั่วโมงโดยไม่มีใครสังเกต
- การคัดกรองตัวเลือกก็นับลิมิตแยกตามโมเดลที่ถูกเปิดประตูด้วย ดังนั้นพูลที่ทุกบัญชีใช้ลิมิต Fable หมดแล้วจึงไม่วนสลับไปเรื่อยๆ (round-robin)

### ช่วงพัก (cooldown)

ช่วงพักหลังการสลับ 45 วินาทีจะควบคุมเส้นทางอัตโนมัติ การ tee ของ statusline จะถูกระงับเป็นเวลา 45 วินาทีเดียวกันนั้นหลังการสลับ (การนำมาใช้ใช้เวลาได้ถึง 30 วินาทีบน macOS) ดังนั้นการประเมินก่อนหน้านั้นจะทำงานบนข้อมูลที่ตัวการสลับเองทำให้ใช้ไม่ได้ สถานการณ์นั้นเคยก่อให้เกิดลูป respawn แบบไป A มา B แล้วกลับ การใช้ `tokenmaxxing switch` ด้วยมือไม่ได้รับผลกระทบจากช่วงพัก

## การตั้งค่า

การตั้งค่าเป็น JSON อยู่ที่ `~/.config/tokenmaxxing/config.json` ทุกฟิลด์เป็นทางเลือก และค่าเริ่มต้นจะถูกใช้เป็นรายฟิลด์

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: แถบคัดกรองที่อธิบายไว้ข้างต้น
- `policy.projectionMargin`: ค่าที่ถูกลบออกจากทั้งสองแถบเพื่อสร้างแถบที่มีผลจริง
- `policy.greedySessionFloor`: เปอร์เซ็นต์การใช้เซสชันที่การลู่เข้าแบบ greedy จะเริ่มทำงาน
- `policy.switchModels`: ตระกูลโมเดลที่ลิมิตรายสัปดาห์แยกตามโมเดลจะเปิดประตูให้สลับ (รายการจะถูกแปลงเป็นตัวพิมพ์เล็กเมื่อโหลด)
- `policy.usagePollTtlMs`: การ poll `/usage` แยกตามโมเดลจะคงความสดใหม่นานเท่าใด
- `policy.maxWaitMs`: ขอบเขตการรออัตโนมัติเมื่อพูลหมด

`tokenmaxxing config` แสดงการตั้งค่าที่มีผลจริงพร้อมแหล่งที่มา `config set`/`unset` แก้ไขคีย์แบบจุด `config tidy` ตัดคีย์ที่ไม่รู้จักออก

## โครงสร้างไดเรกทอรีสถานะ

ทุกอย่างอยู่ใต้ `~/.config/tokenmaxxing/` (แทนที่ได้ด้วย `TOKENMAXXING_HOME` ทุกพาธที่สังเกตได้จากภายนอกมี env override เพื่อให้ทั้งเครื่องมือรันแบบแยกสมบูรณ์ (hermetic) ในการทดสอบได้)

| พาธ | เก็บอะไร |
|---|---|
| `config.json` | การตั้งค่าของคุณ (แบบเบาบาง ค่าเริ่มต้นมีผลรายฟิลด์) |
| `accounts.json` | ดัชนีที่ไม่เป็นความลับของบัญชี Claude ในพูล: ป้ายชื่อ, id, หน้าต่างการใช้งานที่แคชไว้ ไม่เคยเก็บ token |
| `usage.json` | สแนปช็อตหน้าต่างรวมจากการ tee ของ statusline; mtime ของมันคือสัญญาณชีพว่าฟีดยังมีชีวิตอยู่ |
| `model-usage.json` | ลิมิตรายสัปดาห์แยกตามโมเดลจาก `/usage` ที่แคชแบบมี TTL |
| `lastswap.json` | เวลา epoch ของการสลับครั้งล่าสุด ใช้ขับช่วงพัก 45 วินาที |
| `lock` | ไฟล์ `flock` ที่ทำให้การสลับเป็นลำดับ |
| `tokenmaxxing.log` | log เหตุการณ์แบบ append-only |
| `bin/` | shim ของ PATH: `claude`, `codex` และจุดเข้า `tokenmaxxing` / `xx` |
| `respawn/<session-id>` | มาร์กเกอร์ respawn เมื่อรอเพราะโควตาหมด ที่ supervisor คอยเฝ้าดู |
| `creds/` | เฉพาะ Linux: ไฟล์ credential ที่จอดไว้ สิทธิ์ 0600 ในไดเรกทอรี 0700 (บน macOS จะจอด credential เป็นรายการ keychain รายบัญชีแทน) |
| `onboard/`, `sample/` | config home แบบแยกส่วนที่ใช้แล้วทิ้ง สำหรับการล็อกอิน `add`/`auth` และการ probe `/usage` ของบัญชีที่จอดไว้ onboard home ที่มี credential แบบข้อความล้วนจะถูกลบหลังเก็บเกี่ยว |
| `slack.json` | token และลิงก์ช่องของ `xx serve` (0600) |
| `slack-threads/` | บันทึกเซสชันรายเธรดสำหรับ `xx serve` |
| `codex-*` | พูล Codex คู่ขนาน: `codex-accounts.json`, `codex-lastswap.json`, `codex-lock`, `codex-creds/`, `codex-onboard/`, `codex-respawn/` และ `codex-live/` (ไฟล์แสดงการมีอยู่หนึ่งไฟล์ที่ตรวจ PID ต่อเซสชัน codex ที่มี supervisor กำลังรัน เพื่อไม่ให้บัญชีที่กำลังทำงานถูกใช้เป็นเป้าหมายการสลับ) |

นอกไดเรกทอรีของตัวเอง tokenmaxxing แตะต้องเพียง: `~/.claude.json` (การสลับ `oauthAccount`), `settings.json` ของ Claude Code (รายการฮุกและ statusline), ที่เก็บ credential ที่ใช้งานจริง (รายการ keychain `Claude Code-credentials` บน macOS, `.credentials.json` บน Linux), `~/.claude.lock` (ล็อกรีเฟรชของ claude ที่จับระหว่างการสลับ), `auth.json` และ `hooks.json` ของ codex และยูนิตตรวจสอบเป็นระยะใน launchd หรือ systemd

## การจัดเก็บ credential และโมเดลความปลอดภัย

สถานะทั้งหมดอยู่ใน `~/.config/tokenmaxxing/` การอ่านเขียน credential (I/O) ผ่าน facade ของที่เก็บที่เลือกตามแพลตฟอร์มเพียงตัวเดียว จุดที่เรียกใช้จะไม่แยกสาขาตามแพลตฟอร์มเลย

**macOS**: credential อยู่ใน login keychain ในรูปแบบรายการ generic-password ซึ่งตรงกับที่ Claude Code เองเก็บไว้ รายการสด (live item) คือรายการที่ claude อ่าน ไฟล์สำรองของแต่ละบัญชีในพูลจะถูก park เป็นรายการ keychain `tokenmaxxing-cred-<uuid8>` ของตัวเอง ไม่มีอะไรเป็นข้อความธรรมดา (plaintext) อยู่บนดิสก์ การอ่านใช้ `security find-generic-password -w` (ความลับจะปรากฏบน stdout เท่านั้น) การเขียนจะ pipe บรรทัด `add-generic-password` เข้าไปยัง `security -i` ผ่าน stdin เพื่อไม่ให้ความลับปรากฏใน argv ของโปรเซสใดๆ โหมดโต้ตอบมีบัฟเฟอร์บรรทัดประมาณ 4 KB ดังนั้น blob ที่ใหญ่เกินไปจะย้อนกลับไปใช้การเขียนแบบ argv ซึ่งเป็นเหตุผลหนึ่งที่รายการที่ park เก็บเพียงอ็อบเจกต์ OAuth ขั้นต่ำเท่านั้น

**Linux**: Claude Code เก็บ credential เป็นไฟล์ข้อความธรรมดาสิทธิ์ 0600 และ tokenmaxxing ใช้โมเดลเดียวกัน คือไฟล์สดคือ `.credentials.json` ของ claude เอง และไฟล์สำรองที่ park ไว้เป็นไฟล์สิทธิ์ 0600 แบบอะตอมมิกภายใต้ `~/.config/tokenmaxxing/creds/` ในไดเรกทอรีสิทธิ์ 0700 คำว่าอะตอมมิกในที่นี้หมายถึงการเขียนลงไฟล์ชั่วคราว fsync แล้วจึงเปลี่ยนชื่อ (rename) ตัวอ่านที่ทำงานพร้อมกันจะเห็นไฟล์เก่าทั้งไฟล์หรือไฟล์ใหม่ทั้งไฟล์เสมอ ไม่มีทางเห็นไฟล์ที่ไม่สมบูรณ์

กฎความปลอดภัยที่การสลับบังคับใช้:

- **เก็บเกี่ยวตามเจ้าของที่แท้จริง** ก่อนการสลับ เจ้าของที่แท้จริงของ credential สดจะถูกระบุด้วยการถาม API ว่า token เป็นขององค์กรใด (`fetchTokenOrg` กับ OAuth roles endpoint) ไม่ใช่ด้วยการเชื่อป้ายบัญชีที่ใช้งานอยู่ซึ่งเก็บไว้ เพราะมันเลื่อนคลาดได้ ป้ายที่เลื่อนคลาดครั้งหนึ่งเคยทำให้การเก็บเกี่ยวของบัญชีหนึ่งไปเขียนทับไฟล์สำรองเพียงไฟล์เดียวของอีกบัญชี ถ้า credential สดเป็นของบัญชีที่อยู่นอกพูล การสลับจะปฏิเสธทันทีแทนที่จะเขียนทับมัน
- **ส่วนวิกฤตเดียว** การเก็บเกี่ยว การติดตั้ง credential ใหม่ การสำรอง token ที่หมุนเวียนของมัน การสลับบัญชีใน `~/.claude.json` และการยืนยันป้ายบัญชีที่ใช้งานอยู่ ทั้งหมดเกิดขึ้นภายในส่วนที่ล็อกไว้เดียวกัน
- **ประสานล็อกกับการรีเฟรชของ claude เอง** เซสชันที่ใกล้หมดอายุสามารถหมุนเวียน token ของตัวเองได้ทุกเมื่อ ดังนั้นการเขียน credential จึงจับ refresh lock ของ Claude Code ด้วย (แบบพยายามให้ดีที่สุด พร้อมการเรียกคืนล็อกค้าง และการหมดเวลาที่มีขอบเขต)
- **grant ที่ตายแล้วเสื่อมลงอย่างเรียบร้อย** การรีเฟรชที่ตอบกลับมาเป็น `invalid_grant` จะติดธงบัญชีนั้นว่าต้องยืนยันตัวตนใหม่ และบันทึกธงก่อนที่ข้อผิดพลาดจะแพร่กระจาย ดังนั้นลูปการลองใหม่จะทำให้ชุดตัวเลือกเล็กลงและสิ้นสุด `tokenmaxxing auth` ซ่อมบัญชีที่ติดธง ณ ที่เดิม และจะปฏิเสธการเข้าสู่ระบบที่ไปลงคนละบัญชีกับบัญชีที่กำลังซ่อม
- **ไม่บันทึก token** token ไม่เคยปรากฏในบันทึก (log) ข้อผิดพลาด หรือเอาต์พุต เนื้อหาข้อผิดพลาด (error body) จาก token และ usage endpoint ไม่เคยถูกแสดงแบบดิบ มีเพียงชุดฟิลด์ที่อยู่ในรายการอนุญาต (allowlist) เท่านั้นที่ผ่านออกมา เพราะเนื้อหาความล้มเหลวของ token endpoint อาจสะท้อนเนื้อหาของคำขอกลับมาได้
- **สุขอนามัยของการ probe** การ probe `claude` ที่ถูก spawn ทุกครั้งจะล้างตัวแปรสภาพแวดล้อมแปดตัวที่ claude ให้ความสำคัญก่อนการค้นหา keychain (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR` และอื่นๆ) เพื่อไม่ให้การ probe ถูกระบุว่าเป็นของบัญชีที่ผิดได้

## หมายเหตุแพลตฟอร์ม: macOS กับ Linux

| | macOS | Linux |
|---|---|---|
| credential สด | รายการ generic-password ใน login keychain | ไฟล์ `.credentials.json` สิทธิ์ 0600 |
| credential ที่ park ไว้ | รายการ keychain ต่อบัญชี | ไฟล์สิทธิ์ 0600 ในไดเรกทอรีสิทธิ์ 0700 |
| การนำมาใช้หลังการสลับ | ภายในประมาณ 30 วินาที (แคชการอ่าน keychain) | คำขอถัดไป (การ poll ค่า mtime ของไฟล์) |
| การตรวจสอบเป็นระยะ | launchd agent ทุก 180 วินาที | systemd user timer ทุก 180 วินาที |
| ที่เก็บล็อกอินแบบแยกส่วน | บริการ keychain ที่ตั้ง namespace ด้วยแฮชต่อไดเรกทอรี config | ไฟล์ภายในไดเรกทอรี config ที่แยกส่วน |

รายละเอียดเฉพาะของ Linux สองข้อที่ควรทราบ: claude จะระบุไดเรกทอรี credential จาก `CLAUDE_SECURESTORAGE_CONFIG_DIR` ก่อน (จากนั้น `CLAUDE_CONFIG_DIR` แล้วจึง `~/.claude`) และ tokenmaxxing ทำตามการระบุนั้นแบบเป๊ะๆ เพื่อไม่ให้ทั้งสองไม่ตรงกัน และ build ของทั้งสองระบบปฏิบัติการในเวอร์ชัน claude เดียวกันจัดรูปแบบนาฬิการีเซ็ตของ `/usage` ต่างกัน (อันหนึ่งใช้ตัวเชื่อม " at " อีกอันใช้จุลภาค) ตัวแยกวิเคราะห์ (parser) ของ tokenmaxxing รับเฉพาะสองรูปแบบนั้นพอดี และจะบันทึกลง log แทนที่จะเดา หากพบรูปแบบที่สาม

บน macOS มีข้อจำกัดที่ต้องบอกตามตรงหนึ่งข้อ: `init` และ `add` จะแตะ keychain แบบโต้ตอบโดยเจตนา เพื่อให้การเข้าถึง `security` ครั้งแรกไม่ใช่การเข้าถึงแบบเย็น (cold) ภายในฮุกแบบ headless

## statusline

tokenmaxxing เรนเดอร์ statusline ของ Claude Code แบบเนทีฟ (พร้อมกับ tee ฟีดการใช้งาน) หลักการออกแบบคือ: โควตาสื่อสารผ่านสี ไม่ใช่ตัวเลข หนึ่งบรรทัด ตัวอย่างเช่น:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- โทเคนของแต่ละหน้าต่างคือเวลาจนถึงการรีเซ็ตของมัน ทาสีบนแรมป์ (ramp) สีเขียวไปเหลืองไปแดงแบบต่อเนื่องตามเปอร์เซ็นต์การใช้ (truecolor เมื่อเทอร์มินัลรองรับ มิฉะนั้นจะไล่ลงบนคิวบ์สี 256 สี) แรมป์ยึดที่สีเขียวล้วนสำหรับค่า 0 สีเหลืองที่ 75 และสีแดงที่ 95 ขึ้นไป ดังนั้นแถบระดับความรุนแรงแบบเดิมจึงยังคงอยู่ในฐานะจุดยึดของแรมป์
- ชื่อโมเดลถูกทาสีตามปริมาณการเติมของหน้าต่างบริบท (context window) บนแรมป์เดียวกัน
- สัญลักษณ์ `◆` สีเขียวนำหน้าหน้าต่างของบัญชีที่ใช้งานอยู่ ทุกบัญชีที่ park ไว้จะได้ `◇` สีฟ้าคราม (cyan) ของตัวเอง (เป็น `✗` สีแดงหากต้องยืนยันตัวตนใหม่) บัญชีเรียงตามการรีเซ็ตที่กำลังจะมาถึงเร็วที่สุด
- ข้อมูลแยกตามโมเดลมาก่อนในแต่ละบล็อกในรูปอักษรตัวแรกที่ทาสีล้วนๆ: Fable แสดงเป็น `𝒇` ตระกูลอื่นใช้อักษรตัวแรกแบบพิมพ์ใหญ่ จับคู่ตามตระกูลเสมอ
- บัญชีที่ park ไว้และยังไม่ถูกแตะจะแสดงเป็น `full` สีเขียว การใช้งานที่วัดได้แต่ไม่ทราบเวลารีเซ็ตจะแสดงเป็น `?` ที่ทาสี และลิมิตแยกตามโมเดลที่ยังไม่ได้วัดบนโมเดลที่ถูกเปิดประตูจะแสดงเป็น `𝒇?` ที่ไม่ทาสี ค่าที่ยังไม่ได้วัดต้องไม่มีวันดูปลอดภัย
- การนับถอยหลังการรีเซ็ตจะแสดงเฉพาะหน่วยที่ใหญ่ที่สุดเท่านั้น ไม่มีวันแสดง "now" หรือ "0m" หน้าต่างที่ไม่มีการรีเซ็ตที่กำลังจะมาถึงจะแสดงเป็น `0` สีเขียว (ว่างอีกครั้ง)
- basename ของ git worktree ที่ลิงก์ไว้จะนำหน้าบรรทัด ส่วน checkout หลักจะไม่แสดงอะไรตรงนั้น การตรวจจับจะอ่านไฟล์ระบบเพื่อหาไฟล์ `.git` และไม่เคย spawn โปรเซสย่อยของ git
- เมื่อตั้งค่า `NO_COLOR` บรรทัดจะย้อนกลับไปใช้รูปแบบตัวเลขที่ติดกัน (`2h5` หมายถึงรีเซ็ตในอีก 2 ชั่วโมง ใช้ไป 5% ส่วน `ctx 42` คือปริมาณการเติมบริบท) เมื่อไม่มีสี หน้าต่างที่หมดแล้วต้องไม่ดูเหมือนยังสดใหม่

งานของ subagent จะได้แถวในแผงของตัวเองผ่านพื้นผิว subagentStatusLine ของ claude คือหนึ่งแถวต่อหนึ่งงานที่ทำงานอยู่ ชื่อตระกูลทาสีตามปริมาณการเติมบริบทของงานนั้น

## การรองรับ Codex

การรวมพูลแบบเดียวกันนี้ใช้ได้กับ Codex CLI ของ OpenAI โดยใช้กับบัญชี ChatGPT-subscription ของคุณเอง:

```sh
tokenmaxxing init --codex   # นำเข้าล็อกอิน codex ปัจจุบันของคุณ + ติดตั้ง codex supervisor และ Stop hook
tokenmaxxing add --codex    # เข้าสู่ระบบอีกบัญชีแบบแยกส่วน ล็อกอินหลักของคุณจะไม่ถูกแตะต้อง
codex                       # ใช้ codex ได้เหมือนเดิม
```

พูลของ Codex เป็นสถานะที่คู่ขนานกันอย่างสมบูรณ์ มีดัชนีบัญชีของตัวเอง มีไฟล์ credential ที่ park ไว้ของตัวเอง (ไฟล์สิทธิ์ 0600 บนทั้งสองแพลตฟอร์ม เนื่องจากที่เก็บของ codex เองเป็นไฟล์ข้อความธรรมดา) มีล็อกของตัวเอง มี timestamp การสลับครั้งล่าสุดของตัวเอง ไม่มีอะไรถูกใช้ร่วมกับพูลของ Claude ยกเว้นโค้ดนโยบายการตัดสินใจ

### เหตุใด hot-swap จึงเป็นไปไม่ได้บน Codex

โปรเซส codex ที่กำลังทำงานถือ auth manager ในหน่วยความจำเพียงตัวเดียว และปฏิเสธอย่างชัดเจนที่จะโหลด `auth.json` ใหม่เมื่อมันระบุคนละบัญชี ไม่มีตัวเฝ้าดูไฟล์ (file watcher) และไม่มีการ poll credential ต่อคำขอ ดังนั้น credential ที่ถูกสลับอยู่ข้างใต้ codex ที่กำลังทำงานจึงไม่มีวันมีผลต่อการอนุมาน (inference) เลย การรีสตาร์ทคือการสลับ: `codex resume <session-id>` จะดำเนินทรานสคริปต์ภายในต่อบนบัญชีที่ `auth.json` ถืออยู่ในตอนนี้

tokenmaxxing จัดการเรื่องนี้ด้วย shim ของ codex supervisor คือ Stop hook จะรันการตัดสินใจแบบ greedy ตาม pace-pressure เดียวกันที่ขอบเขตของแต่ละเทิร์น และเมื่อมันสลับ มันจะเขียน marker ที่ทำให้ supervisor ส่ง SIGTERM ให้เซสชันที่ขอบเขตที่ยืนยันไปแล้วและเปิด `codex resume <session-id>` ใหม่บนบัญชีที่สด โดยทรานสคริปต์ยังคงอยู่ครบ เนื่องจากทุกการสลับของ codex เป็นการรีสตาร์ทที่มองเห็นได้ เส้นทาง greedy ของ codex จึงมีส่วนเผื่อการปรับปรุง 1.2 เท่า นั่นคือผู้ท้าชิงต้องเอาชนะ pace pressure ของบัญชีปัจจุบัน 20% ไม่ใช่แค่นิดเดียว ส่วนเส้นทาง hard (มีแถบถูกข้าม) จะไม่สนใจส่วนเผื่อนี้ นอกจากนี้ยังไม่มีการนับถอยหลังเมื่อพูลหมดสำหรับ codex เพราะไม่มีอะไรหยุดเซสชัน codex ได้ ดังนั้นพูล codex ที่หมดเกลี้ยงจึงอยู่นิ่งกับที่

กลไกเฉพาะของ codex อื่นๆ:

- การใช้งานถูกอ่านจาก GET แบบยืนยันตัวตนที่ฟรีต่อ rate-limit endpoint ของ codex เอง (คำเรียกเดียวกับที่ `/status` ของ CLI ใช้) ได้เปอร์เซ็นต์พร้อมเวลารีเซ็ตแบบ epoch สัมบูรณ์ ทั้งหน้าต่างยอดรวมและลิมิตแยกตามโมเดลเหมือนกัน การจำแนกหน้าต่างขับเคลื่อนด้วยระยะเวลา ไม่ใช่ด้วยตำแหน่ง เพราะแผนปัจจุบันอาจไม่มีหน้าต่าง 5 ชั่วโมงเลย และหน้าต่างรายสัปดาห์อยู่ในช่องหลัก (primary slot)
- refresh token ของ codex หมุนเวียน และการนำตัวที่ถูกแทนที่แล้วมาใช้ซ้ำจะทำลายทั้งตระกูล grant ทุกการหมุนเวียนจะถูกบันทึกทันทีที่ตอบกลับมา บัญชีที่ใช้งานอยู่จะถูกเก็บตัวอย่างผ่าน blob สดเท่านั้น (ไม่ใช่สำเนาที่ park ไว้ซึ่งเก่าค้าง) และไฟล์การมีอยู่ (presence file) ต่อเซสชันช่วยรับประกันว่าบัญชีที่กำลังทำงานในเซสชันข้างเคียงที่ยังทำงานอยู่จะไม่มีวันเป็นเป้าหมายการสลับ และไม่มีวันถูกรีเฟรช token ที่ park ไว้
- Codex ต้องใช้ที่เก็บ credential แบบไฟล์: `init --codex` จะล้มเหลวทันทีหากมีการปักหมุดที่เก็บแบบ keyring ไว้ และ `add --codex` จะเขียนการตั้งค่าโหมดไฟล์ลงในโฮมสำหรับ onboarding ที่แยกส่วน เพื่อให้ล็อกอินไปลงในที่ที่เก็บเกี่ยวได้
- มีขั้นตอนที่ต้องทำด้วยมือหนึ่งขั้น: codex จะข้ามฮุกที่ยังไม่ได้รับแจ้งให้เชื่อถือ หลังจาก `init --codex` ให้เปิด codex หนึ่งครั้งและเชื่อถือ Stop hook ของ tokenmaxxing ผ่าน `/hooks` มิฉะนั้นการสลับอัตโนมัติจะเงียบและไม่ทำงาน `init --codex` จะพิมพ์คำเตือนนี้ให้

## สะพานเชื่อม Slack: xx serve

`tokenmaxxing serve` รันเดมอน Slack ในเครื่องผ่าน Socket Mode โดยไม่ต้องใช้ URL สาธารณะ การตั้งค่า:

```sh
tokenmaxxing serve setup                    # พิมพ์ manifest ของแอป และถาม token ทั้งสองตัว
tokenmaxxing serve link <channel-id> <repo> # ผูกแชนเนลเข้ากับ checkout ของ repo
tokenmaxxing serve                          # รันเดมอน
```

กล่าวถึง (mention) บอทในแชนเนลที่ลิงก์ไว้ แล้วมันจะเปิดเซสชัน Claude Code สำหรับเธรดนั้นใน checkout ของ repo ที่ลิงก์ไว้ ทุกข้อความในเธรดจะรัน Agent SDK `query()` หนึ่งครั้งพร้อม `resume` ไม่ใช่ query แบบสตรีมมิงที่คงอยู่ถาวร ดังนั้น `ensureBestAccount()` จึงประเมินพูลใหม่ในทุกๆ เทิร์น และเดมอนสามารถรีสตาร์ทได้โดยไม่สูญเสียเธรด (บันทึกเธรดมีความคงทน เดมอนจะสมัครสมาชิก (re-subscribe) ให้ใหม่เมื่อเริ่มทำงาน)

พฤติกรรมที่น่าสังเกต:

- **สตรีมมิง**: การตอบกลับสตรีมเข้าสู่ Slack แบบเนทีฟ พร้อมการ์ดงานสำหรับการคิดและการรันเครื่องมือ โค้ดในบล็อกแบบ fenced เรนเดอร์พร้อมการไฮไลต์ การ์ด "Turn" ปิดท้ายพร้อมต้นทุนและระยะเวลา และมีการเปิดข้อความ Slack ใหม่ทุกครั้งที่การรันเครื่องมือขัดจังหวะข้อความที่สตรีมอยู่ ดังนั้นหนึ่งเทิร์นจึงอ่านได้เป็นข้อความแยกกันรอบๆ การรันเครื่องมือ การเรียก TodoWrite จะอัปเดตการ์ดเช็กลิสต์ที่เสถียรหนึ่งใบ ณ ที่เดิม
- **สิทธิ์**: `permissionMode` ต่อลิงก์มีค่าเริ่มต้นเป็น `acceptEdits` ส่วน `--yolo` (alias `--dangerous`) จะเลือกให้ลิงก์ใช้ `bypassPermissions` ไดอะล็อกแบบโต้ตอบไม่ได้รับอนุญาตในเทิร์นที่ถ่ายทอด (relayed) เพราะไม่มีใครตอบมันผ่าน Slack ได้ ดังนั้นโมเดลจะถามเป็นร้อยแก้วและการตอบกลับในเธรดของคุณคือเทิร์นถัดไป สกิลปลั๊กอินที่มาพร้อมกันจะสอนให้มันแท็กผู้ร้องขอและจบเทิร์นเมื่อต้องการการตัดสินใจ
- **คำสั่งสแลช**: ข้อความในเธรดที่ข้อความหลังตัดคำนำหน้าเริ่มด้วย `/` จะรันเป็นคำสั่งสแลชของ claude ตัวเขียนข้อความ (composer) ของ Slack จะกลืนข้อความที่ขึ้นต้นด้วย `/` ดังนั้นให้ใช้รูปแบบกล่าวถึงก่อน (`@bot /usage`) หรือเว้นวรรคนำหน้า
- **การปิดอย่างนุ่มนวล**: SIGTERM/SIGINT จะระบาย (drain) เทิร์นใหม่จะถูกทิ้งอย่างมีเสียง เทิร์นที่กำลังทำงานได้เวลาสูงสุด 5 นาที และโปรเซสลูก claude รันแบบ detached ในกลุ่มโปรเซสของตัวเอง เพื่อให้การกด Ctrl-C ในเทอร์มินัลไม่สามารถฆ่ามันได้ก่อนที่การระบายจะรักษาเทิร์นไว้
- **การเคลียร์เธรด**: เมื่อคุณบอกว่างานเสร็จแล้ว โมเดลจะเรียกเครื่องมือ `finish_thread` ภายในโปรเซส หลังจากเทิร์นจบสมบูรณ์ เดมอนจะทิ้งบันทึกเธรด ยกเลิกการสมัครสมาชิก และโพสต์คำยืนยันหนึ่งครั้ง การกล่าวถึงใหม่จะเริ่มเซสชันใหม่
- **สุขอนามัยของข้อผิดพลาด**: ข้อผิดพลาดในเทิร์นจะโพสต์ข้อความที่ตัดให้เหลือเฉพาะข้อความ ไม่มีวันโพสต์เนื้อหาข้อผิดพลาดแบบดิบ

## พื้นผิว Agent SDK

จุดเข้าเชิงโปรแกรมของแพ็กเกจ (`exports["."]` ชี้ไปที่ `src/sdk.ts`) จับคู่ tokenmaxxing กับ Claude Agent SDK สำหรับ agent ที่คุณสร้างขึ้นโดยใช้บัญชีในพูลของคุณเอง แอปของคุณต้องรันบน Bun (tokenmaxxing ส่งมาเป็นซอร์สโค้ด TypeScript และใช้ `bun:ffi`)

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK จะ spawn โปรเซสย่อย claude ต่อ `query()` หนึ่งครั้ง และอ่าน credential เพียงครั้งเดียวตอน spawn ไม่มี statusline ไม่มี hot-swap ระหว่าง query ดังนั้นการผสานรวมจึงขับเคลื่อนด้วยขอบเขต:

- `ensureBestAccount()` คือการตัดสินใจแบบเดียวกับที่ฮุกและตัวจับเวลาของ CLI รัน (แถบ, pace pressure, ช่วงพัก ล้วนเป็นโค้ดที่ใช้ร่วมกัน) ไม่เคยทำแบบคาดการณ์ล่วงหน้า เพราะเซสชัน SDK ไม่มีทางถูกหยุดเพื่อนับถอยหลังเมื่อหมดโควตาได้
- `pooledOptions()` ปักหมุด `pathToClaudeCodeExecutable` ไปที่ไบนารี claude ตัวจริง (ไม่ใช่ตัวห่อ supervisor) และจัดหา `env` แทนที่แบบเต็มโดยล้างการ override credential จากสภาพแวดล้อมทุกตัว มันจะล้มเหลวทันทีหากมีการตั้ง `CLAUDE_CONFIG_DIR` หรือ `CLAUDE_SECURESTORAGE_CONFIG_DIR` ในสภาพแวดล้อมของแอปคุณ เพราะบน Linux การสลับจะเขียน credential สดไปยังที่ที่ตัวแปรเหล่านั้นชี้ ในขณะที่โปรเซสย่อยที่ถูกล้างอ่านจากที่เก็บเริ่มต้น เกิดความไม่ตรงกันของบัญชีที่ผิดแบบเงียบๆ
- `stopHookCheck` รันการตัดสินใจซ้ำที่ขอบเขตเทิร์น การสลับที่มันทำจะมีผลในการ spawn ครั้งถัดไป มันดักจับข้อผิดพลาดของตัวเอง (โดยบันทึกไปยัง stderr และ log) แทนที่จะโยนต่อ เพราะข้อยกเว้นของฮุกที่ไม่ได้จัดการอาจขัดจังหวะ agent และการยกเลิกเทิร์นเพราะการตรวจสอบการสลับที่เสียมีต้นทุนสูงกว่าการอยู่กับบัญชีปัจจุบันต่อไป

`sdk.ts` ไม่ import อะไรจาก Agent SDK เองเลย ค่าของมันกระจายเข้าไปในตัวเลือกของ SDK เชิงโครงสร้าง

## การ build และการเผยแพร่

แพ็กเกจ npm เผยแพร่ซอร์ส TypeScript ไม่ใช่ไฟล์ที่ build แล้ว: bin `tokenmaxxing` ชี้ตรงไปที่ `src/main.ts` ด้วย Bun shebang และ Bun 1.2.6 หรือใหม่กว่าจะรันมันได้เลย นั่นคือเหตุผลที่ Bun เป็นข้อกำหนดที่ต้องมี ไม่มีไบนารีที่คอมไพล์แล้วโดยตั้งใจ: รุ่นแรกๆ เคยเผยแพร่ไบนารี macOS ขนาด 61 MB ไฟล์เดียวไปยังทุกแพลตฟอร์ม และล้มเหลวบน Linux ด้วย `exec format error` อีกทั้งแพ็กเกจที่คอมไพล์แยกตามแพลตฟอร์มก็ต้องมี release pipeline ของตัวเองแต่ละอัน การรันซอร์สด้วย Bun จึงกลายเป็นโมเดลการเผยแพร่

แมป `exports` ของแพ็กเกจเปิดเผย `src/sdk.ts` เป็นจุดเข้าเชิงโปรแกรมตามที่อธิบายไว้ข้างต้น รุ่นต่างๆ ถูกแท็กเป็น `v<version>` บน GitHub; CI เผยแพร่ไปยัง npm ผ่าน trusted publishing (OIDC พร้อม provenance) และด่านตรวจก่อนเผยแพร่จะรัน typecheck และชุดทดสอบทั้งหมดก่อน

## การใช้งานส่วนตัวและข้อกำหนดในการให้บริการ [#personal-use-and-terms-of-service]

tokenmaxxing รวมบัญชีที่คุณเป็นเจ้าของ ในเซสชันและ agent ที่คุณรันเอง ถ้อยคำนี้เป็นไปโดยเจตนา: Anthropic ไม่อนุญาตให้ผลิตภัณฑ์ของบุคคลที่สามเสนอการล็อกอิน claude.ai หรือลิมิตอัตราของ claude.ai และนั่นรวมถึง agent ที่สร้างบน Agent SDK ด้วย อย่าส่งมอบพื้นผิว SDK แบบพูล หรือสิ่งใดที่สร้างขึ้นบนมัน ให้แก่บุคคลที่สาม tokenmaxxing ยังคงอยู่บนเส้นทาง `/usage` ที่ผ่าน CLI สำหรับข้อมูลโควตาโดยเจตนา แทนที่จะสร้าง OAuth ขึ้นใหม่หรือทำพร็อกซีให้ทราฟฟิก API มันไม่ใช่พร็อกซี และ OAuth endpoint เดียวที่มันแตะคือ refresh grant มาตรฐานที่ใช้ระหว่างการสลับ และการตรวจสอบตัวตนแบบอ่านอย่างเดียว (roles endpoint) ที่ยืนยันว่า token เป็นของบัญชีใดจริงๆ

## ข้อจำกัดที่บอกตามตรง

- **เทิร์นเย็นหนึ่งครั้ง** แคชพรอมต์อยู่ในขอบเขตขององค์กร ดังนั้นเทิร์นแรกบนบัญชีใหม่จะอัปโหลดบริบทซ้ำหนึ่งครั้ง
- **สะดุดเมื่อหยุดชั่วคราวตอนหมดโควตา** เฉพาะพูลที่หมดเกลี้ยงทั้งพูลเท่านั้นที่จะหยุดเซสชันเพื่อนับถอยหลัง สิ่งใดที่พิมพ์ในเสี้ยววินาทีนั้นจะสูญหาย
- **ความหน่วงในการนำมาใช้** บน macOS เทิร์นแรกภายในประมาณ 30 วินาทีของการสลับยังอาจนับการใช้กับบัญชีเก่าได้ พื้นที่เหลือของแถบจะรองรับมันไว้
- **รัศมีผลกระทบที่ใช้ร่วมกัน** ทุกเซสชันในโปรไฟล์เริ่มต้นใช้ credential สดตัวเดียวกัน ดังนั้นการสลับจะย้ายทั้งหมดไปพร้อมกัน (แต่ละเซสชันนำมาใช้ ณ ที่เดิม)
- **credential แบบข้อความธรรมดาบน Linux** Claude Code เองเก็บ credential บน Linux เป็นไฟล์ข้อความธรรมดาสิทธิ์ 0600 สำเนาที่ park ไว้ของ tokenmaxxing ก็ใช้โมเดลเดียวกัน

## การแก้ปัญหาและคำถามที่พบบ่อย

**`claude` ดูเหมือนจะไม่ได้ถูกควบคุมโดย supervisor**
รัน `tokenmaxxing doctor` shim ต้องชนะการระบุ PATH ตรวจสอบว่าบรรทัด `# tokenmaxxing PATH` ในไฟล์ rc ของเชลล์คุณชี้ไปที่ไดเรกทอรี bin ปัจจุบันและอยู่ก่อน claude ตัวจริง `doctor` ยังเตือนเกี่ยวกับ `alias claude=...` หรือฟังก์ชันเชลล์ `claude()` ที่บดบังตัวห่อ และเกี่ยวกับ alias ที่เปิดไบนารี claude ด้วยพาธสัมบูรณ์ (ซึ่งเลี่ยง supervisor ไปทั้งหมด)

**การสลับอัตโนมัติไม่เคยทำงานบน Codex**
Codex จะข้ามฮุกที่ยังไม่ได้รับแจ้งให้เชื่อถือ เปิด codex รัน `/hooks` และเชื่อถือ Stop hook ของ tokenmaxxing ความเชื่อถือถูกบันทึกไว้กับแฮชของฮุก ดังนั้นต้องให้สิทธิ์ใหม่หากมีการแก้ไขฮุก

**บัญชีแสดง `✗` สีแดงใน statusline**
refresh token ของมันตายแล้ว (ถูกเพิกถอนหรือถูกหมุนเวียนออกไปจากใต้ไฟล์สำรอง) รัน `tokenmaxxing auth <sel>` เพื่อยืนยันตัวตนใหม่ ณ ที่เดิม คำสั่งจะบอกคุณว่าต้องเข้าสู่ระบบด้วยอีเมลใด และปฏิเสธการเข้าสู่ระบบที่ไปลงคนละบัญชี

**ทำไมมันไม่สลับไปยังบัญชีที่มีโควตาเหลือมากที่สุด?**
เพราะนั่นไม่ใช่บัญชีที่เสี่ยงต่อการถูกริบโควตามากที่สุด เป้าหมายคือบัญชีที่ล้าหลังจังหวะรายสัปดาห์ของตัวเองมากที่สุด นั่นคือเปอร์เซ็นต์ที่เหลือหารด้วยเวลาจนถึงการรีเซ็ตรายสัปดาห์ของมัน เมื่อมีปริมาณเหลือเท่ากันก็จะลดเหลือการเลือกวันหมดอายุที่เร็วที่สุดก่อน และเมื่อวันหมดอายุเท่ากันก็เลือกที่เหลือมากที่สุดก่อน

**เพิ่งสลับไปแต่ statusline ยังแสดงบัญชีเก่า**
เป็นเรื่องที่คาดไว้ได้นานถึงประมาณ 30 วินาทีบน macOS เซสชันที่กำลังทำงานจะนำ credential ที่สลับมาใช้ในการรีเฟรชแคช credential ครั้งถัดไป การ tee การใช้งานจะถูกระงับเป็นเวลา 45 วินาทีหลังการสลับด้วยเหตุผลนี้เอง

**`status --force` มีค่าใช้จ่ายอะไรไหม?**
ใช่ โดยเจตนา: มันส่งคำขอ haiku ที่นับการใช้แบบน้อยที่สุดหนึ่งครั้งต่อบัญชี เพื่อให้หน้าต่างเซสชัน 5 ชั่วโมงทุกอันเริ่มนับตอนนั้นแทนที่จะหลับอยู่เฉยๆ แล้วจึงเก็บตัวอย่างใหม่ `status` ธรรมดาและ `watch` ไม่เคย ping การอ่าน `/usage` นั้นฟรี โปรดทราบว่าฟีดการใช้งานของเซิร์ฟเวอร์อาจล่าช้ากว่าหน้าต่างที่เพิ่งเปิดเป็นวินาทีถึงเป็นนาที ดังนั้นการ probe ทันทีหลัง ping อาจยังแสดงสถานะก่อน ping อยู่ `status` จะแสดงหมายเหตุแทนที่จะแกล้งทำเป็นว่า ping ล้มเหลว

**การ probe `/usage` ไม่คืนค่าอะไรมาสำหรับบัญชีที่ใช้งานอยู่**
นั่นเป็นพฤติกรรมที่ทราบกันของ claude: เมื่อการดึงข้อมูลการใช้งานภายในของมันล้มเหลวหรือถูกจำกัดอัตรา `/usage` จะพิมพ์เฉพาะสถิติเซสชันในเครื่องโดยไม่มีบรรทัดเปอร์เซ็นต์ tokenmaxxing เก็บตัวอย่างบัญชีที่ใช้งานอยู่จากการ push ของ statusline และ probe เฉพาะบัญชีที่ park ไว้เท่านั้น เพื่อหลีกเลี่ยงเรื่องนี้โดยเฉพาะ

**เซสชัน claude แบบเบื้องหลัง**
เดมอนเบื้องหลังของ Claude จะ spawn ไบนารีที่มีเวอร์ชันตัวจริงด้วยพาธสัมบูรณ์ โดยเลี่ยง shim ของ PATH ดังนั้นเซสชันเบื้องหลังจึงไม่ถูกควบคุมโดย supervisor ฮุกยังคงทำงานผ่าน `settings.json` และการนำ credential มาใช้บวกกับตัวจับเวลาเป็นระยะครอบคลุมการสลับได้ แต่ไม่มี respawn ที่ขับเคลื่อนด้วย marker สำหรับพวกมัน

**ครั้งหนึ่งมีบางอย่าง spawn โปรเซสจำนวนมาก ยังเป็นไปได้อยู่ไหม?**
supervisor มีการป้องกันการเรียกซ้ำแบบเป็นชั้นๆ ต่อความล้มเหลวในอดีตนั้นโดยเฉพาะ (ตัวห่อที่เก่าค้างถูกปักหมุดเป็น claude "ตัวจริง") ได้แก่ ตัวเฝ้าระดับความลึก (depth sentinel) ในสภาพแวดล้อมที่ยกเลิกเมื่อถึง 5 ระดับ ตัวจำกัดอัตราการ spawn บนดิสก์ การตรวจสอบตัวตนด้วย realpath ที่ปฏิเสธตัวเลือกใดที่ระบุกลับไปยังไดเรกทอรี bin ของ tokenmaxxing เอง และการล้มเหลวแบบเด็ดขาด (ไม่มีวันสแกน PATH แบบเงียบๆ) เมื่อพาธ claude ที่ตั้งค่าไว้ไม่มีอยู่อีกต่อไป `init` และ `doctor` จะยืนยันว่าตัวเลือกเป็น claude จริงๆ ด้วยการรัน `--version` ก่อนปักหมุดมัน

**การถอนการติดตั้ง**
`tokenmaxxing uninstall` ลบ shim ของ supervisor รายการการตั้งค่า และตัวจับเวลาเป็นระยะ และคงบัญชีกับ credential ที่ park ไว้ของคุณไว้ครบถ้วน มันจะลบเฉพาะรายการ statusline ที่มันรู้ว่าเป็นของตัวเองเท่านั้น
