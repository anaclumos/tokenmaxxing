---
title: Credential storage and safety
description: One credential store per account, who writes it, and the rules onboarding enforces
---

All state lives in `~/.config/tokenmaxxing/`. Each pooled Claude account owns one Claude Code credential store, `stores/<uuid8>/`, named from the first 8 characters of the account id. A session runs on an account because its `CLAUDE_SECURESTORAGE_CONFIG_DIR` points at that store; Claude Code resolves the credential from that variable first, and tokenmaxxing mirrors the resolution exactly. Credential I/O goes through a single platform-selected store facade; call sites never branch on platform.

**macOS**: Claude Code keeps the credential of a store in the login keychain as a generic-password item named `Claude Code-credentials-<sha256(store path)[0:8]>` (the hash is over the NFC-normalized path, so the path must be byte-stable). Nothing is plaintext on disk. Reads use `security find-generic-password -w` (the secret only ever appears on stdout); the one write tokenmaxxing makes pipes an `add-generic-password` line into `security -i` over stdin so the secret never appears in any process's argv. The interactive mode has a roughly 4 KB line buffer, so oversized blobs fall back to an argv write; the onboarding write stores only the minimal OAuth object, so it never is.

**Linux**: Claude Code stores credentials as a 0600 plaintext file, and a store is `stores/<uuid8>/.credentials.json`, 0600 in a 0700 directory. Atomic here means write-to-temp, fsync, then rename: a concurrent reader always sees a whole old or whole new file, never a partial one.

The rules:

- **One store per account, never per session.** A refresh rotation revokes the previous access token of that grant, so two stores holding one grant break each other: the sessions on the other copy get 401, force-refresh a superseded refresh token, receive `invalid_grant`, and Claude Code dead-clears their blob. Sessions on the same account share that account's store and coordinate refreshes through Claude Code's own refresh lock, which is rooted at the store.
- **Onboarding is the only tokenmaxxing write.** `init`, `add`, and `auth` log an account in inside a throwaway `CLAUDE_CONFIG_DIR` and harvest the result once into the account's store; the throwaway home and its credential item are deleted afterwards. After that, Claude Code's refresh is the only writer: no harvest, no park, no install, and no refresh grant from tokenmaxxing. The login you already had before `init` keeps its own grant in Claude Code's default store, for sessions started outside the supervisor.
- **Identity by true owner.** Before a harvested login lands in a store, its access token is resolved through the OAuth profile endpoint (`fetchTokenIdentity`, matched on the account UUID), never by the organization, because every seat of a Team plan shares one organization, and never by a stored label. A login whose token belongs to another account than the one its identity file names changes nothing, and `auth` refuses a login that lands on a different account than the one being repaired. `doctor` runs the same check for every store.
- **Dead grants degrade cleanly.** A store whose credential Claude Code cleared after a failed refresh (empty access and refresh tokens) is recognized as dead without spending a request; it flags the account as needs-reauth and the decision tries the next candidate. `tokenmaxxing auth` fixes a flagged account in place.
- **No token logging.** Tokens never appear in logs, errors, or output. Error bodies from the identity endpoint are never surfaced raw; only an allowlisted set of fields survives.
- **Probe hygiene.** Every spawned `claude` probe scrubs the environment variables claude honors before its store lookup (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, and so on) and then sets the store it means to read, so a probe can never be attributed to the wrong account. The onboarding login scrubs the same list, so `add` run inside a supervised session does not land the new login in that session's store.
