---
title: Credential storage and safety
description: One credential store per account, who writes it, and the rules onboarding enforces
---

All state lives in `~/.config/tokenmaxxing/`. Each pooled Claude account owns one Claude Code credential store, `stores/<uuid8>/`, named from the first 8 characters of the account id. A session runs on an account because its `CLAUDE_SECURESTORAGE_CONFIG_DIR` points at that store; Claude Code resolves the credential from that variable first. tokenmaxxing never derives a store from ambient variables: it names the directory itself (the account's store, or a throwaway onboarding home) and computes the same keychain item name Claude Code does. Credential I/O goes through a single platform-selected store facade; call sites never branch on platform.

**macOS**: Claude Code keeps the credential of a store in the login keychain as a generic-password item named `Claude Code-credentials-<sha256(store path)[0:8]>` (the hash is over the NFC-normalized path, so the path must be byte-stable), under the account name `$USER` (`TOKENMAXXING_KEYCHAIN_ACCOUNT` overrides it). The Claude store keeps nothing plaintext on disk. Reads use `security find-generic-password -w` (the secret only ever appears on stdout); a read that fails for any reason other than a missing item, a locked keychain or a denied ACL, throws, and the account is skipped for that evaluation rather than read as empty. The one write tokenmaxxing makes pipes an `add-generic-password` line into `security -i` over stdin so the secret never appears in any process's argv. The interactive mode has a roughly 4 KB line buffer, so an oversized blob falls back to an argv write; the onboarding write stores the `claudeAiOauth` object alone, which stays well under that size.

**Linux**: Claude Code stores credentials as a 0600 plaintext file, and a store is `stores/<uuid8>/.credentials.json`, 0600 in a 0700 directory. Atomic here means write-to-temp, fsync, then rename: a concurrent reader always sees a whole old or whole new file, never a partial one.

The rules:

- **One store per account, never per session.** A refresh rotation revokes the previous access token of that grant, so two stores holding one grant break each other: the sessions on the other copy get 401, force-refresh a superseded refresh token, receive `invalid_grant`, and Claude Code dead-clears their blob. Sessions on the same account share that account's store and coordinate refreshes through Claude Code's own refresh lock, which is rooted at the store.
- **Onboarding is the only tokenmaxxing write.** `init`, `add`, and `auth` log an account in inside a throwaway `CLAUDE_CONFIG_DIR` and harvest the result once into the account's store; the throwaway home and its credential item are deleted afterwards. After that, Claude Code's refresh is the only writer: no harvest, no park, no install, and no refresh grant from tokenmaxxing. The login you already had before `init` keeps its own grant in Claude Code's default store, for sessions started outside the supervisor. `rm` is the only deletion: it removes the store, its keychain item on macOS, the account's tee, and its stored setup token.
- **Identity by true owner.** Before a harvested login lands in a store, its access token is resolved through the OAuth profile endpoint (`fetchTokenIdentity`, matched on the account UUID), never by the organization, because every seat of a Team plan shares one organization, and never by a stored label. A login whose token belongs to another account than the one its identity file names changes nothing, and `auth` refuses a login that lands on a different account than the one being repaired. `doctor` runs the same check for every store whose access token is not about to expire; a store past that is reported as unverifiable, because tokenmaxxing holds no refresh grant.
- **Dead grants degrade cleanly.** A store whose credential Claude Code cleared after a failed refresh (an empty access token or an empty refresh token) is recognized as dead without spending a request; it flags the account as needs-reauth and the decision tries the next candidate. Five consecutive failed store reads on the check tick flag the account the same way. `tokenmaxxing auth` fixes a flagged account in place.
- **No token logging.** Tokens never appear in the log, in errors, or in command output, with one deliberate exception: `setup-token` prints the minted setup tokens as the Cursor secret value (see [Cursor Cloud](/cursor-cloud)). Error bodies from the identity endpoint are never surfaced raw; only an allowlisted set of fields survives.
- **Spawn hygiene.** Every spawned `claude` child that must not re-enter the wrapper scrubs the environment variables claude honors before its store lookup (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, and so on) and then sets the store it means to read. The onboarding login scrubs the same list, so `add` run inside a supervised session does not land the new login in that session's store. The direct usage read is the one place a stored access token leaves the store without a `claude` child: every sampler (the check tick, `status`, the seat's in-decision read, and onboarding) sends it to the no-spend usage endpoint over HTTPS. tokenmaxxing holds no refresh grant, so an expired stored access token stays unmeasured until a session on that store refreshes it.
- **Other pools are plaintext files.** The Codex, grok, and opencode-go stores are 0600 `auth.json` files on both platforms, because those CLIs keep plaintext files themselves, and `setup-tokens.json` holds minted setup tokens the same way.
