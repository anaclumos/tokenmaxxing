---
title: 설정
description: "config.json 스키마, 임계값, 정책 옵션"
---

설정은 `~/.config/tokenmaxxing/config.json`에 있는 JSON입니다. 모든 필드는 선택 사항이며 기본값이 필드별로 적용됩니다.

```json
{
  "thresholds": { "session": [90], "weekly": 98 },
  "hardThresholds": { "session": 100, "weekly": 100 },
  "claudeBin": "/path/to/real/claude",
  "codexBin": "/path/to/real/codex",
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 80,
    "greedySwapMargin": 0.15,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000,
    "checkIntervalMs": 60000
  }
}
```

- `thresholds.session`: 5시간 사다리, 오름차순으로 늘어놓은 선별 단계 목록입니다. 평가할 때마다 활성 단계 하나가 정해지는데, 풀의 계정 중 하나라도 아직 넘지 않은 가장 낮은 단계이며 이 단계가 트리거이자 후보 선별 기준입니다. Codex는 맨 위 단계만 읽습니다. [전환 결정 방식](/ko/switching)을 참고하세요.
- `thresholds.weekly`: 주간 선별 기준선. 7일 합산과 모든 모델별 주간 상한을 함께 다룹니다.
- `hardThresholds.session` / `hardThresholds.weekly`: 벽 기준선(기본 100, 각 계정의 실제 서버 한도). `hardThresholds.session`은 세션 사다리의 맨 위 단계 이상이어야 합니다. 모든 계정이 선별 기준선을 넘어서면 자동 Claude 결정은 park하기 전에 각 계정을 벽까지 쥐어짜냅니다. [벽](/ko/switching)을 참고하세요. 맨 위 단계와 주간 기준선에 각각 같게 설정하면 비활성화됩니다. Codex는 이 설정을 무시합니다.
- `claudeBin` / `codexBin`: supervisor가 실행하는 실제 바이너리를 고정합니다(`init` / `init --codex`가 기록합니다. 재귀 방지 진단이 `claudeBin`을 여기서 고치라고 안내하는 경우는 이 값이 더 이상 실제 Claude 바이너리를 가리키지 않을 때입니다).
- `policy.projectionMargin`: 유효 기준선을 만들기 위해 모든 세션 단계와 주간 기준선, 그리고 벽 기준선에서 빼는 값.
- `policy.greedySessionFloor`: 그리디 수렴이 관여하는 세션 사용 백분율.
- `policy.greedySwapMargin`: 그리디 경로에서 현재 계정에 적용하는 이력 현상으로, 0에서 1 사이의 비율입니다(기본 0.15). 보관된 계정의 진행 압력이 현재 계정의 진행 압력을 이 비율보다 더 크게 앞지르지 않는 한 현재 계정이 자기 자리를 지키므로, 거의 동점인 계정들이 자리를 주고받으며 조직별 프롬프트 캐시를 날려 버리는 일이 없어집니다. 0으로 설정하면 항상 가장 나은 계정을 택하던 예전 동작이 됩니다. 이 값은 넘어선 기준선이나 벽을 결코 완화하지 않습니다. 모든 계정이 기준선 아래에 있을 때의 수평 교체에만 적용됩니다. 수동 `tokenmaxxing switch`는 이 값을 무시하고 항상 가장 나은 계정으로 수렴합니다.
- `policy.switchModels`: 모델별 주간 상한이 전환을 게이트하는 모델 계열(항목은 로드 시 소문자로 변환됩니다).
- `policy.usagePollTtlMs`: `/usage` 모델별 폴링이 최신 상태로 유지되는 시간.
- `policy.maxWaitMs`: 풀 소진 시 자동 대기의 상한.
- `policy.checkIntervalMs`: 주기적 점검의 틱(기본 60000, 최소 10000입니다. launchd가 기본적으로 10초에 한 번보다 자주 작업을 생성하지 않기 때문입니다). `init`은 이 값을 초 단위로 올림해 타이머의 간격으로 기록하고(Linux에서는 systemd `AccuracySec`이 그 12분의 1이며 최소 1초입니다), 여유 구간은 모두 이 값의 배수입니다. 기준선에 가까우면 한 틱, 여유가 넉넉하면 최대 다섯 틱입니다([점검 주기](/ko/switching) 참고). 소진 대기와 교체 후 쿨다운은 대신 각자의 마감 시각까지 잡니다. 일정은 다음 점검에서 새 값을 읽지만, 설치된 타이머는 `tokenmaxxing init`을 다시 실행할 때까지 예전 틱을 유지하고 예정 시각의 여유는 설정된 틱의 절반이므로, 바뀐 틱은 그렇게 다시 실행한 뒤에야 온전히 반영됩니다. Nix가 관리하는 타이머를 쓴다면 `checkTimer.intervalSeconds`를 같은 값으로 설정하세요. 이 옵션에도 동일한 10초 하한이 있습니다.

`tokenmaxxing config`는 출처와 함께 유효 설정을 보여줍니다. `config set`/`unset`은 점 표기 키를 편집합니다. `config tidy`는 알 수 없는 키를 정리합니다.
