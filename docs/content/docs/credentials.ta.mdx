description: "ஒவ்வொரு தளத்திலும் சான்றுதல்கள் எங்கே வாழ்கின்றன மற்றும் ஒவ்வொரு மாற்றமும் அமல்படுத்தும் விதிகள்"
---

அனைத்து நிலையும் `~/.config/tokenmaxxing/` இல் வாழ்கிறது. சான்றுதல் I/O ஒரு ஒற்றை தளம்-தேர்ந்தெடுக்கப்பட்ட சேமிப்பு முகப்பு வழியாகச் செல்கிறது; அழைப்பு தளங்கள் ஒருபோதும் தளத்தில் கிளைபிரியாது.

**macOS**: சான்றுதல்கள் உள்நுழைவு keychain இல் generic-password உருப்படிகளாக வாழ்கின்றன, Claude Code தானே அவற்றை வைத்திருக்கும் இடத்துடன் பொருந்துகிறது. நேரடி உருப்படியே claude படிக்கிறது; ஒவ்வொரு ஒன்றிணைந்த கணக்கின் காப்புப்பிரதியும் அதன் சொந்த `tokenmaxxing-cred-<uuid8>` keychain உருப்படியாக நிறுத்தப்படுகிறது. வட்டில் எதுவும் plaintext அல்ல. வாசிப்புகள் `security find-generic-password -w` ஐப் பயன்படுத்துகின்றன (இரகசியம் எப்போதும் stdout இல் மட்டுமே தோன்றுகிறது); எழுத்துக்கள் ஒரு `add-generic-password` வரியை stdin மீது `security -i` இல் pipe செய்கின்றன, எனவே இரகசியம் எந்த செயல்முறையின் argv இலும் தோன்றுவதில்லை. தொடர்பாடல் முறையில் தோராயமாக ஒரு 4 KB வரி இடையகம் உள்ளது, எனவே அளவுக்கு அதிகமான blobs ஒரு argv எழுத்திற்கு மீளுகின்றன - நிறுத்தப்பட்ட உருப்படிகள் குறைந்தபட்ச OAuth பொருளை மட்டுமே சேமிப்பதற்கான ஒரு காரணம்.

**Linux**: Claude Code சான்றுதல்களை ஒரு 0600 plaintext கோப்பாக சேமிக்கிறது, மேலும் tokenmaxxing அதே மாதிரியைப் பின்பற்றுகிறது: நேரடி கோப்பே claude இன் சொந்த `.credentials.json`, மேலும் நிறுத்தப்பட்ட காப்புப்பிரதிகள் ஒரு 0700 அடைவில் `~/.config/tokenmaxxing/creds/` க்குக் கீழ் அணு 0600 கோப்புகள். இங்கே அணு என்றால் தற்காலிகத்தில்-எழுது, fsync, பிறகு மறுபெயரிடு: ஒரு ஒரே நேர வாசகர் எப்போதும் ஒரு முழு பழைய அல்லது முழு புதிய கோப்பைப் பார்க்கிறார், ஒருபோதும் ஒரு பகுதியை அல்ல.

மாற்றம் அமல்படுத்தும் பாதுகாப்பு விதிகள்:

- **உண்மையான உரிமையாளரால் அறுவடை.** ஒரு மாற்றத்திற்கு முன், நேரடி சான்றுதலின் உண்மையான உரிமையாளர், டோக்கன் எந்த கணக்கிற்குச் சொந்தமானது என்று API ஐக் கேட்பதன் மூலம் தீர்க்கப்படுகிறது (`fetchTokenIdentity` OAuth profile endpoint க்கு எதிராக, கணக்கு UUID இல் பொருத்தப்பட்டது) - நிறுவனத்தால் ஒருபோதும் அல்ல, ஏனெனில் ஒரு Team திட்டத்தின் ஒவ்வொரு இருக்கையும் ஒரே நிறுவனத்தைப் பகிர்ந்து கொள்கிறது, மேலும் சேமிக்கப்பட்ட செயலில் உள்ள லேபிளை நம்புவதன் மூலம் ஒருபோதும் அல்ல, அது நகரக்கூடும். ஒரு நகர்ந்த லேபிள் ஒருமுறை ஒரு கணக்கின் அறுவடை மற்றொரு கணக்கின் ஒரே காப்புப்பிரதியை மேலெழுதச் செய்தது. நேரடி சான்றுதல் தொகுப்பிற்கு வெளியே உள்ள ஒரு கணக்கிற்குச் சொந்தமானதாக இருந்தால், மாற்றம் அதை மேலெழுதுவதற்குப் பதிலாக நேரடியாக மறுக்கிறது.
- **ஒரு முக்கியப் பகுதி.** அறுவடை, புதிய சான்றுதலின் நிறுவல், அதன் சுழற்றப்பட்ட டோக்கனின் காப்புப்பிரதி, `~/.claude.json` கணக்கு மாற்றம், மற்றும் செயலில் உள்ள லேபிள் உறுதிப்படுத்தல் ஆகியவை அனைத்தும் அதே பூட்டப்பட்ட பகுதிக்குள் நடக்கின்றன.
- **claude இன் சொந்த refresh உடன் ஒன்றிணைந்த பூட்டு.** ஒரு காலாவதிக்கு அருகிலுள்ள அமர்வு எந்த நேரத்திலும் அதன் சொந்த டோக்கனை சுழற்றக்கூடும், எனவே சான்றுதல் எழுத்துக்களும் Claude Code இன் refresh பூட்டை எடுக்கின்றன (சிறந்த-முயற்சி, ஒரு பழைய-பூட்டு மீட்பு மற்றும் ஒரு வரம்புக்குட்பட்ட நேரவரம்புடன்).
- **இறந்த மானியங்கள் சுத்தமாகச் சீரழிகின்றன.** `invalid_grant` உடன் திரும்பும் ஒரு refresh அந்த கணக்கை மீள்-அங்கீகாரம் தேவை என்று கொடியிட்டு, பிழை பரவுவதற்கு முன்பு கொடியை நிலைநிறுத்துகிறது, எனவே மறுமுயற்சி வளையங்கள் வேட்பாளர் தொகுப்பைச் சுருக்கி முடிவடைகின்றன. தோல்வியடைந்த refresh க்குப் பிறகு Claude Code தானாகவே அழித்த ஒரு சான்றுதல் (வெற்று அணுகல் மற்றும் refresh டோக்கன்கள்) ஒரு கோரிக்கையையும் செலவிடாமல் இறந்ததாக அடையாளம் காணப்படுகிறது. நிறுத்தப்பட்ட ஒரு refresh டோக்கன் செலவிடப்படுவதற்கு முன், அதன் உரிமையாளர் profile endpoint வழியாக தீர்க்கப்படுகிறது; வேறொரு கணக்கிற்குத் தீர்க்கப்படும் ஒரு நிறுத்தப்பட்ட சான்றுதல், refresh செய்யப்படுவதற்குப் பதிலாக கொடியிடப்படுகிறது, ஏனெனில் மற்றொரு கணக்கின் நேரடி மானியத்தின் நகலை refresh செய்வது அந்தக் கணக்கின் அமர்வுகளை ரத்து செய்கிறது. வேறு எந்த token endpoint நிராகரிப்பும் (`invalid_grant` அல்லாத ஒரு HTTP 4xx) அந்த வேட்பாளரை மதிப்பீட்டின் மீதமுள்ள பகுதிக்குத் தவிர்த்து, எதையும் கொடியிடாது. `tokenmaxxing auth` ஒரு கொடியிடப்பட்ட கணக்கை இடத்திலேயே சரிசெய்கிறது, மேலும் சரிசெய்யப்படும் கணக்கிலிருந்து வேறுபட்ட கணக்கில் இறங்கும் ஒரு உள்நுழைவை அது மறுக்கிறது.
- **டோக்கன் பதிவு இல்லை.** டோக்கன்கள் ஒருபோதும் பதிவுகள், பிழைகள், அல்லது வெளியீட்டில் தோன்றுவதில்லை. டோக்கன் மற்றும் பயன்பாட்டு endpoints இலிருந்து பிழை உடல்கள் ஒருபோதும் மூலமாக வெளிப்படுத்தப்படுவதில்லை; ஒரு அனுமதிப்பட்டியலிடப்பட்ட புலங்களின் தொகுப்பு மட்டுமே தப்பிப்பிழைக்கிறது, ஏனெனில் ஒரு டோக்கன் endpoint இன் தோல்வி உடல் கோரிக்கைப் பொருளை எதிரொலிக்கக்கூடும்.
- **Probe சுகாதாரம்.** எந்த உருவாக்கப்பட்ட `claude` probe உம், claude தன் keychain தேடலுக்கு முன்பு மதிக்கும் எட்டு சூழல் மாறிகளை (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, மற்றும் அது போன்றவை) துடைக்கிறது, எனவே ஒரு probe ஒருபோதும் தவறான கணக்கிற்குக் கூறப்பட முடியாது.
