El paquete npm distribuye código fuente de TypeScript, no un build: el bin `tokenmaxxing` apunta directamente a `src/main.ts` con un shebang de Bun, y Bun 1.2.6 o más reciente lo ejecuta tal cual. Por eso Bun es un requisito estricto. No hay binarios compilados por diseño: un lanzamiento temprano distribuyó un único binario de macOS de 61 MB a todas las plataformas y falló en Linux con `exec format error`, y los paquetes compilados por plataforma necesitarían cada uno su propia canalización de lanzamiento, así que el código fuente ejecutado por Bun se convirtió en el modelo de distribución.

El mapa `exports` del paquete expone `src/sdk.ts` como el punto de entrada programático descrito en [La superficie del SDK de agentes](/es/sdk). Los lanzamientos se etiquetan como `v<version>` en GitHub; CI publica en npm mediante publicación de confianza (OIDC, con procedencia), y la compuerta de publicación ejecuta primero la comprobación de tipos.

## Nix / nix-darwin

El mismo árbol de código fuente también es un flake. Mantiene el modelo de código fuente ejecutado por Bun (vía [bun2nix](https://github.com/nix-community/bun2nix) `writeBunApplication`) y expone:

| Salida | Propósito |
|---|---|
| `packages.default` | `tokenmaxxing` + `xx` en el PATH |
| `darwinModules.default` / `withOverlay` | nix-darwin: instalar la CLI (temporizador de comprobación declarativo opcional) |
| `homeManagerModules.default` | Home Manager en macOS o Linux |
| `nixosModules.default` / `withOverlay` | instalación de sistema en NixOS |

Instala en un perfil (para que los shims supervisores de `init` puedan resolver un `tokenmaxxing` estable en el PATH), y luego ejecuta init:

```sh
nix profile install github:anaclumos/tokenmaxxing
tokenmaxxing init
```

Uso puntual sin instalar (solo help / status, no ejecutes `init` así):

```sh
nix run github:anaclumos/tokenmaxxing -- help
```

nix-darwin (añade el overlay para que `pkgs.tokenmaxxing` se resuelva):

```nix
{
  inputs.tokenmaxxing.url = "github:anaclumos/tokenmaxxing";
  modules = [
    inputs.tokenmaxxing.darwinModules.withOverlay
    { programs.tokenmaxxing.enable = true; }
  ];
}
```

Home Manager (fija el paquete explícitamente, o aplica el overlay de este flake a los pkgs que use Home Manager):

```nix
{
  imports = [ inputs.tokenmaxxing.homeManagerModules.default ];
  programs.tokenmaxxing.enable = true;
  programs.tokenmaxxing.package = inputs.tokenmaxxing.packages.${pkgs.system}.default;
}
```

Nix solo pone la CLI en el PATH. La importación de cuentas, el shim supervisor `claude` en el PATH, los hooks de `settings.json` y (por defecto) el temporizador de comprobación periódica siguen viniendo de `tokenmaxxing init`. Esos pasos tocan credenciales y ajustes del usuario que un módulo puro no debería reescribir. Pon `programs.tokenmaxxing.checkTimer.enable = true` solo cuando quieras que Nix gestione el temporizador en lugar de init (eso también exporta `TOKENMAXXING_SKIP_TIMER=1`, así que init no escribe una segunda unidad). El temporizador declarativo es un temporizador de sesión de usuario, igual que el de init. En Linux sin cabeza hace falta `loginctl enable-linger` para que se dispare sin un inicio de sesión.

Cuando cambie `bun.lock`, regenera la expresión de dependencias de Nix:

```sh
bun run nix:bun   # writes bun.nix via bun2nix@2.1.2
```
