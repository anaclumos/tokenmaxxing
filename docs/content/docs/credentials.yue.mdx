---
title: 憑證儲存同安全模型
description: "憑證喺各平台存喺邊度，同每次切換執行嘅規則"
---

所有狀態都存喺 `~/.config/tokenmaxxing/`。憑證 I/O 全部經過同一個按平台揀好嘅儲存外觀。呼叫點永遠唔會按平台分支。

**macOS**：憑證存喺登入 keychain，做通用密碼項目，同 Claude Code 自己擺嘅位置一樣。活躍嗰個項目就係 claude 讀取嘅嗰個。帳戶池入面每個帳戶嘅備份，就泊存做佢自己一個 `tokenmaxxing-cred-<uuid8>` keychain 項目。磁碟上冇任何明文。讀取用 `security find-generic-password -w`（個秘密只會出現喺 stdout）。寫入就經 stdin 將一行 `add-generic-password` 送入 `security -i`，所以個秘密永遠唔會出現喺任何進程嘅 argv。互動模式有大約 4 KB 嘅行緩衝，所以超大嘅 blob 唯有改用 argv 寫入 - 呢個係泊存項目只儲存最小 OAuth 物件嘅其中一個原因。

**Linux**：Claude Code 將憑證存做 0600 明文檔案，而 tokenmaxxing 都跟同一套做法：活躍檔案係 claude 自己嘅 `.credentials.json`，泊存備份就係擺喺 `~/.config/tokenmaxxing/creds/` 呢個 0700 目錄入面嘅原子性 0600 檔案。呢度講嘅原子性，即係先寫入暫存、fsync，再重新命名：並行讀取者永遠見到完整嘅舊檔案或者完整嘅新檔案，唔會見到殘缺嗰個。

切換所執行嘅安全規則：

- **由真正擁有者收集。** 每次切換之前，都會問 API 個 token 屬於邊個組織，搵出活躍憑證真正嘅擁有者（`fetchTokenOrg` 打去 OAuth roles 端點）- 而唔係靠儲存住嘅活躍標籤，因為個標籤會漂移。試過有個漂移咗嘅標籤，令一個帳戶嘅收集覆寫咗另一個帳戶唯一嘅備份。如果活躍憑證屬於池以外嘅帳戶，切換就會直接拒絕，唔會亂咁覆寫。
- **一個臨界區。** 收集、安裝新憑證、備份佢輪換嘅 token、切換 `~/.claude.json` 嘅帳戶、提交活躍標籤，全部喺同一段上咗鎖嘅區段入面發生。
- **同 claude 自己嘅刷新互鎖。** 接近到期嘅 session 隨時都可以輪換自己嘅 token，所以憑證寫入亦都會攞 Claude Code 嘅刷新鎖（盡力而為，會回收過時鎖，逾時亦有上限）。
- **死咗嘅授權會乾淨咁降級。** 如果刷新返嚟 `invalid_grant`，就會將嗰個帳戶標記做需要重新認證，並喺錯誤傳開之前保存個標記，所以重試迴圈會縮細候選集，最後終止。`tokenmaxxing auth` 會就地修復標記咗嘅帳戶，而如果登入落喺同修復緊嗰個唔同嘅帳戶度，就會拒絕。
- **無 token 記錄。** Token 永遠唔會出現喺記錄、錯誤或者輸出。嚟自 token 同用量端點嘅錯誤內容永遠唔會照原樣顯示出嚟。只有允許清單內嘅欄位先會保留，因為 token 端點嘅失敗內容可能會夾帶請求嘅資料。
- **探測衛生。** 任何開出嚟嘅 `claude` 探測都會喺查 keychain 之前擦除 claude 會認嘅嗰八個環境變數（`ANTHROPIC_API_KEY`、`CLAUDE_CODE_OAUTH_TOKEN`、`CLAUDE_SECURESTORAGE_CONFIG_DIR` 等等），所以一次探測永遠唔會歸咗落錯嘅帳戶度。
