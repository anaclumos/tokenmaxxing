tokenmaxxing হলো স্বয়ংক্রিয় Claude Code অ্যাকাউন্ট সুইচিংয়ের জন্য একটি CLI। এটি আপনার মালিকানাধীন একাধিক সাবস্ক্রিপশন (Pro/Max) অ্যাকাউন্ট একত্র করে এবং ব্যবহৃত অ্যাকাউন্টটি কোনো ব্যবহার সীমার কাছাকাছি পৌঁছালে সক্রিয় ক্রেডেনশিয়ালকে আরও তরতাজা একটি অ্যাকাউন্টে হট-সোয়াপ করে। আপনি সবসময় যেভাবে `claude` চালান, ঠিক সেভাবেই চালাবেন; বদলটি একটি নিরাপদ টার্ন সীমানায় ঘটে এবং আপনার চলমান সেশন পুনরায় চালু না হয়েই নতুন অ্যাকাউন্টে একই কথোপকথন চালিয়ে যায়। এটি একসাথে অনেকগুলো সমান্তরাল সেশনজুড়ে কাজ করে।

একমাত্র দৃশ্যমান আচরণটি সবচেয়ে খারাপ পরিস্থিতিতে দেখা যায়: যখন পুরো পুলটি তার সীমায় থাকে, তখন সেশনটি একটি কাউন্টডাউনসহ থেমে যায় এবং পরবর্তী যে অ্যাকাউন্টটি রিসেট হবে তাতে স্বয়ংক্রিয়ভাবে আবার শুরু হয় (Ctrl-C সঙ্গে সঙ্গে আবার শুরু করে)।

## সমস্যাটি

একটি Claude সাবস্ক্রিপশন একসাথে তিনটি সীমা পরিমাপ করে (সবগুলো `/usage` দিয়ে নিশ্চিত করা):

- **বর্তমান সেশন**: একটি চলমান 5-ঘণ্টার উইন্ডো।
- **বর্তমান সপ্তাহ (সব মডেল)**: একটি 7-দিনের সমষ্টি।
- **বর্তমান সপ্তাহ, প্রতি মডেল**: আলাদা আলাদা মডেল ফ্যামিলির জন্য পৃথক সাপ্তাহিক সীমা। এগুলো বর্তমানে কেবল Sonnet ও Fable-এর জন্য বিদ্যমান, এবং কেবল Fable-এর সীমাটিই যথেষ্ট আঁটসাঁট যে গুরুত্ব রাখে: এটি সমষ্টিগত সীমার অনেক আগেই কার্যকর হয়। একটি মেশিন সপ্তাহ-সবমডেলে 50%-এ থাকতে পারে যখন সপ্তাহ-Fable ইতিমধ্যে 80%-এ।

সাপ্তাহিক কোটা হলো ব্যবহার-করো-নয়তো-হারাও: একটি অ্যাকাউন্ট তার নির্দিষ্ট সাপ্তাহিক রিসেটের মধ্যে যা ব্যবহার করেনি তা বাতিল হয়ে যায়। আপনার যদি একাধিক অ্যাকাউন্ট থাকে, যুক্তিসঙ্গত কৌশল হলো যে অ্যাকাউন্টটি তার নিজের সাপ্তাহিক গতির চেয়ে সবচেয়ে বেশি পিছিয়ে আছে সেটিতে কোটা খরচ করতে থাকা, এবং সেশনের মাঝপথে কোনো একক সীমা দেয়ালে পৌঁছানোর আগেই বদলে যাওয়া।

হাতে হাতে এটি করার মানে হলো লগ আউট করা, লগ ইন করা, এবং আপনার কথোপকথন হারানো। tokenmaxxing এটি স্বয়ংক্রিয় করে: একটি চলমান `claude` অনুরোধগুলোর মাঝে তার ক্রেডেনশিয়াল স্টোর পুনরায় যাচাই করে, তাই এর নিচে বদলে দেওয়া একটি ক্রেডেনশিয়াল সেখানেই গৃহীত হয় (macOS-এ প্রায় 30 সেকেন্ডের মধ্যে, Linux-এ পরবর্তী অনুরোধে)। একটি সাধারণ বদল কখনো আপনার সেশন পুনরায় চালু করে না। যে একটিমাত্র পরিস্থিতিতে এখনও প্রসেস ব্যবস্থাপনা দরকার তা হলো একটি সম্পূর্ণ নিঃশেষিত পুল (একটি সেশন নিজেকে থামাতে পারে না), আর এই কারণেই পাতলা সুপারভাইজরটির অস্তিত্ব।

`claude`-এর বাকি সবকিছু অপরিবর্তিত থাকে: সমস্ত ফ্ল্যাগ, MCP সার্ভার, হুক এবং স্কিল যেমন আছে তেমনই চলে।

## দ্রুত শুরু

macOS বা Linux-এ [Bun](https://bun.sh) এবং Claude Code প্রয়োজন।

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` পাঁচটি কাজ করে:

1. আপনি ইতিমধ্যে যে অ্যাকাউন্ট দিয়ে লগ ইন করে আছেন সেটিকে অ্যাকাউন্ট #1 হিসেবে ইমপোর্ট করে (আলাদা কোনো `adopt` কমান্ড নেই)।
2. `claude` সুপারভাইজর শিম ইনস্টল করে।
3. Claude Code-এর `settings.json`-এ তিনটি এন্ট্রি ইনস্টল করে: একটি statusLine, একটি Stop হুক, এবং একটি SessionStart হুক (সঙ্গে একটি subagentStatusLine এন্ট্রি)।
4. সুপারভাইজরের bin ডিরেক্টরিটি আপনার শেল rc-এর PATH-এ যুক্ত করে (idempotent, একটি `# tokenmaxxing PATH` মন্তব্য দিয়ে চিহ্নিত)। আসল `claude`-কে আটকাতে হলে এটিকে PATH-এ তার আগে থাকতে হবে।
5. একটি পর্যায়ক্রমিক চেক টাইমার ইনস্টল করে (macOS-এ একটি launchd এজেন্ট, Linux-এ একটি systemd ইউজার টাইমার) যা প্রতি 180 সেকেন্ডে `tokenmaxxing check` চালায়।

আপনার শেল পুনরায় চালু করুন, তারপর আরও অ্যাকাউন্ট যোগ করুন এবং এগিয়ে যান:

```sh
tokenmaxxing add        # আরও একটি অ্যাকাউন্ট বিচ্ছিন্নভাবে লগ ইন করে এবং পুলে যুক্ত করে
claude                  # সবসময়ের মতো claude ব্যবহার করুন
```

`tokenmaxxing`-এর একটি উপনাম `xx`-ও আছে। শুধু `tokenmaxxing` (বা `xx`) চালালে `status` চলে; `switch` সুস্পষ্টভাবেই থাকে।

## কমান্ড

| কমান্ড | এটি যা করে |
|---|---|
| `tokenmaxxing init` | বর্তমান অ্যাকাউন্ট ইমপোর্ট করে, সুপারভাইজর, হুক এবং statusline ইনস্টল করে |
| `tokenmaxxing init --codex` | Codex-এর জন্য একই: লগইন ইমপোর্ট করে, codex সুপারভাইজর ও Stop হুক ইনস্টল করে |
| `tokenmaxxing add` | একটি অতিরিক্ত অ্যাকাউন্ট নিবন্ধন করে (বিচ্ছিন্ন লগইন, পুলে সংগ্রহ করা হয়) |
| `tokenmaxxing add --codex` | একটি অতিরিক্ত Codex অ্যাকাউন্ট নিবন্ধন করে (বিচ্ছিন্ন লগইন) |
| `tokenmaxxing auth [sel \| --all]` | একটি পুলড অ্যাকাউন্ট সেখানেই পুনরায় প্রমাণীকরণ করে। শুধু চালালে পুলটি তালিকাভুক্ত করে এবং কোনটি জিজ্ঞাসা করে; একটি সিলেক্টর একটি অ্যাকাউন্টকে লক্ষ্য করে এবং কোন ইমেইল দিয়ে সাইন ইন করতে হবে তা জানায়; `--all` পুনরায়-প্রমাণীকরণ প্রয়োজন এমন প্রতিটি অ্যাকাউন্টে একে একে যায় |
| `tokenmaxxing switch [sel]` | সেরা অ্যাকাউন্টে বদলায় (greedy, idempotent) অথবা একটি নির্দিষ্ট অ্যাকাউন্ট জোর করে বেছে নেয় |
| `tokenmaxxing switch --codex [sel]` | Codex পুল বদলায় (পরবর্তী codex চালুতে কার্যকর হয়) |
| `tokenmaxxing ls` | পুলড অ্যাকাউন্টগুলো তালিকাভুক্ত করে |
| `tokenmaxxing status` | 5ঘণ্টা / সাপ্তাহিক / প্রতি-মডেল ব্যবহারের বার সহ অ্যাকাউন্ট, সক্রিয় এবং রিসেট-পর্যন্ত-নিঃশেষিত |
| `tokenmaxxing status --force` | অতিরিক্তভাবে প্রতিটি অ্যাকাউন্টকে পিং করে (প্রতিটিতে একটি ক্ষুদ্র haiku অনুরোধ) যাতে সব 5ঘণ্টার সেশন টাইমার এখনই শুরু হয়, তারপর তাজা নমুনা নেয় |
| `tokenmaxxing watch [seconds]` | লাইভ স্ট্যাটাস, প্রতি N সেকেন্ডে পুনরায় রেন্ডার করা হয় (ডিফল্ট 120, সর্বনিম্ন 30; কখনো পিং করে না) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | উৎসসহ কার্যকর কনফিগ; ডটেড কী সম্পাদনা করে; `tidy` অজানা কী ছেঁটে ফেলে |
| `tokenmaxxing check` | সুইচ সিদ্ধান্ত একবার মূল্যায়ন করে (পর্যায়ক্রমিক টাইমার এটিই চালায়) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack ব্রিজ ডিমন (Socket Mode, কোনো পাবলিক URL নেই) |
| `tokenmaxxing doctor` | সুপারভাইজর ও সেটিংস এন্ট্রিগুলো টিকে আছে কিনা যাচাই করে |
| `tokenmaxxing rename [--codex] <sel> <label>` | একটি পুলড অ্যাকাউন্টের লেবেল পরিবর্তন করে |
| `tokenmaxxing rm <sel>` | পুল থেকে একটি অ্যাকাউন্ট সরিয়ে ফেলে |
| `tokenmaxxing uninstall` | সুপারভাইজর ও সেটিংস এন্ট্রি সরিয়ে ফেলে (অ্যাকাউন্ট ও ক্রেডেনশিয়াল রাখা হয়) |

## আর্কিটেকচার

tokenmaxxing হলো একটি বহু-কল এন্ট্রি পয়েন্ট (`src/main.ts`) যা সেই নামে চালানো হলে `claude` সুপারভাইজর হিসেবে আচরণ করে, অভ্যন্তরীণ সাবকমান্ডের মাধ্যমে হুক ও statusline শিম পরিবেশন করে, এবং অন্যথায় CLI ডিসপ্যাচ করে। এটি সরাসরি Bun-এর অধীনে চলে; npm প্যাকেজটি TypeScript সোর্স পাঠায়, কোনো বিল্ড নয়।

চলমান অংশগুলো:

### সুপারভাইজর শিম

`init` `~/.config/tokenmaxxing/bin/`-এ `claude` নামে একটি 2-লাইনের শেল শিম লেখে এবং সেই ডিরেক্টরিটিকে PATH-এর প্রথমে বসায়। আপনি যখন `claude` টাইপ করেন, শিমটি সুপারভাইজর চালায়, যা উত্তরাধিকারসূত্রে পাওয়া stdio এবং একটি সংরক্ষিত `stty -g` টার্মিনাল স্ন্যাপশট সহ আসল claude বাইনারি স্পন করে। এটি কেবল একটি প্রসেস ও টার্মিনাল ম্যানেজার: এটি কখনো API ট্র্যাফিক প্রক্সি করে না এবং চলমান টোকেনে কখনো হাত দেয় না।

প্রিন্ট-মোড ইনভোকেশন (`claude -p`, `--version`, `--help`), নন-ইন্টারঅ্যাক্টিভ সাবকমান্ড (`claude mcp`, `claude config`, ইত্যাদি), এবং tokenmaxxing-এর নিজস্ব প্রোব কোনো সেশন ব্যবস্থাপনা ছাড়াই সরাসরি চলে যায়। একটি ইন্টারঅ্যাক্টিভ সেশনের জন্য, সুপারভাইজর একটি সেশন আইডি স্থির করে (একটি তৈরি করে, অথবা আপনি `--session-id` / `-r` / `-c` দিয়ে যেটি দিয়েছেন সেটি পুনরায় ব্যবহার করে), আপনার লঞ্চ ফ্ল্যাগগুলো সংরক্ষণ করে যাতে পরবর্তী কোনো পুনরায়-চালু সেগুলো আবার প্রয়োগ করতে পারে, এবং তারপর সেই সেশনের সঙ্গে সংযুক্ত একটি রিস্পন মার্কার ফাইলের জন্য নজর রাখে।

### statusline tee

Claude Code প্রতি টার্নে statusline-এর stdin-এ রেট-লিমিট ডেটা (`rate_limits.five_hour` এবং `rate_limits.seven_day`) পাঠায়। tokenmaxxing statusline স্লটটির মালিক, তাই এর রেন্ডারার একইসাথে একটি বিনামূল্যের, পুশ-ভিত্তিক ব্যবহার ফিড হিসেবেও কাজ করে: প্রতিটি টিকে এটি সমষ্টিগত উইন্ডোগুলো এবং সক্রিয় মডেলকে `usage.json`-এ টি করে। প্রতি-মডেল সীমা statusline stdin-এ থাকে না; এগুলো কেবল `claude -p '/usage'` (বিনামূল্যে, শূন্য টোকেন) থেকে আসে, যা একটি TTL সহ পোল করা হয় এবং সক্রিয় মডেল ক্ষমতা-সীমাবদ্ধ থাকলে `model-usage.json`-এ ক্যাশ করা হয়।

টি হলো পরিবর্তনে-লেখা: সংখ্যাগুলো অপরিবর্তিত থাকলে এটি কেবল ফাইলের mtime বাড়ায়, যা ফিডের সজীবতার হার্টবিট হিসেবে কাজ করে। তাজাত্ব সর্বদা mtime দিয়ে বিচার করা হয়, কখনো সংযুক্ত টাইমস্ট্যাম্প দিয়ে নয়।

### Stop হুক এবং বদল

প্রতিটি টার্ন সীমানায়, Stop হুক সুইচ সিদ্ধান্ত চালায় (দেখুন [কীভাবে সুইচিং সিদ্ধান্ত নেয়](#how-switching-decides))। যখন একটি বদল যুক্তিযুক্ত হয়, তখন এটি একটি `flock(2)` এক্সক্লুসিভ লকের অধীনে ঘটে (`bun:ffi`-এর মাধ্যমে নেওয়া, যেহেতু macOS কোনো `flock(1)` বাইনারি সরবরাহ করে না), এবং ক্রেডেনশিয়াল লেখাগুলো অতিরিক্তভাবে Claude Code-এর নিজস্ব রিফ্রেশ লকের সঙ্গে ইন্টারলক করে। ক্রিটিক্যাল সেকশনের ভেতরে, একটি বদল:

1. বর্তমান লাইভ ক্রেডেনশিয়ালটিকে তার প্রকৃত মালিকের পার্ক করা ব্যাকআপে সংগ্রহ করে।
2. টার্গেট অ্যাকাউন্টের সদ্য রিফ্রেশ করা ক্রেডেনশিয়ালটিকে লাইভ হিসেবে ইনস্টল করে, বিদ্যমান লাইভ ব্লবের সঙ্গে মিশিয়ে দেয় যাতে সহযোগী স্টেট (যেমন প্রতি-MCP-সার্ভার OAuth টোকেন) টিকে থাকে।
3. টার্গেটের ঘোরানো (rotated) টোকেনটিকে তার নিজের ব্যাকআপে সংরক্ষণ করে।
4. `~/.claude.json`-এর `oauthAccount` ফিল্ডটিকে অ্যাটমিকভাবে পুনরায় লেখে।
5. নতুন সক্রিয় লেবেল কমিট করে এবং পুরনো ব্যবহার স্ন্যাপশটগুলো মুছে ফেলে, সবই লক রিলিজ হওয়ার আগে, যাতে কোনো ক্র্যাশ কখনোই ইনস্টল করা ক্রেডেনশিয়াল আর সক্রিয় লেবেলকে আলাদা অ্যাকাউন্টের দিকে ইঙ্গিত করা অবস্থায় ফেলে রাখতে না পারে।

যেহেতু সমস্ত ডিফল্ট-প্রোফাইল সেশন একটিমাত্র লাইভ ক্রেডেনশিয়াল ভাগ করে, একটি একক বদল একসাথে প্রতিটি সেশনকে স্থানান্তর করে, এবং flock এবং লকের অধীনে একটি পুনরায়-যাচাই প্রতিযোগিতাকারী হুকগুলোকে দুটি অ্যাকাউন্ট পোড়ানো থেকে বিরত রাখে।

### সেখানেই গ্রহণ

একটি চলমান claude সেশন অনুরোধগুলোর মাঝে তার ক্রেডেনশিয়াল স্টোর পোল করে: macOS-এ এটি একটি সংক্ষিপ্ত ক্যাশের মাধ্যমে কীচেইন পুনরায় পড়ে এবং অ্যাক্সেস টোকেন তুলনা করে; Linux-এ এটি ক্রেডেনশিয়াল ফাইলের mtime স্ট্যাট করে এবং পরিবর্তন হলে তার টোকেন ক্যাশ ফ্লাশ করে। এর সামগ্রিক ফলাফল হলো একটি বদলে দেওয়া ক্রেডেনশিয়াল macOS-এ প্রায় 30 সেকেন্ডের মধ্যে এবং Linux-এ ঠিক পরবর্তী অনুরোধেই প্রতিটি চলমান সেশন দ্বারা গৃহীত হয়, কোনো পুনরায় চালু ছাড়াই। এই কারণেই একটি সাধারণ বদল কোনো মার্কার লেখে না এবং কোনো রিস্পন ট্রিগার করে না: সেশনটি কেবল নতুন অ্যাকাউন্টে চলতে থাকে। সেশন-অভ্যন্তরীণ `/usage` একই টোকেন ক্যাশ ভাগ করে, তাই এর অ্যাকাউন্ট প্রদর্শন গ্রহণের সঙ্গে সঙ্গে বদলে যায়।

### নিঃশেষিত-পুল অপেক্ষা এবং স্বয়ংক্রিয়-পুনরায় শুরু

কেবল যখন পুলের প্রতিটি অ্যাকাউন্ট তার বারগুলোর ওপরে থাকে তখনই Stop হুক একটি রিস্পন মার্কার লেখে (মার্কার স্কিমার জন্য একটি `waitUntil` টাইমস্ট্যাম্প প্রয়োজন; একটি সাধারণ বদল কখনো তা তৈরি করতে পারে না)। সুপারভাইজর মার্কারটি দেখে, ইতিমধ্যে-কমিট করা টার্ন সীমানায় তার চাইল্ডকে SIGTERM করে (Stop হুক ট্রান্সক্রিপ্ট ডিস্কে থাকার এবং claude নিষ্ক্রিয় থাকার পরে চলে, তাই কিছুই হারায় না), টার্মিনাল পুনরুদ্ধার করে, সবচেয়ে কাছের রিসেট পর্যন্ত একটি কাউন্টডাউন দেখায়, এবং তারপর পুনরুদ্ধার করা অ্যাকাউন্টে `claude --resume <session-id>` পুনরায় চালু করে। কাউন্টডাউনের সময় Ctrl-C সঙ্গে সঙ্গে আবার শুরু করে। স্বয়ংক্রিয়-অপেক্ষা `policy.maxWaitMs` দ্বারা সীমাবদ্ধ (ডিফল্ট 1 ঘণ্টা); এর বাইরে সিদ্ধান্ত অপেক্ষা করার পরিবর্তে পুলটিকে নিঃশেষিত হিসেবে রিপোর্ট করে।

### পর্যায়ক্রমিক চেক টাইমার

হুকগুলো কেবল টার্ন সীমানায় সক্রিয় হয়, আর একটি দীর্ঘ এজেন্টিক টার্ন একটিও সীমানা ছাড়াই একটি উইন্ডোকে সুস্থ থেকে নিঃশেষিত পর্যন্ত পুড়িয়ে দিতে পারে। তাই `init` একটি পর্যায়ক্রমিক টাইমারও ইনস্টল করে (macOS-এ একটি launchd এজেন্ট, Linux-এ একটি systemd ইউজার টাইমার) যা টার্ন কার্যকলাপ নির্বিশেষে প্রতি 180 সেকেন্ডে `tokenmaxxing check` চালায়।

### একটি SessionStart হুক

একটি সেশন শুরু বা পুনরায় শুরু হলে একই মূল্যায়ন চালায়, যাতে একটি নতুন সেশন সঠিক অ্যাকাউন্টে শুরু হয়। বদল-পরবর্তী কুলডাউন এটিকে একটি রিস্পনের ঠিক পরে একটি সঠিক নো-অপ করে তোলে।

## কীভাবে সুইচিং সিদ্ধান্ত নেয় [#how-switching-decides]

সিদ্ধান্তটির দুটি স্তর আছে: একটি এনগেজমেন্ট গেট, এবং তারপর একটি greedy বা hard পথ।

### এনগেজমেন্ট

`policy.greedySessionFloor`-এর নিচে (ডিফল্ট 50, 5-ঘণ্টার সেশন উইন্ডোর শতাংশে), সিদ্ধান্তটি একেবারেই চলে না: একটি নতুন সেশন তার অ্যাকাউন্টে চলতে থাকে। সক্রিয় সেশন উইন্ডো একবার 50% ব্যবহৃত হলে, অথবা কোনো hard বার অতিক্রম করলে, সিদ্ধান্তটি সক্রিয় হয়।

### স্ক্রিনিং বার

থ্রেশহোল্ডগুলো হলো স্ক্রিনিং বার, আতঙ্কের ট্রিগার নয়:

- `thresholds.session`: 95। একটি 5-ঘণ্টার রিসেট বসে থেকে পার করা সস্তা, তাই সেশন উইন্ডো আগেভাগেই বদলে যায়।
- `thresholds.weekly`: 98। এই একটি বার 7-দিনের সমষ্টি এবং প্রতিটি প্রতি-মডেল সাপ্তাহিক সীমা উভয়ই আওতাভুক্ত করে। সাপ্তাহিক কোটা হলো ব্যবহার-করো-নয়তো-হারাও, তাই এটি দেয়ালের কাছাকাছি পর্যন্ত নিঃশেষিত হয়।

দুটিই ইচ্ছাকৃতভাবে 100-এর নিচে: হেডরুম হলো অ্যাকাউন্টটি আসলে তার সীমায় পৌঁছানোর আগে একটি পরিষ্কার টার্ন সীমানায় পৌঁছানোর বাজেট (সঙ্গে macOS-এ সর্বোচ্চ এক টার্নের গ্রহণ বিলম্ব)। একই বারগুলো বদলের প্রার্থীদের স্ক্রিন করে: তার কোনো বারের ওপরে থাকা একটি অ্যাকাউন্ট বৈধ টার্গেট নয়। ট্রিগার ও স্ক্রিনিং সর্বদা একই কার্যকর বার ব্যবহার করে (থ্রেশহোল্ড বিয়োগ `policy.projectionMargin`), কারণ ট্রিগারের চেয়ে শিথিল একটি স্ক্রিন এমন অ্যাকাউন্টে বদল অবতরণ করাবে যেগুলোকে ট্রিগার সঙ্গে সঙ্গে পুনরায় ফ্ল্যাগ করে, পুলটিকে পিং-পং করায়।

### টার্গেট: গতি চাপ (pace pressure)

ব্যবহারযোগ্য অ্যাকাউন্টগুলোর মধ্যে, টার্গেট হলো সেটি যা তার নিজের সাপ্তাহিক গতির চেয়ে সবচেয়ে বেশি পিছিয়ে: সর্বোচ্চ **গতি চাপ**, যা অবশিষ্ট সাপ্তাহিক শতাংশকে সেই অ্যাকাউন্টের সাপ্তাহিক রিসেট পর্যন্ত সময় দিয়ে ভাগ করে সংজ্ঞায়িত। যে অ্যাকাউন্টের সবচেয়ে বেশি কোটা বাতিল হতে চলেছে সেটি জেতে। সমতা ভাঙে সবচেয়ে কাছের সাপ্তাহিক মেয়াদ শেষ হওয়ার দিকে, তারপর সর্বনিম্ন 7-দিনের ব্যবহারের দিকে।

সবকিছু চলে অ্যাবসোলিউট UTC এপক হিসেবে সংরক্ষিত ক্যাশ করা উইন্ডোর ওপর, তাই একটি পুরনো স্ন্যাপশটও সঠিকভাবে সমাধান হয়: একটি সাপ্তাহিক রিসেট যা পার হয়ে গেছে তা ঠিক 7-দিনের ধাপে সামনের দিকে এক্সট্রাপোলেট করা হয়, এবং তার ক্যাশ করা রিসেট পার হয়ে যাওয়া যেকোনো উইন্ডো তাজাভাবে খালি হিসেবে গণ্য হয় (কখনো বদলানোর কারণ নয়, কখনো একটি অ্যাকাউন্টকে বেঞ্চে রাখার কারণ নয়)।

### Greedy বনাম hard পথ

- **Greedy পথ** (সক্রিয়, কিন্তু প্রতিটি বারের নিচে): বর্তমানসহ প্রতিটি অ্যাকাউন্টকে র‍্যাঙ্ক করে। বর্তমান অ্যাকাউন্ট যদি ইতিমধ্যে জেতে বা সমতা রাখে, কিছুই করে না। অন্যথায় কঠোরভাবে ভালো অ্যাকাউন্টে বদলে যায়। এটি কখনো অপেক্ষা করে না এবং কখনো প্রি-পার্ক করে না: একটি ব্যবহারযোগ্য বর্তমান অ্যাকাউন্ট একটি অপেক্ষার বিনিময়ে দেওয়া হয় না। যেহেতু বর্তমান অ্যাকাউন্টকেও র‍্যাঙ্ক করা হয়, স্বয়ংক্রিয় পথ এবং শুধু `tokenmaxxing switch` উভয়ই idempotent: পর্যায়ক্রমে মূল্যায়ন করলে সঠিক অ্যাকাউন্টে অভিসারিত হয় এবং তারপর স্থির থাকে।
- **Hard পথ** (একটি বার অতিক্রম): সেরা ব্যবহারযোগ্য প্রার্থীতে বদলে যায়। যদি কোনো প্রার্থীর রিফ্রেশ টোকেন মৃত হয়ে যায়, সেটিকে পুনরায়-প্রমাণীকরণ-প্রয়োজন হিসেবে ফ্ল্যাগ করা হয় এবং পরবর্তী প্রার্থীকে চেষ্টা করা হয়। যদি কিছুই ব্যবহারযোগ্য না হয়, তবে নিঃশেষিত-অপেক্ষার লজিক চলে; কেবল এমন একটি কলার যা আসলে সেশনটিকে থামাতে পারে (তত্ত্বাবধানকৃত Stop হুক) একটি এখনও-অবরুদ্ধ কিন্তু সবচেয়ে দ্রুত-পুনরুদ্ধারযোগ্য অ্যাকাউন্টে প্রি-পার্ক করার অনুমতি পায়।

### প্রতি-মডেল সীমা

`policy.switchModels` (ডিফল্ট `["fable"]`) সেই মডেল ফ্যামিলিগুলোর নাম দেয় যাদের প্রতি-মডেল সাপ্তাহিক সীমা একটি বদল ট্রিগার করতে পারে। মিলটি ফ্যামিলি টোকেন দিয়ে হয়, কখনো হুবহু প্রদর্শন স্ট্রিং দিয়ে নয়: মডেল প্রদর্শন নাম বদলে যায় ("Fable" হয়ে গেছে "Fable 5"), এবং একটি হুবহু-স্ট্রিং গেট একবার নীরবে প্রতি-মডেল সুইচিং সম্পূর্ণ নিষ্ক্রিয় করে দিয়েছিল। দুটি সম্পর্কিত নিরাপত্তা নিয়ম:

- একটি অজানা সক্রিয় মডেল প্রতিটি কনফিগার করা ফ্যামিলিকে গেট করে। একটি বদল স্ন্যাপশট পরিষ্কার করার ঠিক পরে, একটি হেডলেস মেশিন মডেল-অন্ধ অবস্থায় চলতে পারে; অজানাকে একবার অসীমাবদ্ধ হিসেবে বিবেচনা করায় একটি অ্যাকাউন্ট ঘণ্টার পর ঘণ্টা অলক্ষ্যে তার Fable সীমায় বসে ছিল।
- প্রার্থী স্ক্রিনিং গেট করা প্রতি-মডেল সীমাও গণনা করে, তাই যে পুলে প্রতিটি অ্যাকাউন্ট তার Fable সীমা পুড়িয়ে ফেলেছে সেটি রাউন্ড-রবিন করে না।

### কুলডাউন

একটি 45-সেকেন্ডের বদল-পরবর্তী কুলডাউন স্বয়ংক্রিয় পথকে গেট করে। বদলের পরে একই 45 সেকেন্ডের জন্য statusline টি দমন করা হয় (macOS-এ গ্রহণে সর্বোচ্চ 30 সেকেন্ড লাগে), যাতে একটি আগের মূল্যায়ন এমন ডেটার ওপর না চলে যা বদল নিজেই অবৈধ করেছে: ঠিক এই পরিস্থিতিই একবার একটি A-থেকে-B-এবং-ফিরে রিস্পন লুপ তৈরি করেছিল। ম্যানুয়াল `tokenmaxxing switch` কুলডাউন দ্বারা প্রভাবিত হয় না।

## কনফিগারেশন

কনফিগ হলো `~/.config/tokenmaxxing/config.json`-এ JSON। প্রতিটি ফিল্ড ঐচ্ছিক; ডিফল্টগুলো প্রতি-ফিল্ডে প্রযোজ্য।

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: উপরে বর্ণিত স্ক্রিনিং বার।
- `policy.projectionMargin`: কার্যকর বার তৈরি করতে উভয় বার থেকে বিয়োগ করা হয়।
- `policy.greedySessionFloor`: সেশন-ব্যবহৃত শতাংশ যেখানে greedy অভিসরণ সক্রিয় হয়।
- `policy.switchModels`: সেই মডেল ফ্যামিলি যাদের প্রতি-মডেল সাপ্তাহিক সীমা একটি বদলকে গেট করে (এন্ট্রিগুলো লোড করার সময় ছোট হাতের অক্ষরে রূপান্তরিত হয়)।
- `policy.usagePollTtlMs`: একটি `/usage` প্রতি-মডেল পোল কতক্ষণ তাজা থাকে।
- `policy.maxWaitMs`: নিঃশেষিত-পুল স্বয়ংক্রিয়-অপেক্ষার সীমা।

`tokenmaxxing config` উৎসসহ কার্যকর কনফিগ দেখায়; `config set`/`unset` ডটেড কী সম্পাদনা করে; `config tidy` অজানা কী ছেঁটে ফেলে।

## স্টেট ডিরেক্টরি বিন্যাস

সবকিছু `~/.config/tokenmaxxing/`-এর অধীনে থাকে (`TOKENMAXXING_HOME` দিয়ে ওভাররাইড করা যায়; প্রতিটি বাহ্যিকভাবে পর্যবেক্ষণযোগ্য পাথের একটি env ওভাররাইড আছে যাতে পুরো টুলটি পরীক্ষায় হার্মেটিকভাবে চলতে পারে)।

| পাথ | এটি যা ধারণ করে |
|---|---|
| `config.json` | আপনার কনফিগারেশন (স্পার্স; ডিফল্টগুলো প্রতি ফিল্ডে প্রযোজ্য) |
| `accounts.json` | পুলড Claude অ্যাকাউন্টগুলোর অ-গোপন ইনডেক্স: লেবেল, আইডি, ক্যাশ করা ব্যবহার উইন্ডো। কখনো টোকেন নয় |
| `usage.json` | statusline টি-এর সমষ্টিগত উইন্ডো স্ন্যাপশট; এর mtime হলো ফিডের সজীবতার হার্টবিট |
| `model-usage.json` | `/usage` থেকে TTL-ক্যাশ করা প্রতি-মডেল সাপ্তাহিক সীমা |
| `lastswap.json` | শেষ বদলের এপক টাইমস্ট্যাম্প; 45-সেকেন্ডের কুলডাউন চালায় |
| `lock` | `flock` ফাইল যা বদলগুলোকে ক্রমিক করে |
| `tokenmaxxing.log` | কেবল-যোগ করা ইভেন্ট লগ |
| `bin/` | PATH শিমগুলো: `claude`, `codex`, এবং `tokenmaxxing` / `xx` এন্ট্রি পয়েন্ট |
| `respawn/<session-id>` | নিঃশেষিত-অপেক্ষার রিস্পন মার্কার যা সুপারভাইজর নজরে রাখে |
| `creds/` | কেবল Linux: পার্ক করা ক্রেডেনশিয়াল ফাইল, একটি 0700 ডিরেক্টরিতে 0600 (macOS পরিবর্তে ক্রেডেনশিয়ালগুলোকে প্রতি-অ্যাকাউন্ট কীচেইন আইটেম হিসেবে পার্ক করে) |
| `onboard/`, `sample/` | `add`/`auth` লগইন এবং পার্ক-করা-অ্যাকাউন্টের `/usage` প্রোবের জন্য একবার-ব্যবহার্য বিচ্ছিন্ন কনফিগ হোম; প্লেইনটেক্সট ক্রেডেনশিয়াল ধারণকারী অনবোর্ড হোমগুলো সংগ্রহের পরে মুছে ফেলা হয় |
| `slack.json` | `xx serve` টোকেন এবং চ্যানেল লিঙ্ক (0600) |
| `slack-threads/` | `xx serve`-এর জন্য প্রতি-থ্রেড সেশন রেকর্ড |
| `codex-*` | সমান্তরাল Codex পুল: `codex-accounts.json`, `codex-lastswap.json`, `codex-lock`, `codex-creds/`, `codex-onboard/`, `codex-respawn/`, এবং `codex-live/` (প্রতিটি চলমান তত্ত্বাবধানকৃত codex সেশনের জন্য একটি PID-যাচাইকৃত উপস্থিতি ফাইল, তাই একটি লাইভ অ্যাকাউন্ট কখনো বদলের টার্গেট নয়) |

এর নিজের ডিরেক্টরির বাইরে, tokenmaxxing ঠিক এগুলোই স্পর্শ করে: `~/.claude.json` (`oauthAccount` বদল), Claude Code-এর `settings.json` (হুক ও statusline এন্ট্রি), লাইভ ক্রেডেনশিয়াল স্টোর (macOS-এ `Claude Code-credentials` কীচেইন আইটেম, Linux-এ `.credentials.json`), `~/.claude.lock` (claude-এর রিফ্রেশ লক, বদলের সময় নেওয়া হয়), codex-এর `auth.json` ও `hooks.json`, এবং launchd বা systemd-এ পর্যায়ক্রমিক-চেক ইউনিট।

## ক্রেডেনশিয়াল সংরক্ষণ ও নিরাপত্তা মডেল

সমস্ত স্টেট `~/.config/tokenmaxxing/`-এ থাকে। ক্রেডেনশিয়াল I/O একটি একক প্ল্যাটফর্ম-নির্বাচিত স্টোর ফ্যাসাডের মধ্য দিয়ে যায়; কল সাইটগুলো কখনো প্ল্যাটফর্মের ওপর ভিত্তি করে শাখাবিন্যাস করে না।

**macOS**: ক্রেডেনশিয়ালগুলো লগইন কীচেইনে জেনেরিক-পাসওয়ার্ড আইটেম হিসেবে থাকে, Claude Code নিজে যেখানে সেগুলো রাখে তার সঙ্গে মিলিয়ে। লাইভ আইটেমটিই claude পড়ে; প্রতিটি পুলড অ্যাকাউন্টের ব্যাকআপ তার নিজের `tokenmaxxing-cred-<uuid8>` কীচেইন আইটেম হিসেবে পার্ক করা হয়। ডিস্কে কিছুই প্লেইনটেক্সট নয়। পড়া হয় `security find-generic-password -w` দিয়ে (গোপন তথ্য কেবল stdout-এ প্রকাশ পায়); লেখা একটি `add-generic-password` লাইনকে stdin-এর মাধ্যমে `security -i`-তে পাইপ করে যাতে গোপন তথ্য কোনো প্রসেসের argv-তে কখনো প্রকাশ না পায়। ইন্টারঅ্যাক্টিভ মোডে প্রায় 4 KB লাইন বাফার আছে, তাই অতিরিক্ত বড় ব্লব একটি argv লেখায় ফিরে যায়: এটাই একটি কারণ যে পার্ক করা আইটেমগুলো কেবল ন্যূনতম OAuth অবজেক্ট সংরক্ষণ করে।

**Linux**: Claude Code ক্রেডেনশিয়ালগুলো একটি 0600 প্লেইনটেক্সট ফাইল হিসেবে সংরক্ষণ করে, এবং tokenmaxxing একই মডেল অনুসরণ করে: লাইভ ফাইলটি claude-এর নিজস্ব `.credentials.json`, এবং পার্ক করা ব্যাকআপগুলো একটি 0700 ডিরেক্টরির মধ্যে `~/.config/tokenmaxxing/creds/`-এর অধীনে অ্যাটমিক 0600 ফাইল। এখানে অ্যাটমিক মানে অস্থায়ীতে-লেখা, fsync, তারপর rename: একটি সমকালীন পাঠক সর্বদা একটি সম্পূর্ণ পুরনো বা সম্পূর্ণ নতুন ফাইল দেখে, কখনো আংশিক নয়।

বদল যে নিরাপত্তা নিয়মগুলো কার্যকর করে:

- **প্রকৃত মালিক দ্বারা সংগ্রহ।** একটি বদলের আগে, লাইভ ক্রেডেনশিয়ালের প্রকৃত মালিক নির্ধারণ করা হয় API-কে জিজ্ঞাসা করে যে টোকেনটি কোন প্রতিষ্ঠানের (OAuth রোলস এন্ডপয়েন্টের বিপরীতে `fetchTokenOrg`), কখনো সংরক্ষিত সক্রিয় লেবেলের ওপর বিশ্বাস করে নয়, যা বিচ্যুত হতে পারে। একটি বিচ্যুত লেবেল একবার একটি অ্যাকাউন্টের সংগ্রহকে অন্য একটি অ্যাকাউন্টের একমাত্র ব্যাকআপ ওভাররাইট করতে বাধ্য করেছিল। লাইভ ক্রেডেনশিয়াল যদি পুলের বাইরের কোনো অ্যাকাউন্টের হয়, তবে বদল সেটিকে ধ্বংস করার পরিবর্তে সরাসরি প্রত্যাখ্যান করে।
- **একটি ক্রিটিক্যাল সেকশন।** সংগ্রহ, নতুন ক্রেডেনশিয়াল ইনস্টল, তার ঘোরানো টোকেনের ব্যাকআপ, `~/.claude.json` অ্যাকাউন্ট বদল, এবং সক্রিয়-লেবেল কমিট সবই একই লক করা সেকশনের ভেতরে ঘটে।
- **claude-এর নিজস্ব রিফ্রেশের সঙ্গে ইন্টারলক।** মেয়াদ-শেষের-কাছাকাছি একটি সেশন যেকোনো মুহূর্তে তার নিজের টোকেন ঘোরাতে পারে, তাই ক্রেডেনশিয়াল লেখাগুলোও Claude Code-এর রিফ্রেশ লক নেয় (সর্বোত্তম-প্রচেষ্টায়, একটি পুরনো-লক পুনরুদ্ধার এবং একটি সীমাবদ্ধ টাইমআউট সহ)।
- **মৃত গ্রান্ট পরিচ্ছন্নভাবে অবনমিত হয়।** একটি রিফ্রেশ যা `invalid_grant` ফিরিয়ে আনে সেই অ্যাকাউন্টকে পুনরায়-প্রমাণীকরণ-প্রয়োজন হিসেবে ফ্ল্যাগ করে এবং ত্রুটি ছড়ানোর আগে ফ্ল্যাগটি সংরক্ষণ করে, যাতে পুনঃচেষ্টা লুপ প্রার্থী সেট সংকুচিত করে এবং সমাপ্ত হয়। `tokenmaxxing auth` একটি ফ্ল্যাগ করা অ্যাকাউন্ট সেখানেই ঠিক করে, এবং এটি এমন একটি লগইন প্রত্যাখ্যান করে যা যে অ্যাকাউন্টটি মেরামত করা হচ্ছে তার চেয়ে ভিন্ন অ্যাকাউন্টে অবতরণ করে।
- **কোনো টোকেন লগিং নেই।** টোকেন কখনো লগ, ত্রুটি বা আউটপুটে প্রকাশ পায় না। টোকেন ও ব্যবহার এন্ডপয়েন্ট থেকে আসা ত্রুটির বডি কখনো কাঁচা অবস্থায় দেখানো হয় না; কেবল একটি অনুমোদিত-তালিকাভুক্ত ফিল্ড সেট টিকে থাকে, কারণ একটি টোকেন এন্ডপয়েন্টের ব্যর্থতার বডি অনুরোধের উপাদান প্রতিধ্বনিত করতে পারে।
- **প্রোব স্বাস্থ্যবিধি।** যেকোনো স্পন করা `claude` প্রোব claude তার কীচেইন লুকআপের আগে যে আটটি এনভায়রনমেন্ট ভেরিয়েবল মান্য করে সেগুলো মুছে ফেলে (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, ইত্যাদি), যাতে একটি প্রোব কখনোই ভুল অ্যাকাউন্টে দায়ী করা না যায়।

## প্ল্যাটফর্ম নোট: macOS বনাম Linux

| | macOS | Linux |
|---|---|---|
| লাইভ ক্রেডেনশিয়াল | লগইন কীচেইন জেনেরিক-পাসওয়ার্ড আইটেম | 0600 `.credentials.json` ফাইল |
| পার্ক করা ক্রেডেনশিয়াল | প্রতি-অ্যাকাউন্ট কীচেইন আইটেম | 0700 ডিরেক্টরিতে 0600 ফাইল |
| বদলের পরে গ্রহণ | ~30 সেকেন্ডের মধ্যে (কীচেইন রিড ক্যাশ) | পরবর্তী অনুরোধ (ফাইল mtime পোল) |
| পর্যায়ক্রমিক চেক | launchd এজেন্ট, প্রতি 180সে | systemd ইউজার টাইমার, প্রতি 180সে |
| বিচ্ছিন্ন-লগইন স্টোর | প্রতি কনফিগ ডিরেক্টরিতে হ্যাশ-নেমস্পেসড কীচেইন সার্ভিস | বিচ্ছিন্ন কনফিগ ডিরেক্টরির ভেতরে একটি ফাইল |

জানার মতো দুটি Linux-নির্দিষ্ট বিবরণ: claude তার ক্রেডেনশিয়াল ডিরেক্টরি প্রথমে `CLAUDE_SECURESTORAGE_CONFIG_DIR` থেকে নির্ধারণ করে (তারপর `CLAUDE_CONFIG_DIR`, তারপর `~/.claude`), এবং tokenmaxxing সেই নির্ধারণ হুবহু অনুকরণ করে যাতে দুটি কখনো ডিসিঙ্ক না হয়। আর একই claude সংস্করণের দুটি OS বিল্ড `/usage` রিসেট ঘড়ি ভিন্নভাবে ফরম্যাট করে (একটি " at " জোড়া ব্যবহার করে, অন্যটি একটি কমা); tokenmaxxing-এর পার্সার ঠিক এই দুটি রূপ গ্রহণ করে এবং তৃতীয় যেকোনো কিছুতে অনুমানের পরিবর্তে লগ করে।

macOS-এ, একটি সৎ সীমাবদ্ধতা: `init` এবং `add` ইচ্ছাকৃতভাবে ইন্টারঅ্যাক্টিভভাবে কীচেইন স্পর্শ করে, যাতে প্রথম `security` অ্যাক্সেস একটি হেডলেস হুকের ভেতরে ঠান্ডা না থাকে।

## statusline

tokenmaxxing Claude Code-এর statusline স্থানীয়ভাবে রেন্ডার করে (একই সঙ্গে ব্যবহার ফিড টি করে)। ডিজাইন নীতি: কোটা রঙে বহন করা হয়, সংখ্যায় নয়। একটি লাইন, উদাহরণস্বরূপ:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- প্রতিটি উইন্ডো টোকেন হলো তার রিসেট-পর্যন্ত-সময়, ব্যবহৃত শতাংশ অনুযায়ী একটি অবিচ্ছিন্ন সবুজ-থেকে-হলুদ-থেকে-লাল র‍্যাম্পে রং করা (টার্মিনাল সমর্থন করলে truecolor, অন্যথায় 256-রঙের কিউবে ধাপে ধাপে)। র‍্যাম্প 0-এর জন্য বিশুদ্ধ সবুজে, 75-এ হলুদে, এবং 95 ও তার উপরে লালে নোঙর করে, তাই পুরনো তীব্রতা ব্যান্ডগুলো র‍্যাম্প নোঙর হিসেবে টিকে থাকে।
- মডেলের নাম একই র‍্যাম্পে কনটেক্সট-উইন্ডো পূর্ণতা দ্বারা রং করা হয়।
- একটি সবুজ `◆` সক্রিয় অ্যাকাউন্টের উইন্ডোগুলোর শুরুতে থাকে; প্রতিটি পার্ক করা অ্যাকাউন্ট তার নিজস্ব সায়ান `◇` পায় (পুনরায় প্রমাণীকরণ প্রয়োজন হলে লাল `✗`)। অ্যাকাউন্টগুলো সবচেয়ে কাছের আসন্ন রিসেট অনুযায়ী সাজানো হয়।
- প্রতিটি ব্লকে প্রতি-মডেল প্রথমে আসে একটি খালি রং করা আদ্যক্ষর হিসেবে: Fable `𝒇` হিসেবে রেন্ডার হয়; অন্য ফ্যামিলিগুলো তাদের বড় হাতের প্রথম অক্ষর ব্যবহার করে, সর্বদা ফ্যামিলি-মিলিত।
- একটি অস্পর্শিত পার্ক করা অ্যাকাউন্ট একটি সবুজ `full` রেন্ডার করে। অজানা রিসেট সহ পরিমাপকৃত ব্যবহার একটি রং করা `?` রেন্ডার করে, এবং একটি গেট করা মডেলে একটি অপরিমাপিত প্রতি-মডেল সীমা একটি রং-না-করা `𝒇?` রেন্ডার করে: অপরিমাপিত কখনোই নিরাপদ দেখাতে হবে না।
- রিসেট কাউন্টডাউন কেবল বৃহত্তম এককটি দেখায়, কখনো "now" বা "0m" নয়; কোনো আসন্ন রিসেট নেই এমন একটি উইন্ডো একটি সবুজ `0` রেন্ডার করে (আবার খালি)।
- একটি লিঙ্কড git ওয়ার্কট্রির বেসনেম লাইনের শুরুতে থাকে; একটি মূল চেকআউট সেখানে কিছুই রেন্ডার করে না। শনাক্তকরণ একটি `.git` ফাইলের জন্য ফাইলসিস্টেম পড়ে এবং কখনো একটি git সাবপ্রসেস স্পন করে না।
- `NO_COLOR` সেট থাকলে, লাইনটি একটি জোড়া সাংখ্যিক ফরম্যাটে ফিরে যায় (`2h5` মানে 2 ঘণ্টায় রিসেট, 5% ব্যবহৃত; কনটেক্সট পূর্ণতার জন্য `ctx 42`): রঙ ছাড়া, একটি নিঃশেষিত উইন্ডো তাজা দেখাতে হবে না।

সাবএজেন্ট টাস্কগুলো claude-এর subagentStatusLine পৃষ্ঠের মাধ্যমে তাদের নিজস্ব প্যানেল সারি পায়: প্রতিটি সক্রিয় টাস্কের জন্য একটি সারি, ফ্যামিলির নাম সেই টাস্কের কনটেক্সট পূর্ণতা দ্বারা রং করা।

## Codex সমর্থন

একই পুলিং OpenAI-এর Codex CLI-এর জন্য কাজ করে, আপনার নিজের ChatGPT-সাবস্ক্রিপশন অ্যাকাউন্টের বিপরীতে:

```sh
tokenmaxxing init --codex   # আপনার বর্তমান codex লগইন ইমপোর্ট করুন + codex সুপারভাইজর ও Stop হুক ইনস্টল করুন
tokenmaxxing add --codex    # আরেকটি অ্যাকাউন্ট লগ ইন করুন, বিচ্ছিন্নভাবে: আপনার প্রাথমিক লগইন অস্পর্শিত থাকে
codex                       # সবসময়ের মতো codex ব্যবহার করুন
```

Codex পুল সম্পূর্ণ সমান্তরাল স্টেট: এর নিজস্ব অ্যাকাউন্ট ইনডেক্স, এর নিজস্ব পার্ক করা ক্রেডেনশিয়াল ফাইল (উভয় প্ল্যাটফর্মে 0600 ফাইল, যেহেতু codex-এর নিজস্ব স্টোর একটি প্লেইনটেক্সট ফাইল), এর নিজস্ব লক, এর নিজস্ব শেষ-বদল টাইমস্ট্যাম্প। সিদ্ধান্ত-নীতি কোড ছাড়া Claude পুলের সঙ্গে কিছুই ভাগ করা হয় না।

### কেন Codex-এ হট-সোয়াপ অসম্ভব

একটি চলমান codex প্রসেস একটি ইন-মেমরি auth ম্যানেজার ধরে রাখে এবং `auth.json` এখন একটি ভিন্ন অ্যাকাউন্টের নাম ধারণ করলে তা পুনরায় লোড করতে সুস্পষ্টভাবে অস্বীকার করে। কোনো ফাইল ওয়াচার নেই এবং কোনো প্রতি-অনুরোধ ক্রেডেনশিয়াল পোল নেই, তাই একটি চলমান codex-এর নিচে বদলে দেওয়া একটি ক্রেডেনশিয়াল ইনফারেন্সের জন্য কেবল কখনোই কার্যকর হয় না। পুনরায় চালুই হলো বদল: `codex resume <session-id>` `auth.json` এখন যে অ্যাকাউন্টই ধারণ করুক তাতে স্থানীয় ট্রান্সক্রিপ্ট চালিয়ে যায়।

tokenmaxxing এটি একটি codex সুপারভাইজর শিম দিয়ে সামলায়: Stop হুক প্রতিটি টার্ন সীমানায় একই greedy গতি-চাপ সিদ্ধান্ত চালায়, এবং যখন এটি বদলায়, এটি একটি মার্কার লেখে যা সুপারভাইজরকে কমিট করা সীমানায় সেশনটিকে SIGTERM করায় এবং নতুন অ্যাকাউন্টে `codex resume <session-id>` পুনরায় চালু করায়, ট্রান্সক্রিপ্ট অক্ষত রেখে। যেহেতু প্রতিটি codex বদল একটি দৃশ্যমান পুনরায় চালু, codex greedy পথ একটি 1.2x উন্নতি মার্জিন বহন করে: একটি চ্যালেঞ্জারকে বর্তমান অ্যাকাউন্টের গতি চাপকে 20% দিয়ে হারাতে হবে, চুল পরিমাণে নয়। hard পথ (একটি অতিক্রম করা বার) মার্জিন উপেক্ষা করে। codex-এর জন্য কোনো নিঃশেষিত-পুল কাউন্টডাউনও নেই (কিছুই একটি codex সেশন থামাতে পারে না), তাই একটি সম্পূর্ণ নিঃশেষিত codex পুল স্থির থাকে।

অন্যান্য codex-নির্দিষ্ট প্রক্রিয়া:

- ব্যবহার পড়া হয় codex-এর নিজস্ব রেট-লিমিট এন্ডপয়েন্টের বিপরীতে একটি বিনামূল্যের প্রমাণীকৃত GET থেকে (CLI-এর `/status` যে একই কল করে): শতাংশ এবং অ্যাবসোলিউট এপক রিসেট সময়, সমষ্টিগত উইন্ডো ও প্রতি-মডেল সীমা একইভাবে। উইন্ডো শ্রেণীবিভাগ সময়কাল-চালিত, কখনো অবস্থান-চালিত নয়, কারণ বর্তমান প্ল্যানে হয়তো কোনো 5-ঘণ্টার উইন্ডোই নেই এবং সাপ্তাহিক উইন্ডোটি প্রাথমিক স্লটে বসে।
- Codex রিফ্রেশ টোকেন ঘোরে, এবং একটি প্রতিস্থাপিত টোকেন পুনরায় ব্যবহার করলে পুরো গ্রান্ট ফ্যামিলি মারা যায়। প্রতিটি ঘূর্ণন ফিরে আসার সঙ্গে সঙ্গে সংরক্ষণ করা হয়, সক্রিয় অ্যাকাউন্ট কেবল লাইভ ব্লবের মাধ্যমে নমুনা নেওয়া হয় (কখনো একটি পুরনো পার্ক করা কপি নয়), এবং প্রতি-সেশন উপস্থিতি ফাইল নিশ্চিত করে যে একটি লাইভ সহযোগী সেশনে চলমান একটি অ্যাকাউন্ট কখনো বদলের টার্গেট নয় এবং কখনো তার পার্ক করা টোকেন রিফ্রেশ হয় না।
- Codex-এর ফাইল ক্রেডেনশিয়াল স্টোর প্রয়োজন: keyring স্টোর পিন করা থাকলে `init --codex` দ্রুত ব্যর্থ হয়, এবং `add --codex` বিচ্ছিন্ন অনবোর্ডিং হোমে ফাইল-মোড সেটিং লেখে যাতে লগইন সংগ্রহযোগ্য অবস্থায় অবতরণ করে।
- একটি ম্যানুয়াল ধাপ: codex এমন হুক এড়িয়ে যায় যেগুলোকে বিশ্বাস করতে বলা হয়নি। `init --codex`-এর পরে, একবার codex খুলুন এবং `/hooks`-এর মাধ্যমে tokenmaxxing Stop হুকটিকে বিশ্বাস করুন, নয়তো স্বয়ংক্রিয়-সুইচিং নীরবে নিষ্ক্রিয় থাকে। `init --codex` এই অনুস্মারকটি প্রিন্ট করে।

## Slack ব্রিজ: xx serve

`tokenmaxxing serve` Socket Mode-এর মাধ্যমে একটি স্থানীয় Slack ডিমন চালায়: কোনো পাবলিক URL প্রয়োজন নেই। সেটআপ:

```sh
tokenmaxxing serve setup                    # অ্যাপ ম্যানিফেস্ট প্রিন্ট করে, দুটি টোকেনের জন্য অনুরোধ করে
tokenmaxxing serve link <channel-id> <repo> # একটি চ্যানেলকে একটি রিপো চেকআউটের সঙ্গে বাঁধে
tokenmaxxing serve                          # ডিমনটি চালায়
```

একটি লিঙ্কড চ্যানেলে বটকে মেনশন করুন এবং এটি সেই থ্রেডের জন্য লিঙ্কড রিপো চেকআউটে একটি Claude Code সেশন খোলে। প্রতিটি থ্রেড বার্তা `resume` সহ একটি Agent SDK `query()` চালায় (কখনো একটি স্থায়ী স্ট্রিমিং কোয়েরি নয়), তাই `ensureBestAccount()` প্রতিটি একক টার্নে পুলটি পুনরায় মূল্যায়ন করে এবং ডিমন থ্রেড না হারিয়ে পুনরায় চালু হতে পারে (থ্রেড রেকর্ড টেকসই; ডিমন চালু হওয়ার সময় সেগুলো পুনরায় সাবস্ক্রাইব করে)।

উল্লেখযোগ্য আচরণ:

- **স্ট্রিমিং**: উত্তরগুলো স্থানীয়ভাবে Slack-এ স্ট্রিম হয়, চিন্তা ও টুল রানের জন্য টাস্ক কার্ড সহ, হাইলাইটিং সহ রেন্ডার করা ফেন্সড কোড, খরচ ও সময়কাল সহ একটি সমাপনী "Turn" কার্ড, এবং যখনই একটি টুল রান স্ট্রিম করা টেক্সটে বাধা দেয় তখন একটি নতুন Slack বার্তা খোলা হয়, যাতে একটি টার্ন টুল রানের চারপাশে আলাদা বার্তা হিসেবে পড়া যায়। TodoWrite কল একটি স্থিতিশীল চেকলিস্ট কার্ড সেখানেই আপডেট করে।
- **অনুমতি**: প্রতি-লিঙ্ক `permissionMode` ডিফল্টে `acceptEdits`; `--yolo` (উপনাম `--dangerous`) একটি লিঙ্ককে `bypassPermissions`-এ নেয়। রিলে করা টার্নে ইন্টারঅ্যাক্টিভ ডায়ালগ অনুমোদিত নয় (কেউ Slack-এর মাধ্যমে কোনোটির উত্তর দিতে পারে না), তাই মডেল গদ্যে জিজ্ঞাসা করে এবং আপনার থ্রেড উত্তরই পরবর্তী টার্ন। একটি বান্ডিল করা প্লাগইন স্কিল এটিকে শেখায় যে যখন একটি সিদ্ধান্ত প্রয়োজন তখন অনুরোধকারীকে ট্যাগ করতে এবং টার্ন শেষ করতে।
- **স্ল্যাশ কমান্ড**: একটি থ্রেড বার্তা যার ছাঁটা টেক্সট `/` দিয়ে শুরু হয় তা একটি claude স্ল্যাশ কমান্ড হিসেবে চলে। Slack-এর কম্পোজার `/` দিয়ে শুরু হওয়া বার্তা খেয়ে ফেলে, তাই মেনশন-প্রথম রূপ (`@bot /usage`) বা একটি অগ্রবর্তী স্পেস ব্যবহার করুন।
- **সুশৃঙ্খল শাটডাউন**: SIGTERM/SIGINT নিষ্কাশন করে: নতুন টার্ন উচ্চস্বরে বাদ দেওয়া হয়, চলমান টার্ন সর্বোচ্চ 5 মিনিট পায়, এবং claude চাইল্ড তার নিজস্ব প্রসেস গ্রুপে বিচ্ছিন্নভাবে চলে যাতে একটি টার্মিনাল Ctrl-C নিষ্কাশন টার্নটি সংরক্ষণ করার আগে এটিকে মেরে ফেলতে না পারে।
- **থ্রেড পরিষ্করণ**: যখন আপনি এটিকে বলেন কাজটি সম্পন্ন, মডেল একটি ইন-প্রসেস `finish_thread` টুল কল করে; টার্ন সম্পূর্ণ শেষ হওয়ার পরে, ডিমন থ্রেড রেকর্ড ফেলে দেয়, আনসাবস্ক্রাইব করে, এবং একটি নিশ্চিতকরণ পোস্ট করে। একটি নতুন মেনশন একটি নতুন সেশন শুরু করে।
- **ত্রুটি স্বাস্থ্যবিধি**: টার্ন ত্রুটিগুলো ছাঁটা কেবল-বার্তা টেক্সট পোস্ট করে, কখনো কাঁচা ত্রুটি বডি নয়।

## Agent SDK পৃষ্ঠতল

প্যাকেজের প্রোগ্রাম্যাটিক এন্ট্রি (`exports["."]` `src/sdk.ts`-কে নির্দেশ করে) tokenmaxxing-কে Claude Agent SDK-এর সঙ্গে জোড়া দেয়, আপনার নিজের পুলড অ্যাকাউন্টের বিপরীতে আপনি যে এজেন্ট তৈরি করেন তার জন্য। আপনার অ্যাপ অবশ্যই Bun-এর অধীনে চলবে (tokenmaxxing TypeScript সোর্স পাঠায় এবং `bun:ffi` ব্যবহার করে)।

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK প্রতি `query()`-এ একটি claude সাবপ্রসেস স্পন করে এবং স্পনের সময় একবার ক্রেডেনশিয়াল পড়ে (কোনো statusline নয়, কোনো কোয়েরি-মধ্যবর্তী হট-সোয়াপ নয়), তাই ইন্টিগ্রেশনটি সীমানা-চালিত:

- `ensureBestAccount()` হলো ঠিক সেই সিদ্ধান্ত যা CLI হুক ও টাইমার চালায় (বার, গতি চাপ, কুলডাউন, সব ভাগ করা কোড), কখনো প্রত্যাশামূলক নয়: একটি SDK সেশন কখনো একটি নিঃশেষিত কাউন্টডাউনের জন্য থামানো যায় না।
- `pooledOptions()` `pathToClaudeCodeExecutable`-কে আসল claude বাইনারিতে পিন করে (কখনো সুপারভাইজর র‍্যাপার নয়) এবং প্রতিটি পারিপার্শ্বিক ক্রেডেনশিয়াল ওভাররাইড মুছে ফেলা একটি সম্পূর্ণ প্রতিস্থাপন `env` সরবরাহ করে। আপনার অ্যাপের এনভায়রনমেন্টে `CLAUDE_CONFIG_DIR` বা `CLAUDE_SECURESTORAGE_CONFIG_DIR` সেট থাকলে এটি দ্রুত ব্যর্থ হয়: Linux-এ একটি বদল লাইভ ক্রেডেনশিয়ালটি সেগুলো যেখানে নির্দেশ করে সেখানে লিখবে যখন মুছে ফেলা সাবপ্রসেস ডিফল্ট স্টোর পড়ে, একটি নীরব ভুল-অ্যাকাউন্ট ডিসিঙ্ক।
- `stopHookCheck` টার্ন সীমানায় সিদ্ধান্তটি পুনরায় চালায়; এটি যে বদল অবতরণ করায় তা পরবর্তী স্পনে কার্যকর হয়। এটি পুনরায় ছুঁড়ে দেওয়ার পরিবর্তে তার নিজের ত্রুটি ধরে (stderr ও লগে লগিং করে), কারণ একটি অপরিচালিত হুক ব্যতিক্রম এজেন্টকে বাধা দিতে পারে, এবং একটি ভাঙা সুইচ চেকের জন্য একটি টার্ন বাতিল করার খরচ বর্তমান অ্যাকাউন্টে চালিয়ে যাওয়ার চেয়ে বেশি।

`sdk.ts` Agent SDK নিজে থেকে কিছুই ইমপোর্ট করে না; এর মানগুলো কাঠামোগতভাবে SDK-এর অপশনে ছড়িয়ে যায়।

## বিল্ড ও বিতরণ

npm প্যাকেজটি TypeScript সোর্স পাঠায়, কোনো বিল্ড নয়: `tokenmaxxing` বিন একটি Bun শেবাং সহ সরাসরি `src/main.ts`-কে নির্দেশ করে, এবং Bun 1.2.6 বা তার নতুন সংস্করণ এটিকে যেমন আছে তেমনই চালায়। এই কারণেই Bun একটি কঠোর প্রয়োজনীয়তা। নকশা অনুযায়ী কোনো কম্পাইল করা বাইনারি নেই: একটি প্রাথমিক রিলিজ প্রতিটি প্ল্যাটফর্মে একটি একক 61 MB macOS বাইনারি পাঠিয়েছিল এবং Linux-এ `exec format error` দিয়ে ব্যর্থ হয়েছিল, আর প্রতি-প্ল্যাটফর্ম কম্পাইল করা প্যাকেজগুলোর প্রত্যেকের নিজস্ব রিলিজ পাইপলাইন প্রয়োজন হতো, তাই Bun-দিয়ে-সোর্স-চালানো বিতরণ মডেল হয়ে উঠল।

প্যাকেজের `exports` ম্যাপ উপরে বর্ণিত প্রোগ্রাম্যাটিক এন্ট্রি হিসেবে `src/sdk.ts` উন্মুক্ত করে। রিলিজগুলো GitHub-এ `v<version>` হিসেবে ট্যাগ করা হয়; CI বিশ্বস্ত প্রকাশনার (OIDC, প্রোভেন্যান্স সহ) মাধ্যমে npm-এ প্রকাশ করে, এবং প্রকাশনা গেট প্রথমে টাইপচেক ও সম্পূর্ণ টেস্ট স্যুট চালায়।

## ব্যক্তিগত ব্যবহার ও পরিষেবার শর্তাবলি [#personal-use-and-terms-of-service]

tokenmaxxing আপনার নিজের মালিকানাধীন অ্যাকাউন্ট একত্র করে, আপনার নিজের চালানো সেশন ও এজেন্টে। এই শব্দচয়নটি ইচ্ছাকৃত: Anthropic তৃতীয়-পক্ষের পণ্যকে claude.ai লগইন বা claude.ai রেট লিমিট অফার করার অনুমতি দেয় না, এবং তার মধ্যে Agent SDK-এর ওপর তৈরি এজেন্টও অন্তর্ভুক্ত। পুলড SDK পৃষ্ঠতল, বা তার ওপর তৈরি কিছু, তৃতীয় পক্ষের কাছে সরবরাহ করবেন না। tokenmaxxing কোটা ডেটার জন্য OAuth পুনরায় বাস্তবায়ন বা API ট্র্যাফিক প্রক্সি করার পরিবর্তে ইচ্ছাকৃতভাবে CLI-মধ্যস্থ `/usage` পথেই থাকে: এটি একটি প্রক্সি নয়, এবং এটি যে একমাত্র OAuth এন্ডপয়েন্ট স্পর্শ করে তা হলো একটি বদলের সময় ব্যবহৃত মানক রিফ্রেশ গ্রান্ট এবং একটি কেবল-পঠনযোগ্য পরিচয় যাচাই (রোলস এন্ডপয়েন্ট) যা যাচাই করে একটি টোকেন আসলে কোন অ্যাকাউন্টের।

## সৎ সীমাবদ্ধতা

- **একটি ঠান্ডা টার্ন।** প্রম্পট ক্যাশ প্রতিষ্ঠান-পরিসীমাবদ্ধ, তাই একটি নতুন অ্যাকাউন্টে প্রথম টার্ন একবার কনটেক্সট পুনরায় আপলোড করে।
- **নিঃশেষিত-বিরতির হেঁচকি।** কেবল একটি সম্পূর্ণ নিঃশেষিত পুল কাউন্টডাউনের জন্য সেশনটি থামায়; সেই মুহূর্তে টাইপ করা যেকোনো কিছু হারিয়ে যায়।
- **গ্রহণ বিলম্ব।** macOS-এ একটি বদলের ~30 সেকেন্ডের মধ্যে প্রথম টার্ন এখনও পুরনো অ্যাকাউন্টে পরিমাপ করতে পারে; বারগুলোর হেডরুম এটি শোষণ করে।
- **ভাগ করা বিস্ফোরণ ব্যাসার্ধ।** সমস্ত ডিফল্ট-প্রোফাইল সেশন একটি লাইভ ক্রেডেনশিয়াল ভাগ করে, তাই একটি বদল তাদের সবাইকে একসাথে সরায় (প্রতিটি সেখানেই গ্রহণ করে)।
- **Linux-এ প্লেইনটেক্সট ক্রেডেনশিয়াল।** Claude Code নিজেই Linux ক্রেডেনশিয়ালগুলো একটি 0600 প্লেইনটেক্সট ফাইল হিসেবে সংরক্ষণ করে; tokenmaxxing-এর পার্ক করা কপিগুলো একই মডেল অনুসরণ করে।

## সমস্যা সমাধান ও প্রায়শই জিজ্ঞাসিত প্রশ্ন

**`claude` তত্ত্বাবধানকৃত বলে মনে হচ্ছে না।**
`tokenmaxxing doctor` চালান। শিমকে অবশ্যই PATH নির্ধারণে জিততে হবে; যাচাই করুন যে আপনার শেল rc-এর `# tokenmaxxing PATH` লাইনটি বর্তমান bin ডিরেক্টরিকে নির্দেশ করে এবং আসল claude-এর আগে বসে। `doctor` `alias claude=...` বা একটি `claude()` শেল ফাংশন র‍্যাপারকে ছায়া দেওয়া সম্পর্কেও সতর্ক করে, এবং একটি claude বাইনারিকে অ্যাবসোলিউট পাথ দিয়ে চালু করা উপনামগুলো সম্পর্কে (সেগুলো সম্পূর্ণরূপে সুপারভাইজরকে বাইপাস করে)।

**Codex-এ স্বয়ংক্রিয়-সুইচিং কখনো সক্রিয় হয় না।**
Codex এমন হুক এড়িয়ে যায় যেগুলোকে বিশ্বাস করতে বলা হয়নি। codex খুলুন, `/hooks` চালান, এবং tokenmaxxing Stop হুকটিকে বিশ্বাস করুন। বিশ্বাস হুকের হ্যাশের বিপরীতে রেকর্ড করা হয়, তাই হুকটি কখনো সম্পাদিত হলে এটি পুনরায় মঞ্জুর করতে হবে।

**একটি অ্যাকাউন্ট statusline-এ একটি লাল `✗` দেখায়।**
এর রিফ্রেশ টোকেন মৃত (বাতিল করা হয়েছে বা তার ব্যাকআপের নিচ থেকে ঘোরানো হয়েছে)। এটিকে সেখানেই পুনরায় প্রমাণীকরণ করতে `tokenmaxxing auth <sel>` চালান; কমান্ডটি আপনাকে কোন ইমেইল দিয়ে সাইন ইন করতে হবে তা জানায় এবং একটি ভিন্ন অ্যাকাউন্টে অবতরণ করা একটি লগইন প্রত্যাখ্যান করে।

**এটি কেন সবচেয়ে বেশি অবশিষ্ট কোটা থাকা অ্যাকাউন্টে বদলায় না?**
কারণ সেটি কোটা বাতিল হওয়ার সবচেয়ে বেশি ঝুঁকিতে থাকা অ্যাকাউন্ট নয়। টার্গেট হলো সেই অ্যাকাউন্ট যা তার নিজের সাপ্তাহিক গতির চেয়ে সবচেয়ে বেশি পিছিয়ে: অবশিষ্ট শতাংশকে তার সাপ্তাহিক রিসেট পর্যন্ত সময় দিয়ে ভাগ করা। সমান পরিমাণ অবশিষ্ট থাকলে তা সবচেয়ে কাছের মেয়াদ শেষ আগে হিসেবে হ্রাস পায়, এবং সমান মেয়াদ শেষে সবচেয়ে বেশি অবশিষ্ট আগে।

**এটি সবেমাত্র বদলেছে এবং statusline এখনও পুরনো অ্যাকাউন্ট দেখাচ্ছে।**
macOS-এ সর্বোচ্চ ~30 সেকেন্ড পর্যন্ত এটি প্রত্যাশিত: চলমান সেশন তার পরবর্তী ক্রেডেনশিয়াল-ক্যাশ রিফ্রেশে বদলে দেওয়া ক্রেডেনশিয়াল গ্রহণ করে। ঠিক এই কারণেই একটি বদলের পরে 45 সেকেন্ডের জন্য ব্যবহার টি দমন করা হয়।

**`status --force` কি কিছু খরচ করে?**
হ্যাঁ, ইচ্ছাকৃতভাবে: এটি প্রতি অ্যাকাউন্টে একটি ন্যূনতম পরিমাপকৃত haiku অনুরোধ পাঠায় যাতে প্রতিটি 5-ঘণ্টার সেশন উইন্ডো নিষ্ক্রিয় পড়ে থাকার পরিবর্তে সেই মুহূর্তে শুরু হয়, তারপর তাজা নমুনা নেয়। সাধারণ `status` এবং `watch` কখনো পিং করে না; `/usage` পড়া বিনামূল্যে। লক্ষ্য করুন সার্ভার ব্যবহার ফিড একটি সদ্য খোলা উইন্ডোকে সেকেন্ড থেকে মিনিট বিলম্ব করতে পারে, তাই পিংয়ের ঠিক পরে একটি প্রোব এখনও পিং-পূর্ব অবস্থা দেখাতে পারে: `status` পিং ব্যর্থ হওয়ার ভান করার পরিবর্তে একটি নোট রেন্ডার করে।

**`/usage` প্রোব সক্রিয় অ্যাকাউন্টের জন্য কিছুই ফেরত দেয়নি।**
এটি একটি পরিচিত claude আচরণ: যখন এর অভ্যন্তরীণ ব্যবহার ফেচ ব্যর্থ হয় বা রেট-সীমিত হয়, `/usage` কোনো শতাংশ লাইন ছাড়াই কেবল স্থানীয় সেশন পরিসংখ্যান প্রিন্ট করে। tokenmaxxing statusline পুশ থেকে সক্রিয় অ্যাকাউন্টের নমুনা নেয় এবং কেবল পার্ক করা অ্যাকাউন্ট প্রোব করে, ঠিক এটি এড়াতেই।

**পটভূমির claude সেশন।**
Claude-এর পটভূমি ডিমন আসল সংস্করণকৃত বাইনারিটিকে অ্যাবসোলিউট পাথ দিয়ে স্পন করে, PATH শিম বাইপাস করে, তাই পটভূমির সেশনগুলো তত্ত্বাবধানহীন। হুকগুলো এখনও `settings.json`-এর মাধ্যমে সক্রিয় হয়, এবং ক্রেডেনশিয়াল গ্রহণ ও পর্যায়ক্রমিক টাইমার সুইচিং সামলায়, কিন্তু সেগুলোর জন্য কোনো মার্কার-চালিত রিস্পন নেই।

**একবার কিছু অনেকগুলো প্রসেস স্পন করেছিল। এটি কি এখনও সম্ভব?**
সুপারভাইজর ঠিক সেই ঐতিহাসিক ব্যর্থতার বিরুদ্ধে স্তরীভূত রিকার্সন প্রহরী বহন করে (একটি পুরনো র‍্যাপার "আসল" claude হিসেবে পিন করা): এনভায়রনমেন্টে একটি গভীরতা সেন্টিনেল যা 5 স্তরে বাতিল করে, একটি অন-ডিস্ক স্পন-রেট সীমাবদ্ধকারী, realpath পরিচয় যাচাই যা tokenmaxxing-এর নিজের bin ডিরেক্টরিতে ফিরে যাওয়া যেকোনো প্রার্থীকে প্রত্যাখ্যান করে, এবং একটি কনফিগার করা claude পাথ আর বিদ্যমান না থাকলে একটি কঠিন ব্যর্থতা (কখনো একটি নীরব PATH স্ক্যান নয়)। `init` এবং `doctor` একটি প্রার্থীকে পিন করার আগে `--version` চালিয়ে যাচাই করে যে সেটি আসলেই claude।

**আনইনস্টল করা।**
`tokenmaxxing uninstall` সুপারভাইজর শিম, সেটিংস এন্ট্রি, এবং পর্যায়ক্রমিক টাইমার সরিয়ে ফেলে, এবং আপনার অ্যাকাউন্ট ও পার্ক করা ক্রেডেনশিয়াল অক্ষত রাখে। এটি কেবল সেই statusline এন্ট্রিগুলো সরায় যেগুলোকে এটি তার নিজের হিসেবে চিনতে পারে।
