title: క్రెడెన్షియల్ నిల్వ మరియు భద్రతా నమూనా
description: "ప్రతి ప్లాట్‌ఫారమ్‌లో క్రెడెన్షియల్‌లు ఎక్కడ ఉంటాయి మరియు ప్రతి మార్పిడి అమలు చేసే నియమాలు"
---

మొత్తం స్థితి `~/.config/tokenmaxxing/`లో ఉంటుంది. క్రెడెన్షియల్ I/O ఒకే ప్లాట్‌ఫారమ్-ఎంపిక చేసిన స్టోర్ ఫసాడ్ ద్వారా వెళ్తుంది; కాల్ సైట్‌లు ప్లాట్‌ఫారమ్‌పై ఎప్పుడూ శాఖలు చేయవు.

**macOS**: క్రెడెన్షియల్‌లు జెనరిక్-పాస్‌వర్డ్ అంశాలుగా లాగిన్ కీచైన్‌లో ఉంటాయి, Claude Code స్వయంగా వాటిని ఉంచే చోటుతో సరిపోతూ. లైవ్ అంశం claude చదివేది; ప్రతి పూల్ చేసిన ఖాతా బ్యాకప్ దాని స్వంత `tokenmaxxing-cred-<uuid8>` కీచైన్ అంశంగా పార్క్ చేయబడుతుంది. డిస్క్‌పై ఏదీ ప్లెయిన్‌టెక్స్ట్ కాదు. చదవడాలు `security find-generic-password -w` ఉపయోగిస్తాయి (రహస్యం కేవలం stdoutపై మాత్రమే కనిపిస్తుంది); రాయడాలు stdin ద్వారా `add-generic-password` లైన్‌ను `security -i`లోకి పైప్ చేస్తాయి, తద్వారా రహస్యం ఏ ప్రాసెస్ argvలో ఎప్పుడూ కనిపించదు. ఇంటరాక్టివ్ మోడ్‌కు సుమారు 4 KB లైన్ బఫర్ ఉంది, కాబట్టి పెద్ద పరిమాణపు బ్లాబ్‌లు argv రైట్‌కు తిరిగివస్తాయి - పార్క్ చేసిన అంశాలు కేవలం కనీస OAuth ఆబ్జెక్ట్‌ను మాత్రమే నిల్వ చేయడానికి ఒక కారణం.

**Linux**: Claude Code క్రెడెన్షియల్‌లను 0600 ప్లెయిన్‌టెక్స్ట్ ఫైల్‌గా నిల్వ చేస్తుంది, మరియు tokenmaxxing అదే నమూనాను అనుసరిస్తుంది: లైవ్ ఫైల్ claude యొక్క స్వంత `.credentials.json`, మరియు పార్క్ చేసిన బ్యాకప్‌లు 0700 డైరెక్టరీలోని `~/.config/tokenmaxxing/creds/` కింద ఆటమిక్ 0600 ఫైల్‌లు. ఇక్కడ ఆటమిక్ అంటే తాత్కాలికంలోకి-రాయడం, fsync, ఆపై పేరుమార్చడం: ఏకకాల రీడర్ ఎల్లప్పుడూ పూర్తి పాత లేదా పూర్తి కొత్త ఫైల్‌ను చూస్తుంది, పాక్షికంగా ఎప్పుడూ కాదు.

మార్పిడి అమలు చేసే భద్రతా నియమాలు:

- **నిజమైన యజమాని ద్వారా సేకరణ.** మార్పిడికి ముందు, టోకెన్ ఏ సంస్థకు చెందుతుందో API నుండి అడగడం ద్వారా (OAuth roles ఎండ్‌పాయింట్‌పై `fetchTokenOrg`) లైవ్ క్రెడెన్షియల్ వాస్తవ యజమాని పరిష్కరించబడతాడు - మారగలిగే నిల్వ చేసిన క్రియాశీల లేబుల్‌ను నమ్మడం ద్వారా ఎప్పుడూ కాదు. మారిపోయిన లేబుల్ ఒకసారి ఒక ఖాతా సేకరణ మరో ఖాతా ఏకైక బ్యాకప్‌ను దిద్దివేసేలా చేసింది. లైవ్ క్రెడెన్షియల్ పూల్ వెలుపలి ఖాతాకు చెందితే, మార్పిడి దాన్ని దిద్దివేయడం కంటే పూర్తిగా తిరస్కరిస్తుంది.
- **ఒక క్రిటికల్ సెక్షన్.** సేకరణ, కొత్త క్రెడెన్షియల్ ఇన్‌స్టాల్, దాని తిప్పబడిన టోకెన్ బ్యాకప్, `~/.claude.json` ఖాతా మార్పిడి, మరియు క్రియాశీల-లేబుల్ కమిట్ అన్నీ ఒకే లాక్ చేసిన సెక్షన్ లోపల జరుగుతాయి.
- **claude యొక్క స్వంత రిఫ్రెష్‌తో ఇంటర్‌లాక్.** గడువు-సమీపంలో ఉన్న సెషన్ ఏ క్షణంలోనైనా తన స్వంత టోకెన్‌ను తిప్పగలదు, కాబట్టి క్రెడెన్షియల్ రైట్‌లు Claude Code యొక్క రిఫ్రెష్ లాక్‌ను కూడా తీసుకుంటాయి (బెస్ట్-ఎఫర్ట్, పాత-లాక్ తిరిగి పొందడం మరియు పరిమిత టైమ్‌అవుట్‌తో).
- **చనిపోయిన గ్రాంట్‌లు శుభ్రంగా తగ్గుతాయి.** `invalid_grant`గా తిరిగివచ్చే రిఫ్రెష్ ఆ ఖాతాను తిరిగి-ప్రామాణీకరణ అవసరమని ఫ్లాగ్ చేసి, లోపం వ్యాప్తి చెందే ముందు ఫ్లాగ్‌ను నిల్వ చేస్తుంది, తద్వారా పునఃప్రయత్న లూప్‌లు అభ్యర్థి సమూహాన్ని కుదించి ముగుస్తాయి. `tokenmaxxing auth` ఫ్లాగ్ చేసిన ఖాతాను యథాస్థానంలో సరిచేస్తుంది, మరియు రిపేర్ చేయబడుతున్న ఖాతా కంటే వేరే ఖాతాపై దిగే లాగిన్‌ను తిరస్కరిస్తుంది.
- **టోకెన్ లాగింగ్ లేదు.** టోకెన్‌లు లాగ్‌లు, లోపాలు, లేదా అవుట్‌పుట్‌లో ఎప్పుడూ కనిపించవు. టోకెన్ మరియు వినియోగ ఎండ్‌పాయింట్‌ల నుండి వచ్చే లోప బాడీలు ఎప్పుడూ ముడి రూపంలో బయటపెట్టబడవు; కేవలం అనుమతించబడిన ఫీల్డ్‌ల సమూహం మాత్రమే నిలుస్తుంది, ఎందుకంటే ఒక టోకెన్ ఎండ్‌పాయింట్ యొక్క వైఫల్య బాడీ అభ్యర్థన పదార్థాన్ని ప్రతిధ్వనించగలదు.
- **ప్రోబ్ పరిశుభ్రత.** స్పాన్ చేయబడిన ఏ `claude` ప్రోబ్ అయినా claude తన కీచైన్ లుకప్‌కు ముందు గౌరవించే ఎనిమిది ఎన్విరాన్‌మెంట్ వేరియబుల్‌లను (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, మొదలైనవి) శుభ్రం చేస్తుంది, తద్వారా ఒక ప్రోబ్ తప్పు ఖాతాకు ఎప్పుడూ ఆపాదించబడదు.
