tokenmaxxing - это единая точка входа с множественным вызовом (`src/main.ts`), которая ведёт себя как супервизор `claude`, когда вызывается под этим именем, обслуживает shim-ы хуков и statusline через внутренние подкоманды, а в остальных случаях диспетчеризует CLI. Он работает напрямую под Bun; npm-пакет поставляется как исходный код на TypeScript, а не как сборка.

Движущиеся части:

## Shim-супервизор

`init` записывает shell-shim из 2 строк с именем `claude` в `~/.config/tokenmaxxing/bin/` и ставит этот каталог первым в PATH. Когда вы вводите `claude`, shim запускает супервизор, который порождает настоящий бинарник claude с унаследованным stdio и сохранённым снимком терминала `stty -g`. Это только менеджер процессов и терминала: он никогда не проксирует трафик API и никогда не трогает токены в процессе передачи.

Вызовы в режиме печати (`claude -p`, `--version`, `--help`), неинтерактивные подкоманды (`claude mcp`, `claude config` и так далее) и собственные проверки tokenmaxxing проходят напрямую без управления сессией. Для интерактивной сессии супервизор фиксирует id сессии (генерируя новый или переиспользуя тот, что вы передали через `--session-id` / `-r` / `-c`), сохраняет ваши флаги запуска, чтобы более поздний перезапуск мог их воспроизвести, а затем следит за файлом-маркером перезапуска, привязанным к этой сессии.

## Ответвление statusline

Claude Code передаёт данные о лимитах (`rate_limits.five_hour` и `rate_limits.seven_day`) в stdin statusline на каждом ходу. tokenmaxxing владеет слотом statusline, поэтому его отрисовщик заодно служит бесплатным push-каналом данных об использовании: на каждом такте он ответвляет агрегированные окна плюс активную модель в `usage.json`. Лимиты по каждой модели не приходят в stdin statusline; они поступают только из `claude -p '/usage'` (бесплатно, ноль токенов), который опрашивается с TTL и кэшируется в `model-usage.json`, когда активная модель ограничена по ёмкости.

Ответвление работает по принципу записи при изменении: когда показатели не меняются, оно лишь обновляет mtime файла, что служит сигналом жизнеспособности канала. Свежесть всегда определяется по mtime, а не по встроенной временной метке.

## Хук Stop и переключение

На каждой границе хода хук Stop выполняет решение о переключении (см. [Как принимается решение о переключении](/ru/switching)). Когда переключение оправдано, оно происходит под эксклюзивной блокировкой `flock(2)` (взятой через `bun:ffi`, поскольку в macOS нет бинарника `flock(1)`), а запись учётных данных дополнительно взаимоблокируется с собственной блокировкой обновления Claude Code. Внутри критической секции одно переключение:

1. Собирает текущие активные учётные данные в припаркованную резервную копию их истинного владельца.
2. Устанавливает свежеобновлённые учётные данные целевого аккаунта в качестве активных, сливая их с существующим активным blob-ом, чтобы сопутствующее состояние (например, OAuth-токены для каждого сервера MCP) сохранилось. (Ротированный refresh-токен цели уже был сохранён в её собственную резервную копию в тот момент, когда обновление вернулось: под flock, но до этой критической секции с блокировкой обновления.)
3. Атомарно перезаписывает поле `oauthAccount` в `~/.claude.json`.
4. Фиксирует новую активную метку и очищает устаревшие снимки использования до снятия блокировки. Эти файлы невозможно записать атомарно все вместе, поэтому сбой может оставить промежуточное состояние. Следующее переключение определяет истинного владельца активных учётных данных независимо от метки и логирует любое обнаруженное расхождение.

Поскольку все сессии профиля по умолчанию используют одни активные учётные данные, единственное переключение мигрирует все сессии сразу, а flock плюс повторная проверка под блокировкой не дают конкурирующим хукам сжечь два аккаунта.

## Принятие на месте

Работающая сессия claude опрашивает своё хранилище учётных данных между запросами: на macOS она перечитывает keychain через короткий кэш и сравнивает access-токены; в Linux она проверяет mtime файла учётных данных и сбрасывает свои кэши токенов при изменении. В итоге подменённые учётные данные принимаются каждой работающей сессией примерно за 30 секунд на macOS и уже на следующем запросе в Linux, без всякого перезапуска. Именно поэтому обычное переключение не записывает маркер и не вызывает повторного порождения процесса - сессия просто продолжается на новом аккаунте. Внутрисессионный `/usage` использует те же кэши токенов, поэтому отображаемый им аккаунт меняется вместе с принятием.

## Ожидание при исчерпанном пуле и автовозобновление

Только когда каждый аккаунт в пуле превысил свои пороги, хук Stop записывает маркер перезапуска (схема маркера требует временную метку `waitUntil`; обычное переключение никогда не может её создать). Супервизор видит маркер, посылает SIGTERM своему дочернему процессу на уже зафиксированной границе хода (хук Stop выполняется после того, как транскрипт записан на диск и claude бездействует, поэтому ничего не теряется), восстанавливает терминал, показывает обратный отсчёт до ближайшего сброса, а затем перезапускает `claude --resume <session-id>` на восстановленном аккаунте. Ctrl-C во время обратного отсчёта возобновляет немедленно. Автоожидание ограничено `policy.maxWaitMs` (по умолчанию 1 час); сверх этого решение сообщает о пуле как об исчерпанном вместо ожидания.

## Таймер периодической проверки

Хуки срабатывают только на границах ходов, а один длинный агентский ход может сжечь окно от здорового до исчерпанного без единой границы. Поэтому `init` также устанавливает периодический таймер - агент launchd на macOS, пользовательский таймер systemd в Linux - который запускает `tokenmaxxing check --if-due` раз в такт (`policy.checkIntervalMs`, по умолчанию 60 секунд) независимо от активности ходов. Проверка сама задаёт себе темп исходя из запаса активного аккаунта: когда до каждого барьера ещё далеко, она выполняется раз в пять тактов, а вблизи барьера - на каждом такте (см. [Как принимается решение о переключении](/ru/switching)).

## Хук SessionStart

Запускает ту же оценку, когда сессия начинается или возобновляется, чтобы новая сессия стартовала на нужном аккаунте. Пауза после переключения делает его корректным no-op сразу после повторного порождения процесса.
