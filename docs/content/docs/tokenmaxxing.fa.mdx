tokenmaxxing یک CLI برای جابه‌جایی خودکار حساب Claude Code است. این ابزار چند حساب اشتراکی (Pro/Max) متعلق به خودتان را یکجا جمع می‌کند و هنگامی که حساب در حال استفاده به یک محدودیت مصرف نزدیک می‌شود، اعتبارنامه فعال را به‌صورت داغ به حسابی تازه‌تر جابه‌جا می‌کند. شما دقیقاً مثل همیشه `claude` را اجرا می‌کنید؛ جابه‌جایی در یک مرز امن نوبت رخ می‌دهد و نشست در حال اجرای شما همان گفتگو را روی حساب جدید بدون راه‌اندازی مجدد ادامه می‌دهد. این ابزار روی چندین نشست همزمان به‌طور یکجا کار می‌کند.

تنها رفتار قابل مشاهده، بدترین حالت است: وقتی کل استخر حساب‌ها به محدودیت خود رسیده باشد، نشست با یک شمارش معکوس متوقف می‌شود و روی نخستین حسابی که بازنشانی شود به‌طور خودکار از سر گرفته می‌شود (با Ctrl-C بلافاصله از سر گرفته می‌شود).

<Callout>
دامنه: Claude Code روی macOS و Linux، به‌علاوه Codex CLI شرکت OpenAI به‌عنوان یک استخر دوم و موازی. این ابزار حساب‌های اشتراکی را جمع می‌کند، نه کلیدهای API را. این ابزاری برای استفاده شخصی است، برای جمع کردن حساب‌هایی که خودتان مالک آن هستید، در نشست‌ها و عامل‌هایی که خودتان اجرا می‌کنید - به [استفاده شخصی و شرایط خدمات](#personal-use-and-terms-of-service) مراجعه کنید.
</Callout>

## مسئله

یک اشتراک Claude به‌طور همزمان سه محدودیت را اندازه‌گیری می‌کند (همه از طریق `/usage` تأیید شده‌اند):

- **نشست جاری**: یک پنجره غلتان ۵ ساعته.
- **هفته جاری (همه مدل‌ها)**: یک مجموع ۷ روزه.
- **هفته جاری، به‌ازای هر مدل**: سقف‌های هفتگی جداگانه برای خانواده‌های مدل مجزا. این‌ها در حال حاضر فقط برای Sonnet و Fable وجود دارند، و تنها سقف Fable آن‌قدر تنگ هست که اهمیت داشته باشد - این سقف خیلی پیش از آنکه مجموع کل مقید شود، مقید می‌شود. یک دستگاه می‌تواند در ۵۰٪ هفته-کل باشد در حالی که همزمان در ۸۰٪ هفته-Fable قرار دارد.

سهمیه هفتگی از نوع استفاده‌کن-وگرنه-از-دست-می‌رود است: هر مقدار که یک حساب تا زمان بازنشانی هفتگی ثابتش مصرف نکرده باشد از دست می‌رود. اگر مالک چند حساب باشید، راهبرد منطقی این است که سهمیه را روی هر حسابی که بیش از همه از سرعت هفتگی خودش عقب است بسوزانید، و پیش از آنکه هر محدودیت واحدی در میانه نشست به دیوار بخورد، از آن حساب جابه‌جا شوید.

انجام دستی این کار یعنی خروج از حساب، ورود دوباره، و از دست دادن گفتگویتان. tokenmaxxing این را خودکار می‌کند: یک `claude` در حال اجرا، مخزن اعتبارنامه خود را بین درخواست‌ها دوباره بررسی می‌کند، بنابراین اعتبارنامه‌ای که زیر آن جابه‌جا شده در همان جا پذیرفته می‌شود (در حدود ۳۰ ثانیه روی macOS، و در درخواست بعدی روی Linux). یک جابه‌جایی ساده هرگز نشست شما را راه‌اندازی مجدد نمی‌کند. تنها موردی که هنوز به مدیریت فرایند نیاز دارد، یک استخر کاملاً تهی است - یک نشست نمی‌تواند خودش را متوقف کند - و ناظر نازک دقیقاً برای همین وجود دارد.

هر چیز دیگری درباره `claude` بدون تغییر است: همه پرچم‌ها، سرورهای MCP، قلاب‌ها و مهارت‌ها بدون تغییر عبور می‌کنند.

## شروع سریع

به [Bun](https://bun.sh) و Claude Code نیاز دارد، روی macOS یا Linux.

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` پنج کار انجام می‌دهد:

1. حسابی را که هم‌اکنون با آن وارد شده‌اید به‌عنوان حساب شماره ۱ وارد می‌کند (فرمان جداگانه‌ای به نام `adopt` وجود ندارد).
2. شیم ناظر `claude` را نصب می‌کند.
3. سه ورودی را در `settings.json` مربوط به Claude Code نصب می‌کند: یک statusLine، یک قلاب Stop، و یک قلاب SessionStart (به‌علاوه یک ورودی subagentStatusLine).
4. دایرکتوری bin ناظر را به PATH در فایل rc پوسته شما اضافه می‌کند (خنثی نسبت به تکرار، با یک نظر `# tokenmaxxing PATH` علامت‌گذاری شده). این باید جلوتر از `claude` واقعی روی PATH قرار بگیرد تا آن را رهگیری کند.
5. یک زمان‌سنج بررسی دوره‌ای نصب می‌کند (یک عامل launchd روی macOS، یک زمان‌سنج کاربری systemd روی Linux) که هر ۱۸۰ ثانیه `tokenmaxxing check` را اجرا می‌کند.

پوسته خود را راه‌اندازی مجدد کنید، سپس حساب‌های بیشتری اضافه کنید و شروع کنید:

```sh
tokenmaxxing add        # یک حساب دیگر را به‌صورت ایزوله وارد می‌کند و آن را به استخر می‌افزاید
claude                  # مثل همیشه از claude استفاده کنید
```

`tokenmaxxing` با نام مستعار `xx` نیز در دسترس است. `tokenmaxxing` تنها (یا `xx`) فرمان `status` را اجرا می‌کند؛ `switch` صریح باقی می‌ماند.

## فرمان‌ها

| فرمان | چه کار می‌کند |
|---|---|
| `tokenmaxxing init` | وارد کردن حساب جاری، نصب ناظر، قلاب‌ها و statusline |
| `tokenmaxxing init --codex` | همان کار برای Codex: وارد کردن ورود به سیستم، نصب ناظر codex و قلاب Stop |
| `tokenmaxxing add` | ثبت یک حساب اضافی (ورود ایزوله، برداشت‌شده به داخل استخر) |
| `tokenmaxxing add --codex` | ثبت یک حساب Codex اضافی (ورود ایزوله) |
| `tokenmaxxing auth [sel \| --all]` | احراز هویت دوباره یک حساب استخرشده در همان جا. حالت تنها استخر را فهرست می‌کند و می‌پرسد کدام؛ یک انتخابگر یک حساب را هدف می‌گیرد و به شما می‌گوید با کدام ایمیل وارد شوید؛ `--all` تک‌تک هر حساب نیازمند احراز هویت مجدد را طی می‌کند |
| `tokenmaxxing switch [sel]` | جابه‌جایی به بهترین حساب (حریصانه، خنثی نسبت به تکرار) یا اجبار به یک حساب مشخص |
| `tokenmaxxing switch --codex [sel]` | جابه‌جایی استخر Codex (در راه‌اندازی بعدی codex اعمال می‌شود) |
| `tokenmaxxing ls` | فهرست حساب‌های استخرشده |
| `tokenmaxxing status` | حساب‌ها با نوارهای مصرف ۵ ساعته / هفتگی / به‌ازای هر مدل، فعال و تهی‌تا‌بازنشانی |
| `tokenmaxxing status --force` | افزون بر این، به هر حساب یک پینگ می‌زند (هر کدام یک درخواست کوچک haiku) تا همه زمان‌سنج‌های نشست ۵ ساعته همین حالا شروع شوند، سپس نمونه‌برداری تازه انجام می‌دهد |
| `tokenmaxxing watch [seconds]` | وضعیت زنده، هر N ثانیه دوباره ترسیم‌شده (پیش‌فرض ۱۲۰، کف ۳۰؛ هرگز پینگ نمی‌زند) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | پیکربندی مؤثر با منابع؛ ویرایش کلیدهای نقطه‌ای؛ `tidy` کلیدهای ناشناخته را هرس می‌کند |
| `tokenmaxxing check` | یک‌بار ارزیابی تصمیم جابه‌جایی (این همان چیزی است که زمان‌سنج دوره‌ای اجرا می‌کند) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | شبح پل Slack (حالت Socket، بدون URL عمومی) |
| `tokenmaxxing doctor` | تأیید اینکه ناظر و ورودی‌های تنظیمات باقی مانده‌اند |
| `tokenmaxxing rename [--codex] <sel> <label>` | تغییر برچسب یک حساب استخرشده |
| `tokenmaxxing rm <sel>` | حذف یک حساب از استخر |
| `tokenmaxxing uninstall` | حذف ناظر و ورودی‌های تنظیمات (حساب‌ها و اعتبارنامه‌ها نگه داشته می‌شوند) |

## معماری

tokenmaxxing یک نقطه ورود چند-فراخوانی (`src/main.ts`) است که وقتی با آن نام فراخوانی شود مانند ناظر `claude` رفتار می‌کند، شیم‌های قلاب و statusline را از طریق زیرفرمان‌های داخلی سرویس می‌دهد، و در غیر این صورت CLI را ارجاع می‌دهد. این ابزار مستقیماً زیر Bun اجرا می‌شود؛ بسته npm کد منبع TypeScript را عرضه می‌کند، نه یک ساخت را.

بخش‌های متحرک:

### شیم ناظر

`init` یک شیم پوسته ۲ خطی با نام `claude` را در `~/.config/tokenmaxxing/bin/` می‌نویسد و آن دایرکتوری را نخست در PATH قرار می‌دهد. وقتی `claude` را تایپ می‌کنید، شیم ناظر را اجرا می‌کند که باینری claude واقعی را با stdio به‌ارث‌رسیده و یک عکس فوری ذخیره‌شده `stty -g` از پایانه فرا می‌خواند. این تنها یک مدیر فرایند و پایانه است: هرگز ترافیک API را واسطه نمی‌کند و هرگز توکن‌های در حال انتقال را دست نمی‌زند.

فراخوانی‌های حالت چاپ (`claude -p`، `--version`، `--help`)، زیرفرمان‌های غیرتعاملی (`claude mcp`، `claude config` و مانند آن)، و کاوش‌های خود tokenmaxxing بدون هیچ مدیریت نشستی مستقیم عبور می‌کنند. برای یک نشست تعاملی، ناظر یک شناسه نشست را پین می‌کند (یکی تولید می‌کند، یا همانی را که از طریق `--session-id` / `-r` / `-c` پاس داده‌اید دوباره استفاده می‌کند)، پرچم‌های راه‌اندازی شما را پایدار می‌کند تا یک راه‌اندازی مجدد بعدی بتواند آن‌ها را بازپخش کند، و سپس مراقب یک فایل نشانگر بازآفرینی مرتبط با آن نشست می‌ماند.

### شاخه statusline

Claude Code داده محدودیت نرخ (`rate_limits.five_hour` و `rate_limits.seven_day`) را در هر نوبت به داخل stdin مربوط به statusline می‌فرستد. tokenmaxxing مالک جایگاه statusline است، بنابراین ترسیم‌کننده آن به‌عنوان یک خوراک مصرف رایگان و مبتنی بر ارسال نیز عمل می‌کند: در هر ضربان، پنجره‌های مجموع به‌علاوه مدل فعال را به داخل `usage.json` شاخه می‌زند. سقف‌های به‌ازای هر مدل در stdin مربوط به statusline نیستند؛ آن‌ها فقط از `claude -p '/usage'` می‌آیند (رایگان، صفر توکن)، که با یک TTL پیمایش می‌شود و وقتی مدل فعال از نظر ظرفیت محدود است در `model-usage.json` نهانی می‌شود.

شاخه از نوع نوشتن-هنگام-تغییر است: وقتی ارقام بدون تغییر باشند فقط mtime فایل را بالا می‌برد، که به‌عنوان ضربان زنده‌بودن خوراک عمل می‌کند. تازگی همیشه بر پایه mtime سنجیده می‌شود، نه بر پایه برچسب زمانی تعبیه‌شده.

### قلاب Stop و جابه‌جایی

در هر مرز نوبت، قلاب Stop تصمیم جابه‌جایی را اجرا می‌کند (به [چگونگی تصمیم‌گیری برای جابه‌جایی](#how-switching-decides) مراجعه کنید). وقتی یک جابه‌جایی موجه باشد، زیر یک قفل انحصاری `flock(2)` رخ می‌دهد (که از طریق `bun:ffi` گرفته می‌شود، چون macOS هیچ باینری `flock(1)` عرضه نمی‌کند)، و نوشتن اعتبارنامه‌ها افزون بر این با قفل نوسازی خود Claude Code هم‌قفل می‌شود. درون بخش بحرانی، یک جابه‌جایی:

1. اعتبارنامه زنده جاری را به پشتیبان پارک‌شده مالک واقعی‌اش برداشت می‌کند.
2. اعتبارنامه تازه نوسازی‌شده حساب هدف را به‌عنوان اعتبارنامه زنده نصب می‌کند و آن را در قطعه زنده موجود ادغام می‌کند تا وضعیت هم‌نوع (مانند توکن‌های OAuth به‌ازای هر سرور MCP) باقی بماند.
3. توکن چرخانده‌شده هدف را در پشتیبان خودش پایدار می‌کند.
4. به‌صورت اتمی فیلد `oauthAccount` را در `~/.claude.json` بازنویسی می‌کند.
5. برچسب فعال جدید را ثبت می‌کند و عکس‌های فوری کهنه مصرف را پاک می‌کند، همه پیش از آنکه قفل آزاد شود، تا یک فروپاشی هرگز نتواند اعتبارنامه نصب‌شده و برچسب فعال را به دو حساب متفاوت اشاره‌کننده باقی بگذارد.

چون همه نشست‌های نمایه پیش‌فرض همان یک اعتبارنامه زنده را به اشتراک می‌گذارند، یک جابه‌جایی واحد هر نشست را یکجا کوچ می‌دهد، و flock به‌علاوه یک بررسی دوباره زیر قفل، از سوزاندن دو حساب توسط قلاب‌های در حال رقابت جلوگیری می‌کند.

### پذیرش در همان جا

یک نشست claude در حال اجرا، مخزن اعتبارنامه خود را بین درخواست‌ها پیمایش می‌کند: روی macOS keychain را از طریق یک نهان کوتاه دوباره می‌خواند و توکن‌های دسترسی را مقایسه می‌کند؛ روی Linux مقدار mtime فایل اعتبارنامه‌ها را می‌سنجد و نهان‌های توکن خود را هنگام تغییر پاکسازی می‌کند. اثر خالص این است که یک اعتبارنامه جابه‌جاشده توسط هر نشست در حال اجرا در حدود ۳۰ ثانیه روی macOS و در همان درخواست بعدی روی Linux پذیرفته می‌شود، بدون هیچ راه‌اندازی مجدد. به همین دلیل است که یک جابه‌جایی ساده هیچ نشانگری نمی‌نویسد و هیچ بازآفرینی‌ای را برنمی‌انگیزد - نشست فقط روی حساب جدید ادامه می‌دهد. `/usage` درون‌نشست همان نهان‌های توکن را به اشتراک می‌گذارد، بنابراین نمایش حساب آن همراه با پذیرش تغییر می‌کند.

### انتظار استخر تهی و از سر گرفتن خودکار

تنها زمانی که هر حساب در استخر بالای نوارهایش باشد، قلاب Stop یک نشانگر بازآفرینی می‌نویسد (شمای نشانگر به یک برچسب زمانی `waitUntil` نیاز دارد؛ یک جابه‌جایی ساده هرگز نمی‌تواند چنین چیزی تولید کند). ناظر نشانگر را می‌بیند، در مرز نوبت از پیش ثبت‌شده به فرزندش SIGTERM می‌دهد (قلاب Stop پس از آنکه رونوشت روی دیسک است و claude بیکار است اجرا می‌شود، بنابراین چیزی از دست نمی‌رود)، پایانه را بازیابی می‌کند، یک شمارش معکوس تا نزدیک‌ترین بازنشانی نشان می‌دهد، و سپس `claude --resume <session-id>` را روی حساب بازیابی‌شده دوباره راه‌اندازی می‌کند. Ctrl-C در حین شمارش معکوس بلافاصله از سر می‌گیرد. انتظار خودکار با `policy.maxWaitMs` (پیش‌فرض ۱ ساعت) محدود می‌شود؛ فراتر از آن، تصمیم به‌جای انتظار، استخر را به‌عنوان تهی گزارش می‌دهد.

### زمان‌سنج بررسی دوره‌ای

قلاب‌ها فقط در مرزهای نوبت شلیک می‌شوند، و یک نوبت عاملی طولانی می‌تواند بدون یک مرز واحد، یک پنجره را از سالم به تهی بسوزاند. بنابراین `init` یک زمان‌سنج دوره‌ای هم نصب می‌کند - یک عامل launchd روی macOS، یک زمان‌سنج کاربری systemd روی Linux - که بدون توجه به فعالیت نوبت، هر ۱۸۰ ثانیه `tokenmaxxing check` را اجرا می‌کند.

### یک قلاب SessionStart

همان ارزیابی را وقتی یک نشست شروع می‌شود یا از سر گرفته می‌شود اجرا می‌کند، تا یک نشست تازه روی حساب درست آغاز شود. دوره خنک‌شدن پس از جابه‌جایی سبب می‌شود که این قلاب درست پس از یک بازآفرینی یک بی‌عمل درست باشد.

## چگونگی تصمیم‌گیری برای جابه‌جایی [#how-switching-decides]

تصمیم دو لایه دارد: یک دروازه درگیرشدن، و سپس یک مسیر حریصانه یا سخت.

### درگیرشدن

زیر `policy.greedySessionFloor` (پیش‌فرض ۵۰، بر حسب درصد پنجره نشست ۵ ساعته)، تصمیم اصلاً اجرا نمی‌شود - یک نشست تازه روی حساب خود سوار می‌ماند. به‌محض آنکه پنجره نشست فعال ۵۰٪ استفاده شد، یا هر نوار سختی رد شد، تصمیم درگیر می‌شود.

### نوارهای غربالگری

آستانه‌ها نوارهای غربالگری هستند، نه ماشه وحشت:

- `thresholds.session`: ۹۵. نشستن روی یک بازنشانی ۵ ساعته ارزان است، بنابراین پنجره نشست زودتر جابه‌جا می‌شود.
- `thresholds.weekly`: ۹۸. این یک نوار هم مجموع ۷ روزه و هم هر سقف هفتگی به‌ازای هر مدل را پوشش می‌دهد. سهمیه هفتگی از نوع استفاده‌کن-وگرنه-از-دست-می‌رود است، بنابراین نزدیک به دیوار تخلیه می‌شود.

هر دو به‌عمد زیر ۱۰۰ هستند: این فضای آزاد بودجه‌ای است برای رسیدن به یک مرز نوبت تمیز (به‌علاوه تا یک نوبت تأخیر پذیرش روی macOS) پیش از آنکه حساب واقعاً به محدودیتش برسد. همان نوارها نامزدهای جابه‌جایی را غربال می‌کنند: یک حساب بالای هر یک از نوارهایش یک هدف معتبر نیست. ماشه و غربالگری همیشه از همان نوارهای مؤثر استفاده می‌کنند (آستانه‌ها منهای `policy.projectionMargin`)، چون یک غربال سست‌تر از ماشه، جابه‌جایی‌ها را روی حساب‌هایی می‌نشاند که ماشه بلافاصله دوباره آن‌ها را علامت‌گذاری می‌کند و استخر را پینگ‌پونگ می‌کند.

### هدف: فشار سرعت

در میان حساب‌های قابل استفاده، هدف حسابی است که بیش از همه از سرعت هفتگی خودش عقب است: بالاترین **فشار سرعت**، که به‌صورت درصد هفتگی باقی‌مانده تقسیم بر زمان تا بازنشانی هفتگی آن حساب تعریف می‌شود. حسابی که بیشترین سهمیه در شرف از دست رفتن را دارد برنده می‌شود. در حالت تساوی، ابتدا نزدیک‌ترین انقضای هفتگی و سپس کمترین مصرف ۷ روزه ملاک است.

همه چیز از پنجره‌های نهانی‌شده ذخیره‌شده به‌صورت اپوک‌های مطلق UTC اجرا می‌شود، بنابراین یک عکس فوری کهنه هم به‌درستی حل می‌شود: یک بازنشانی هفتگی که گذشته باشد در گام‌های دقیق ۷ روزه رو به جلو برون‌یابی می‌شود، و هر پنجره‌ای که از بازنشانی نهانی‌شده‌اش گذشته باشد به‌عنوان تازه تهی به‌شمار می‌آید (هرگز دلیلی برای جابه‌جایی، هرگز دلیلی برای نگه داشتن یک حساب روی نیمکت نیست).

### مسیر حریصانه در برابر مسیر سخت

- **مسیر حریصانه** (درگیر، اما زیر هر نوار): هر حساب، از جمله حساب جاری، را رتبه‌بندی کن. اگر حساب جاری از پیش برنده است یا تساوی دارد، هیچ کاری نکن. در غیر این صورت به حسابی که به‌طور اکید بهتر است جابه‌جا شو. این مسیر هرگز منتظر نمی‌ماند و هرگز از پیش پارک نمی‌کند - یک حساب جاری قابل استفاده با یک انتظار مبادله نمی‌شود. چون حساب جاری هم رتبه‌بندی می‌شود، هم مسیر خودکار و هم `tokenmaxxing switch` تنها خنثی نسبت به تکرار هستند: ارزیابی دوره‌ای روی حساب درست همگرا می‌شود و سپس در جای خود می‌ماند.
- **مسیر سخت** (یک نوار رد شد): به بهترین نامزد قابل استفاده جابه‌جا شو. اگر معلوم شود توکن نوسازی یک نامزد مرده است، آن به‌عنوان نیازمند احراز هویت مجدد علامت‌گذاری می‌شود و نامزد بعدی امتحان می‌شود. اگر هیچ چیز قابل استفاده نباشد، منطق انتظار-تهی اجرا می‌شود؛ تنها فراخواننده‌ای که واقعاً می‌تواند نشست را متوقف کند (قلاب Stop تحت نظارت) مجاز است روی حسابی که هنوز مسدود اما زودترین در حال بازیابی است از پیش پارک کند.

### سقف‌های به‌ازای هر مدل

`policy.switchModels` (پیش‌فرض `["fable"]`) خانواده‌های مدلی را نام می‌برد که سقف هفتگی به‌ازای هر مدلشان می‌تواند یک جابه‌جایی را برانگیزد. تطبیق بر پایه نشانه خانواده است، هرگز بر پایه رشته نمایشی دقیق: نام‌های نمایشی مدل جابه‌جا می‌شوند ("Fable" به "Fable 5" تبدیل شد)، و یک دروازه رشته-دقیق یک‌بار به‌طور خاموش جابه‌جایی به‌ازای هر مدل را کاملاً غیرفعال کرد. دو قاعده ایمنی مرتبط:

- یک مدل فعال ناشناخته هر خانواده پیکربندی‌شده را دروازه‌بندی می‌کند. درست پس از آنکه یک جابه‌جایی عکس‌های فوری را پاک می‌کند، یک دستگاه بی‌کله می‌تواند مدل-کور اجرا شود؛ رفتار با ناشناخته به‌عنوان نامحدود یک‌بار سبب شد یک حساب ساعت‌ها بدون توجه روی سقف Fable خود بنشیند.
- غربالگری نامزد، سقف‌های دروازه‌بندی‌شده به‌ازای هر مدل را هم به‌شمار می‌آورد، بنابراین استخری که هر حسابش سقف Fable خود را سوزانده باشد به‌صورت نوبتی نمی‌چرخد.

### دوره خنک‌شدن

یک دوره خنک‌شدن ۴۵ ثانیه‌ای پس از جابه‌جایی مسیر خودکار را دروازه‌بندی می‌کند. شاخه statusline برای همان ۴۵ ثانیه پس از یک جابه‌جایی سرکوب می‌شود (پذیرش روی macOS تا ۳۰ ثانیه طول می‌کشد)، بنابراین یک ارزیابی زودتر روی داده‌ای اجرا می‌شد که خود جابه‌جایی آن را نامعتبر کرده - همان سناریوی دقیق یک‌بار یک حلقه بازآفرینی A-به-B-و-برگشت تولید کرد. `tokenmaxxing switch` دستی از دوره خنک‌شدن متأثر نیست.

## پیکربندی

پیکربندی به‌صورت JSON در `~/.config/tokenmaxxing/config.json` است. هر فیلد اختیاری است؛ پیش‌فرض‌ها به‌ازای هر فیلد اعمال می‌شوند.

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: نوارهای غربالگری توصیف‌شده در بالا.
- `policy.projectionMargin`: از هر دو نوار کم می‌شود تا نوارهای مؤثر شکل بگیرند.
- `policy.greedySessionFloor`: درصد استفاده نشست که در آن همگرایی حریصانه درگیر می‌شود.
- `policy.switchModels`: خانواده‌های مدلی که سقف هفتگی به‌ازای هر مدلشان یک جابه‌جایی را دروازه‌بندی می‌کند (ورودی‌ها هنگام بارگذاری کوچک‌حروف می‌شوند).
- `policy.usagePollTtlMs`: مدت زمانی که یک پیمایش `/usage` به‌ازای هر مدل تازه می‌ماند.
- `policy.maxWaitMs`: مرز انتظار خودکار استخر تهی.

`tokenmaxxing config` پیکربندی مؤثر را با منابع نشان می‌دهد؛ `config set`/`unset` کلیدهای نقطه‌ای را ویرایش می‌کنند؛ `config tidy` کلیدهای ناشناخته را هرس می‌کند.

## چیدمان دایرکتوری وضعیت

همه چیز زیر `~/.config/tokenmaxxing/` زندگی می‌کند (قابل بازنویسی با `TOKENMAXXING_HOME`؛ هر مسیر قابل مشاهده از بیرون یک بازنویسی محیطی دارد تا کل ابزار بتواند به‌صورت محصور در تست‌ها اجرا شود).

| مسیر | چه نگه می‌دارد |
|---|---|
| `config.json` | پیکربندی شما (پراکنده؛ پیش‌فرض‌ها به‌ازای هر فیلد اعمال می‌شوند) |
| `accounts.json` | نمایه غیرمحرمانه حساب‌های استخرشده Claude: برچسب‌ها، شناسه‌ها، پنجره‌های مصرف نهانی‌شده. هرگز توکن‌ها |
| `usage.json` | عکس فوری پنجره مجموع مربوط به شاخه statusline؛ mtime آن ضربان زنده‌بودن خوراک است |
| `model-usage.json` | سقف‌های هفتگی به‌ازای هر مدل نهانی‌شده با TTL از `/usage` |
| `lastswap.json` | برچسب زمانی اپوک آخرین جابه‌جایی؛ دوره خنک‌شدن ۴۵ ثانیه‌ای را هدایت می‌کند |
| `lock` | فایل `flock` که جابه‌جایی‌ها را ترتیبی‌سازی می‌کند |
| `tokenmaxxing.log` | گزارش رویداد فقط-افزودنی |
| `bin/` | شیم‌های PATH: `claude`، `codex`، و نقاط ورود `tokenmaxxing` / `xx` |
| `respawn/<session-id>` | نشانگرهای بازآفرینی انتظار-تهی که ناظر مراقب آن‌هاست |
| `creds/` | فقط Linux: فایل‌های اعتبارنامه پارک‌شده، ۰۶۰۰ در یک دایرکتوری ۰۷۰۰ (در macOS به‌جای آن، اعتبارنامه‌ها به‌عنوان اقلام keychain به‌ازای هر حساب پارک می‌شوند) |
| `onboard/`، `sample/` | خانه‌های پیکربندی ایزوله یک‌بارمصرف برای ورودهای `add`/`auth` و کاوش‌های `/usage` حساب‌های پارک‌شده؛ خانه‌های onboard که اعتبارنامه‌های متن ساده را نگه می‌دارند پس از برداشت حذف می‌شوند |
| `slack.json` | توکن‌ها و پیوندهای کانال `xx serve` (۰۶۰۰) |
| `slack-threads/` | رکوردهای نشست به‌ازای هر رشته برای `xx serve` |
| `codex-*` | استخر موازی Codex: `codex-accounts.json`، `codex-lastswap.json`، `codex-lock`، `codex-creds/`، `codex-onboard/`، `codex-respawn/`، و `codex-live/` (یک فایل حضور اعتبارسنجی‌شده با PID به‌ازای هر نشست codex تحت نظارت در حال اجرا، بنابراین یک حساب زنده هرگز یک هدف جابه‌جایی نیست) |

بیرون از دایرکتوری خودش، tokenmaxxing دقیقاً این‌ها را دست می‌زند: `~/.claude.json` (جابه‌جایی `oauthAccount`)، `settings.json` مربوط به Claude Code (ورودی‌های قلاب و statusline)، مخزن اعتبارنامه زنده (قلم keychain با نام `Claude Code-credentials` روی macOS، `.credentials.json` روی Linux)، `~/.claude.lock` (قفل نوسازی claude که در حین جابه‌جایی‌ها گرفته می‌شود)، `auth.json` و `hooks.json` مربوط به codex، و واحد بررسی دوره‌ای در launchd یا systemd.

## مخزن اعتبارنامه و مدل ایمنی

همه وضعیت در `~/.config/tokenmaxxing/` زندگی می‌کند. ورودی/خروجی اعتبارنامه از یک نمای مخزن انتخاب‌شده بر پایه سکو عبور می‌کند؛ نقاط فراخوانی هرگز بر پایه سکو شاخه نمی‌شوند.

**macOS**: اعتبارنامه‌ها در keychain ورود به‌عنوان اقلام generic-password زندگی می‌کنند، مطابق همان جایی که خود Claude Code آن‌ها را نگه می‌دارد. قلم زنده همان چیزی است که claude می‌خواند؛ پشتیبان هر حساب استخرشده به‌عنوان قلم keychain مخصوص خودش با نام `tokenmaxxing-cred-<uuid8>` پارک می‌شود. چیزی روی دیسک به‌صورت متن ساده نیست. خواندن‌ها از `security find-generic-password -w` استفاده می‌کنند (راز فقط روی stdout ظاهر می‌شود)؛ نوشتن‌ها یک خط `add-generic-password` را به داخل `security -i` روی stdin می‌ریزند تا راز هرگز در argv هیچ فرایندی ظاهر نشود. حالت تعاملی یک بافر خط تقریباً ۴ کیلوبایتی دارد، بنابراین قطعه‌های بیش از حد بزرگ به یک نوشتن argv بازمی‌گردند - یک دلیل اینکه اقلام پارک‌شده فقط شیء OAuth کمینه را ذخیره می‌کنند.

**Linux**: Claude Code اعتبارنامه‌ها را به‌عنوان یک فایل متن ساده ۰۶۰۰ ذخیره می‌کند، و tokenmaxxing همان مدل را دنبال می‌کند: فایل زنده همان `.credentials.json` خود claude است، و پشتیبان‌های پارک‌شده فایل‌های اتمی ۰۶۰۰ زیر `~/.config/tokenmaxxing/creds/` در یک دایرکتوری ۰۷۰۰ هستند. اتمی در اینجا یعنی نوشتن-در-موقت، fsync، سپس تغییر نام: یک خواننده همزمان همیشه یا کل فایل قدیمی یا کل فایل جدید را می‌بیند، هرگز یک فایل ناقص را نمی‌بیند.

قاعده‌های ایمنی که جابه‌جایی اعمال می‌کند:

- **برداشت توسط مالک واقعی.** پیش از یک جابه‌جایی، مالک واقعی اعتبارنامه زنده با پرسیدن از API که توکن به کدام سازمان تعلق دارد حل می‌شود (`fetchTokenOrg` در برابر نقطه پایانی roles از OAuth) - هرگز با اعتماد به برچسب فعال ذخیره‌شده که می‌تواند جابه‌جا شود. یک برچسب جابه‌جاشده یک‌بار سبب شد برداشت یک حساب تنها پشتیبان حساب دیگری را بازنویسی کند. اگر اعتبارنامه زنده به حسابی خارج از استخر تعلق داشته باشد، جابه‌جایی به‌جای درهم‌کوبیدن آن، یکسره امتناع می‌کند.
- **یک بخش بحرانی.** برداشت، نصب اعتبارنامه جدید، پشتیبان‌گیری از توکن چرخانده‌شده آن، جابه‌جایی حساب `~/.claude.json`، و ثبت برچسب فعال، همه درون همان بخش قفل‌شده رخ می‌دهند.
- **هم‌قفلی با نوسازی خود claude.** یک نشست نزدیک به انقضا می‌تواند در هر لحظه توکن خودش را بچرخاند، بنابراین نوشتن اعتبارنامه‌ها قفل نوسازی Claude Code را هم می‌گیرد (به‌بهترین شکل ممکن، با بازپس‌گیری قفل کهنه و یک زمان‌سنج محدود).
- **اعطاهای مرده به‌تمیزی افت می‌کنند.** یک نوسازی که با `invalid_grant` بازمی‌گردد آن حساب را به‌عنوان نیازمند احراز هویت مجدد علامت‌گذاری می‌کند و پیش از انتشار خطا این علامت را پایدار می‌کند، بنابراین حلقه‌های تلاش مجدد مجموعه نامزدها را کوچک کرده و پایان می‌یابند. `tokenmaxxing auth` یک حساب علامت‌گذاری‌شده را در همان جا تعمیر می‌کند، و یک ورود را که روی حسابی متفاوت از حساب در حال تعمیر بنشیند امتناع می‌کند.
- **بدون ثبت توکن.** توکن‌ها هرگز در گزارش‌ها، خطاها یا خروجی ظاهر نمی‌شوند. بدنه‌های خطا از نقاط پایانی توکن و مصرف هرگز خام نمایش داده نمی‌شوند؛ فقط یک مجموعه مجاز از فیلدها باقی می‌ماند، چون بدنه شکست یک نقطه پایانی توکن می‌تواند مواد درخواست را بازتاب دهد.
- **بهداشت کاوش.** هر کاوش `claude` فراخوانده‌شده هشت متغیر محیطی را که claude پیش از جستجوی keychain خود محترم می‌شمارد پاکسازی می‌کند (`ANTHROPIC_API_KEY`، `CLAUDE_CODE_OAUTH_TOKEN`، `CLAUDE_SECURESTORAGE_CONFIG_DIR` و مانند آن)، بنابراین یک کاوش هرگز نمی‌تواند به حساب اشتباه نسبت داده شود.

## یادداشت‌های سکو: macOS در برابر Linux

| | macOS | Linux |
|---|---|---|
| اعتبارنامه زنده | قلم generic-password در keychain ورود | فایل `.credentials.json` با مجوز ۰۶۰۰ |
| اعتبارنامه‌های پارک‌شده | اقلام keychain به‌ازای هر حساب | فایل‌های ۰۶۰۰ در یک دایرکتوری ۰۷۰۰ |
| پذیرش پس از یک جابه‌جایی | در حدود ۳۰ ثانیه (نهان خواندن keychain) | درخواست بعدی (پیمایش mtime فایل) |
| بررسی دوره‌ای | عامل launchd، هر ۱۸۰ ثانیه | زمان‌سنج کاربری systemd، هر ۱۸۰ ثانیه |
| مخزن ورود ایزوله | سرویس keychain با فضای نام درهم‌سازی‌شده به‌ازای هر دایرکتوری پیکربندی | یک فایل درون دایرکتوری پیکربندی ایزوله |

دو جزئیات مخصوص Linux که دانستنشان می‌ارزد: claude دایرکتوری اعتبارنامه‌اش را نخست از `CLAUDE_SECURESTORAGE_CONFIG_DIR` حل می‌کند (سپس `CLAUDE_CONFIG_DIR`، سپس `~/.claude`)، و tokenmaxxing دقیقاً همان حل را بازتاب می‌دهد تا این دو هرگز از هم واگرا نشوند. و دو ساخت سیستم‌عاملی از یک نسخه واحد claude ساعت‌های بازنشانی `/usage` را متفاوت قالب‌بندی می‌کنند (یکی از چسب " at " استفاده می‌کند، دیگری از ویرگول)؛ تجزیه‌کننده tokenmaxxing دقیقاً همان دو شکل را می‌پذیرد و در هر شکل سومی، به‌جای حدس زدن، گزارش می‌دهد.

روی macOS، یک محدودیت صادقانه: `init` و `add` به‌عمد به‌صورت تعاملی keychain را دست می‌زنند، تا نخستین دسترسی `security` درون یک قلاب بی‌کله سرد نباشد.

## statusline

tokenmaxxing statusline مربوط به Claude Code را به‌صورت بومی ترسیم می‌کند (در حالی که خوراک مصرف را شاخه می‌زند). اصل طراحی: سهمیه در رنگ حمل می‌شود، نه در اعداد. یک خط، برای نمونه:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- هر نشانه پنجره، زمان-تا-بازنشانی آن است که روی یک شیب پیوسته سبز-به-زرد-به-قرمز بر پایه درصد استفاده رنگ می‌شود (رنگ واقعی وقتی پایانه پشتیبانی کند، در غیر این صورت گام‌به‌گام روی مکعب ۲۵۶ رنگ). شیب در سبز خالص برای ۰، زرد در ۷۵، و قرمز در ۹۵ و بالاتر لنگر می‌گیرد، بنابراین باندهای شدت قدیمی به‌عنوان لنگرهای شیب باقی می‌مانند.
- نام مدل بر پایه پرشدگی پنجره متن روی همان شیب رنگ می‌شود.
- یک `◆` سبز پیشاپیش پنجره‌های حساب فعال می‌آید؛ هر حساب پارک‌شده `◇` فیروزه‌ای مخصوص خودش را می‌گیرد (`✗` قرمز اگر نیاز به احراز هویت مجدد داشته باشد). حساب‌ها بر پایه زودترین بازنشانی پیش‌رو مرتب می‌شوند.
- به‌ازای هر مدل نخست در هر بلوک به‌عنوان یک حرف اول رنگ‌شده لخت می‌آید: Fable به‌صورت `𝒇` ترسیم می‌شود؛ خانواده‌های دیگر از حرف اول بزرگ‌شده خود استفاده می‌کنند، همیشه با تطبیق خانواده.
- یک حساب پارک‌شده دست‌نخورده یک `full` سبز ترسیم می‌کند. مصرف اندازه‌گیری‌شده با بازنشانی ناشناخته یک `?` رنگ‌شده ترسیم می‌کند، و یک سقف اندازه‌گیری‌نشده به‌ازای هر مدل روی یک مدل دروازه‌بندی‌شده یک `𝒇?` بی‌رنگ ترسیم می‌کند - اندازه‌گیری‌نشده هرگز نباید امن به‌نظر برسد.
- شمارش‌های معکوس بازنشانی فقط بزرگ‌ترین واحد را نشان می‌دهند، هرگز "now" یا "0m" را؛ یک پنجره بدون بازنشانی پیش‌رو یک `0` سبز ترسیم می‌کند (دوباره تهی).
- نام پایه یک درخت کاری git پیوندشده پیشاپیش خط می‌آید؛ یک برداشت اصلی چیزی آنجا ترسیم نمی‌کند. تشخیص، سیستم فایل را برای یک فایل `.git` می‌خواند و هرگز یک زیرفرایند git فرا نمی‌خواند.
- با تنظیم `NO_COLOR`، خط به یک قالب عددی چسبیده بازمی‌گردد (`2h5` یعنی در ۲ ساعت بازنشانی می‌شود، ۵٪ استفاده‌شده؛ `ctx 42` برای پرشدگی متن) - بدون رنگ، یک پنجره تخلیه‌شده نباید تازه به‌نظر برسد.

نوبت‌های زیرعامل ردیف‌های پنل مخصوص خود را از طریق سطح subagentStatusLine مربوط به claude می‌گیرند: یک ردیف به‌ازای هر نوبت فعال، نام خانواده بر پایه پرشدگی متن آن نوبت رنگ‌شده.

## پشتیبانی Codex

همان جمع کردن استخر برای Codex CLI شرکت OpenAI، در برابر حساب‌های اشتراک ChatGPT متعلق به خودتان کار می‌کند:

```sh
tokenmaxxing init --codex   # وارد کردن ورود codex جاری شما + نصب ناظر codex و قلاب Stop
tokenmaxxing add --codex    # ورود یک حساب دیگر، ایزوله - ورود اصلی شما دست‌نخورده می‌ماند
codex                       # مثل همیشه از codex استفاده کنید
```

استخر Codex وضعیت کاملاً موازی است: نمایه حساب‌های خودش، فایل‌های اعتبارنامه پارک‌شده خودش (فایل‌های ۰۶۰۰ روی هر دو سکو، چون مخزن خود codex یک فایل متن ساده است)، قفل خودش، برچسب زمانی آخرین جابه‌جایی خودش. چیزی جز کد سیاست تصمیم با استخر Claude به اشتراک گذاشته نمی‌شود.

### چرا جابه‌جایی داغ روی Codex ناممکن است

یک فرایند codex در حال اجرا یک مدیر احراز هویت درون‌حافظه‌ای را نگه می‌دارد و به‌صراحت از نوسازی مجدد `auth.json` وقتی اکنون یک حساب متفاوت را نام می‌برد امتناع می‌کند. هیچ ناظر فایل و هیچ پیمایش اعتبارنامه به‌ازای هر درخواست وجود ندارد، بنابراین اعتبارنامه‌ای که زیر یک codex در حال اجرا جابه‌جا شده به‌سادگی هرگز برای استنتاج اعمال نمی‌شود. راه‌اندازی مجدد همان جابه‌جایی است: `codex resume <session-id>` رونوشت محلی را روی هر حسابی که `auth.json` اکنون نگه می‌دارد ادامه می‌دهد.

tokenmaxxing این را با یک شیم ناظر codex مدیریت می‌کند: قلاب Stop همان تصمیم حریصانه فشار سرعت را در هر مرز نوبت اجرا می‌کند، و وقتی جابه‌جا می‌شود، یک نشانگر می‌نویسد که سبب می‌شود ناظر در مرز ثبت‌شده به نشست SIGTERM بدهد و `codex resume <session-id>` را روی حساب تازه دوباره راه‌اندازی کند، با رونوشت دست‌نخورده. چون هر جابه‌جایی codex یک راه‌اندازی مجدد قابل مشاهده است، مسیر حریصانه codex یک حاشیه بهبود ۱.۲ برابری دارد: یک رقیب باید فشار سرعت حساب جاری را با ۲۰٪ شکست دهد، نه با یک مو. مسیر سخت (یک نوار رد‌شده) این حاشیه را نادیده می‌گیرد. همچنین هیچ شمارش معکوس استخر تهی برای codex وجود ندارد - چیزی نمی‌تواند یک نشست codex را متوقف کند - بنابراین یک استخر codex کاملاً تهی در جای خود می‌ماند.

سازوکارهای دیگر مخصوص codex:

- مصرف از یک GET احراز هویت‌شده رایگان در برابر نقطه پایانی محدودیت نرخ خود codex خوانده می‌شود (همان فراخوانی که `/status` مربوط به CLI انجام می‌دهد): درصدها به‌علاوه زمان‌های بازنشانی اپوک مطلق، هم پنجره‌های مجموع و هم سقف‌های به‌ازای هر مدل. دسته‌بندی پنجره بر پایه مدت‌زمان است، هرگز بر پایه موقعیت، چون طرح‌های جاری ممکن است اصلاً هیچ پنجره ۵ ساعته‌ای نداشته باشند و پنجره هفتگی در جایگاه اصلی می‌نشیند.
- توکن‌های نوسازی codex می‌چرخند، و استفاده مجدد از یک توکن جایگزین‌شده کل خانواده اعطا را می‌کشد. هر چرخش لحظه‌ای که بازمی‌گردد پایدار می‌شود، حساب فعال فقط همیشه از طریق قطعه زنده نمونه‌برداری می‌شود (هرگز یک رونوشت پارک‌شده کهنه)، و فایل‌های حضور به‌ازای هر نشست تضمین می‌کنند که حسابی که در یک نشست هم‌نوع زنده در حال اجراست هرگز یک هدف جابه‌جایی نیست و هرگز توکن پارک‌شده‌اش نوسازی نمی‌شود.
- Codex به مخزن اعتبارنامه فایلی نیاز دارد: `init --codex` اگر مخزن keyring پین شده باشد سریع شکست می‌خورد، و `add --codex` تنظیم حالت-فایل را در خانه راه‌اندازی ایزوله می‌نویسد تا ورود قابل برداشت بنشیند.
- یک گام دستی: codex از قلاب‌هایی که به آن گفته نشده به آن‌ها اعتماد کند صرف‌نظر می‌کند. پس از `init --codex`، یک‌بار codex را باز کنید و از طریق `/hooks` به قلاب Stop مربوط به tokenmaxxing اعتماد کنید، وگرنه جابه‌جایی خودکار به‌طور خاموش بی‌اثر می‌ماند. `init --codex` این یادآوری را چاپ می‌کند.

## پل Slack: xx serve

`tokenmaxxing serve` یک شبح محلی Slack را روی حالت Socket اجرا می‌کند - بدون نیاز به هیچ URL عمومی. راه‌اندازی:

```sh
tokenmaxxing serve setup                    # مانیفست برنامه را چاپ می‌کند، برای دو توکن درخواست می‌کند
tokenmaxxing serve link <channel-id> <repo> # یک کانال را به یک برداشت مخزن گره می‌زند
tokenmaxxing serve                          # شبح را اجرا می‌کند
```

ربات را در یک کانال پیوندشده منشن کنید و آن یک نشست Claude Code برای آن رشته باز می‌کند، در برداشت مخزن پیوندشده. هر پیام رشته یک `query()` از Agent SDK را با `resume` اجرا می‌کند - هرگز یک پرس‌وجوی جریانی پایدار - بنابراین `ensureBestAccount()` استخر را در تک‌تک هر نوبت دوباره ارزیابی می‌کند و شبح می‌تواند بدون از دست دادن رشته‌ها راه‌اندازی مجدد شود (رکوردهای رشته بادوام هستند؛ شبح آن‌ها را هنگام راه‌اندازی دوباره مشترک می‌کند).

رفتار قابل توجه:

- **جریان‌سازی**: پاسخ‌ها به‌صورت بومی به داخل Slack جریان می‌یابند، با کارت‌های نوبت برای اندیشیدن و اجراهای ابزار، کد حصارکشی‌شده که با برجسته‌سازی ترسیم می‌شود، یک کارت پایانی "Turn" با هزینه و مدت، و یک پیام Slack جدید که هر گاه یک اجرای ابزار متن جریانی را قطع کند باز می‌شود، بنابراین یک نوبت به‌عنوان پیام‌های جداگانه پیرامون اجراهای ابزار خوانده می‌شود. فراخوانی‌های TodoWrite یک کارت فهرست وارسی پایدار را در همان جا به‌روز می‌کنند.
- **مجوزها**: `permissionMode` به‌ازای هر پیوند به‌طور پیش‌فرض `acceptEdits` است؛ `--yolo` (نام مستعار `--dangerous`) یک پیوند را به `bypassPermissions` وارد می‌کند. گفتگوهای تعاملی در نوبت‌های بازپخش‌شده مجاز نیستند - هیچ‌کس نمی‌تواند از طریق Slack به یکی پاسخ دهد - بنابراین مدل در قالب نثر می‌پرسد و پاسخ رشته شما نوبت بعدی است. یک مهارت افزونه همراه، به آن می‌آموزد که درخواست‌کننده را برچسب بزند و نوبت را وقتی به یک تصمیم نیاز دارد پایان دهد.
- **فرمان‌های اسلش**: یک پیام رشته که متن پیرایش‌شده‌اش با `/` شروع می‌شود به‌عنوان یک فرمان اسلش claude اجرا می‌شود. آهنگ‌ساز Slack پیام‌هایی را که با `/` شروع می‌شوند می‌خورد، بنابراین از شکل منشن-نخست (`@bot /usage`) یا یک فاصله ابتدایی استفاده کنید.
- **خاموش شدن باوقار**: SIGTERM/SIGINT تخلیه می‌کند - نوبت‌های جدید با صدای بلند رها می‌شوند، نوبت‌های در حال اجرا تا ۵ دقیقه فرصت می‌گیرند، و فرزند claude در گروه فرایند خودش جدا اجرا می‌شود تا یک Ctrl-C پایانه نتواند پیش از آنکه تخلیه نوبت را حفظ کند آن را بکشد.
- **پاکسازی رشته**: وقتی به آن می‌گویید کار تمام شده، مدل یک ابزار درون‌فرایندی `finish_thread` را فرا می‌خواند؛ پس از آنکه نوبت به‌طور کامل پایان یافت، شبح رکورد رشته را رها می‌کند، اشتراک را لغو می‌کند، و یک تأیید ارسال می‌کند. یک منشن تازه یک نشست جدید شروع می‌کند.
- **بهداشت خطا**: خطاهای نوبت متن پیام-تنها پیرایش‌شده ارسال می‌کنند، هرگز بدنه‌های خطای خام.

## سطح Agent SDK

نقطه ورود برنامه‌نویسی‌شده بسته (`exports["."]` به `src/sdk.ts` اشاره می‌کند) tokenmaxxing را با Claude Agent SDK جفت می‌کند، برای عامل‌هایی که در برابر حساب‌های استخرشده خودتان می‌سازید. برنامه شما باید زیر Bun اجرا شود (tokenmaxxing کد منبع TypeScript را عرضه می‌کند و از `bun:ffi` استفاده می‌کند).

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK یک زیرفرایند claude به‌ازای هر `query()` فرا می‌خواند و اعتبارنامه‌ها را یک‌بار هنگام فراخوانی می‌خواند - بدون statusline، بدون جابه‌جایی داغ در میانه پرس‌وجو - بنابراین این یکپارچگی بر پایه مرز است:

- `ensureBestAccount()` دقیقاً همان تصمیمی است که قلاب‌ها و زمان‌سنج CLI اجرا می‌کنند (نوارها، فشار سرعت، دوره خنک‌شدن، همه کد مشترک)، هرگز پیش‌بینانه: یک نشست SDK هرگز نمی‌تواند برای یک شمارش معکوس تهی متوقف شود.
- `pooledOptions()` مقدار `pathToClaudeCodeExecutable` را به باینری claude واقعی پین می‌کند (هرگز پوشش‌دهنده ناظر) و یک `env` جایگزین کامل با هر پوشش اعتبارنامه محیطی پاکسازی‌شده فراهم می‌کند. اگر `CLAUDE_CONFIG_DIR` یا `CLAUDE_SECURESTORAGE_CONFIG_DIR` در محیط برنامه شما تنظیم شده باشد سریع شکست می‌خورد: روی Linux یک جابه‌جایی، اعتبارنامه زنده را جایی که آن‌ها اشاره می‌کنند می‌نویسد در حالی که زیرفرایند پاکسازی‌شده مخزن پیش‌فرض را می‌خواند، یک واگرایی خاموش حساب اشتباه.
- `stopHookCheck` تصمیم را در مرزهای نوبت دوباره اجرا می‌کند؛ یک جابه‌جایی که این می‌نشاند در فراخوانی بعدی اعمال می‌شود. این خطاهای خودش را می‌گیرد (به stderr و گزارش ثبت می‌کند) به‌جای آنکه دوباره پرتاب کند، چون یک استثنای قلاب مدیریت‌نشده می‌تواند عامل را قطع کند، و لغو یک نوبت به‌خاطر یک بررسی جابه‌جایی خراب، بیش از سوار ماندن روی حساب جاری هزینه دارد.

`sdk.ts` هیچ چیز از خود Agent SDK وارد نمی‌کند؛ مقادیرش به‌صورت ساختاری به داخل گزینه‌های SDK پخش می‌شوند.

## ساخت و توزیع

بسته npm کد منبع TypeScript را عرضه می‌کند، نه یک ساخت را: فایل اجرایی `tokenmaxxing` مستقیماً به `src/main.ts` با یک shebang مربوط به Bun اشاره می‌کند، و Bun نسخه ۱.۲.۶ یا جدیدتر آن را همان‌طور که هست اجرا می‌کند. به همین دلیل است که Bun یک الزام قطعی است. به‌عمد هیچ باینری کامپایل‌شده‌ای وجود ندارد: یک انتشار اولیه یک باینری macOS واحد ۶۱ مگابایتی را به هر سکو عرضه کرد و روی Linux با `exec format error` شکست خورد، و بسته‌های کامپایل‌شده به‌ازای هر سکو هر کدام به خط لوله انتشار مخصوص خود نیاز داشتند، بنابراین اجرای-منبع-توسط-Bun به مدل توزیع تبدیل شد.

نقشه `exports` بسته، `src/sdk.ts` را به‌عنوان نقطه ورود برنامه‌نویسی‌شده توصیف‌شده در بالا نمایان می‌کند. انتشارها روی GitHub با `v<version>` برچسب‌گذاری می‌شوند؛ CI از طریق انتشار مورد اعتماد (OIDC، با provenance) به npm منتشر می‌کند، و دروازه انتشار ابتدا بررسی نوع و کل مجموعه تست را اجرا می‌کند.

## استفاده شخصی و شرایط خدمات [#personal-use-and-terms-of-service]

tokenmaxxing حساب‌هایی را که مالک آن هستید، در نشست‌ها و عامل‌هایی که خودتان اجرا می‌کنید، جمع می‌کند. این عبارت‌بندی عمدی است: Anthropic به محصولات شخص ثالث اجازه نمی‌دهد ورود claude.ai یا محدودیت‌های نرخ claude.ai را عرضه کنند، و این شامل عامل‌های ساخته‌شده روی Agent SDK هم می‌شود. سطح استخرشده SDK، یا هر چیز ساخته‌شده روی آن را، به شخص ثالث عرضه نکنید. tokenmaxxing همچنین به‌عمد برای داده سهمیه روی مسیر `/usage` واسطه‌شده با CLI می‌ماند، به‌جای آنکه OAuth را دوباره پیاده‌سازی کند یا ترافیک API را واسطه کند: این یک واسط نیست، و تنها نقاط پایانی OAuth که دست می‌زند، اعطای نوسازی استاندارد که در حین یک جابه‌جایی استفاده می‌شود و یک بررسی هویت فقط-خواندنی (نقطه پایانی roles) که تأیید می‌کند یک توکن واقعاً به کدام حساب تعلق دارد، هستند.

## محدودیت‌های صادقانه

- **یک نوبت سرد.** نهان درخواست به دامنه سازمان محدود است، بنابراین نخستین نوبت روی یک حساب جدید یک‌بار زمینه را دوباره بارگذاری می‌کند.
- **سکسکه توقف تهی.** فقط یک استخر کاملاً تهی نشست را برای شمارش معکوس متوقف می‌کند؛ هر چیزی که در آن کسر ثانیه تایپ شود از دست می‌رود.
- **تأخیر پذیرش.** روی macOS نخستین نوبت در حدود ۳۰ ثانیه پس از یک جابه‌جایی هنوز می‌تواند حساب قدیمی را اندازه‌گیری کند؛ فضای آزاد نوارها آن را جذب می‌کند.
- **شعاع انفجار مشترک.** همه نشست‌های نمایه پیش‌فرض یک اعتبارنامه زنده را به اشتراک می‌گذارند، بنابراین یک جابه‌جایی همه آن‌ها را با هم کوچ می‌دهد (هر کدام در همان جا می‌پذیرد).
- **اعتبارنامه‌های متن ساده روی Linux.** خود Claude Code اعتبارنامه‌های Linux را به‌عنوان یک فایل متن ساده ۰۶۰۰ ذخیره می‌کند؛ رونوشت‌های پارک‌شده tokenmaxxing همان مدل را دنبال می‌کنند.

## عیب‌یابی و پرسش‌های متداول

**به‌نظر نمی‌رسد `claude` تحت نظارت باشد.**
`tokenmaxxing doctor` را اجرا کنید. شیم باید حل PATH را ببرد؛ بررسی کنید که خط `# tokenmaxxing PATH` در فایل rc پوسته شما به دایرکتوری bin جاری اشاره می‌کند و جلوتر از claude واقعی می‌نشیند. `doctor` همچنین درباره `alias claude=...` یا یک تابع پوسته `claude()` که پوشش‌دهنده را سایه می‌اندازد، و درباره نام‌های مستعاری که یک باینری claude را با مسیر مطلق راه‌اندازی می‌کنند (آن‌ها ناظر را به‌کلی دور می‌زنند)، هشدار می‌دهد.

**جابه‌جایی خودکار هرگز روی Codex شلیک نمی‌شود.**
Codex از قلاب‌هایی که به آن گفته نشده به آن‌ها اعتماد کند صرف‌نظر می‌کند. codex را باز کنید، `/hooks` را اجرا کنید، و به قلاب Stop مربوط به tokenmaxxing اعتماد کنید. اعتماد در برابر درهم‌سازی قلاب ثبت می‌شود، بنابراین اگر قلاب هرگز ویرایش شود باید دوباره اعطا شود.

**یک حساب یک `✗` قرمز در statusline نشان می‌دهد.**
توکن نوسازی آن مرده است (باطل‌شده یا از زیر پشتیبانش چرخانده‌شده). `tokenmaxxing auth <sel>` را اجرا کنید تا آن را در همان جا دوباره احراز هویت کنید؛ فرمان به شما می‌گوید با کدام ایمیل وارد شوید و یک ورود را که روی حسابی متفاوت بنشیند امتناع می‌کند.

**چرا به حسابی با بیشترین سهمیه باقی‌مانده جابه‌جا نمی‌شود؟**
چون آن، حسابی نیست که بیش از همه در معرض از دست دادن سهمیه باشد. هدف، حسابی است که بیش از همه از سرعت هفتگی خودش عقب است: درصد باقی‌مانده تقسیم بر زمان تا بازنشانی هفتگی آن. با مقادیر باقی‌مانده برابر، این به ابتدا-زودترین-انقضا کاهش می‌یابد، و با انقضای برابر به ابتدا-بیشترین-باقی‌مانده.

**همین حالا جابه‌جا شد و statusline هنوز حساب قدیمی را نشان می‌دهد.**
تا حدود ۳۰ ثانیه روی macOS انتظار می‌رود: نشست در حال اجرا اعتبارنامه جابه‌جاشده را در نوسازی بعدی نهان اعتبارنامه‌اش می‌پذیرد. شاخه مصرف دقیقاً به همین دلیل برای ۴۵ ثانیه پس از یک جابه‌جایی سرکوب می‌شود.

**آیا `status --force` هزینه‌ای دارد؟**
بله، به‌عمد: یک درخواست haiku کمینه اندازه‌گیری‌شده به‌ازای هر حساب می‌فرستد تا هر پنجره نشست ۵ ساعته در همان لحظه شروع شود به‌جای آنکه غیرفعال دراز بکشد، سپس نمونه‌برداری تازه می‌کند. `status` ساده و `watch` هرگز پینگ نمی‌زنند؛ خواندن‌های `/usage` رایگان‌اند. توجه کنید که خوراک مصرف سرور می‌تواند یک پنجره تازه بازشده را از ثانیه‌ها تا دقیقه‌ها به تأخیر بیندازد، بنابراین یک کاوش بلافاصله پس از پینگ ممکن است هنوز وضعیت پیش-پینگ را نشان دهد - `status` به‌جای وانمود کردن به شکست پینگ، یک یادداشت ترسیم می‌کند.

**کاوش `/usage` برای حساب فعال چیزی برنگرداند.**
این یک رفتار شناخته‌شده claude است: وقتی واکشی مصرف داخلی‌اش شکست بخورد یا محدود به نرخ شود، `/usage` فقط آمار نشست محلی را بدون خطوط درصد چاپ می‌کند. tokenmaxxing حساب فعال را از ارسال statusline نمونه‌برداری می‌کند و فقط حساب‌های پارک‌شده را کاوش می‌کند، دقیقاً برای پرهیز از این.

**نشست‌های پس‌زمینه claude.**
شبح پس‌زمینه claude باینری نسخه‌دار واقعی را با مسیر مطلق فرا می‌خواند و شیم‌های PATH را دور می‌زند، بنابراین نشست‌های پس‌زمینه تحت نظارت نیستند. قلاب‌ها هنوز از طریق `settings.json` شلیک می‌شوند، و پذیرش اعتبارنامه به‌علاوه زمان‌سنج دوره‌ای جابه‌جایی را پوشش می‌دهند، اما هیچ بازآفرینی نشانگر-محور برای آن‌ها وجود ندارد.

**چیزی یک‌بار مقدار زیادی فرایند فرا خواند. آیا این هنوز ممکن است؟**
ناظر محافظ‌های بازگشتی لایه‌بندی‌شده دقیقاً در برابر همان شکست تاریخی حمل می‌کند (یک پوشش‌دهنده کهنه که به‌عنوان claude "واقعی" پین شده): یک نگهبان عمق در محیط که در ۵ سطح لغو می‌کند، یک محدودکننده نرخ فراخوانی روی دیسک، بررسی‌های هویت realpath که هر نامزدی را که به دایرکتوری bin خود tokenmaxxing برمی‌گردد رد می‌کند، و یک شکست سخت (هرگز یک پیمایش خاموش PATH) وقتی یک مسیر claude پیکربندی‌شده دیگر وجود ندارد. `init` و `doctor` با اجرای `--version` پیش از پین کردن، تأیید می‌کنند که یک نامزد واقعاً claude است.

**حذف نصب.**
`tokenmaxxing uninstall` شیم‌های ناظر، ورودی‌های تنظیمات، و زمان‌سنج دوره‌ای را حذف می‌کند، و حساب‌ها و اعتبارنامه‌های پارک‌شده شما را دست‌نخورده می‌گذارد. فقط ورودی‌های statusline را که به‌عنوان مال خودش می‌شناسد حذف می‌کند.
