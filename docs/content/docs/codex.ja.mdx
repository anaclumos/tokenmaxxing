同じプーリングは OpenAI の Codex CLI でも、自分の ChatGPT サブスクリプションアカウントを対象に機能します。

```sh
tokenmaxxing init --codex   # 現在の codex ログインをインポートし codex スーパーバイザーと Stop フックをインストールする
tokenmaxxing add --codex    # 別のアカウントを分離してログインする。主要ログインには触れない
codex                       # これまでどおり codex を使う
```

Codex プールは完全に並列した状態です。独自のアカウントインデックス、独自のパーク済み認証情報ファイル (codex 自身のストアが平文ファイルであるため、両プラットフォームで0600ファイル)、独自のロック、独自の直近切り替えタイムスタンプを持ちます。判断ポリシーのコードを除いて、Claude プールと共有されるものは何もありません。

## なぜ Codex ではホットスワップが不可能なのか

実行中の codex プロセスは1つのインメモリ認証マネージャーを保持し、`auth.json` が別のアカウントを指すようになると明示的にリロードを拒否します。ファイルウォッチャーもリクエストごとの認証情報ポーリングもないため、実行中の codex の裏で入れ替えられた認証情報は推論には決して反映されません。再起動が切り替えです。`codex resume <session-id>` は、`auth.json` が今保持しているアカウント上でローカルのトランスクリプトを継続します。

tokenmaxxing はこれを codex スーパーバイザーシムで処理します。Stop フックが各ターン境界で同じグリーディなペースプレッシャー判断を実行し、切り替えるときはマーカーを書き込みます。それによりスーパーバイザーはコミット済みの境界でセッションに SIGTERM を送り、新しいアカウント上でトランスクリプトを保ったまま `codex resume <session-id>` を再起動します。すべての codex 切り替えは目に見える再起動であるため、codex のグリーディパスは1.2倍の改善マージンを持ちます。挑戦者は現在のアカウントのペースプレッシャーをわずかにではなく20%上回らなければなりません。ハードパス (バーを超えた) はマージンを無視します。codex には枯渇プールのカウントダウンもありません。codex セッションを一時停止できるものは何もないため、完全に枯渇した codex プールはそのまま留まります。

その他の codex 固有の仕組み:

- 使用量は、codex 自身のレート制限エンドポイントに対する無料の認証済み GET から読み取られます (CLI の `/status` が行うのと同じ呼び出し)。パーセンテージに加えて絶対エポックのリセット時刻、集計ウィンドウとモデルごとの上限の両方です。ウィンドウ分類は位置ではなく期間で決まります。現在のプランには5時間ウィンドウがまったくない場合があり、週次ウィンドウが主要スロットにあるためです。
- Codex のリフレッシュトークンはローテートし、置き換えられたものを再利用するとグラントファミリー全体が失効します。すべてのローテーションは返ってきた瞬間に保存され、アクティブアカウントは常にライブ blob からのみサンプリングされ (古いパークコピーからは決して行われません)、セッションごとのプレゼンスファイルにより、ライブの兄弟セッションで動作しているアカウントが切り替えターゲットになることも、そのパークトークンがリフレッシュされることもないようにします。
- Codex はファイル認証情報ストアを必要とします。`init --codex` はキーリングストアが固定されている場合は速やかに失敗し、`add --codex` は分離オンボーディングホームにファイルモード設定を書き込むため、ログインが取り込み可能な状態で残ります。
- 手動ステップが1つあります。codex は信頼するよう指示されていないフックをスキップします。`init --codex` の後、codex を1度開いて `/hooks` から tokenmaxxing の Stop フックを信頼してください。さもないと自動切り替えは静かに不活性のままです。`init --codex` はこのリマインダーを表示します。
