ውሳኔው ሁለት ንብርብሮች አሉት፦ የ engagement gate፣ ከዚያም greedy ወይም hard path።

## Engagement

ከ `policy.greedySessionFloor` በታች (ነባሪ 80፣ በ5-ሰዓት session መስኮት መቶኛ)፣ ውሳኔው በጭራሽ አይሄድም - አዲስ session መለያውን ይጋልባል። ንቁ የሆነው session መስኮት 80% ጥቅም ላይ ከዋለ በኋላ፣ ወይም ማንኛውም bar ከተሻገረ፣ ውሳኔው ይሳተፋል።

## Screening barዎች

threshold ዎቹ screening barዎች ናቸው እንጂ ለድንጋጤ ቀስቃሽ አይደሉም፦

- `thresholds.session`፦ መሰላል፣ ነባሪ `[90]`፣ አንድ ደረጃ ብቻ። እያንዳንዱ ግምገማ አንድ ንቁ ደረጃ ይፈታል፦ አሁን ያለውን ጨምሮ አንዳች የተሰበሰበ መለያ ገና ጥቅም ላይ ሊውል የሚችልበት ዝቅተኛው ደረጃ። እንደ `[50, 80, 95]` ያለ ባለብዙ ደረጃ መሰላል ሲኖር፣ ማንኛውም መለያ ከ50 በታች እስካለ ድረስ bar ው 50 ነው፣ ስለዚህ 50 ን የተሻገረ መቀመጫ ወደዚያ መለያ ያስረክባል። እያንዳንዱ መለያ 50 ን ካለፈ በኋላ bar ው ወደ 80 ይወጣል፣ በሁሉም ቦታ 80 ን ካለፈ ደግሞ ወደ 95 ይወጣል። የላይኛው ደረጃ የመጨረሻው bar ነው፤ ከሱ ባሻገር ግድግዳው (ከታች) ይረከባል። የ5-ሰዓት ዳግም ማስጀመሪያ ዝም ብሎ ለመቀመጥ ርካሽ ነው፣ ስለዚህ ባለብዙ ደረጃ pool ደረጃ በደረጃ ይሟጠጣል እና ማንም መለያ ከወንድሞቹ ቀድሞ ብዙ አይሮጥም።
- `thresholds.weekly`፦ 98። ይህ አንድ bar የ7-ቀን ጥቅሉንም ሆነ እያንዳንዱን በ-ሞዴል ሳምንታዊ ገደብ ይሸፍናል። ሳምንታዊ ኮታ ተጠቀም-ወይም-አጣ ነው፣ ስለዚህ ወደ ግድግዳው ቅርብ ይሟጠጣል።

ሁለቱም ሆን ተብለው ከ100 በታች ናቸው፦ ክፍተቱ መለያው በትክክል ገደቡን ከመምታቱ በፊት ንጹህ turn ወሰን ለመድረስ (በተጨማሪም በ macOS ላይ እስከ አንድ turn የመቀበል መዘግየት) የሚያገለግል በጀት ነው። ተመሳሳዮቹ barዎች የመቀያየር እጩዎችን ይመረምራሉ፦ ከ barዎቹ ማንኛውም በላይ የሆነ መለያ ትክክለኛ ኢላማ አይደለም። Trigger እና screening ሁልጊዜ ተመሳሳይ ተግባራዊ barዎችን ይጠቀማሉ (ንቁው ደረጃ እና ሳምንታዊው bar፣ እያንዳንዳቸው ሲቀነሱ `policy.projectionMargin`)፣ ምክንያቱም ከ trigger ይልቅ የላላ screen trigger ወዲያውኑ እንደገና-የሚሰይማቸው መለያዎች ላይ መቀያየሮችን ስለሚያሳርፍ pool ን ወደ ping-pong ይለውጣል። አንድ ደረጃ የሚቆጥረው በዚያ ደረጃ ጥቅም ላይ ሊውሉ የሚችሉ መለያዎችን ብቻ ነው፦ የሞተ grant፣ የተቃጠለ የተገደበ በ-ሞዴል ገደብ፣ ወይም በ server የተሰካ ማስፈጸሚያ bar ውን ወደታች አይዝም፣ እና ደረጃው በአንድ ግምገማ ውስጥ በእያንዳንዱ ዳግም ሙከራ ከ pool ው እንደገና ይነበባል። Codex የላይኛውን ደረጃ ብቻ ያነባል፣ ምክንያቱም ዳግም ማስጀመር የሱ መቀያየር ስለሆነ።

## ኢላማው፦ pace pressure

ጥቅም ላይ ሊውሉ ከሚችሉ መለያዎች መካከል፣ ኢላማው ከራሱ ሳምንታዊ ፍጥነት ወደኋላ በጣም የቀረው ነው፦ ከፍተኛ **pace pressure**፣ እንደ ቀሪ ሳምንታዊ መቶኛ ተከፍሎ ለዚያ መለያ ሳምንታዊ ዳግም ማስጀመሪያ እስከሚደርስ ባለው ጊዜ የሚገለጽ። ሊወረስ የሚቃረብ በጣም ብዙ ኮታ ያለው መለያ ያሸንፋል። እኩልነቶች ወደ ቀጣዩ ሳምንታዊ ማብቂያ ይሰበራሉ፣ ከዚያ ወደ ዝቅተኛ የ7-ቀን አጠቃቀም።

ሁሉም ነገር እንደ ፍጹም UTC epoch የተከማቹ cache-የተደረጉ መስኮቶች ላይ ይሄዳል፣ ስለዚህ ያረጀ snapshot አሁንም በትክክል ይፈታል፦ ያለፈ ሳምንታዊ ዳግም ማስጀመሪያ በትክክለኛ የ7-ቀን ደረጃዎች ወደፊት ይራዘማል፣ እና ከ cache-የተደረገ ዳግም ማስጀመሪያው ያለፈ ማንኛውም መስኮት እንደ አዲስ ባዶ ይቆጠራል (ለመቀየር ምክንያት በጭራሽ አይደለም፣ መለያን ማቆየት ለ bench ምክንያት በጭራሽ አይደለም)።

## Greedy በተቃራኒ hard path

- **Greedy path** (የተሳተፈ፣ ግን ከ bar ሁሉ በታች)፦ አሁን ያለውን ጨምሮ እያንዳንዱን መለያ ደረጃ ይስጥ። አሁን ያለው መለያ አስቀድሞ ካሸነፈ ወይም እኩል ከሆነ፣ ምንም አታድርግ። አለበለዚያ ወደ በጥብቅ የተሻለ መለያ ተቀየር። በጭራሽ አይጠብቅም እና በጭራሽ አስቀድሞ አያቆምም - ጥቅም ላይ ሊውል የሚችል አሁን ያለ መለያ ለጥበቃ አይለወጥም። አሁን ያለው መለያም ደረጃ ስለሚሰጠው፣ ሁለቱም automatic path እና ባዶ `tokenmaxxing switch` idempotent ናቸው፦ ወቅታዊ መገምገም በትክክለኛው መለያ ላይ ይሰበሰብ እና ከዚያ ይቆያል።

  automatic የሆነው greedy path ነባሩን መለያ በ hysteresis ይይዛል። pace pressure ቀጣይነት ያለው ዋጋ ነው፣ ስለዚህ ወደ እኩልነት የቀረቡ ሁለት መለያዎች በትክክል እኩል የሚሆኑበት ጊዜ ፈጽሞ የለም ማለት ይቻላል፣ እና በቀጥታው መለያ ላይ መስራት የተያዘ መለያ ጥቂት ቀድሞ እንዲወጣ ያደርገዋል - pool በየጥቂት ደቂቃው መቀመጫውን ping-pong ሲያደርግ የነበረው በዚህ ምክንያት ነው፣ እና እያንዳንዱ መቀያየር በ-ድርጅት prompt cache ን ያበላሻል እና በሚቀጥለው turn ሙሉ cache-ያልተደረገ ዳግም ንባብ ያስከፍላል። መፍትሄው `policy.greedySwapMargin` (ነባሪ 0.15) ነው፦ greedy path ከመቀያየሩ በፊት የተያዘ መለያ አሁን ያለውን መለያ pace pressure ከዚህ ክፍልፋይ በበለጠ ማሸነፍ አለበት። ከዚያም ማስረከብ የሚከሰተው ነባሩ መለያ በእውነት ወደኋላ እስኪቀር ድረስ ሲሟጠጥ ብቻ ነው እንጂ በማጠጋጋት ደረጃ ባለ ብልጫ አይደለም። ህዳጉ የተሻገረ bar ን፣ hard path ን፣ ወይም ግድግዳውን በጭራሽ አያለዝብም - ሁሉም ከ barዎቹ በታች በሆኑ መለያዎች መካከል ያሉ የጎን መቀያየሮችን ብቻ ነው የሚነካው። ባዶ `tokenmaxxing switch` ህዳጉን ዜሮ ያደርገዋል፣ ስለዚህ በእጅ የሚደረግ መቀያየር አሁንም በጥብቅ ምርጡ በሆነው መለያ ላይ ይሰበሰባል።
- **Hard path** (bar የተሻገረ)፦ ወደ ምርጡ ጥቅም ላይ ሊውል የሚችል እጩ ተቀየር። የአንድ እጩ refresh token የሞተ ከሆነ፣ needs-reauth ተብሎ ምልክት ይደረግበታል እና ቀጣዩ እጩ ይሞከራል። ምንም ጥቅም ላይ ሊውል የሚችል ከሌለ፣ የግድግዳ ጭመቃ (ከታች) ይሄዳል፣ እና እያንዳንዱ ጥቅም ላይ ሊውል የሚችል መለያ ግድግዳውን ሲመታ ብቻ depleted-wait logic ይሄዳል፤ session ን በትክክል ማቆም የሚችል ጠሪ (የተቆጣጠረው Stop hook) ብቻ ወደ አሁንም-የታገደ ግን ቀድሞ-የሚያገግም መለያ አስቀድሞ እንዲያቆም ይፈቀድለታል።

## ግድግዳው

hard path ጥቅም ላይ ሊውል የሚችል እጩ ሲያጣ - እያንዳንዱ መለያ ከ screening barዎቹ በላይ ሲሆን - automatic ውሳኔው ወዲያውኑ አያቆምም። መጀመሪያ በ **ግድግዳ barዎቹ** (`hardThresholds`፣ ነባሪ 100፣ የእያንዳንዱ መለያ እውነተኛ የ server ገደብ) ላይ እንደገና ይገመግማል፦ session ገና ከግድግዳው በታች እያለ መቀመጫውን ይይዛል እና ይጨምቃል፣ አለበለዚያ ወደ ምርጡ አሁንም-ከግድግዳ-በታች መለያ ይቀየራል (ተመሳሳይ pace-pressure ደረጃ አሰጣጥ)፣ እና እያንዳንዱ ጥቅም ላይ ሊውል የሚችል መለያ ግድግዳውን በእውነት ሲመታ ብቻ ያቆማል። refresh token ው የሞተ መለያ ለ reauth ወደ ጎን ይቀመጣል እንጂ አይጠበቅም። ማገገም ከግድግዳው አንጻር ይለካል፣ ስለዚህ የ5-ሰዓት መስኮቱ ዳግም የሚጀምር መለያ ሳምንታዊ መስኮቱ ገና ከ screening bar በላይ እያለም እንደገና ሊጨመቅ ይችላል።

ይህ የእያንዳንዱ መለያ ኮታ የመጨረሻዎቹ ጥቂት መቶኛዎች ሳይውሉ እንዳይቀሩ ያደርጋል። የግድግዳው ንባብ ውሳኔው አስቀድሞ ከሚጠቀመው ከየትኛውም የአጠቃቀም ምንጭ ይመጣል - በተቆጣጠረ session ላይ የ statusline tee ው፣ ወይም headless run ላይ የ `/usage` probe - እነዚህ Claude የ `/rate-limit-options` የሚያሳያቸው ተመሳሳይ አኃዞች ናቸው፣ ስለዚህ በእውነት የሚሞላ መለያ ተለይቶ ይታለፋል። የአንድ-turn ማለፍ ውሳኔው በሚቀጥለው ጊዜ ሲሄድ ይያዛል - ወቅታዊው ምርመራ፣ ወይም headless run ላይ ቀጣዩ spawn ወይም Stop ወሰን.

`hardThresholds` ልክ screening barዎቹ እንደሚያደርጉት `policy.projectionMargin` ን ይቀንሳል፣ ስለዚህ ከ `thresholds` ጋር እኩል ማድረግ የግድግዳ ጭመቃውን ያሰናክላል። ይህ የ Claude-ብቻ path ነው፦ ባዶ `tokenmaxxing switch` cache-ብቻ ማቆሚያውን ይይዛል፣ እና Codex `hardThresholds` ን ሙሉ በሙሉ ችላ ይላል - የሚሮጥ Codex በ session መሃል የተቀየረ credential መቀበል አይችልም፣ ስለዚህ እስከ እውነተኛው የ server ገደብ ድረስ አሁን ባለው መለያው ላይ ይቆያል (ከ100 በታች ብጁ ግድግዳ ለ Codex አይተገበርም)።

## በ-ሞዴል ገደቦች

`policy.switchModels` (ነባሪ `["fable"]`) በ-ሞዴል ሳምንታዊ ገደባቸው መቀያየር ሊያስነሳ የሚችል የሞዴል ቤተሰቦችን ይሰይማል። ተዛማጅነት በ family token ነው እንጂ በትክክለኛ display string በጭራሽ አይደለም፦ የሞዴል display ስሞች ይለዋወጣሉ ("Fable" "Fable 5" ሆነ)፣ እና የትክክለኛ-string gate በአንድ ወቅት በ-ሞዴል መቀያየርን በጸጥታ ሙሉ በሙሉ አሰናከለ። ሁለት ተዛማጅ የደህንነት ደንቦች፦

- ያልታወቀ ንቁ ሞዴል የተዋቀረውን እያንዳንዱን ቤተሰብ ይገድባል። መቀያየር snapshotዎችን ካጸዳ በኋላ ወዲያውኑ፣ headless ማሽን model-blind ሆኖ ሊሄድ ይችላል፤ ያልታወቀን እንደ ያልተገደበ መቁጠር በአንድ ወቅት አንድ መለያ በ Fable ገደቡ ላይ ሳይስተዋል ለሰዓታት እንዲቀመጥ አድርጎታል።
- የእጩ screening የተገደቡ በ-ሞዴል ገደቦችንም ይቆጥራል፣ ስለዚህ እያንዳንዱ መለያ የ Fable ገደቡን ያቃጠለበት pool round-robin አያደርግም።

## Cooldown

የ45-ሰከንድ post-swap cooldown automatic path ን ይገድባል። statusline tee ው ከመቀያየር በኋላ ለተመሳሳይ 45 ሰከንድ ይታፈናል (መቀበል በ macOS ላይ እስከ 30 ሰከንድ ይወስዳል)፣ ስለዚህ ቀደም ያለ ግምገማ መቀያየሩ ራሱ ባበላሸው ውሂብ ላይ ይሄዳል - ያ ትክክለኛ ሁኔታ በአንድ ወቅት A-ወደ-B-እና-ተመልሶ የ respawn loop አመንጭቷል። በእጅ የሚደረግ `tokenmaxxing switch` በ cooldown አይነካም።

## የተጣሉ ገደቦች

cache የተደረጉት አኃዞች ከእውነታው ወደኋላ ሊቀሩ ይችላሉ፦ የቀጥታው መለያ በ-ሞዴል ገደብ የሚመጣው ስራ ከበዛበት ቀጥታ token ላይ ከሚደረግ የ `/usage` probe ብቻ ነው፣ እሱም በ session ጫና ስር ብዙ ጊዜ ምንም አያትምም። server ው በእውነት turn ን ሲከለክል፣ Claude Code በ API ስህተት ያጠናቅቀዋል እና ከ `Stop` ይልቅ የራሱን `StopFailure` hook ያስነሳል። tokenmaxxing ያንን hook በ `rate_limit` matcher ይጭናል፣ እናም የ transcript ውን የተዋቀረ የስህተት ረድፍ ያነባል (Claude Code ራሱ `isApiErrorMessage` ብሎ ምልክት የሚያደርግበትን ተመሳሳይ ረድፍ)፦ የ `quotaLimits` block መስኮቱን (`five_hour`፣ `seven_day`፣ ወይም በ-ሞዴል አይነት) ከ server ው ዳግም ማስጀመሪያ ጋር ይሰይማል፣ እና ምንም `quotaLimits` የማይይዘው የ Fable ገደብ ውድቀት ከ client ው የራሱ የስህተት አቀራረብ እና ከ 429 body ተለይቶ ይታወቃል። የሞዴል ጽሁፍ በጭራሽ አይነበብም።

hook ው ለዚያ መለያ የተጣለውን መስኮት 100 ላይ ያትማል እና እስከዚያ ዳግም ማስጀመሪያ ድረስ በ server የተጠቀሰ ቀን ያለው session ወይም ሳምንታዊ ገደብ በመለያው ላይ ይሰካል፣ ስለዚህ ገና የአጠቃቀም ናሙና የሌለው መለያ ወዲያውኑ ተመልሶ ሊመረጥ አይችልም። ማስፈጸሚያውን ከየትኛውም cache ከተደረገ መስኮት የበለጠ ጠንካራ እውነታ አድርጎ ለውሳኔው ያስረክባል (የ post-swap cooldown ን ያልፋል፣ እጩዎችን በተነካው ቤተሰብ ይገድባል፣ እና በጭራሽ መቀመጫውን አይይዝም)፣ እና hard path ወደ ሌላ ይቀየራል። ዋናው turn ው በወደቀበት በተቆጣጠረ session ውስጥ፣ በተጨማሪም respawn marker ይጥላል፦ supervisor ው በአዲሱ መለያ ላይ `--resume` ን እንደገና ያስነሳል እና የተቋረጠው ስራ እንዲቀጥል አንድ የመቀጠያ prompt ያቀርባል። በ subagent ውስጥ የሚከሰት ውድቀት ይቀያየራል እንጂ በጭራሽ respawn አያደርግም (የወላጁ turn ገና እየሄደ ነው)፣ እና ያልተቆጣጠረ session መቀያየሩን ያገኛል እና በሚቀጥለው request ላይ ይቀበለዋል።

ውድቀት የሚቆጠረው ከመቀያየር በኋላ ባለው credential ላይ መከሰቱ በማስረጃ ሲረጋገጥ ብቻ ነው፦ ከመቀያየሩ በኋላ የተደረገ ዳግም ማስጀመር፣ ወይም ከመቀያየሩና ከ cooldown በኋላ ያረፈ የወደቀ request። የ rate-limit ክልከላ የሚደርሰው request በሚጀምርበት ጊዜ ነው፣ ስለዚህ turn ው ምንም ያህል ቢሄድ የስህተቱ ረድፍ የራሱ ሰዓት መልህቁ ነው። አንድ የዳግም ቀስቀሳ ቅደም ተከተል ብዙ የተቃጠሉ መለያዎችን እንዲያቋርጥ የሚያስችለው ይህ ነው፣ ያረጀ token የያዘ request አዲሱን መቀመጫ ሳያትም።

## የፍተሻ ምት

ወቅታዊው timer `tokenmaxxing check --if-due` ን በየ tick ው ያሄዳል (`policy.checkIntervalMs`፣ በነባሪ 60 ሰከንድ)፣ እና እያንዳንዱ ግምገማ ቀጣዩን ከ tick ው መጀመሪያ ተቆጥሮ ይመድባል፣ የቀጥታው መለያ ወደ ቅርብ bar ው ካለው ክፍተት አንጻር (ንቁው session ደረጃ፣ ሳምንታዊው ጥቅል፣ እና እያንዳንዱ የተገደበ በ-ሞዴል ገደብ)፦ 40 ነጥብ ወይም ከዚያ በላይ ክፍተት አምስት tick ይተኛል፣ 20 ሦስት ይተኛል፣ 8 ሁለት ይተኛል፣ ከዚያ ያነሰ ደግሞ በእያንዳንዱ tick ይገመግማል። መሰላሉም እንዲሁ በተወጣ ደረጃ አንድ ባንድ ያንን እንቅልፍ ይገድባል፦ በመጀመሪያው ደረጃ እስከ አምስት tick፣ በሁለተኛው እስከ ሦስት፣ በሦስተኛው እስከ ሁለት፣ እና ከዚያ ያለፈ ማንኛውም ደረጃ በእያንዳንዱ tick፣ ስለዚህ አንድ ደረጃ የወጣ pool ገና በመጀመሪያው ደረጃ ላይ ካለው በበለጠ ተደጋግሞ ይጠየቃል። ከመድረሻው ሰዓት በግማሽ tick ውስጥ የሚያርፍ tick እንደደረሰ ይቆጠራል፣ ስለዚህ ዘገምተኛ ግምገማ ባንድን በሙሉ tick ወደኋላ መግፋት አይችልም። ባዶ `tokenmaxxing check` መርሃ ግብሩን ችላ ብሎ ወዲያውኑ ይገመግማል። ከ poll TTL ያረጀ tee፣ ወይም ለቀጥታው org ምንም tee አለመኖር፣ የሦስት-tick ምቱን ይይዛል፣ እና የገደብ ረድፍ የሌለው የተገደበ ቤተሰብ በጭራሽ ከሁለት tick በላይ አይተኛም፣ ስለዚህ ያልተለካ መስኮት በጭራሽ ዘገምተኛውን መስመር መግዛት አይችልም። የተሟጠጠ ጥበቃ ወደ ዳግም ማስጀመሪያው ይተኛል፣ በ post-swap cooldown ውስጥ የሚያርፍ tick በትክክል እስከ መጨረሻው ይተኛል፣ እና ከ poll TTL ያረጀ የገደብ ረድፍ እንደ ያልተለካ ይቆጠራል። መቀያየር መርሃ ግብሩን ያጸዳል ስለዚህ cooldown ው እንደተነሳ አዲሱ መቀመጫ ወዲያውኑ ይገመገማል። ዘገምተኛው መስመር ደህና የሚሆነው StopFailure hook ው ማስፈጸሚያውን በተከሰተበት ቅጽበት ስለሚይዘው ብቻ ነው።
