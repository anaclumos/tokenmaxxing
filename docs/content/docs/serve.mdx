---
title: The Slack bridge
description: xx serve runs Claude Code sessions from Slack threads over Socket Mode
---

`tokenmaxxing serve` runs a local Slack daemon over Socket Mode - no public URL required. Setup:

```sh
tokenmaxxing serve setup                    # prints the app manifest, prompts for the two tokens
tokenmaxxing serve link <channel-id> <repo> # tie a channel to a repo checkout
tokenmaxxing serve                          # run the daemon
```

Mention the bot in a linked channel and it opens a Claude Code session for that thread, in the linked repo checkout. Each new turn spawns one Agent SDK `query()` with `resume` - so `ensureBestAccount()` re-evaluates the pool per turn and the daemon can restart without losing threads (thread records are durable; the daemon re-subscribes them on startup) - while a reply arriving during a live query is fed into that query's streaming input instead of spawning its own; a reply that misses the steering window runs as the next turn.

Notable behavior:

- **Steering**: a reply that lands while the thread's turn is still running folds into that turn - the same mid-turn injection Claude Code uses interactively - so the model sees it at its next tool boundary and adjusts course instead of finishing the wrong thing first. A reply that arrives after the turn's last tool call runs as its own turn right after; nothing is dropped either way. Steered messages wear the hourglass reaction and settle with the turn, and their text rides the turn's durable marker, so restarts and usage-limit resumes replay it. Only a message queued behind another waiting message skips the fold (order is preserved), and a draining daemon still drops loudly instead of steering.
- **Streaming**: replies stream natively into Slack, with task cards for thinking and tool runs, fenced code rendered with highlighting, and a closing "Turn" card with cost and duration; a turn's cards collapse into one expandable plan block, so a turn normally reads as a single message: the reply plus one dropdown of its activity (a mid-turn retry or a rejected append opens a follow-on message). TodoWrite calls update one stable checklist card in place. Slack expires a native stream server-side after roughly 30 seconds of silence or 5 minutes of life, freezing the message as a "Something went wrong" pill, so the daemon closes an idle or long-lived message cleanly before either timer and continues in a fresh one.
- **Permissions**: per-link `permissionMode` defaults to `acceptEdits`; `--yolo` (alias `--dangerous`) opts a link into `bypassPermissions`. Interactive dialogs are disallowed in relayed turns - nobody can answer one through Slack - so the model asks in prose and your thread reply is the next turn. A bundled plugin skill teaches it to tag the requester and end the turn when it needs a decision.
- **Status reactions**: the message that triggered a turn carries its state as an emoji reaction: an hourglass while the turn runs, then a check mark (done), an x (failed), or a question mark (the model needs your decision). Requires the `reactions:write` scope from the current manifest; existing apps must re-paste the manifest and reinstall.
- **Attention and nudges**: when the model asks you for a decision it calls an in-process `need_attention` tool, so the daemon knows the thread is waiting on you. If you stay quiet for 10 minutes it tags you once in the thread. While a thread is waiting, reacting to the question relays as your answer (a thumbs up picks the recommended option); any other reaction you add in a tracked thread is folded into the next turn as context. Requires `reactions:read` and the `reaction_added` event from the current manifest; existing apps must re-paste the manifest and reinstall.
- **Slash commands**: a thread message whose stripped text starts with `/` runs as a claude slash command. Slack's composer eats messages starting with `/`, so use the mention-first form (`@bot /usage`) or a leading space.
- **Usage-limit auto-resume**: when every pooled account is at its limit, a short outage parks the message and retries in place; a longer one posts a holding notice and resumes the turn automatically once the pool recovers, surviving daemon restarts. Only a limit with no known recovery time asks you to re-send.
- **Failure retry**: a turn that fails without completing (a crashed claude child, an API error) silently retries up to 2 more times, resuming the same session so finished work is never re-run; only after that does the thread get the real error. A turn whose answer completed is never retried, and a failure that turns out to be pool exhaustion hands off to the usage-limit machinery above.
- **Fault isolation**: one thread's failure never takes the others down. Each queued task owns its errors (a crashed handler posts a diagnostic into its own thread and the daemon keeps serving), and the daemon holds a last-resort rejection guard because the runtime would otherwise kill the whole process - and every concurrent thread's turn - over a single stray rejection.
- **Graceful shutdown**: SIGTERM/SIGINT drains - new turns are dropped loudly, in-flight turns get up to 5 minutes, and the claude child runs detached in its own process group so a terminal Ctrl-C cannot kill it before the drain preserves the turn.
- **Thread cleanup**: when you tell it the work is done, the model calls an in-process `finish_thread` tool; after the turn fully ends, the daemon drops the thread record, unsubscribes, and posts one confirmation. A fresh mention starts a new session.
- **Error hygiene**: turn errors post trimmed message-only text, never raw error bodies.
