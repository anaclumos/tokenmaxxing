---
title: "La passerelle Slack : xx serve"
description: "xx serve exécute des sessions Claude Code depuis des fils Slack via Socket Mode"
---

`tokenmaxxing serve` exécute un démon Slack local via Socket Mode, sans URL publique requise. Configuration :

```sh
tokenmaxxing serve setup                    # affiche le manifeste de l'app, demande les deux jetons
tokenmaxxing serve link <channel-id> <repo> # lie un canal à un checkout de dépôt
tokenmaxxing serve                          # exécute le démon
```

Mentionnez le bot dans un canal lié et il ouvre une session Claude Code pour ce fil, dans le checkout du dépôt lié. Chaque nouveau tour lance un unique `query()` de l'Agent SDK avec `resume`, de sorte que `ensureBestAccount()` réévalue le pool à chaque tour et que le démon peut redémarrer sans perdre de fils (les enregistrements de fils sont durables ; le démon les réabonne au démarrage), tandis qu'une réponse qui arrive pendant qu'une requête est en cours est intégrée à l'entrée en streaming de cette requête au lieu d'en lancer une nouvelle ; une réponse qui arrive trop tard pour piloter le tour s'exécute comme le tour suivant.

Comportements notables :

- **Pilotage** : une réponse qui arrive pendant que le tour du fil est encore en cours s'intègre à ce tour (la même injection en cours de tour que Claude Code utilise aussi de façon interactive), de sorte que le modèle la voit à sa prochaine frontière d'outil et corrige sa trajectoire au lieu de terminer d'abord la mauvaise chose. Une réponse qui arrive après le dernier appel d'outil du tour s'exécute comme son propre tour juste après ; rien n'est perdu dans un cas comme dans l'autre. Les messages pilotés portent la réaction du sablier et se concluent avec le tour, et leur texte voyage sur le marqueur durable du tour, de sorte que les redémarrages et les reprises après limite d'usage le rejouent. Seul un message mis en file derrière un autre message en attente échappe à cette intégration (l'ordre est préservé), et un démon en cours de vidange continue de rejeter bruyamment plutôt que de piloter.
- **Streaming** : les réponses sont diffusées nativement dans Slack, avec des cartes de tâche pour la réflexion et les exécutions d'outils, du code entre balises rendu avec coloration syntaxique, et une carte « Turn » de clôture avec le coût et la durée ; toutes les cartes d'un tour se replient en un unique bloc de plan dépliable, de sorte qu'un tour se lit normalement comme un seul message : la réponse plus un menu déroulant de son activité (une nouvelle tentative en cours de tour ou un ajout rejeté ouvre un message de suite). Les appels TodoWrite mettent à jour sur place une unique carte de liste de contrôle stable.
- **Permissions** : le `permissionMode` par lien vaut par défaut `acceptEdits` ; `--yolo` (alias `--dangerous`) fait passer un lien en `bypassPermissions`. Les dialogues interactifs sont interdits dans les tours relayés (personne ne peut y répondre via Slack), de sorte que le modèle demande en prose et que votre réponse dans le fil constitue le tour suivant. Un skill de plugin intégré lui apprend à mentionner le demandeur et à terminer le tour lorsqu'il a besoin d'une décision.
- **Réactions de statut** : le message qui a déclenché un tour porte son état sous forme de réaction emoji : un sablier pendant que le tour s'exécute, puis une coche (terminé), une croix (échec) ou un point d'interrogation (le modèle a besoin de votre décision). Nécessite le scope `reactions:write` du manifeste actuel ; les apps existantes doivent recoller le manifeste et réinstaller.
- **Attention et relances** : lorsque le modèle vous demande une décision, il appelle un outil `need_attention` en cours de processus, de sorte que le démon sait que le fil vous attend. Si vous restez silencieux pendant 10 minutes, il vous mentionne une fois dans le fil. Pendant qu'un fil est en attente, réagir à la question est relayé comme votre réponse (un pouce levé choisit l'option recommandée) ; toute autre réaction que vous ajoutez dans un fil suivi est intégrée au tour suivant comme contexte. Nécessite `reactions:read` et l'événement `reaction_added`.
- **Commandes slash** : un message de fil dont le texte nettoyé commence par `/` s'exécute comme une commande slash de claude. Le compositeur de Slack avale les messages commençant par `/`, donc utilisez la forme mention en premier (`@bot /usage`) ou une espace initiale.
- **Reprise automatique après limite d'usage** : lorsque tous les comptes du pool sont à leur limite, une brève interruption met le message en attente et réessaie sur place ; une interruption plus longue publie un avis d'attente et reprend le tour automatiquement une fois le pool rétabli, en survivant aux redémarrages du démon. Seule une limite dont l'heure de récupération est inconnue vous demande de renvoyer votre message.
- **Arrêt gracieux** : SIGTERM/SIGINT vidange : les nouveaux tours sont rejetés bruyamment, les tours en cours disposent de jusqu'à 5 minutes, et l'enfant claude s'exécute détaché dans son propre groupe de processus afin qu'un Ctrl-C de terminal ne puisse pas le tuer avant que la vidange ne préserve le tour.
- **Nettoyage des fils** : lorsque vous lui dites que le travail est terminé, le modèle appelle un outil `finish_thread` en cours de processus ; une fois le tour entièrement terminé, le démon supprime l'enregistrement du fil, se désabonne et publie une confirmation. Une nouvelle mention démarre une nouvelle session.
- **Hygiène des erreurs** : les erreurs de tour publient un texte réduit au seul message, jamais de corps d'erreur bruts.
