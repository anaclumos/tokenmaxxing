同样的汇集机制适用于 OpenAI 的 Codex CLI，针对你自己的 ChatGPT 订阅账户：

```sh
tokenmaxxing init --codex   # 导入你当前的 codex 登录，并安装 codex 监督进程和 Stop hook
tokenmaxxing add --codex    # 以隔离方式登录另一个账户，你的主登录不受影响
codex                       # 像往常一样使用 codex
```

Codex 账户池维护着一套完全独立的状态：有自己的账户索引、自己的停放凭证文件（两个平台上都是 0600 文件，因为 codex 自身的存储就是一个明文文件）、自己的锁、自己的上次切换时间戳。除了决策策略代码之外，它与 Claude 账户池不共享任何东西。

## 为什么 Codex 上无法热切换

正在运行的 codex 进程持有一个内存中的认证管理器，一旦 `auth.json` 指向了另一个账户，就会明确拒绝重新加载。没有文件监视器，也没有按请求的凭证轮询，因此在 codex 运行期间从底层换掉的凭证，对推理根本不会生效。重启就是切换：`codex resume <session-id>` 会在 `auth.json` 当前持有的账户上继续本地转录。

tokenmaxxing 用 codex 监督进程 shim 来处理这一点：Stop hook 在每个回合边界运行同样的贪心进度压力决策，切换时会写入一个标记，让监督进程在已提交的边界 SIGTERM 会话，并在新账户上重新启动 `codex resume <session-id>`，转录完好无损。因为每次 codex 切换都是一次可见的重启，codex 贪心路径带有 1.2 倍的改进裕度：挑战者必须在进度压力上比当前账户高出 20%，而不能只是略微领先。硬路径（越过阈值条）会忽略该裕度。codex 也没有账户池耗尽倒计时（没有什么能暂停 codex 会话），因此彻底耗尽的 codex 账户池会保持不动。

其他 codex 特有的机制：

- 用量来自对 codex 自己的速率限制端点发起的一次免费、经认证的 GET 请求（与 CLI 的 `/status` 所发出的调用相同）：百分比加上绝对纪元重置时间，汇总窗口和按模型上限皆然。窗口分类由时长决定，绝不由位置决定，因为当前套餐可能根本没有 5 小时窗口，而周窗口位于主槽位。
- Codex 刷新 token 会轮换，而重用已被取代的 token 会杀掉整个授权家族。每次轮换一返回就立即持久化，活动账户只通过活动数据块采样（绝不用陈旧的停放副本），而按会话的存在文件确保：正在活动兄弟会话中运行的账户绝不会成为切换目标，其停放 token 也绝不会被刷新。
- Codex 要求使用文件凭证存储：如果固定使用了 keyring 存储，`init --codex` 会快速失败，而 `add --codex` 会把文件模式设置写入隔离的引导 home，让登录以可收集的形态落地。
- 一个手动步骤：codex 会跳过尚未被告知要信任的 hooks。在 `init --codex` 之后，打开一次 codex 并通过 `/hooks` 信任 tokenmaxxing 的 Stop hook，否则自动切换会一直悄悄失效。`init --codex` 会打印这条提醒。
