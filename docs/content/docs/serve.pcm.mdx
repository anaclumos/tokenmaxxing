title: "The Slack bridge: xx serve"
description: "xx serve dey run Claude Code sessions from Slack threads over Socket Mode"
---

`tokenmaxxing serve` dey run one local Slack daemon over Socket Mode - no public URL required. Setup:

```sh
tokenmaxxing serve setup                    # e go print the app manifest, prompt for the two tokens
tokenmaxxing serve link <channel-id> <repo> # tie one channel to one repo checkout
tokenmaxxing serve                          # run the daemon
```

Mention the bot for one linked channel and e go open one Claude Code session for dat thread, for the linked repo checkout. Every new turn dey spawn one fresh Agent SDK `query()` with `resume` - so `ensureBestAccount()` dey re-evaluate the pool for every single turn and the daemon fit restart without losing threads (thread records dey durable; the daemon dey re-subscribe dem for startup) - while one reply wey land while one query still dey run dey enter dat same query im streaming input instead of e dey spawn im own; one reply wey miss the steering window dey run as the next turn.

Notable behavior:

- **Steering**: one reply wey land while the thread turn still dey run dey fold enter dat turn - na the same mid-turn injection wey Claude Code dey use interactively - so the model dey see am for im next tool boundary and e dey adjust course instead of finishing the wrong thing first. One reply wey arrive after the turn last tool call dey run as im own turn right after; nothing no dey drop for either case. Steered messages dey wear the hourglass reaction and dey settle with the turn, and dia text dey ride the turn durable marker, so restarts and usage-limit resumes dey replay am. Na only message wey dey queue behind another waiting message dey skip the fold (order dey preserved), and one draining daemon still dey drop am loudly instead of steering.
- **Streaming**: replies dey stream natively go inside Slack, with task cards for thinking and tool runs, fenced code wey dem render with highlighting, and one closing "Turn" card with cost and duration; all the cards for one turn dey fold enter one expandable plan block, so one turn dey normally read as single message: the reply plus one dropdown wey carry im activity (one retry for mid-turn or one rejected append dey open one follow-on message). TodoWrite calls dey update one stable checklist card for the same place. Slack dey expire native stream for server side after like 30 seconds of silence or 5 minutes of life, wey dey freeze the message as one "Something went wrong" pill, so the daemon dey close any idle or long-life message cleanly before either timer reach, and e go continue for one fresh one.
- **Permissions**: per-link `permissionMode` dey default to `acceptEdits`; `--yolo` (alias `--dangerous`) dey opt one link go inside `bypassPermissions`. Interactive dialogs no dey allowed for relayed turns - nobody fit answer one through Slack - so the model dey ask for prose and your thread reply na the next turn. One bundled plugin skill dey teach am to tag the requester and end the turn when e need a decision.
- **Status reactions**: the message wey trigger one turn dey carry im state as emoji reaction: hourglass while the turn dey run, then check mark (done), one x (failed), or question mark (the model need your decision). E need the `reactions:write` scope from the current manifest; existing apps must re-paste the manifest and reinstall.
- **Attention and nudges**: when the model ask you for one decision e dey call one in-process `need_attention` tool, so the daemon go know say the thread dey wait for you. If you stay quiet for 10 minutes e go tag you once for the thread. While one thread dey wait, if you react to the question e go relay as your answer (thumbs up dey pick the recommended option); any other reaction wey you add for one tracked thread dey fold into the next turn as context. E need `reactions:read` and the `reaction_added` event.
- **Slash commands**: one thread message wey im stripped text start with `/` dey run as one claude slash command. Slack im composer dey chop messages wey start with `/`, so use the mention-first form (`@bot /usage`) or one leading space.
- **Usage-limit auto-resume**: when every pooled account don reach im limit, one short outage dey park the message and retry for the same place; one longer one dey post one holding notice and e go resume the turn automatically once the pool recover - e go survive daemon restarts. Na only limit wey no get known recovery time go ask you to resend.
- **Failure retry**: one turn wey fail without finishing (claude child wey crash, one API error) dey quietly retry up to 2 more times, e dey resume the same session so work wey don finish no go run again; na only after dat one the thread go see the real error. Turn wey im answer don complete no dey ever retry, and failure wey turn out to be pool exhaustion dey hand over give the usage-limit machinery wey dey up there.
- **Fault isolation**: one thread failure no dey ever carry the others go down. Every queued task dey own im own errors (handler wey crash dey post one diagnostic inside im own thread and the daemon dey continue to serve), and the daemon dey hold one last-resort rejection guard because if e no be so, the runtime for don kill the whole process - and every concurrent thread turn - because of one single stray rejection.
- **Graceful shutdown**: SIGTERM/SIGINT dey drain - dem dey drop new turns loudly, in-flight turns dey get up to 5 minutes, and the claude child dey run detached for im own process group so one terminal Ctrl-C no fit kill am before the drain preserve the turn.
- **Thread cleanup**: when you tell am say the work don finish, the model dey call one in-process `finish_thread` tool; after the turn fully end, the daemon dey drop the thread record, unsubscribe, and post one confirmation. One fresh mention dey start one new session.
- **Error hygiene**: turn errors dey post trimmed message-only text, never raw error bodies.
