tokenmaxxing என்பது தானியங்கி Claude Code கணக்கு மாற்றத்திற்கான ஒரு CLI ஆகும். இது நீங்கள் வைத்திருக்கும் பல சந்தா (Pro/Max) கணக்குகளை ஒன்றிணைத்து, பயன்பாட்டில் உள்ள கணக்கு ஒரு பயன்பாட்டு வரம்பை நெருங்கும்போது செயலில் உள்ள சான்றுதலை புத்துணர்ச்சியான கணக்கிற்கு உடனுக்குடன் மாற்றுகிறது. நீங்கள் எப்போதும் போலவே `claude` ஐ இயக்குகிறீர்கள்; மாற்றம் ஒரு பாதுகாப்பான திருப்பு எல்லையில் நிகழ்கிறது, மேலும் உங்கள் இயங்கும் அமர்வு புதிய கணக்கில் அதே உரையாடலை மறுதொடக்கம் இல்லாமல் தொடர்கிறது. இது ஒரே நேரத்தில் பல ஒருங்கிணைந்த அமர்வுகள் நெடுகிலும் வேலை செய்கிறது.

தெரியும் ஒரே நடத்தை மிக மோசமான சூழ்நிலையாகும்: முழு தொகுப்பும் அதன் வரம்பில் இருக்கும்போது, அமர்வு ஒரு எண்ணிக்கையுடன் இடைநிறுத்தப்பட்டு, அடுத்து மீட்டமையும் கணக்கில் தானாகவே மீண்டும் தொடங்கும் (Ctrl-C உடனடியாக மீண்டும் தொடங்குகிறது).

<Callout>
வரம்பு: macOS மற்றும் Linux இல் Claude Code, மேலும் OpenAI இன் Codex CLI ஒரு இரண்டாவது, இணையான தொகுப்பாக. இது API சாவிகளை அல்ல, சந்தா கணக்குகளை ஒன்றிணைக்கிறது. இது நீங்கள் வைத்திருக்கும் கணக்குகளை, நீங்களே இயக்கும் அமர்வுகளிலும் ஏஜென்ட்களிலும் ஒன்றிணைப்பதற்கான ஒரு தனிப்பட்ட-பயன்பாட்டு கருவி - [தனிப்பட்ட பயன்பாடு மற்றும் சேவை விதிமுறைகள்](#personal-use-and-terms-of-service) ஐப் பார்க்கவும்.
</Callout>

## சிக்கல்

ஒரு Claude சந்தா ஒரே நேரத்தில் மூன்று வரம்புகளை அளவிடுகிறது (அனைத்தும் `/usage` வழியாக உறுதிப்படுத்தப்பட்டவை):

- **தற்போதைய அமர்வு**: ஒரு உருளும் 5-மணிநேர சாளரம்.
- **தற்போதைய வாரம் (அனைத்து மாதிரிகள்)**: ஒரு 7-நாள் மொத்தம்.
- **தற்போதைய வாரம், ஒவ்வொரு மாதிரிக்கும்**: தனிப்பட்ட மாதிரி குடும்பங்களுக்கான தனித்தனி வாராந்திர வரம்புகள். இவை தற்போது Sonnet மற்றும் Fable க்கு மட்டுமே உள்ளன, மேலும் Fable வரம்பு மட்டுமே முக்கியமாக இருக்கும் அளவுக்கு இறுக்கமானது - இது மொத்தத்திற்கு நன்கு முன்பே கட்டுப்படுத்துகிறது. ஒரு இயந்திரம் ஏற்கனவே 80% வார-Fable இல் இருக்கும்போது 50% வார-அனைத்து இல் அமர்ந்திருக்க முடியும்.

வாராந்திர ஒதுக்கீடு பயன்படுத்து-அல்லது-இழ: ஒரு கணக்கு அதன் நிலையான வாராந்திர மீட்டமைப்பால் எதை நுகராமல் விடுகிறதோ அது இழக்கப்படுகிறது. நீங்கள் பல கணக்குகளை வைத்திருந்தால், பகுத்தறிவு உத்தி என்னவென்றால், எந்த கணக்கு அதன் சொந்த வாராந்திர வேகத்திற்கு மிகவும் பின்தங்கியிருக்கிறதோ அதில் ஒதுக்கீட்டை எரித்துக்கொண்டே இருப்பதும், அமர்வின் நடுவே எந்த ஒற்றை வரம்பும் சுவரை அடைவதற்கு முன்பு விலகி மாறுவதும் ஆகும்.

அதைக் கையால் செய்வது என்பது வெளியேறுதல், உள்நுழைதல், மற்றும் உங்கள் உரையாடலை இழத்தல் என்று அர்த்தம். tokenmaxxing அதைத் தானியக்கமாக்குகிறது: ஒரு இயங்கும் `claude` கோரிக்கைகளுக்கு இடையே அதன் சான்றுதல் சேமிப்பகத்தை மறுபரிசோதனை செய்கிறது, எனவே அதன் அடியில் மாற்றப்பட்ட ஒரு சான்றுதல் இடத்திலேயே ஏற்றுக்கொள்ளப்படுகிறது (macOS இல் சுமார் 30 வினாடிகளுக்குள், Linux இல் அடுத்த கோரிக்கையில்). ஒரு எளிய மாற்றம் உங்கள் அமர்வை ஒருபோதும் மறுதொடக்கம் செய்யாது. இன்னும் செயல்முறை மேலாண்மை தேவைப்படும் ஒரே சூழ்நிலை முழுமையாக தீர்ந்துபோன தொகுப்பு - ஒரு அமர்வு தன்னைத்தானே இடைநிறுத்த முடியாது - அதற்காகவே மெல்லிய மேற்பார்வையாளர் இருக்கிறார்.

`claude` பற்றிய மற்ற அனைத்தும் மாறாமல் உள்ளன: அனைத்து கொடிகள், MCP சேவையகங்கள், hooks, மற்றும் skills கடந்து செல்கின்றன.

## விரைவுத் தொடக்கம்

macOS அல்லது Linux இல், [Bun](https://bun.sh) மற்றும் Claude Code தேவை.

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` ஐந்து காரியங்களைச் செய்கிறது:

1. நீங்கள் ஏற்கனவே உள்நுழைந்திருக்கும் கணக்கை கணக்கு #1 ஆக இறக்குமதி செய்கிறது (தனி `adopt` கட்டளை எதுவும் இல்லை).
2. `claude` மேற்பார்வையாளர் shim ஐ நிறுவுகிறது.
3. Claude Code இன் `settings.json` இல் மூன்று உள்ளீடுகளை நிறுவுகிறது: ஒரு statusLine, ஒரு Stop hook, மற்றும் ஒரு SessionStart hook (மேலும் ஒரு subagentStatusLine உள்ளீடு).
4. மேற்பார்வையாளரின் bin அடைவை உங்கள் ஷெல் rc இன் PATH இல் இணைக்கிறது (idempotent, ஒரு `# tokenmaxxing PATH` கருத்துடன் குறிக்கப்பட்டது). அதை இடைமறிக்க அது PATH இல் உண்மையான `claude` க்கு முன்பே அமர வேண்டும்.
5. ஒரு காலமுறை சரிபார்ப்பு டைமரை நிறுவுகிறது (macOS இல் ஒரு launchd ஏஜென்ட், Linux இல் ஒரு systemd பயனர் டைமர்), இது ஒவ்வொரு 180 வினாடிகளுக்கும் `tokenmaxxing check` ஐ இயக்குகிறது.

உங்கள் ஷெல்லை மறுதொடக்கம் செய்யுங்கள், பிறகு மேலும் கணக்குகளைச் சேர்த்து செல்லுங்கள்:

```sh
tokenmaxxing add        # இன்னொரு கணக்கை, தனிமையில், உள்நுழைத்து அதை ஒன்றிணைக்கிறது
claude                  # எப்போதும் போலவே claude ஐப் பயன்படுத்துங்கள்
```

`tokenmaxxing` க்கு `xx` என்றும் புனைப்பெயர் உள்ளது. வெறும் `tokenmaxxing` (அல்லது `xx`) `status` ஐ இயக்குகிறது; `switch` வெளிப்படையாகவே இருக்கிறது.

## கட்டளைகள்

| கட்டளை | அது என்ன செய்கிறது |
|---|---|
| `tokenmaxxing init` | தற்போதைய கணக்கை இறக்குமதி செய், மேற்பார்வையாளர், hooks, மற்றும் statusline ஐ நிறுவு |
| `tokenmaxxing init --codex` | Codex க்கும் அதே: உள்நுழைவை இறக்குமதி செய், codex மேற்பார்வையாளர் மற்றும் Stop hook ஐ நிறுவு |
| `tokenmaxxing add` | ஒரு கூடுதல் கணக்கைப் பதிவு செய் (தனிமைப்படுத்தப்பட்ட உள்நுழைவு, தொகுப்பில் அறுவடை செய்யப்பட்டது) |
| `tokenmaxxing add --codex` | ஒரு கூடுதல் Codex கணக்கைப் பதிவு செய் (தனிமைப்படுத்தப்பட்ட உள்நுழைவு) |
| `tokenmaxxing auth [sel \| --all]` | ஒன்றிணைந்த கணக்கை இடத்திலேயே மீண்டும் அங்கீகரி. வெறுமையானது தொகுப்பை பட்டியலிட்டு எதை என்று கேட்கிறது; ஒரு தேர்வி ஒரு கணக்கை இலக்காக்கி எந்த மின்னஞ்சலுடன் உள்நுழைய வேண்டும் என்று சொல்கிறது; `--all` ஒவ்வொரு மீள்-அங்கீகாரம் தேவைப்படும் கணக்கையும் ஒவ்வொன்றாக நடந்து செல்கிறது |
| `tokenmaxxing switch [sel]` | சிறந்த கணக்கிற்கு மாறு (பேராசை, idempotent) அல்லது ஒரு குறிப்பிட்டதை கட்டாயப்படுத்து |
| `tokenmaxxing switch --codex [sel]` | Codex தொகுப்பை மாற்று (அடுத்த codex தொடக்கத்தில் நடைமுறைக்கு வருகிறது) |
| `tokenmaxxing ls` | ஒன்றிணைந்த கணக்குகளை பட்டியலிடு |
| `tokenmaxxing status` | 5h / வாராந்திர / ஒவ்வொரு-மாதிரி பயன்பாட்டுப் பட்டைகள், செயலில் மற்றும் மீட்டமைப்பு-வரை-தீர்ந்த கணக்குகள் |
| `tokenmaxxing status --force` | கூடுதலாக ஒவ்வொரு கணக்கையும் ping செய் (ஒவ்வொன்றும் ஒரு சிறிய haiku கோரிக்கை) அதனால் அனைத்து 5h அமர்வு டைமர்களும் இப்போது தொடங்கும், பிறகு புதிதாக மாதிரி எடு |
| `tokenmaxxing watch [seconds]` | நேரடி நிலை, ஒவ்வொரு N வினாடிகளுக்கும் மீண்டும் காட்டப்படுகிறது (இயல்பு 120, தளம் 30; ஒருபோதும் ping செய்யாது) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | மூலங்களுடன் செயலில் உள்ள கட்டமைப்பு; புள்ளியிட்ட சாவிகளைத் திருத்து; `tidy` தெரியாத சாவிகளை நீக்குகிறது |
| `tokenmaxxing check` | மாற்று முடிவை ஒருமுறை மதிப்பீடு செய் (இதைத்தான் காலமுறை டைமர் இயக்குகிறது) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack பாலம் டீமன் (Socket Mode, பொது URL இல்லை) |
| `tokenmaxxing doctor` | மேற்பார்வையாளர் மற்றும் அமைப்பு உள்ளீடுகள் தப்பிப்பிழைத்தனவா என்று சரிபார் |
| `tokenmaxxing rename [--codex] <sel> <label>` | ஒன்றிணைந்த கணக்கை மறு-அடையாளப்படுத்து |
| `tokenmaxxing rm <sel>` | தொகுப்பிலிருந்து ஒரு கணக்கை அகற்று |
| `tokenmaxxing uninstall` | மேற்பார்வையாளர் மற்றும் அமைப்பு உள்ளீடுகளை அகற்று (கணக்குகள் மற்றும் சான்றுதல்கள் வைத்திருக்கப்படுகின்றன) |

## கட்டமைப்பு (Architecture)

tokenmaxxing என்பது ஒரு பல-அழைப்பு நுழைவுப் புள்ளி (`src/main.ts`), இது அந்தப் பெயரின் கீழ் அழைக்கப்படும்போது `claude` மேற்பார்வையாளராக நடந்துகொள்கிறது, உள் துணைக்கட்டளைகள் வழியாக hook மற்றும் statusline shims ஐ வழங்குகிறது, இல்லையெனில் CLI ஐ அனுப்புகிறது. இது நேரடியாக Bun இன் கீழ் இயங்குகிறது; npm தொகுப்பு ஒரு build ஐ அல்ல, TypeScript மூலத்தை அனுப்புகிறது.

நகரும் பாகங்கள்:

### மேற்பார்வையாளர் shim

`init` `claude` எனப்படும் ஒரு 2-வரி ஷெல் shim ஐ `~/.config/tokenmaxxing/bin/` இல் எழுதி, அந்த அடைவை PATH இல் முதலில் வைக்கிறது. நீங்கள் `claude` என்று தட்டச்சு செய்யும்போது, shim மேற்பார்வையாளரை இயக்குகிறது, இது மரபுரிமையாகப் பெற்ற stdio மற்றும் சேமிக்கப்பட்ட `stty -g` முனைய ஸ்னாப்ஷாட்டுடன் உண்மையான claude பைனரியை உருவாக்குகிறது. இது ஒரு செயல்முறை மற்றும் முனைய மேலாளர் மட்டுமே: இது ஒருபோதும் API போக்குவரத்தை பதிலாள் செய்யாது, மேலும் ஓட்டத்தில் உள்ள டோக்கன்களை ஒருபோதும் தொடாது.

அச்சு-முறை அழைப்புகள் (`claude -p`, `--version`, `--help`), தொடர்பில்லா துணைக்கட்டளைகள் (`claude mcp`, `claude config`, மற்றும் அது போன்றவை), மற்றும் tokenmaxxing இன் சொந்த probes எந்த அமர்வு மேலாண்மையும் இல்லாமல் நேராகக் கடந்து செல்கின்றன. ஒரு தொடர்பாடல் அமர்விற்கு, மேற்பார்வையாளர் ஒரு அமர்வு id ஐ பொருத்துகிறது (ஒன்றை உருவாக்குகிறது, அல்லது `--session-id` / `-r` / `-c` வழியாக நீங்கள் அனுப்பியதை மீண்டும் பயன்படுத்துகிறது), பிற்பாடு ஒரு மறுதொடக்கம் அவற்றை மீண்டும் இயக்க முடியும் என்பதற்காக உங்கள் தொடக்கக் கொடிகளை நிலைத்திருக்கச் செய்கிறது, பிறகு அந்த அமர்விற்குக் குறியிடப்பட்ட ஒரு respawn குறிப்பான் கோப்பைக் கவனிக்கிறது.

### statusline tee

Claude Code ஒவ்வொரு திருப்பத்திலும் rate-limit தரவை (`rate_limits.five_hour` மற்றும் `rate_limits.seven_day`) statusline இன் stdin இல் தள்ளுகிறது. tokenmaxxing statusline இடத்தை சொந்தமாக்குகிறது, எனவே அதன் rendererர் ஒரு இலவச, தள்ளு-அடிப்படையிலான பயன்பாட்டு ஊட்டமாக இரட்டிக்கிறது: ஒவ்வொரு துடிப்பிலும் அது மொத்த சாளரங்களையும் செயலில் உள்ள மாதிரியையும் `usage.json` இல் tee செய்கிறது. ஒவ்வொரு-மாதிரி வரம்புகள் statusline stdin இல் இல்லை; அவை `claude -p '/usage'` (இலவசம், பூஜ்ஜியம் டோக்கன்கள்) இலிருந்து மட்டுமே வருகின்றன, இது ஒரு TTL உடன் poll செய்யப்பட்டு, செயலில் உள்ள மாதிரி கொள்ளளவு-கட்டுப்படுத்தப்படும்போது `model-usage.json` இல் cache செய்யப்படுகிறது.

tee என்பது மாற்றத்தில்-எழுது வகை: புள்ளிவிவரங்கள் மாறாதபோது அது கோப்பின் mtime ஐ மட்டுமே அதிகரிக்கிறது, இது ஊட்டத்தின் உயிர்ப்பு இதயத்துடிப்பாக செயல்படுகிறது. புத்துணர்ச்சி எப்போதும் mtime மூலம் தீர்மானிக்கப்படுகிறது, ஒருபோதும் உட்பொதிக்கப்பட்ட நேர முத்திரையால் அல்ல.

### Stop hook மற்றும் மாற்றம்

ஒவ்வொரு திருப்பு எல்லையிலும், Stop hook மாற்று முடிவை இயக்குகிறது ([மாற்றம் எப்படி முடிவு செய்கிறது](#how-switching-decides) ஐப் பார்க்கவும்). ஒரு மாற்றம் நியாயமானதாக இருக்கும்போது, அது ஒரு `flock(2)` பிரத்யேக பூட்டின் கீழ் நடக்கிறது (macOS எந்த `flock(1)` பைனரியையும் அனுப்பாததால், `bun:ffi` வழியாக எடுக்கப்படுகிறது), மேலும் சான்றுதல் எழுத்துக்கள் கூடுதலாக Claude Code இன் சொந்த refresh பூட்டுடன் ஒன்றிணைந்து பூட்டப்படுகின்றன. முக்கியப் பகுதிக்குள், ஒரு மாற்றம்:

1. தற்போதைய நேரடி சான்றுதலை அதன் உண்மையான உரிமையாளரின் நிறுத்தப்பட்ட காப்புப்பிரதியில் அறுவடை செய்கிறது.
2. இலக்கு கணக்கின் புதிதாக புத்துணர்ச்சி பெற்ற சான்றுதலை நேரடியானதாக நிறுவுகிறது, தற்போதுள்ள நேரடி blob இல் இணைத்து, சகோதர நிலை (ஒவ்வொரு-MCP-சேவையக OAuth டோக்கன்கள் போன்றவை) தப்பிப்பிழைக்கும்படி செய்கிறது.
3. இலக்கின் சுழற்றப்பட்ட டோக்கனை அதன் சொந்த காப்புப்பிரதியில் நிலைநிறுத்துகிறது.
4. `~/.claude.json` இல் உள்ள `oauthAccount` புலத்தை அணு அளவில் மீண்டும் எழுதுகிறது.
5. புதிய செயலில் உள்ள லேபிளை உறுதி செய்து பழைய பயன்பாட்டு ஸ்னாப்ஷாட்களை அழிக்கிறது, இவை அனைத்தும் பூட்டு விடுவிக்கப்படுவதற்கு முன்பே, எனவே ஒரு செயலிழப்பு நிறுவப்பட்ட சான்றுதலையும் செயலில் உள்ள லேபிளையும் வெவ்வேறு கணக்குகளை சுட்டிக்காட்டும் நிலையில் ஒருபோதும் விட்டுவிட முடியாது.

அனைத்து இயல்பு-சுயவிவர அமர்வுகளும் ஒரே நேரடி சான்றுதலைப் பகிர்ந்து கொள்வதால், ஒரே மாற்றம் ஒவ்வொரு அமர்வையும் ஒரே நேரத்தில் இடம்பெயர்க்கிறது, மேலும் flock மற்றும் பூட்டின் கீழ் ஒரு மறுசரிபார்ப்பு போட்டியிடும் hooks இரண்டு கணக்குகளை எரிப்பதைத் தடுக்கிறது.

### இடத்திலேயே ஏற்றுக்கொள்ளல்

ஒரு இயங்கும் claude அமர்வு கோரிக்கைகளுக்கு இடையே அதன் சான்றுதல் சேமிப்பகத்தை poll செய்கிறது: macOS இல் அது ஒரு குறுகிய cache வழியாக keychain ஐ மீண்டும் படித்து அணுகல் டோக்கன்களை ஒப்பிடுகிறது; Linux இல் அது சான்றுதல் கோப்பின் mtime ஐ stat செய்து, மாற்றத்தில் அதன் டோக்கன் caches ஐ ஃப்ளஷ் செய்கிறது. நிகர விளைவு என்னவென்றால், மாற்றப்பட்ட ஒரு சான்றுதல் ஒவ்வொரு இயங்கும் அமர்வாலும் macOS இல் சுமார் 30 வினாடிகளுக்குள்ளும் Linux இல் அடுத்த கோரிக்கையிலேயேயும், எந்த மறுதொடக்கமும் இல்லாமல் ஏற்றுக்கொள்ளப்படுகிறது. இதனால்தான் ஒரு எளிய மாற்றம் எந்த குறிப்பானையும் எழுதுவதில்லை, எந்த respawn ஐயும் தூண்டுவதில்லை - அமர்வு புதிய கணக்கில் தொடர்ந்து செல்கிறது. அமர்வுக்குள் `/usage` அதே டோக்கன் caches ஐப் பகிர்ந்து கொள்கிறது, எனவே அதன் கணக்கு காட்சி ஏற்றுக்கொள்ளலுடன் மாறுகிறது.

### தீர்ந்துபோன-தொகுப்பு காத்திருப்பு மற்றும் தானியங்கி-மீள்தொடக்கம்

தொகுப்பில் உள்ள ஒவ்வொரு கணக்கும் அதன் பட்டைகளுக்கு மேல் இருக்கும்போது மட்டுமே Stop hook ஒரு respawn குறிப்பானை எழுதுகிறது (குறிப்பான் ஸ்கீமாவிற்கு ஒரு `waitUntil` நேர முத்திரை தேவை; ஒரு எளிய மாற்றம் ஒருபோதும் ஒன்றை உருவாக்க முடியாது). மேற்பார்வையாளர் குறிப்பானைப் பார்த்து, ஏற்கனவே-உறுதி செய்யப்பட்ட திருப்பு எல்லையில் அதன் குழந்தையை SIGTERM செய்கிறார் (Stop hook உரைபிரதி வட்டில் இருந்து claude சும்மா இருந்த பிறகு இயங்குகிறது, எனவே எதுவும் இழக்கப்படுவதில்லை), முனையத்தை மீட்டெடுத்து, மிக விரைவான மீட்டமைப்பிற்கு ஒரு எண்ணிக்கையைக் காட்டி, பிறகு மீட்கப்பட்ட கணக்கில் `claude --resume <session-id>` ஐ மீண்டும் இயக்குகிறது. எண்ணிக்கையின் போது Ctrl-C உடனடியாக மீண்டும் தொடங்குகிறது. தானியங்கி-காத்திருப்பு `policy.maxWaitMs` (இயல்பு 1 மணிநேரம்) ஆல் வரம்பிடப்பட்டுள்ளது; அதற்கு அப்பால் முடிவு தொகுப்பை காத்திருப்பதற்குப் பதிலாக தீர்ந்துபோனதாக அறிவிக்கிறது.

### காலமுறை சரிபார்ப்பு டைமர்

Hooks திருப்பு எல்லைகளில் மட்டுமே இயங்குகின்றன, மேலும் ஒரு நீண்ட ஏஜென்டிக் திருப்பு ஒரு சாளரத்தை ஆரோக்கியமான நிலையிலிருந்து தீர்ந்துபோன நிலைக்கு ஒரு எல்லையும் இல்லாமல் எரிக்க முடியும். எனவே `init` ஒரு காலமுறை டைமரையும் நிறுவுகிறது - macOS இல் ஒரு launchd ஏஜென்ட், Linux இல் ஒரு systemd பயனர் டைமர் - இது திருப்பு நடவடிக்கையைப் பொருட்படுத்தாமல் ஒவ்வொரு 180 வினாடிகளுக்கும் `tokenmaxxing check` ஐ இயக்குகிறது.

### ஒரு SessionStart hook

ஒரு அமர்வு தொடங்கும்போது அல்லது மீண்டும் தொடங்கும்போது அதே மதிப்பீட்டை இயக்குகிறது, எனவே ஒரு புதிய அமர்வு சரியான கணக்கில் தொடங்குகிறது. மாற்றத்திற்குப் பிந்தைய குளிர்ச்சிக் காலம் ஒரு respawn க்குப் பிறகு உடனடியாக அதை ஒரு சரியான no-op ஆக்குகிறது.

## மாற்றம் எப்படி முடிவு செய்கிறது [#how-switching-decides]

முடிவுக்கு இரண்டு அடுக்குகள் உள்ளன: ஒரு ஈடுபாட்டு வாயில், பிறகு ஒரு பேராசை அல்லது கடுமையான பாதை.

### ஈடுபாடு

`policy.greedySessionFloor` (இயல்பு 50, 5-மணிநேர அமர்வு சாளரத்தின் சதவீதத்தில்) க்குக் கீழே, முடிவு அறவே இயங்காது - ஒரு புதிய அமர்வு அதன் கணக்கில் சவாரி செய்கிறது. செயலில் உள்ள அமர்வு சாளரம் 50% பயன்படுத்தப்பட்டவுடன், அல்லது ஏதேனும் கடுமையான பட்டை கடக்கப்பட்டவுடன், முடிவு ஈடுபடுகிறது.

### திரையிடல் பட்டைகள்

வரம்புகள் திரையிடல் பட்டைகள், பீதிக்கான தூண்டுதல் அல்ல:

- `thresholds.session`: 95. ஒரு 5-மணிநேர மீட்டமைப்பை உட்கார்ந்து காத்திருப்பது மலிவானது, எனவே அமர்வு சாளரம் முன்னதாகவே விலகி மாறுகிறது.
- `thresholds.weekly`: 98. இந்த ஒற்றைப் பட்டை 7-நாள் மொத்தத்தையும் ஒவ்வொரு-மாதிரி வாராந்திர வரம்பையும் இரண்டையும் உள்ளடக்கியது. வாராந்திர ஒதுக்கீடு பயன்படுத்து-அல்லது-இழ, எனவே அது சுவருக்கு நெருக்கமாக வடிகிறது.

இரண்டும் வேண்டுமென்றே 100 க்குக் கீழே: கணக்கு உண்மையில் அதன் வரம்பை அடைவதற்கு முன்பு ஒரு சுத்தமான திருப்பு எல்லையை (மேலும் macOS இல் ஒரு திருப்பு வரையிலான ஏற்றுக்கொள்ளல் தாமதம்) அடைவதற்கான பட்ஜெட்டே அந்த இடமாகும். அதே பட்டைகள் மாற்று வேட்பாளர்களைத் திரையிடுகின்றன: அதன் பட்டைகள் எதற்கும் மேல் இருக்கும் ஒரு கணக்கு ஒரு செல்லுபடியாகும் இலக்கு அல்ல. தூண்டுதலும் திரையிடலும் எப்போதும் ஒரே செயலில் உள்ள பட்டைகளைப் (வரம்புகள் கழித்தல் `policy.projectionMargin`) பயன்படுத்துகின்றன, ஏனெனில் தூண்டுதலை விட தளர்வான ஒரு திரை, தூண்டுதல் உடனடியாக மீண்டும் கொடியிடும் கணக்குகளில் மாற்றங்களை இறக்கி, தொகுப்பை பிங்-பாங் செய்யும்.

### இலக்கு: வேக அழுத்தம்

பயன்படுத்தக்கூடிய கணக்குகளில், இலக்கு என்பது அதன் சொந்த வாராந்திர வேகத்திற்கு மிகவும் பின்தங்கியிருப்பது: மிக உயர்ந்த **வேக அழுத்தம் (pace pressure)**, இது எஞ்சிய வாராந்திர சதவீதத்தை அந்த கணக்கின் வாராந்திர மீட்டமைப்பு வரையிலான நேரத்தால் வகுத்ததாக வரையறுக்கப்படுகிறது. மிக அதிக ஒதுக்கீடு இழக்கப்படவிருக்கும் கணக்கு வெல்கிறது. சமநிலைகள் மிக விரைவான வாராந்திர காலாவதிக்கு, பிறகு மிகக் குறைந்த 7-நாள் பயன்பாட்டிற்கு உடைகின்றன.

அனைத்தும் முழுமையான UTC epochs ஆக சேமிக்கப்பட்ட cache செய்யப்பட்ட சாளரங்களிலிருந்து இயங்குகிறது, எனவே ஒரு பழைய ஸ்னாப்ஷாட் இன்னும் சரியாகத் தீர்க்கிறது: கடந்துவிட்ட ஒரு வாராந்திர மீட்டமைப்பு சரியாக 7-நாள் படிகளில் முன்னோக்கி வெளிநிரப்பப்படுகிறது, மேலும் அதன் cache செய்யப்பட்ட மீட்டமைப்பைக் கடந்த எந்த சாளரமும் புதிதாக காலியானதாக (மாறுவதற்கான காரணம் ஒருபோதும் அல்ல, ஒரு கணக்கை ஒதுக்கி வைத்திருப்பதற்கான காரணமும் ஒருபோதும் அல்ல) கணக்கிடப்படுகிறது.

### பேராசை vs கடுமையான பாதை

- **பேராசைப் பாதை** (ஈடுபட்டது, ஆனால் ஒவ்வொரு பட்டைக்கும் கீழே): தற்போதையது உட்பட ஒவ்வொரு கணக்கையும் தரவரிசைப்படுத்து. தற்போதைய கணக்கு ஏற்கனவே வென்றாலோ அல்லது சமநிலையிலோ இருந்தால், எதுவும் செய்ய வேண்டாம். இல்லையெனில் கண்டிப்பாக சிறந்த கணக்கிற்கு மாறு. இது ஒருபோதும் காத்திருக்காது, ஒருபோதும் முன்-நிறுத்தம் செய்யாது - பயன்படுத்தக்கூடிய ஒரு தற்போதைய கணக்கு ஒரு காத்திருப்புக்காக பரிமாற்றப்படாது. தற்போதைய கணக்கும் தரவரிசைப்படுத்தப்படுவதால், தானியங்கி பாதையும் வெறும் `tokenmaxxing switch` உம் idempotent: காலமுறையாக மதிப்பீடு செய்வது சரியான கணக்கில் ஒன்றுசேர்ந்து, பிறகு அப்படியே நிற்கிறது.
- **கடுமையான பாதை** (ஒரு பட்டை கடக்கப்பட்டது): சிறந்த பயன்படுத்தக்கூடிய வேட்பாளருக்கு விலகி மாறு. ஒரு வேட்பாளரின் refresh டோக்கன் இறந்துவிட்டதாக மாறினால், அது மீள்-அங்கீகாரம் தேவை என்று கொடியிடப்பட்டு அடுத்த வேட்பாளர் முயற்சிக்கப்படுகிறது. எதுவும் பயன்படுத்த முடியாவிட்டால், தீர்ந்துபோன-காத்திருப்பு தர்க்கம் இயங்குகிறது; அமர்வை உண்மையில் இடைநிறுத்த முடியும் ஒரு அழைப்பாளருக்கு (மேற்பார்வையிடப்பட்ட Stop hook) மட்டுமே இன்னும் தடுக்கப்பட்ட ஆனால் மிக விரைவாக மீட்கப்படும் ஒரு கணக்கில் முன்-நிறுத்த அனுமதிக்கப்படுகிறது.

### ஒவ்வொரு-மாதிரி வரம்புகள்

`policy.switchModels` (இயல்பு `["fable"]`) என்பது ஒரு மாற்றத்தைத் தூண்டக்கூடிய ஒவ்வொரு-மாதிரி வாராந்திர வரம்பைக் கொண்ட மாதிரி குடும்பங்களைப் பெயரிடுகிறது. பொருத்தம் குடும்ப டோக்கன் மூலம், ஒருபோதும் சரியான காட்சி சரம் மூலம் அல்ல: மாதிரி காட்சிப் பெயர்கள் நகர்கின்றன ("Fable" "Fable 5" ஆனது), மேலும் ஒரு சரியான-சரம் வாயில் ஒருமுறை ஒவ்வொரு-மாதிரி மாற்றத்தை அமைதியாக முழுவதுமாக முடக்கியது. இரண்டு தொடர்புடைய பாதுகாப்பு விதிகள்:

- ஒரு தெரியாத செயலில் உள்ள மாதிரி கட்டமைக்கப்பட்ட ஒவ்வொரு குடும்பத்தையும் வாயிலிடுகிறது. ஒரு மாற்றம் ஸ்னாப்ஷாட்களை அழித்த உடனேயே, ஒரு தலையில்லா இயந்திரம் மாதிரி-குருடாக இயங்கலாம்; தெரியாததை கட்டுப்பாடற்றதாகக் கருதுவது ஒருமுறை ஒரு கணக்கை மணிக்கணக்கில் கவனிக்கப்படாமல் அதன் Fable வரம்பில் அமரச் செய்தது.
- வேட்பாளர் திரையிடல் வாயிலிடப்பட்ட ஒவ்வொரு-மாதிரி வரம்புகளையும் கணக்கிடுகிறது, எனவே ஒவ்வொரு கணக்கும் அதன் Fable வரம்பை எரித்திருக்கும் ஒரு தொகுப்பு round-robin செய்யாது.

### குளிர்ச்சிக் காலம்

ஒரு 45-வினாடி மாற்றத்திற்குப் பிந்தைய குளிர்ச்சிக் காலம் தானியங்கி பாதையை வாயிலிடுகிறது. மாற்றத்திற்குப் பிறகு அதே 45 வினாடிகளுக்கு statusline tee அடக்கப்படுகிறது (macOS இல் ஏற்றுக்கொள்ளல் 30 வினாடிகள் வரை எடுக்கிறது), எனவே முந்தைய ஒரு மதிப்பீடு மாற்றமே செல்லாததாக்கிய தரவில் இயங்கும் - அந்த சரியான சூழ்நிலை ஒருமுறை ஒரு A-to-B-and-back respawn வளையத்தை உருவாக்கியது. கையேடு `tokenmaxxing switch` குளிர்ச்சிக் காலத்தால் பாதிக்கப்படுவதில்லை.

## கட்டமைப்பு (Configuration)

கட்டமைப்பு `~/.config/tokenmaxxing/config.json` இல் JSON ஆக உள்ளது. ஒவ்வொரு புலமும் விருப்பமானது; இயல்புகள் ஒவ்வொரு புலத்திற்கும் பொருந்தும்.

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: மேலே விவரிக்கப்பட்ட திரையிடல் பட்டைகள்.
- `policy.projectionMargin`: செயலில் உள்ள பட்டைகளை உருவாக்க இரண்டு பட்டைகளிலிருந்தும் கழிக்கப்படுகிறது.
- `policy.greedySessionFloor`: பேராசை ஒன்றுசேர்தல் ஈடுபடும் அமர்வு-பயன்படுத்தப்பட்ட சதவீதம்.
- `policy.switchModels`: ஒரு மாற்றத்தை வாயிலிடும் ஒவ்வொரு-மாதிரி வாராந்திர வரம்பைக் கொண்ட மாதிரி குடும்பங்கள் (உள்ளீடுகள் ஏற்றப்படும்போது சிறிய எழுத்துக்களாக்கப்படுகின்றன).
- `policy.usagePollTtlMs`: ஒரு `/usage` ஒவ்வொரு-மாதிரி poll எவ்வளவு காலம் புத்துணர்ச்சியாக இருக்கிறது.
- `policy.maxWaitMs`: தீர்ந்துபோன-தொகுப்பு தானியங்கி-காத்திருப்பு வரம்பு.

`tokenmaxxing config` மூலங்களுடன் செயலில் உள்ள கட்டமைப்பைக் காட்டுகிறது; `config set`/`unset` புள்ளியிட்ட சாவிகளைத் திருத்துகிறது; `config tidy` தெரியாத சாவிகளை நீக்குகிறது.

## நிலை அடைவு அமைப்பு

அனைத்தும் `~/.config/tokenmaxxing/` இன் கீழ் வாழ்கிறது (`TOKENMAXXING_HOME` மூலம் மேலெழுதக்கூடியது; வெளிப்புறமாகக் காணக்கூடிய ஒவ்வொரு பாதைக்கும் ஒரு env மேலெழுதல் உள்ளது, எனவே முழு கருவியும் சோதனைகளில் ஹெர்மெடிக்காக இயங்க முடியும்).

| பாதை | இது எதை வைத்திருக்கிறது |
|---|---|
| `config.json` | உங்கள் கட்டமைப்பு (சிதறலானது; ஒவ்வொரு புலத்திற்கும் இயல்புகள் பொருந்தும்) |
| `accounts.json` | ஒன்றிணைந்த Claude கணக்குகளின் இரகசியமற்ற அட்டவணை: லேபிள்கள், ids, cache செய்யப்பட்ட பயன்பாட்டு சாளரங்கள். ஒருபோதும் டோக்கன்கள் அல்ல |
| `usage.json` | statusline tee இன் மொத்த சாளர snapshot; அதன் mtime அந்த feed இன் உயிர்ப்பு இதயத்துடிப்பு |
| `model-usage.json` | `/usage` இலிருந்து TTL-cache செய்யப்பட்ட ஒவ்வொரு-மாதிரி வாராந்திர வரம்புகள் |
| `lastswap.json` | கடைசி மாற்றத்தின் epoch நேரமுத்திரை; 45-வினாடி cooldown ஐ இயக்குகிறது |
| `lock` | மாற்றங்களை வரிசைப்படுத்தும் `flock` கோப்பு |
| `tokenmaxxing.log` | பின்னிணைப்பு-மட்டும் நிகழ்வுப் பதிவு |
| `bin/` | PATH shims: `claude`, `codex`, மற்றும் `tokenmaxxing` / `xx` நுழைவுப் புள்ளிகள் |
| `respawn/<session-id>` | மேற்பார்வையாளர் கண்காணிக்கும் தீர்ந்துபோன-காத்திருப்பு மறுஉருவாக்க குறிப்பான்கள் |
| `creds/` | Linux மட்டும்: நிறுத்தப்பட்ட சான்றுதல் கோப்புகள், ஒரு 0700 அடைவில் 0600 (macOS அதற்குப் பதிலாக சான்றுதல்களை ஒவ்வொரு-கணக்கு keychain உருப்படிகளாக நிறுத்துகிறது) |
| `onboard/`, `sample/` | `add`/`auth` உள்நுழைவுகள் மற்றும் நிறுத்தப்பட்ட-கணக்கு `/usage` probes க்கான தூக்கியெறியும் தனிமைப்படுத்தப்பட்ட கட்டமைப்பு homes; plaintext சான்றுதல்களை வைத்திருக்கும் onboard homes அறுவடைக்குப் பிறகு நீக்கப்படுகின்றன |
| `slack.json` | `xx serve` டோக்கன்கள் மற்றும் சேனல் இணைப்புகள் (0600) |
| `slack-threads/` | `xx serve` க்கான ஒவ்வொரு-த்ரெட் அமர்வுப் பதிவுகள் |
| `codex-*` | இணையான Codex தொகுப்பு: `codex-accounts.json`, `codex-lastswap.json`, `codex-lock`, `codex-creds/`, `codex-onboard/`, `codex-respawn/`, மற்றும் `codex-live/` (இயங்கும் ஒவ்வொரு மேற்பார்வை செய்யப்பட்ட codex அமர்வுக்கும் ஒரு PID-சரிபார்க்கப்பட்ட இருப்புக் கோப்பு, எனவே ஒரு நேரடிக் கணக்கு ஒருபோதும் மாற்று இலக்கு அல்ல) |

அதன் சொந்த அடைவுக்கு வெளியே, tokenmaxxing சரியாக இவற்றை மட்டும் தொடுகிறது: `~/.claude.json` (`oauthAccount` மாற்றம்), Claude Code இன் `settings.json` (hook மற்றும் statusline உள்ளீடுகள்), நேரடி சான்றுதல் சேமிப்பு (macOS இல் `Claude Code-credentials` keychain உருப்படி, Linux இல் `.credentials.json`), `~/.claude.lock` (claude இன் புதுப்பிப்பு lock, மாற்றங்களின் போது எடுக்கப்படுகிறது), codex இன் `auth.json` மற்றும் `hooks.json`, மற்றும் launchd அல்லது systemd இல் உள்ள காலமுறை-சரிபார்ப்பு அலகு.

## சான்றுதல் சேமிப்பு மற்றும் பாதுகாப்பு மாதிரி

அனைத்து நிலையும் `~/.config/tokenmaxxing/` இல் வாழ்கிறது. சான்றுதல் I/O ஒரு ஒற்றை தளம்-தேர்ந்தெடுக்கப்பட்ட சேமிப்பு முகப்பு வழியாகச் செல்கிறது; அழைப்பு தளங்கள் ஒருபோதும் தளத்தில் கிளைபிரியாது.

**macOS**: சான்றுதல்கள் உள்நுழைவு keychain இல் generic-password உருப்படிகளாக வாழ்கின்றன, Claude Code தானே அவற்றை வைத்திருக்கும் இடத்துடன் பொருந்துகிறது. நேரடி உருப்படியே claude படிக்கிறது; ஒவ்வொரு ஒன்றிணைந்த கணக்கின் காப்புப்பிரதியும் அதன் சொந்த `tokenmaxxing-cred-<uuid8>` keychain உருப்படியாக நிறுத்தப்படுகிறது. வட்டில் எதுவும் plaintext அல்ல. வாசிப்புகள் `security find-generic-password -w` ஐப் பயன்படுத்துகின்றன (இரகசியம் எப்போதும் stdout இல் மட்டுமே தோன்றுகிறது); எழுத்துக்கள் ஒரு `add-generic-password` வரியை stdin மீது `security -i` இல் pipe செய்கின்றன, எனவே இரகசியம் எந்த செயல்முறையின் argv இலும் தோன்றுவதில்லை. தொடர்பாடல் முறையில் தோராயமாக ஒரு 4 KB வரி இடையகம் உள்ளது, எனவே அளவுக்கு அதிகமான blobs ஒரு argv எழுத்திற்கு மீளுகின்றன - நிறுத்தப்பட்ட உருப்படிகள் குறைந்தபட்ச OAuth பொருளை மட்டுமே சேமிப்பதற்கான ஒரு காரணம்.

**Linux**: Claude Code சான்றுதல்களை ஒரு 0600 plaintext கோப்பாக சேமிக்கிறது, மேலும் tokenmaxxing அதே மாதிரியைப் பின்பற்றுகிறது: நேரடி கோப்பே claude இன் சொந்த `.credentials.json`, மேலும் நிறுத்தப்பட்ட காப்புப்பிரதிகள் ஒரு 0700 அடைவில் `~/.config/tokenmaxxing/creds/` க்குக் கீழ் அணு 0600 கோப்புகள். இங்கே அணு என்றால் தற்காலிகத்தில்-எழுது, fsync, பிறகு மறுபெயரிடு: ஒரு ஒரே நேர வாசகர் எப்போதும் ஒரு முழு பழைய அல்லது முழு புதிய கோப்பைப் பார்க்கிறார், ஒருபோதும் ஒரு பகுதியை அல்ல.

மாற்றம் அமல்படுத்தும் பாதுகாப்பு விதிகள்:

- **உண்மையான உரிமையாளரால் அறுவடை.** ஒரு மாற்றத்திற்கு முன், நேரடி சான்றுதலின் உண்மையான உரிமையாளர், டோக்கன் எந்த நிறுவனத்திற்குச் சொந்தமானது என்று API ஐக் கேட்பதன் மூலம் தீர்க்கப்படுகிறது (`fetchTokenOrg` OAuth roles endpoint க்கு எதிராக) - சேமிக்கப்பட்ட செயலில் உள்ள லேபிளை நம்புவதன் மூலம் ஒருபோதும் அல்ல, அது நகரக்கூடும். ஒரு நகர்ந்த லேபிள் ஒருமுறை ஒரு கணக்கின் அறுவடை மற்றொரு கணக்கின் ஒரே காப்புப்பிரதியை மேலெழுதச் செய்தது. நேரடி சான்றுதல் தொகுப்பிற்கு வெளியே உள்ள ஒரு கணக்கிற்குச் சொந்தமானதாக இருந்தால், மாற்றம் அதை மேலெழுதுவதற்குப் பதிலாக நேரடியாக மறுக்கிறது.
- **ஒரு முக்கியப் பகுதி.** அறுவடை, புதிய சான்றுதலின் நிறுவல், அதன் சுழற்றப்பட்ட டோக்கனின் காப்புப்பிரதி, `~/.claude.json` கணக்கு மாற்றம், மற்றும் செயலில் உள்ள லேபிள் உறுதிப்படுத்தல் ஆகியவை அனைத்தும் அதே பூட்டப்பட்ட பகுதிக்குள் நடக்கின்றன.
- **claude இன் சொந்த refresh உடன் ஒன்றிணைந்த பூட்டு.** ஒரு காலாவதிக்கு அருகிலுள்ள அமர்வு எந்த நேரத்திலும் அதன் சொந்த டோக்கனை சுழற்றக்கூடும், எனவே சான்றுதல் எழுத்துக்களும் Claude Code இன் refresh பூட்டை எடுக்கின்றன (சிறந்த-முயற்சி, ஒரு பழைய-பூட்டு மீட்பு மற்றும் ஒரு வரம்புக்குட்பட்ட நேரவரம்புடன்).
- **இறந்த மானியங்கள் சுத்தமாகச் சீரழிகின்றன.** `invalid_grant` உடன் திரும்பும் ஒரு refresh அந்த கணக்கை மீள்-அங்கீகாரம் தேவை என்று கொடியிட்டு, பிழை பரவுவதற்கு முன்பு கொடியை நிலைநிறுத்துகிறது, எனவே மறுமுயற்சி வளையங்கள் வேட்பாளர் தொகுப்பைச் சுருக்கி முடிவடைகின்றன. `tokenmaxxing auth` ஒரு கொடியிடப்பட்ட கணக்கை இடத்திலேயே சரிசெய்கிறது, மேலும் சரிசெய்யப்படும் கணக்கிலிருந்து வேறுபட்ட கணக்கில் இறங்கும் ஒரு உள்நுழைவை அது மறுக்கிறது.
- **டோக்கன் பதிவு இல்லை.** டோக்கன்கள் ஒருபோதும் பதிவுகள், பிழைகள், அல்லது வெளியீட்டில் தோன்றுவதில்லை. டோக்கன் மற்றும் பயன்பாட்டு endpoints இலிருந்து பிழை உடல்கள் ஒருபோதும் மூலமாக வெளிப்படுத்தப்படுவதில்லை; ஒரு அனுமதிப்பட்டியலிடப்பட்ட புலங்களின் தொகுப்பு மட்டுமே தப்பிப்பிழைக்கிறது, ஏனெனில் ஒரு டோக்கன் endpoint இன் தோல்வி உடல் கோரிக்கைப் பொருளை எதிரொலிக்கக்கூடும்.
- **Probe சுகாதாரம்.** எந்த உருவாக்கப்பட்ட `claude` probe உம், claude தன் keychain தேடலுக்கு முன்பு மதிக்கும் எட்டு சூழல் மாறிகளை (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, மற்றும் அது போன்றவை) துடைக்கிறது, எனவே ஒரு probe ஒருபோதும் தவறான கணக்கிற்குக் கூறப்பட முடியாது.

## தள குறிப்புகள்: macOS vs Linux

| | macOS | Linux |
|---|---|---|
| நேரடி சான்றுதல் | உள்நுழைவு keychain generic-password உருப்படி | 0600 `.credentials.json` கோப்பு |
| நிறுத்தப்பட்ட சான்றுதல்கள் | ஒவ்வொரு-கணக்கு keychain உருப்படிகள் | 0700 அடைவில் 0600 கோப்புகள் |
| மாற்றத்திற்குப் பிந்தைய ஏற்றுக்கொள்ளல் | ~30 வினாடிகளுக்குள் (keychain வாசிப்பு cache) | அடுத்த கோரிக்கை (கோப்பு mtime poll) |
| காலமுறை சரிபார்ப்பு | launchd ஏஜென்ட், ஒவ்வொரு 180s | systemd பயனர் டைமர், ஒவ்வொரு 180s |
| தனிமைப்படுத்தப்பட்ட-உள்நுழைவு சேமிப்பு | ஒவ்வொரு config அடைவுக்கும் Hash-namespace செய்யப்பட்ட keychain சேவை | தனிமைப்படுத்தப்பட்ட config அடைவுக்குள் ஒரு கோப்பு |

தெரிந்துகொள்ள மதிப்புள்ள இரண்டு Linux-குறிப்பிட்ட விவரங்கள்: claude அதன் சான்றுதல் அடைவை முதலில் `CLAUDE_SECURESTORAGE_CONFIG_DIR` இலிருந்து தீர்க்கிறது (பிறகு `CLAUDE_CONFIG_DIR`, பிறகு `~/.claude`), மேலும் tokenmaxxing அந்தத் தீர்வை சரியாகப் பிரதிபலிக்கிறது, எனவே இரண்டும் ஒருபோதும் ஒத்திசைவு இழக்காது. மேலும் அதே claude பதிப்பின் இரண்டு OS builds `/usage` மீட்டமைப்பு கடிகாரங்களை வித்தியாசமாக வடிவமைக்கின்றன (ஒன்று " at " பசையைப் பயன்படுத்துகிறது, மற்றொன்று ஒரு காற்புள்ளி); tokenmaxxing இன் parser சரியாக அந்த இரண்டு வடிவங்களையும் ஏற்றுக்கொண்டு, மூன்றாவது எதிலும் ஊகிப்பதற்குப் பதிலாக பதிவு செய்கிறது.

macOS இல், ஒரு நேர்மையான வரம்பு: `init` மற்றும் `add` வேண்டுமென்றே keychain ஐ தொடர்பாடலாகத் தொடுகின்றன, எனவே முதல் `security` அணுகல் ஒரு தலையில்லா hook இனுள் குளிராக இருக்காது.

## statusline

tokenmaxxing Claude Code இன் statusline ஐ இயல்பாக render செய்கிறது (பயன்பாட்டு ஊட்டத்தை tee செய்யும்போது). வடிவமைப்புக் கொள்கை: ஒதுக்கீடு எண்களில் அல்ல, நிறத்தில் சுமக்கப்படுகிறது. ஒரு வரி, உதாரணமாக:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- ஒவ்வொரு சாளர டோக்கனும் அதன் மீட்டமைப்பு-வரையிலான-நேரம், பயன்படுத்தப்பட்ட சதவீதத்தால் தொடர்ச்சியான பச்சை-இருந்து-மஞ்சள்-இருந்து-சிவப்பு சாய்வில் வர்ணம் தீட்டப்படுகிறது (முனையம் ஆதரிக்கும்போது truecolor, இல்லையெனில் 256-நிற கனசதுரத்தில் படிக்கப்படுகிறது). சாய்வு 0 க்கு தூய பச்சையிலும், 75 இல் மஞ்சளிலும், 95 இலும் அதற்கு மேலும் சிவப்பிலும் நங்கூரமிடுகிறது, எனவே பழைய தீவிரப் பட்டைகள் சாய்வு நங்கூரங்களாக தப்பிப்பிழைக்கின்றன.
- மாதிரிப் பெயர் அதே சாய்வில் சூழல்-சாளர நிரப்பால் வர்ணம் தீட்டப்படுகிறது.
- ஒரு பச்சை `◆` செயலில் உள்ள கணக்கின் சாளரங்களை வழிநடத்துகிறது; ஒவ்வொரு நிறுத்தப்பட்ட கணக்கும் அதன் சொந்த cyan `◇` ஐப் பெறுகிறது (மீள்-அங்கீகாரம் தேவைப்பட்டால் சிவப்பு `✗`). கணக்குகள் மிக விரைவில் வரவிருக்கும் மீட்டமைப்பால் வரிசைப்படுத்தப்படுகின்றன.
- ஒவ்வொரு-மாதிரி ஒவ்வொரு தொகுதியிலும் ஒரு வெறும் வர்ணம் தீட்டப்பட்ட முதலெழுத்தாக முதலில் வருகிறது: Fable `𝒇` ஆக render செய்கிறது; மற்ற குடும்பங்கள் தங்கள் பெரிய எழுத்தான முதலெழுத்தைப் பயன்படுத்துகின்றன, எப்போதும் குடும்பம்-பொருத்தப்பட்டது.
- தொடப்படாத ஒரு நிறுத்தப்பட்ட கணக்கு ஒரு பச்சை `full` ஐ render செய்கிறது. தெரியாத மீட்டமைப்புடன் அளவிடப்பட்ட பயன்பாடு ஒரு வர்ணம் தீட்டப்பட்ட `?` ஐ render செய்கிறது, மேலும் ஒரு வாயிலிடப்பட்ட மாதிரியில் அளவிடப்படாத ஒவ்வொரு-மாதிரி வரம்பு ஒரு வர்ணம் தீட்டப்படாத `𝒇?` ஐ render செய்கிறது - அளவிடப்படாதது ஒருபோதும் பாதுகாப்பானதாகத் தெரியக்கூடாது.
- மீட்டமைப்பு எண்ணிக்கைகள் மிகப்பெரிய அலகை மட்டுமே காட்டுகின்றன, ஒருபோதும் "now" அல்லது "0m" அல்ல; வரவிருக்கும் மீட்டமைப்பு இல்லாத ஒரு சாளரம் ஒரு பச்சை `0` ஐ (மீண்டும் காலியானது) render செய்கிறது.
- இணைக்கப்பட்ட ஒரு git worktree இன் basename வரியை வழிநடத்துகிறது; ஒரு பிரதான checkout அங்கே எதையும் render செய்யாது. கண்டறிதல் ஒரு `.git` கோப்பிற்காக கோப்பு அமைப்பைப் படிக்கிறது, ஒருபோதும் ஒரு git துணைச்செயல்முறையை உருவாக்காது.
- `NO_COLOR` அமைக்கப்பட்டால், வரி ஒரு பசையிடப்பட்ட எண் வடிவத்திற்கு (`2h5` என்றால் 2 மணிநேரத்தில் மீட்டமைகிறது, 5% பயன்படுத்தப்பட்டது; சூழல் நிரப்பிற்கு `ctx 42`) மீளுகிறது - நிறம் இல்லாமல், வடிந்த ஒரு சாளரம் புத்துணர்ச்சியாகத் தெரியக்கூடாது.

subagent பணிகள் claude இன் subagentStatusLine மேற்பரப்பு வழியாக தங்கள் சொந்த panel வரிசைகளைப் பெறுகின்றன: ஒவ்வொரு செயலில் உள்ள பணிக்கும் ஒரு வரிசை, அந்தப் பணியின் சூழல் நிரப்பால் வர்ணம் தீட்டப்பட்ட குடும்பப் பெயர்.

## Codex ஆதரவு

அதே ஒன்றிணைத்தல் OpenAI இன் Codex CLI க்கு, உங்கள் சொந்த ChatGPT-சந்தா கணக்குகளுக்கு எதிராக வேலை செய்கிறது:

```sh
tokenmaxxing init --codex   # உங்கள் தற்போதைய codex உள்நுழைவை இறக்குமதி செய் + codex மேற்பார்வையாளர் & Stop hook ஐ நிறுவு
tokenmaxxing add --codex    # இன்னொரு கணக்கை உள்நுழை, தனிமைப்படுத்தப்பட்டது - உங்கள் முதன்மை உள்நுழைவு தொடப்படவில்லை
codex                       # எப்போதும் போலவே codex ஐப் பயன்படுத்துங்கள்
```

Codex தொகுப்பு முழுமையாக இணையான நிலை: அதன் சொந்த கணக்குகள் அட்டவணை, அதன் சொந்த நிறுத்தப்பட்ட சான்றுதல் கோப்புகள் (இரண்டு தளங்களிலும் 0600 கோப்புகள், ஏனெனில் codex இன் சொந்த சேமிப்பு ஒரு plaintext கோப்பு), அதன் சொந்த பூட்டு, அதன் சொந்த கடைசி-மாற்ற நேர முத்திரை. முடிவு-கொள்கை குறியீட்டைத் தவிர எதுவும் Claude தொகுப்புடன் பகிரப்படவில்லை.

### Codex இல் ஏன் உடனுக்குடன் மாற்றம் சாத்தியமில்லை

ஒரு இயங்கும் codex செயல்முறை ஒரு நினைவகத்திலுள்ள auth மேலாளரை வைத்திருக்கிறது, மேலும் அது இப்போது வேறு கணக்கைப் பெயரிடும்போது `auth.json` ஐ மீண்டும் ஏற்ற வெளிப்படையாக மறுக்கிறது. எந்த கோப்பு கண்காணிப்பாளரும் இல்லை, எந்த ஒவ்வொரு-கோரிக்கை சான்றுதல் poll உம் இல்லை, எனவே ஒரு இயங்கும் codex இன் அடியில் மாற்றப்பட்ட ஒரு சான்றுதல் அனுமானத்திற்கு வெறுமனே ஒருபோதும் நடைமுறைக்கு வராது. மறுதொடக்கமே மாற்றம்: `codex resume <session-id>` `auth.json` இப்போது வைத்திருக்கும் எந்த கணக்கிலும் உள்ளூர் உரைபிரதியைத் தொடர்கிறது.

tokenmaxxing இதை ஒரு codex மேற்பார்வையாளர் shim மூலம் கையாளுகிறது: Stop hook ஒவ்வொரு திருப்பு எல்லையிலும் அதே பேராசை வேக-அழுத்த முடிவை இயக்குகிறது, மேலும் அது மாறும்போது, மேற்பார்வையாளர் உறுதி செய்யப்பட்ட எல்லையில் அமர்வை SIGTERM செய்து புதிய கணக்கில் `codex resume <session-id>` ஐ மீண்டும் இயக்கச் செய்யும் ஒரு குறிப்பானை எழுதுகிறது, உரைபிரதி அப்படியே. ஒவ்வொரு codex மாற்றமும் ஒரு தெரியும் மறுதொடக்கமாக இருப்பதால், codex பேராசைப் பாதை ஒரு 1.2x முன்னேற்ற வரம்பைச் சுமக்கிறது: ஒரு போட்டியாளர் தற்போதைய கணக்கின் வேக அழுத்தத்தை 20% ஆல் அடிக்க வேண்டும், ஒரு முடி அளவால் அல்ல. கடுமையான பாதை (ஒரு கடக்கப்பட்ட பட்டை) வரம்பைப் புறக்கணிக்கிறது. codex க்கு தீர்ந்துபோன-தொகுப்பு எண்ணிக்கையும் இல்லை - எதுவும் ஒரு codex அமர்வை இடைநிறுத்த முடியாது - எனவே முழுமையாக தீர்ந்துபோன ஒரு codex தொகுப்பு அப்படியே நிற்கிறது.

பிற codex-குறிப்பிட்ட இயங்குமுறைகள்:

- பயன்பாடு codex இன் சொந்த rate-limit endpoint க்கு எதிராக ஒரு இலவச அங்கீகரிக்கப்பட்ட GET இலிருந்து படிக்கப்படுகிறது (CLI இன் `/status` செய்யும் அதே அழைப்பு): சதவீதங்கள் மற்றும் முழுமையான epoch மீட்டமைப்பு நேரங்கள், மொத்த சாளரங்கள் மற்றும் ஒவ்வொரு-மாதிரி வரம்புகள் அனைத்தும். சாளர வகைப்பாடு காலம்-உந்தப்பட்டது, ஒருபோதும் நிலை-உந்தப்பட்டது அல்ல, ஏனெனில் தற்போதைய திட்டங்களுக்கு எந்த 5-மணிநேர சாளரமும் இல்லாதிருக்கக்கூடும், மேலும் வாராந்திர சாளரம் முதன்மை இடத்தில் அமர்கிறது.
- Codex refresh டோக்கன்கள் சுழல்கின்றன, மேலும் மூத்துப்போன ஒன்றை மீண்டும் பயன்படுத்துவது முழு மானியக் குடும்பத்தையும் கொல்கிறது. ஒவ்வொரு சுழற்சியும் அது திரும்பும் நொடியில் நிலைநிறுத்தப்படுகிறது, செயலில் உள்ள கணக்கு எப்போதும் நேரடி blob வழியாக மட்டுமே மாதிரி எடுக்கப்படுகிறது (ஒருபோதும் ஒரு பழைய நிறுத்தப்பட்ட நகல் அல்ல), மேலும் ஒவ்வொரு-அமர்வு இருப்பு கோப்புகள் ஒரு நேரடி சகோதர அமர்வில் இயங்கும் ஒரு கணக்கு ஒருபோதும் மாற்று இலக்கு அல்ல, அதன் நிறுத்தப்பட்ட டோக்கன் ஒருபோதும் புத்துணர்ச்சி பெறாது என்பதை உறுதிசெய்கின்றன.
- Codex க்கு கோப்பு சான்றுதல் சேமிப்பு தேவை: keyring சேமிப்பு பொருத்தப்பட்டிருந்தால் `init --codex` விரைவாகத் தோல்வியடைகிறது, மேலும் `add --codex` தனிமைப்படுத்தப்பட்ட onboarding home இல் கோப்பு-முறை அமைப்பை எழுதுகிறது, எனவே உள்நுழைவு அறுவடை செய்யக்கூடியதாக இறங்குகிறது.
- ஒரு கையேடு படி: codex தான் நம்பச் சொல்லப்படாத hooks ஐத் தவிர்க்கிறது. `init --codex` க்குப் பிறகு, codex ஐ ஒருமுறை திறந்து `/hooks` வழியாக tokenmaxxing Stop hook ஐ நம்புங்கள், இல்லையெனில் தானியங்கி-மாற்றம் அமைதியாக செயலிழந்தே இருக்கும். `init --codex` இந்த நினைவூட்டலை அச்சிடுகிறது.

## Slack பாலம்: xx serve

`tokenmaxxing serve` Socket Mode மீது ஒரு உள்ளூர் Slack டீமனை இயக்குகிறது - எந்த பொது URL உம் தேவையில்லை. அமைப்பு:

```sh
tokenmaxxing serve setup                    # ஆப் manifest ஐ அச்சிடுகிறது, இரண்டு டோக்கன்களைக் கேட்கிறது
tokenmaxxing serve link <channel-id> <repo> # ஒரு channel ஐ ஒரு repo checkout உடன் இணைக்கிறது
tokenmaxxing serve                          # டீமனை இயக்கு
```

இணைக்கப்பட்ட ஒரு channel இல் botஐ mention செய்யுங்கள், அது அந்த thread க்கு, இணைக்கப்பட்ட repo checkout இல் ஒரு Claude Code அமர்வைத் திறக்கிறது. ஒவ்வொரு thread செய்தியும் `resume` உடன் ஒரு Agent SDK `query()` ஐ இயக்குகிறது - ஒருபோதும் ஒரு நிலையான ஸ்ட்ரீமிங் query அல்ல - எனவே `ensureBestAccount()` ஒவ்வொரு ஒற்றைத் திருப்பிலும் தொகுப்பை மறுமதிப்பீடு செய்கிறது மற்றும் threads ஐ இழக்காமல் டீமன் மறுதொடக்கம் செய்ய முடியும் (thread பதிவுகள் நீடித்தவை; டீமன் தொடக்கத்தில் அவற்றை மீண்டும் சந்தா செய்கிறது).

குறிப்பிடத்தக்க நடத்தை:

- **ஸ்ட்ரீமிங்**: பதில்கள் Slack இல் இயல்பாக ஸ்ட்ரீம் செய்கின்றன, சிந்தனை மற்றும் கருவி இயக்கங்களுக்கான பணி அட்டைகள், ஹைலைட்டிங்குடன் render செய்யப்பட்ட வேலிட்ட குறியீடு, செலவு மற்றும் கால அளவுடன் ஒரு நிறைவு "Turn" அட்டை, மற்றும் ஒரு கருவி இயக்கம் ஸ்ட்ரீம் செய்யப்பட்ட உரையை இடைமறிக்கும் போதெல்லாம் திறக்கப்படும் ஒரு புதிய Slack செய்தி, எனவே ஒரு திருப்பு கருவி இயக்கங்களைச் சுற்றி தனித்தனி செய்திகளாகப் படிக்கிறது. TodoWrite அழைப்புகள் ஒரு நிலையான checklist அட்டையை இடத்திலேயே புதுப்பிக்கின்றன.
- **அனுமதிகள்**: ஒவ்வொரு-இணைப்பு `permissionMode` இயல்பாக `acceptEdits`; `--yolo` (புனைப்பெயர் `--dangerous`) ஒரு இணைப்பை `bypassPermissions` இல் தேர்ந்தெடுக்கிறது. தொடர்பாடல் உரையாடல்கள் திருப்பப்பட்ட திருப்புகளில் அனுமதிக்கப்படுவதில்லை - Slack வழியாக யாராலும் ஒன்றுக்கு பதிலளிக்க முடியாது - எனவே மாதிரி உரைநடையில் கேட்கிறது, உங்கள் thread பதிலே அடுத்த திருப்பாகும். ஒரு தொகுக்கப்பட்ட plugin skill, ஒரு முடிவு தேவைப்படும்போது கோரிக்கையாளரை tag செய்து திருப்பை முடிக்க அதற்குக் கற்பிக்கிறது.
- **Slash கட்டளைகள்**: ஒரு thread செய்தியின் துடைக்கப்பட்ட உரை `/` இல் தொடங்கினால் அது ஒரு claude slash கட்டளையாக இயங்குகிறது. Slack இன் composer `/` இல் தொடங்கும் செய்திகளை உண்கிறது, எனவே mention-முதல் வடிவத்தை (`@bot /usage`) அல்லது ஒரு முன்னணி இடைவெளியைப் பயன்படுத்துங்கள்.
- **அழகான பணிநிறுத்தம்**: SIGTERM/SIGINT வடிகட்டுகிறது - புதிய திருப்புகள் சத்தமாக கைவிடப்படுகின்றன, ஓட்டத்தில் உள்ள திருப்புகள் 5 நிமிடங்கள் வரை பெறுகின்றன, மேலும் claude குழந்தை அதன் சொந்த செயல்முறை குழுவில் பிரிக்கப்பட்டு இயங்குகிறது, எனவே ஒரு முனைய Ctrl-C அது வடிகட்டல் திருப்பைப் பாதுகாக்கும் முன் அதைக் கொல்ல முடியாது.
- **Thread சுத்தம்**: வேலை முடிந்துவிட்டது என்று நீங்கள் அதற்குச் சொல்லும்போது, மாதிரி ஒரு செயல்முறைக்குள்ளான `finish_thread` கருவியை அழைக்கிறது; திருப்பு முழுமையாக முடிந்த பிறகு, டீமன் thread பதிவைக் கைவிட்டு, சந்தாவை நீக்கி, ஒரு உறுதிப்படுத்தலை இடுகிறது. ஒரு புதிய mention ஒரு புதிய அமர்வைத் தொடங்குகிறது.
- **பிழை சுகாதாரம்**: திருப்பு பிழைகள் ஒழுங்குபடுத்தப்பட்ட செய்தி-மட்டும் உரையை இடுகின்றன, ஒருபோதும் மூல பிழை உடல்களை அல்ல.

## Agent SDK மேற்பரப்பு

தொகுப்பின் நிரலாக்க நுழைவு (`exports["."]` `src/sdk.ts` ஐ சுட்டிக்காட்டுகிறது) உங்கள் சொந்த ஒன்றிணைந்த கணக்குகளுக்கு எதிராக நீங்கள் கட்டமைக்கும் ஏஜென்ட்களுக்கு tokenmaxxing ஐ Claude Agent SDK உடன் இணைக்கிறது. உங்கள் ஆப் Bun இன் கீழ் இயங்க வேண்டும் (tokenmaxxing TypeScript மூலத்தை அனுப்புகிறது மற்றும் `bun:ffi` ஐப் பயன்படுத்துகிறது).

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK ஒவ்வொரு `query()` க்கும் ஒரு claude துணைச்செயல்முறையை உருவாக்கி, spawn இல் ஒருமுறை சான்றுதல்களைப் படிக்கிறது - எந்த statusline உம் இல்லை, எந்த query-நடு உடனுக்குடன் மாற்றமும் இல்லை - எனவே ஒருங்கிணைப்பு எல்லை-உந்தப்பட்டது:

- `ensureBestAccount()` என்பது CLI hooks மற்றும் டைமர் இயக்கும் அதே முடிவு (பட்டைகள், வேக அழுத்தம், குளிர்ச்சிக் காலம், அனைத்தும் பகிரப்பட்ட குறியீடு), ஒருபோதும் முன்கணிப்பானது அல்ல: ஒரு SDK அமர்வை தீர்ந்துபோன எண்ணிக்கைக்காக ஒருபோதும் இடைநிறுத்த முடியாது.
- `pooledOptions()` `pathToClaudeCodeExecutable` ஐ உண்மையான claude பைனரிக்கு (ஒருபோதும் மேற்பார்வையாளர் wrapper க்கு அல்ல) பொருத்துகிறது, மேலும் ஒவ்வொரு சூழல் சான்றுதல் மேலெழுதலும் துடைக்கப்பட்ட ஒரு முழு மாற்று `env` ஐ வழங்குகிறது. உங்கள் ஆப்பின் சூழலில் `CLAUDE_CONFIG_DIR` அல்லது `CLAUDE_SECURESTORAGE_CONFIG_DIR` அமைக்கப்பட்டிருந்தால் அது விரைவாகத் தோல்வியடைகிறது: Linux இல் ஒரு மாற்றம் அவை சுட்டிக்காட்டும் இடத்தில் நேரடி சான்றுதலை எழுதும் அதே சமயம் துடைக்கப்பட்ட துணைச்செயல்முறை இயல்பு சேமிப்பைப் படிக்கும், ஒரு அமைதியான தவறான-கணக்கு ஒத்திசைவின்மை.
- `stopHookCheck` திருப்பு எல்லைகளில் முடிவை மீண்டும் இயக்குகிறது; அது இறக்கும் ஒரு மாற்றம் அடுத்த spawn இல் நடைமுறைக்கு வருகிறது. இது தன் சொந்த பிழைகளைப் பிடிக்கிறது (stderr மற்றும் பதிவுக்கு பதிவிடுகிறது) மீண்டும் எறிவதற்குப் பதிலாக, ஏனெனில் கையாளப்படாத ஒரு hook விதிவிலக்கு ஏஜென்ட்டை இடைமறிக்கக்கூடும், மேலும் ஒரு உடைந்த மாற்றுச் சரிபார்ப்பின் மீது ஒரு திருப்பை நிறுத்துவது தற்போதைய கணக்கில் சவாரி செய்வதை விட அதிக செலவாகும்.

`sdk.ts` Agent SDK இலிருந்து எதையும் இறக்குமதி செய்யவில்லை; அதன் மதிப்புகள் கட்டமைப்பு ரீதியாக SDK இன் options இல் பரவுகின்றன.

## பில்ட் மற்றும் விநியோகம்

npm தொகுப்பு ஒரு பில்டை அல்ல, TypeScript மூலத்தை அனுப்புகிறது: `tokenmaxxing` bin ஒரு Bun shebang உடன் நேராக `src/main.ts` ஐ சுட்டுகிறது, மேலும் Bun 1.2.6 அல்லது புதியது அதை அப்படியே இயக்குகிறது. அதனால்தான் Bun ஒரு கடினமான தேவை. வடிவமைப்பின்படி எந்த தொகுக்கப்பட்ட binaries உம் இல்லை: ஒரு ஆரம்ப வெளியீடு ஒவ்வொரு தளத்திற்கும் ஒரு ஒற்றை 61 MB macOS binary ஐ அனுப்பியது, மேலும் Linux இல் `exec format error` உடன் தோல்வியடைந்தது, மேலும் ஒவ்வொரு-தளத்திற்கும் தொகுக்கப்பட்ட தொகுப்புகள் ஒவ்வொன்றும் அதற்கே சொந்தமான வெளியீட்டு pipeline தேவைப்படும், எனவே Bun-ஆல்-இயக்கப்படும்-மூலம் விநியோக மாதிரியாக மாறியது.

தொகுப்பின் `exports` வரைபடம் மேலே விவரிக்கப்பட்ட நிரல்முறை நுழைவாக `src/sdk.ts` ஐ வெளிப்படுத்துகிறது. வெளியீடுகள் GitHub இல் `v<version>` என குறியிடப்படுகின்றன; CI நம்பகமான வெளியீடு வழியாக npm க்கு வெளியிடுகிறது (OIDC, provenance உடன்), மேலும் வெளியீட்டு வாயில் முதலில் typecheck மற்றும் முழு சோதனைத் தொகுப்பையும் இயக்குகிறது.

## தனிப்பட்ட பயன்பாடு மற்றும் சேவை விதிமுறைகள் [#personal-use-and-terms-of-service]

tokenmaxxing நீங்கள் வைத்திருக்கும் கணக்குகளை, நீங்களே இயக்கும் அமர்வுகளிலும் ஏஜென்ட்களிலும் ஒன்றிணைக்கிறது. அந்த வார்த்தைகள் வேண்டுமென்றே: Anthropic மூன்றாம் தரப்பு தயாரிப்புகள் claude.ai உள்நுழைவு அல்லது claude.ai rate limits ஐ வழங்க அனுமதிக்காது, அதில் Agent SDK மீது கட்டமைக்கப்பட்ட ஏஜென்ட்களும் அடங்கும். ஒன்றிணைந்த SDK மேற்பரப்பையோ, அல்லது அதன் மீது கட்டமைக்கப்பட்ட எதையுமோ மூன்றாம் தரப்பினருக்கு அனுப்ப வேண்டாம். tokenmaxxing OAuth ஐ மறுசெயலாக்குவதற்கு அல்லது API போக்குவரத்தை பதிலாள் செய்வதற்குப் பதிலாக, ஒதுக்கீட்டுத் தரவுக்கு வேண்டுமென்றே CLI-மத்தியஸ்த `/usage` பாதையிலேயே இருக்கிறது: இது ஒரு பதிலாள் அல்ல, மேலும் அது தொடும் ஒரே OAuth endpoints ஒரு மாற்றத்தின்போது பயன்படுத்தப்படும் நிலையான refresh மானியமும், ஒரு டோக்கன் உண்மையில் எந்த கணக்கிற்குச் சொந்தமானது என்பதைச் சரிபார்க்கும் ஒரு படிக்க-மட்டும் அடையாளச் சரிபார்ப்பும் (roles endpoint) மட்டுமே.

## நேர்மையான வரம்புகள்

- **ஒரு குளிர்ச்சியான திருப்பு.** Prompt cache நிறுவனம்-வரம்பிடப்பட்டது, எனவே ஒரு புதிய கணக்கில் முதல் திருப்பு சூழலை ஒருமுறை மீண்டும் பதிவேற்றுகிறது.
- **தீர்ந்துபோன-இடைநிறுத்த இடையூறு.** முழுமையாக தீர்ந்துபோன ஒரு தொகுப்பு மட்டுமே எண்ணிக்கைக்காக அமர்வை நிறுத்துகிறது; அந்த பிளவு நொடியில் தட்டச்சு செய்யப்பட்ட எதுவும் இழக்கப்படுகிறது.
- **ஏற்றுக்கொள்ளல் தாமதம்.** macOS இல் ஒரு மாற்றத்தின் ~30 வினாடிகளுக்குள் முதல் திருப்பு இன்னும் பழைய கணக்கை அளவிடக்கூடும்; பட்டைகளின் இடம் அதை உள்வாங்குகிறது.
- **பகிரப்பட்ட வெடிப்பு ஆரம்.** அனைத்து இயல்பு-சுயவிவர அமர்வுகளும் ஒரு நேரடி சான்றுதலைப் பகிர்ந்து கொள்கின்றன, எனவே ஒரு மாற்றம் அவை அனைத்தையும் ஒன்றாக நகர்த்துகிறது (ஒவ்வொன்றும் இடத்திலேயே ஏற்றுக்கொள்கிறது).
- **Linux இல் plaintext சான்றுதல்கள்.** Claude Code தானே Linux சான்றுதல்களை ஒரு 0600 plaintext கோப்பாக சேமிக்கிறது; tokenmaxxing இன் நிறுத்தப்பட்ட நகல்கள் அதே மாதிரியைப் பின்பற்றுகின்றன.

## சிக்கல் தீர்த்தல் மற்றும் FAQ

**`claude` மேற்பார்வையிடப்பட்டதாகத் தெரியவில்லை.**
`tokenmaxxing doctor` ஐ இயக்குங்கள். shim PATH தீர்வை வெல்ல வேண்டும்; உங்கள் ஷெல் rc இல் உள்ள `# tokenmaxxing PATH` வரி தற்போதைய bin அடைவைச் சுட்டிக்காட்டி உண்மையான claude க்கு முன்பே அமர்கிறதா என்று சரிபார்க்கவும். `doctor` `alias claude=...` அல்லது ஒரு `claude()` ஷெல் செயல்பாடு wrapper ஐ நிழலிடுவது பற்றியும், ஒரு claude பைனரியை முழுமையான பாதையால் தொடங்கும் புனைப்பெயர்கள் (அவை மேற்பார்வையாளரை முழுவதுமாகத் தவிர்க்கின்றன) பற்றியும் எச்சரிக்கிறது.

**Codex இல் தானியங்கி-மாற்றம் ஒருபோதும் இயங்குவதில்லை.**
Codex தான் நம்பச் சொல்லப்படாத hooks ஐத் தவிர்க்கிறது. codex ஐத் திறந்து, `/hooks` ஐ இயக்கி, tokenmaxxing Stop hook ஐ நம்புங்கள். நம்பிக்கை hook இன் hash க்கு எதிராக பதிவு செய்யப்படுகிறது, எனவே hook எப்போதேனும் திருத்தப்பட்டால் அது மீண்டும் வழங்கப்பட வேண்டும்.

**statusline இல் ஒரு கணக்கு சிவப்பு `✗` ஐக் காட்டுகிறது.**
அதன் refresh டோக்கன் இறந்துவிட்டது (ரத்து செய்யப்பட்டது அல்லது அதன் காப்புப்பிரதியின் அடியில் சுழற்றப்பட்டது). அதை இடத்திலேயே மீண்டும் அங்கீகரிக்க `tokenmaxxing auth <sel>` ஐ இயக்குங்கள்; கட்டளை எந்த மின்னஞ்சலுடன் உள்நுழைய வேண்டும் என்று சொல்கிறது மற்றும் வேறு கணக்கில் இறங்கும் ஒரு உள்நுழைவை மறுக்கிறது.

**மிக அதிக எஞ்சிய ஒதுக்கீடு உள்ள கணக்கிற்கு ஏன் அது மாறுவதில்லை?**
ஏனெனில் அது ஒதுக்கீட்டை இழக்கும் அபாயத்தில் மிக அதிகமாக உள்ள கணக்கு அல்ல. இலக்கு அதன் சொந்த வாராந்திர வேகத்திற்கு மிகவும் பின்தங்கியிருக்கும் கணக்கு: எஞ்சிய சதவீதம் அதன் வாராந்திர மீட்டமைப்பு வரையிலான நேரத்தால் வகுக்கப்படுகிறது. சம அளவுகள் எஞ்சியிருக்கும்போது அது மிக விரைவான காலாவதி முதலில் என்பதாகக் குறைகிறது, மேலும் சம காலாவதியுடன் மிக அதிக எஞ்சியது முதலில் என்பதாகக் குறைகிறது.

**அது இப்போதுதான் மாறியது, statusline இன்னும் பழைய கணக்கைக் காட்டுகிறது.**
macOS இல் ~30 வினாடிகள் வரை எதிர்பார்க்கப்படுவது: இயங்கும் அமர்வு அதன் அடுத்த சான்றுதல்-cache புத்துணர்ச்சியில் மாற்றப்பட்ட சான்றுதலை ஏற்றுக்கொள்கிறது. பயன்பாட்டு tee ஒரு மாற்றத்திற்குப் பிறகு சரியாக இந்தக் காரணத்திற்காக 45 வினாடிகளுக்கு அடக்கப்படுகிறது.

**`status --force` க்கு ஏதேனும் செலவாகுமா?**
ஆம், வேண்டுமென்றே: ஒவ்வொரு 5-மணிநேர அமர்வு சாளரமும் சும்மா கிடப்பதற்குப் பதிலாக அந்த நொடியில் தொடங்குவதற்காக ஒவ்வொரு கணக்கிற்கும் ஒரு குறைந்தபட்ச அளவிடப்பட்ட haiku கோரிக்கையை அது அனுப்புகிறது, பிறகு புதிதாக மாதிரி எடுக்கிறது. வெறும் `status` மற்றும் `watch` ஒருபோதும் ping செய்யாது; `/usage` வாசிப்புகள் இலவசம். சேவையக பயன்பாட்டு ஊட்டம் புதிதாக திறக்கப்பட்ட ஒரு சாளரத்தை வினாடிகள் முதல் நிமிடங்கள் வரை தாமதப்படுத்தக்கூடும் என்பதைக் கவனியுங்கள், எனவே ping க்குப் பிறகு உடனடியாக ஒரு probe இன்னும் ping-க்கு-முந்தைய நிலையைக் காட்டக்கூடும் - `status` ping தோல்வியடைந்ததாக நடிப்பதற்குப் பதிலாக ஒரு குறிப்பை render செய்கிறது.

**`/usage` probe செயலில் உள்ள கணக்கிற்கு எதையும் திருப்பித் தரவில்லை.**
அது ஒரு அறியப்பட்ட claude நடத்தை: அதன் உள் பயன்பாட்டு fetch தோல்வியடையும்போது அல்லது rate-limit செய்யப்படும்போது, `/usage` எந்த சதவீத வரிகளும் இல்லாமல் உள்ளூர் அமர்வு புள்ளிவிவரங்களை மட்டுமே அச்சிடுகிறது. tokenmaxxing செயலில் உள்ள கணக்கை statusline தள்ளுதலிலிருந்து மாதிரி எடுக்கிறது மற்றும் நிறுத்தப்பட்ட கணக்குகளை மட்டுமே probe செய்கிறது, சரியாக இதைத் தவிர்ப்பதற்காக.

**பின்னணி claude அமர்வுகள்.**
Claude இன் பின்னணி டீமன் உண்மையான பதிப்பிடப்பட்ட பைனரியை முழுமையான பாதையால் உருவாக்குகிறது, PATH shims ஐத் தவிர்க்கிறது, எனவே பின்னணி அமர்வுகள் மேற்பார்வையிடப்படாதவை. Hooks இன்னும் `settings.json` வழியாக இயங்குகின்றன, மேலும் சான்றுதல் ஏற்றுக்கொள்ளலும் காலமுறை டைமரும் மாற்றத்தை உள்ளடக்குகின்றன, ஆனால் அவற்றுக்கு எந்த குறிப்பான்-உந்தப்பட்ட respawn உம் இல்லை.

**ஏதோ ஒருமுறை நிறைய செயல்முறைகளை உருவாக்கியது. அது இன்னும் சாத்தியமா?**
மேற்பார்வையாளர் சரியாக அந்த வரலாற்றுத் தோல்விக்கு எதிராக (ஒரு பழைய wrapper "உண்மையான" claude ஆக பொருத்தப்பட்டது) அடுக்கு recursion காவல்களைச் சுமக்கிறார்: 5 நிலைகளில் நிறுத்தும் சூழலில் ஒரு ஆழ சென்டினல், ஒரு வட்டில்-உள்ள spawn-வீத வரம்பிடி, tokenmaxxing இன் சொந்த bin அடைவுக்குள் மீண்டும் தீர்க்கும் எந்த வேட்பாளரையும் நிராகரிக்கும் realpath அடையாள சரிபார்ப்புகள், மற்றும் கட்டமைக்கப்பட்ட ஒரு claude பாதை இனி இல்லாதபோது ஒரு கடுமையான தோல்வி (ஒருபோதும் ஒரு அமைதியான PATH scan அல்ல). `init` மற்றும் `doctor` ஒரு வேட்பாளரைப் பொருத்துவதற்கு முன்பு `--version` ஐ இயக்குவதன் மூலம் அது உண்மையில் claude தானா என்று சரிபார்க்கின்றன.

**நிறுவல் நீக்கம்.**
`tokenmaxxing uninstall` மேற்பார்வையாளர் shims, அமைப்பு உள்ளீடுகள், மற்றும் காலமுறை டைமரை அகற்றி, உங்கள் கணக்குகளையும் நிறுத்தப்பட்ட சான்றுதல்களையும் அப்படியே விட்டுவிடுகிறது. அது தனது சொந்தமாக அங்கீகரிக்கும் statusline உள்ளீடுகளை மட்டுமே அகற்றுகிறது.
