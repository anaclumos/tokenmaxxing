---
title: 疑難排解同常見問題
description: "常見問題，同背後嘅診斷"
---

**`claude` 好似冇受監督。**
行 `tokenmaxxing doctor`。個 shim 必須喺 PATH 解析入面勝出;檢查 shell rc 入面嘅 `# tokenmaxxing PATH` 行係咪指向現時嘅 bin 目錄，而且排喺真正 claude 前面。`doctor` 亦都會警告 `alias claude=...` 或者 `claude()` shell 函數遮蔽咗個包裝，同埋以絕對路徑啟動 claude 二進位檔嘅別名（嗰啲完全繞過監督者）。

**Codex 上面自動切換永遠唔觸發。**
Codex 會跳過啲未獲信任嘅 hook。開 codex，行 `/hooks`，然後信任 tokenmaxxing Stop hook。信任係按個 hook 嘅 hash 記錄嘅，所以只要改過個 hook 就必須重新授予。

**有帳戶喺 statusline 顯示紅色 `✗`。**
佢嘅刷新 token 死咗（俾人撤銷咗,或者喺備份底下俾人輪換走咗）。行 `tokenmaxxing auth <sel>` 就地重新認證佢;個指令會話你知用邊個 email 登入,亦都會拒絕落喺另一個帳戶嘅登入。

**點解佢唔切換去剩餘配額最多嗰個帳戶？**
因為嗰個唔係最有機會白白損失配額嘅帳戶。目標係最跟唔上自己每週步伐嘅帳戶：剩餘百分比除以距離每週重設嘅時間。如果剩餘量一樣，就變成最快到期嗰個行先，到期時間又一樣就變成剩餘最多嗰個行先。

**佢啱啱切換咗但係 statusline 仍然顯示舊帳戶。**
喺 macOS 上面最多 ~30 秒都算正常：行緊嘅 session 會喺下一次憑證快取刷新時，採用換咗嘅憑證。用量 tee 喺切換之後嘅 45 秒內會受抑制，就係為咗呢個原因。

**`status --ping` 使唔使錢？**
使，係刻意嘅：佢會向每個帳戶發送一個最小嘅計量 haiku 請求，令每個 5 小時 session 窗口喺嗰一刻開始，而唔係一直休眠住，然後重新採樣。普通嘅 `status` 同 `watch` 永遠都唔會 ping;`/usage` 讀取係免費嘅。留意伺服器用量資訊來源反映啱啱開嘅窗口時，可能會滯後幾秒到幾分鐘，所以喺 ping 之後即刻探測，可能仍然顯示 ping 前嘅狀態 - `status` 會顯示一個備註，而唔係扮 ping 失敗咗。

**`/usage` 探測為活躍帳戶乜都返唔到。**
呢個係 claude 已知嘅行為：當佢內部用量抓取失敗或者受速率限制嗰陣,`/usage` 淨係列印本地 session 統計，冇百分比行。tokenmaxxing 靠 statusline 推送嚟採樣活躍帳戶,淨係探測泊存帳戶，正正就係為咗避免呢個情況。

**背景 claude session。**
Claude 嘅背景守護程序以絕對路徑生成真正嘅版本化二進位檔，繞過 PATH shim，所以背景 session 係唔受監督嘅。Hook 仍然會透過 `settings.json` 觸發，而憑證採用同定期計時器就涵蓋咗切換，但係佢哋就冇標記驅動嘅重生。

**有樣嘢曾經生成咗好多進程。呢個仲有冇可能發生？**
監督者有分層嘅遞迴防護，專門對付嗰個歷史故障（有個過時包裝俾人固定做「真正」claude）：環境入面有個深度哨兵，去到 5 層就中止、磁碟上有個生成速率限制器、realpath 身分檢查會拒絕任何解析返 tokenmaxxing 自己 bin 目錄嘅候選，同埋當一個已設定嘅 claude 路徑唔再存在，就會硬失敗（永遠唔會靜靜哋掃描 PATH）。`init` 同 `doctor` 喺固定一個候選之前，會先行 `--version` 驗證佢真係 claude。

**解除安裝。**
`tokenmaxxing uninstall` 會移除監督者 shim、設定項目同定期計時器，同時保留你嘅帳戶同泊存憑證，完好無缺。佢只會移除辨認得出係自己嘅 statusline 項目。
