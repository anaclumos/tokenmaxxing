---
title: Mga tapat na limitasyon
description: "Ang mga tradeoff na kaakibat ng pooled hot-swapping"
---

- **Isang malamig na turn.** Ang prompt cache ay org-scoped, kaya't ang unang turn sa isang bagong account ay muling nag-a-upload ng konteksto nang minsan.
- **Depleted-pause na aberya.** Tanging ang isang ganap na naubos na pool ang humihinto sa session para sa countdown; anumang na-type sa split-second na iyon ay nawawala.
- **Adoption lag.** Sa macOS ang unang turn sa loob ng ~30 segundo ng isang pagpapalit ay maaari pa ring mag-meter sa lumang account; sinisipsip ito ng headroom ng mga bar.
- **Shared na blast radius.** Ibinabahagi ng lahat ng default-profile na session ang isang live credential, kaya't inililipat silang lahat nang sabay ng isang pagpapalit (bawat isa ay ina-adopt sa lugar).
- **Mga plaintext na credential sa Linux.** Ang Claude Code mismo ay nag-iimbak ng mga Linux credential bilang isang 0600 plaintext file; sinusunod ng mga naka-park na kopya ng tokenmaxxing ang parehong modelo.
- **Isang pool kada host.** Gumagana ang pag-pool ng parehong mga account sa ilang makina, ngunit ang bawat host ay nagpa-park at nag-i-rotate ng mga token nang hiwalay, walang cross-host na lock: dalawang host na nagre-refresh ng token ng parehong account nang sabay-sabay ay nagbabanggaan. Sa Claude, agad na pinawawalang-bisa ng isang refresh rotation ang naunang access token, kaya nabibigo ang mga session sa kabilang host nang may 401 at bumabalik ang lipas na nitong refresh token bilang `invalid_grant` (kailangan nang mag-reauth). Para sa Codex, ang isang refresh mula sa isang lipas nang naka-park na kopya ay nakamamatay sa login na iyon (pinawawalang-bisa ng OpenAI ang buong grant family sa muling paggamit ng refresh token, na pumipilit sa `auth` sa bawat host). Kung mag-i-pool ka ng isang account sa mahigit sa isang makina, asahan ang churn ng muling pag-authenticate sa Claude at iwasan ito nang lubusan para sa Codex.
