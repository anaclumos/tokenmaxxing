tokenmaxxing हे स्वयंचलित Claude Code खाते बदलण्यासाठीचे एक CLI आहे. ते तुमच्या मालकीची अनेक सबस्क्रिप्शन (Pro/Max) खाती एकत्र करते आणि वापरात असलेले खाते वापर मर्यादेजवळ पोहोचल्यावर सक्रिय क्रेडेन्शियल एका ताज्या खात्यावर हॉट-स्वॅप करते. तुम्ही नेहमीप्रमाणेच `claude` चालवता; बदल सुरक्षित टर्न सीमेवर होतो आणि तुमचे चालू सत्र त्याच संभाषणासह नवीन खात्यावर पुन्हा सुरू न करता सुरू राहते. हे एकाच वेळी अनेक समांतर सत्रांमध्ये कार्य करते.

एकमेव दृश्यमान वर्तन म्हणजे सर्वात वाईट परिस्थिती: जेव्हा संपूर्ण पूल त्याच्या मर्यादेवर असतो, तेव्हा सत्र काउंटडाउनसह थांबते आणि पुढील रीसेट होणाऱ्या खात्यावर आपोआप पुन्हा सुरू होते (Ctrl-C लगेच पुन्हा सुरू करते).

<Callout>
व्याप्ती: macOS आणि Linux वर Claude Code, तसेच OpenAI चे Codex CLI दुसरा, समांतर पूल म्हणून. ते सबस्क्रिप्शन खाती एकत्र करते, API कीज नव्हे. हे तुमच्या मालकीची खाती, तुम्ही स्वतः चालवत असलेल्या सत्रांमध्ये आणि एजंट्समध्ये एकत्र करण्यासाठीचे वैयक्तिक-वापर साधन आहे - पहा [वैयक्तिक वापर आणि सेवा अटी](#personal-use-and-terms-of-service).
</Callout>

## समस्या

Claude सबस्क्रिप्शन एकाच वेळी तीन मर्यादा मोजते (सर्व `/usage` द्वारे पुष्टी केलेल्या):

- **सध्याचे सत्र**: एक रोलिंग ५-तासांची विंडो.
- **सध्याचा आठवडा (सर्व मॉडेल्स)**: ७-दिवसांची एकत्रित बेरीज.
- **सध्याचा आठवडा, प्रति मॉडेल**: वैयक्तिक मॉडेल कुटुंबांसाठी वेगळ्या साप्ताहिक मर्यादा. सध्या या फक्त Sonnet आणि Fable साठीच अस्तित्वात आहेत, आणि फक्त Fable ची मर्यादा इतकी घट्ट आहे की महत्त्वाची ठरते - एकत्रित मर्यादेच्या बरेच आधी ती बंधनकारक होते. एखादे मशीन week-Fable वर आधीच ८०% असताना week-all वर ५०% वर बसू शकते.

साप्ताहिक कोटा वापरा-किंवा-गमवा असा आहे: एका खात्याने त्याच्या निश्चित साप्ताहिक रीसेटपर्यंत जे वापरले नाही ते गमावले जाते. जर तुमच्याकडे अनेक खाती असतील, तर तर्कसंगत रणनीती म्हणजे जे खाते त्याच्या स्वतःच्या साप्ताहिक गतीच्या सर्वात मागे आहे त्यावर कोटा वापरत राहणे, आणि कोणतीही एक मर्यादा सत्राच्या मध्यभागी भिंतीला गाठण्यापूर्वी दूर बदलणे.

हे हाताने करणे म्हणजे लॉग आउट करणे, लॉग इन करणे, आणि तुमचे संभाषण गमावणे. tokenmaxxing हे स्वयंचलित करते: चालू `claude` विनंत्यांदरम्यान त्याचे क्रेडेन्शियल स्टोअर पुन्हा तपासते, त्यामुळे त्याखाली बदललेले क्रेडेन्शियल जागच्या जागी स्वीकारले जाते (macOS वर सुमारे ३० सेकंदांत, Linux वर पुढील विनंतीवर). साधा बदल तुमचे सत्र कधीही पुन्हा सुरू करत नाही. एकमेव अशी परिस्थिती ज्याला अजूनही प्रक्रिया व्यवस्थापन लागते ती म्हणजे पूर्णपणे संपलेला पूल - सत्र स्वतःला थांबवू शकत नाही - आणि पातळ पर्यवेक्षक (supervisor) याच कारणासाठी अस्तित्वात आहे.

`claude` बद्दल बाकी सर्व काही अपरिवर्तित राहते: सर्व फ्लॅग्ज, MCP सर्व्हर, हुक्स आणि स्किल्स तसेच पास होतात.

## झटपट सुरुवात

macOS किंवा Linux वर [Bun](https://bun.sh) आणि Claude Code आवश्यक आहेत.

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` पाच गोष्टी करते:

1. तुम्ही आधीच ज्या खात्याने लॉग इन आहात ते खाते #1 म्हणून आयात करते (वेगळी `adopt` कमांड नाही).
2. `claude` पर्यवेक्षक शिम स्थापित करते.
3. Claude Code च्या `settings.json` मध्ये तीन नोंदी स्थापित करते: एक statusLine, एक Stop हुक, आणि एक SessionStart हुक (तसेच एक subagentStatusLine नोंद).
4. तुमच्या शेल rc च्या PATH मध्ये पर्यवेक्षकाची bin डिरेक्टरी जोडते (आयडेम्पोटेंट, `# tokenmaxxing PATH` टिप्पणीने चिन्हांकित). त्याला रोखण्यासाठी ते PATH वर खऱ्या `claude` च्या पुढे बसणे आवश्यक आहे.
5. एक नियतकालिक तपासणी टायमर स्थापित करते (macOS वर launchd एजंट, Linux वर systemd यूजर टायमर) जो दर १८० सेकंदांनी `tokenmaxxing check` चालवतो.

तुमचे शेल पुन्हा सुरू करा, नंतर अधिक खाती जोडा आणि सुरू करा:

```sh
tokenmaxxing add        # आणखी एक खाते वेगळेपणाने लॉग इन करते आणि पूलमध्ये जोडते
claude                  # नेहमीप्रमाणे claude वापरा
```

`tokenmaxxing` ला `xx` असे टोपणनाव देखील आहे. साधा `tokenmaxxing` (किंवा `xx`) `status` चालवतो; `switch` स्पष्ट राहतो.

## कमांड्स

| कमांड | ती काय करते |
|---|---|
| `tokenmaxxing init` | सध्याचे खाते आयात करा, पर्यवेक्षक, हुक्स आणि statusline स्थापित करा |
| `tokenmaxxing init --codex` | Codex साठी तेच: लॉगिन आयात करा, codex पर्यवेक्षक आणि Stop हुक स्थापित करा |
| `tokenmaxxing add` | अतिरिक्त खाते नोंदवा (वेगळे लॉगिन, पूलमध्ये संकलित) |
| `tokenmaxxing add --codex` | अतिरिक्त Codex खाते नोंदवा (वेगळे लॉगिन) |
| `tokenmaxxing auth [sel \| --all]` | पूलमधील खाते जागच्या जागी पुन्हा प्रमाणित करा. साधा पूलची यादी करतो आणि कोणते ते विचारतो; निवडक एका खात्याला लक्ष्य करतो आणि कोणत्या ईमेलने साइन इन करायचे ते सांगतो; `--all` प्रत्येक पुन्हा-प्रमाणीकरण-आवश्यक खात्यातून एकेक करून जातो |
| `tokenmaxxing switch [sel]` | सर्वोत्तम खात्यावर बदला (हावरट, आयडेम्पोटेंट) किंवा विशिष्ट खाते सक्ती करा |
| `tokenmaxxing switch --codex [sel]` | Codex पूल बदला (पुढील codex सुरुवातीला लागू होतो) |
| `tokenmaxxing ls` | पूलमधील खात्यांची यादी करा |
| `tokenmaxxing status` | ५तास / साप्ताहिक / प्रति-मॉडेल वापर बारसह खाती, सक्रिय आणि रीसेटपर्यंत संपलेली |
| `tokenmaxxing status --force` | अतिरिक्तपणे प्रत्येक खात्याला पिंग करा (प्रत्येकी एक लहान haiku विनंती) जेणेकरून सर्व ५तासांचे सत्र टायमर आता सुरू होतील, नंतर ताजे नमुने घ्या |
| `tokenmaxxing watch [seconds]` | थेट स्थिती, दर N सेकंदांनी पुन्हा प्रस्तुत केली जाते (डीफॉल्ट १२०, किमान ३०; कधीही पिंग करत नाही) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | स्रोतांसह प्रभावी कॉन्फिग; डॉट-केलेल्या कीज संपादित करा; `tidy` अज्ञात कीज काढून टाकते |
| `tokenmaxxing check` | बदल निर्णयाचे एकदा मूल्यांकन करा (हेच नियतकालिक टायमर चालवतो) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | Slack ब्रिज डिमन (Socket Mode, सार्वजनिक URL नाही) |
| `tokenmaxxing doctor` | पर्यवेक्षक आणि सेटिंग्ज नोंदी टिकून राहिल्याची पडताळणी करा |
| `tokenmaxxing rename [--codex] <sel> <label>` | पूलमधील खात्याचे नाव पुन्हा द्या |
| `tokenmaxxing rm <sel>` | पूलमधून खाते काढा |
| `tokenmaxxing uninstall` | पर्यवेक्षक आणि सेटिंग्ज नोंदी काढा (खाती आणि क्रेडेन्शियल्स ठेवले जातात) |

## आर्किटेक्चर

tokenmaxxing हा एकच मल्टी-कॉल एंट्री पॉइंट (`src/main.ts`) आहे जो त्या नावाने बोलावल्यावर `claude` पर्यवेक्षक म्हणून वागतो, अंतर्गत सबकमांड्सद्वारे हुक आणि statusline शिम्स सेवतो, आणि अन्यथा CLI डिस्पॅच करतो. तो थेट Bun अंतर्गत चालतो; npm पॅकेज TypeScript स्रोत पाठवते, बिल्ड नव्हे.

चलणारे भाग:

### पर्यवेक्षक शिम

`init` हा `claude` नावाचा २-ओळींचा शेल शिम `~/.config/tokenmaxxing/bin/` मध्ये लिहितो आणि ती डिरेक्टरी PATH वर प्रथम ठेवतो. जेव्हा तुम्ही `claude` टाइप करता, तेव्हा शिम पर्यवेक्षक चालवतो, जो खरी claude बायनरी वारसाहक्काने मिळालेल्या stdio आणि जतन केलेल्या `stty -g` टर्मिनल स्नॅपशॉटसह स्पॉन करतो. तो केवळ एक प्रक्रिया आणि टर्मिनल व्यवस्थापक आहे: तो कधीही API ट्रॅफिक प्रॉक्सी करत नाही आणि उड्डाणातील टोकन्सना कधीही स्पर्श करत नाही.

प्रिंट-मोड आवाहने (`claude -p`, `--version`, `--help`), नॉन-इंटरॲक्टिव्ह सबकमांड्स (`claude mcp`, `claude config`, वगैरे), आणि tokenmaxxing च्या स्वतःच्या प्रोब्स कोणत्याही सत्र व्यवस्थापनाशिवाय थेट पास होतात. इंटरॲक्टिव्ह सत्रासाठी, पर्यवेक्षक एक session id पिन करतो (एक तयार करतो, किंवा तुम्ही `--session-id` / `-r` / `-c` द्वारे दिलेला पुन्हा वापरतो), तुमचे लॉन्च फ्लॅग्ज टिकवतो जेणेकरून नंतरचे पुन्हा-लॉन्च ते पुन्हा चालवू शकेल, आणि नंतर त्या सत्राशी संबंधित respawn मार्कर फाइलवर लक्ष ठेवतो.

### statusline टी

Claude Code प्रत्येक टर्नला statusline च्या stdin मध्ये दर-मर्यादा डेटा (`rate_limits.five_hour` आणि `rate_limits.seven_day`) पाठवते. tokenmaxxing statusline स्लॉटचे मालक आहे, त्यामुळे त्याचे रेंडरर एक मुक्त, पुश-आधारित वापर फीड म्हणून दुहेरी काम करते: प्रत्येक टिकला ते एकत्रित विंडोज तसेच सक्रिय मॉडेल `usage.json` मध्ये टी करते. प्रति-मॉडेल मर्यादा statusline stdin मध्ये नसतात; त्या फक्त `claude -p '/usage'` (मुक्त, शून्य टोकन्स) कडून येतात, जे TTL सह पोल केले जाते आणि सक्रिय मॉडेल क्षमता-मर्यादित असताना `model-usage.json` मध्ये कॅश केले जाते.

टी बदल-झाल्यावर-लिहिणारी आहे: जेव्हा आकडे अपरिवर्तित असतात तेव्हा ती फक्त फाइलचा mtime वाढवते, जो फीडचा जिवंतपणा दर्शवणारा ठोका म्हणून काम करतो. ताजेपणा नेहमी mtime द्वारे ठरवला जातो, अंतर्भूत टाइमस्टॅम्पद्वारे कधीही नाही.

### Stop हुक आणि बदल

प्रत्येक टर्न सीमेवर, Stop हुक बदल निर्णय चालवतो (पहा [बदल कसा ठरवला जातो](#how-switching-decides)). जेव्हा बदल आवश्यक असतो, तेव्हा तो `flock(2)` अनन्य लॉकखाली होतो (`bun:ffi` द्वारे घेतलेला, कारण macOS कोणतीही `flock(1)` बायनरी पाठवत नाही), आणि क्रेडेन्शियल लेखन Claude Code च्या स्वतःच्या रीफ्रेश लॉकशी अतिरिक्तपणे इंटरलॉक करते. क्रिटिकल सेक्शनच्या आत, एक बदल:

1. सध्याचे थेट क्रेडेन्शियल त्याच्या खऱ्या मालकाच्या पार्क केलेल्या बॅकअपमध्ये संकलित करतो.
2. लक्ष्य खात्याचे ताजे रीफ्रेश केलेले क्रेडेन्शियल थेट म्हणून स्थापित करतो, विद्यमान थेट ब्लॉबमध्ये विलीन करतो जेणेकरून सहचर स्थिती (जसे की प्रति-MCP-सर्व्हर OAuth टोकन्स) टिकून राहील.
3. लक्ष्याचे फिरवलेले टोकन त्याच्या स्वतःच्या बॅकअपमध्ये टिकवतो.
4. `~/.claude.json` मधील `oauthAccount` फील्ड अणुरूपपणे पुन्हा लिहितो.
5. नवीन सक्रिय लेबल कमिट करतो आणि जुने वापर स्नॅपशॉट्स साफ करतो, हे सर्व लॉक सोडण्यापूर्वी, जेणेकरून एखादा क्रॅश कधीही स्थापित केलेले क्रेडेन्शियल आणि सक्रिय लेबल वेगवेगळ्या खात्यांकडे इशारा करत ठेवू शकणार नाही.

कारण सर्व डीफॉल्ट-प्रोफाइल सत्रे ते एकच थेट क्रेडेन्शियल सामायिक करतात, एकच बदल एकाच वेळी प्रत्येक सत्र स्थलांतरित करतो, आणि flock तसेच लॉकखाली पुन्हा-तपासणी शर्यत करणाऱ्या हुक्सना दोन खाती जाळण्यापासून रोखते.

### जागच्या जागी स्वीकार

चालू claude सत्र विनंत्यांदरम्यान त्याचे क्रेडेन्शियल स्टोअर पोल करते: macOS वर ते एका छोट्या कॅशद्वारे कीचेन पुन्हा वाचते आणि अॅक्सेस टोकन्सची तुलना करते; Linux वर ते क्रेडेन्शियल्स फाइलचा mtime स्टॅट करते आणि बदलावर त्याचे टोकन कॅश फ्लश करते. निव्वळ परिणाम असा की बदललेले क्रेडेन्शियल प्रत्येक चालू सत्राद्वारे macOS वर सुमारे ३० सेकंदांत आणि Linux वर अगदी पुढील विनंतीवर, कोणत्याही पुन्हा सुरू न करता स्वीकारले जाते. यामुळेच साधा बदल कोणताही मार्कर लिहीत नाही आणि कोणताही respawn ट्रिगर करत नाही - सत्र फक्त नवीन खात्यावर सुरू राहते. सत्रांतर्गत `/usage` तेच टोकन कॅश सामायिक करते, त्यामुळे त्याचे खाते प्रदर्शन स्वीकारासोबत बदलते.

### संपलेल्या पूलची प्रतीक्षा आणि स्वयं-पुन्हा-सुरू

फक्त जेव्हा पूलमधील प्रत्येक खाते त्याच्या बारांवर असते तेव्हाच Stop हुक respawn मार्कर लिहितो (मार्कर स्कीमाला `waitUntil` टाइमस्टॅम्प आवश्यक असतो; साधा बदल कधीही एक तयार करू शकत नाही). पर्यवेक्षक मार्कर पाहतो, आधीच-कमिट-केलेल्या टर्न सीमेवर त्याच्या मुलाला SIGTERM करतो (Stop हुक ट्रान्सक्रिप्ट डिस्कवर आल्यानंतर आणि claude निष्क्रिय असताना चालतो, त्यामुळे काहीही गमावले जात नाही), टर्मिनल पुनर्संचयित करतो, सर्वात लवकर रीसेटपर्यंत काउंटडाउन दाखवतो, आणि नंतर पुनर्प्राप्त खात्यावर `claude --resume <session-id>` पुन्हा-लॉन्च करतो. काउंटडाउनदरम्यान Ctrl-C लगेच पुन्हा सुरू करते. स्वयं-प्रतीक्षा `policy.maxWaitMs` (डीफॉल्ट १ तास) ने बांधलेली असते; त्यापलीकडे निर्णय प्रतीक्षा करण्याऐवजी पूल संपलेला असल्याचे नोंदवतो.

### नियतकालिक तपासणी टायमर

हुक्स फक्त टर्न सीमांवर फायर होतात, आणि एक लांब एजंटिक टर्न एकाही सीमेशिवाय एका विंडोला निरोगीपासून संपलेल्यापर्यंत जाळू शकतो. म्हणून `init` एक नियतकालिक टायमर देखील स्थापित करते - macOS वर launchd एजंट, Linux वर systemd यूजर टायमर - जो टर्न क्रियाकलापाकडे दुर्लक्ष करून दर १८० सेकंदांनी `tokenmaxxing check` चालवतो.

### एक SessionStart हुक

जेव्हा सत्र सुरू होते किंवा पुन्हा सुरू होते तेव्हा तेच मूल्यांकन चालवते, जेणेकरून ताजे सत्र योग्य खात्यावर सुरू होईल. बदल-नंतरचा कूलडाउन respawn नंतर लगेच याला एक योग्य नो-ऑप बनवतो.

## बदल कसा ठरवला जातो [#how-switching-decides]

निर्णयाला दोन स्तर आहेत: एक सहभाग गेट, आणि नंतर एक हावरट किंवा कठोर मार्ग.

### सहभाग

`policy.greedySessionFloor` (डीफॉल्ट ५०, ५-तासांच्या सत्र विंडोच्या टक्केवारीत) च्या खाली, निर्णय अजिबात चालत नाही - ताजे सत्र त्याच्या खात्यावर चालते. एकदा सक्रिय सत्र विंडो ५०% वापरली गेली, किंवा कोणताही कठोर बार ओलांडला गेला, की निर्णय सहभागी होतो.

### स्क्रीनिंग बार

थ्रेशोल्ड्स हे स्क्रीनिंग बार आहेत, घबराटीचे ट्रिगर नव्हे:

- `thresholds.session`: ९५. ५-तासांचा रीसेट थांबून पार करणे स्वस्त आहे, त्यामुळे सत्र विंडो आधीच दूर बदलते.
- `thresholds.weekly`: ९८. हा एक बार ७-दिवसांची एकत्रित बेरीज आणि प्रत्येक प्रति-मॉडेल साप्ताहिक मर्यादा या दोन्ही व्यापतो. साप्ताहिक कोटा वापरा-किंवा-गमवा असा आहे, त्यामुळे तो भिंतीच्या जवळ जाईपर्यंत रिकामा होतो.

दोन्ही मुद्दाम १०० च्या खाली आहेत: मोकळीक हे बजेट आहे स्वच्छ टर्न सीमेपर्यंत पोहोचण्यासाठी (तसेच macOS वर एका टर्नपर्यंत स्वीकार विलंब) खाते प्रत्यक्षात त्याची मर्यादा गाठण्याआधी. तेच बार बदल उमेदवारांची तपासणी करतात: त्याच्या कोणत्याही बारांवर असलेले खाते वैध लक्ष्य नाही. ट्रिगर आणि स्क्रीनिंग नेहमी तेच प्रभावी बार वापरतात (थ्रेशोल्ड्स वजा `policy.projectionMargin`), कारण ट्रिगरपेक्षा शिथिल स्क्रीन बदल अशा खात्यांवर उतरवेल ज्यांना ट्रिगर लगेच पुन्हा-फ्लॅग करतो, ज्यामुळे पूल पिंग-पॉंग होतो.

### लक्ष्य: गती दबाव

वापरण्यायोग्य खात्यांमध्ये, लक्ष्य ते खाते आहे जे त्याच्या स्वतःच्या साप्ताहिक गतीच्या सर्वात मागे आहे: सर्वात जास्त **गती दबाव (pace pressure)**, म्हणजे उरलेली साप्ताहिक टक्केवारी भागिले त्या खात्याच्या साप्ताहिक रीसेटपर्यंतचा वेळ. ज्या खात्याचा सर्वात जास्त कोटा गमावला जाणार आहे ते जिंकते. बरोबरी झाल्यास सर्वात लवकर साप्ताहिक समाप्ती, नंतर सर्वात कमी ७-दिवसांचा वापर या क्रमाने तुटते.

सर्व काही निरपेक्ष UTC युगांमध्ये साठवलेल्या कॅश केलेल्या विंडोजवर चालते, त्यामुळे जुना स्नॅपशॉट देखील योग्यरित्या सुटतो: उलटून गेलेला साप्ताहिक रीसेट अचूक ७-दिवसांच्या पावलांनी पुढे बाह्यरेखित होतो, आणि त्याच्या कॅश केलेल्या रीसेटच्या पलीकडे असलेली कोणतीही विंडो ताजी रिकामी मोजली जाते (बदलण्याचे कधीही कारण नाही, खाते बेंचवर ठेवण्याचे कधीही कारण नाही).

### हावरट विरुद्ध कठोर मार्ग

- **हावरट मार्ग** (सहभागी, पण प्रत्येक बाराच्या खाली): सध्याच्यासह प्रत्येक खात्याची क्रमवारी लावा. जर सध्याचे खाते आधीच जिंकते किंवा बरोबरी करते, तर काहीही करू नका. अन्यथा काटेकोरपणे चांगल्या खात्यावर बदला. ते कधीही प्रतीक्षा करत नाही आणि कधीही पूर्व-पार्क करत नाही - वापरण्यायोग्य सध्याचे खाते प्रतीक्षेसाठी बदलले जात नाही. कारण सध्याच्या खात्याचीही क्रमवारी लावली जाते, स्वयंचलित मार्ग आणि साधा `tokenmaxxing switch` दोन्ही आयडेम्पोटेंट आहेत: नियतकालिक मूल्यांकन योग्य खात्यावर एकवटते आणि नंतर तिथेच राहते.
- **कठोर मार्ग** (एक बार ओलांडला): सर्वोत्तम वापरण्यायोग्य उमेदवाराकडे दूर बदला. जर एखाद्या उमेदवाराचे रीफ्रेश टोकन मृत निघाले, तर त्याला needs-reauth म्हणून फ्लॅग केले जाते आणि पुढील उमेदवार वापरून पाहिला जातो. जर काहीही वापरण्यायोग्य नसेल, तर संपलेल्या-प्रतीक्षेचे तर्क चालते; फक्त असा कॉलर जो प्रत्यक्षात सत्र थांबवू शकतो (पर्यवेक्षित Stop हुक) त्यालाच अजूनही-अवरोधित पण सर्वात-लवकर-पुनर्प्राप्त होणाऱ्या खात्यावर पूर्व-पार्क करण्याची परवानगी आहे.

### प्रति-मॉडेल मर्यादा

`policy.switchModels` (डीफॉल्ट `["fable"]`) ती मॉडेल कुटुंबे नावाने सांगते ज्यांची प्रति-मॉडेल साप्ताहिक मर्यादा बदल ट्रिगर करू शकते. जुळवणी कुटुंब टोकनद्वारे होते, कधीही अचूक प्रदर्शन स्ट्रिंगद्वारे नाही: मॉडेल प्रदर्शन नावे बदलतात ("Fable" चे "Fable 5" झाले), आणि अचूक-स्ट्रिंग गेटने एकदा प्रति-मॉडेल बदल पूर्णपणे गप्पपणे बंद केला होता. दोन संबंधित सुरक्षा नियम:

- अज्ञात सक्रिय मॉडेल प्रत्येक कॉन्फिगर केलेल्या कुटुंबाला गेट करते. बदल स्नॅपशॉट्स साफ केल्यानंतर लगेच, हेडलेस मशीन मॉडेल-आंधळेपणाने चालू शकते; अज्ञात म्हणजे अमर्यादित असे मानल्याने एकदा एक खाते त्याच्या Fable मर्यादेवर तासभर लक्षात न येता बसले होते.
- उमेदवार स्क्रीनिंग गेट केलेल्या प्रति-मॉडेल मर्यादा देखील मोजते, त्यामुळे जिथे प्रत्येक खात्याने आपली Fable मर्यादा जाळली आहे असा पूल राउंड-रॉबिन करत नाही.

### कूलडाउन

४५-सेकंदांचा बदल-नंतरचा कूलडाउन स्वयंचलित मार्गाला गेट करतो. बदलानंतर त्याच ४५ सेकंदांसाठी statusline टी दाबली जाते (macOS वर स्वीकाराला ३० सेकंदांपर्यंत वेळ लागतो), त्यामुळे आधीचे मूल्यांकन बदलानेच अवैध केलेल्या डेटावर चालेल - त्या नेमक्या परिस्थितीने एकदा A-ते-B-आणि-परत respawn लूप निर्माण केला होता. मॅन्युअल `tokenmaxxing switch` कूलडाउनने प्रभावित होत नाही.

## कॉन्फिगरेशन

कॉन्फिग `~/.config/tokenmaxxing/config.json` येथे JSON आहे. प्रत्येक फील्ड ऐच्छिक आहे; डीफॉल्ट्स प्रति-फील्ड लागू होतात.

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: वर वर्णन केलेले स्क्रीनिंग बार.
- `policy.projectionMargin`: प्रभावी बार तयार करण्यासाठी दोन्ही बारांमधून वजा केला जातो.
- `policy.greedySessionFloor`: सत्र-वापर टक्केवारी ज्यावर हावरट एकवटणे सहभागी होते.
- `policy.switchModels`: मॉडेल कुटुंबे ज्यांची प्रति-मॉडेल साप्ताहिक मर्यादा बदल गेट करते (नोंदी लोड होताना लोअरकेस केल्या जातात).
- `policy.usagePollTtlMs`: एक `/usage` प्रति-मॉडेल पोल किती काळ ताजा राहतो.
- `policy.maxWaitMs`: संपलेल्या-पूलची स्वयं-प्रतीक्षा मर्यादा.

`tokenmaxxing config` स्रोतांसह प्रभावी कॉन्फिग दाखवते; `config set`/`unset` डॉट-केलेल्या कीज संपादित करतात; `config tidy` अज्ञात कीज काढून टाकते.

## स्थिती डिरेक्टरी मांडणी

सर्व काही `~/.config/tokenmaxxing/` अंतर्गत राहते (`TOKENMAXXING_HOME` ने ओव्हरराइड करता येते; प्रत्येक बाह्यरित्या निरीक्षण करण्यायोग्य मार्गाला एक env ओव्हरराइड आहे जेणेकरून संपूर्ण साधन चाचण्यांमध्ये पूर्णपणे विलगपणे चालू शकते).

| मार्ग | ते काय धरते |
|---|---|
| `config.json` | तुमचे कॉन्फिगरेशन (विरळ; डीफॉल्ट्स प्रति फील्ड लागू होतात) |
| `accounts.json` | पूल केलेल्या Claude खात्यांचा गुप्त-नसलेला निर्देशांक: लेबले, ids, कॅश केलेल्या वापर विंडोज. कधीही टोकन्स नाहीत |
| `usage.json` | statusline टीचा एकत्रित विंडो स्नॅपशॉट; त्याचा mtime फीडचा जिवंतपणा दर्शवणारा ठोका आहे |
| `model-usage.json` | `/usage` कडून TTL-कॅश केलेल्या प्रति-मॉडेल साप्ताहिक मर्यादा |
| `lastswap.json` | शेवटच्या बदलाचा युग टाइमस्टॅम्प; ४५-सेकंदांचा कूलडाउन चालवतो |
| `lock` | बदलांना क्रमवार करणारी `flock` फाइल |
| `tokenmaxxing.log` | केवळ-जोडणी घटना लॉग |
| `bin/` | PATH शिम्स: `claude`, `codex`, आणि `tokenmaxxing` / `xx` एंट्री पॉइंट्स |
| `respawn/<session-id>` | पर्यवेक्षक ज्यांवर लक्ष ठेवतो ते संपलेल्या-प्रतीक्षेचे respawn मार्कर्स |
| `creds/` | फक्त Linux: पार्क केलेल्या क्रेडेन्शियल फाइल्स, 0700 डिरेक्टरीमध्ये 0600 (macOS त्याऐवजी क्रेडेन्शियल्स प्रति-खाते कीचेन आयटम्स म्हणून पार्क करते) |
| `onboard/`, `sample/` | `add`/`auth` लॉगिन आणि पार्क-खाते `/usage` प्रोब्ससाठी टाकाऊ विलग कॉन्फिग होम्स; साध्या-मजकूर क्रेडेन्शियल्स धरणारी onboard होम्स संकलनानंतर हटवली जातात |
| `slack.json` | `xx serve` टोकन्स आणि चॅनेल लिंक्स (0600) |
| `slack-threads/` | `xx serve` साठी प्रति-थ्रेड सत्र नोंदी |
| `codex-*` | समांतर Codex पूल: `codex-accounts.json`, `codex-lastswap.json`, `codex-lock`, `codex-creds/`, `codex-onboard/`, `codex-respawn/`, आणि `codex-live/` (प्रति चालू पर्यवेक्षित codex सत्र एक PID-पडताळलेली उपस्थिती फाइल, त्यामुळे थेट खाते कधीही बदल लक्ष्य नसते) |

स्वतःच्या डिरेक्टरीबाहेर, tokenmaxxing नेमके यांनाच स्पर्श करते: `~/.claude.json` (`oauthAccount` बदल), Claude Code ची `settings.json` (हुक आणि statusline नोंदी), थेट क्रेडेन्शियल स्टोअर (macOS वर `Claude Code-credentials` कीचेन आयटम, Linux वर `.credentials.json`), `~/.claude.lock` (claude चे रीफ्रेश लॉक, बदलांदरम्यान घेतलेले), codex ची `auth.json` आणि `hooks.json`, आणि launchd किंवा systemd मधील नियतकालिक-तपासणी युनिट.

## क्रेडेन्शियल साठवण आणि सुरक्षा मॉडेल

सर्व स्थिती `~/.config/tokenmaxxing/` मध्ये राहते. क्रेडेन्शियल I/O एका प्लॅटफॉर्म-निवडलेल्या स्टोअर फसाडमधून जाते; कॉल साइट्स कधीही प्लॅटफॉर्मवर शाखा करत नाहीत.

**macOS**: क्रेडेन्शियल्स लॉगिन कीचेनमध्ये generic-password आयटम म्हणून राहतात, Claude Code स्वतः ती जिथे ठेवते तिथेच जुळत. थेट आयटम तो आहे जो claude वाचते; प्रत्येक पूल केलेल्या खात्याचा बॅकअप त्याच्या स्वतःच्या `tokenmaxxing-cred-<uuid8>` कीचेन आयटम म्हणून पार्क केला जातो. डिस्कवर काहीही साध्या मजकुरात नसते. वाचन `security find-generic-password -w` वापरते (गुपित फक्त stdout वरच दिसते); लेखन stdin वरून `security -i` मध्ये `add-generic-password` ओळ पाईप करते जेणेकरून गुपित कोणत्याही प्रक्रियेच्या argv मध्ये कधीही दिसत नाही. इंटरॲक्टिव्ह मोडमध्ये सुमारे ४ KB ची ओळ बफर आहे, त्यामुळे अवाढव्य ब्लॉब्स argv लेखनावर परत पडतात - पार्क केलेले आयटम फक्त किमान OAuth ऑब्जेक्ट साठवतात याचे एक कारण.

**Linux**: Claude Code क्रेडेन्शियल्स 0600 साध्या-मजकूर फाइल म्हणून साठवते, आणि tokenmaxxing तेच मॉडेल अनुसरते: थेट फाइल claude ची स्वतःची `.credentials.json` आहे, आणि पार्क केलेले बॅकअप्स `~/.config/tokenmaxxing/creds/` अंतर्गत 0700 डिरेक्टरीमध्ये अणुरूप 0600 फाइल्स आहेत. येथे अणुरूप म्हणजे तात्पुरत्यात-लिहा, fsync, नंतर पुनर्नामकरण: समांतर वाचक नेहमी संपूर्ण जुनी किंवा संपूर्ण नवी फाइल पाहतो, कधीही आंशिक नाही.

बदल लागू करणारे सुरक्षा नियम:

- **खऱ्या मालकाकडून संकलन.** बदलापूर्वी, थेट क्रेडेन्शियलचा प्रत्यक्ष मालक API ला विचारून सोडवला जातो की टोकन कोणत्या संस्थेचे आहे (OAuth roles एंडपॉइंटवर `fetchTokenOrg`) - कधीही साठवलेल्या सक्रिय लेबलवर विश्वास ठेवून नाही, जे भरकटू शकते. एका भरकटलेल्या लेबलमुळे एकदा एका खात्याच्या संकलनाने दुसऱ्या खात्याचा एकमेव बॅकअप ओव्हरराइट केला होता. जर थेट क्रेडेन्शियल पूलबाहेरील खात्याचे असेल, तर बदल त्याला दडपण्याऐवजी सरळ नकार देतो.
- **एक क्रिटिकल सेक्शन.** संकलन, नवीन क्रेडेन्शियलची स्थापना, त्याच्या फिरवलेल्या टोकनचा बॅकअप, `~/.claude.json` खाते बदल, आणि सक्रिय-लेबल कमिट हे सर्व एकाच लॉक केलेल्या सेक्शनमध्ये होते.
- **claude च्या स्वतःच्या रीफ्रेशशी इंटरलॉक.** समाप्तीजवळील सत्र कोणत्याही क्षणी त्याचे स्वतःचे टोकन फिरवू शकते, त्यामुळे क्रेडेन्शियल लेखन Claude Code चे रीफ्रेश लॉक देखील घेते (सर्वोत्तम-प्रयत्न, जुने-लॉक पुन्हा-दावा आणि बांधलेल्या टाइमआउटसह).
- **मृत ग्रांट्स स्वच्छपणे कमी होतात.** `invalid_grant` परत येणारा रीफ्रेश त्या खात्याला needs-reauth म्हणून फ्लॅग करतो आणि त्रुटी प्रसारित होण्यापूर्वी फ्लॅग टिकवतो, त्यामुळे retry लूप्स उमेदवार संच लहान करतात आणि संपतात. `tokenmaxxing auth` फ्लॅग केलेले खाते जागच्या जागी दुरुस्त करते, आणि दुरुस्त होत असलेल्या खात्यापेक्षा वेगळ्या खात्यावर उतरणाऱ्या लॉगिनला नकार देते.
- **टोकन लॉगिंग नाही.** टोकन्स कधीही लॉग्स, त्रुटी, किंवा आउटपुटमध्ये दिसत नाहीत. टोकन आणि वापर एंडपॉइंट्समधील त्रुटी बॉडी कधीही कच्च्या दाखवल्या जात नाहीत; फक्त परवानगी-यादीतील फील्ड्सचा संच टिकतो, कारण टोकन एंडपॉइंटची अपयश बॉडी विनंती सामग्रीचा प्रतिध्वनी करू शकते.
- **प्रोब स्वच्छता.** कोणतीही स्पॉन केलेली `claude` प्रोब claude आपल्या कीचेन शोधापूर्वी सन्मानित करणाऱ्या आठ पर्यावरण चलांना स्वच्छ करते (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, वगैरे), त्यामुळे प्रोब कधीही चुकीच्या खात्याला श्रेय दिली जाऊ शकत नाही.

## प्लॅटफॉर्म नोंदी: macOS विरुद्ध Linux

| | macOS | Linux |
|---|---|---|
| थेट क्रेडेन्शियल | लॉगिन कीचेन generic-password आयटम | 0600 `.credentials.json` फाइल |
| पार्क केलेली क्रेडेन्शियल्स | प्रति-खाते कीचेन आयटम्स | 0700 डिरेक्टरीमध्ये 0600 फाइल्स |
| बदलानंतर स्वीकार | सुमारे ३० सेकंदांत (कीचेन वाचन कॅश) | पुढील विनंती (फाइल mtime पोल) |
| नियतकालिक तपासणी | launchd एजंट, दर १८०सेकंद | systemd यूजर टायमर, दर १८०सेकंद |
| वेगळ्या-लॉगिनचे स्टोअर | प्रति कॉन्फिग डिरेक्टरी हॅश-नेमस्पेस केलेली कीचेन सेवा | वेगळ्या कॉन्फिग डिरेक्टरीमधील फाइल |

जाणून घेण्यासारखे दोन Linux-विशिष्ट तपशील: claude आपली क्रेडेन्शियल डिरेक्टरी प्रथम `CLAUDE_SECURESTORAGE_CONFIG_DIR` वरून सोडवते (नंतर `CLAUDE_CONFIG_DIR`, नंतर `~/.claude`), आणि tokenmaxxing ती सोडवणी अगदी अचूक प्रतिबिंबित करते जेणेकरून त्या दोघी कधीही डीसिंक होणार नाहीत. आणि तीच claude आवृत्ती दोन OS बिल्ड्स `/usage` रीसेट घड्याळे वेगवेगळ्या स्वरूपात करतात (एक " at " ग्लू वापरते, दुसरी स्वल्पविराम); tokenmaxxing चा पार्सर नेमके त्या दोन स्वरूपांना स्वीकारतो आणि कोणत्याही तिसऱ्यावर अंदाज लावण्याऐवजी लॉग करतो.

macOS वर, एक प्रामाणिक मर्यादा: `init` आणि `add` मुद्दाम कीचेनला इंटरॲक्टिव्हपणे स्पर्श करतात, जेणेकरून हेडलेस हुकच्या आत पहिला `security` अॅक्सेस थंड नसतो.

## statusline

tokenmaxxing Claude Code ची statusline मूळतः प्रस्तुत करते (वापर फीड टी करत असताना). डिझाइन तत्त्व: कोटा रंगात वाहून नेला जातो, आकड्यांत नाही. एक ओळ, उदाहरणार्थ:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- प्रत्येक विंडो टोकन म्हणजे त्याचा रीसेटपर्यंतचा-वेळ, वापरलेल्या टक्केवारीनुसार सलग हिरवा-ते-पिवळा-ते-लाल रॅम्पवर रंगवलेला (टर्मिनल समर्थन देते तेव्हा truecolor, अन्यथा २५६-रंग क्यूबवर पायरीबद्ध). रॅम्प ० साठी शुद्ध हिरव्यावर, ७५ वर पिवळ्यावर, आणि ९५ व त्याहून अधिकवर लाल रंगावर स्थिर होतो, त्यामुळे जुने तीव्रता बँड रॅम्प अँकर म्हणून टिकतात.
- मॉडेल नाव त्याच रॅम्पवर संदर्भ-विंडो भरणीने रंगवले जाते.
- हिरवा `◆` सक्रिय खात्याच्या विंडोजना पुढे नेतो; प्रत्येक पार्क केलेल्या खात्याला त्याचा स्वतःचा निळसर `◇` मिळतो (पुन्हा-प्रमाणन आवश्यक असल्यास लाल `✗`). खाती सर्वात लवकर येणाऱ्या रीसेटनुसार क्रमवारी लावतात.
- प्रत्येक ब्लॉकमध्ये प्रति-मॉडेल एका उघड्या रंगवलेल्या आद्याक्षराने प्रथम येते: Fable `𝒇` प्रस्तुत करते; इतर कुटुंबे त्यांचे अपरकेस केलेले पहिले अक्षर वापरतात, नेहमी कुटुंब-जुळवलेले.
- अस्पर्शित पार्क केलेले खाते हिरवा `full` प्रस्तुत करते. अज्ञात रीसेटसह मोजलेला वापर रंगवलेला `?` प्रस्तुत करतो, आणि गेट केलेल्या मॉडेलवरील न-मोजलेली प्रति-मॉडेल मर्यादा एक न-रंगवलेला `𝒇?` प्रस्तुत करते - न-मोजलेले कधीही सुरक्षित दिसू नये.
- रीसेट काउंटडाउन फक्त सर्वात मोठे एकक दाखवतात, कधीही "now" किंवा "0m" नाही; येणारा रीसेट नसलेली विंडो हिरवा `0` (पुन्हा रिकामी) प्रस्तुत करते.
- लिंक केलेल्या git worktree चे बेसनेम ओळ पुढे नेते; मुख्य चेकआउट तिथे काहीही प्रस्तुत करत नाही. शोध फाइलसिस्टममध्ये `.git` फाइल शोधतो आणि कधीही git सबप्रोसेस स्पॉन करत नाही.
- `NO_COLOR` सेट असल्यास, ओळ चिकटवलेल्या संख्यात्मक स्वरूपावर परत पडते (`2h5` म्हणजे २ तासांत रीसेट होते, ५% वापरले; संदर्भ भरणीसाठी `ctx 42`) - रंगाशिवाय, संपलेली विंडो ताजी दिसू नये.

Subagent कार्ये claude च्या subagentStatusLine पृष्ठभागाद्वारे त्यांच्या स्वतःच्या पॅनेल पंक्ती मिळवतात: प्रति सक्रिय कार्य एक पंक्ती, कुटुंब नाव त्या कार्याच्या संदर्भ भरणीने रंगवलेले.

## Codex समर्थन

तेच पूलिंग OpenAI च्या Codex CLI साठी कार्य करते, तुमच्या स्वतःच्या ChatGPT-सबस्क्रिप्शन खात्यांविरुद्ध:

```sh
tokenmaxxing init --codex   # तुमचे सध्याचे codex लॉगिन आयात करा + codex पर्यवेक्षक व Stop हुक स्थापित करा
tokenmaxxing add --codex    # आणखी एक खाते वेगळेपणाने लॉग इन करा - तुमचे प्राथमिक लॉगिन अस्पर्शित राहते
codex                       # नेहमीप्रमाणे codex वापरा
```

Codex पूल पूर्णपणे समांतर स्थिती आहे: त्याचा स्वतःचा खाते निर्देशांक, त्याच्या स्वतःच्या पार्क केलेल्या क्रेडेन्शियल फाइल्स (दोन्ही प्लॅटफॉर्मवर 0600 फाइल्स, कारण codex चे स्वतःचे स्टोअर एक साध्या-मजकूर फाइल आहे), त्याचे स्वतःचे लॉक, त्याचा स्वतःचा शेवटच्या-बदलाचा टाइमस्टॅम्प. निर्णय-धोरण कोड वगळता Claude पूलशी काहीही सामायिक केले जात नाही.

### Codex वर हॉट-स्वॅप का अशक्य आहे

चालू codex प्रक्रिया एक इन-मेमरी auth manager धरते आणि `auth.json` आता वेगळ्या खात्याचे नाव घेते तेव्हा तो पुन्हा लोड करण्यास स्पष्टपणे नकार देते. कोणताही फाइल वॉचर आणि कोणताही प्रति-विनंती क्रेडेन्शियल पोल नाही, त्यामुळे चालू codex खाली बदललेले क्रेडेन्शियल इन्फरन्ससाठी फक्त कधीही लागू होत नाही. पुन्हा सुरू करणे हाच बदल आहे: `codex resume <session-id>` `auth.json` आता जे खाते धरते त्यावर स्थानिक ट्रान्सक्रिप्ट सुरू ठेवते.

tokenmaxxing हे codex पर्यवेक्षक शिमसह हाताळते: Stop हुक प्रत्येक टर्न सीमेवर तोच हावरट गती-दबाव निर्णय चालवतो, आणि जेव्हा तो बदलतो, तेव्हा तो एक मार्कर लिहितो जो पर्यवेक्षकाला कमिट केलेल्या सीमेवर सत्राला SIGTERM करायला आणि ताज्या खात्यावर `codex resume <session-id>` पुन्हा-लॉन्च करायला लावतो, ट्रान्सक्रिप्ट अबाधित. कारण प्रत्येक codex बदल एक दृश्यमान पुन्हा सुरू करणे आहे, codex हावरट मार्ग १.२x सुधारणा मार्जिन बाळगतो: आव्हानकर्त्याने सध्याच्या खात्याच्या गती दबावाला २०% ने हरवले पाहिजे, केसाइतक्या फरकाने नाही. कठोर मार्ग (ओलांडलेला बार) मार्जिनकडे दुर्लक्ष करतो. codex साठी कोणताही संपलेल्या-पूलचा काउंटडाउन देखील नाही - काहीही codex सत्र थांबवू शकत नाही - त्यामुळे पूर्णपणे संपलेला codex पूल तिथेच राहतो.

इतर codex-विशिष्ट यंत्रणा:

- वापर codex च्या स्वतःच्या दर-मर्यादा एंडपॉइंटविरुद्ध एका मुक्त प्रमाणित GET वरून वाचला जातो (CLI च्या `/status` जो कॉल करते तोच): टक्केवारी तसेच निरपेक्ष युग रीसेट वेळा, एकत्रित विंडोज आणि प्रति-मॉडेल मर्यादा सारख्याच. विंडो वर्गीकरण कालावधी-आधारित आहे, कधीही स्थान-आधारित नाही, कारण सध्याच्या योजनांना अजिबात ५-तासांची विंडो नसू शकते आणि साप्ताहिक विंडो प्राथमिक स्लॉटमध्ये बसते.
- Codex रीफ्रेश टोकन्स फिरतात, आणि निवृत्त झालेले पुन्हा वापरल्याने संपूर्ण ग्रांट कुटुंब मारते. प्रत्येक फिरवणी परत येताच लगेच टिकवली जाते, सक्रिय खात्याचा नमुना फक्त थेट ब्लॉबमधूनच घेतला जातो (कधीही जुन्या पार्क केलेल्या प्रतीतून नाही), आणि प्रति-सत्र उपस्थिती फाइल्स हे सुनिश्चित करतात की थेट सहचर सत्रात चालणारे खाते कधीही बदल लक्ष्य नसते आणि त्याचे पार्क केलेले टोकन कधीही रीफ्रेश होत नाही.
- Codex ला फाइल क्रेडेन्शियल स्टोअर आवश्यक आहे: keyring स्टोअर पिन केले असल्यास `init --codex` झटपट अपयशी होते, आणि `add --codex` वेगळ्या ऑनबोर्डिंग होममध्ये फाइल-मोड सेटिंग लिहितो जेणेकरून लॉगिन संकलनयोग्य उतरते.
- एक मॅन्युअल पायरी: codex ज्या हुक्सवर विश्वास ठेवण्यास सांगितले गेले नाही ते वगळते. `init --codex` नंतर, codex एकदा उघडा आणि `/hooks` द्वारे tokenmaxxing Stop हुकवर विश्वास ठेवा, अन्यथा स्वयंचलित-बदल गप्पपणे निष्क्रिय राहतो. `init --codex` ही आठवण प्रिंट करते.

## Slack ब्रिज: xx serve

`tokenmaxxing serve` Socket Mode वर एक स्थानिक Slack डिमन चालवतो - कोणत्याही सार्वजनिक URL ची गरज नाही. सेटअप:

```sh
tokenmaxxing serve setup                    # अॅप मॅनिफेस्ट प्रिंट करते, दोन टोकन्ससाठी विचारते
tokenmaxxing serve link <channel-id> <repo> # एक चॅनेल एका रेपो चेकआउटशी जोडा
tokenmaxxing serve                          # डिमन चालवा
```

लिंक केलेल्या चॅनेलमध्ये बॉटचा उल्लेख करा आणि तो त्या थ्रेडसाठी, लिंक केलेल्या रेपो चेकआउटमध्ये एक Claude Code सत्र उघडतो. प्रत्येक थ्रेड संदेश `resume` सह एक Agent SDK `query()` चालवतो - कधीही सतत स्ट्रीमिंग क्वेरी नाही - त्यामुळे `ensureBestAccount()` प्रत्येकाच टर्नला पूलचे पुन्हा-मूल्यांकन करते आणि डिमन थ्रेड्स न गमावता पुन्हा सुरू होऊ शकतो (थ्रेड नोंदी टिकाऊ आहेत; डिमन सुरुवातीला त्यांना पुन्हा-सबस्क्राइब करतो).

लक्षणीय वर्तन:

- **स्ट्रीमिंग**: उत्तरे मूळतः Slack मध्ये स्ट्रीम होतात, विचारांसाठी आणि साधन धावांसाठी कार्य कार्ड्ससह, हायलाइटिंगसह प्रस्तुत केलेला फेन्स्ड कोड, किंमत आणि कालावधीसह एक शेवटचे "Turn" कार्ड, आणि जेव्हा साधन धाव स्ट्रीम केलेल्या मजकुरात व्यत्यय आणते तेव्हा एक नवीन Slack संदेश उघडला जातो, त्यामुळे एक टर्न साधन धावांभोवती वेगवेगळे संदेश म्हणून वाचला जातो. TodoWrite कॉल्स एक स्थिर चेकलिस्ट कार्ड जागच्या जागी अद्यतनित करतात.
- **परवानग्या**: प्रति-लिंक `permissionMode` डीफॉल्ट `acceptEdits` असतो; `--yolo` (टोपणनाव `--dangerous`) एका लिंकला `bypassPermissions` मध्ये निवडतो. रिले केलेल्या टर्नमध्ये इंटरॲक्टिव्ह संवाद अनुमत नाहीत - कोणीही Slack द्वारे एकाचे उत्तर देऊ शकत नाही - त्यामुळे मॉडेल गद्यात विचारते आणि तुमचे थ्रेड उत्तर पुढील टर्न असते. एक बंडल केलेली प्लगइन स्किल त्याला विनंतीकर्त्याला टॅग करायला आणि निर्णय आवश्यक असताना टर्न संपवायला शिकवते.
- **स्लॅश कमांड्स**: ज्या थ्रेड संदेशाचा छाटलेला मजकूर `/` ने सुरू होतो तो एक claude स्लॅश कमांड म्हणून चालतो. Slack चा कंपोझर `/` ने सुरू होणारे संदेश खातो, त्यामुळे उल्लेख-प्रथम स्वरूप (`@bot /usage`) किंवा एक अग्रगण्य स्पेस वापरा.
- **सुरळीत बंद**: SIGTERM/SIGINT निचरा करते - नवीन टर्न मोठ्याने टाकले जातात, उड्डाणातील टर्नना ५ मिनिटांपर्यंत वेळ मिळतो, आणि claude मूल त्याच्या स्वतःच्या प्रक्रिया गटात वेगळे चालते जेणेकरून टर्मिनल Ctrl-C निचरा टर्न जतन करण्याआधी त्याला मारू शकत नाही.
- **थ्रेड साफसफाई**: जेव्हा तुम्ही त्याला काम पूर्ण झाल्याचे सांगता, तेव्हा मॉडेल एका इन-प्रोसेस `finish_thread` साधनाला कॉल करते; टर्न पूर्णपणे संपल्यानंतर, डिमन थ्रेड नोंद टाकतो, अनसबस्क्राइब करतो, आणि एक पुष्टीकरण पोस्ट करतो. एक ताजा उल्लेख नवीन सत्र सुरू करतो.
- **त्रुटी स्वच्छता**: टर्न त्रुटी छाटलेला केवळ-संदेश मजकूर पोस्ट करतात, कधीही कच्च्या त्रुटी बॉडी नाहीत.

## Agent SDK पृष्ठभाग

पॅकेजचा प्रोग्रामॅटिक एंट्री (`exports["."]` `src/sdk.ts` कडे इशारा करतो) tokenmaxxing ला Claude Agent SDK शी जोडतो, तुम्ही तुमच्या स्वतःच्या पूल केलेल्या खात्यांविरुद्ध बांधलेल्या एजंट्ससाठी. तुमचा अॅप Bun अंतर्गत चालला पाहिजे (tokenmaxxing TypeScript स्रोत पाठवते आणि `bun:ffi` वापरते).

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // स्पॉनआधी बदल निर्णय चालवा

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // पिन केलेले खरे claude + स्वच्छ केलेले env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // प्रत्येक टर्न सीमेवर पुन्हा-निर्णय घ्या
  },
})) {
  // बदलांदरम्यान `resume` साठी init संदेशातून session id पकडा
}
```

Agent SDK प्रति `query()` एक claude सबप्रोसेस स्पॉन करते आणि स्पॉनवर एकदाच क्रेडेन्शियल्स वाचते - कोणतीही statusline नाही, कोणताही मध्य-क्वेरी हॉट-स्वॅप नाही - त्यामुळे एकत्रीकरण सीमा-आधारित आहे:

- `ensureBestAccount()` हा नेमका तोच निर्णय आहे जो CLI हुक्स आणि टायमर चालवतात (बार, गती दबाव, कूलडाउन, सर्व सामायिक कोड), कधीही पूर्वानुमानात्मक नाही: एक SDK सत्र संपलेल्या काउंटडाउनसाठी कधीही थांबवले जाऊ शकत नाही.
- `pooledOptions()` `pathToClaudeCodeExecutable` ला खऱ्या claude बायनरीशी पिन करते (कधीही पर्यवेक्षक रॅपर नाही) आणि प्रत्येक सभोवतालचे क्रेडेन्शियल ओव्हरराइड स्वच्छ केलेले संपूर्ण बदली `env` पुरवते. जर तुमच्या अॅपच्या वातावरणात `CLAUDE_CONFIG_DIR` किंवा `CLAUDE_SECURESTORAGE_CONFIG_DIR` सेट असेल तर ते झटपट अपयशी होते: Linux वर एक बदल थेट क्रेडेन्शियल त्या जिथे इशारा करतात तिथे लिहेल तर स्वच्छ केलेला सबप्रोसेस डीफॉल्ट स्टोअर वाचतो, एक गप्प चुकीच्या-खात्याचा डीसिंक.
- `stopHookCheck` टर्न सीमांवर निर्णय पुन्हा-चालवते; तो जो बदल उतरवतो तो पुढील स्पॉनवर लागू होतो. तो पुन्हा फेकण्याऐवजी त्याच्या स्वतःच्या त्रुटी पकडतो (stderr आणि लॉगमध्ये लॉग करत), कारण न-हाताळलेला हुक अपवाद एजंटमध्ये व्यत्यय आणू शकतो, आणि तुटलेल्या बदल तपासणीवरून टर्न रद्द करणे सध्याचे खाते पार करण्यापेक्षा जास्त महाग पडते.

`sdk.ts` Agent SDK कडून स्वतः काहीही आयात करत नाही; त्याची मूल्ये संरचनात्मकपणे SDK च्या पर्यायांमध्ये पसरतात.

## बिल्ड आणि वितरण

npm पॅकेज TypeScript स्रोत पाठवते, बिल्ड नव्हे: `tokenmaxxing` bin थेट Bun shebang सह `src/main.ts` कडे इशारा करते, आणि Bun 1.2.6 किंवा नवीन ते जसेच्या तसे चालवते. म्हणूनच Bun ही एक कठोर आवश्यकता आहे. डिझाइनने कोणतीही संकलित बायनरी नाहीत: एका सुरुवातीच्या रिलीजने प्रत्येक प्लॅटफॉर्मवर एकच 61 MB macOS बायनरी पाठवली आणि Linux वर `exec format error` सह अपयशी झाली, आणि प्रति-प्लॅटफॉर्म संकलित पॅकेजेसना प्रत्येकी स्वतःची रिलीज पाइपलाइन लागली असती, त्यामुळे Bun द्वारे थेट स्रोत चालवणे हे वितरण मॉडेल बनले.

पॅकेजचा `exports` नकाशा वर वर्णन केलेला प्रोग्रामॅटिक एंट्री म्हणून `src/sdk.ts` उघड करतो. रिलीज GitHub वर `v<version>` असे टॅग केले जातात; CI विश्वसनीय प्रकाशनाद्वारे (OIDC, provenance सह) npm वर प्रकाशित करते, आणि प्रकाशन गेट प्रथम typecheck आणि संपूर्ण चाचणी संच चालवतो.

- **एक थंड टर्न.** प्रॉम्प्ट कॅश संस्था-व्याप्तीचा आहे, त्यामुळे नवीन खात्यावरील पहिला टर्न संदर्भ एकदा पुन्हा-अपलोड करतो.
- **संपलेल्या-थांब्याचा अडथळा.** फक्त पूर्णपणे संपलेला पूल काउंटडाउनसाठी सत्र थांबवतो; त्या क्षणार्धात टाइप केलेले काहीही गमावले जाते.
- **स्वीकार विलंब.** macOS वर बदलानंतरच्या सुमारे ३० सेकंदांतील पहिला टर्न अजूनही जुने खाते मोजू शकतो; बारांची मोकळीक ते शोषून घेते.
- **सामायिक स्फोट त्रिज्या.** सर्व डीफॉल्ट-प्रोफाइल सत्रे एक थेट क्रेडेन्शियल सामायिक करतात, त्यामुळे एक बदल त्या सर्वांना एकत्र हलवतो (प्रत्येक जागच्या जागी स्वीकारतो).
- **Linux वर साध्या-मजकूर क्रेडेन्शियल्स.** Claude Code स्वतः Linux क्रेडेन्शियल्स 0600 साध्या-मजकूर फाइल म्हणून साठवते; tokenmaxxing च्या पार्क केलेल्या प्रती तेच मॉडेल अनुसरतात.

## समस्यानिवारण आणि FAQ

**`claude` पर्यवेक्षित असल्याचे वाटत नाही.**
`tokenmaxxing doctor` चालवा. शिमने PATH सोडवणी जिंकली पाहिजे; तपासा की तुमच्या शेल rc मधील `# tokenmaxxing PATH` ओळ सध्याच्या bin डिरेक्टरीकडे इशारा करते आणि खऱ्या claude च्या पुढे बसते. `doctor` `alias claude=...` किंवा रॅपरला झाकणाऱ्या `claude()` शेल फंक्शनबद्दल, आणि निरपेक्ष मार्गाने claude बायनरी लॉन्च करणाऱ्या टोपणनावांबद्दल (जे पर्यवेक्षकाला पूर्णपणे टाळतात) देखील इशारा देतो.

**Codex वर स्वयंचलित-बदल कधीही फायर होत नाही.**
Codex ज्या हुक्सवर विश्वास ठेवण्यास सांगितले गेले नाही ते वगळते. codex उघडा, `/hooks` चालवा, आणि tokenmaxxing Stop हुकवर विश्वास ठेवा. विश्वास हुकच्या हॅशविरुद्ध नोंदवला जातो, त्यामुळे हुक कधी संपादित केला गेला तर तो पुन्हा-द्यावा लागतो.

**statusline मध्ये एका खात्यावर लाल `✗` दिसतो.**
त्याचे रीफ्रेश टोकन मृत आहे (रद्द केले किंवा त्याच्या बॅकअपखाली फिरवले गेले). त्याला जागच्या जागी पुन्हा प्रमाणित करण्यासाठी `tokenmaxxing auth <sel>` चालवा; कमांड तुम्हाला कोणत्या ईमेलने साइन इन करायचे ते सांगते आणि वेगळ्या खात्यावर उतरणाऱ्या लॉगिनला नकार देते.

**सर्वात जास्त उरलेला कोटा असलेल्या खात्यावर ते का बदलत नाही?**
कारण ते सर्वात जास्त कोटा गमावण्याच्या धोक्यात असलेले खाते नाही. लक्ष्य ते खाते आहे जे त्याच्या स्वतःच्या साप्ताहिक गतीच्या सर्वात मागे आहे: उरलेली टक्केवारी भागिले त्याच्या साप्ताहिक रीसेटपर्यंतचा वेळ. समान प्रमाणात उरल्यास ते सर्वात लवकर समाप्ती प्रथम असे कमी होते, आणि समान समाप्तीसह सर्वात जास्त उरलेले प्रथम असे.

**ते नुकतेच बदलले आणि statusline अजूनही जुने खाते दाखवते.**
macOS वर सुमारे ३० सेकंदांपर्यंत अपेक्षित: चालू सत्र त्याच्या पुढील क्रेडेन्शियल-कॅश रीफ्रेशवर बदललेले क्रेडेन्शियल स्वीकारते. वापर टी नेमके याच कारणासाठी बदलानंतर ४५ सेकंद दाबली जाते.

**`status --force` ला काही खर्च येतो का?**
होय, मुद्दाम: ते प्रति खाते एक किमान मोजलेली haiku विनंती पाठवते जेणेकरून प्रत्येक ५-तासांची सत्र विंडो निष्क्रिय पडून राहण्याऐवजी त्या क्षणी सुरू होईल, नंतर ताजे नमुने घेते. साधा `status` आणि `watch` कधीही पिंग करत नाहीत; `/usage` वाचन मुक्त आहेत. लक्षात घ्या की सर्व्हर वापर फीड ताज्या उघडलेल्या विंडोला सेकंदांपासून मिनिटांपर्यंत मागे ठेवू शकते, त्यामुळे पिंगनंतर लगेच केलेली प्रोब अजूनही पिंग-पूर्व स्थिती दाखवू शकते - `status` पिंग अपयशी झाल्याचा आव आणण्याऐवजी एक नोंद प्रस्तुत करते.

**`/usage` प्रोबने सक्रिय खात्यासाठी काहीही परत केले नाही.**
हे एक ज्ञात claude वर्तन आहे: जेव्हा त्याचे अंतर्गत वापर आणणे अपयशी होते किंवा दर-मर्यादित होते, तेव्हा `/usage` फक्त स्थानिक सत्र आकडेवारी प्रिंट करते, कोणत्याही टक्केवारी ओळींशिवाय. tokenmaxxing सक्रिय खात्याचा नमुना statusline पुशवरून घेते आणि नेमके हे टाळण्यासाठी फक्त पार्क केलेल्या खात्यांना प्रोब करते.

**पार्श्वभूमी claude सत्रे.**
Claude चा पार्श्वभूमी डिमन खरी आवृत्तीबद्ध बायनरी निरपेक्ष मार्गाने स्पॉन करतो, PATH शिम्स टाळत, त्यामुळे पार्श्वभूमी सत्रे पर्यवेक्षित नसतात. हुक्स अजूनही `settings.json` द्वारे फायर होतात, आणि क्रेडेन्शियल स्वीकार तसेच नियतकालिक टायमर बदल व्यापतात, पण त्यांच्यासाठी कोणताही मार्कर-आधारित respawn नाही.

**एकदा काहीतरी बऱ्याच प्रक्रिया स्पॉन झाल्या. ते अजूनही शक्य आहे का?**
पर्यवेक्षक नेमके त्या ऐतिहासिक अपयशाविरुद्ध (जुना रॅपर "खरा" claude म्हणून पिन केलेला) स्तरित पुनरावृत्ती संरक्षक बाळगतो: पर्यावरणातील एक खोली सेंटिनेल जो ५ स्तरांवर रद्द करतो, एक ऑन-डिस्क स्पॉन-दर मर्यादक, realpath ओळख तपासण्या ज्या tokenmaxxing च्या स्वतःच्या bin डिरेक्टरीत परत सुटणाऱ्या कोणत्याही उमेदवाराला नाकारतात, आणि कॉन्फिगर केलेला claude मार्ग यापुढे अस्तित्वात नसताना एक कठोर अपयश (कधीही गप्प PATH स्कॅन नाही). `init` आणि `doctor` एखादा उमेदवार पिन करण्याआधी `--version` चालवून तो प्रत्यक्षात claude आहे याची पडताळणी करतात.

**अनइन्स्टॉल करणे.**
`tokenmaxxing uninstall` पर्यवेक्षक शिम्स, सेटिंग्ज नोंदी आणि नियतकालिक टायमर काढते, आणि तुमची खाती व पार्क केलेली क्रेडेन्शियल्स अबाधित ठेवते. ते फक्त त्याची स्वतःची म्हणून ओळखणाऱ्या statusline नोंदीच काढते.
