tokenmaxxing አውቶማቲክ የ Claude Code መለያ መቀያየር የሚያከናውን CLI ነው። የእርስዎ የሆኑ በርካታ የደንበኝነት ምዝገባ (Pro/Max) መለያዎችን ያሰባስባል እና በስራ ላይ ያለው መለያ ወደ አጠቃቀም ገደብ ሲቃረብ ንቁ የሆነውን credential ወደ ትኩስ መለያ hot-swap ያደርጋል። `claude` ን ልክ ሁልጊዜ እንደሚያደርጉት በትክክል ያሄዳሉ፤ መቀያየሩ ደህንነቱ በተጠበቀ የ turn ወሰን ላይ ይከሰታል እና እየሄደ ያለው session በአዲሱ መለያ ላይ ተመሳሳዩን ውይይት ዳግም ሳይጀምር ይቀጥላል። በአንድ ጊዜ በበርካታ ተባባሪ sessionዎች ላይ ይሰራል።

ብቸኛው የሚታይ ባህሪ የከፋው ሁኔታ ነው፦ ሙሉ pool ገደቡ ላይ በሚሆንበት ጊዜ፣ session በ countdown ይቆም እና ዳግም በሚጀምረው ቀጣይ መለያ ላይ በራስ-ሰር ይቀጥላል (Ctrl-C ወዲያውኑ ይቀጥላል)።

## ችግሩ

የ Claude ደንበኝነት ምዝገባ በአንድ ጊዜ ሦስት ገደቦችን ይለካል (ሁሉም በ `/usage` የተረጋገጡ)፦

- **አሁን ያለው session**፦ ተንከባላይ የ5-ሰዓት መስኮት።
- **አሁን ያለው ሳምንት (ሁሉም ሞዴሎች)**፦ የ7-ቀን ጥቅል።
- **አሁን ያለው ሳምንት፣ በሞዴል**፦ ለተናጠል ሞዴል ቤተሰቦች የተለያዩ ሳምንታዊ ገደቦች። እነዚህ በአሁኑ ጊዜ ለ Sonnet እና Fable ብቻ የሚገኙ ናቸው፣ እና ጠቃሚ የሚሆነው የ Fable ገደብ ብቻ ነው - ከጥቅሉ ቀድሞ በጣም ይይዛል። አንድ ማሽን በ week-Fable ላይ 80% ላይ እያለ በ week-all ላይ 50% ላይ ሊሆን ይችላል።

ሳምንታዊ ኮታ ተጠቀም-ወይም-አጣ ነው፦ አንድ መለያ በተወሰነው ሳምንታዊ ዳግም ማስጀመሪያው ያልተጠቀመው ማንኛውም ነገር ይወረሳል። በርካታ መለያዎች ካሉዎት፣ ምክንያታዊው ስልት ከራሱ ሳምንታዊ ፍጥነት ወደኋላ በጣም በቀረው መለያ ላይ ኮታ ማቃጠሉን መቀጠል፣ እና ማንኛውም አንድ ገደብ በ session መካከል ግድግዳውን ከመምታቱ በፊት መቀየር ነው።

ይህን በእጅ ማድረግ ማለት መውጣት፣ መግባት እና ውይይትዎን ማጣት ማለት ነው። tokenmaxxing ያንን በራስ-ሰር ያደርገዋል፦ እየሄደ ያለ `claude` በ request መካከል የ credential store ውን እንደገና ይፈትሻል፣ ስለዚህ ከሱ ስር የተቀየረ credential በቦታው ይወሰዳል (በ macOS ላይ በ30 ሰከንድ ገደማ ውስጥ፣ በ Linux ላይ በሚቀጥለው request)። ተራ መቀያየር session ዎን በጭራሽ ዳግም አያስጀምርም። አሁንም process አስተዳደር የሚያስፈልገው ብቸኛው ሁኔታ ሙሉ በሙሉ የተሟጠጠ pool ነው - session ራሱን ማቆም አይችልም - እና ቀጭኑ supervisor የሚኖረው ለዚህ ነው።

ስለ `claude` ሌላው ሁሉ ነገር አልተለወጠም፦ ሁሉም flagዎች፣ MCP serverዎች፣ hookዎች እና skillዎች ያልፋሉ።

## ፈጣን ጅምር

[Bun](https://bun.sh) እና Claude Code ን ይፈልጋል፣ በ macOS ወይም Linux ላይ።

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` አምስት ነገሮችን ያደርጋል፦

1. አስቀድመው የገቡበትን መለያ እንደ መለያ #1 ያስገባል (የተለየ `adopt` command የለም)።
2. የ `claude` supervisor shim ን ይጭናል።
3. በ Claude Code `settings.json` ውስጥ ሦስት ግቤቶችን ይጭናል፦ statusLine፣ Stop hook፣ እና SessionStart hook (በተጨማሪም subagentStatusLine ግቤት)።
4. የ supervisor ን bin directory ወደ shell rc ዎ PATH ላይ ያክላል (idempotent፣ በ `# tokenmaxxing PATH` አስተያየት ምልክት የተደረገበት)። ትክክለኛውን `claude` ለመጥለፍ በ PATH ላይ ከሱ ፊት መቀመጥ አለበት።
5. በየ180 ሰከንዱ `tokenmaxxing check` ን የሚያሄድ ወቅታዊ የፍተሻ timer (በ macOS ላይ launchd agent፣ በ Linux ላይ systemd user timer) ይጭናል።

shell ዎን ዳግም ያስጀምሩ፣ ከዚያ ተጨማሪ መለያዎችን ይጨምሩ እና ይቀጥሉ፦

```sh
tokenmaxxing add        # አንድ ተጨማሪ መለያ በተናጠል ያስገባል እና ያሰባስበዋል
claude                  # claude ን እንደ ሁልጊዜው ይጠቀሙ
```

`tokenmaxxing` እንደ `xx` ተለዋጭ ስም አለው። ባዶ `tokenmaxxing` (ወይም `xx`) `status` ን ያሄዳል፤ `switch` ግልጽ ሆኖ ይቆያል።

## Commandዎች

| Command | ምን እንደሚያደርግ |
|---|---|
| `tokenmaxxing init` | አሁን ያለውን መለያ ያስገባል፣ supervisor፣ hookዎች እና statusline ን ይጭናል |
| `tokenmaxxing init --codex` | ለ Codex ተመሳሳይ፦ login ን ያስገባል፣ codex supervisor እና Stop hook ን ይጭናል |
| `tokenmaxxing add` | ተጨማሪ መለያ ይመዘግባል (የተነጠለ login፣ ወደ pool የተሰበሰበ) |
| `tokenmaxxing add --codex` | ተጨማሪ የ Codex መለያ ይመዘግባል (የተነጠለ login) |
| `tokenmaxxing auth [sel \| --all]` | የተሰበሰበ መለያን በቦታው እንደገና ያረጋግጣል። ባዶ pool ን ዘርዝሮ የትኛውን እንደሆነ ይጠይቃል፤ selector አንድ መለያ ላይ ያነጣጥራል እና በየትኛው email መግባት እንዳለብዎ ይነግርዎታል፤ `--all` reauth-የሚያስፈልገውን እያንዳንዱን መለያ አንድ በአንድ ያልፋል |
| `tokenmaxxing switch [sel]` | ወደ ምርጡ መለያ ይቀይራል (greedy፣ idempotent) ወይም የተወሰነን በግድ ያደርጋል |
| `tokenmaxxing switch --codex [sel]` | የ Codex pool ን ይቀይራል (በሚቀጥለው codex ጅምር ላይ ተግባራዊ ይሆናል) |
| `tokenmaxxing ls` | የተሰበሰቡ መለያዎችን ይዘረዝራል |
| `tokenmaxxing status` | መለያዎችን ከ5ሰ / ሳምንታዊ / በሞዴል የአጠቃቀም barዎች ጋር፣ ንቁ እና እስከ-ዳግም-ማስጀመሪያ-የተሟጠጠ |
| `tokenmaxxing status --force` | በተጨማሪም እያንዳንዱን መለያ ping ያደርጋል (ለእያንዳንዱ አንድ ትንሽ haiku request) ሁሉም የ5ሰ session timerዎች አሁን እንዲጀምሩ፣ ከዚያ በአዲስ ናሙና ይወስዳል |
| `tokenmaxxing watch [seconds]` | ቀጥታ status፣ በየ N ሰከንዱ እንደገና የሚቀርብ (ነባሪ 120፣ ዝቅተኛ 30፤ በጭራሽ ping አያደርግም) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | ተግባራዊ config ከምንጮች ጋር፤ በነጥብ የተለዩ keyዎችን ያርትዑ፤ `tidy` የማይታወቁ keyዎችን ያስወግዳል |
| `tokenmaxxing check` | የመቀያየር ውሳኔን አንድ ጊዜ ይገመግማል (ወቅታዊው timer የሚያሄደው ይህ ነው) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | የ Slack bridge daemon (Socket Mode፣ ይፋዊ URL የለም) |
| `tokenmaxxing doctor` | supervisor እና የ settings ግቤቶች መቆየታቸውን ያረጋግጣል |
| `tokenmaxxing rename [--codex] <sel> <label>` | የተሰበሰበ መለያን እንደገና ይሰይማል |
| `tokenmaxxing rm <sel>` | መለያን ከ pool ያስወግዳል |
| `tokenmaxxing uninstall` | supervisor እና የ settings ግቤቶችን ያስወግዳል (መለያዎች እና credentialዎች ይቀመጣሉ) |

## Architecture

tokenmaxxing በዚያ ስም ሲጠራ እንደ `claude` supervisor የሚሰራ፣ hook እና statusline shimዎችን በውስጣዊ subcommandዎች የሚያገለግል፣ አለበለዚያ ደግሞ CLI ን የሚያከፋፍል አንድ ባለ-ብዙ-ጥሪ መግቢያ ነጥብ (`src/main.ts`) ነው። በቀጥታ በ Bun ስር ይሄዳል፤ የ npm ጥቅሉ የ TypeScript ምንጭ ኮድ እንጂ build አይልክም።

የሚንቀሳቀሱ ክፍሎች፦

### የ supervisor shim

`init` `claude` የተሰኘ ባለ2-መስመር shell shim ወደ `~/.config/tokenmaxxing/bin/` ይጽፋል እና ያንን directory በ PATH ላይ አንደኛ ያደርገዋል። `claude` ብለው ሲተይቡ፣ shim ው supervisor ን ያሄዳል፣ እሱም ትክክለኛውን claude binary በተወረሰ stdio እና በተቀመጠ `stty -g` የterminal snapshot ያስነሳል። እሱ የ process እና terminal አስተዳዳሪ ብቻ ነው፦ የ API ትራፊክን በጭራሽ proxy አያደርግም እና በበረራ ላይ ያሉ tokenዎችን በጭራሽ አይነካም።

Print-mode ጥሪዎች (`claude -p`፣ `--version`፣ `--help`)፣ interactive-ያልሆኑ subcommandዎች (`claude mcp`፣ `claude config`፣ ወዘተ)፣ እና የ tokenmaxxing የራሱ probeዎች ያለ session አስተዳደር በቀጥታ ያልፋሉ። ለ interactive session፣ supervisor ው session id ይይዛል (አዲስ በማመንጨት፣ ወይም በ `--session-id` / `-r` / `-c` ያስተላለፉትን እንደገና በመጠቀም)፣ የ launch flagዎችዎን ያስቀምጣል ስለዚህ በኋላ ዳግም ማስጀመር እነሱን መልሶ ማጫወት ይችላል፣ ከዚያም ለዚያ session የተያዘ የ respawn marker ፋይል ይጠብቃል።

### የ statusline tee

Claude Code በእያንዳንዱ turn የ rate-limit ውሂብ (`rate_limits.five_hour` እና `rate_limits.seven_day`) ወደ statusline ው stdin ይገፋል። tokenmaxxing የ statusline ቦታውን ስለሚይዝ፣ renderer ው እንደ ነጻ፣ በ push-ላይ የተመሰረተ የአጠቃቀም feed ሆኖ ያገለግላል፦ በእያንዳንዱ tick ጥቅል መስኮቶቹን ከንቁ ሞዴሉ ጋር ወደ `usage.json` ይtee ያደርጋል። በሞዴል ገደቦች በ statusline stdin ውስጥ የሉም፤ የሚመጡት ከ `claude -p '/usage'` ብቻ ነው (ነጻ፣ ዜሮ tokenዎች)፣ እሱም በ TTL የሚጠየቅ እና ንቁ ሞዴሉ በአቅም ሲገደብ ወደ `model-usage.json` cache የሚደረግ።

tee ው በለውጥ-ላይ-ይጽፋል፦ ቁጥሮች ሳይለወጡ ሲቀሩ የፋይሉን mtime ብቻ ያስተካክላል፣ ይህም እንደ feed ው የህያውነት heartbeat ሆኖ ይሰራል። ትኩስነት ሁልጊዜ በ mtime ይፈረዳል እንጂ በተካተተው timestamp በጭራሽ አይደለም።

### የ Stop hook እና መቀያየሩ

በእያንዳንዱ turn ወሰን፣ Stop hook ው የመቀያየር ውሳኔን ያሄዳል ([መቀያየር እንዴት እንደሚወስን](#how-switching-decides) ይመልከቱ)። መቀያየር ሲያስፈልግ፣ በ `flock(2)` ብቸኛ lock ስር ይከሰታል (macOS የ `flock(1)` binary ስለማይልክ በ `bun:ffi` የተወሰደ)፣ እና የ credential ጽሁፎች በተጨማሪም ከ Claude Code የራሱ refresh lock ጋር ይተሳሰራሉ። በወሳኙ ክፍል ውስጥ፣ አንድ መቀያየር፦

1. አሁን ያለውን ቀጥታ credential ወደ ትክክለኛ ባለቤቱ የተያዘ backup ይሰበስባል።
2. የታለመውን መለያ አዲስ የተታደሰ credential እንደ ቀጥታ ይጭናል፣ ወደ ነባሩ ቀጥታ blob በማዋሃድ ስለዚህ ተጓዳኝ ሁኔታ (እንደ በ-MCP-server OAuth tokenዎች ያሉ) ይተርፋል።
3. የታለመውን የተሽከረከረ token ወደ ራሱ backup ያስቀምጣል።
4. በ `~/.claude.json` ውስጥ ያለውን `oauthAccount` field በ atomic መንገድ እንደገና ይጽፋል።
5. አዲሱን ንቁ label ያረጋግጣል እና ያረጁ የአጠቃቀም snapshotዎችን ያጸዳል፣ ሁሉም lock ከመለቀቁ በፊት፣ ስለዚህ crash በጭራሽ የተጫነውን credential እና ንቁ label ን የተለያዩ መለያዎችን እያመለከቱ አይተውም።

ሁሉም default-profile sessionዎች አንዱን ቀጥታ credential ስለሚጋሩ፣ አንድ መቀያየር እያንዳንዱን session በአንድ ጊዜ ያዛውራል፣ እና flock ው በተጨማሪም lock ስር እንደገና-ማረጋገጥ የሚሽቀዳደሙ hookዎች ሁለት መለያዎችን ከማቃጠል ይከለክላል።

### በቦታው መቀበል

እየሄደ ያለ claude session በ request መካከል የ credential store ውን ይጠይቃል፦ በ macOS ላይ keychain ን በአጭር cache እንደገና ያነባል እና access tokenዎችን ያነጻጽራል፤ በ Linux ላይ የ credentials ፋይሉን mtime ይመረምራል እና በለውጥ ላይ token cacheዎቹን ያጸዳል። የመጨረሻው ውጤት የተቀየረ credential በ macOS ላይ በ30 ሰከንድ ገደማ ውስጥ እና በ Linux ላይ በሚቀጥለው request በእያንዳንዱ እየሄደ ባለ session፣ ያለ ምንም ዳግም ማስጀመር ይወሰዳል። ተራ መቀያየር ምንም marker የማይጽፍ እና ምንም respawn የማያስነሳ ለዚህ ነው - session በአዲሱ መለያ ላይ ብቻ ይቀጥላል። በ session ውስጥ ያለ `/usage` ተመሳሳይ token cacheዎችን ስለሚጋራ፣ የመለያ ማሳያው ከመቀበል ጋር አብሮ ይገለበጣል።

### የተሟጠጠ-pool ጥበቃ እና በራስ-ሰር መቀጠል

በ pool ውስጥ ያለ እያንዳንዱ መለያ ከ barዎቹ በላይ ሲሆን ብቻ Stop hook ው respawn marker ይጽፋል (marker schema ው `waitUntil` timestamp ይፈልጋል፤ ተራ መቀያየር በጭራሽ ማምረት አይችልም)። supervisor ው marker ውን ያያል፣ child ውን አስቀድሞ-በተረጋገጠው turn ወሰን ላይ SIGTERM ያደርገዋል (Stop hook ው transcript ው disk ላይ ከሆነ እና claude idle ከሆነ በኋላ ስለሚሄድ፣ ምንም አይጠፋም)፣ terminal ን ይመልሳል፣ ወደ ቀጣዩ ዳግም ማስጀመሪያ countdown ያሳያል፣ ከዚያም `claude --resume <session-id>` ን በተመለሰው መለያ ላይ እንደገና ያስነሳል። በ countdown ጊዜ Ctrl-C ወዲያውኑ ይቀጥላል። በራስ-ሰር ጥበቃ በ `policy.maxWaitMs` የተገደበ ነው (ነባሪ 1 ሰዓት)፤ ከዚያ ባሻገር ውሳኔው ከመጠበቅ ይልቅ pool ን እንደተሟጠጠ ያሳውቃል።

### ወቅታዊው የፍተሻ timer

Hookዎች የሚቀሰቀሱት በ turn ወሰኖች ላይ ብቻ ነው፣ እና አንድ ረጅም agentic turn መስኮትን ያለ አንድ ወሰን ከጤናማ ወደ የተሟጠጠ ማቃጠል ይችላል። ስለዚህ `init` በተጨማሪም ወቅታዊ timer ይጭናል - በ macOS ላይ launchd agent፣ በ Linux ላይ systemd user timer - እሱም ከ turn እንቅስቃሴ ውጭ በየ180 ሰከንዱ `tokenmaxxing check` ን ያሄዳል።

### SessionStart hook

session ሲጀምር ወይም ሲቀጥል ተመሳሳዩን ግምገማ ያሄዳል፣ ስለዚህ አዲስ session በትክክለኛው መለያ ላይ ይጀምራል። post-swap cooldown ው ከ respawn በኋላ ወዲያውኑ ትክክለኛ no-op ያደርገዋል።

## መቀያየር እንዴት እንደሚወስን [#how-switching-decides]

ውሳኔው ሁለት ንብርብሮች አሉት፦ የ engagement gate፣ ከዚያም greedy ወይም hard path።

### Engagement

ከ `policy.greedySessionFloor` በታች (ነባሪ 50፣ በ5-ሰዓት session መስኮት መቶኛ)፣ ውሳኔው በጭራሽ አይሄድም - አዲስ session መለያውን ይጋልባል። ንቁ የሆነው session መስኮት 50% ጥቅም ላይ ከዋለ በኋላ፣ ወይም ማንኛውም hard bar ከተሻገረ፣ ውሳኔው ይሳተፋል።

### Screening barዎች

threshold ዎቹ screening barዎች ናቸው እንጂ ለድንጋጤ ቀስቃሽ አይደሉም፦

- `thresholds.session`፦ 95። የ5-ሰዓት ዳግም ማስጀመሪያ ዝም ብሎ ለመቀመጥ ርካሽ ነው፣ ስለዚህ session መስኮቱ ቀደም ብሎ ይቀየራል።
- `thresholds.weekly`፦ 98። ይህ አንድ bar የ7-ቀን ጥቅሉንም ሆነ እያንዳንዱን በ-ሞዴል ሳምንታዊ ገደብ ይሸፍናል። ሳምንታዊ ኮታ ተጠቀም-ወይም-አጣ ነው፣ ስለዚህ ወደ ግድግዳው ቅርብ ይሟጠጣል።

ሁለቱም ሆን ተብለው ከ100 በታች ናቸው፦ ክፍተቱ መለያው በትክክል ገደቡን ከመምታቱ በፊት ንጹህ turn ወሰን ለመድረስ (በተጨማሪም በ macOS ላይ እስከ አንድ turn የመቀበል መዘግየት) የሚያገለግል በጀት ነው። ተመሳሳዮቹ barዎች የመቀያየር እጩዎችን ይመረምራሉ፦ ከ barዎቹ ማንኛውም በላይ የሆነ መለያ ትክክለኛ ኢላማ አይደለም። Trigger እና screening ሁልጊዜ ተመሳሳይ ተግባራዊ barዎችን ይጠቀማሉ (threshold ሲቀነስ `policy.projectionMargin`)፣ ምክንያቱም ከ trigger ይልቅ የላላ screen trigger ወዲያውኑ እንደገና-የሚሰይማቸው መለያዎች ላይ መቀያየሮችን ስለሚያሳርፍ pool ን ወደ ping-pong ይለውጣል።

### ኢላማው፦ pace pressure

ጥቅም ላይ ሊውሉ ከሚችሉ መለያዎች መካከል፣ ኢላማው ከራሱ ሳምንታዊ ፍጥነት ወደኋላ በጣም የቀረው ነው፦ ከፍተኛ **pace pressure**፣ እንደ ቀሪ ሳምንታዊ መቶኛ ተከፍሎ ለዚያ መለያ ሳምንታዊ ዳግም ማስጀመሪያ እስከሚደርስ ባለው ጊዜ የሚገለጽ። ሊወረስ የሚቃረብ በጣም ብዙ ኮታ ያለው መለያ ያሸንፋል። እኩልነቶች ወደ ቀጣዩ ሳምንታዊ ማብቂያ ይሰበራሉ፣ ከዚያ ወደ ዝቅተኛ የ7-ቀን አጠቃቀም።

ሁሉም ነገር እንደ ፍጹም UTC epoch የተከማቹ cache-የተደረጉ መስኮቶች ላይ ይሄዳል፣ ስለዚህ ያረጀ snapshot አሁንም በትክክል ይፈታል፦ ያለፈ ሳምንታዊ ዳግም ማስጀመሪያ በትክክለኛ የ7-ቀን ደረጃዎች ወደፊት ይራዘማል፣ እና ከ cache-የተደረገ ዳግም ማስጀመሪያው ያለፈ ማንኛውም መስኮት እንደ አዲስ ባዶ ይቆጠራል (ለመቀየር ምክንያት በጭራሽ አይደለም፣ መለያን ማቆየት ለ bench ምክንያት በጭራሽ አይደለም)።

### Greedy በተቃራኒ hard path

- **Greedy path** (የተሳተፈ፣ ግን ከ bar ሁሉ በታች)፦ አሁን ያለውን ጨምሮ እያንዳንዱን መለያ ደረጃ ይስጥ። አሁን ያለው መለያ አስቀድሞ ካሸነፈ ወይም እኩል ከሆነ፣ ምንም አታድርግ። አለበለዚያ ወደ በጥብቅ የተሻለ መለያ ተቀየር። በጭራሽ አይጠብቅም እና በጭራሽ አስቀድሞ አያቆምም - ጥቅም ላይ ሊውል የሚችል አሁን ያለ መለያ ለጥበቃ አይለወጥም። አሁን ያለው መለያም ደረጃ ስለሚሰጠው፣ ሁለቱም automatic path እና ባዶ `tokenmaxxing switch` idempotent ናቸው፦ ወቅታዊ መገምገም በትክክለኛው መለያ ላይ ይሰበሰብ እና ከዚያ ይቆያል።
- **Hard path** (bar የተሻገረ)፦ ወደ ምርጡ ጥቅም ላይ ሊውል የሚችል እጩ ተቀየር። የአንድ እጩ refresh token የሞተ ከሆነ፣ needs-reauth ተብሎ ምልክት ይደረግበታል እና ቀጣዩ እጩ ይሞከራል። ምንም ጥቅም ላይ ሊውል የሚችል ከሌለ፣ depleted-wait logic ይሄዳል፤ session ን በትክክል ማቆም የሚችል ጠሪ (የተቆጣጠረው Stop hook) ብቻ ወደ አሁንም-የታገደ ግን ቀድሞ-የሚያገግም መለያ አስቀድሞ እንዲያቆም ይፈቀድለታል።

### በ-ሞዴል ገደቦች

`policy.switchModels` (ነባሪ `["fable"]`) በ-ሞዴል ሳምንታዊ ገደባቸው መቀያየር ሊያስነሳ የሚችል የሞዴል ቤተሰቦችን ይሰይማል። ተዛማጅነት በ family token ነው እንጂ በትክክለኛ display string በጭራሽ አይደለም፦ የሞዴል display ስሞች ይለዋወጣሉ ("Fable" "Fable 5" ሆነ)፣ እና የትክክለኛ-string gate በአንድ ወቅት በ-ሞዴል መቀያየርን በጸጥታ ሙሉ በሙሉ አሰናከለ። ሁለት ተዛማጅ የደህንነት ደንቦች፦

- ያልታወቀ ንቁ ሞዴል የተዋቀረውን እያንዳንዱን ቤተሰብ ይገድባል። መቀያየር snapshotዎችን ካጸዳ በኋላ ወዲያውኑ፣ headless ማሽን model-blind ሆኖ ሊሄድ ይችላል፤ ያልታወቀን እንደ ያልተገደበ መቁጠር በአንድ ወቅት አንድ መለያ በ Fable ገደቡ ላይ ሳይስተዋል ለሰዓታት እንዲቀመጥ አድርጎታል።
- የእጩ screening የተገደቡ በ-ሞዴል ገደቦችንም ይቆጥራል፣ ስለዚህ እያንዳንዱ መለያ የ Fable ገደቡን ያቃጠለበት pool round-robin አያደርግም።

### Cooldown

የ45-ሰከንድ post-swap cooldown automatic path ን ይገድባል። statusline tee ው ከመቀያየር በኋላ ለተመሳሳይ 45 ሰከንድ ይታፈናል (መቀበል በ macOS ላይ እስከ 30 ሰከንድ ይወስዳል)፣ ስለዚህ ቀደም ያለ ግምገማ መቀያየሩ ራሱ ባበላሸው ውሂብ ላይ ይሄዳል - ያ ትክክለኛ ሁኔታ በአንድ ወቅት A-ወደ-B-እና-ተመልሶ የ respawn loop አመንጭቷል። በእጅ የሚደረግ `tokenmaxxing switch` በ cooldown አይነካም።

## ውቅር

Config በ `~/.config/tokenmaxxing/config.json` JSON ነው። እያንዳንዱ field አማራጭ ነው፤ ነባሪዎች በ-field ይተገበራሉ።

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`፦ ከላይ የተገለጹት screening barዎች።
- `policy.projectionMargin`፦ ተግባራዊ barዎችን ለመፍጠር ከሁለቱም barዎች ይቀነሳል።
- `policy.greedySessionFloor`፦ greedy convergence የሚሳተፍበት session-የተጠቀመ መቶኛ።
- `policy.switchModels`፦ በ-ሞዴል ሳምንታዊ ገደባቸው መቀያየርን የሚገድብ የሞዴል ቤተሰቦች (ግቤቶች በ load ጊዜ ወደ ትንንሽ ፊደላት ይቀየራሉ)።
- `policy.usagePollTtlMs`፦ የ `/usage` በ-ሞዴል poll ምን ያህል ጊዜ ትኩስ ሆኖ እንደሚቆይ።
- `policy.maxWaitMs`፦ የተሟጠጠ-pool በራስ-ሰር ጥበቃ ገደብ።

`tokenmaxxing config` ተግባራዊ config ን ከምንጮች ጋር ያሳያል፤ `config set`/`unset` በነጥብ የተለዩ keyዎችን ያርትዑ፤ `config tidy` የማይታወቁ keyዎችን ያስወግዳል።

## የ State directory አቀማመጥ

ሁሉም ነገር በ `~/.config/tokenmaxxing/` ስር ይኖራል (በ `TOKENMAXXING_HOME` ሊሻር የሚችል፤ በውጭ ሊታይ የሚችል እያንዳንዱ path የ env override አለው ስለዚህ ሙሉ መሳሪያው በ testዎች ውስጥ hermetic ሆኖ ሊሄድ ይችላል)።

| Path | ምን እንደሚይዝ |
|---|---|
| `config.json` | የእርስዎ ውቅር (sparse፤ ነባሪዎች በ-field ይተገበራሉ) |
| `accounts.json` | የተሰበሰቡ Claude መለያዎች ሚስጥር-ያልሆነ index፦ labelዎች፣ idዎች፣ cache-የተደረጉ የአጠቃቀም መስኮቶች። በጭራሽ tokenዎች አይደሉም |
| `usage.json` | የ statusline tee ው ጥቅል መስኮት snapshot፤ mtime ው የ feed ው የህያውነት heartbeat ነው |
| `model-usage.json` | ከ `/usage` የ TTL-cache የተደረጉ በ-ሞዴል ሳምንታዊ ገደቦች |
| `lastswap.json` | የመጨረሻው መቀያየር epoch timestamp፤ የ45-ሰከንድ cooldown ን ይነዳል |
| `lock` | መቀያየሮችን serialize የሚያደርግ የ `flock` ፋይል |
| `tokenmaxxing.log` | Append-only የ event log |
| `bin/` | የ PATH shimዎች፦ `claude`፣ `codex`፣ እና የ `tokenmaxxing` / `xx` entry pointዎች |
| `respawn/<session-id>` | supervisor ው የሚከታተላቸው የተሟጠጠ-ጥበቃ respawn markerዎች |
| `creds/` | ለ Linux ብቻ፦ የተያዙ credential ፋይሎች፣ በ 0700 directory ውስጥ 0600 (macOS credentialዎችን በ-መለያ keychain ንጥሎች አድርጎ ይይዛል) |
| `onboard/`, `sample/` | ለ `add`/`auth` loginዎች እና የተያዙ-መለያ `/usage` probeዎች የሚጣሉ የተነጠሉ config homeዎች፤ plaintext credentialዎችን የያዙ onboard homeዎች ከመሰብሰብ በኋላ ይሰረዛሉ |
| `slack.json` | የ `xx serve` tokenዎች እና channel linkዎች (0600) |
| `slack-threads/` | ለ `xx serve` በ-thread session መዝገቦች |
| `codex-*` | ትይዩ የ Codex pool፦ `codex-accounts.json`፣ `codex-lastswap.json`፣ `codex-lock`፣ `codex-creds/`፣ `codex-onboard/`፣ `codex-respawn/`፣ እና `codex-live/` (በእያንዳንዱ የሚሄድ የተቆጣጠረ codex session አንድ በ PID-የተረጋገጠ presence ፋይል፣ ስለዚህ ቀጥታ መለያ በጭራሽ የመቀያየር ኢላማ አይሆንም) |

ከራሱ directory ውጭ፣ tokenmaxxing በትክክል የሚነካቸው፦ `~/.claude.json` (የ `oauthAccount` መቀያየር)፣ የ Claude Code `settings.json` (የ hook እና statusline ግቤቶች)፣ ቀጥታው credential store (በ macOS ላይ የ `Claude Code-credentials` keychain ንጥል፣ በ Linux ላይ `.credentials.json`)፣ `~/.claude.lock` (የ claude refresh lock፣ በመቀያየር ጊዜ የተወሰደ)፣ የ codex `auth.json` እና `hooks.json`፣ እና በ launchd ወይም systemd ውስጥ ያለው ወቅታዊ-ፍተሻ unit ናቸው።

## Credential ማከማቻ እና የደህንነት ሞዴል

ሁሉም state በ `~/.config/tokenmaxxing/` ውስጥ ይኖራል። Credential I/O በአንድ በ platform-የተመረጠ store facade ውስጥ ያልፋል፤ የጥሪ ቦታዎች በ platform ላይ በጭራሽ አይከፋፈሉም።

**macOS**፦ credentialዎች በ login keychain ውስጥ እንደ generic-password ንጥሎች ይኖራሉ፣ Claude Code ራሱ ከሚያስቀምጥበት ጋር የሚዛመድ። ቀጥታው ንጥል claude የሚያነበው ነው፤ የእያንዳንዱ የተሰበሰበ መለያ backup እንደ ራሱ `tokenmaxxing-cred-<uuid8>` keychain ንጥል ይያዛል። በ disk ላይ ምንም plaintext የለም። ንባቦች `security find-generic-password -w` ን ይጠቀማሉ (ምስጢሩ በ stdout ላይ ብቻ ይታያል)፤ ጽሁፎች `add-generic-password` መስመርን በ stdin በኩል ወደ `security -i` ያስተላልፋሉ ስለዚህ ምስጢሩ በማንኛውም process argv ላይ በጭራሽ አይታይም። interactive mode ው ወደ 4 KB የሚጠጋ line buffer አለው፣ ስለዚህ ከመጠን በላይ የሆኑ blobዎች ወደ argv ጽሁፍ ይመለሳሉ - የተያዙ ንጥሎች አነስተኛውን OAuth ነገር ብቻ የሚያከማቹበት አንድ ምክንያት።

**Linux**፦ Claude Code credentialዎችን እንደ 0600 plaintext ፋይል ያከማቻል፣ እና tokenmaxxing ተመሳሳዩን ሞዴል ይከተላል፦ ቀጥታው ፋይል የ claude የራሱ `.credentials.json` ነው፣ እና የተያዙ backupዎች በ 0700 directory ውስጥ በ `~/.config/tokenmaxxing/creds/` ስር atomic 0600 ፋይሎች ናቸው። እዚህ atomic ማለት ወደ-temp-መጻፍ፣ fsync፣ ከዚያ rename ማለት ነው፦ ተባባሪ አንባቢ ሁልጊዜ ሙሉ አሮጌ ወይም ሙሉ አዲስ ፋይል ያያል እንጂ በጭራሽ ከፊል አይደለም።

መቀያየር የሚያስፈጽማቸው የደህንነት ደንቦች፦

- **በትክክለኛ ባለቤት መሰብሰብ።** ከመቀያየር በፊት፣ የቀጥታው credential ትክክለኛ ባለቤት token የትኛው ድርጅት እንደሆነ API ን በመጠየቅ ይፈታል (`fetchTokenOrg` በ OAuth roles endpoint ላይ) - ሊለዋወጥ የሚችለውን የተከማቸ ንቁ label በማመን በጭራሽ አይደለም። የተለዋወጠ label በአንድ ወቅት የአንድ መለያ መሰብሰብ የሌላ መለያ ብቸኛ backup እንዲደፈጥጥ አድርጓል። ቀጥታው credential ከ pool ውጭ ላለ መለያ ከሆነ፣ መቀያየሩ ከመድፍጠጥ ይልቅ ፍጹም እምቢ ይላል።
- **አንድ ወሳኝ ክፍል።** መሰብሰቡ፣ የአዲሱ credential መጫን፣ የተሽከረከረ token ው backup፣ የ `~/.claude.json` መለያ መቀያየር፣ እና ንቁ-label commit ሁሉም በተመሳሳይ የተቆለፈ ክፍል ውስጥ ይከሰታሉ።
- **ከ claude የራሱ refresh ጋር መተሳሰር።** ማብቂያ-የተቃረበ session በማንኛውም ጊዜ የራሱን token ማሽከርከር ይችላል፣ ስለዚህ የ credential ጽሁፎች የ Claude Code refresh lock ንም ይወስዳሉ (best-effort፣ ከ stale-lock መልሶ ማግኘት እና ከተገደበ timeout ጋር)።
- **የሞቱ grantዎች በንጽህና ይቀንሳሉ።** `invalid_grant` ተመልሶ የመጣ refresh ያንን መለያ needs-reauth ብሎ ምልክት ያደርገዋል እና ስህተቱ ከመሰራጨቱ በፊት flag ን ያስቀምጣል፣ ስለዚህ retry loopዎች የእጩ ስብስቡን ያሳንሱ እና ያቆማሉ። `tokenmaxxing auth` ምልክት የተደረገበትን መለያ በቦታው ያስተካክላል፣ እና ከሚጠገነው የተለየ መለያ ላይ የሚያርፍ login ን እምቢ ይላል።
- **token አለመመዝገብ።** tokenዎች በ logዎች፣ ስህተቶች ወይም output ውስጥ በጭራሽ አይታዩም። ከ token እና usage endpointዎች የስህተት አካላት በጭራሽ ጥሬ አይቀርቡም፤ የተፈቀደ የ fieldዎች ስብስብ ብቻ ይተርፋል፣ ምክንያቱም የ token endpoint የውድቀት አካል የ request ንጥረ ነገርን ሊያስተጋባ ስለሚችል።
- **የ probe ንጽህና።** ማንኛውም የተነሳ `claude` probe claude keychain lookup ከማድረጉ በፊት የሚያከብራቸውን ስምንት environment variableዎችን ያጸዳል (`ANTHROPIC_API_KEY`፣ `CLAUDE_CODE_OAUTH_TOKEN`፣ `CLAUDE_SECURESTORAGE_CONFIG_DIR`፣ ወዘተ)፣ ስለዚህ probe በጭራሽ ለተሳሳተ መለያ ሊሰጥ አይችልም።

## የ Platform ማስታወሻዎች፦ macOS በተቃራኒ Linux

| | macOS | Linux |
|---|---|---|
| ቀጥታ credential | Login keychain generic-password ንጥል | 0600 `.credentials.json` ፋይል |
| የተያዙ credentialዎች | በ-መለያ keychain ንጥሎች | 0600 ፋይሎች በ 0700 directory ውስጥ |
| ከመቀያየር በኋላ መቀበል | በ~30 ሰከንድ ውስጥ (keychain read cache) | ቀጣይ request (file mtime poll) |
| ወቅታዊ ፍተሻ | launchd agent፣ በየ180ሰ | systemd user timer፣ በየ180ሰ |
| የተነጠለ-login store | በ config dir ውስጥ Hash-namespaced keychain service | በተነጠለ config dir ውስጥ ያለ ፋይል |

ማወቅ የሚገባቸው ሁለት ለ Linux-የተለዩ ዝርዝሮች፦ claude የ credential directory ውን መጀመሪያ ከ `CLAUDE_SECURESTORAGE_CONFIG_DIR` ይፈታል (ከዚያ `CLAUDE_CONFIG_DIR`፣ ከዚያ `~/.claude`)፣ እና tokenmaxxing ያንን አፈታት በትክክል ስለሚያንጸባርቅ ሁለቱ በጭራሽ አይለያዩም። እና የተመሳሳዩ claude ስሪት ሁለቱ የ OS buildዎች የ `/usage` ዳግም ማስጀመሪያ ሰዓቶችን በተለየ ሁኔታ ይቀርጻሉ (አንዱ " at " ማጣበቂያ ይጠቀማል፣ ሌላው ኮማ)፤ የ tokenmaxxing parser በትክክል እነዚያን ሁለት ቅርጾች ይቀበላል እና በማንኛውም ሦስተኛ ላይ ከመገመት ይልቅ ይመዘግባል።

በ macOS ላይ፣ አንድ ግልጽ ገደብ፦ `init` እና `add` ሆን ብለው keychain ን በ interactive ይነካሉ፣ ስለዚህ የመጀመሪያው `security` መዳረሻ በ headless hook ውስጥ ቀዝቃዛ አይሆንም።

## statusline ው

tokenmaxxing የ Claude Code statusline ን በnative ያቀርባል (የአጠቃቀም feed ን tee እያደረገ)። የ design መርህ፦ ኮታ በቀለም ይሸከማል እንጂ በቁጥሮች አይደለም። አንድ መስመር፣ ለምሳሌ፦

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- እያንዳንዱ window token የራሱ time-to-reset ነው፣ በተጠቀመ መቶኛ በተከታታይ አረንጓዴ-ወደ-ቢጫ-ወደ-ቀይ ramp ላይ የተቀባ (terminal ሲደግፈው truecolor፣ አለበለዚያ ወደ 256-color cube የተደረገ)። ramp ው ለ0 በንጹህ አረንጓዴ፣ በ75 ቢጫ፣ እና በ95 እና ከዚያ በላይ ቀይ ላይ ይያዛል፣ ስለዚህ የቆዩ የ severity ባንዶች እንደ ramp anchor ይተርፋሉ።
- የሞዴል ስሙ በተመሳሳይ ramp ላይ በ context-window fill ይቀባል።
- አረንጓዴ `◆` የንቁ መለያውን መስኮቶች ይመራል፤ እያንዳንዱ የተያዘ መለያ የራሱ cyan `◇` ያገኛል (reauth ካስፈለገው ቀይ `✗`)። መለያዎች በቀደመው ቀጣይ ዳግም ማስጀመሪያ ይደረደራሉ።
- በ-ሞዴል በእያንዳንዱ ብሎክ ውስጥ እንደ ባዶ የተቀባ የመጀመሪያ ፊደል መጀመሪያ ይመጣል፦ Fable `𝒇` ያቀርባል፤ ሌሎች ቤተሰቦች የከፍተኛ-ፊደል የመጀመሪያ ፊደላቸውን ይጠቀማሉ፣ ሁልጊዜ በ family-የተዛመደ።
- ያልተነካ የተያዘ መለያ አረንጓዴ `full` ያቀርባል። ካልታወቀ ዳግም ማስጀመሪያ ጋር የተለካ አጠቃቀም የተቀባ `?` ያቀርባል፣ እና በ gated ሞዴል ላይ ያልተለካ በ-ሞዴል ገደብ ያልተቀባ `𝒇?` ያቀርባል - ያልተለካ በጭራሽ ደህና መምሰል የለበትም።
- የዳግም ማስጀመሪያ countdownዎች ትልቁን አሃድ ብቻ ያሳያሉ፣ በጭራሽ "now" ወይም "0m" አይደለም፤ ቀጣይ ዳግም ማስጀመሪያ የሌለው መስኮት አረንጓዴ `0` ያቀርባል (እንደገና ባዶ)።
- የተገናኘ git worktree basename መስመሩን ይመራል፤ main checkout እዚያ ምንም አያቀርብም። ማወቁ filesystem ን ለ `.git` ፋይል ያነባል እና በጭራሽ git subprocess አያስነሳም።
- `NO_COLOR` ሲዋቀር፣ መስመሩ ወደ የተጣበቀ ቁጥራዊ ቅርጸት ይመለሳል (`2h5` ማለት በ2 ሰዓት ውስጥ ዳግም ይጀምራል፣ 5% ጥቅም ላይ ውሏል፤ `ctx 42` ለ context fill) - ያለ ቀለም፣ የተሟጠጠ መስኮት ትኩስ መምሰል የለበትም።

Subagent taskዎች በ claude subagentStatusLine surface በኩል የራሳቸውን panel rowዎች ያገኛሉ፦ በ ንቁ task አንድ row፣ የ family ስም በዚያ task context fill የተቀባ።

## Codex ድጋፍ

ተመሳሳዩ ማሰባሰብ ለ OpenAI Codex CLI ይሰራል፣ በራስዎ የ ChatGPT-ደንበኝነት ምዝገባ መለያዎች ላይ፦

```sh
tokenmaxxing init --codex   # አሁን ያለውን codex login ያስገቡ + codex supervisor እና Stop hook ን ይጫኑ
tokenmaxxing add --codex    # ሌላ መለያ ይግቡ፣ የተነጠለ - ዋና login ዎ አይነካም
codex                       # codex ን እንደ ሁልጊዜው ይጠቀሙ
```

የ Codex pool ሙሉ በሙሉ ትይዩ state ነው፦ የራሱ accounts index፣ የራሱ የተያዙ credential ፋይሎች (በሁለቱም platformዎች ላይ 0600 ፋይሎች፣ የ codex የራሱ store plaintext ፋይል ስለሆነ)፣ የራሱ lock፣ የራሱ last-swap timestamp። ከ decision-policy ኮድ በስተቀር ከ Claude pool ጋር ምንም አይጋራም።

### በ Codex ላይ hot-swap ለምን የማይቻል እንደሆነ

እየሄደ ያለ codex process አንድ in-memory auth manager ይይዛል እና አሁን የተለየ መለያ ሲሰይም `auth.json` ን እንደገና መጫን በግልጽ እምቢ ይላል። ምንም file watcher እና ምንም በ-request credential poll የለም፣ ስለዚህ እየሄደ ካለ codex ስር የተቀየረ credential ለ inference በቀላሉ በጭራሽ ተግባራዊ አይሆንም። ዳግም ማስጀመር መቀያየሩ ነው፦ `codex resume <session-id>` local transcript ን `auth.json` አሁን በያዘው ማንኛውም መለያ ላይ ይቀጥላል።

tokenmaxxing ይህን በ codex supervisor shim ይይዘዋል፦ Stop hook ው ተመሳሳዩን greedy pace-pressure ውሳኔ በእያንዳንዱ turn ወሰን ላይ ያሄዳል፣ እና ሲቀይር፣ supervisor ው session ን በተረጋገጠው ወሰን ላይ SIGTERM እንዲያደርግ እና `codex resume <session-id>` ን በአዲሱ መለያ ላይ transcript ሳይበላሽ እንደገና እንዲያስነሳ የሚያደርግ marker ይጽፋል። እያንዳንዱ codex መቀያየር የሚታይ ዳግም ማስጀመር ስለሆነ፣ የ codex greedy path 1.2x የማሻሻያ margin ይይዛል፦ ተፎካካሪ የአሁኑን መለያ pace pressure በ20% ማሸነፍ አለበት እንጂ በጭራሽ በጥቂት አይደለም። hard path (የተሻገረ bar) margin ን ችላ ይላል። ለ codex የተሟጠጠ-pool countdown የለም - ምንም codex session ማቆም አይችልም - ስለዚህ ሙሉ በሙሉ የተሟጠጠ codex pool ይቆያል።

ሌሎች ለ codex-የተለዩ ስልቶች፦

- አጠቃቀም በ codex የራሱ rate-limit endpoint ላይ ከነጻ የተረጋገጠ GET ይነበባል (CLI `/status` የሚያደርገው ተመሳሳይ ጥሪ)፦ መቶኛዎች በተጨማሪም ፍጹም epoch የዳግም ማስጀመሪያ ጊዜያት፣ ጥቅል መስኮቶች እና በ-ሞዴል ገደቦች እኩል። የመስኮት ምደባ duration-driven ነው እንጂ position-driven በጭራሽ አይደለም፣ ምክንያቱም የአሁኑ planዎች ምንም የ5-ሰዓት መስኮት ላይኖራቸው ስለሚችል እና ሳምንታዊው መስኮት በ primary slot ውስጥ ስለሚቀመጥ።
- የ Codex refresh tokenዎች ይሽከረከራሉ፣ እና የተተካውን እንደገና መጠቀም ሙሉ grant family ን ይገድላል። እያንዳንዱ ማሽከርከር ወዲያውኑ ሲመለስ ይቀመጣል፣ ንቁ መለያው በቀጥታ blob በኩል ብቻ ናሙና ይወሰዳል (በጭራሽ ያረጀ የተያዘ ቅጂ አይደለም)፣ እና በ-session presence ፋይሎች በ live sibling session ውስጥ የሚሄድ መለያ በጭራሽ የመቀያየር ኢላማ እንዳይሆን እና የተያዘ token ው በጭራሽ እንዳይታደስ ያረጋግጣሉ።
- Codex የ file credential store ን ይፈልጋል፦ keyring store ከተያዘ `init --codex` በፍጥነት ይወድቃል፣ እና `add --codex` login harvestable ሆኖ እንዲያርፍ የ file-mode ቅንብርን ወደ ተነጠለው onboarding home ይጽፋል።
- አንድ በእጅ የሚደረግ ደረጃ፦ codex እንዲያምናቸው ያልተነገሩትን hookዎች ይዘላል። ከ `init --codex` በኋላ፣ codex ን አንድ ጊዜ ይክፈቱ እና የ tokenmaxxing Stop hook ን በ `/hooks` በኩል ያመኑ፣ አለበለዚያ auto-switching በጸጥታ ስራ ፈት ሆኖ ይቆያል። `init --codex` ይህን ማስታወሻ ያትማል።

## Slack bridge ው፦ xx serve

`tokenmaxxing serve` local Slack daemon ን በ Socket Mode ያሄዳል - ይፋዊ URL አያስፈልግም። ማዋቀር፦

```sh
tokenmaxxing serve setup                    # የ app manifest ን ያትማል፣ ለሁለቱ tokenዎች ይጠይቃል
tokenmaxxing serve link <channel-id> <repo> # channel ን ከ repo checkout ጋር ያስተሳስራል
tokenmaxxing serve                          # daemon ን ያሄዳል
```

bot ን በተገናኘ channel ውስጥ ይጥቀሱ እና ለዚያ thread በተገናኘ repo checkout ውስጥ Claude Code session ይከፍታል። እያንዳንዱ የ thread መልእክት አንድ Agent SDK `query()` ን ከ `resume` ጋር ያሄዳል - በጭራሽ ቋሚ streaming query አይደለም - ስለዚህ `ensureBestAccount()` pool ን በእያንዳንዱ turn እንደገና ይገመግማል እና daemon ው threadዎችን ሳያጣ ዳግም ማስጀመር ይችላል (የ thread መዝገቦች ዘላቂ ናቸው፤ daemon ው በ startup ላይ እንደገና ይመዘግባቸዋል)።

ትኩረት የሚሹ ባህሪያት፦

- **Streaming**፦ ምላሾች በnative ወደ Slack ይተላለፋሉ፣ ለ thinking እና tool runዎች የ task cardዎች ጋር፣ fenced code በ highlighting የቀረበ፣ ከ cost እና duration ጋር የመዝጊያ "Turn" card፣ እና tool run የተላለፈ ጽሁፍን በሚያቋርጥበት ጊዜ ሁሉ የተከፈተ አዲስ Slack መልእክት፣ ስለዚህ turn በ tool runዎች ዙሪያ እንደ የተለያዩ መልእክቶች ይነበባል። TodoWrite ጥሪዎች አንድ የተረጋጋ checklist card ን በቦታው ያዘምናሉ።
- **Permissions**፦ በ-link `permissionMode` ነባሪው `acceptEdits` ነው፤ `--yolo` (ተለዋጭ ስም `--dangerous`) link ን ወደ `bypassPermissions` ያስገባል። Interactive dialogዎች በተላለፉ turnዎች ውስጥ አይፈቀዱም - ማንም በ Slack በኩል መመለስ አይችልም - ስለዚህ ሞዴሉ በ prose ይጠይቃል እና የ thread ምላሽዎ ቀጣዩ turn ነው። የተጣመረ plugin skill ውሳኔ ሲፈልግ ጠያቂውን እንዲጠቅስ እና turn ን እንዲያጠናቅቅ ያስተምረዋል።
- **Slash commandዎች**፦ የተከረከመ ጽሁፉ በ `/` የሚጀምር የ thread መልእክት እንደ claude slash command ይሄዳል። የ Slack composer በ `/` የሚጀምሩ መልእክቶችን ይበላል፣ ስለዚህ mention-first ቅጹን (`@bot /usage`) ወይም መጀመሪያ ላይ ክፍተት ይጠቀሙ።
- **Graceful shutdown**፦ SIGTERM/SIGINT ያፈሳል - አዲስ turnዎች በጩኸት ይጣላሉ፣ በበረራ ላይ ያሉ turnዎች እስከ 5 ደቂቃ ያገኛሉ፣ እና claude child በራሱ process group ውስጥ ተነጥሎ ይሄዳል ስለዚህ terminal Ctrl-C drain ው turn ን ከመጠበቁ በፊት ሊገድለው አይችልም።
- **Thread cleanup**፦ ስራው መጠናቀቁን ሲነግሩት፣ ሞዴሉ in-process `finish_thread` tool ን ይጠራል፤ turn ሙሉ በሙሉ ካበቃ በኋላ፣ daemon ው የ thread መዝገቡን ይጥላል፣ ይሰርዛል፣ እና አንድ ማረጋገጫ ይለጥፋል። አዲስ mention አዲስ session ይጀምራል።
- **Error hygiene**፦ የ turn ስህተቶች የተከረከመ መልእክት-ብቻ ጽሁፍ ይለጥፋሉ፣ በጭራሽ ጥሬ የስህተት አካላት አይደሉም።

## Agent SDK surface ው

የጥቅሉ programmatic entry (`exports["."]` ወደ `src/sdk.ts` ያመለክታል) በራስዎ የተሰበሰቡ መለያዎች ላይ ለሚገነቧቸው agentዎች tokenmaxxing ን ከ Claude Agent SDK ጋር ያጣምራል። መተግበሪያዎ በ Bun ስር መሄድ አለበት (tokenmaxxing የ TypeScript ምንጭ ኮድ ይልካል እና `bun:ffi` ን ይጠቀማል)።

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

Agent SDK በ `query()` አንድ claude subprocess ያስነሳል እና credentialዎችን በ spawn አንድ ጊዜ ያነባል - ምንም statusline የለም፣ ምንም mid-query hot-swap የለም - ስለዚህ ውህደቱ boundary-driven ነው፦

- `ensureBestAccount()` CLI hookዎች እና timer የሚያሄዱት ትክክለኛው ውሳኔ ነው (barዎች፣ pace pressure፣ cooldown፣ ሁሉም የተጋራ ኮድ)፣ በጭራሽ anticipatory አይደለም፦ SDK session በጭራሽ ለተሟጠጠ countdown ሊቆም አይችልም።
- `pooledOptions()` `pathToClaudeCodeExecutable` ን ወደ ትክክለኛው claude binary ይይዛል (በጭራሽ supervisor wrapper አይደለም) እና እያንዳንዱ ambient credential override የተጸዳ ሙሉ ምትክ `env` ያቀርባል። በመተግበሪያዎ environment ውስጥ `CLAUDE_CONFIG_DIR` ወይም `CLAUDE_SECURESTORAGE_CONFIG_DIR` ከተዋቀረ በፍጥነት ይወድቃል፦ በ Linux ላይ መቀያየር ቀጥታውን credential እነዚያ ወደሚያመለክቱበት ይጽፋል የተጸዳው subprocess ደግሞ ነባሪውን store ያነባል፣ የጸጥታ የተሳሳተ-መለያ desync።
- `stopHookCheck` ውሳኔውን በ turn ወሰኖች ላይ እንደገና ያሄዳል፤ የሚያሳርፈው መቀያየር በሚቀጥለው spawn ላይ ተግባራዊ ይሆናል። ከመድገም ይልቅ የራሱን ስህተቶች ይይዛል (ወደ stderr እና log በመመዝገብ)፣ ምክንያቱም ያልተያዘ hook exception agent ን ሊያቋርጥ ስለሚችል፣ እና በተሰበረ switch check ላይ turn ን ማቋረጥ አሁን ያለውን መለያ ከመቀጠል የበለጠ ዋጋ ስለሚያስከፍል።

`sdk.ts` ከ Agent SDK ራሱ ምንም አያስገባም፤ እሴቶቹ በ structural ወደ SDK options ይሰራጫሉ።

## Build እና ስርጭት

የ npm ጥቅሉ የ TypeScript ምንጭ ኮድ ይልካል እንጂ build አይደለም፦ የ `tokenmaxxing` bin በ Bun shebang በቀጥታ ወደ `src/main.ts` ያመለክታል፣ እና Bun 1.2.6 ወይም ከዚያ በኋላ እንዳለ ያሄደዋል። Bun ጠንካራ መስፈርት የሆነው ለዚህ ነው። በ design ምንም compiled binaryዎች የሉም፦ አንድ ቀደምት release አንድ ነጠላ 61 MB የ macOS binary ወደ እያንዳንዱ platform ልኮ በ Linux ላይ በ `exec format error` ወደቀ፣ እና በ-platform compiled ጥቅሎች እያንዳንዳቸው የራሳቸው release pipeline ያስፈልጋቸዋል፣ ስለዚህ በ-Bun-የሚሄድ-ምንጭ የስርጭት ሞዴል ሆነ።

የጥቅሉ `exports` map ከላይ የተገለጸውን programmatic entry `src/sdk.ts` ን ያጋልጣል። Releaseዎች በ GitHub ላይ `v<version>` ተብለው ይሰየማሉ፤ CI በ trusted publishing (OIDC፣ ከ provenance ጋር) ወደ npm ያትማል፣ እና የ publish gate መጀመሪያ typecheck ን እና ሙሉ test suite ን ያሄዳል።

## የግል አጠቃቀም እና የአገልግሎት ውሎች [#personal-use-and-terms-of-service]

tokenmaxxing የራስዎ የሆኑ መለያዎችን፣ በራስዎ በሚያሄዷቸው sessionዎች እና agentዎች ውስጥ ያሰባስባል። ያ አገላለጽ ሆን ተብሎ ነው፦ Anthropic third-party ምርቶች የ claude.ai login ወይም claude.ai rate limits እንዲያቀርቡ አይፈቅድም፣ እና ያም በ Agent SDK ላይ የተገነቡ agentዎችን ያካትታል። የተሰበሰበውን SDK surface ን ወይም በሱ ላይ የተገነባውን ማንኛውንም ነገር ለ third-party አይላኩ። tokenmaxxing እንዲሁ ለ quota ውሂብ OAuth ን ከመድገም ወይም የ API ትራፊክን ከ proxy ከማድረግ ይልቅ ሆን ብሎ በ CLI-አማካኝ `/usage` path ላይ ይቆያል፦ proxy አይደለም፣ እና የሚነካቸው ብቸኛ OAuth endpointዎች በመቀያየር ጊዜ የሚያገለግለው መደበኛ refresh grant እና token በትክክል የትኛው መለያ እንደሆነ የሚያረጋግጥ read-only identity check (roles endpoint) ናቸው።

## ችግር መፍታት እና FAQ

**`claude` የተቆጣጠረ አይመስልም።**
`tokenmaxxing doctor` ን ያሂዱ። shim ው የ PATH አፈታት ማሸነፍ አለበት፤ በ shell rc ዎ ውስጥ ያለው የ `# tokenmaxxing PATH` መስመር አሁን ያለውን bin directory እንደሚያመለክት እና ከትክክለኛው claude ፊት እንደሚቀመጥ ያረጋግጡ። `doctor` በተጨማሪም wrapper ን ስለሚሸፍኑ `alias claude=...` ወይም `claude()` shell function፣ እና claude binary ን በ absolute path ስለሚያስነሱ ተለዋጭ ስሞች (እነዚያ supervisor ን ሙሉ በሙሉ ያልፋሉ) ያስጠነቅቃል።

**Auto-switching በ Codex ላይ በጭራሽ አይቀሰቀስም።**
Codex እንዲያምናቸው ያልተነገሩትን hookዎች ይዘላል። codex ን ይክፈቱ፣ `/hooks` ን ያሂዱ፣ እና የ tokenmaxxing Stop hook ን ያመኑ። እምነት በ hook hash ላይ ይመዘገባል፣ ስለዚህ hook ከተስተካከለ እንደገና መሰጠት አለበት።

**አንድ መለያ በ statusline ውስጥ ቀይ `✗` ያሳያል።**
የ refresh token ው ሞቷል (የተሻረ ወይም ከ backup ው ስር የተሽከረከረ)። በቦታው እንደገና ለማረጋገጥ `tokenmaxxing auth <sel>` ን ያሂዱ፤ command ው በየትኛው email መግባት እንዳለብዎ ይነግርዎታል እና በተለየ መለያ ላይ የሚያርፍ login ን እምቢ ይላል።

**ለምን ወደ በጣም ብዙ ቀሪ ኮታ ወዳለው መለያ አይቀይርም?**
ምክንያቱም ያ ኮታ የማጣት አደጋ ላይ በጣም ያለው መለያ አይደለም። ኢላማው ከራሱ ሳምንታዊ ፍጥነት ወደኋላ በጣም የቀረው መለያ ነው፦ ቀሪ መቶኛ ተከፍሎ ለሳምንታዊ ዳግም ማስጀመሪያው ባለው ጊዜ። እኩል መጠን በሚቀርበት ጊዜ ወደ ቀጣይ ማብቂያ በመጀመሪያ ይቀንሳል፣ እና በእኩል ማብቂያ ወደ በጣም ብዙ ቀሪ በመጀመሪያ።

**አሁን ተቀየረ እና statusline አሁንም አሮጌውን መለያ ያሳያል።**
በ macOS ላይ እስከ ~30 ሰከንድ ድረስ የሚጠበቅ ነው፦ እየሄደ ያለው session የተቀየረውን credential በሚቀጥለው credential-cache refresh ላይ ይቀበላል። የ usage tee ው ከመቀያየር በኋላ ለ45 ሰከንድ የሚታፈነው በትክክል ለዚህ ምክንያት ነው።

**`status --force` ማንኛውንም ወጪ አለው?**
አዎ፣ ሆን ተብሎ፦ ለእያንዳንዱ መለያ አንድ አነስተኛ የተለካ haiku request ይልካል ስለዚህ እያንዳንዱ የ5-ሰዓት session መስኮት ዝም ብሎ ከመተኛት ይልቅ በዚያ ቅጽበት ይጀምራል፣ ከዚያ በአዲስ ናሙና ይወስዳል። ተራ `status` እና `watch` በጭራሽ ping አያደርጉም፤ የ `/usage` ንባቦች ነጻ ናቸው። የ server usage feed አዲስ የተከፈተ መስኮትን በሰከንዶች እስከ ደቂቃዎች ሊያዘገይ እንደሚችል ልብ ይበሉ፣ ስለዚህ ከ ping በኋላ ወዲያውኑ ያለ probe አሁንም pre-ping ሁኔታን ሊያሳይ ይችላል - `status` ping አልተሳካም ብሎ ከማስመሰል ይልቅ ማስታወሻ ያቀርባል።

**የ `/usage` probe ለንቁ መለያ ምንም አልመለሰም።**
ያ የታወቀ የ claude ባህሪ ነው፦ ውስጣዊ የ usage fetch ው ሲወድቅ ወይም rate-limited ሲሆን፣ `/usage` ያለ መቶኛ መስመሮች local session stats ብቻ ያትማል። tokenmaxxing ንቁ መለያውን ከ statusline push ናሙና ይወስዳል እና የተያዙ መለያዎችን ብቻ probe ያደርጋል፣ በትክክል ይህን ለማስወገድ።

**የ background claude sessionዎች።**
የ Claude background daemon ትክክለኛውን versioned binary በ absolute path ያስነሳል፣ የ PATH shimዎችን በማለፍ፣ ስለዚህ background sessionዎች ያልተቆጣጠሩ ናቸው። Hookዎች አሁንም በ `settings.json` በኩል ይቀሰቀሳሉ፣ እና credential መቀበል በተጨማሪም ወቅታዊ timer መቀያየርን ይሸፍናሉ፣ ግን ለእነሱ marker-driven respawn የለም።

**አንድ ነገር በአንድ ወቅት ብዙ processዎችን አስነስቷል። ያ አሁንም ይቻላል?**
supervisor ው በትክክል ያንን ታሪካዊ ውድቀት ላይ (እንደ "ትክክለኛ" claude የተያዘ ያረጀ wrapper) የተደራረቡ recursion ጠባቂዎችን ይይዛል፦ በ environment ውስጥ በ5 ደረጃ የሚያቋርጥ depth sentinel፣ on-disk spawn-rate limiter፣ ወደ tokenmaxxing የራሱ bin directory ተመልሶ የሚፈታ ማንኛውንም እጩ የሚክዱ realpath identity checkዎች፣ እና የተዋቀረ claude path ሲጠፋ hard failure (በጭራሽ የጸጥታ PATH scan አይደለም)። `init` እና `doctor` እጩ በእውነት claude መሆኑን ከመያዙ በፊት `--version` ን በማሄድ ያረጋግጣሉ።

**ማራገፍ።**
`tokenmaxxing uninstall` supervisor shimዎችን፣ የ settings ግቤቶችን እና ወቅታዊ timer ን ያስወግዳል፣ እና መለያዎችዎን እና የተያዙ credentialዎችን ሳይነካ ይተዋል። እንደ ራሱ የሚያውቃቸውን statusline ግቤቶች ብቻ ያስወግዳል።
