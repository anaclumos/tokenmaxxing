---
title: تخزين الـ credentials ونموذج الأمان
description: "الـ credentials بتتخزّن فين على كل منصة والقواعد اللي كل تبديل بيفرضها"
---

كل الحالة موجودة في `~/.config/tokenmaxxing/`. عمليات الإدخال والإخراج للـ credential بتعدّي عن طريق واجهة مخزن واحدة بتتحدّد حسب المنصة؛ مواقع الاستدعاء عمرها ما بتتفرّع حسب المنصة.

**macOS**: الـ credentials موجودة في الـ login keychain كعناصر generic-password، مطابقة للمكان اللي Claude Code نفسه بيحطها فيه. العنصر الحي هو اللي claude بيقراه؛ النسخة الاحتياطية بتاعت كل حساب في الـ pool بتتركن كعنصر keychain خاص بيها `tokenmaxxing-cred-<uuid8>`. مفيش حاجة نص عادي على الديسك. القراءات بتستخدم `security find-generic-password -w` (السر بيظهر بس على stdout)؛ الكتابات بتمرّر سطر `add-generic-password` لـ `security -i` عن طريق stdin عشان السر عمره ما يظهر في argv بتاع أي عملية. الوضع التفاعلي عنده line buffer حوالي 4 KB، فالـ blobs الكبيرة بترجع لكتابة argv. ده سبب واحد إن العناصر المركونة بتخزّن بس كائن OAuth الأدنى.

**Linux**: Claude Code بيخزّن الـ credentials كملف نص عادي 0600، و tokenmaxxing بيمشي على نفس النموذج: الملف الحي هو `.credentials.json` بتاع claude نفسه، والنسخ الاحتياطية المركونة ملفات ذرّية 0600 تحت `~/.config/tokenmaxxing/creds/` في مجلد 0700. الذرّي هنا معناه اكتب لملف مؤقت، اعمل fsync، وبعدين rename: القارئ المتزامن بيشوف دايمًا ملف قديم كامل أو جديد كامل، عمره ما جزئي.

قواعد الأمان اللي التبديل بيفرضها:

- **الحصاد عن طريق المالك الحقيقي.** قبل التبديل، بيتم تحديد المالك الفعلي للـ credential الحي عن طريق سؤال الـ API الـ token ده تابع لأنهي منظمة (`fetchTokenOrg` على الـ OAuth roles endpoint)، عمره ما بالثقة في اللابل النشط المخزّن، اللي ممكن يتغيّر. لابل متغيّر مرة خلّى حصاد حساب يكتب فوق النسخة الاحتياطية الوحيدة بتاعت حساب تاني. لو الـ credential الحي تابع لحساب برّه الـ pool، التبديل بيرفض تمامًا بدل ما يدهس عليه.
- **قسم حرج واحد.** الحصاد، وتثبيت الـ credential الجديد، والنسخة الاحتياطية للـ token المُدوَّر بتاعه، وتبديل الحساب في `~/.claude.json`، وتثبيت اللابل النشط كلهم بيحصلوا جوّا نفس القسم المقفول.
- **التشابك مع تحديث claude نفسه.** الـ session اللي قربت تنتهي ممكن تدوّر الـ token بتاعها في أي لحظة، فكتابة الـ credential كمان بتاخد قفل التحديث بتاع Claude Code (على قد الإمكان، مع استرجاع للقفل القديم و timeout محدود).
- **المِنَح الميتة بتتدهور بنظافة.** التحديث اللي بيرجع `invalid_grant` بيعلّم على الحساب ده إنه محتاج إعادة مصادقة وبيحفظ العلامة قبل ما الخطأ ينتشر، فحلقات إعادة المحاولة بتصغّر مجموعة المرشحين وبتنتهي. `tokenmaxxing auth` بيصلّح الحساب المعلّم عليه في مكانه، وبيرفض تسجيل دخول بيوقع على حساب مختلف عن اللي بيتصلّح.
- **مفيش تسجيل للـ tokens.** الـ tokens عمرها ما بتظهر في اللوجات، أو الأخطاء، أو المخرجات. أجسام الأخطاء من endpoints الـ token والاستخدام عمرها ما بتتعرض خام؛ بس مجموعة حقول مسموح بيها هي اللي بتفضل، لأن جسم فشل token endpoint ممكن يردّد مادة الطلب.
- **نظافة الـ probe.** أي `claude` probe بيتطلّع بينضّف الـ 8 متغيرات بيئة اللي claude بيحترمها قبل بحثه في الـ keychain (`ANTHROPIC_API_KEY`، `CLAUDE_CODE_OAUTH_TOKEN`، `CLAUDE_SECURESTORAGE_CONFIG_DIR`، وهكذا)، عشان الـ probe عمره ما يتنسب للحساب الغلط.
