---
title: Status-only pools
description: grok and opencode-go accounts, pooled for inventory with no supervisor and no switching
---

Two more pools share the account commands, the state layout, and the `status` view with the Claude and Codex pools, and nothing else: no supervisor shim, no hooks, no statusline tee, no presence, no usage source, and no switching. They keep an inventory of accounts and the credential each one holds.

```sh
tokenmaxxing init --grok          # pool the first grok login (status-only)
tokenmaxxing add --grok           # pool another one through an isolated login
tokenmaxxing init --opencode-go   # pool the first opencode-go key (status-only)
tokenmaxxing add --opencode-go    # pool another key
```

`init`, `add`, `auth`, `rm`, and `rename` take `--grok` or `--opencode-go`; every other command refuses the flags with exit code 2, and the pool flags are mutually exclusive. `init` verifies the vendor CLI and pins its path (`grokBin` or `opencodeBin` in `config.json`; `TOKENMAXXING_GROK_BIN` and `TOKENMAXXING_OPENCODE_BIN` override it), then prints that the pool is status-only. `doctor`, `check`, and the periodic timer ignore both pools, and `uninstall` keeps their stores.

## grok

An account is a grok CLI login. `init --grok` imports the first entry of `~/.grok/auth.json` (`GROK_HOME` is honored) and points at `add --grok` for the rest; with no live login it runs `grok login` in a throwaway `GROK_HOME` under the state directory. `add --grok` and `auth --grok` always use the isolated login. Identity is the entry's user id, the label defaults to the email in the entry, and the harvested entry is written verbatim to `grok-stores/<uuid8>/auth.json` at mode 0600.

## opencode-go

An account is an opencode Zen API key for the `opencode-go` provider. `init --opencode-go` imports the key from opencode's auth file (`$XDG_DATA_HOME/opencode/auth.json`, `~/.local/share/opencode/auth.json` by default) when it holds an `opencode-go` entry of type `api`; otherwise, and for `add` and `auth`, it runs `opencode providers login -p opencode-go` in a throwaway data home and you paste the key from opencode.ai/zen when opencode asks. Identity is a hash of the key, so the account has no email and its tier reads `go`. The key is written to `opencode-go-stores/<uuid8>/auth.json` at mode 0600.

## What status shows

`status` renders the two pools after Claude and Codex, each headed `<pool>  (N accounts, status-only)` and skipped when empty. An account renders as `○ <label>` with no usage bars, because neither product exposes a quota signal. The live sample is a store check, not a network read: `status` prints `sampling grok usage...` on stderr, then reports `live sample failed` when the store no longer holds a credential that matches the account (run `auth` with the pool flag); `status --cached` skips the check and notes `never sampled`. `status --json` always carries both pools under `grok` and `opencodeGo`, with the same pool shape as the others: `usage`, `usageAt`, and `limitsAt` are `null`, `sessions` is 0, and `exhausted` is `false`.

## State

| Path | What it holds |
|---|---|
| `grok-accounts.json`, `opencode-go-accounts.json` | The pool indexes, the same schema as `accounts.json`; `activeId` is always `null` |
| `grok-lock`, `opencode-go-lock` | The `flock` files that serialize each pool's commands |
| `grok-stores/<uuid8>/auth.json`, `opencode-go-stores/<uuid8>/auth.json` | One 0600 store per account |
| `grok-onboard/`, `opencode-go-onboard/` | Throwaway login homes, wiped before and after each isolated login |
