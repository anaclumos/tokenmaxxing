---
title: Status-only pools
description: grok, Cursor, and Kimi Code accounts, pooled for inventory with no supervisor and no switching
---

The grok, Cursor, and Kimi Code pools share the account commands, the state layout, and the `status` view with the other pools, and nothing else: no supervisor shim, no hooks, no statusline tee, no session presence, and no switching. Each keeps an inventory of accounts and the credential each one holds; `status` reads each grok account's subscription credit window, each Cursor account's monthly included usage, and each Kimi Code account's 5-hour, weekly, and monthly limits.

```sh
tokenmaxxing init --grok          # pool the first grok login (status-only)
tokenmaxxing add --grok           # pool another one through an isolated login
tokenmaxxing init --cursor        # pool the Cursor CLI login (status-only)
tokenmaxxing add --cursor         # pool another one through an isolated login
tokenmaxxing init --kimi          # pool a Kimi Code account through an isolated login (status-only)
tokenmaxxing add --kimi           # pool another one the same way
```

`init`, `add`, `auth`, `emails`, `rm`, and `rename` take `--grok`, `--cursor`, or `--kimi`; every other command refuses the flags with exit code 2, and the pool flags are mutually exclusive. `init` verifies the vendor CLI and pins its path (`grokBin`, `cursorBin`, or `kimiBin` in `config.json`; `TOKENMAXXING_GROK_BIN`, `TOKENMAXXING_CURSOR_BIN`, and `TOKENMAXXING_KIMI_BIN` override them), then prints that the pool is status-only. `doctor`, `check`, and the periodic timer ignore these pools, and `uninstall` keeps their stores.

Muse Code was a status-only pool until it got a supervisor; see [Muse Code support](/muse).

## grok

An account is a grok CLI login. `init --grok` imports the first entry of `~/.grok/auth.json` (`GROK_HOME` is honored) and points at `add --grok` for the rest; with no live login it runs `grok login` in a throwaway `GROK_HOME` under the state directory. `add --grok` and `auth --grok` always use the isolated login. Identity is the entry's user id, the label defaults to the email in the entry, and the harvested entry is written verbatim to `grok-stores/<uuid8>/auth.json` at mode 0600.

Usage is the weekly subscription credit window from `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` (`creditUsagePercent`, classified by the period's duration). The endpoint leaves `creditUsagePercent` out while the period's use is 0, so a credits body without it reads as 0%. `TOKENMAXXING_GROK_USAGE_URL` overrides that URL for hermetic runs. The dollar billing body (`GET /v1/billing` without `format=credits`) is not quota: subscription accounts report `monthlyLimit` 0 there while credits remain, and a parser that treats that body as usage reports the account depleted. tokenmaxxing does not refresh grok tokens; a stored access token that has expired is retried against the live `GROK_HOME` login when that login is the same account. A failed read does not write the dollar body: an account with no stored window stays unmeasured, and one with a stored credits window keeps that figure as stale as it was.

## Cursor

An account is a Cursor CLI (`cursor-agent`) login. `init --cursor` imports `$XDG_CONFIG_HOME/cursor/auth.json` (`~/.config/cursor/auth.json` when `XDG_CONFIG_HOME` is unset) and points at `add --cursor` for more; with no live login it runs `cursor-agent login` with `XDG_CONFIG_HOME` set to a throwaway directory under the state directory, so the login lands in `cursor/auth.json` there. `add --cursor` and `auth --cursor` always use the isolated login. The file holds only tokens, so identity is the sha256 of the access token's `sub` claim; the email comes from the `authInfo` the CLI caches in `cli-config.json` beside `auth.json` when its `authId` matches that claim, else from the dashboard's `GetMe` when the login is harvested, and the label defaults to it. The file is written to `cursor-stores/<uuid8>/auth.json` at mode 0600. On macOS the Cursor CLI keeps its login in the keychain, which tokenmaxxing does not read, so the pool imports nothing there.

Usage is `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentPeriodUsage` with the store's `accessToken` as the bearer and an empty JSON body; it is the read behind the Cursor CLI's own usage notice, and it spends no quota. `TOKENMAXXING_CURSOR_API_URL` overrides the origin for hermetic runs. The unnamed window is `planUsage.totalPercentUsed` (the included usage that Auto draws on; `includedSpend` over `limit` when the field is absent), and the `API` window is `apiPercentUsed` (the included usage that a named model draws on); both span the billing cycle from `billingCycleStart` to `billingCycleEnd`. The plan, lowercased, comes from `GetPlanInfo`. tokenmaxxing does not refresh Cursor tokens: a 401 or 403 flags the account for `auth --cursor`. A failed read keeps the stored windows as stale as they were.

## Kimi Code

An account is a Kimi Code 2.x (`kimi`) login. Every Kimi account comes from an isolated login: `init --kimi`, `add --kimi`, and `auth --kimi` all run `kimi login` with `KIMI_CODE_HOME` set to a throwaway directory under the state directory, and `init --kimi` never imports the live login in `~/.kimi-code`. Kimi Code's access token lives 15 minutes and its refresh rotates the refresh token, so one grant in two homes would sign one of them out. The login passes `--region global` when the host's own Kimi Code login (in `KIMI_CODE_HOME`, else `~/.kimi-code`) signs in at `https://auth.kimi.ai`, because a bare `kimi login` in a fresh home signs in to the mainland-cn region. `init` requires `kimi --version` to report 2.0 or later, since the legacy kimi-cli also installs a `kimi`.

A store is a whole Kimi Code home, `kimi-stores/<uuid8>/`: the login's `config.toml`, the `credentials/<name>.json` that its `providers."managed:kimi-code".oauth.key` (`oauth/<name>`) names, and the `region` and `device_id` markers, each 0600, with `credentials/` at 0700. Identity is the sha256 of the access token's `user_id` claim. The email and the plan (the profile's `user_level_name`, lowercased) come from `GET <base_url>/me` when the login is harvested, and from every sample after it.

Usage runs Kimi Code's own local server on the store: `kimi web --no-open --port <free port>` with `KIMI_CODE_HOME` and the working directory set to the store, then `GET /api/v1/oauth/usage?provider=managed:kimi-code` and `GET /api/v1/oauth/userinfo` on `127.0.0.1` with the bearer the server writes to the store's `server.token`, then the server is stopped. The server refreshes the store's access token under Kimi Code's own lock before it asks Kimi's free usage endpoint (`GET <base_url>/usages`), so tokenmaxxing writes a store only at onboarding, and a read spends no quota. The server takes about a second to start. The windows follow Kimi Code's own `/usage` rows: `limit5h` is the 5-hour window, `limit7d` the weekly window that only legacy plans carry, and `monthTotal` the monthly limit, unnamed when there is no weekly window and named `month` beside one. A Kimi error that names a missing or rejected login (`re-login required`, `Run /login`), or a 401 or 403, flags the account for `auth --kimi`; any other failure keeps the stored windows as stale as they were.

## What status shows

`status` renders the pool after Claude and Codex, headed `grok  (N accounts, status-only)` and skipped when empty. A grok account renders the weekly credit bar from the credits billing read. The live sample is the credits GET (and a live-login retry when the stored access token is expired). `status` shows `sampling grok usage...` on a terminal while the check runs, erases it, then reports `live sample failed` when the read fails (run `auth --grok` when the store has no usable credential); `status --cached` skips the check and notes `never sampled` when nothing is stored. `status --json` always carries the pool under `grok`, with the same pool shape as the others. `usage` is the weekly credit window when a sample has landed. `sessions` is 0. `exhausted` follows the same bars as the other pools when the account has a stored window, and is `false` when the account is unmeasured.

The Cursor pool renders last, headed `cursor  (N accounts, status-only)` and skipped when empty, and `status --json` always carries it under `cursor`. Each account renders the billing-cycle bar, labeled `month`, and the `api` bar; `usage.week` carries the billing-cycle window (its `windowSeconds` is the cycle's length) and `usage.limits` the `API` window.

The Kimi Code pool renders after Cursor, headed `kimi  (N accounts, status-only)` and skipped when empty, and `status --json` always carries it under `kimi`. An account renders the `5h` bar and the monthly bar, labeled `month`, with a `week` bar between them on a legacy plan; `usage.fiveHour` carries the 5-hour window, `usage.week` the weekly window or else the monthly one, and `usage.limits` the `month` window when a weekly window takes `usage.week`.

## State

| Path | What it holds |
|---|---|
| `grok-accounts.json` | The pool index, the same schema as `accounts.json`; it names no active account |
| `grok-lock` | The `flock` file that serializes the pool's commands |
| `grok-stores/<uuid8>/auth.json` | One 0600 store per account |
| `cursor-accounts.json` | The Cursor pool index, the same schema |
| `cursor-lock` | The `flock` file of the Cursor pool |
| `cursor-stores/<uuid8>/auth.json` | One 0600 store per account |
| `kimi-accounts.json` | The Kimi Code pool index, the same schema |
| `kimi-lock` | The `flock` file of the Kimi Code pool |
| `kimi-stores/<uuid8>/` | One Kimi Code home per account: `config.toml`, `credentials/<name>.json`, `region`, and `device_id`, plus what Kimi Code's server writes there (`server.token`, its logs) |
| `onboard/grok-<pid>-<random>/`, `onboard/cursor-<pid>-<random>/`, `onboard/kimi-<pid>-<random>/` | The throwaway home of one isolated login (for Cursor, its `XDG_CONFIG_HOME`; for Kimi Code, its `KIMI_CODE_HOME`), deleted after it |
