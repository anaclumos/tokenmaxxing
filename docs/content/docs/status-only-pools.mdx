---
title: Status-only pools
description: Cursor, Kimi Code, Mistral Vibe, and Google Antigravity accounts, pooled for inventory with no supervisor and no switching
---

The Cursor, Kimi Code, Mistral Vibe, and Google Antigravity pools share the account commands, the state layout, and the `status` view with the other pools, and nothing else: no supervisor shim, no hooks, no statusline tee, no session presence, and no switching. Each keeps an inventory of accounts and the credential each one holds; `status` reads each Cursor account's monthly included usage, each Kimi Code account's 5-hour, weekly, and monthly limits, each Mistral Vibe account's monthly Vibe allowance, and each Antigravity account's 5-hour and weekly model quotas.

```sh
tokenmaxxing init --cursor        # pool the Cursor CLI login (status-only)
tokenmaxxing add --cursor         # pool another one through an isolated login
tokenmaxxing init --kimi          # pool a Kimi Code account through an isolated login (status-only)
tokenmaxxing add --kimi           # pool another one the same way
tokenmaxxing init --vibe          # pool the API key that vibe signs in with (status-only)
tokenmaxxing add --vibe           # pool another one through an isolated vibe --setup
tokenmaxxing init --agy           # pool the Google Antigravity login that agy uses (status-only)
tokenmaxxing add --agy            # pool another one through an isolated agy sign-in
```

`init`, `add`, `auth`, `emails`, `rm`, and `rename` take `--cursor`, `--kimi`, `--vibe`, or `--agy`; every other command refuses the flags with exit code 2, and the pool flags are mutually exclusive. `init` verifies the vendor CLI and pins its path (`cursorBin`, `kimiBin`, `vibeBin`, or `agyBin` in `config.json`; `TOKENMAXXING_CURSOR_BIN`, `TOKENMAXXING_KIMI_BIN`, `TOKENMAXXING_VIBE_BIN`, and `TOKENMAXXING_AGY_BIN` override them), then prints that the pool is status-only. `doctor`, `check`, and the periodic timer ignore these pools, and `uninstall` keeps their stores.

grok and Muse Code have supervisors and are not status-only pools; see [grok support](/grok) and [Muse Code support](/muse).

## Cursor

An account is a Cursor CLI (`cursor-agent`) login. `init --cursor` imports `$XDG_CONFIG_HOME/cursor/auth.json` (`~/.config/cursor/auth.json` when `XDG_CONFIG_HOME` is unset) and points at `add --cursor` for more; with no live login it runs `cursor-agent login` with `XDG_CONFIG_HOME` set to a throwaway directory under the state directory, so the login lands in `cursor/auth.json` there. `add --cursor` and `auth --cursor` always use the isolated login. The file holds only tokens, so identity is the sha256 of the access token's `sub` claim; the email comes from the `authInfo` the CLI caches in `cli-config.json` beside `auth.json` when its `authId` matches that claim, else from the dashboard's `GetMe` when the login is harvested, and the label defaults to it. The file is written to `cursor-stores/<uuid8>/auth.json` at mode 0600. On macOS the Cursor CLI keeps its login in the keychain, which tokenmaxxing does not read, so the pool imports nothing there.

Usage is `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentPeriodUsage` with the store's `accessToken` as the bearer and an empty JSON body; it is the read behind the Cursor CLI's own usage notice, and it spends no quota. `TOKENMAXXING_CURSOR_API_URL` overrides the origin for hermetic runs. The unnamed window is `planUsage.totalPercentUsed` (the included usage that Auto draws on; `includedSpend` over `limit` when the field is absent), and the `API` window is `apiPercentUsed` (the included usage that a named model draws on); both span the billing cycle from `billingCycleStart` to `billingCycleEnd`. The plan, lowercased, comes from `GetPlanInfo`. tokenmaxxing does not refresh Cursor tokens: a 401 or 403 flags the account for `auth --cursor`. A failed read keeps the stored windows as stale as they were.

## Kimi Code

An account is a Kimi Code 2.x (`kimi`) login. Every Kimi account comes from an isolated login: `init --kimi`, `add --kimi`, and `auth --kimi` all run `kimi login` with `KIMI_CODE_HOME` set to a throwaway directory under the state directory, and `init --kimi` never imports the live login in `~/.kimi-code`. Kimi Code's access token lives 15 minutes and its refresh rotates the refresh token, so one grant in two homes would sign one of them out. The login passes `--region global` when the host's own Kimi Code login (in `KIMI_CODE_HOME`, else `~/.kimi-code`) signs in at `https://auth.kimi.ai`, because a bare `kimi login` in a fresh home signs in to the mainland-cn region. `init` requires `kimi --version` to report 2.0 or later, since the separate kimi-cli also installs a `kimi`.

A store is a whole Kimi Code home, `kimi-stores/<uuid8>/`: the login's `config.toml`, the `credentials/<name>.json` that its `providers."managed:kimi-code".oauth.key` (`oauth/<name>`) names, and the `region` and `device_id` markers, each 0600, with `credentials/` at 0700. Identity is the sha256 of the access token's `user_id` claim. The email and the plan (the profile's `user_level_name`, lowercased) come from `GET <base_url>/me` when the login is harvested, and from every sample after it.

Usage runs Kimi Code's own local server on the store: `kimi web --no-open --port <free port>` with `KIMI_CODE_HOME` and the working directory set to the store, then `GET /api/v1/oauth/usage?provider=managed:kimi-code` and `GET /api/v1/oauth/userinfo` on `127.0.0.1` with the bearer the server writes to the store's `server.token`, then the server is stopped. The server refreshes the store's access token under Kimi Code's own lock before it asks Kimi's free usage endpoint (`GET <base_url>/usages`), so tokenmaxxing writes a store only at onboarding, and a read spends no quota. The server takes about a second to start. The windows follow Kimi Code's own `/usage` rows: `limit5h` is the 5-hour window, `limit7d` the weekly window that only legacy plans carry, and `monthTotal` the monthly limit, unnamed when there is no weekly window and named `month` beside one. A Kimi error that names a missing or rejected login (`re-login required`, `Run /login`), or a 401 or 403, flags the account for `auth --kimi`; any other failure keeps the stored windows as stale as they were.

## Mistral Vibe

An account is a Mistral API key that the Mistral Vibe CLI (`vibe`) signs in with. A key does not rotate, so a pooled copy and the live login keep working side by side. `init --vibe` imports the key that `vibe` reads: `MISTRAL_API_KEY` in `$VIBE_HOME/.env` (`~/.vibe/.env` when `VIBE_HOME` is unset), else, on macOS, the keychain item `ai.mistral.vibe` that `vibe` writes. With no live key it runs `vibe --setup` with `VIBE_HOME` set to a throwaway directory under the state directory, `VIBE_TEST_DISABLE_KEYRING=1`, and `MISTRAL_API_KEY` and `VIBE_CLI_OIDC_ENABLED` unset, so the setup saves the key to `.env` there instead of the global keychain item. `add --vibe` and `auth --vibe` always use the isolated setup. `init` requires `vibe --version` to report `vibe X.Y.Z`.

Identity is the sha256 of the Mistral user id and organization id from `GET https://api.mistral.ai/v1/users/me`, so a new key for the same user and organization updates its account, and the email comes from the same read. A key that Mistral refuses there pools nothing. The store is `vibe-stores/<uuid8>/auth.json` at mode 0600, holding the account id and the key.

Usage is `GET https://api.mistral.ai/v1/billing/budget` with the key as the bearer, the read behind `vibe`'s own usage footer, and it spends no quota. `TOKENMAXXING_VIBE_API_URL` overrides the origin for hermetic runs. The one window is `vibe_budget.usage_percentage` (0 to 100) of the plan's monthly Vibe allowance, resetting at `vibe_budget.reset_at`; an account whose `vibe_budget` is missing or has no `initial_budget` reports no allowance. The plan, lowercased, comes from `GET /v1/billing/subscription` (`plan_name`). A 401 flags the account for `auth --vibe`. A 403 means the key's member cannot read the organization's usage, so it fails the read without flagging. Any failed read keeps the stored window as stale as it was.

## Google Antigravity

An account is a Google Antigravity CLI (`agy`) OAuth login. `agy` keeps its credential in `antigravity-oauth-token` under `$AGY_HOME` (`~/.gemini/antigravity-cli` when unset) or, when the OS keyring is available, in the keychain item `gemini` / `antigravity`; tokenmaxxing imports the file and, on macOS when the file is absent, the keychain document. A copy in a pooled store does not sign the live login out. `init --agy`, `add --agy`, and `auth --agy` run `agy` with `HOME` set to a throwaway directory, `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR` cleared so OAuth lands in a file there, and `AGY_CLI_DISABLE_AUTO_UPDATE=1`. Identity is the sha256 of the Google `sub` from the login's `id_token`, scoped by `:gcp:<project_id>` for GCP project accounts; the email comes from `id_token_email` or the token's email claim. The store is `agy-stores/<uuid8>/antigravity-oauth-token` at mode 0600. `init` requires `agy --version` to report a semver.

Usage is the same read `agy /usage` uses: `POST https://daily-cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` and `POST .../v1internal:retrieveUserQuotaSummary` with the store's access token, the Antigravity CLI `User-Agent`, and a project id from the store, `TOKENMAXXING_AGY_PROJECT_ID`, `ANTIGRAVITY_PROJECT_ID`, `GEMINI_DEFAULT_PROJECT`, or `~/.gemini/antigravity-cli/cache/default_project_id.txt`, else `default-cli-project`. tokenmaxxing refreshes an expired access token with the stored refresh token, discovering the embedded OAuth client from the pinned `agy` binary or from `TOKENMAXXING_AGY_CLIENT_ID` / `TOKENMAXXING_AGY_CLIENT_SECRET` (and the `..._GCP_...` pair for GCP accounts). `TOKENMAXXING_AGY_API_URL` overrides the Code Assist origin for hermetic runs. The windows are the lowest remaining fraction across quota groups for the 5-hour and weekly buckets, shown as used percentages; the plan, lowercased, comes from `loadCodeAssist`. A 401 or 403, or a refresh failure, flags the account for `auth --agy`. Any other failed read keeps the stored windows as stale as they were.

## What status shows

The Cursor pool renders after Muse Code, headed `cursor  (N accounts, status-only)` and skipped when empty, and `status --json` always carries it under `cursor`. Each account renders the billing-cycle bar, labeled `month`, and the `api` bar; `usage.week` carries the billing-cycle window (its `windowSeconds` is the cycle's length) and `usage.limits` the `API` window.

The Kimi Code pool renders after Cursor, headed `kimi  (N accounts, status-only)` and skipped when empty, and `status --json` always carries it under `kimi`. An account renders the `5h` bar and the monthly bar, labeled `month`, with a `week` bar between them on a legacy plan; `usage.fiveHour` carries the 5-hour window, `usage.week` the weekly window or else the monthly one, and `usage.limits` the `month` window when a weekly window takes `usage.week`.

The Mistral Vibe pool renders after Kimi Code, headed `vibe  (N accounts, status-only)` and skipped when empty, and `status --json` always carries it under `vibe`. An account renders the monthly allowance bar, labeled `month`; `usage.week` carries that window.

The Antigravity pool renders after Vibe, headed `agy  (N accounts, status-only)` and skipped when empty, and `status --json` always carries it under `agy`. An account renders the 5h bar and, when both windows are present, a `week` bar; `usage.fiveHour` and `usage.week` carry those windows.

## State

| Path | What it holds |
|---|---|
| `cursor-accounts.json` | The Cursor pool index, the same schema as `accounts.json`; it names no active account |
| `cursor-lock` | The `flock` file of the Cursor pool |
| `cursor-stores/<uuid8>/auth.json` | One 0600 store per account |
| `kimi-accounts.json` | The Kimi Code pool index, the same schema |
| `kimi-lock` | The `flock` file of the Kimi Code pool |
| `kimi-stores/<uuid8>/` | One Kimi Code home per account: `config.toml`, `credentials/<name>.json`, `region`, and `device_id`, plus what Kimi Code's server writes there (`server.token`, its logs) |
| `vibe-accounts.json` | The Mistral Vibe pool index, the same schema |
| `vibe-lock` | The `flock` file of the Mistral Vibe pool |
| `vibe-stores/<uuid8>/auth.json` | One 0600 store per account: the account id and the API key |
| `agy-accounts.json` | The Antigravity pool index, the same schema |
| `agy-lock` | The `flock` file of the Antigravity pool |
| `agy-stores/<uuid8>/antigravity-oauth-token` | One 0600 store per account: the OAuth document agy uses |
| `onboard/cursor-<pid>-<random>/`, `onboard/kimi-<pid>-<random>/`, `onboard/vibe-<pid>-<random>/`, `onboard/agy-<pid>-<random>/` | The throwaway home of one isolated login (for Cursor, its `XDG_CONFIG_HOME`; for Kimi Code, its `KIMI_CODE_HOME`; for Mistral Vibe, its `VIBE_HOME`; for Antigravity, its `HOME`), deleted after it |
