---
title: 切换如何决策
description: "参与门槛、筛选阈值条、进度压力，以及贪心路径与硬路径"
---

决策分两层：先是参与门槛，然后走贪心路径或硬路径。

## 参与

在 `policy.greedySessionFloor`（默认 80，以 5 小时会话窗口的百分比计）之下，决策完全不运行，新会话继续跑在自己的账户上。一旦活动会话窗口用到 80%，或越过任一阈值条，决策就会参与进来。

## 筛选阈值条

这些阈值是筛选用的门槛条，而非触发恐慌的信号：

- `thresholds.session`：一道阶梯，默认 `[90]`，只有一档。每次评估都会解析出一个生效档位：池中仍有账户在其之下可用的最低一档，当前账户也算在内。若配置成 `[50, 80, 95]` 这样的多档阶梯，只要还有账户在 50 以下，阈值条就是 50，于是越过 50 的席位会把位置交给那个账户。等到每个账户都过了 50，阈值条爬到 80；到处都过了 80，就再爬到 95。最高的一档是终点阈值条，再往上就交给下文的上限墙。坐等一次 5 小时重置的成本很低，所以账户池会一层一层地往下耗，没有哪个账户会跑得远远超前于同伴。
- `thresholds.weekly`：98。这一条同时覆盖 7 天汇总额度和每个按模型的周上限。周配额是用不完就作废，所以会消耗到接近上限。

两者都刻意低于 100：留出这段余量，是为了在账户真正触及限额之前抵达干净的回合边界（在 macOS 上还要再加最多一个回合的采用延迟）。筛选切换候选账户用的是同一批阈值条：账户只要超过其中任一条，就不是有效目标。触发与筛选始终使用同一套有效阈值条（生效档位与周阈值条，各自减去 `policy.projectionMargin`）：筛选一旦比触发宽松，切换就会落到触发立刻会重新标记的账户上，让账户池来回抖动。一个档位只统计在这一档上仍然可用的账户：授权已死、受门槛限制的按模型上限已烧光、被服务端钉住的强制限额，都不会把阈值条压住不放；而且在一次评估内部，每次重试都会从账户池重新读取这一档。Codex 只读取最高的一档，因为对它来说重启就是切换。

## 目标：进度压力

在可用账户中，目标是最落后于自身周进度的那个：**进度压力**最高，即剩余周百分比除以该账户距离周重置的时间。即将作废最多配额的账户胜出。平手时先取周到期最早的，再取 7 天用量最低的。

一切都基于以绝对 UTC 纪元存储的缓存窗口运行，因此陈旧快照仍能正确解析：已经过去的周重置会以精确的 7 天步长向前外推，而任何超过其缓存重置的窗口都计为刚刚清空（既不构成切换的理由，也不构成把账户搁置的理由）。

## 贪心路径 vs 硬路径

- **贪心路径**（已参与，但未超过任何阈值条）：对每个账户排名，包括当前账户。当前账户若已胜出或平手，就什么都不做，否则切换到严格更优的账户。贪心路径从不等待，也从不预停放，不会拿可用的当前账户去换等待。因为当前账户也在排名之内，自动路径和裸执行 `tokenmaxxing switch` 都是幂等的：周期性评估会收敛到正确的账户，然后保持不动。
- **硬路径**（越过了某个阈值条）：切走到最佳可用候选账户。如果某个候选账户的刷新 token 已经失效，就将其标记为需重新认证，并尝试下一个候选。如果没有可用账户，就运行上限墙压榨（见下文），只有当每个可用账户都触及其上限墙时，才会运行耗尽等待逻辑；只有真正能暂停会话的调用方（受监督的 Stop hook）才可以预停放到仍被阻塞、但最快恢复的账户上。

## 上限墙

当硬路径找不到可用候选账户时，也就是每个账户都超过了它的筛选阈值条，自动决策并不会立刻停放。它会先对照**上限墙阈值条**（`hardThresholds`，默认 100，即每个账户真实的服务端限额）重新评估：只要会话仍在上限墙之下，就保住自己的席位并继续压榨，否则切换到仍处于上限墙之下的最佳账户（同样按进度压力排名），只有当每个可用账户都真正触及其上限墙时才停放。刷新 token 已失效的账户会被搁置以待重新认证，而不会去等待它。恢复是相对上限墙来衡量的，因此某个账户即使其周窗口仍高于筛选阈值条，只要其 5 小时窗口重置，就可以再次被压榨。

这样可以避免每个账户最后那几个百分点的配额被浪费掉。上限墙的读数来自决策本就在用的用量数据源，在受监督的交互式会话上是 statusline 分流，在无头运行上则是一次 `/usage` 探测，也就是 Claude 的 `/rate-limit-options` 所显示的同一批数字，因此真正用满的账户会被检测到并跳过。单个回合的超额会在决策下次运行时被捕获 - 可能是周期性检查，也可能是无头运行上的下一次 spawn 或 Stop 边界。

`hardThresholds` 会像筛选阈值条那样减去 `policy.projectionMargin`，因此把它设为与 `thresholds` 相等就会禁用上限墙压榨。这是一条仅限 Claude 的路径：裸执行 `tokenmaxxing switch` 保持其仅依赖缓存的停放，而 Codex 会完全忽略 `hardThresholds`，运行中的 Codex 无法在会话中途采用被切换的凭据，所以它会一直用当前账户直到真实的服务端限额（低于 100 的自定义上限墙对 Codex 不适用）。

## 按模型上限

`policy.switchModels`（默认 `["fable"]`）指定哪些模型家族的按模型周上限可以触发切换。匹配以家族标记为准，绝不用精确显示字符串：模型显示名会漂移（"Fable" 变成了 "Fable 5"），而精确字符串门槛曾经悄悄地完全禁用了按模型切换。两条相关的安全规则：

- 未知的活动模型会对每个配置的家族都施加门槛。就在切换清除快照之后，一台无头机器可能以模型盲的方式运行；曾经把未知当作无约束处理，导致某个账户卡在 Fable 上限上数小时而无人察觉。
- 候选账户筛选也会把受门槛限制的按模型上限计入，因此当账户池里每个账户都已烧掉 Fable 上限时，就不会做轮询式切换。

## 冷却期

45 秒的切换后冷却期为自动路径设了门槛。切换后同样这 45 秒内也会抑制 statusline 分流（在 macOS 上采用最多需 30 秒），否则更早的评估就会跑在被切换本身作废的数据上，正是这种场景曾经造成 A 到 B 又切回来的 respawn 循环。手动 `tokenmaxxing switch` 不受冷却期影响。

## 强制限额

缓存的数字可能落后于现实：活动账户的按模型上限只能靠对繁忙的活动 token 做一次 `/usage` 探测拿到，而在会话负载之下它往往什么都不打印。当服务端真的拒绝了一个回合时，Claude Code 会以 API 错误结束这个回合，并触发它的 `StopFailure` hook 而不是 `Stop`。tokenmaxxing 安装这个 hook 时带上了 `rate_limit` 匹配器，它读取转录里那一行结构化的错误记录（也就是 Claude Code 自己标记为 `isApiErrorMessage` 的那一行）：`quotaLimits` 块会连同服务端给出的重置时间一起指明是哪个窗口（`five_hour`、`seven_day`，或某个按模型的类型）；而 Fable 上限的失败不带 `quotaLimits`，靠客户端自己的错误呈现加上 429 响应体来识别。模型写出的文字从不作为判据。

这个 hook 会把该账户被强制限制的那个窗口标记为 100，并在账户上钉住一个带服务端日期的会话或周限额，直到那次重置为止，这样一个还没有任何用量采样的账户就不会被立刻选回来。它把这次强制限额当作比任何缓存窗口都更强的事实交给决策（绕过切换后的冷却期，按触发的模型家族给候选账户设门槛，而且绝不保住席位），随后硬路径切走。如果是受监督的会话、失败的又是主回合，它还会放下一个 respawn 标记：监督进程在新账户上以 `--resume` 重新启动，并提交一条续接提示词，让被打断的工作接着做下去。发生在子 agent 内部的失败只切换、绝不 respawn（父回合还在运行中），而未受监督的会话会拿到这次切换，并在下一次请求时采用它。

只有当一次失败可以被证明发生在切换之后的凭证上时才算数：要么是切换之后的一次重新启动，要么是落在切换加冷却期之后的一次失败请求。速率限制的拒绝在请求刚开始时就到达，所以无论这个回合跑了多久，锚点都是错误行自身的时间。正因如此，一串重新触发的序列才能连着跨过好几个已烧光的账户，而不会让某个仍握着旧 token 的请求把新席位也标记成受限。

## 检查节奏

周期性定时器每 60 秒运行一次 `tokenmaxxing check --if-due`，每次评估都会从这一跳的起点算起安排下一次评估，依据是活动账户距离最近那道阈值条（生效的会话档位、7 天汇总，以及每一个受门槛限制的按模型上限）还剩多少余量：余量在 40 个百分点及以上就睡五分钟，20 睡三分钟，8 睡两分钟，比这更少则每一跳都评估。阶梯还会随着爬升的档数把这个睡眠时长逐档收紧：第一档最多睡五分钟，第二档最多三分钟，第三档最多两分钟，再往上的任何一档都是每跳都评估，所以已经爬过一层的账户池，轮询起来会比还停在第一档的更勤。落点与到期时间相差不到半跳的那一跳也算到期，这样一次慢评估就不会把一个档次整整推迟一跳。裸执行 `tokenmaxxing check` 会忽略这套排期，立刻评估。分流数据比轮询 TTL 还旧、或者活动组织根本没有分流数据时，沿用原来的三分钟节奏；受门槛限制的模型家族若没有上限数据行，睡眠就绝不会超过两分钟，因此没测量到的窗口永远换不来慢车道。耗尽等待会一直睡到自己的重置，落在切换后冷却期内的一跳恰好睡到冷却期结束，而比轮询 TTL 更旧的上限数据行按未测量处理。切换会清空排期，让新席位在冷却期一解除就被评估。慢车道之所以安全，只是因为 StopFailure hook 会在强制限额发生的那一刻就抓住它。
