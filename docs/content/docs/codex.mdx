---
title: Codex support
description: Pooling ChatGPT-subscription accounts for the Codex CLI, per session
---

The same pooling works for OpenAI's Codex CLI, against your own ChatGPT-subscription accounts:

```sh
tokenmaxxing init --codex   # log in the first account, isolated, + install the codex supervisor & Stop hook
tokenmaxxing add --codex    # log in another account, isolated - your primary login is untouched
codex                       # use codex as always
```

The Codex pool is separate state: its own accounts index, its own per-account stores (0600 files on both platforms, since codex's own store is a plaintext file), and its own lock. The engine is shared: one account model (`id`, `label`, `email`, `tier`, cached `windows`), one picker, one decision, and one set of account commands (`init`, `add`, `auth`, `rm`, and `rename`) run against a Codex provider when you pass `--codex`; `status` renders every pool and takes no pool flag. The provider holds only what differs: identity from `auth.json` (the account id, with the id token's claims for the email and plan), the usage GET and the refresh it needs, the credential store, presence, and the store check before a move. The restart itself belongs to the codex supervisor and its Stop hook.

## One store per account, sessions shared

Each pooled account owns one store under the state directory: `codex-stores/<uuid8>/`. The store holds that account's `auth.json`; every other entry that exists in your real `~/.codex` when a session launches (config, hooks, sessions, sqlite state, skills, caches) is linked into the store by symlink, so transcripts, thread history, and settings stay shared and `codex resume <session-id>` works across stores. An entry created in `~/.codex` after a launch gets its link at the next launch. Only the credential is namespaced. A session runs on an account because the supervisor sets `CODEX_HOME` to that account's store before it spawns codex; `codex` and `codex resume` are supervised, while `codex exec`, `codex review`, `codex login`, `codex mcp`, and the other non-interactive subcommands pass straight through on your primary `~/.codex` login.

tokenmaxxing writes a store at onboarding, when `init`, `add`, or `auth` harvests an isolated login into it, and again when it reads usage for an account whose access token is about to expire and that has no live session: it runs the refresh itself and stores the rotation at once. An account running in a session is never refreshed from outside; codex refreshes it in place against its own store. A credential is never copied between stores: a refresh rotation revokes the superseded refresh token, so two stores holding one grant would kill the grant family. A refresh that comes back `invalid_grant`, or a reused, expired, or invalidated refresh token, flags the account `needsReauth`, which drops it from placement until `auth --codex`. `rm --codex` deletes the whole store directory, symlinks included.

## Why restart is the switch on Codex

A running codex process holds one in-memory auth manager and explicitly refuses to reload `auth.json` when it now names a different account. There is no file watcher and no per-request credential poll, so a credential swapped underneath a running codex simply never takes effect for inference. Restart is the switch: `codex resume <session-id>` continues the local transcript on whatever account the new process started under.

tokenmaxxing handles this with a codex supervisor shim: the Stop hook reads the seat's usage when its cached figure is older than `policy.usagePollTtlMs`, runs the same decision against the same two bars at each turn boundary, and when it moves, it writes a marker that makes the supervisor SIGTERM the session at the committed boundary and relaunch `codex resume <session-id>` under the target's store, transcript intact (`resume --last` when the hook carried no session id). The relaunch prints which account it switched to; unlike the Claude path it submits no first prompt, so you type the next turn. A marker the supervisor cannot parse stops the session instead of resuming it. The hook does nothing in a codex started outside the supervisor. Because every codex switch is a visible restart, the automatic codex decision moves only once the session's account is at or over a bar. There is no depleted-pool countdown for codex - nothing can pause a codex session - so a fully depleted codex pool stays put. When the session's account is at or over a bar, the hook first compacts the thread on that account through `codex app-server` (`thread/resume`, then `thread/compact/start`), bounded at 3 minutes and best effort, so the resumed session on the fresh account starts from the summary rather than re-uploading the whole history; see [Compaction before a move](/switching#compaction-before-a-move). The hook is declared in `~/.codex/hooks.json` with a 300-second timeout that covers the usage read, the compaction, and the decision.

Other codex-specific mechanics:

- Usage is read from a free authenticated GET against codex's own rate-limit endpoint: percentages plus absolute epoch reset times, the aggregate windows and every named additional limit alike, and every named limit screens and triggers against its own bar by duration. Window classification is duration-driven, never position-driven, because current plans may have no 5-hour window at all and the weekly window sits in the primary slot.
- Codex refresh tokens rotate, and reusing a superseded one kills the whole grant family. Every rotation tokenmaxxing performs is persisted the instant it returns into the account's own store, and per-session presence files ensure an account running in a live sibling session is never a placement or move target and never gets its store refreshed from outside.
- Codex requires the file credential store: `init --codex` fails fast when `~/.codex/config.toml` pins `cli_auth_credentials_store` to anything but `file`, and every isolated login (`init`, `add`, and `auth`) writes the file-mode setting into its onboarding home so the login lands harvestable. `auth --codex <sel>` reauthenticates a pooled Codex account in place through the same isolated login and refuses a login that lands on a different account.
- Parked Codex figures refresh when `status` samples the pool, and a seat's figure refreshes in its own Stop hook; the periodic check tick samples Claude accounts only, so a parked Codex account's figure is as old as the last `status`, with a passed reset reading as empty.
- Codex keeps no pool-wide active label, no post-swap cooldown, and no manual `switch`: each codex session runs on its own account's store and moves on its own, so placement at launch replaces the manual pick.
- One manual step per seat: codex trusts hooks per store path, so after `init --codex` open a supervised session on each pooled account, run `/hooks`, and trust the tokenmaxxing Stop hook - auto-switching stays silently inert on an untrusted seat. `tokenmaxxing doctor` reads the trust state from `~/.codex/config.toml`, keyed by the store's `hooks.json` path and the hook's position in the Stop list (so another Stop hook inserted ahead of tokenmaxxing's resets every seat to untrusted), lists seats still needing trust, and cannot tell a stale hash from a current one. `init --codex` prints this reminder.
