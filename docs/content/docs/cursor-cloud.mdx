title: Cursor Cloud
description: Hand work from a Cursor Cloud Agent to Claude Code running on your own subscription accounts
---

A Cursor Cloud Agent runs on an isolated Ubuntu VM with no keychain, no tokenmaxxing pool state, and no hot swap. The Cursor Cloud path uses what the VM does have, environment variables, a shell, and repo files. A project subagent checked into the repo forwards a task to `tokenmaxxing cloud run`, which spawns `claude -p` under one long-lived setup token per thread and moves that thread to the next token when the account it runs on hits a usage limit.

Setup tokens are for Cursor Cloud only. Regular Claude Code use stays on the keychain login. A setup token is inference-only, `/usage` reports no percentages under it, and the local switching engine never reads one.

## Setup

1. Mint the tokens on your own machine. `tokenmaxxing setup-token` walks the pool and runs `claude setup-token` once per account that has no stored token; each run opens the browser flow and you sign into that account. The tokens land in `setup-tokens.json` under the state directory (mode 0600) and the command prints the value for the Cursor secret, a JSON array of `{label, token}` objects.
2. Add a user-scoped Runtime Secret named `TOKENMAXXING_TOKENS` at [cursor.com/dashboard/cloud-agents](https://cursor.com/dashboard/cloud-agents) with the printed value. `tokenmaxxing setup-token --print` prints it again later.
3. Run `tokenmaxxing cursor init` in the repo and commit `.cursor/agents/claude.md` and `.cursor/environment.json`. An existing `environment.json` is left untouched and the command prints the install line to add to it.
4. Start a cloud agent on the repo. The first Build runs `install`, which puts Bun, Claude Code, and tokenmaxxing on the disk snapshot.
5. Invoke `/claude <task>` in the agent, or let the parent delegate on its own; the subagent's description says "use proactively".

## Why user scope and Runtime Secret

- User secrets are added only when an agent starts. They are not available during Builds and do not become part of a shared snapshot.
- Runtime Secret values are loaded as environment variables and replaced with `[REDACTED]` in the agent's tool call results, chat transcript, commits, and commit messages. They stay visible to anyone who uses the agent's environment through its terminal.

## What runs on the VM

- `install`, written by `cursor init`: `curl -fsSL https://bun.sh/install | bash && curl -fsSL https://claude.ai/install.sh | bash && "$HOME/.bun/bin/bun" add -g tokenmaxxing && test -x "$HOME/.bun/bin/bun" && test -x "$HOME/.local/bin/claude" && test -e "$HOME/.bun/bin/tokenmaxxing"`. Absolute paths throughout, because a Build keeps disk state and drops exported shell variables; every step is idempotent because `install` runs for every Build on previously prepared disk; the trailing tests fail the Build when an installer download produced nothing, since `curl | bash` alone reports the shell's status, not curl's.
- The relay, `.cursor/agents/claude.md`: a project subagent named `claude` whose one job is one shell call, `TOKENMAXXING_CLAUDE_BIN="$HOME/.local/bin/claude" "$HOME/.bun/bin/bun" "$HOME/.bun/bin/tokenmaxxing" cloud run` with the task on stdin through a quoted heredoc whose delimiter the relay picks fresh per call (`TASK_` plus eight random characters), returning stdout unchanged. Bun is named explicitly because a Bun global bin is a symlink to the package's `main.ts` and its `#!/usr/bin/env bun` shebang needs Bun on PATH, which a non-login cloud shell may not have. `TOKENMAXXING_CLAUDE_BIN` pins the native installer's launcher so the runner never scans PATH, and a missing binary fails fast. `readonly` stays false because the relay's one call changes state; the parent decides per call whether to run it in the background.
- `tokenmaxxing cloud run`: reads `TOKENMAXXING_TOKENS`, picks a token, runs `claude -p --output-format json --dangerously-skip-permissions` in the repo checkout with `CLAUDE_CODE_OAUTH_TOKEN` set on the child only and `TOKENMAXXING_TOKENS` removed from it, and prints the result text followed by one `session <id>` line. State lives in `cloud/sessions.json` (session id to label) and `cloud/walled.json` (label to reset time) under the state directory, read fresh under a lock before every pick, so parallel subagents can share one VM.
- Pick: with `--session <id>`, the recorded label unless it is walled; otherwise the unwalled label with the fewest recorded sessions, first in the array on ties. A walled label whose reset has passed counts as unwalled. The pick writes a reservation for the chosen label before it releases the lock, so a burst of parallel new runs spreads across tokens; a reservation whose process is gone is dropped on the next read.
- Rotation: when a run ends on an error and the session transcript holds an API error row appended during that run (past the transcript's size at the spawn) that is a non-transient rate limit, the same structured row the StopFailure hook reads, the label is walled until the `quotaLimits.resetsAt` that row names, or five hours when the row carries no reset (the credits branch), and the same prompt is retried with `--resume <id>` on the next pick. The thread keeps its transcript and only its cache is rebuilt. The result's `api_error_status` alone never walls a label: a transient 429 or a limit row left by an earlier token in the same session is not a limit for this run. Any other error exits 1 with the errors and the session id, without spending another account.
- Not on the VM: hooks, MCP, `/usage`, `settings.json` writes, the supervisor, the periodic timer, `accounts.json`.

Permissions are yolo only, `--dangerously-skip-permissions`, because the VM is disposable and cloud agents auto-run terminal commands already. Claude Code refuses that flag under root, so the environment must run as a non-root user (Cursor's reference Dockerfile creates `ubuntu`, and `environment.json` carries a `user` field).

One token per thread, pinned for the life of the session. The API caches by exact prefix and each model has its own cache, so a mid-thread account change rebuilds that thread's cache. Pinning means a rotation busts one thread, not every thread at once.

## Limits

- No usage percentages under a setup token. Rotation is reactive, on a limit error only.
- Transcripts live on the VM disk. A thread resumes across follow-ups within one VM life and not after the runtime workspace is recycled; the recycle timer is not published.
- Tokens expire a year after minting and never rotate. `doctor` warns once a stored token is eleven months old; `setup-token rm <label>` then `setup-token` re-mints it. Removal is local, Claude Code documents no revocation for setup tokens. The printed secret carries pooled accounts only, under their current labels; `tokenmaxxing rm` drops the removed account's token with it, and a stored token whose account is gone is listed as left out, with its uuid, until `setup-token rm <label|uuid>` drops it (a pooled label always selects the pooled account's token, so an orphan under a reused label goes by its uuid).
- The token's owner is not verified: an inference-only token cannot read the profile endpoint, so the label is the sign-in you chose in the browser.
- The secret lives in the VM's process environment. Every process under the agent's user can read it, `printenv` and `/proc/<pid>/environ` included, and so can the Claude child a run spawns with shell access; `cloud run` strips the secret from that child's own environment and nothing more. Treat a relayed task as trusted input.
- Keep team follow-ups disabled while the tokens are in play: a follow-up from another team member can instruct an agent that holds your secrets to read environment variables.
- Cloud agents sometimes begin in a read-only environment for early exploratory turns. A relay call during that phase fails and says so.
- Restricted egress: the install and the runner need at least `bun.sh`, `claude.ai`, `downloads.claude.ai`, `registry.npmjs.org`, and `api.anthropic.com`. Internet is allowed by default, so this applies only to allowlist modes, and the full set of hosts the claude binary reaches is not documented.
- Every cloud run draws on the same account windows the local pool uses. A busy cloud fleet drains the accounts the local pool draws on.
- Cursor caps API-created environment variables at 4096 bytes per value and `setup-token` warns when the printed value passes that cap; whether the dashboard applies the same cap is not documented.
- Whether `claude setup-token` prints the token to a piped stdout is not documented. `setup-token` forwards the child's output to your terminal while it captures it, reads the token from between the two marker lines the flow prints, and asks you to paste the token when the markers are missing.
