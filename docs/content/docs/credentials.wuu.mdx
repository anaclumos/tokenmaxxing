所有状态侪勒 `~/.config/tokenmaxxing/` 里向。凭据 I/O 走一个单一嗰、按平台拣好嗰存储门面；调用点从来勿按平台分支。

**macOS**：凭据当作 generic-password 条目存勒登录 keychain 里向，搭 Claude Code 自家存嗰地方对得牢。活跃条目就是 claude 读嗰埃个；池子里每个账户嗰备份各自当作一个 `tokenmaxxing-cred-<uuid8>` keychain 条目停放。磁盘高头呒没啥明文。读用 `security find-generic-password -w`（秘密只会出现勒 stdout 高头）；写是拿一条 `add-generic-password` 通过 stdin 管进 `security -i`，所以秘密从来勿会出现勒任何进程嗰 argv 里向。交互模式有一个大约 4 KB 嗰行缓冲，所以超大嗰 blob 会退回到 argv 写入，搿也是停放条目只存最小 OAuth 对象嗰一个道理。

**Linux**：Claude Code 拿凭据存成一个 0600 嗰明文文件，tokenmaxxing 也照同一套模型走：活跃文件是 claude 自家嗰 `.credentials.json`，停放备份是 `~/.config/tokenmaxxing/creds/` 底下一个 0700 目录里向嗰原子 0600 文件。搿搭嗰原子意思是先写临时文件、fsync、再改名字：一个并发嗰读者一直看到嗰要么是整份旧文件、要么是整份新文件，从来勿会是残缺嗰。

切换强制执行嗰安全规则：

- **按真正主人采集。** 切换之前，活跃凭据实际嗰主人是通过问 API 搿个 token 属于啥个组织来定嗰（对 OAuth roles 端点跑 `fetchTokenOrg`），从来勿去相信存牢嗰活跃标签，因为标签会漂移。一趟漂移嗰标签曾经害得一个账户嗰采集覆盖脱另外一个账户唯一嗰备份。假使活跃凭据属于池子外头嗰一个账户，切换会直接拒绝，勿去覆盖伊。
- **一个临界区。** 采集、装新凭据、备份伊轮换过嗰 token、`~/.claude.json` 账户切换、搭活跃标签嗰提交，统统勒同一个锁牢嗰区块里向发生。
- **搭 claude 自家嗰刷新互锁。** 一个快过期嗰会话随便啥辰光侪好轮换伊自家嗰 token，所以凭据写入也拿 Claude Code 嗰刷新锁（尽力而为，带一个过时锁嗰回收搭一个有界超时）。
- **死授权干净降级。** 一趟刷新假使回来是 `invalid_grant`，就拿埃个账户标成需要重新认证，还勒错误传播之前拿搿个标记持久化好，所以重试循环会缩小候选集合、然后终止。`tokenmaxxing auth` 就地修好一个被标嗰账户，而且伊会拒绝一个落到跟要修嗰账户勿一样嗰账户高头嗰登录。
- **勿记录 token。** token 从来勿会出现勒日志、错误或者输出里向。从 token 搭用量端点来嗰错误主体从来勿会原样露出来；只有一组白名单里嗰字段保得下来，因为一个 token 端点嗰失败主体好回显请求材料。
- **探测卫生。** 任何生出来嗰 `claude` 探测侪会擦脱 claude 勒 keychain 查询之前会认嗰八个环境变量（`ANTHROPIC_API_KEY`、`CLAUDE_CODE_OAUTH_TOKEN`、`CLAUDE_SECURESTORAGE_CONFIG_DIR` 等等），所以一趟探测永远勿会被算到勿对嗰账户高头。
