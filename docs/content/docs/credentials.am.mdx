---
title: Credential ማከማቻ እና የደህንነት ሞዴል
description: "credentialዎች በእያንዳንዱ platform የት እንደሚኖሩ እና እያንዳንዱ መቀያየር የሚያስፈጽማቸው ደንቦች"
---

ሁሉም state በ `~/.config/tokenmaxxing/` ውስጥ ይኖራል። Credential I/O በአንድ በ platform-የተመረጠ store facade ውስጥ ያልፋል፤ የጥሪ ቦታዎች በ platform ላይ በጭራሽ አይከፋፈሉም።

**macOS**፦ credentialዎች በ login keychain ውስጥ እንደ generic-password ንጥሎች ይኖራሉ፣ Claude Code ራሱ ከሚያስቀምጥበት ጋር የሚዛመድ። ቀጥታው ንጥል claude የሚያነበው ነው፤ የእያንዳንዱ የተሰበሰበ መለያ backup እንደ ራሱ `tokenmaxxing-cred-<uuid8>` keychain ንጥል ይያዛል። በ disk ላይ ምንም plaintext የለም። ንባቦች `security find-generic-password -w` ን ይጠቀማሉ (ምስጢሩ በ stdout ላይ ብቻ ይታያል)፤ ጽሁፎች `add-generic-password` መስመርን በ stdin በኩል ወደ `security -i` ያስተላልፋሉ ስለዚህ ምስጢሩ በማንኛውም process argv ላይ በጭራሽ አይታይም። interactive mode ው ወደ 4 KB የሚጠጋ line buffer አለው፣ ስለዚህ ከመጠን በላይ የሆኑ blobዎች ወደ argv ጽሁፍ ይመለሳሉ - የተያዙ ንጥሎች አነስተኛውን OAuth ነገር ብቻ የሚያከማቹበት አንድ ምክንያት።

**Linux**፦ Claude Code credentialዎችን እንደ 0600 plaintext ፋይል ያከማቻል፣ እና tokenmaxxing ተመሳሳዩን ሞዴል ይከተላል፦ ቀጥታው ፋይል የ claude የራሱ `.credentials.json` ነው፣ እና የተያዙ backupዎች በ 0700 directory ውስጥ በ `~/.config/tokenmaxxing/creds/` ስር atomic 0600 ፋይሎች ናቸው። እዚህ atomic ማለት ወደ-temp-መጻፍ፣ fsync፣ ከዚያ rename ማለት ነው፦ ተባባሪ አንባቢ ሁልጊዜ ሙሉ አሮጌ ወይም ሙሉ አዲስ ፋይል ያያል እንጂ በጭራሽ ከፊል አይደለም።

መቀያየር የሚያስፈጽማቸው የደህንነት ደንቦች፦

- **በትክክለኛ ባለቤት መሰብሰብ።** ከመቀያየር በፊት፣ የቀጥታው credential ትክክለኛ ባለቤት token የትኛው መለያ እንደሆነ API ን በመጠየቅ ይፈታል (`fetchTokenIdentity` በ OAuth profile endpoint ላይ፣ የመለያውን UUID በማመሳከር) - በድርጅት መሠረት በጭራሽ አይደለም፣ ምክንያቱም የ Team plan እያንዳንዱ seat አንድ ድርጅት ስለሚጋራ፣ እና ሊለዋወጥ የሚችለውን የተከማቸ ንቁ label በማመን በጭራሽ አይደለም። የተለዋወጠ label በአንድ ወቅት የአንድ መለያ መሰብሰብ የሌላ መለያ ብቸኛ backup እንዲደፈጥጥ አድርጓል። ቀጥታው credential ከ pool ውጭ ላለ መለያ ከሆነ፣ መቀያየሩ ከመድፍጠጥ ይልቅ ፍጹም እምቢ ይላል።
- **አንድ ወሳኝ ክፍል።** መሰብሰቡ፣ የአዲሱ credential መጫን፣ የተሽከረከረ token ው backup፣ የ `~/.claude.json` መለያ መቀያየር፣ እና ንቁ-label commit ሁሉም በተመሳሳይ የተቆለፈ ክፍል ውስጥ ይከሰታሉ።
- **ከ claude የራሱ refresh ጋር መተሳሰር።** ማብቂያ-የተቃረበ session በማንኛውም ጊዜ የራሱን token ማሽከርከር ይችላል፣ ስለዚህ የ credential ጽሁፎች የ Claude Code refresh lock ንም ይወስዳሉ (best-effort፣ ከ stale-lock መልሶ ማግኘት እና ከተገደበ timeout ጋር)።
- **የሞቱ grantዎች በንጽህና ይቀንሳሉ።** `invalid_grant` ተመልሶ የመጣ refresh ያንን መለያ needs-reauth ብሎ ምልክት ያደርገዋል እና ስህተቱ ከመሰራጨቱ በፊት flag ን ያስቀምጣል፣ ስለዚህ retry loopዎች የእጩ ስብስቡን ያሳንሱ እና ያቆማሉ። `tokenmaxxing auth` ምልክት የተደረገበትን መለያ በቦታው ያስተካክላል፣ እና ከሚጠገነው የተለየ መለያ ላይ የሚያርፍ login ን እምቢ ይላል።
- **token አለመመዝገብ።** tokenዎች በ logዎች፣ ስህተቶች ወይም output ውስጥ በጭራሽ አይታዩም። ከ token እና usage endpointዎች የስህተት አካላት በጭራሽ ጥሬ አይቀርቡም፤ የተፈቀደ የ fieldዎች ስብስብ ብቻ ይተርፋል፣ ምክንያቱም የ token endpoint የውድቀት አካል የ request ንጥረ ነገርን ሊያስተጋባ ስለሚችል።
- **የ probe ንጽህና።** ማንኛውም የተነሳ `claude` probe claude keychain lookup ከማድረጉ በፊት የሚያከብራቸውን ስምንት environment variableዎችን ያጸዳል (`ANTHROPIC_API_KEY`፣ `CLAUDE_CODE_OAUTH_TOKEN`፣ `CLAUDE_SECURESTORAGE_CONFIG_DIR`፣ ወዘተ)፣ ስለዚህ probe በጭራሽ ለተሳሳተ መለያ ሊሰጥ አይችልም።
