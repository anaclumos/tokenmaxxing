---

呢個決定有兩層：先係一道參與閘門，跟住係貪婪或者強硬路徑。

## 參與

喺 `policy.greedySessionFloor`（預設 80，以 5 小時 session 窗口嘅百分比計）之下，個決定根本唔會行 - 新嘅 session 會繼續騎住自己個帳戶。一旦活躍嘅 session 窗口用咗 80%，或者任何一條界線被跨過，個決定就會參與。

## 篩選界線

呢啲閾值係篩選界線，唔係恐慌嘅觸發器：

- `thresholds.session`：一條階梯，預設 `[90]`，只得一級。每次評估都會解析出一個活躍級數：即係仲有已入池帳戶（連當前嗰個都計埋）仲用得嘅最低嗰級。如果用 `[50, 80, 95]` 咁樣嘅多級階梯，只要仲有帳戶喺 50 之下，界線就係 50，所以一個跨過 50 嘅座位就會交俾嗰個帳戶。當每個帳戶都過咗 50，界線就爬上 80，全部都過咗 80 就再爬上 95。最高嗰級就係終點界線，再上去就交由撞牆（見下文）接手。一次 5 小時重設好平就等得起，所以多級嘅帳戶池會一級一級噉消耗，冇邊個帳戶會遠遠拋離自己啲兄弟。
- `thresholds.weekly`：98。呢一條界線同時涵蓋 7 日總量同每個模型嘅每週上限。每週配額係用剩即棄，所以會消耗到好接近撞牆。

兩個都刻意低過 100：留低嘅餘裕就係喺帳戶真正撞到上限之前，行到一個乾淨回合邊界（加上 macOS 上面最多一個回合嘅採用延遲）所需嘅預算。同一批界線亦都用嚟篩選切換候選：超咗任何一條界線嘅帳戶就唔係有效目標。觸發同篩選永遠用同一組有效界線（活躍級數同每週界線，各自減去 `policy.projectionMargin`），因為篩選一旦鬆過觸發器，就會將切換落喺觸發器即刻會重新標記嘅帳戶度，搞到成個帳戶池乒乓咁彈嚟彈去。一級只會計喺嗰級仲用得嘅帳戶：死咗嘅授權、燒晒又被閘住嘅每模型上限，或者伺服器釘死嘅強制，都唔會將界線壓住唔准升；而喺同一次評估入面，每次重試都會由帳戶池重新讀一次嗰級。Codex 淨係讀最高嗰級，因為重新啟動就係佢嘅切換。

## 目標：步伐壓力

喺可用帳戶之中，目標就係最落後於自己每週步伐嗰個：**步伐壓力**最高嗰個，即係剩餘每週百分比除以距離嗰個帳戶每週重設嘅時間。快將浪費最多配額嗰個帳戶勝出。打和就睇邊個每週最快到期，再睇邊個 7 日用量最低。

一切都靠儲存做絕對 UTC epoch 嘅快取窗口運行，所以就算快照過時都仍然可以正確解析：過咗期嘅每週重設會以剛好 7 日嘅步伐向前外推，而任何超過咗快取重設嘅窗口都當做啱啱清空（永遠唔係切換嘅理由，亦都唔係令帳戶留喺後備席嘅理由）。

## 貪婪對強硬路徑

- **貪婪路徑**（已參與，但喺每條界線之下）：將每個帳戶排名，連當前嗰個都計埋。如果當前帳戶已經勝出或者打和，就咩都唔做。否則就切換去嚴格更好嗰個帳戶。呢條路徑永遠唔等，亦唔會預先泊存 - 唔會為咗一次等待而放棄一個仲用得嘅當前帳戶。因為當前帳戶都一齊排咗名，所以自動路徑同淨行 `tokenmaxxing switch` 兩者都係冪等：定期評估會收斂到啱嘅帳戶，然後就留喺度。

  自動嘅貪婪路徑會用遲滯守住現任。步伐壓力係一個連續值，所以兩個近乎打和嘅帳戶幾乎永遠唔會啱啱好打和，而用緊活躍帳戶會不斷將一個泊存帳戶推到稍為領先，一個帳戶池以前就係噉樣每隔幾分鐘就將個位乒乓咁彈嚟彈去，而每次切換都會搞爆每個組織嘅提示快取，下一個回合就要付返一次完全冇快取嘅重讀。`policy.greedySwapMargin`（預設 0.15）就係解決方法：一個泊存帳戶要贏當前帳戶嘅步伐壓力超過呢個分數，貪婪路徑先至會切換。噉交接就淨係喺現任消耗到真係落後咗先至發生，而唔係靠一個四捨五入級別嘅領先。呢個邊際永遠唔會放鬆一條已經跨過嘅界線、強硬路徑，又或者撞牆，淨係管全部都喺界線之下嘅帳戶之間嘅橫向切換。淨行 `tokenmaxxing switch` 會將個邊際設做零，所以手動切換仍然會收斂到嚴格最佳嗰個帳戶。
- **強硬路徑**（跨過咗一條界線）：切換走去最佳嘅可用候選。如果某個候選嘅刷新 token 原來已經死咗，就會標記做需要重新認證，然後試下一個候選。如果無嘢可用，就會行撞牆榨取（見下文），只有當每個可用帳戶都撞到自己嘅牆，先至會行耗盡等待邏輯；只有真正可以暫停 session 嘅呼叫者（受監督嘅 Stop hook）先可以預先泊存去一個仍然封鎖住但最快復原嘅帳戶。

## 撞牆

當強硬路徑搵唔到任何可用候選 - 即每個帳戶都超咗自己嘅篩選界線 - 自動決定唔會即刻泊存。佢會先對照**撞牆界線**（`hardThresholds`，預設 100，即每個帳戶喺伺服器嘅真正上限）重新評估：session 只要仲喺牆之下就會守住個位繼續榨，否則就切換去最佳嘅、仲喺牆之下嘅帳戶（同樣用步伐壓力排名），要到每個可用帳戶都真係撞到自己嘅牆先至泊存。一個刷新 token 已經死咗嘅帳戶會撥去重新認證，而唔係去等佢。復原係對照撞牆嚟量度，所以一個 5 小時窗口重設咗嘅帳戶，就算佢嘅每週窗口仲喺篩選界線之上，都可以再被榨多次。

咁做可以令每個帳戶最後嗰幾個百分比嘅配額唔會用剩。撞牆嘅讀數嚟自個決定本身已經用緊嘅用量來源 - 受監督嘅互動式 session 用 statusline tee，無頭運行就用一次 `/usage` 探測 - 同 Claude `/rate-limit-options` 顯示嘅係同一組數字，所以一個真係去到盡嘅帳戶會被偵測到並跳過。單一回合超標會喺個決定下一次運行嗰陣捕捉到 - 即定期檢查，又或者無頭運行上嘅下一次 spawn 或者 Stop 邊界。

`hardThresholds` 會同篩選界線一樣減走 `policy.projectionMargin`，所以將佢設成同 `thresholds` 一樣就會停用撞牆榨取。呢條路徑只限 Claude：淨行 `tokenmaxxing switch` 維持佢淨快取嘅泊存，而 Codex 就完全唔理 `hardThresholds` - 運行緊嘅 Codex 冇辦法喺 session 中途採用一個換咗嘅憑證，所以佢會騎住當前帳戶，直到伺服器嘅真正上限（一個低過 100 嘅自訂撞牆對 Codex 唔適用）。

## 每模型上限

`policy.switchModels`（預設 `["fable"]`）指定咗邊啲模型系列嘅每模型每週上限可以觸發切換。配對係靠系列 token，永遠唔靠準確嘅顯示字串：模型顯示名會漂移（「Fable」變咗做「Fable 5」），而用準確字串嘅閘門曾經靜靜哋完全停用咗每模型切換。兩條相關嘅安全規則：

- 活躍模型一旦未知，就會閘住每一個已設定嘅系列。喺切換清除快照之後，一部無頭機器可以喺對模型無感嘅狀態下運行；試過將未知當做無限制，結果令一個帳戶喺自己個 Fable 上限度坐咗幾個鐘都無人察覺。
- 候選篩選都會計埋被閘住嘅每模型上限，所以就算帳戶池入面每個帳戶都燒晒自己嘅 Fable 上限，都唔會循環輪替。

## 冷卻

45 秒嘅切換後冷卻會閘住自動路徑。切換之後嗰 45 秒同樣會抑制 statusline tee（macOS 上面採用最多需要 30 秒），所以較早嘅評估會走去用切換本身已經搞到失效嘅數據 - 就係呢個情境曾經整出一個 A 去 B 又彈返轉頭嘅重生迴圈。手動行 `tokenmaxxing switch` 唔受冷卻影響。

## 被強制執行嘅上限

快取落嚟嘅數字可以落後於現實：活躍帳戶嘅每模型上限，淨係嚟自對住忙碌活躍 token 嗰次 `/usage` 探測，而 session 有負載嗰陣佢好多時咩都唔會印出嚟。當伺服器真係拒絕咗一個回合，Claude Code 會以 API 錯誤結束嗰個回合，並且觸發佢個 `StopFailure` hook 而唔係 `Stop`。tokenmaxxing 安裝呢個 hook 嗰陣會配上 `rate_limit` matcher，而佢會讀轉錄稿入面有結構嘅錯誤行（就係 Claude Code 自己標記做 `isApiErrorMessage` 嗰行）：一個 `quotaLimits` 區塊會講明係邊個窗口（`five_hour`、`seven_day`，或者某個每模型類型）連同伺服器嘅重設時間；至於冇 `quotaLimits` 嘅 Fable 上限失敗，就靠客戶端自己嘅錯誤呈現加上 429 回應內容認得出。模型講嘅文字內容永遠都唔會讀。

呢個 hook 會將嗰個帳戶被強制嘅窗口蓋成 100，再喺個帳戶上面釘住一個由伺服器落日期嘅 session 或者每週上限，直到嗰次重設為止，咁一個仲未有用量樣本嘅帳戶就唔會即刻俾人揀返轉頭。佢會將呢個強制當成一件強過任何快取窗口嘅事實交俾個決定（會繞過切換後冷卻、按被觸發嘅系列閘住候選，亦都永遠唔會守住個位），跟住強硬路徑就切換走。喺一個主回合失敗咗嘅受監督 session 入面，佢仲會落一個重生標記：監督者會喺新帳戶上面重新啟動 `--resume`，再提交一個繼續嘅提示，等打斷咗嘅工作接得返落去。subagent 入面嘅失敗就淨係切換，永遠唔會重生（父回合仲行緊），而未受監督嘅 session 就攞到嗰次切換，喺佢下一次請求嗰陣採用。

一次失敗要證明得到係發生喺切換後嗰個憑證上面先至算數：即係切換之後嘅一次重新啟動，又或者喺切換加冷卻之後先落到嘅一個失敗請求。速率限制嘅拒絕係喺請求開始嗰刻就到，所以無論個回合行咗幾耐，錨點都係錯誤行自己嘅時間。就係咁，一連串重新觸發先至可以連續跨過幾個燒晒嘅帳戶，而唔會俾一個仲揸住舊 token 嘅請求蓋壞個新座位。

## 檢查節奏

定期計時器每一下 tick 行一次 `tokenmaxxing check --if-due`（`policy.checkIntervalMs`，預設 60 秒），而每次評估都會由今次 tick 開始嗰刻計起，按活躍帳戶距離最近一條界線（活躍嘅 session 級數、每週總量，同每一個被閘住嘅每模型上限）嘅餘裕，排定下一次幾時行：餘裕有 40 點或者以上就瞓五下 tick，20 點瞓三下，8 點瞓兩下，再細過噉就每一下 tick 都評估。個階梯仲會每爬高一級就將個瞓覺時間收窄一檔：喺第一級最多五下 tick，第二級最多三下，第三級最多兩下，再高過噉嘅級數就每一下 tick 都行，所以一個已經爬咗一級嘅帳戶池，會比仲喺第一級嗰個輪詢得密啲。一下 tick 只要落喺到期時間半下 tick 之內就當到期，咁一次慢嘅評估就唔會將一檔推遲成足足一下 tick。淨行 `tokenmaxxing check` 會唔理個排程，即刻評估。一個舊過輪詢 TTL 嘅 tee，又或者活躍組織根本冇 tee，就維持三下 tick 嘅節奏；而一個被閘住、又冇上限資料行嘅系列，永遠唔會瞓多過兩下 tick，所以一個未量度嘅窗口點都買唔到條慢線。耗盡等待會瞓向自己嘅重設時間，落喺切換後冷卻入面嘅一下 tick 就啱啱瞓到冷卻完，而舊過輪詢 TTL 嘅上限資料行就當做未量度。一次切換會清走個排程，等冷卻一完就即刻評估新嗰個座位。條慢線之所以安全，全靠 StopFailure hook 喺強制發生嗰一刻就捉到佢。
