tokenmaxxing هو CLI للتبديل التلقائي بين حسابات Claude Code. بيجمّع كذا حساب اشتراك (Pro/Max) بتاعتك وبيبدّل الـ credential النشط فوريًا لحساب أحدث لما اللي شغّال يقرّب من حد الاستخدام. بتشغّل `claude` بالظبط زي ما بتعمل دايمًا؛ التبديل بيحصل عند حدود turn آمنة والـ session اللي شغّال بيكمّل نفس المحادثة على الحساب الجديد من غير إعادة تشغيل. وبيشتغل عبر كذا session متوازية في نفس الوقت.

السلوك الوحيد اللي بيبان هو أسوأ حالة: لما كل الـ pool يوصل لحده، الـ session بيتوقّف مؤقتًا مع عدّاد تنازلي وبيكمّل تلقائيًا على أول حساب هيتعمله reset (Ctrl-C بيكمّل على طول).

<Callout>
النطاق: Claude Code على macOS و Linux، بالإضافة لـ Codex CLI من OpenAI كـ pool ثاني ومتوازي. بيجمّع حسابات الاشتراك، مش API keys. دي أداة للاستخدام الشخصي عشان تجمّع حسابات بتملكها، في sessions و agents بتشغّلها بنفسك. بص [الاستخدام الشخصي وشروط الخدمة](#personal-use-and-terms-of-service).
</Callout>

## المشكلة

اشتراك Claude بيقيس تلات حدود في نفس الوقت (كلها متأكد منها عن طريق `/usage`):

- **الـ session الحالية**: نافذة متحركة مدتها 5 ساعات.
- **الأسبوع الحالي (كل الموديلات)**: إجمالي على مدار 7 أيام.
- **الأسبوع الحالي، لكل موديل**: حدود أسبوعية منفصلة لكل عيلة موديل. دي موجودة حاليًا بس لـ Sonnet و Fable، وحد Fable بس هو الضيّق كفاية عشان يفرق. بيوصل لحده قبل الإجمالي بكتير. الجهاز ممكن يكون عند 50% في إجمالي الأسبوع وهو أصلاً عند 80% في أسبوع Fable.

الحصة الأسبوعية إما تستخدمها أو تخسرها: أي حاجة الحساب ماستهلكهاش لحد ما يوصل للـ reset الأسبوعي الثابت بتاعه بتضيع. لو بتملك كذا حساب، الاستراتيجية العقلانية إنك تفضل تستهلك الحصة على الحساب اللي متأخّر أكتر عن الإيقاع الأسبوعي بتاعه، وتبدّل بعيد عنه قبل ما أي حد يوصل للنهاية في نص الـ session.

لو عملت ده بإيدك يبقى معناه إنك تعمل logout و login وتخسر المحادثة بتاعتك. tokenmaxxing بيأتمت ده: الـ `claude` اللي شغّال بيعيد فحص مخزن الـ credential بتاعه بين الطلبات، فالـ credential اللي اتبدّل تحته بيتم تبنّيه في مكانه (خلال حوالي 30 ثانية على macOS، وفي الطلب اللي بعده على Linux). التبديل العادي عمره ما بيعيد تشغيل الـ session بتاعتك. الحالة الوحيدة اللي لسه محتاجة إدارة عمليات هي الـ pool المستنفد بالكامل. الـ session مش قادرة توقّف نفسها، وده اللي الـ supervisor الخفيف موجود عشانه.

أي حاجة تانية في `claude` زي ما هي: كل الـ flags، والـ MCP servers، والـ hooks، والـ skills بتعدّي زي ما هي.

## البداية السريعة

بيحتاج [Bun](https://bun.sh) و Claude Code، على macOS أو Linux.

```sh
bun add -g tokenmaxxing
tokenmaxxing init
```

`init` بيعمل خمس حاجات:

1. بيستورد الحساب اللي انت أصلاً مسجّل دخول بيه كحساب رقم 1 (مفيش أمر `adopt` منفصل).
2. بيثبّت الـ `claude` supervisor shim.
3. بيثبّت تلات مدخلات في الـ `settings.json` بتاع Claude Code: statusLine، و Stop hook، و SessionStart hook (بالإضافة لمدخل subagentStatusLine).
4. بيضيف مجلد الـ bin بتاع الـ supervisor لـ PATH في الـ shell rc بتاعك (idempotent، ومتعلّم عليه بتعليق `# tokenmaxxing PATH`). لازم يبقى قدّام الـ `claude` الحقيقي في الـ PATH عشان يعترضه.
5. بيثبّت timer للفحص الدوري (launchd agent على macOS، و systemd user timer على Linux) بيشغّل `tokenmaxxing check` كل 180 ثانية.

اعمل restart للـ shell بتاعك، وبعدين ضيف حسابات أكتر واتفضّل:

```sh
tokenmaxxing add        # بيسجّل دخول حساب زيادة، بمعزل، وبيضمّه للـ pool
claude                  # استخدم claude زي العادة
```

`tokenmaxxing` كمان ليه اسم مختصر `xx`. `tokenmaxxing` (أو `xx`) لوحده بيشغّل `status`؛ و `switch` بيفضل صريح.

## الأوامر

| الأمر | بيعمل إيه |
|---|---|
| `tokenmaxxing init` | استورد الحساب الحالي، وثبّت الـ supervisor والـ hooks والـ statusline |
| `tokenmaxxing init --codex` | نفس الحاجة لـ Codex: استورد تسجيل الدخول، وثبّت الـ codex supervisor و Stop hook |
| `tokenmaxxing add` | سجّل حساب إضافي (تسجيل دخول معزول، بيتم ضمّه للـ pool) |
| `tokenmaxxing add --codex` | سجّل حساب Codex إضافي (تسجيل دخول معزول) |
| `tokenmaxxing auth [sel \| --all]` | أعد المصادقة لحساب في الـ pool في مكانه. من غير خيارات بيعرض الـ pool وبيسألك أنهي؛ الـ selector بيستهدف حساب واحد وبيقولك تسجّل دخول بأنهي إيميل؛ `--all` بيمشي على كل حساب محتاج إعادة مصادقة واحد ورا التاني |
| `tokenmaxxing switch [sel]` | بدّل لأحسن حساب (greedy، idempotent) أو افرض حساب معيّن |
| `tokenmaxxing switch --codex [sel]` | بدّل الـ Codex pool (بيسري مفعوله في أول تشغيل codex جاي) |
| `tokenmaxxing ls` | اعرض الحسابات اللي في الـ pool |
| `tokenmaxxing status` | الحسابات مع شرايط استخدام لـ 5 ساعات / أسبوعي / لكل موديل، النشط والمستنفد لحد الـ reset |
| `tokenmaxxing status --force` | كمان بيعمل ping لكل حساب (طلب haiku صغيّر لكل واحد) عشان كل تايمرات الـ session بتاعت الـ 5 ساعات تبدأ دلوقتي، وبعدين ياخد عيّنة جديدة |
| `tokenmaxxing watch [seconds]` | حالة مباشرة، بيتعاد رسمها كل N ثانية (الافتراضي 120، الحد الأدنى 30؛ عمره ما بيعمل ping) |
| `tokenmaxxing config [get\|set\|unset\|tidy]` | الإعدادات الفعّالة مع مصادرها؛ عدّل المفاتيح المنقّطة؛ `tidy` بيشيل المفاتيح المجهولة |
| `tokenmaxxing check` | قيّم قرار التبديل مرة واحدة (ده اللي الـ timer الدوري بيشغّله) |
| `tokenmaxxing serve [setup\|link\|unlink\|links]` | daemon جسر Slack (Socket Mode، من غير URL عام) |
| `tokenmaxxing doctor` | اتأكد إن الـ supervisor ومدخلات الإعدادات لسه موجودين |
| `tokenmaxxing rename [--codex] <sel> <label>` | غيّر اسم حساب في الـ pool |
| `tokenmaxxing rm <sel>` | شيل حساب من الـ pool |
| `tokenmaxxing uninstall` | شيل الـ supervisor ومدخلات الإعدادات (الحسابات والـ credentials بتفضل موجودة) |

## البنية المعمارية

tokenmaxxing هو نقطة دخول واحدة متعددة الاستدعاءات (`src/main.ts`) بتتصرف كـ `claude` supervisor لما تتنادى بالاسم ده، وبتقدّم الـ hook و statusline shims عن طريق subcommands داخلية، وغير كده بتوزّع أوامر الـ CLI. بتشتغل مباشرة تحت Bun؛ باكدج الـ npm بيشحن كود TypeScript، مش build.

الأجزاء المتحركة:

### الـ supervisor shim

`init` بيكتب shell shim من سطرين اسمه `claude` في `~/.config/tokenmaxxing/bin/` وبيحط المجلد ده أول حاجة في الـ PATH. لما تكتب `claude`، الـ shim بيشغّل الـ supervisor، اللي بيطلّع الـ claude binary الحقيقي مع stdio موروث و snapshot للتيرمينال محفوظ بـ `stty -g`. ده مدير عمليات وتيرمينال بس: عمره ما بيعمل proxy لترافيك الـ API وعمره ما بيلمس الـ tokens وهي شغّالة.

استدعاءات وضع الطباعة (`claude -p`، `--version`، `--help`)، والـ subcommands غير التفاعلية (`claude mcp`، `claude config`، وهكذا)، والـ probes بتاعت tokenmaxxing نفسها بتعدّي على طول من غير إدارة session. بالنسبة للـ session التفاعلية، الـ supervisor بيثبّت session id (بيولّد واحد، أو بيعيد استخدام اللي مرّرته عن طريق `--session-id` / `-r` / `-c`)، وبيحفظ الـ launch flags بتاعتك عشان أي إعادة تشغيل بعدين تقدر تعيدها، وبعدين بيراقب ملف respawn marker مرتبط بالـ session دي.

### الـ statusline tee

Claude Code بيدفع بيانات حدود المعدل (`rate_limits.five_hour` و `rate_limits.seven_day`) لـ stdin بتاع الـ statusline كل turn. tokenmaxxing بيملك خانة الـ statusline، فالـ renderer بتاعه بيشتغل كمان كـ usage feed مجاني قايم على الدفع: كل tick بيعمل tee للنوافذ الإجمالية بالإضافة للموديل النشط في `usage.json`. حدود الموديل مش موجودة في stdin بتاع الـ statusline؛ بتيجي بس من `claude -p '/usage'` (مجاني، صفر tokens)، اللي بيتعمله poll بـ TTL وبيتخزّن في `model-usage.json` لما الموديل النشط يكون محدود السعة.

الـ tee بيكتب عند التغيير بس: لما الأرقام تكون زي ما هي بيحدّث بس الـ mtime بتاع الملف، اللي بيشتغل كنبضة حياة للـ feed. الحداثة بتتحكم عليها دايمًا بالـ mtime، عمره ما بالـ timestamp المدمج.

### الـ Stop hook والتبديل

عند كل حدود turn، الـ Stop hook بيشغّل قرار التبديل (بص [إزاي بيتقرّر التبديل](#how-switching-decides)). لما التبديل يكون مبرَّر، بيحصل تحت قفل حصري `flock(2)` (بيتاخد عن طريق `bun:ffi`، لأن macOS ماعندهاش binary اسمه `flock(1)`)، وكتابة الـ credential كمان بتتشابك مع قفل التحديث بتاع Claude Code نفسه. جوّا القسم الحرج، التبديل الواحد:

1. بيحصد الـ credential الحي الحالي في النسخة الاحتياطية المركونة بتاعت مالكه الحقيقي.
2. بيثبّت الـ credential المحدَّث حديثًا بتاع الحساب المستهدف كالحي، وبيدمجه في الـ blob الحي الموجود عشان الحالة الشقيقة (زي OAuth tokens لكل MCP server) تفضل موجودة.
3. بيحفظ الـ token المُدوَّر بتاع المستهدف في النسخة الاحتياطية بتاعته.
4. بيعيد كتابة حقل `oauthAccount` في `~/.claude.json` بشكل ذرّي.
5. بيثبّت اللابل النشط الجديد وبيمسح لقطات الاستخدام القديمة، كل ده قبل ما القفل يتحرّر، عشان أي crash عمره ما يسيب الـ credential المثبّت واللابل النشط بيأشّروا على حسابات مختلفة.

لأن كل الـ sessions بتاعت البروفايل الافتراضي بتشارك نفس الـ credential الحي، تبديل واحد بينقل كل session في نفس الوقت، والـ flock بالإضافة لإعادة فحص تحت القفل بيمنع الـ hooks المتسابقة من إنها تحرق حسابين.

### التبني في المكان

الـ claude session اللي شغّالة بتعمل poll لمخزن الـ credential بتاعها بين الطلبات: على macOS بتعيد قراءة الـ keychain عن طريق كاش قصير وبتقارن الـ access tokens؛ على Linux بتشوف الـ mtime بتاع ملف الـ credentials وبتفرّغ كاشات الـ token بتاعتها عند التغيير. النتيجة النهائية إن الـ credential اللي اتبدّل بيتبنّاه كل session شغّالة خلال حوالي 30 ثانية على macOS وفي الطلب اللي بعده مباشرة على Linux، من غير أي إعادة تشغيل. عشان كده التبديل العادي مابيكتبش marker ومابيسببش respawn. الـ session بتكمّل عادي على الحساب الجديد. الـ `/usage` جوّا الـ session بيشارك نفس كاشات الـ token، فعرض الحساب بتاعه بيتقلب مع التبني.

### انتظار الـ pool المستنفد والإكمال التلقائي

بس لما كل حساب في الـ pool يعدّي حدوده الـ Stop hook بيكتب respawn marker (الـ schema بتاع الـ marker بيتطلّب timestamp اسمه `waitUntil`؛ والتبديل العادي عمره ما يقدر يطلّع واحد). الـ supervisor بيشوف الـ marker، وبيبعت SIGTERM للـ child بتاعه عند حدود الـ turn المُثبَّتة أصلاً (الـ Stop hook بيشتغل بعد ما الـ transcript يكون على الديسك و claude يكون خامل، فمفيش حاجة بتضيع)، وبيرجّع التيرمينال لحالته، وبيوريّك عدّاد تنازلي لأقرب reset، وبعدين بيعيد تشغيل `claude --resume <session-id>` على الحساب اللي رجع. Ctrl-C أثناء العدّاد التنازلي بيكمّل على طول. الانتظار التلقائي محدود بـ `policy.maxWaitMs` (الافتراضي ساعة واحدة)؛ بعد كده القرار بيبلّغ إن الـ pool مستنفد بدل ما ينتظر.

### تايمر الفحص الدوري

الـ hooks بتشتغل بس عند حدود الـ turn، و turn واحد طويل من نوع agentic ممكن يحرق نافذة من سليمة لمستنفدة من غير أي حدود. عشان كده `init` كمان بيثبّت timer دوري (launchd agent على macOS، و systemd user timer على Linux) بيشغّل `tokenmaxxing check` كل 180 ثانية بغض النظر عن نشاط الـ turn.

### هوك SessionStart

بيشغّل نفس التقييم لما الـ session تبدأ أو تكمّل، عشان الـ session الجديدة تبدأ على الحساب الصح. فترة التهدئة اللي بعد التبديل بتخلّيه عملية لا-فعل صحيحة بعد الـ respawn على طول.

## إزاي بيتقرّر التبديل [#how-switching-decides]

القرار ليه طبقتين: بوابة انخراط، وبعدين مسار greedy أو hard.

### الانخراط

تحت `policy.greedySessionFloor` (الافتراضي 50، كنسبة مئوية من نافذة الـ session بتاعت الـ 5 ساعات)، القرار مابيشتغلش خالص. الـ session الجديدة بتركب حسابها. أول ما نافذة الـ session النشطة تستخدم 50%، أو أي bar صعب يتعدّى، القرار بينخرط.

### شرايط الفرز

العتبات دي شرايط فرز، مش الزناد للهلع:

- `thresholds.session`: 95. الـ reset بتاع الـ 5 ساعات رخيص إنك تستناه، فنافذة الـ session بتبدّل بعيد بدري.
- `thresholds.weekly`: 98. الـ bar الواحد ده بيغطّي الإجمالي بتاع الـ 7 أيام وكمان كل حد أسبوعي لكل موديل. الحصة الأسبوعية إما تستخدمها أو تخسرها، فبتتصفّى قريّب من النهاية.

الاتنين تحت 100 بشكل مقصود: المساحة الفاضية هي الميزانية عشان توصل لحدود turn نضيفة (بالإضافة لغاية turn واحد من تأخير التبني على macOS) قبل ما الحساب يوصل لحده فعلاً. نفس الشرايط بتفرز مرشحي التبديل: أي حساب عدّى أي bar من بتوعه مش هدف صالح. الزناد والفرز بيستخدموا دايمًا نفس الشرايط الفعّالة (العتبات ناقص `policy.projectionMargin`)، لأن فرز أرخى من الزناد هيوقّع التبديلات على حسابات الزناد بيرجع يعلّم عليها على طول، وده بيخلّي الـ pool يروح ويجي زي البينج بونج.

### الهدف: ضغط الإيقاع

من بين الحسابات القابلة للاستخدام، الهدف هو اللي متأخّر أكتر عن الإيقاع الأسبوعي بتاعه: أعلى **ضغط إيقاع**، اللي معرّف كنسبة النسبة المئوية الأسبوعية المتبقية مقسومة على الوقت لحد الـ reset الأسبوعي بتاع الحساب ده. الحساب اللي على وشك يخسر أكبر حصة بيكسب. التعادل بيتحل لأقرب انتهاء أسبوعي، وبعدين لأقل استخدام على مدار 7 أيام.

كل حاجة بتشتغل من نوافذ مخزّنة في الكاش على شكل UTC epochs مطلقة، فاللقطة القديمة برضه بتتحل صح: الـ reset الأسبوعي اللي عدّى بيتم استقراؤه لقدّام بخطوات 7 أيام بالظبط، وأي نافذة عدّت الـ reset المخزّن بتاعها بتتحسب فاضية من جديد (عمرها ما سبب للتبديل، وعمرها ما سبب لإبقاء الحساب على الدكة).

### مسار greedy مقابل hard

- **مسار greedy** (منخرط، بس تحت كل bar): رتّب كل حساب، بما فيهم الحالي. لو الحساب الحالي كسبان أصلاً أو متعادل، ماتعملش حاجة. غير كده بدّل للحساب الأحسن بشكل قاطع. عمره ما بينتظر وعمره ما بيركن بدري. الحساب الحالي القابل للاستخدام مابيتبدلش بانتظار. لأن الحساب الحالي بيتم ترتيبه هو كمان، المسار التلقائي و `tokenmaxxing switch` لوحده الاتنين idempotent: التقييم بشكل دوري بيتقارب على الحساب الصح وبعدين بيفضل مكانه.
- **مسار hard** (اتعدّى bar): بدّل بعيد لأحسن مرشح قابل للاستخدام. لو طلع الـ refresh token بتاع مرشح ميّت، بيتعلّم عليه إنه محتاج إعادة مصادقة وبيتجرّب المرشح اللي بعده. لو مفيش حاجة قابلة للاستخدام، منطق انتظار الاستنفاد بيشتغل؛ بس المُنادي اللي يقدر فعلاً يوقّف الـ session (الـ Stop hook المُشرَف عليه) هو اللي مسموح له إنه يركن بدري على حساب لسه متحجوب بس هيرجع أقرب.

### حدود لكل موديل

`policy.switchModels` (الافتراضي `["fable"]`) بيحدّد عيلات الموديلات اللي حدها الأسبوعي لكل موديل يقدر يشغّل تبديل. المطابقة بتكون بـ family token، عمرها ما بالنص المعروض بالظبط: أسماء عرض الموديلات بتتغيّر ("Fable" بقت "Fable 5")، وبوابة قايمة على النص المطابق بالظبط مرة عطّلت التبديل لكل موديل بالكامل من غير ما حد يحس. قاعدتين أمان مرتبطين:

- الموديل النشط المجهول بيبوّب كل عيلة متضبطة. بعد التبديل على طول لما اللقطات تتمسح، الجهاز اللي من غير واجهة ممكن يشتغل وهو أعمى عن الموديل؛ معاملة المجهول كإنه من غير قيود مرة سابت حساب قاعد على حد Fable بتاعه ساعات من غير ما حد ياخد باله.
- فرز المرشحين بيحسب كمان الحدود لكل موديل المُبوَّبة، فالـ pool اللي كل حساب فيه حرق حد Fable بتاعه مابيعملش round-robin.

### فترة التهدئة

فترة تهدئة 45 ثانية بعد التبديل بتبوّب المسار التلقائي. الـ statusline tee بيتوقف نفس الـ 45 ثانية بعد التبديل (التبني بياخد لغاية 30 ثانية على macOS)، فأي تقييم أبكر كان هيشتغل على بيانات التبديل نفسه أبطلها. السيناريو ده بالظبط مرة طلّع loop respawn من A لـ B وراجع. `tokenmaxxing switch` اليدوي مابيتأثرش بفترة التهدئة.

## الإعدادات

الإعدادات JSON في `~/.config/tokenmaxxing/config.json`. كل حقل اختياري؛ القيم الافتراضية بتتطبّق لكل حقل.

```json
{
  "thresholds": { "session": 95, "weekly": 98 },
  "policy": {
    "projectionMargin": 0,
    "greedySessionFloor": 50,
    "switchModels": ["fable"],
    "usagePollTtlMs": 90000,
    "maxWaitMs": 3600000
  }
}
```

- `thresholds.session` / `thresholds.weekly`: شرايط الفرز الموصوفة فوق.
- `policy.projectionMargin`: بيتطرح من الشرطين عشان يكوّن الشرايط الفعّالة.
- `policy.greedySessionFloor`: نسبة استخدام الـ session اللي عندها التقارب الـ greedy بينخرط.
- `policy.switchModels`: عيلات الموديلات اللي حدها الأسبوعي لكل موديل بيبوّب التبديل (المدخلات بتتحول لحروف صغيرة عند التحميل).
- `policy.usagePollTtlMs`: قد إيه الـ poll بتاع `/usage` لكل موديل بيفضل حديث.
- `policy.maxWaitMs`: حد الانتظار التلقائي للـ pool المستنفد.

`tokenmaxxing config` بيوريّك الإعدادات الفعّالة مع مصادرها؛ `config set`/`unset` بيعدّلوا المفاتيح المنقّطة؛ `config tidy` بيشيل المفاتيح المجهولة.

## تخزين الـ credentials ونموذج الأمان

كل الحالة موجودة في `~/.config/tokenmaxxing/`. عمليات الإدخال والإخراج للـ credential بتعدّي عن طريق واجهة مخزن واحدة بتتحدّد حسب المنصة؛ مواقع الاستدعاء عمرها ما بتتفرّع حسب المنصة.

**macOS**: الـ credentials موجودة في الـ login keychain كعناصر generic-password، مطابقة للمكان اللي Claude Code نفسه بيحطها فيه. العنصر الحي هو اللي claude بيقراه؛ النسخة الاحتياطية بتاعت كل حساب في الـ pool بتتركن كعنصر keychain خاص بيها `tokenmaxxing-cred-<uuid8>`. مفيش حاجة نص عادي على الديسك. القراءات بتستخدم `security find-generic-password -w` (السر بيظهر بس على stdout)؛ الكتابات بتمرّر سطر `add-generic-password` لـ `security -i` عن طريق stdin عشان السر عمره ما يظهر في argv بتاع أي عملية. الوضع التفاعلي عنده line buffer حوالي 4 KB، فالـ blobs الكبيرة بترجع لكتابة argv. ده سبب واحد إن العناصر المركونة بتخزّن بس كائن OAuth الأدنى.

**Linux**: Claude Code بيخزّن الـ credentials كملف نص عادي 0600، و tokenmaxxing بيمشي على نفس النموذج: الملف الحي هو `.credentials.json` بتاع claude نفسه، والنسخ الاحتياطية المركونة ملفات ذرّية 0600 تحت `~/.config/tokenmaxxing/creds/` في مجلد 0700. الذرّي هنا معناه اكتب لملف مؤقت، اعمل fsync، وبعدين rename: القارئ المتزامن بيشوف دايمًا ملف قديم كامل أو جديد كامل، عمره ما جزئي.

قواعد الأمان اللي التبديل بيفرضها:

- **الحصاد عن طريق المالك الحقيقي.** قبل التبديل، بيتم تحديد المالك الفعلي للـ credential الحي عن طريق سؤال الـ API الـ token ده تابع لأنهي منظمة (`fetchTokenOrg` على الـ OAuth roles endpoint)، عمره ما بالثقة في اللابل النشط المخزّن، اللي ممكن يتغيّر. لابل متغيّر مرة خلّى حصاد حساب يكتب فوق النسخة الاحتياطية الوحيدة بتاعت حساب تاني. لو الـ credential الحي تابع لحساب برّه الـ pool، التبديل بيرفض تمامًا بدل ما يدهس عليه.
- **قسم حرج واحد.** الحصاد، وتثبيت الـ credential الجديد، والنسخة الاحتياطية للـ token المُدوَّر بتاعه، وتبديل الحساب في `~/.claude.json`، وتثبيت اللابل النشط كلهم بيحصلوا جوّا نفس القسم المقفول.
- **التشابك مع تحديث claude نفسه.** الـ session اللي قربت تنتهي ممكن تدوّر الـ token بتاعها في أي لحظة، فكتابة الـ credential كمان بتاخد قفل التحديث بتاع Claude Code (على قد الإمكان، مع استرجاع للقفل القديم و timeout محدود).
- **المِنَح الميتة بتتدهور بنظافة.** التحديث اللي بيرجع `invalid_grant` بيعلّم على الحساب ده إنه محتاج إعادة مصادقة وبيحفظ العلامة قبل ما الخطأ ينتشر، فحلقات إعادة المحاولة بتصغّر مجموعة المرشحين وبتنتهي. `tokenmaxxing auth` بيصلّح الحساب المعلّم عليه في مكانه، وبيرفض تسجيل دخول بيوقع على حساب مختلف عن اللي بيتصلّح.
- **مفيش تسجيل للـ tokens.** الـ tokens عمرها ما بتظهر في اللوجات، أو الأخطاء، أو المخرجات. أجسام الأخطاء من endpoints الـ token والاستخدام عمرها ما بتتعرض خام؛ بس مجموعة حقول مسموح بيها هي اللي بتفضل، لأن جسم فشل token endpoint ممكن يردّد مادة الطلب.
- **نظافة الـ probe.** أي `claude` probe بيتطلّع بينضّف الـ 8 متغيرات بيئة اللي claude بيحترمها قبل بحثه في الـ keychain (`ANTHROPIC_API_KEY`، `CLAUDE_CODE_OAUTH_TOKEN`، `CLAUDE_SECURESTORAGE_CONFIG_DIR`، وهكذا)، عشان الـ probe عمره ما يتنسب للحساب الغلط.

## ملاحظات المنصة: macOS مقابل Linux

| | macOS | Linux |
|---|---|---|
| الـ credential الحي | عنصر generic-password في الـ login keychain | ملف `.credentials.json` بصلاحية 0600 |
| الـ credentials المركونة | عناصر keychain لكل حساب | ملفات 0600 في مجلد 0700 |
| التبني بعد التبديل | خلال حوالي 30 ثانية (كاش قراءة الـ keychain) | الطلب اللي بعده (poll لـ mtime الملف) |
| الفحص الدوري | launchd agent، كل 180 ثانية | systemd user timer، كل 180 ثانية |
| مخزن تسجيل الدخول المعزول | خدمة keychain باسم مساحة مبني على hash لكل مجلد إعدادات | ملف جوّا مجلد الإعدادات المعزول |

تفصيلتين خاصين بـ Linux يستاهلوا تعرفهم: claude بيحدّد مجلد الـ credential بتاعه من `CLAUDE_SECURESTORAGE_CONFIG_DIR` الأول (وبعدين `CLAUDE_CONFIG_DIR`، وبعدين `~/.claude`)، و tokenmaxxing بيطابق التحديد ده بالظبط عشان الاتنين عمرهم ما يختلفوا. وبناءات الـ OS الاتنين لنفس نسخة claude بينسّقوا ساعات الـ reset بتاعت `/usage` بشكل مختلف (واحد بيستخدم رابط `" at "`، والتاني فاصلة)؛ الـ parser بتاع tokenmaxxing بيقبل الشكلين دول بالظبط وبيسجّل في اللوج، بدل ما يخمّن، لو لقى أي شكل تالت.

على macOS، قيد واحد بصراحة: `init` و `add` بيلمسوا الـ keychain بشكل تفاعلي عن قصد، عشان أول وصول لـ `security` مايكونش بارد جوّا hook من غير واجهة.

## الـ statusline

tokenmaxxing بيرسم الـ statusline بتاع Claude Code بشكل أصلي (وهو بيعمل tee للـ usage feed). مبدأ التصميم: الحصة بتتحمل في اللون، مش الأرقام. سطر واحد، مثلاً:

```
tm-wt-demo Fable 5 (high) +156/-23  ◆ 𝒇 2h 1d  ◇ 19h  ◇ 𝒇 2d  ◇ full  ✗ ?
```

- كل window token هو الوقت لحد الـ reset بتاعه، متلوّن على تدرّج مستمر من الأخضر للأصفر للأحمر حسب النسبة المستخدمة (truecolor لما التيرمينال يدعمه، متدرّج على مكعّب الـ 256 لون غير كده). التدرّج بيتثبّت عند أخضر خالص لـ 0، وأصفر عند 75، وأحمر عند 95 وفوق، عشان نطاقات الخطورة القديمة تفضل موجودة كمراسي للتدرّج.
- اسم الموديل بيتلوّن حسب امتلاء نافذة السياق على نفس التدرّج.
- `◆` أخضر بيتصدّر نوافذ الحساب النشط؛ كل حساب مركون بياخد `◇` سماوي خاص بيه (`✗` أحمر لو محتاج إعادة مصادقة). الحسابات بتترتّب حسب أقرب reset جاي.
- لكل موديل بيجي الأول في كل بلوك كحرف أولاني ملوّن مجرّد: Fable بيتعرض `𝒇`؛ العيلات التانية بتستخدم أول حرف بحروف كبيرة، دايمًا مطابق للعيلة.
- الحساب المركون اللي ماتلمسش بيتعرض `full` أخضر. الاستخدام المقاس بـ reset مجهول بيتعرض `?` ملوّن، والحد لكل موديل غير المقاس على موديل مبوّب بيتعرض `𝒇?` من غير لون. اللي مش متقاس عمره ما المفروض يبان آمن.
- العدّادات التنازلية للـ reset بتوريّ أكبر وحدة بس، عمرها ما "now" أو "0m"؛ النافذة اللي مالهاش reset جاي بتتعرض `0` أخضر (فاضية من تاني).
- اسم الـ basename بتاع الـ git worktree المرتبط بيتصدّر السطر؛ الـ checkout الرئيسي مابيعرضش حاجة هناك. الكشف بيقرا نظام الملفات عشان يدوّر على ملف `.git` وعمره ما بيطلّع عملية git فرعية.
- لو `NO_COLOR` متضبط، السطر بيرجع لصيغة رقمية ملزوقة (`2h5` معناه بيعمل reset خلال ساعتين، 5% مستخدمة؛ `ctx 42` لامتلاء السياق). من غير لون، النافذة المستنزفة مايصحّش تبان جديدة.

مهام الـ subagent بتاخد صفوف لوحة خاصة بيها عن طريق واجهة الـ subagentStatusLine بتاعت claude: صف واحد لكل مهمة نشطة، اسم العيلة متلوّن حسب امتلاء السياق بتاع المهمة دي.

## دعم Codex

نفس التجميع بيشتغل مع Codex CLI بتاع OpenAI، مقابل حسابات اشتراك ChatGPT بتاعتك:

```sh
tokenmaxxing init --codex   # استورد تسجيل دخول codex الحالي بتاعك + ثبّت الـ codex supervisor و Stop hook
tokenmaxxing add --codex    # سجّل دخول حساب تاني، معزول: تسجيل دخولك الأساسي مايتلمسش
codex                       # استخدم codex زي العادة
```

الـ Codex pool حالة متوازية بالكامل: index حسابات خاص بيه، ملفات credential مركونة خاصة بيه (ملفات 0600 على المنصتين، لأن مخزن codex نفسه ملف نص عادي)، قفل خاص بيه، timestamp آخر تبديل خاص بيه. مفيش حاجة بتتشارك مع الـ Claude pool غير كود سياسة القرار.

### ليه الـ hot-swap مستحيل على Codex

عملية codex اللي شغّالة بتمسك auth manager واحد في الذاكرة وبترفض صراحة إنها تعيد تحميل `auth.json` لما يبقى بيسمّي حساب مختلف. مفيش file watcher ومفيش poll للـ credential لكل طلب، فالـ credential اللي اتبدّل تحت codex شغّال ببساطة عمره ما بيسري مفعوله على الـ inference. إعادة التشغيل هي التبديل: `codex resume <session-id>` بيكمّل الـ transcript المحلي على أي حساب `auth.json` ماسكه دلوقتي.

tokenmaxxing بيتعامل مع ده عن طريق codex supervisor shim: الـ Stop hook بيشغّل نفس قرار ضغط الإيقاع الـ greedy عند كل حدود turn، ولما بيبدّل، بيكتب marker بيخلّي الـ supervisor يبعت SIGTERM للـ session عند الحدود المُثبَّتة ويعيد تشغيل `codex resume <session-id>` على الحساب الجديد، والـ transcript سليم. لأن كل تبديل codex هو إعادة تشغيل ظاهرة، مسار codex الـ greedy بيحمل هامش تحسين 1.2x: المُتحدّي لازم يتفوّق على ضغط الإيقاع بتاع الحساب الحالي بـ 20%، مش بشعرة. مسار الـ hard (bar اتعدّى) بيتجاهل الهامش. كمان مفيش عدّاد تنازلي للـ pool المستنفد بالنسبة لـ codex. مفيش حاجة تقدر توقّف codex session، فالـ codex pool المستنفد بالكامل بيفضل مكانه.

ميكانيكيات تانية خاصة بـ codex:

- الاستخدام بيتقرا من GET مصادَق عليه مجاني على الـ rate-limit endpoint بتاع codex نفسه (نفس الاستدعاء اللي `/status` بتاع الـ CLI بيعمله): نسب مئوية بالإضافة لأوقات reset مطلقة بالـ epoch، النوافذ الإجمالية والحدود لكل موديل على حد سوا. تصنيف النافذة بيتحدّد بالمدة، عمره ما بالموضع، لأن الخطط الحالية ممكن مايبقاش عندها نافذة 5 ساعات خالص والنافذة الأسبوعية بتقعد في الخانة الأساسية.
- الـ refresh tokens بتاعت Codex بتتدوّر، وإعادة استخدام واحد اتبدّل بيقتل عيلة المنحة كلها. كل تدوير بيتحفظ في اللحظة اللي بيرجع فيها، والحساب النشط بيتاخد منه عيّنة بس عن طريق الـ blob الحي (عمره ما نسخة مركونة قديمة)، وملفات الحضور لكل session بتضمن إن الحساب اللي شغّال في session شقيقة حية عمره ما يبقى هدف تبديل وعمره ما الـ token المركون بتاعه يتحدّث.
- Codex بيتطلّب مخزن الـ credential الملف: `init --codex` بيفشل بسرعة لو مخزن الـ keyring مثبّت، و `add --codex` بيكتب إعداد وضع الملف في الـ home المعزول بتاع الإعداد الأولي عشان تسجيل الدخول ينزل قابل للحصاد.
- خطوة يدوية واحدة: codex بيتخطّى الـ hooks اللي ماتقالوش يثق فيها. بعد `init --codex`، افتح codex مرة وثِق في الـ tokenmaxxing Stop hook عن طريق `/hooks`، وإلا التبديل التلقائي بيفضل خامل في صمت. `init --codex` بيطبع التذكير ده.

## جسر Slack: xx serve

`tokenmaxxing serve` بيشغّل daemon محلي لـ Slack عن طريق Socket Mode، من غير حاجة لـ URL عام. الإعداد:

```sh
tokenmaxxing serve setup                    # بيطبع manifest التطبيق، وبيطلب الـ token الاتنين
tokenmaxxing serve link <channel-id> <repo> # اربط قناة بـ checkout لريبو
tokenmaxxing serve                          # شغّل الـ daemon
```

منشِن البوت في قناة مربوطة وهيفتح Claude Code session للـ thread ده، في الـ repo checkout المربوط. كل رسالة thread بتشغّل `query()` واحدة من الـ Agent SDK مع `resume`، عمره ما query بث مستمر، عشان `ensureBestAccount()` بيعيد تقييم الـ pool في كل turn لوحده والـ daemon يقدر يعمل restart من غير ما يخسر الـ threads (سجلات الـ thread دايمة؛ الـ daemon بيعيد الاشتراك فيها عند الإقلاع).

سلوك ملحوظ:

- **البث**: الردود بتتبثّ بشكل أصلي في Slack، مع task cards للتفكير وتشغيل الأدوات، وكود محاط برندره بتظليل، وكارت "Turn" ختامي بالتكلفة والمدة، ورسالة Slack جديدة بتتفتح كل ما تشغيل أداة يقطع النص المبثوث، عشان الـ turn يتقرا كرسايل منفصلة حوالين تشغيل الأدوات. استدعاءات TodoWrite بتحدّث كارت checklist ثابت واحد في مكانه.
- **الصلاحيات**: `permissionMode` لكل رابط بيكون الافتراضي `acceptEdits`؛ `--yolo` (الاسم المختصر `--dangerous`) بيخلّي الرابط يختار `bypassPermissions`. الحوارات التفاعلية ممنوعة في الـ turns المُمرَّرة. مفيش حد يقدر يجاوب واحدة عن طريق Slack، فالموديل بيسأل بالكلام وردّك في الـ thread هو الـ turn اللي بعده. فيه skill إضافي مدمج بيعلّمه إنه يعمل tag للطالب وينهي الـ turn لما يحتاج قرار.
- **أوامر السلاش**: رسالة thread نصها بعد التجريد بيبدأ بـ `/` بتشتغل كـ claude slash command. الـ composer بتاع Slack بياكل الرسايل اللي بتبدأ بـ `/`، فاستخدم صيغة المنشِن الأول (`@bot /usage`) أو مسافة في الأول.
- **الإغلاق السلس**: SIGTERM/SIGINT بيصرّف: الـ turns الجديدة بتتشال بصوت عالي، والـ turns اللي شغّالة بتاخد لغاية 5 دقايق، والـ claude child بيشتغل منفصل في مجموعة العمليات الخاصة بيه عشان Ctrl-C من التيرمينال مايقدرش يقتله قبل ما التصريف يحافظ على الـ turn.
- **تنظيف الـ thread**: لما تقوله الشغل خلص، الموديل بينادي أداة `finish_thread` جوّا العملية؛ بعد ما الـ turn يخلص تمامًا، الـ daemon بيشيل سجل الـ thread، وبيلغي الاشتراك، وبيبعت تأكيد واحد. أي منشِن جديد بيبدأ session جديدة.
- **نظافة الأخطاء**: أخطاء الـ turn بتبعت نص مقصوص رسالة بس، عمره ما أجسام أخطاء خام.

## واجهة الـ Agent SDK

نقطة الدخول البرمجية للباكدج (`exports["."]` بيأشّر على `src/sdk.ts`) بتربط tokenmaxxing مع الـ Claude Agent SDK للـ agents اللي بتبنيها على حساباتك المجمّعة. تطبيقك لازم يشتغل تحت Bun (tokenmaxxing بيشحن كود TypeScript وبيستخدم `bun:ffi`).

```ts
import { query } from "@anthropic-ai/claude-agent-sdk";
import { ensureBestAccount, pooledOptions, stopHookCheck } from "tokenmaxxing";

await ensureBestAccount(); // run the switch decision before the spawn

for await (const message of query({
  prompt: "...",
  options: {
    ...pooledOptions(), // pinned real claude + scrubbed env
    hooks: { Stop: [{ hooks: [stopHookCheck] }] }, // re-decide at every turn boundary
  },
})) {
  // capture the session id from the init message for `resume` across swaps
}
```

الـ Agent SDK بيطلّع claude subprocess لكل `query()` وبيقرا الـ credentials مرة واحدة عند الإطلاق. مفيش statusline، مفيش hot-swap في نص الـ query، فالتكامل بيتحدّد بالحدود:

- `ensureBestAccount()` هو نفس القرار بالظبط اللي الـ CLI hooks والـ timer بيشغّلوه (الشرايط، ضغط الإيقاع، فترة التهدئة، كله كود مشترك)، عمره ما استباقي: الـ SDK session عمرها ما تقدر تتوقّف لعدّاد تنازلي بسبب الاستنفاد.
- `pooledOptions()` بيثبّت `pathToClaudeCodeExecutable` على الـ claude binary الحقيقي (عمره ما الـ supervisor wrapper) وبيوفّر `env` بديل كامل مع تنضيف كل تجاوز credential محيطي. بيفشل بسرعة لو `CLAUDE_CONFIG_DIR` أو `CLAUDE_SECURESTORAGE_CONFIG_DIR` متضبط في بيئة تطبيقك: على Linux التبديل هيكتب الـ credential الحي في المكان اللي دول بيأشّروا عليه بينما الـ subprocess المنضّف بيقرا المخزن الافتراضي، وده عدم تزامن صامت لحساب غلط.
- `stopHookCheck` بيعيد تشغيل القرار عند حدود الـ turn؛ أي تبديل بيوقّعه بيسري مفعوله في الإطلاق اللي بعده. بيمسك أخطاءه بنفسه (وبيسجّلها في stderr واللوج) بدل ما يرميها تاني، لأن استثناء hook مش متعامَل معاه ممكن يقطع الـ agent، وإجهاض turn بسبب فحص تبديل باظ بيكلّف أكتر من إنك تكمّل على الحساب الحالي.

`sdk.ts` مابيستوردش أي حاجة من الـ Agent SDK نفسه؛ قيمه بتنتشر هيكليًا في خيارات الـ SDK.

## الاستخدام الشخصي وشروط الخدمة [#personal-use-and-terms-of-service]

tokenmaxxing بيجمّع حسابات بتملكها، في sessions و agents بتشغّلها بنفسك. الصياغة دي مقصودة: Anthropic مابتسمحش لمنتجات طرف تالت إنها تقدّم تسجيل دخول claude.ai أو حدود معدل claude.ai، وده بيشمل الـ agents المبنية على الـ Agent SDK. ماتشحنش واجهة الـ SDK المجمّعة، ولا أي حاجة مبنية عليها، لأطراف تالتة. tokenmaxxing كمان بيفضل عن قصد على مسار `/usage` بواسطة الـ CLI لبيانات الحصة بدل ما يعيد تنفيذ OAuth أو يعمل proxy لترافيك الـ API: هو مش proxy، والـ OAuth endpoints الوحيدة اللي بيلمسها هي منحة التحديث القياسية المستخدمة أثناء التبديل وفحص هوية للقراءة بس (الـ roles endpoint) اللي بيتأكد الـ token تابع فعلاً لأنهي حساب.

## قيود بصراحة

- **turn واحد بارد.** كاش الـ prompt نطاقه المنظمة، فأول turn على حساب جديد بيرفع السياق من تاني مرة واحدة.
- **تلعثم توقف الاستنفاد.** بس الـ pool المستنفد بالكامل هو اللي بيوقّف الـ session للعدّاد التنازلي؛ أي حاجة تتكتب في الجزء ده من الثانية بتضيع.
- **تأخير التبني.** على macOS أول turn خلال حوالي 30 ثانية من التبديل ممكن لسه يحسب على الحساب القديم؛ المساحة الفاضية في الشرايط بتمتصه.
- **نطاق تأثير مشترك.** كل الـ sessions بتاعت البروفايل الافتراضي بتشارك credential حي واحد، فالتبديل بينقلهم كلهم مع بعض (كل واحد بيتبنّى في مكانه).
- **credentials نص عادي على Linux.** Claude Code نفسه بيخزّن credentials الـ Linux كملف نص عادي 0600؛ النسخ المركونة بتاعت tokenmaxxing بتمشي على نفس النموذج.

## حل المشاكل والأسئلة الشائعة

**`claude` مش باين إنه متحكوم عليه.**
شغّل `tokenmaxxing doctor`. الـ shim لازم يكسب في تحديد الـ PATH؛ اتأكد إن سطر `# tokenmaxxing PATH` في الـ shell rc بتاعك بيأشّر على مجلد الـ bin الحالي وقاعد قدّام الـ claude الحقيقي. `doctor` كمان بيحذّر من `alias claude=...` أو دالة shell اسمها `claude()` بتحجب الـ wrapper، ومن الـ aliases اللي بتشغّل claude binary بمسار مطلق (دي بتتخطّى الـ supervisor بالكامل).

**التبديل التلقائي عمره ما بيشتغل على Codex.**
Codex بيتخطّى الـ hooks اللي ماتقالوش يثق فيها. افتح codex، وشغّل `/hooks`، وثِق في الـ tokenmaxxing Stop hook. الثقة بتتسجّل على hash الـ hook، فلازم تتمنح من تاني لو الـ hook اتعدّل في أي وقت.

**حساب بيوريّ `✗` أحمر في الـ statusline.**
الـ refresh token بتاعه ميّت (اتلغى أو اتدوّر من تحت النسخة الاحتياطية بتاعته). شغّل `tokenmaxxing auth <sel>` عشان تعيد مصادقته في مكانه؛ الأمر بيقولك تسجّل دخول بأنهي إيميل وبيرفض تسجيل دخول بيوقع على حساب مختلف.

**ليه مابيبدّلش للحساب اللي عنده أكبر حصة متبقية؟**
لأن ده مش الحساب الأكتر عرضة إنه يخسر حصة. الهدف هو الحساب المتأخّر أكتر عن الإيقاع الأسبوعي بتاعه: النسبة المتبقية مقسومة على الوقت لحد الـ reset الأسبوعي بتاعه. لو الكميات المتبقية متساوية بيرجع لأقرب انتهاء الأول، ولو الانتهاء متساوي لأكبر كمية متبقية الأول.

**بدّل دلوقتي والـ statusline لسه بيوريّ الحساب القديم.**
متوقّع لغاية حوالي 30 ثانية على macOS: الـ session اللي شغّالة بتتبنّى الـ credential اللي اتبدّل عند أول تحديث لكاش الـ credential بتاعها. الـ usage tee بيتوقف 45 ثانية بعد التبديل للسبب ده بالظبط.

**هل `status --force` بيكلّف حاجة؟**
أيوة، عن قصد: بيبعت طلب haiku محسوب أدنى لكل حساب عشان كل نافذة session بتاعت 5 ساعات تبدأ في اللحظة دي بدل ما تفضل خاملة، وبعدين ياخد عيّنة جديدة. `status` العادي و `watch` عمرهم ما بيعملوا ping؛ قراءات `/usage` مجانية. خلّي بالك إن الـ usage feed بتاع السيرفر ممكن يتأخّر عن النافذة اللي اتفتحت جديد من ثواني لدقايق، فالـ probe بعد الـ ping على طول ممكن لسه يوريّ الحالة اللي قبل الـ ping. `status` بيعرض ملاحظة بدل ما يدّعي إن الـ ping فشل.

**الـ `/usage` probe مارجّعش حاجة للحساب النشط.**
ده سلوك معروف في claude: لما جلب الاستخدام الداخلي بتاعه يفشل أو يتعمله rate-limit، `/usage` بيطبع بس إحصائيات الـ session المحلية من غير أسطر نسب مئوية. tokenmaxxing بياخد عيّنة الحساب النشط من دفعة الـ statusline وبيعمل probe بس للحسابات المركونة، بالظبط عشان يتجنّب ده.

**جلسات claude في الخلفية.**
الـ background daemon بتاع Claude بيطلّع الـ binary الحقيقي المُصدَّر بمسار مطلق، وبيتخطّى الـ PATH shims، فجلسات الخلفية مش متحكوم عليها. الـ hooks لسه بتشتغل عن طريق `settings.json`، وتبني الـ credential بالإضافة للـ timer الدوري بيغطّوا التبديل، بس مفيش respawn مدفوع بـ marker ليها.

**حاجة طلّعت كتير من العمليات مرة. ده لسه ممكن؟**
الـ supervisor بيحمل حراسات تكرار متعددة الطبقات ضد الفشل التاريخي ده بالظبط (wrapper قديم متثبّت كـ claude "الحقيقي"): حارس عمق في البيئة بيجهض عند 5 مستويات، ومحدّد لمعدل الإطلاق على الديسك، وفحوصات هوية بالـ realpath بترفض أي مرشح بيرجع لمجلد الـ bin بتاع tokenmaxxing نفسه، وفشل صريح (عمره ما مسح PATH صامت) لما مسار claude المتضبط مايبقاش موجود. `init` و `doctor` بيتأكدوا إن المرشح فعلاً هو claude عن طريق تشغيل `--version` قبل ما يثبّتوه.

**إلغاء التثبيت.**
`tokenmaxxing uninstall` بيشيل الـ supervisor shims، ومدخلات الإعدادات، والـ timer الدوري، وبيسيب حساباتك والـ credentials المركونة زي ما هي. بيشيل بس مدخلات الـ statusline اللي بيعرفها إنها بتاعته.
