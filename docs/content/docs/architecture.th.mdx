tokenmaxxing เป็นจุดเข้า (entry point) แบบเรียกได้หลายชื่อเพียงจุดเดียว (`src/main.ts`) ที่ทำหน้าที่เป็น supervisor ของ `claude` เมื่อถูกเรียกด้วยชื่อนั้น ให้บริการ shim ของฮุกและ statusline ผ่านคำสั่งย่อยภายใน และในกรณีอื่นก็ส่งต่อไปยัง CLI มันรันโดยตรงบน Bun แพ็กเกจ npm ส่งมาเป็นซอร์สโค้ด TypeScript ไม่ใช่ไฟล์ที่ผ่านการ build

ส่วนประกอบที่ทำงานอยู่:

## shim ของ supervisor

`init` เขียน shim ของเชลล์ 2 บรรทัดชื่อ `claude` ลงใน `~/.config/tokenmaxxing/bin/` และวางไดเรกทอรีนั้นไว้เป็นอันดับแรกใน PATH เมื่อคุณพิมพ์ `claude` shim จะรัน supervisor ซึ่งจะ spawn ไบนารี claude ตัวจริงโดยสืบทอด stdio และสแนปช็อตของเทอร์มินัลที่บันทึกด้วย `stty -g` มันเป็นเพียงตัวจัดการโปรเซสและเทอร์มินัลเท่านั้น ไม่เคยทำหน้าที่เป็นพร็อกซีให้ทราฟฟิก API และไม่เคยแตะต้อง token ที่กำลังส่งอยู่

การเรียกใช้ในโหมด print (`claude -p`, `--version`, `--help`) คำสั่งย่อยที่ไม่โต้ตอบ (`claude mcp`, `claude config` และอื่นๆ) และการ probe ของ tokenmaxxing เองจะส่งผ่านตรงๆ โดยไม่มีการจัดการเซสชัน สำหรับเซสชันแบบโต้ตอบ supervisor จะปักหมุด session id (โดยสร้างขึ้นใหม่ หรือใช้ตัวที่คุณส่งมาผ่าน `--session-id` / `-r` / `-c` ซ้ำ) เก็บแฟล็กการเปิดใช้งานของคุณไว้เพื่อให้การเปิดใหม่ในภายหลังสามารถเล่นซ้ำได้ จากนั้นจึงเฝ้าดูไฟล์ marker สำหรับ respawn ที่ผูกกับเซสชันนั้น

## การ tee ของ statusline

Claude Code จะส่งข้อมูลลิมิตอัตรา (`rate_limits.five_hour` และ `rate_limits.seven_day`) เข้าไปยัง stdin ของ statusline ในทุกเทิร์น tokenmaxxing เป็นเจ้าของช่อง statusline ดังนั้นตัวเรนเดอร์ของมันจึงทำหน้าที่เป็นฟีดการใช้งานแบบ push ที่ฟรีไปในตัว โดยในแต่ละจังหวะ (tick) มันจะ tee หน้าต่างยอดรวมพร้อมกับโมเดลที่ใช้งานอยู่ลงใน `usage.json` ลิมิตแยกตามโมเดลไม่ได้อยู่ใน stdin ของ statusline แต่มาจาก `claude -p '/usage'` เท่านั้น (ฟรี ไม่ใช้ token) ซึ่งจะถูก poll พร้อม TTL และแคชลงใน `model-usage.json` เมื่อโมเดลที่ใช้งานอยู่ถูกจำกัดความจุ

การ tee เป็นแบบเขียนเมื่อมีการเปลี่ยนแปลง (write-on-change) เมื่อตัวเลขไม่เปลี่ยนแปลง มันจะเพียงอัปเดต mtime ของไฟล์ ซึ่งทำหน้าที่เป็นสัญญาณชีพ (heartbeat) ของฟีด ความสดใหม่จะถูกตัดสินจาก mtime เสมอ ไม่ใช่จาก timestamp ที่ฝังอยู่ในไฟล์

## Stop hook และการสลับ

ที่ขอบเขตของทุกเทิร์น Stop hook จะรันการตัดสินใจสลับ (ดู [การตัดสินใจสลับทำงานอย่างไร](/th/switching)) เมื่อการสลับมีความจำเป็น มันจะเกิดขึ้นภายใต้ล็อกแบบเอ็กซ์คลูซีฟ `flock(2)` (ทำผ่าน `bun:ffi` เนื่องจาก macOS ไม่มีไบนารี `flock(1)` มาให้) และการเขียน credential ยังประสานล็อก (interlock) กับ refresh lock ของ Claude Code เองด้วย ภายในส่วนวิกฤต (critical section) การสลับหนึ่งครั้งจะ:

1. เก็บเกี่ยว credential สดปัจจุบันไปยังไฟล์สำรอง (parked backup) ของเจ้าของที่แท้จริง
2. ติดตั้ง credential ที่รีเฟรชใหม่ของบัญชีเป้าหมายเป็นตัวสด โดยรวมเข้ากับ blob สดที่มีอยู่เดิม เพื่อให้สถานะข้างเคียง (เช่น token OAuth ต่อเซิร์ฟเวอร์ MCP) ยังคงอยู่ (refresh token ที่หมุนเวียนแล้วของบัญชีเป้าหมายถูกบันทึกลงไฟล์สำรองของตัวเองไปแล้วในวินาทีที่การรีเฟรชคืนค่ากลับมา ภายใต้ flock แต่ก่อนถึงส่วนวิกฤตของ refresh lock นี้)
3. เขียนฟิลด์ `oauthAccount` ใน `~/.claude.json` ใหม่แบบอะตอมมิก
4. ยืนยันป้ายบัญชีที่ใช้งานอยู่อันใหม่และล้างสแนปช็อตการใช้งานที่เก่าค้าง ทั้งหมดก่อนที่ล็อกจะถูกปล่อย ไฟล์เหล่านี้ไม่สามารถเป็นอะตอมมิกต่อการล่มพร้อมกันได้ การล่มจึงอาจทิ้งสถานะกลางไว้ การสลับครั้งถัดไปจะหาเจ้าของที่แท้จริงของ credential สดโดยไม่พึ่งป้ายบัญชี และบันทึกความคลาดเคลื่อนที่ตรวจพบลง log

เนื่องจากทุกเซสชันในโปรไฟล์เริ่มต้นใช้ credential สดตัวเดียวกัน การสลับเพียงครั้งเดียวจึงย้ายทุกเซสชันพร้อมกัน และ flock พร้อมกับการตรวจสอบซ้ำภายใต้ล็อกช่วยป้องกันไม่ให้ฮุกที่แข่งกัน (racing hooks) เผาผลาญสองบัญชี

## การนำมาใช้ ณ ที่เดิม

เซสชัน claude ที่กำลังทำงานจะ poll ที่เก็บ credential ระหว่างคำขอ บน macOS มันจะอ่าน keychain ใหม่ผ่านแคชระยะสั้นและเปรียบเทียบ access token ส่วนบน Linux มันจะ stat ค่า mtime ของไฟล์ credential และล้างแคช token เมื่อมีการเปลี่ยนแปลง ผลลัพธ์สุทธิคือ credential ที่ถูกสลับจะถูกนำมาใช้โดยทุกเซสชันที่กำลังทำงานภายในประมาณ 30 วินาทีบน macOS และในคำขอถัดไปทันทีบน Linux โดยไม่ต้องรีสตาร์ทใดๆ นี่คือเหตุผลที่การสลับแบบธรรมดาไม่เขียน marker และไม่กระตุ้นให้เกิด respawn เซสชันเพียงแค่ดำเนินต่อบนบัญชีใหม่ `/usage` ภายในเซสชันใช้แคช token ชุดเดียวกัน ดังนั้นการแสดงบัญชีของมันจึงเปลี่ยนไปพร้อมกับการนำมาใช้

## การรอเมื่อพูลหมดและการกลับมาทำงานอัตโนมัติ

เฉพาะเมื่อทุกบัญชีในพูลเกินแถบ (bars) ของตัวเองแล้วเท่านั้น Stop hook จึงจะเขียน respawn marker (สคีมาของ marker กำหนดให้ต้องมี timestamp `waitUntil` การสลับแบบธรรมดาไม่มีทางสร้างมันได้) supervisor เห็น marker จึงส่ง SIGTERM ให้โปรเซสลูกที่ขอบเขตเทิร์นที่ยืนยันไปแล้ว (Stop hook รันหลังจากทรานสคริปต์อยู่บนดิสก์และ claude ว่างอยู่ ดังนั้นจึงไม่มีอะไรสูญหาย) คืนค่าเทอร์มินัล แสดงการนับถอยหลังไปยังการรีเซ็ตที่เร็วที่สุด แล้วจึงเปิด `claude --resume <session-id>` ใหม่บนบัญชีที่ฟื้นแล้ว การกด Ctrl-C ระหว่างนับถอยหลังจะกลับมาทำงานต่อทันที การรออัตโนมัติถูกจำกัดด้วย `policy.maxWaitMs` (ค่าเริ่มต้น 1 ชั่วโมง) หากเกินกว่านั้น การตัดสินใจจะรายงานว่าพูลหมดแทนที่จะรอต่อ

## ตัวจับเวลาตรวจสอบเป็นระยะ

ฮุกจะทำงานเฉพาะที่ขอบเขตเทิร์นเท่านั้น และเทิร์นแบบ agentic ที่ยาวเพียงเทิร์นเดียวสามารถเผาผลาญหน้าต่างจากสภาพดีจนหมดได้โดยไม่มีขอบเขตเลยแม้แต่ครั้งเดียว ดังนั้น `init` จึงติดตั้งตัวจับเวลาเป็นระยะด้วย (launchd agent บน macOS และ systemd user timer บน Linux) ที่รัน `tokenmaxxing check --if-due` ทุกหนึ่ง tick (`policy.checkIntervalMs` ค่าเริ่มต้น 60 วินาที) โดยไม่ขึ้นกับกิจกรรมของเทิร์น ตัวการตรวจสอบจะกำหนดจังหวะของตัวเองจากพื้นที่เหลือของบัญชีที่ใช้งานอยู่ ถ้ายังเหลือพื้นที่ถึงทุกแถบอยู่มากก็ประเมินทุกห้า tick และเมื่อใกล้แถบใดแถบหนึ่งก็ประเมินทุก tick (ดู [การตัดสินใจสลับทำงานอย่างไร](/th/switching))

## SessionStart hook

รันการประเมินแบบเดียวกันเมื่อเซสชันเริ่มหรือกลับมาทำงานต่อ เพื่อให้เซสชันใหม่เริ่มต้นบนบัญชีที่ถูกต้อง ช่วงพัก (cooldown) หลังการสลับทำให้มันเป็น no-op ที่ถูกต้องทันทีหลัง respawn
