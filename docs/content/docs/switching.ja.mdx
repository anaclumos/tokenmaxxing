title: 切り替えの判断方法
description: "エンゲージメント、スクリーニングバー、ペースプレッシャー、そしてグリーディパスとハードパス"
---

判断は2つの層からなります。エンゲージメントゲートと、それに続くグリーディパスまたはハードパスです。

## エンゲージメント

`policy.greedySessionFloor` (デフォルト80、5時間セッションウィンドウの使用パーセント) を下回っている間、判断はまったく実行されません。新しいセッションはそのアカウントに乗り続けます。アクティブなセッションウィンドウの使用率が80%に達するか、いずれかのバーを超えると、判断がエンゲージします。

## スクリーニングバー

しきい値はスクリーニングバーであり、パニックのトリガーではありません。

- `thresholds.session`: ラダーで、デフォルトは `[90]` の1段だけです。評価のたびにアクティブな段を1つ決めます。現在のアカウントも含め、プールのどれかのアカウントがまだ使用可能でいられる最も低い段です。`[50, 80, 95]` のような複数段のラダーでは、50未満のアカウントが1つでもあるうちはバーは50なので、50を超えた席はそのアカウントへ引き継ぎます。すべてのアカウントが50を過ぎるとバーは80へ上がり、どこも80を過ぎると95へ上がります。最上段が最終バーで、その先はウォール (後述) が引き継ぎます。5時間リセットは待つコストが低いため、プールは段ごとに消費されていき、どのアカウントも兄弟から大きく先行することはありません。
- `thresholds.weekly`: 98。この1つのバーが7日間の集計とすべてのモデルごとの週次上限の両方をカバーします。週次クォータは使い切らなければ失われるため、上限に近いところまで消費します。

どちらも意図的に100未満です。この余裕は、アカウントが実際に制限に達する前に、きれいなターン境界へ (加えて macOS では最大1ターンの採用ラグを見込んで) 到達するための予算です。同じバーが切り替え候補もスクリーニングします。いずれかのバーを超えたアカウントは有効なターゲットではありません。トリガーとスクリーニングは常に同じ有効バー (アクティブな段と週次バーから、それぞれ `policy.projectionMargin` を引いたもの) を使います。スクリーニングがトリガーより緩いと、トリガーが即座に再フラグするアカウントに切り替えが着地し、プールが行ったり来たりしてしまうためです。ある段が数えるのは、その段で使用可能なアカウントだけです。失効したグラント、使い切ったゲート対象のモデルごとの上限、サーバー側で確定した制限の強制は、バーを低いまま押しとどめる理由にはなりません。また段は、1回の評価の中でもリトライのたびにプールから読み直されます。Codex は最上段だけを読みます。再起動が Codex にとっての切り替えだからです。

## ターゲット: ペースプレッシャー

使用可能なアカウントの中で、ターゲットは自身の週次ペースから最も遅れているアカウントです。すなわち**ペースプレッシャー**が最も高いもので、これは残りの週次パーセントをそのアカウントの週次リセットまでの時間で割った値と定義されます。最も多くのクォータを失効させかけているアカウントが勝ちます。同点の場合は週次期限が最も早いもの、次に7日間使用量が最も低いものへとタイブレークします。

すべては絶対 UTC エポックとして保存されたキャッシュ済みウィンドウで動作するため、古いスナップショットでも正しく解決されます。すでに過ぎた週次リセットは正確な7日刻みで先へ外挿され、キャッシュ済みリセットを過ぎたウィンドウは新しく空とみなされます (切り替える理由にも、アカウントをベンチに置き続ける理由にもなりません)。

## グリーディパスとハードパス

- **グリーディパス** (エンゲージ済みだが、すべてのバー未満): 現在のアカウントを含むすべてのアカウントをランク付けします。現在のアカウントがすでに勝っているか同点なら、何もしません。そうでなければ厳密により良いアカウントへ切り替えます。決して待機せず、事前パークもしません。使用可能な現在のアカウントを待機と引き換えにすることはありません。現在のアカウントもランク付けされるため、自動パスと引数なしの `tokenmaxxing switch` はどちらも冪等です。定期的に評価すると正しいアカウントに収束し、その後はそのまま留まります。
- **ハードパス** (バーを超えた): 最良の使用可能な候補へ切り替えます。候補のリフレッシュトークンが失効していると判明したら、そのアカウントは再認証が必要としてフラグされ、次の候補が試されます。何も使用可能でなければウォール絞り出し (後述) が動き、すべての使用可能なアカウントがウォールに達したときにのみ枯渇待機ロジックが動きます。実際にセッションを一時停止できる呼び出し元 (スーパーバイズされた Stop フック) だけが、まだブロックされているが最も早く回復するアカウントへの事前パークを許可されます。

## ウォール

ハードパスが使用可能な候補を見つけられない (すべてのアカウントがスクリーニングバーを超えている) とき、自動判断はすぐにはパークしません。まず**ウォールバー** (`hardThresholds`、デフォルト100、各アカウントの実際のサーバー制限) に対して再評価します。セッションはまだウォール未満の間は席を保持して絞り出し、そうでなければ最良のまだウォール未満のアカウントへ切り替え (ペースプレッシャーによる同じランク付け)、すべての使用可能なアカウントが本当にウォールに達して初めてパークします。リフレッシュトークンが失効しているアカウントは、待機の対象とはせず、再認証のために脇に置きます。回復はウォールを基準に測られるため、5時間ウィンドウがリセットされたアカウントは、週次ウィンドウがまだスクリーニングバーを超えていても、再び絞り出しの対象になります。

これにより、各アカウントのクォータの最後の数パーセントが使われずに終わるのを防ぎます。ウォールの値は、判断がすでに使っている使用状況ソース (スーパーバイズされたインタラクティブセッションでは statusline の tee、ヘッドレス実行では `/usage` プローブ) から得られ、これは Claude の `/rate-limit-options` が表示するのと同じ数値なので、本当に上限に達したアカウントは検出されてスキップされます。1ターン分の超過は、次に判断が実行されるとき、つまり定期チェック、あるいはヘッドレス実行では次のスポーンまたは Stop 境界で捕捉されます。

`hardThresholds` はスクリーニングバーと同じように `policy.projectionMargin` を差し引くので、`thresholds` と同じ値に設定するとウォール絞り出しが無効になります。これは Claude 専用のパスです。引数なしの `tokenmaxxing switch` はキャッシュのみのパークを維持し、Codex は `hardThresholds` をまったく無視します。実行中の Codex はセッションの途中で切り替えられた認証情報を採用できないため、実際のサーバー制限に達するまで現在のアカウントに留まります (100 未満のカスタムウォールは Codex には適用されません)。

## モデルごとの上限

`policy.switchModels` (デフォルト `["fable"]`) は、モデルごとの週次上限が切り替えをトリガーできるモデルファミリーを指定します。マッチングはファミリートークンで判定し、正確な表示文字列は決して使いません。モデルの表示名は変動し (「Fable」は「Fable 5」になりました)、正確な文字列によるゲートはかつてモデルごとの切り替えを丸ごと無効にしてしまったことがあります。関連する2つの安全ルールがあります。

- 不明なアクティブモデルは、設定されたすべてのファミリーをゲートします。切り替えがスナップショットをクリアした直後、ヘッドレスなマシンはモデル不明で動作することがあります。不明を無制約として扱っていたために、あるアカウントが Fable 上限のまま何時間も気付かれずに留まったことがありました。
- 候補スクリーニングはゲートされたモデルごとの上限も数えるため、すべてのアカウントが Fable 上限を使い切ったプールはラウンドロビンしません。

## クールダウン

45秒の切り替え後クールダウンが自動パスをゲートします。statusline の tee も切り替え後の同じ45秒間は抑制されます (採用には macOS で最大30秒かかります)。そうしないと、より早い評価が切り替え自身によって無効化されたデータ上で走ってしまいます。まさにこのシナリオが、かつて A から B へ、そして戻る再起動ループを生み出しました。手動の `tokenmaxxing switch` はクールダウンの影響を受けません。

## 強制された制限

キャッシュ済みの数値は実態から遅れることがあります。ライブアカウントのモデルごとの上限は、稼働中のライブトークンに対する `/usage` プローブからしか得られず、セッションの負荷が高いとこのプローブは何も出力しないことがよくあります。サーバーが実際にターンを拒否すると、Claude Code はそのターンを API エラーで終了し、`Stop` の代わりに `StopFailure` フックを発火させます。tokenmaxxing はこのフックを `rate_limit` マッチャー付きでインストールし、フックはトランスクリプトの構造化されたエラー行 (Claude Code 自身が `isApiErrorMessage` と印を付けたのと同じ行) を読みます。`quotaLimits` ブロックは、ウィンドウ (`five_hour`、`seven_day`、またはモデルごとの種別) をサーバー側のリセット時刻とともに示します。`quotaLimits` を持たない Fable 上限の失敗は、クライアント自身のエラー表示と 429 のボディから判定します。モデルの書いた文章を読むことは決してありません。

フックはそのアカウントの強制されたウィンドウを100として記録し、サーバーの日付が付いたセッション制限または週次制限を、そのリセットまでアカウントに固定します。そのため、まだ使用量のサンプルがないアカウントでも、すぐに選び直されることはありません。フックはこの強制を、どのキャッシュ済みウィンドウよりも強い事実として判断へ渡し (切り替え後のクールダウンを飛び越え、引っかかったファミリーで候補をゲートし、決して席を保持しません)、ハードパスが切り替えを実行します。メインのターンが失敗したスーパーバイズ済みセッションでは、再起動マーカーも書き込みます。スーパーバイザーは新しいアカウント上で `--resume` を再起動し、継続用のプロンプトを1つ送信して、中断された作業を再開させます。サブエージェント内部での失敗は切り替えを行いますが再起動はしません (親のターンがまだ実行中のため)。スーパーバイズされていないセッションは切り替えだけを受け取り、次のリクエストでそれを採用します。

失敗が数えられるのは、それが切り替え後の認証情報の上で起きたと証明できるときだけです。切り替え後の再起動か、切り替えとクールダウンの後に届いた失敗リクエストのどちらかです。レート制限による拒否はリクエストの開始時点で返るため、ターンがどれだけ長く走っていても、エラー行自身の時刻が基準になります。これにより、古いトークンを握ったままのリクエストが新しい席を誤って記録することなく、1回の再トリガーの連鎖が使い切った複数のアカウントを渡り歩けます。

## チェックの間隔

定期タイマーは60秒ごとに `tokenmaxxing check --if-due` を実行し、評価のたびに次回をティックの開始時刻を起点として予約します。間隔は、ライブアカウントから最も近いバー (アクティブなセッションの段、週次の集計、ゲート対象のすべてのモデルごとの上限) までの余裕から決まります。余裕が40ポイント以上なら5分、20なら3分、8なら2分スリープし、それ未満なら毎ティック評価します。ラダーもまた、段を1つ上がるごとにこのスリープを1段階ずつ短く制限します。1段目では最大5分、2段目では最大3分、3段目では最大2分、それより上の段では毎ティックです。そのため、段を上がったプールは、まだ1段目にいるプールより頻繁にポーリングされます。予定時刻の半ティック以内に来たティックは予定到来とみなされるので、評価が遅れても間隔がまるまる1ティック分ずれ込むことはありません。引数なしの `tokenmaxxing check` は予約を無視して即座に評価します。ポーリング TTL より古い tee、あるいはライブ org の tee がない場合は、従来の3分間隔を維持します。ゲート対象のファミリーに上限の行がないときは、2分を超えてスリープすることはありません。未計測のウィンドウが低速レーンを手に入れることは決してない、ということです。枯渇待機はそのリセットに向けてスリープし、切り替え後のクールダウン中のティックはその終了時刻ちょうどまでスリープし、ポーリング TTL より古い上限の行は未計測として扱われます。切り替えは予約をクリアするので、新しい席はクールダウンが解けたらすぐに評価されます。低速レーンが安全なのは、StopFailure フックが強制の発生した瞬間にそれを捕らえるからです。
