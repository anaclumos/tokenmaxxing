---
title: 切り替えの判断方法
description: "エンゲージメント、スクリーニングバー、ペースプレッシャー、そしてグリーディパスとハードパス"
---

判断は2つの層からなります。エンゲージメントゲートと、それに続くグリーディパスまたはハードパスです。

## エンゲージメント

`policy.greedySessionFloor` (デフォルト50、5時間セッションウィンドウの使用パーセント) を下回っている間、判断はまったく実行されません。新しいセッションはそのアカウントに乗り続けます。アクティブなセッションウィンドウの使用率が50%に達するか、いずれかのハードバーを超えると、判断がエンゲージします。

## スクリーニングバー

しきい値はスクリーニングバーであり、パニックのトリガーではありません。

- `thresholds.session`: 95。5時間リセットは待つコストが低いため、セッションウィンドウはより早く切り替えます。
- `thresholds.weekly`: 98。この1つのバーが7日間の集計とすべてのモデルごとの週次上限の両方をカバーします。週次クォータは使い切らなければ失われるため、上限に近いところまで消費します。

どちらも意図的に100未満です。この余裕は、アカウントが実際に制限に達する前に、きれいなターン境界へ (加えて macOS では最大1ターンの採用ラグを見込んで) 到達するための予算です。同じバーが切り替え候補もスクリーニングします。いずれかのバーを超えたアカウントは有効なターゲットではありません。トリガーとスクリーニングは常に同じ有効バー (しきい値から `policy.projectionMargin` を引いたもの) を使います。スクリーニングがトリガーより緩いと、トリガーが即座に再フラグするアカウントに切り替えが着地し、プールが行ったり来たりしてしまうためです。

## ターゲット: ペースプレッシャー

使用可能なアカウントの中で、ターゲットは自身の週次ペースから最も遅れているアカウントです。すなわち**ペースプレッシャー**が最も高いもので、これは残りの週次パーセントをそのアカウントの週次リセットまでの時間で割った値と定義されます。最も多くのクォータを失効させかけているアカウントが勝ちます。同点の場合は週次期限が最も早いもの、次に7日間使用量が最も低いものへとタイブレークします。

すべては絶対 UTC エポックとして保存されたキャッシュ済みウィンドウで動作するため、古いスナップショットでも正しく解決されます。すでに過ぎた週次リセットは正確な7日刻みで先へ外挿され、キャッシュ済みリセットを過ぎたウィンドウは新しく空とみなされます (切り替える理由にも、アカウントをベンチに置き続ける理由にもなりません)。

## グリーディパスとハードパス

- **グリーディパス** (エンゲージ済みだが、すべてのバー未満): 現在のアカウントを含むすべてのアカウントをランク付けします。現在のアカウントがすでに勝っているか同点なら、何もしません。そうでなければ厳密により良いアカウントへ切り替えます。決して待機せず、事前パークもしません。使用可能な現在のアカウントを待機と引き換えにすることはありません。現在のアカウントもランク付けされるため、自動パスと引数なしの `tokenmaxxing switch` はどちらも冪等です。定期的に評価すると正しいアカウントに収束し、その後はそのまま留まります。
- **ハードパス** (バーを超えた): 最良の使用可能な候補へ切り替えます。候補のリフレッシュトークンが失効していると判明したら、そのアカウントは再認証が必要としてフラグされ、次の候補が試されます。何も使用可能でなければウォール絞り出し (後述) が動き、すべての使用可能なアカウントがウォールに達したときにのみ枯渇待機ロジックが動きます。実際にセッションを一時停止できる呼び出し元 (スーパーバイズされた Stop フック) だけが、まだブロックされているが最も早く回復するアカウントへの事前パークを許可されます。

## ウォール

ハードパスが使用可能な候補を見つけられない (すべてのアカウントがスクリーニングバーを超えている) とき、自動判断はすぐにはパークしません。まず**ウォールバー** (`hardThresholds`、デフォルト100、各アカウントの実際のサーバー制限) に対して再評価します。セッションはまだウォール未満の間は席を保持して絞り出し、そうでなければ最良のまだウォール未満のアカウントへ切り替え (ペースプレッシャーによる同じランク付け)、すべての使用可能なアカウントが本当にウォールに達して初めてパークします。リフレッシュトークンが失効しているアカウントは、待機の対象とはせず、再認証のために脇に置きます。回復はウォールを基準に測られるため、5時間ウィンドウがリセットされたアカウントは、週次ウィンドウがまだスクリーニングバーを超えていても、再び絞り出しの対象になります。

これにより、各アカウントのクォータの最後の数パーセントが使われずに終わるのを防ぎます。ウォールの値は、判断がすでに使っている使用状況ソース (スーパーバイズされたインタラクティブセッションでは statusline の tee、ヘッドレス実行では `/usage` プローブ) から得られ、これは Claude の `/rate-limit-options` が表示するのと同じ数値なので、本当に上限に達したアカウントは検出されてスキップされます。1ターン分の超過は、次に判断が実行されるとき、つまり定期チェック、あるいはヘッドレス実行では次のスポーンまたは Stop 境界で捕捉され、加えて `serve` は観測された制限のフェイルセーフを通じてエラーとなった制限を永続化するため、そのリトライはウォールに達したアカウントを即座に認識します。

`hardThresholds` はスクリーニングバーと同じように `policy.projectionMargin` を差し引くので、`thresholds` と同じ値に設定するとウォール絞り出しが無効になります。これは Claude 専用のパスです。引数なしの `tokenmaxxing switch` はキャッシュのみのパークを維持し、Codex は `hardThresholds` をまったく無視します。実行中の Codex はセッションの途中で切り替えられた認証情報を採用できないため、実際のサーバー制限に達するまで現在のアカウントに留まります (100 未満のカスタムウォールは Codex には適用されません)。

## モデルごとの上限

`policy.switchModels` (デフォルト `["fable"]`) は、モデルごとの週次上限が切り替えをトリガーできるモデルファミリーを指定します。マッチングはファミリートークンで判定し、正確な表示文字列は決して使いません。モデルの表示名は変動し (「Fable」は「Fable 5」になりました)、正確な文字列によるゲートはかつてモデルごとの切り替えを丸ごと無効にしてしまったことがあります。関連する2つの安全ルールがあります。

- 不明なアクティブモデルは、設定されたすべてのファミリーをゲートします。切り替えがスナップショットをクリアした直後、ヘッドレスなマシンはモデル不明で動作することがあります。不明を無制約として扱っていたために、あるアカウントが Fable 上限のまま何時間も気付かれずに留まったことがありました。
- 候補スクリーニングはゲートされたモデルごとの上限も数えるため、すべてのアカウントが Fable 上限を使い切ったプールはラウンドロビンしません。

## クールダウン

45秒の切り替え後クールダウンが自動パスをゲートします。statusline の tee も切り替え後の同じ45秒間は抑制されます (採用には macOS で最大30秒かかります)。そうしないと、より早い評価が切り替え自身によって無効化されたデータ上で走ってしまいます。まさにこのシナリオが、かつて A から B へ、そして戻る再起動ループを生み出しました。手動の `tokenmaxxing switch` はクールダウンの影響を受けません。
