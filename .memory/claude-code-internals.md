Verified against Claude Code 2.1.204 through 2.1.280. The binary changes monthly: re-verify a line before building on it.

**Credential store.** The store directory is `CLAUDE_SECURESTORAGE_CONFIG_DIR`, else `CLAUDE_CONFIG_DIR`, else `~/.claude`, NFC-normalized; an empty value falls through. On Linux the store is a 0600 `.credentials.json` inside that directory and the build has no keyring path. On macOS the default store is the login-keychain item `Claude Code-credentials`; when the store variable is set the item is `Claude Code-credentials-<first 8 hex of sha256(NFC(value))>`, hashed over the raw string, so the value must be byte-stable (a trailing slash or `~` names another item). A missing namespaced item falls back to `<dir>/.credentials.json` and then to an empty credential, never to the default item. The binary reads `CLAUDE_CODE_OAUTH_TOKEN` (memoized per process), `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, the Bedrock and Vertex switches, `CLAUDE_CODE_SUBSCRIPTION_TYPE`, and `CLAUDE_CODE_RATE_LIMIT_TIER` before the store; `CRED_ENV_OVERRIDES` mirrors that list and is audited on each bump. `~/.claude.json` keeps one `oauthAccount`, rewritten by whichever session refreshed last, so it never identifies a session's account.

**Refresh.** The client refreshes within 300 s of `expiresAt` and force-refreshes, at most twice per request loop, on a 401 or a 403 `OAuth token has been revoked`. It re-reads the store file only inside the refresh orchestrator and only when the mtime moved; the rotated pair is written back under a three-attempt compare-and-swap on `refreshToken` (the `/login` save has no CAS); on `invalid_grant` it dead-clears the store to empty tokens and leaves the file in place; the in-memory credential has no TTL. The refresh takes two mkdir locks rooted at the store, `<store>/.oauth_refresh.lock` and the legacy `<realpath(store)>.lock`, with a 60 s stale bar and five retries before `lock_timeout`; it never refreshes unlocked. A running session adopts a store change on its next freshness poll (the file mtime on Linux, a 30 s keychain cache on macOS); a request stuck in a 429 retry keeps its token until that request dies. The token endpoint (`platform.claude.com/v1/oauth/token`) rotates the refresh token on every success and revokes the previous access token at once, which is why one grant in two stores dies: the other copy 401s, force-refreshes a superseded refresh token, and gets `invalid_grant`. Grant failures are the flat OAuth body `{"error":"invalid_grant",...}` (a superseded refresh token included); request-validation failures are the nested `{"type":"error","error":{"type":"invalid_request_error",...}}` body (an empty `refresh_token`, an unknown client id, a malformed body), so a dead-cleared store must be recognized before any request.

**Identity and plan.** `GET api.anthropic.com/api/oauth/profile` (plain Bearer, `Content-Type: application/json`, no beta header) is what the binary itself calls to fill `oauthAccount`; `account.uuid` is the seat and `organization.uuid` is shared by every seat of a Team plan. `GET /api/oauth/claude_cli/roles` names only the organization and is not an identity. `/api/claude_cli_profile` answers 403 for a raw token (consumer-OAuth enforcement) while the usage, profile, and roles endpoints answer 200. The credential blob's `rateLimitTier` (`default_claude_max_20x`, `default_claude_max_5x`, `default_claude_zero`) is the only 5x/20x discriminator; `subscriptionType` is `max` for both, so the multiplier segment is parsed structurally.

**Hooks.** `StopFailure` fires instead of `Stop` when a turn ends on an API error, for subagents too (`agent_id` set); its matcher is an exact match on the `error` kind, it is fire-and-forget, and its exit code is ignored. The classifiable facts live on the transcript row: `isApiErrorMessage: true`, `apiErrorStatus: 429`, `message.model: "<synthetic>"`, `quotaLimits.rateLimitType` in `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`, `overage`, with `resetsAt` in epoch seconds; the per-model credits refusal carries no `quotaLimits`, only an `errorDetails` body with `error.type: "rate_limit_error"` (and `error.details.error_code: "credits_required"`); a transient 429 sets `apiErrorIsTransient`. `Stop` stdin has no error field and no usage data. Hook output has no compaction field and cannot make the client wait. There is no `CLAUDE_CODE_DISABLE_HOOKS`; `--bare` disables hooks but also skips the keychain, and `--settings '{"disableAllHooks":true}'` disables them for one nested call.

**Statusline.** The main statusLine stdin carries `rate_limits.{five_hour,seven_day}` after every turn (300 ms debounce) and never reflects the focused subagent; `model` is the main-loop model and there is no `hook_event_name`. Subagent rows come only through the `subagentStatusLine` settings key: the client pipes base fields plus `tasks[]` (`id`, `name`, `type`, `status`, `description`, `label`, `startTime`, `model`, `effort`, `contextWindowSize`, `tokenCount`, `tokenSamples`, `cwd`) for every active task and reads back `{id, content}` JSON lines that replace that task's row (empty content hides it). ANSI is re-emitted through the client's own chalk: truecolor survives on a truecolor terminal and downsamples to 256 elsewhere, tmux clamps to 256 unless `CLAUDE_CODE_TMUX_TRUECOLOR=1`, and the line renders inside the client's dim wrapper.

**Processes.** `claude daemon` and `bg-pty-host` sessions spawn the real versioned binary by absolute path, so they bypass PATH shims, run unsupervised, and keep an old version alive after an auto-update. A setup token (`sk-ant-oat01-`, one year, non-rotating, precedence above the store) is inference-only: `/usage` prints no percentages under it. `claude-md-or-agents-md` is the default project-instruction mode since 2.1.277: a project with no `CLAUDE.md` loads `AGENTS.md` in its place, behind the `tengu_agents_md_mod` gate and the `instructionFiles` setting; when project instructions stop loading, check those two first.

**Constraint.** Anthropic does not allow third parties to offer claude.ai login or rate limits in their products, including agents built on the Agent SDK. tokenmaxxing is personal use of the owner's own accounts and ships no SDK or plugin surface.
