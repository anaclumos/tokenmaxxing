# T3 Code forensics

Where a T3 Code thread keeps its Claude session logs and state, and how to correlate them with the tokenmaxxing log when a thread is blamed on a missed move.

- T3 Code drives claude through the Claude Agent SDK, which spawns the tokenmaxxing wrapper as `__supervise --output-format stream-json --input-format stream-json --include-partial-messages --permission-prompt-tool stdio` and loads hooks through `--setting-sources=user,project,local`.
- Per-thread provider logs are `~/.t3/userdata/logs/provider/events.<threadId>.log`, rotated to `.log.1` and `.log.2`; `providerThreadId` in a line is the Claude session id, and `claude/rate_limit_event` lines carry `rate_limit_info.status` (`allowed`, `allowed_warning`, `rejected`) and `unifiedWindows.five_hour.utilization`.
- Thread state is `~/.t3/userdata/state.sqlite`, tables `projection_threads`, `projection_thread_sessions`, `projection_turns`, `projection_thread_messages`, `projection_thread_activities`; read it readonly with `bun:sqlite` when no `sqlite3` binary is installed.
- The Claude transcript for a T3 session is `~/.claude/projects/<slug>/<sessionId>.jsonl`, where the slug is the session's cwd with every non-alphanumeric character replaced by `-`.
- The server bundle that decides what a supervisor notice renders as is `apps/server/dist/bin.mjs` inside the app's `app.asar` (`handleSystemMessage`); read it by parsing the asar header (8-byte pickle, JSON index, file offsets) with a scratch script instead of installing an extractor.
- Start a missed-move investigation from the thread's events log and `tokenmaxxing.log` in the tokenmaxxing state directory (`~/.config/tokenmaxxing/` unless `TOKENMAXXING_HOME` moves it) for the same session id; the causes seen are a seat burned between turns with no turn boundary (the supervisor's seat watch covers it) and an orphaned claude after a harness restart (SIGTERM is forwarded).
- Never paste account labels or the `--mcp-config` bearer from `sessions/<sid>.json` into an issue or PR.
- T3 Code renames a dispatched thread's local branch within about a minute of the first message, from `t3code/<8 hex>` to a title slug that can be a placeholder (`t3code/your-branch-name-here`) or unrelated; that reflog rename is the harness, not concurrent work, so it freezes nothing. Read `git branch --show-current` before the first push and push `git push -u origin HEAD:<current>`, because the old name fails with `src refspec ... does not match any` or `Head ref must be a branch`; never rename it back, and correct a claim comment that names the old branch.
- A thread dispatched into an existing PR worktree whose branch is `t3code/<8 hex>` loses the PR's branch name the same way, and `git push -u origin HEAD` then opens a branch detached from the PR; rename it back with `git branch -m <current> <original>` and send `thread.meta.update` with `expectedBranch` before the thread works.
- A thread's linked pull requests are rows of `projection_thread_pull_requests` (`thread_id`, `repository`, `number`, `url`, `source`, `linked_at`) in the same state store; query it `where thread_id=?` to find the PR a taken-over thread was shipping.
- The T3 Code runtime keeps its server bundle, and the Claude Agent SDK inside it, in the single `t3` binary of `runtime/versions/<activeVersion>/` under the T3 home (`activeVersion` from `runtime/service-state.json`), with no `sdk.mjs` on disk. Read SDK control handling (`pendingControlResponses`, `unmatchedControlResponses`, `liveTaskIds`) or a feature's decoders (`decodeAuthFiles`, `decodeCodexUsage`) there with the byte-offset read in [[claude_code]], and re-read it on each T3 bump.
- T3 Code's periodic provider status probe launches a short stream-json session through the wrapper with `--no-session-persistence` and hooks disabled and sends `initialize` plus the control request `get_usage` with no prompt; the supervisor passes it through unseated and unmanaged, so Claude Code reads `GET /api/oauth/usage` on the ambient login, a read no tokenmaxxing sampler logs, and on a host whose ambient login is a pooled account it spends that account's per-account usage-read budget. A signed-out ambient login answers `rate_limits_available: false`. Never seat the probe.
- Never record a `get_usage` control reply as a usage sample: after a failed read (a 429 included) the binary can answer from a cache up to an hour old, and the reply carries no age and no retry time.
