# Shipping

The ship rules (branch, PR, CI, every review handled, squash merge, the `publish` job as the release, teardown) are in `AGENTS.md` "Release and CI". These entries keep a loop from stalling.

- Confirm `gh auth status` before the loop starts and again before the merge; when it fails, read the PR over unauthenticated REST, stop before the merge, and ask the owner. Never run `gh auth login` and never search files or process environments for a token.
- Poll over REST, never GraphQL: `gh api repos/<owner>/<repo>/pulls/<n>`, `.../pulls/<n>/reviews` (the only endpoint that returns review bodies), `.../pulls/<n>/comments`, `.../issues/<n>/comments`, `.../commits/<sha>/check-runs`, `.../commits/<sha>/status`, and `.../issues/<n>` for the source issue.
- `gh api graphql`, `gh pr view --json`, `gh pr checks`, and `gh pr merge` all spend the per-user GraphQL quota that the owner's other sessions share, and `gh api rate_limit` does not show the exhaustion; keep one GraphQL read for the final review-thread check.
- Merge over REST: `gh api -X PUT .../pulls/<n>/merge` with `merge_method` `squash` and the head `sha`, so a moved head cannot merge.
- Collect reviews unfiltered every round: every inline comment and every review body, filtered by timestamp only, never by author, because a withheld approval can name its finding only in the review body.
- Answer every inline finding as a threaded reply on that comment (`.../pulls/<n>/comments/<id>/replies`) with the fixing SHA or the refutation; a PR-level comment is not handling.
- Main has no required checks, so the ship skill's clean round is the only merge gate.
- Schedule periodic wakeups through every wait and never rely on a background shell or monitor alone; keep poll scripts and their state out of `/tmp`, which a reboot clears.
- Read the full staged diff untruncated before every commit, bulk and agent-generated changes included; a stat plus greps is not the read.
- Some hosts have no `git user.name`: pass `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, and `GIT_COMMITTER_EMAIL` per commit with the identity the repo's recent commits carry, and never write git config, because worktrees share `.git/config` with the owner's checkout.
- A locked vault-backed SSH signing agent fails every commit with `failed to fill whole buffer`, and retries only queue unlock dialogs; attempt the signed commit once, fall back to `--no-gpg-sign`, and note the fallback in the commit body. Squash merges are signed by GitHub regardless.
- A docs change ships when the GitHub production deployment for the merge commit reports `success` (`gh api repos/<owner>/<repo>/deployments`, the Production entry whose `ref` is the merge SHA, then its statuses).
- The Vercel URLs are SSO-protected, so no page fetch proves anything; the content check before the merge is the Preview entry for the head commit (`.../deployments?sha=<head sha>`), read the same way. A failed build posts `failure` on that entry and on the `Vercel` commit status, which keeps the merge state out of `CLEAN`, and a head with no Preview entry does not merge either.
- A PR poll script starts with `set -euo pipefail` and never pipes `gh api` output through `cut` or `head` without it, because a failed read otherwise prints as an empty section and an outage reads as silence before a merge; on a failed read it keeps its cursor and counts no quiet time.
- A poll script's `SINCE` cursor comes from the clock at the start of the tick, never a hand-typed time, because a cursor in the future hides every new review; its first tick also lists the reviews and comments from before the cursor, because an unresolved change request that predates it never reappears.
- Each threaded reply the session posts through `.../replies` also appears in `.../pulls/<n>/reviews` as an empty `COMMENTED` review by its author, and `vercel[bot]` edits its one deploy comment in place, so a rising review or comment count is no new finding: compare review ids and `submitted_at` against the last push, and read every review whose author is not the session.
- Every REST list read of a PR takes `--paginate`: `gh api .../pulls/<n>/comments` returns 30 items per page, so a poll without it misses later review comments. Before the merge, run `gh api --paginate repos/<owner>/<repo>/pulls/<n>/comments --jq '.[] | [.id, .user.login, (.in_reply_to_id // 0)] | @tsv'` and require a reply on every top-level reviewer comment.
- A reply call that fails with `unexpected end of JSON input` can still have posted the reply: list the comment's replies before retrying, or the thread gets a duplicate. One review comment is `GET repos/<owner>/<repo>/pulls/comments/<id>` with no PR number (`pulls/<n>/comments/<id>` answers 404), while the reply route keeps the number.
- The REST merge `sha` needs the full 40-character head SHA, and one wrong character answers HTTP 409 `Head branch was modified`; read it with `gh api repos/<owner>/<repo>/pulls/<n> --jq .head.sha` and compare it with `git rev-parse HEAD`, never type it by hand.
- A 502 from `gh api -X PUT .../pulls/<n>/merge` can arrive after the squash landed: read `pulls/<n>` (`merged`, `merge_commit_sha`) and `git diff origin/main <branch>` before a retry, and close the PR by hand when the diff is empty.
- The REST core pool runs out too: reads answer 403 `API rate limit exceeded for user ID` for 15 to 20 minutes while `gh api rate_limit` can still show quota, so a failed read never counts as a quiet tick. Poll with `If-None-Match` and each response's `ETag` (a `304` spends nothing), and fall back to unauthenticated `curl https://api.github.com/repos/<owner>/<repo>/...` reads, which have a small per-IP budget.
- `gh pr create`, `gh pr comment`, `gh pr edit`, and `gh issue comment` spend GraphQL and fail with `GraphQL: API rate limit already exceeded` when it is spent; write over REST: `gh api -X POST repos/<owner>/<repo>/pulls -f title=<title> -f head=<branch> -f base=main -F body=@<file>`, `gh api -X POST repos/<owner>/<repo>/issues/<n>/comments -f body=...`, `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@<file>`.
- Worktrees share one `.git`, so another session's fetch moves `origin/main` under a branch: judge the PR with `git diff origin/main...HEAD`, never the two-dot form, which shows a later release commit's `package.json` bump as the PR's; test a conflict with `git merge-tree --write-tree HEAD origin/main`, because `mergeable_state` reads `unknown` for minutes after `main` moves.
- The repository keeps a merged head branch (`delete_branch_on_merge` is false), so teardown deletes it with `git push origin --delete <branch>` and confirms with `git ls-remote --heads origin <branch>`.
- A `git push` or other command that exits 137 while a tokenmaxxing move restarts the session was killed by the restart, not by an out-of-memory kill, and may have landed: compare `git ls-remote origin <branch>` with `git rev-parse HEAD`, or read `gh api repos/<owner>/<repo>/pulls/<n>`, before a rerun.
