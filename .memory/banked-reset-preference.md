`policy.preferToUseBankedReset` (provider list, default `[]`) makes the HARD path spend a banked limit reset on the seat before swapping, because a swap cold-starts the per-org prompt cache and a reset keeps it.

**Verified mechanics (2026-09-07):**
- Claude Code 2.1.263: `/limit-reset` is the `juniper_tide` server program. The command is `type: "local"`, `supportsNonInteractive: false`, hidden, so print mode filters it out and `claude -p '/limit-reset'` cannot run it. The claim is `POST /api/organizations/{org}/reset_rate_limits` with body `{"program":"juniper_tide"}` under the OAuth bearer plus the `anthropic-beta: oauth-2025-04-20` header (the request runs as `auth: "async"`, whose header builder `t3()` attaches exactly `Authorization` and that beta header to every OAuth request, verified in the 2.1.263 binary) and the `claude-cli/<ver> (external, cli)` user agent, 25s timeout. Result strings: `reset`, `already_used`, `not_limited`, `ineligible`, `unavailable`, with `next_available_at`; HTTP 429 is `rate_limited`, 401/403 `auth_error`. Product copy: once a week, the reset session window still counts toward the weekly limit. Eligibility is a growthbook flag, so `ineligible` is possible on any account.
- Codex 0.149.1: "banked reset" is the official OpenAI term (help center): a one-time reset saved to the account (promotional or referral, expires), consumed only when it refreshes at least one window, and a full reset refreshes the 5h AND weekly windows and moves the weekly reset date. Wire: `POST https://chatgpt.com/backend-api/wham/rate-limit-reset-credits/consume` with `{"redeem_request_id":"<uuid>"}` (optional `credit_id`), response `{"code":"reset"|"nothing_to_reset"|"no_credit"|"already_redeemed","windows_reset":N}`; `GET /wham/usage` carries `rate_limit_reset_credits.available_count` and `rate_limit_reached_type`. The TUI reuses the idempotency key on a transport retry and treats `already_redeemed` as success then. No restart is needed after a reset.

**Why the reserve is measured, not configured:** Anthropic publishes no ratio between the 5h and weekly windows, and it differs per plan and per model mix. `sessionWindowWeeklyCost` is learned per account from the statusline tee: anchor at the first sample of a session window, and once the session window has grown by 25 points the weekly delta scaled to 100 session points is the cost of one full window. Unmeasured never holds (unmeasured must never look safe). Codex needs no reserve because its reset refreshes the weekly window too.

**How to apply:** Claude holds between the active rung and the wall only while a reset is believed available (`account.bankedReset` with `nextAvailableAt`, a week after `reset`/`already_used` without a date, a day after `ineligible`) and every weekly bar has room for the cost, claims at the wall (StopFailure `five_hour`, or the tee at the session wall bar), and a `reset` clears the enforced stamp, zeroes the cached 5h window, stamps `lastreset.json` (post-swap proof counts it as a seat change), and writes a respawn marker with a reset continuation prompt instead of swapping. Every non-`reset` answer, `not_limited` included, falls through to the swap (hook ruling 2026-09-07: a claim never holds a seat the server did not reset). Codex rides to the wall while `resetCredits > 0`, consumes with a UUID key kept for 10 minutes for retry, re-samples on `reset` and never restarts; every other answer falls through to the restart-swap. Hermetic proof runs against stub servers through `TOKENMAXXING_OAUTH_API_BASE_URL` and `TOKENMAXXING_CODEX_RESET_URL`. Related: [[switch-policy-pace-pressure]], [[stopfailure-enforced-limit-signal]], [[hermetic-ladder-verification]].

**Rulings (2026-09-07):**

AGENTS.md rejects bypassing the CLI for the usage GET; the reset has no CLI method to fix, and the owner approved the direct call as the one Claude exception (2026-09-07, via AskUserQuestion).
