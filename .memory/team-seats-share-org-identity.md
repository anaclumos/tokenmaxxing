**What happened (2026-09-06, 1.15.0 on a Linux host):** the owner pooled six seats of one Claude Team organization. Every identity site keyed on `organizationUuid`: the live seat lookup (`accounts.find(a => a.organizationUuid === org)` returns the FIRST seat in array order), the tee match (`usage.json.org`), `overlayLive`, the enforced-limit stamp, `checkIdentity`, and the swap's live-owner resolution through the roles endpoint. Consequences, all observed: `status` marked every seat active and gave all six the live tee's numbers; the enforced 5h stamp landed on the first seat of the org rather than the live one; after a swap onto a second seat the hard path resolved the seat as the first one, excluded it, and picked the ACTUALLY live seat as the swap target, so `performSwap` refreshed the live seat's own parked copy; the harvest wrote the live blob into the first seat's slot, so that seat's only credential was overwritten and later revoked by a rotation (its slot now 401s "OAuth access token has been revoked"); every hook and check for four minutes failed with `token refresh failed (HTTP 400): (unparsable error body withheld)` because the 400 body was the nested Anthropic shape the error parser did not read (separate follow-up release).

**Rules shipped in 1.17.0:**
- Identity is `account.uuid` from `GET https://api.anthropic.com/api/oauth/profile` (`fetchTokenIdentity`), the endpoint Claude Code itself uses to fill `oauthAccount`. The organization is informational only. Every former `organizationUuid` comparison now compares `accountUuid`; the tee and model-usage files carry `account` instead of `org`; `EnforcedLimit.account`; the stamp outcome `org-moved` became `account-moved`.
- The live seat without a network call is `readOAuthAccount().accountUuid` from `~/.claude.json`, which both `/login` and the swap write.
- The owner gate on a parked token fails closed. A profile failure other than 401 (`IdentityUnavailableError`: unreachable, 5xx) skips the candidate for that evaluation without a refresh and without a stamp. A 401 means the parked access token is expired or revoked, so the refresh is the arbiter, and the refreshed token's owner is verified before it is parked; a mismatch there stamps the target and keeps the rotated pair under its true owner (the live store when that owner is live, else its parked slot, else the target's stamped slot when the owner is outside the pool), because the rotation just superseded every other copy of that grant. The 401-gated refresh, its verification, and the rescue run inside one `withClaudeRefreshLock` section, in the swap and in the parked probe alike, so Claude Code cannot spend the superseded refresh token in the gap. The `switch` command carries its rejected set through the earliest-reset fallback as well. A parked pair whose access token validates but resolves to another pooled account that is not live is copied to that owner's slot before the target is stamped: a rotation revokes the prior access token, so a validating pair is that owner's current grant state, and this is how a pair stranded by a verification outage reaches its owner on the next pass. `refreshCredential` itself refuses a dead-cleared blob. The `rejected` set narrows only the candidate list; the ladder bars come from the full freshly loaded pool, or the rung climbs mid-evaluation and the seat ping-pongs between the greedy and hard paths. (Codex review findings on the 1.18.0 PR.)
- A refresh rotation revokes the previous access token immediately (verified by rotating a parked seat and re-reading the profile with the old token). Refreshing any copy of a credential that is live somewhere else (another host, or the live seat itself when identity mis-resolves) kills those sessions' token. Cross-host pooling on Claude therefore means 401s on the other host plus `invalid_grant` on its stale refresh token, not just churn; `docs/limitations.mdx` and AGENTS.md say so.

**Follow-up shipped in 1.18.0 (the HTTP 400 livelock):** forensics on the incident logs and the 2.1.263 binary gave the chain. The org identity made a hook pick the live seat as the swap target and POST the live seat's just-rotated refresh token to the token endpoint about 0.7 s after Claude Code minted it, while Claude Code still held it. The grant family was revoked; the token endpoint then answered the pool's copies with the nested `invalid_request_error` 400 rather than `invalid_grant`; and every retry loop in `decide.ts` continued only on `InvalidGrantError`, so any other error aborted the evaluation and the next hook started over (about 4.5 minutes, 24 hooks, 6 check ticks, two supervised sessions exiting 1 without a respawn marker). Claude Code's own recovery dead-cleared the live blob to empty tokens, and the pool then tried to refresh the empty refresh token. Fixes: the error parser reads the nested shape (`safeErrorDetail` prints `type: message (request_id)`); a non-`invalid_grant` 4xx is `RefreshRejectedError` and skips the candidate for the evaluation (`rejected` set, `isSkippableSwapError`) without stamping `needsReauth`; `isDeadCredential` recognizes the dead-cleared blob before any request; the owner of a parked token is resolved through the profile endpoint before its refresh grant is spent; and `log()` no longer drops lines whose fields carry `undefined` (`JSON.stringify(undefined)` made `redact` throw into an empty catch, which hid the `swap.invalid_grant` lines during the incident).

**Repair after the incident:** the seat whose slot was overwritten needs `tokenmaxxing auth <label>`; every other slot was re-verified by resolving each parked token through the profile endpoint (a free read). A host running an older npm global keeps executing the org-keyed code until the owner updates it; the periodic timer there swapped seats twice more during the fix.

**How to apply:** never key anything on the organization; a pool may hold several accounts with one `organizationUuid`. When a hermetic scenario needs the team case, seed two accounts with the same `organizationUuid` and different `accountUuid`s (see [[hermetic-ladder-verification]]). Endpoint facts and the token endpoint error shapes live in [[cc-codex-auth-mechanics]].
