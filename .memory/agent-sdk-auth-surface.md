Research for the tokenmaxxing SDK follow-up (v0.11.0), verified against code.claude.com Agent SDK docs 2026-07-16 (full report: session task ac4a8da46a2f17ff4). Re-verify before building; the SDK changes monthly.

- The Agent SDK spawns the claude CLI as a subprocess per `query()` (`claude --print --output-format stream-json`), stdin/stdout JSON. No persistent process across queries; credentials are read at spawn time, NO mid-query hot-swap adoption and no 30s keychain poll (unlike the interactive CLI).
- Useful options: `pathToClaudeCodeExecutable` (custom binary - could point at the tokenmaxxing supervisor shim), per-session `env`, `resume: sessionId`, Stop hooks (both SDKs; SessionStart callbacks TS-only), `settingSources` controls whether ~/.claude and .claude settings.json (incl. shell hooks) load. NO statusLine machinery: the SDK never renders it, so the usage.json tee never fires for SDK sessions.
- Second doc-verification pass (official TS reference + hooks guide, 2026-07-16, for the shipped sdk.ts): `Options.env` REPLACES the subprocess env (default `process.env`, docs say "replaces, not merges") - a scrubbed full copy works, a patch object would drop the rest of the environment. Hooks shape `{ Stop: [{ hooks: [cb] }] }` (no matcher on Stop); returning `{}` is the documented no-op; the hooks guide says to catch errors inside callbacks because an unhandled exception can interrupt the agent. Current docs state default settingSources DOES load `~/.claude` + project `.claude` settings (the old claude-code->agent-sdk migration note claimed the opposite; docs drift monthly - phrase claims neutrally). Subprocess-per-query is NOT in public docs (known from the earlier binary/source research only).
- Credential precedence in the spawned CLI: cloud env vars > ANTHROPIC_AUTH_TOKEN > ANTHROPIC_API_KEY > apiKeyHelper > CLAUDE_CODE_OAUTH_TOKEN > subscription OAuth from /login.
- BLOCKER to surface to the user before building: Anthropic docs state "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" (quickstart + support article 15036540). So a published tokenmaxxing SDK that pools claude.ai subscription accounts under the Agent SDK is ToS-prohibited territory; the compliant shape is API-key rotation per query (no 5h/weekly windows, no /usage - would need its own metering), which loses most of tokenmaxxing's machinery. See [[cc-codex-auth-mechanics]] ToS note for the related consumer-OAuth server enforcement.
- Plausible integration shapes to discuss: (a) `pathToClaudeCodeExecutable` -> supervisor shim so SDK subprocesses at least resolve the pooled live credential each spawn + swap between queries via Stop-hook-driven checks (personal-use, same accounts the CLI already pools); (b) API-key pool rotation via per-query env (compliant, different feature); (c) drop the SDK and document CLI-side pooling as the supported path.

**Why:** the user asked for "Tokenmaxxing SDK that works in pair with Claude Code Agent SDK" (2026-07-16, ship as 0.11.0 after 0.10.0); the design space is constrained by the subprocess auth model and the ToS line above.

**How to apply:** the blocker and the three shapes were presented and the user explicitly chose shape (a), personal-use integration, on 2026-07-16 (AskUserQuestion answer "Personal-use integration"): helpers so the Agent SDK runs against the owner's own pooled accounts (greedy swap check at query/turn boundaries, pathToClaudeCodeExecutable pinned to the real claude, scrubbed env resolving the live pooled credential), documented in the README as personal use of your own accounts. Shipped as 0.11.0. Link: [[tokenmaxxing-project]].
