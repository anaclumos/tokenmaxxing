**What happened (2026-09-05, 1.12.0 on a Linux dev host):** `status --ping` showed the active account at 5h 100% (a real refusal: the haiku ping was rejected with a `rate_limit` row in its own transcript, `quotaLimits.rateLimitType` `five_hour`), and a plain `status` a minute later showed the same account at 21% with the same reset clocks. The 21% was the statusLine tee, written 20 minutes earlier and never refreshed because the host's hooks, statusLine shim, and check timer had been stripped seconds after that write (the throwaway-root `uninstall` incident recorded in AGENTS.md under Testing). The plain run then overwrote the fresh 100% record in accounts.json with the older tee, so the pool state regressed to healthy-looking.

**Rules shipped in 1.13.1 (opened as 1.12.1; PR #60 took 1.13.0 first):**
- The active account's row is the newest of the tee and the stored sample. `status` compares the tee's mtime (read from the same open descriptor as the payload by `loadUsageSnapshot`, so a statusline write landing mid-read cannot pair old figures with a new mtime; the same clock the engine's `usageFresh` gate reads from the same snapshot, because `writeUsage` only touches an unchanged payload and freezes the embedded `ts` for up to 10 minutes, see [[headless-decision-freshness]]) with the account's `lastUsageAt` and, when the tee is older, ignores it and probes the live login (or, under `--ping`, keeps the failed probe and renders the cached record). The decision engine applies the same rule before its engagement checks (`freshest` in decide.ts substitutes the account record's windows when a same-org tee is older than the record, keeping the tee's org and model) and again as the guard on the write-back, so a newer stored probe can drive a switch even while the older tee is still inside `usagePollTtlMs`. Rationale: a sample must never overwrite a newer one; the stored record can be fresher than the tee after any live probe (`--ping`, a stale-tee re-probe by the engine) until the next statusLine turn.
- A tee-sourced row prints its age from that mtime (`statusline tee 20m ago`, yellow with `(stale)` past `usagePollTtlMs`), and `lastUsageAt`/`usageAt` are stamped from it too, so text, JSON, and the engine agree on one freshness clock.
- A failed `--ping` ping reads the ping's own transcript row (`<configDir>/projects/<cwd slug>/<session_id>.jsonl`, slug = every non-alphanumeric character of the cwd replaced by `-`) and, when Claude Code marked it `isApiErrorMessage` with `error: rate_limit` and it is not `apiErrorIsTransient` (a `quotaLimits` window, or the credits-branch `rate_limit_error` body, the same guards as `classifyEnforcedLimit`), reports `ping rejected at the 5h limit: <server text>` (JSON `pingRejected: true`) instead of `ping failed (5h timer may not have started)`. Classification is structural (the same row the StopFailure hook trusts); the prose is display only and never stamps anything.

**Observation worth keeping:** the live `/usage` probe is fail-silent only when Claude's internal usage fetch errors or 429s. On 2026-09-05 (2.1.261) every live probe of the day succeeded (0 `usage.probe_*` failures against 44 pings in the log), and the decision engine already relies on it whenever the tee is older than the TTL. The absolute "never probe the active token" wording in AGENTS.md was replaced with the conditional one; the fail-silent case still exists under load ([[cc-codex-auth-mechanics]]).

**How to apply:** when `status` and `status --ping` disagree only on the active row, suspect a stale tee first and check `doctor` for missing hooks or timer. Never bring back an unconditional tee-wins copy. Cost facts for the two commands are in [[live-pool-runs-need-permission]]: plain `status` spends no model tokens; `--ping` is one haiku turn per Claude account.
