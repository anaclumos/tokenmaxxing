Verified 2026-07-08 against installed binaries (Claude Code 2.1.204, Codex CLI 0.143.0) and `openai/codex` @ rust-v0.143.0. Both CLIs change monthly - re-verify before trusting in a later month. Full detail + citations live in [[tokenmaxxing-project]]'s `DESIGN.md` §2.

**Claude Code (macOS):** creds in macOS Keychain, generic-password, service `Claude Code-credentials`, account `$USER` (no `~/.claude/.credentials.json` on macOS; on Linux/Windows creds ARE that file, mode 0600 - relevant for the container runner).

**Claude Code (Linux, binary-verified 2.1.205 native ELF + strace, 2026-07-09):** the Linux build is compile-time specialized - `Rc()` (credential storage selector) returns the plaintext-file store unconditionally and `startKeychainPrefetch` is a stub; there is NO keyring/libsecret path. Creds file = `<credDir>/.credentials.json`, written mkdir + write + chmod 0600, where credDir = `CLAUDE_SECURESTORAGE_CONFIG_DIR ?? CLAUDE_CONFIG_DIR ?? ~/.claude` (CLAUDE_SECURESTORAGE_CONFIG_DIR checked FIRST, empty string falls to `~/.claude`, `.normalize("NFC")` applied). No hash-namespacing on Linux - CLAUDE_CONFIG_DIR isolation is just the file inside that dir. `.claude.json` = `$CLAUDE_CONFIG_DIR/.claude.json` else `~/.claude.json`, same as macOS. The ensure-fresh-token path (`dEi`) calls an mtime watcher (`lch`) that stats `.credentials.json` and clears the in-memory token caches when mtime changed - so external file swaps are noticed at the next token-freshness check on Linux (macOS equivalent: the catch branch re-reads the keychain and compares accessToken). strace confirms repeated `openat`+`statx` of the file. Bun `dlopen("libc.so.6")` flock(2) works on Linux arm64 glibc (LOCK constants identical to darwin); GNU stty present. Setting `CLAUDE_CONFIG_DIR` namespaces the Keychain service to `Claude Code-credentials-<first 8 hex of sha256(NFC(raw env string))>` - hash is over the RAW string, so the path must be byte-stable (trailing slash / `~` vs absolute → different entry). Account identity in `$CLAUDE_CONFIG_DIR/.claude.json` `oauthAccount`; quota metered server-side per `organizationUuid`. `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) works interactive, inference-only, not read in `--bare`.

**CRITICAL (CORRECTED 2026-07-10, binary-verified 2.1.206 `Fhh`/`Pwi`; same mechanism confirmed in 2.1.204 `klh`/`pvi` and 2.1.205 `hch` - the previous "no hot-swap" version of this paragraph was a verification error caught by the user's live observation): a running claude session DOES adopt an externally swapped credential, on both platforms, without restart.** Every ensure-fresh call (`cb()`->`Pwi`) begins with a freshness poll (`Fhh`): on Linux it mtime-stats `.credentials.json` and hard-flushes all token caches on change (no throttle); on macOS the stat ENOENTs into the catch branch, which clears the token memos (`hs`/`bF`) and re-reads the keychain through a raw 30s cache (`$x`, TTL 30000), comparing accessToken. `cb()` runs at every inference-client creation (the query loop creates the client on the first attempt of EVERY request and recreates it on 401/407/connection-reset) and on every firstPartyApi call with `refreshOAuth` (including in-session `/usage`). Net adoption: the first request >=30s after the last raw keychain read on macOS; the next request on Linux. Near-expiry margin is 300s (not 120s), and the refresh path resolves races by adopting a mid-flight external write. A 401 (or 403 "OAuth token has been revoked") force-flushes the 30s cache and adopts immediately. **A 429 still never invalidates the token, but that no longer matters:** only the currently-retrying request keeps its snapshotted old token (429 retries reuse the same client); the session's next request adopts the swap. In-session `/usage` shares the exact token caches inference uses (`jie`->`hs`), so its account display flips with adoption and within any 30s window `/usage` and inference necessarily hold the same token (user observed the flip live 2026-07-10; then binary-verified). Consequence: process restarts are NOT required for Claude Code credential adoption - a periodic external swap is picked up mid-session; restart-for-adoption remains true only for Codex. Unchanged: swaps must run under claude's refresh lock, and a near-expiry session can refresh-write its own account's rotated token into the live store at any time, so harvest-by-true-owner stays mandatory. There is NO `CLAUDE_CODE_DISABLE_HOOKS` env/flag; `--bare` disables hooks but also kills keychain reads; `--settings '{"disableAllHooks":true}'` disables hooks for a nested call. The default keychain item (`Claude Code-credentials`, unnamespaced) is shared by ALL default-profile sessions -> a swap migrates every session. statusLine stdin carries `rate_limits` (Stop hook stdin does not) -> feed usage via a statusLine shim writing a state file.

**Primary quota source (canonical, user-decided 2026-07-09): `claude -p '/usage'` (free, `num_turns:0`, 0 tokens), run in a throwaway `CLAUDE_CONFIG_DIR` for parked accounts.** The direct `GET api.anthropic.com/api/oauth/usage` (Bearer, no beta header; response `limits[]` with `kind` ∈ `session|weekly_all|weekly_scoped`, `percent`, ISO `resets_at`, per-model named by `scope.model.display_name`) was tried and REJECTED by the user: it 429s (`rate_limit_error`) when the account being sampled is the token actively running the current session, and it is "the web one" - the user's steer is to fix the CLI method, not bypass it. `/usage` is just a renderer over that same endpoint (verified in the 2.1.205 bundle), so it inherits the same figures for free while staying on the sanctioned path. Two real gotchas the CLI method has: (1) it is fail-silent - when claude's internal usage fetch errors/429s, `/usage` prints only local session stats with NO percentage lines (so the ACTIVE/busy token yields nothing; sample the active account from the statusLine `usage.json` push instead, never by probing its own token); (2) reset times are human-formatted (`resets Jul 13 at 11:59pm (Asia/Seoul)`), so parse them to epoch (`parseResetClock` in usage.ts: month/day + h[:mm]am/pm + IANA tz, year inferred as nearest-to-now, zoned-wall-to-epoch via Intl offset). Contamination fix for the CLI method = scrub every ambient credential override before spawning (see below) + harvest-by-true-owner; the isolation (namespaced keychain item) was always correct. ToS note: consumer-OAuth server enforcement (2026-01) blocks some endpoints for raw tokens (`/api/claude_cli_profile` 403s "OAuth authentication is currently not allowed"), but `/api/oauth/usage` and `/api/oauth/claude_cli/roles` answer 200.

**Probe env MUST scrub these (claude 2.1.205 reads them BEFORE the keychain, so an inherited value silently meters the wrong account):** `CLAUDE_CODE_OAUTH_TOKEN` (checked first, memoized per process), `CLAUDE_SECURESTORAGE_CONFIG_DIR` (re-points the keychain namespace), `CLAUDE_CODE_SUBSCRIPTION_TYPE`, `CLAUDE_CODE_RATE_LIMIT_TIER`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`. Missing namespaced keychain item does NOT fall back to the un-suffixed live item - it falls back to `<CLAUDE_CONFIG_DIR>/.credentials.json` then `{}` (binary-verified), so isolation is sound once the env is clean.

**Token identity ground truth: `GET api.anthropic.com/api/oauth/claude_cli/roles`** (endpoint string from the 2.1.205 binary; works with plain Bearer) → `{organization_uuid, organization_name, organization_role, ...}` = the org the token ACTUALLY belongs to. Used as tokenmaxxing's identity guard after the 2026-07-09 contamination incident: a mis-harvested backup held a different account's token, and distinct blob hashes proved nothing (two rotations of the same account differ byte-for-byte). Labels drift; only the token API is authoritative.

**Claude's background daemon bypasses PATH shims (observed on the ARM Linux box 2026-07-10):** `claude daemon` / `bg-pty-host` sessions spawn the REAL versioned binary by absolute path (`~/.local/share/claude/versions/<v>`), so they never pass through the tokenmaxxing supervisor wrapper - bg sessions are unsupervised (hooks still fire via settings.json; on Linux adoption + the periodic timer cover switching, but there is no marker-driven respawn). Long-lived bg processes also keep running an OLD version after an auto-update (a 2.1.204 bg-pty-host was alive with 2.1.206 installed). A supervisor auto-`--resume` can collide with a bg fork of the same transcript and exit immediately; `supervisor.exit` log (added 2026-07-10) records child exit code/signal for diagnosis.

**Codex (re-verified 2026-07-16 at rust-v0.144.5 + local 0.144.4 binary + one live usage read, for the 0.13.0 build):** creds in `$CODEX_HOME/auth.json` (0600); store config key is `cli_auth_credentials_store` (file/keyring/auto/ephemeral, default auto; keyring service "Codex Auth", per-home namespaced) - tokenmaxxing requires file mode. CORRECTED 2026-07-19 (binary strings, 0.144.5 native serde table): the earlier "`cli_auth_credentials_store_mode`" recording here misread the enum TYPE name (`AuthCredentialsStoreMode`) as the key; `_store_mode` appears nowhere in the binary, so config writes/scans using it were silently ignored by codex until PR fixed them. **Hot-swap still impossible** (`reload_if_account_id_matches`): restart IS the switch; `codex resume <sid>` continues the transcript on the new account. Refresh: auth.openai.com/oauth/token, client `app_EMoamEEZ73f0CkXaXp7hrann`, 5-min margin + 8-day interval, refresh_token ROTATES with reuse punished (`refresh_token_reused` = dead grant), NO cross-process auth.json lock (in-process semaphore only). Usage: free authed GET `chatgpt.com/backend-api/wham/usage` returns identity (account_id/email/plan_type = token ground truth) + windows with `used_percent`/`limit_window_seconds`/`reset_at` epoch-seconds; the WEEKLY window is PRIMARY on current Plus/Pro (5h window removed ~Jul 12 2026) so classify windows by DURATION, never position; per-model caps arrive as `additional_rate_limits[]` by `limit_name`. Codex now has a full HOOKS system incl. Stop (hooks.json / config.toml [hooks]; Stop stdin carries session_id; `{}` + exit 0 = no-op) gated by a TRUST step: users must trust new hooks via `/hooks` in the TUI or they are silently skipped. Legacy `notify` still works (the Mac's config.toml uses it for Computer Use - never clobber). `codex exec` exits 1 at the limit with per-limit_name message. Login isolation: `CODEX_HOME=<dir> codex login`, `--device-auth`, `--with-access-token` stdin. Full detail in AGENTS.md "Codex internals (verified for 0.13.0)".

**No-hot-swap re-verified in depth 2026-07-16 (rust-v0.144.5 = the installed binary; 6-agent source sweep incl. two adversarial passes, after the user asked whether respawn was needed at all):** the session AuthManager is built ONCE per process (`app-server/src/in_process.rs:392`, shared by tui and exec) and auth.json is never re-read for inference - no file watcher anywhere in codex-rs, no timer, and `/new` inside a live tui reuses the same manager (ThreadStart does not re-bootstrap). Per-request tokens come from the in-memory cache (`core/src/client.rs:1413` -> `manager.rs:1997`). Near-expiry refresh runs a GUARDED reload first (`manager.rs:2384 reload_if_account_id_matches`) and on cross-account mismatch returns a permanent "signed in to another account" error WITHOUT refreshing (so a post-swap session cannot rotate the harvested old account's token via the refresh path; the mismatch error is swallowed to logs and the session limps on the stale token until a server 401, where UnauthorizedRecovery also refuses on mismatch and the user sees "Please sign in again"). Ecosystem corroborates (third-party switchers all restart; a forked CLI exists solely to add restart-free switching). **CAVEAT found by the adversarial pass: the ChatGPT Apps/connectors surface (Feature::Apps, Stable + default-enabled) builds THROWAWAY AuthManagers that fresh-read auth.json mid-run** (`chatgpt/src/connectors.rs:36-48`, `chatgpt/src/chatgpt_client.rs:26-31`), triggered automatically on every SessionConfigured incl. `/new`, and on `/apps`. Those backend GETs go out under the SWAPPED-IN account's Bearer, and the throwaway manager's `.auth()` can proactively refresh-and-persist that account's rotating refresh_token into auth.json under codex's in-process semaphore only, OUTSIDE tokenmaxxing's codex flock. Inference identity still never flips (restart remains the switch; the codex supervisor SIGTERM+respawn machinery is load-bearing), but "idle tui = touches no tokens" is FALSE: tokenmaxxing must read the live blob fresh at the last moment, persist rotations instantly, and treat harvest-vs-inflight-rotation as a real (narrow) race.

**`claude setup-token` / `CLAUDE_CODE_OAUTH_TOKEN` (investigated + ABANDONED 2026-07-09, do not revisit without solving usage):** the setup-token (`sk-ant-oat01-`, 1yr, non-rotating, precedence above keychain, meters against the subscription) would kill the reauth churn, BUT it is INFERENCE-ONLY scoped and VERIFIED (real token, 2.1.205) to break monitoring: `claude -p '/usage'` returns the headless cost footer with NO rate-limit percentages under it (reproduced in both a disposable and the real config dir). Since tokenmaxxing's switch trigger parses `/usage` (still the canonical usage source), the env-token path has no usable usage signal, so it stays dropped. Verified-good under the token: precedence over keychain, no keychain mutation, no rotation collision (5/5 parallel probes survived). Also: 2.1.205 checks `CLAUDE_CODE_OAUTH_TOKEN` FIRST, before all keychain/config-dir logic (memoized per process), so any probe/subprocess env must scrub it or it silently hijacks identity. Stay on keychain-swap.

**Plan-tier discriminator (verified live 2026-07-17, for the 0.16.0 tier display):** `subscriptionType` in the credential blob is just "max" for every Max account - the ONLY per-account 5x/20x discriminator is the blob's `rateLimitTier` (strings in the 2.1.211 binary: `default_claude_max_20x`, `default_claude_max_5x`, `default_claude_zero`; parse the multiplier segment structurally, never exact-match). The live `~/.claude.json` `oauthAccount` mirrors it as `organizationRateLimitTier` (plus a null `userRateLimitTier`) once claude's profile fetch has run - stored `oauthAccount` snapshots from before that fetch lack the field. tokenmaxxing stamps `Account.rateLimitTier` from the blob after the roles-endpoint identity check (sample.ts), and for the tee-fed active account from the live oauthAccount (uuid-matched); `claudeTierLabel` in cli/render.ts renders "max 20x".

**Design consequence (updated 2026-07-10):** tokenmaxxing lets each vendor CLI own its own credential store and swaps under claude's refresh lock with harvest-by-true-owner. For Claude Code, in-place swaps ARE adopted mid-session (see the corrected CRITICAL paragraph), so the supervisor's SIGTERM+respawn is not needed for adoption - its remaining value is UX (depleted-pool countdown + auto `--resume`) - and a periodic timer-driven switch is architecturally sound on both platforms. Codex still requires a process restart to switch accounts (`reload_if_account_id_matches`). Neither CLI has native multi-account as of these versions.

**Refresh lock (binary-verified 2.1.214, 2026-07-19, extracted embedded JS around `.oauth_refresh.lock`):** claude's refresh path takes TWO proper-lockfile mkdir locks rooted at credDir (the securestorage-aware credentials dir, same resolution as the creds file): primary `<credDir>/.oauth_refresh.lock` + legacy `<realpath(credDir)>.lock` (`~/.claude.lock` by default - built dynamically, so a literal string-grep for `.claude.lock` finds NOTHING; the docs' old lock name was the legacy half, not pure fiction). Options: `stale: 60000`, `update: 5000` (mtime heartbeat), `onCompromised` -> flag + abort the in-flight refresh HTTP call, with CAS recovery on compromised persists (`tengu_oauth_refresh_compromised_cas_adopted_sibling` / `_cas_saved`). On contention claude retries 5x with 1-2s jitter then gives up with `lock_timeout` - it NEVER refreshes unlocked. Legacy-lock contention releases the new lock and aborts (`tengu_oauth_refresh_legacy_lock_contended`); a legacy acquire ERROR (non-ELOCKED) is logged and the refresh proceeds under the primary only. tokenmaxxing's `withClaudeRefreshLock` mirrors all of this since PR #27 (2026-07-19); before that it held a single lock at claudeDir with a 20s stale bar and PROCEEDED UNLOCKED after 3s - and two live-store writes (performSwap step-2 pre-refresh, init's import refresh) ran outside the interlock entirely.

**statusLine payload + subagent surface (binary-verified 2.1.214 + docs sweep, 2026-07-18):** the main statusLine command's stdin NEVER reflects the focused subagent - the drill-in view state (viewingAgentTaskId / viewSelectionMode) is UI-only, absent from the payload builder and its re-render deps; `model` is always the main-loop model, `agent.name`/`agent_type` are the session-level agent identity (--agents / resumed agent), and there is NO `hook_event_name` in statusline stdin. Subagent info flows ONLY through the separate `subagentStatusLine` settings key (same `{type:"command"}` shape): claude pipes base fields + `columns` + `tasks[]` `{id, name, type, status, description, label, startTime, model, effort, contextWindowSize, tokenCount, tokenSamples, cwd}` for ALL active tasks on a 300ms-debounce + 5s timer, and expects `{id, content}` JSON lines back that REPLACE that task's row body in the agents panel (empty content HIDES the row; omitted id keeps the default). `model`/`contextWindowSize` need claude >= 2.1.205, `effort` >= 2.1.214. ANSI rendering: claude parses statusline output into a style model and re-emits via bundled chalk - 16/256/truecolor all survive on a truecolor terminal, truecolor auto-downsamples to the 256 cube elsewhere, tmux clamps to 256 unless `CLAUDE_CODE_TMUX_TRUECOLOR=1`, and the whole statusline renders inside claude's own dim wrapper.
