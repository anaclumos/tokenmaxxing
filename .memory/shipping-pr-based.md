# Shipping is PR-based

User decision 2026-07-18: "shipping will now be PR-based". Supersedes the direct-push-to-main flow used through 0.18.0. Refined by the user later the same day: "ship = do the work, open a PR, wait 10 minutes for reviews to kick in, handle reviews (refute or agree), then merge, tear down (clean up). tag user in slack when decision is needed or user intervention is needed." WIDENED by the user 2026-07-20 ("You must also do all of those when you ship", after PR #38 merged with no release): ship always includes the release; a merge without a publish is not shipped. MOVED 2026-09-17 (issue #151): the version is assigned by CI at merge time, never in the PR. Three collisions in one week forced it: two PRs bumped to the same version, so the second bump no-op'd and its code sat on main unpublished until a fix-forward PR (1.42.0 shipped as `chore: version 1.42.0`, and 1.44.0 was bumped by #129 and #131 both); sibling releases conflicted on the version line; and `gh release create --target <short-sha>` returned 422 three times.

- Ship = do the work, then land it through a pull request: work on a branch, leave `package.json` alone, commit there, push the branch, `gh pr create`, make CI pass.
- After opening the PR, babysit it every minute: poll for new reviews, comments, check results, and merge state, handle each item as it lands, and merge only after 10 consecutive quiet minutes. Owner rule 2026-09-06 ("10 minutes of silence but you should babysit every minute"), replacing the fixed 10-minute timer from the last push.
- Handle every review: agree and fix, or refute with a reasoned reply on the PR. Never merge over an unanswered review.
- Merge when all clear. The `publish` job of `ci.yml` on the merge commit does the release: when a packed file changed since the tag of the current version it bumps the minor version, commits `chore: release <version>` to main, creates the GitHub release at that commit with the full SHA, and publishes through trusted publishing. Watch that job (`gh run watch`), then verify the publish landed (`npm view tokenmaxxing version`). Then tear down: delete the merged branch, remove temporary worktrees and other session artifacts.
- A PR that changes no PACKED file publishes nothing, and merging it IS shipping it; CI decides membership with `npm pack --dry-run`, never by reading the `files` array (owner 2026-09-08, now enforced by the job). `files` names `src`, `README.md`, `DESIGN.md` (the `agent-plugin` entry left with the plugin in #87), but npm also always packs `LICENSE` and `package.json`, so a LICENSE-only or metadata-only PR does change the artifact and is NOT exempt (caught in review on PR #76). A change confined to `docs/`, `.memory/`, `.github/`, or AGENTS.md publishes nothing, and the docs site deploys from main through Vercel without a release. The rest of the ship is unchanged: branch, PR, CI, the full review window, every review answered, squash merge, tear down. The written rule had been unconditional while the practice was not (PR #71, a docs-only locale sync, took no bump and no release), and PR #75 merged the same way before the conflict was noticed; this records which one wins.
- A version set by hand in a PR is published as it is when the registry lacks it; that is the path for a major release and the only reason to touch the version line. Two publish jobs serialize on one concurrency group, the loser of the push race fails without publishing, and the queued job releases both merges as one version. A job that pushed its release commit and then failed to publish leaves main and the tag one version ahead of the registry; the next push to main, or `gh workflow run ci.yml --ref main`, publishes that version. The job runs only for `main`; a dispatch on another ref does nothing.
- Never push work directly to main.
- Tag the user in Slack when a decision or user intervention is needed; otherwise run the whole sequence end to end without asking.
- The standing "commit and push after each verified milestone" rule still holds, but pushes go to the work branch.
- Canonical rule text lives in AGENTS.md "Release and CI" (first bullet).
