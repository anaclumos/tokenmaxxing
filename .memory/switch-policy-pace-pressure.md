User's decision (2026-07-13): rank usable switch targets by how far behind their own weekly pace they are, picking the furthest-behind first. The user initially specified a backward pace ratio (actual used % over expected % for elapsed window time) and explicitly delegated improving the equation ("Is this the best? You can improve the equation if needed"); the shipped metric is the forward-looking equivalent, `pacePressure` = remaining% / time-to-weekly-reset, highest first. The raw backward ratio was rejected because it blows up right after a reset (expected ~0, so tiny usage reads as "way ahead of pace") and ignores how much quota is at risk (5 used at 50% elapsed and 8 used at 80% elapsed score identically).

This supersedes the 2026-07-10/12 soonest-weekly-expiry policy but is a strict refinement, not a reversal: equal remaining reduces to soonest expiry first, equal expiry to most remaining first. It is still NOT most-remaining-first in general. Earlier greedy/idempotent semantics survive unchanged: bare `xx switch` ranks every account (current included) and no-ops when the current one wins; hooks/decide.ts exclude the active account; everything decides off cached windows (absolute UTC epoch resetsAt, weekly resets extrapolate forward in exact 7-day steps, a window past its cached reset counts as empty/fresh).

Extended 2026-07-16 (user: "use threshold only for exempting as switch candidate... if there is a more greedily available underused account, we should switch often. Maybe after using 50% of session, start switching?"): the hooks/timer path (`evaluateAndMaybeSwap`) now ENGAGES at `policy.greedySessionFloor` (default 50, session-used %) or any crossed screening bar, then runs the same greedy convergence as bare `xx switch` via the shared `currentWins` (picker.ts). Thresholds became per-window SCREENING bars only: `thresholds.session` 95, `thresholds.weekly` 98 (7-day aggregate AND per-model caps - the user re-confirmed 98 for the Fable cap when asked directly, after a transient edit suggested 95). Trigger floors and every PickCtx are built from `effectiveBars` (thresholds minus projectionMargin) so trigger and screening can never diverge (margin ping-pong). The greedy path never depleted-waits or pre-parks. Shipped in v0.10.0.

**Why:** weekly allowance is use-it-or-lose-it at a fixed per-account reset (support.claude.com article 11049741), so the account that must burn its remaining quota fastest to beat its reset is the one most quota is about to be forfeited on - draining it first maximizes total pooled tokens, the point of [[tokenmaxxing-project]].

**How to apply:** `pacePressure` + `swapPreference` in `src/lib/picker.ts` (shared with the statusline pool sort, so the leftmost usable parked account IS the next swap target). Rolled-over cached week = fresh (100 remaining, extrapolated deadline); never-sampled or no reset anchor = pressure 0, ranks last. Tiebreak soonest `weeklyExpiry`, then lowest 7-day usage. Exhaustion filtering (aggregates + gated per-model caps, see [[cc-per-model-limits]]) is unchanged. Shipped in v0.7.0 (released + npm-published 2026-07-13). See [[cc-codex-auth-mechanics]] for quota internals.
