# Supervisor, hooks, and the move

- A Claude move is `swap` = verify the target's store, then the caller's respawn marker (`writeRespawnMarker` in `sessions.ts`, one shared site for the Stop, StopFailure, and SessionStart hooks). The engine returns `needs-respawn` for a shared-seat provider when the caller cannot respawn (an unsupervised session, a subagent failure, the check tick), after the enforced stamp and before any pick. The Stop hook writes the marker on `swapped` too, because every Claude move is a respawn; the supervisor honors the marker's `accountId` on relaunch and re-picks only when that account left the pool.
- A session id is not fixed for the life of a process: `/clear` and an in-session `/resume` give the same process a new id, while `--resume` keeps the id unless `--fork-session` is passed. The live id is `TOKENMAXXING_SESSION_ID`, or the `current` id in `sessions/<sid>.json` (`liveSessionId`); the 30-day prune skips a record whose session has a presence record under `live/`. The Stop, StopFailure, and SessionStart hooks write the marker only when stdin `session_id` is absent or equals the live id. A hook whose stdin id differs adopts it (`adoptLiveSession`) only when the hook's own process descends, through shell processes alone, from the pid in the session's presence record (a hook runs as `hook <- sh -c <- claude`; a shell that execs its last command drops the middle hop). `source` cannot prove the emitter, because `/clear` is `supportsNonInteractive` and a nested `claude -p /clear` reports `source: "clear"` too. Any other differing id belongs to a nested process that inherits the supervised environment and runs its own session; it does not move the parent. The marker file stays named after the launch id; the marker carries the live id, and a relaunch whose live id has no transcript yet starts it with `--session-id` instead of `--resume`, because `claude --resume` on an id without a transcript exits with `No conversation found`. A first launch with `--resume <id>` does the same when `sessions/<id>.json` exists and no transcript does, so an id the supervisor advertised before its first turn stays resumable; an id the supervisor never launched passes through unchanged. "No transcript" means no Claude Code project directory holds `<id>.jsonl` (`findTranscript`), because the binary's own `--resume` falls back to the repository's worktrees and then to every project directory.
- The marker's `compact` flag (`true` from Stop, SessionStart, and the seat watch, `false` from StopFailure) makes the supervisor run `claude -p --resume <live id> /compact` under the old seat's store between the kill and the relaunch, unless that seat's record carries a live `enforcedUntil` or the marker is a depleted stop, where no account has quota to compact on (`src/lib/compact.ts`; `/compact` is `supportsNonInteractive`, and `--resume` honors the `compact_boundary` row). A refused compaction still exits 0, so the only success signal is a `compact_boundary` row appended to the transcript after the spawn. The marker's `origin` (`stop`, `sessionstart`, `stopfailure`, `seatwatch`) names its writer and picks the first prompt. `compact` stays beside `origin` although the writers make it a function of the origin: the check-tick self-update replaces the hooks under supervisors that still run the previous release, and such a supervisor rejects a marker that lacks one of its required keys as corrupt and ends the session. Adding a marker key is safe, because the older schema strips it; removing or renaming one is not. No hook can compact a running session from outside: only the restart path works. Codex compacts hook-side instead, before the decision, through `codex app-server` (`thread/resume` then `thread/compact/start`, JSONL over stdio), because after the respawn the old account's store is no longer the session's home. Both steps are bounded and best-effort: a failure logs and the move proceeds with the full context.
- A `--resume` relaunch submits a first prompt that names the move (and the compaction, when it landed). After a `stop` move the previous turn had finished, so the prompt asks Claude to end the turn without restating it and to relaunch the background work that turn waited on. Every other origin gets the continue text, which says the restart ended the session's background Bash tasks, Monitors, and Workflow runs; `sessionstart` is in that group because a prompt sent inside the marker poll window can start on the old seat before the kill. The prompt is a positional prompt after the session id in a terminal session, or the first `user` line through the supervisor's stdin relay in a stream-json session, because the binary ignores a positional prompt under `--input-format stream-json`. In a stream-json session every relaunched child first gets the latest line of each control request in `REPLAYED_REQUESTS` (`initialize` and the SDK's session-state setters) that the session ever sent, on the `--resume` path too, because the SDK sends `initialize` once per query and it carries the appended system prompt, the hook callback ids, and the SDK MCP servers; the SDK keeps those ids for the life of the query and files the second answer as unmatched. A `--session-id` relaunch (a live id with no transcript yet) gets no compaction and no first prompt. In a stream-json session the relay replays to it the other lines the killed child received since its launch, `user` lines included, except control traffic. Each control request outside `REPLAYED_REQUESTS` gets an error `control_response` on stdout instead, because it can have an effect outside the transcript (`mcp_call`, `rewind_files`, `update_settings`) that a replay would repeat. `control_response` lines answer the killed child's own requests and are dropped. The Agent SDK awaits every control request it sends with no timeout, and a client that awaits one before its first `user` line (the TypeScript SDK's `supportedCommands`, `supportedModels`, `supportedAgents`, or `accountInfo`, which await `initialize`) hangs on a lost answer; the TypeScript SDK itself streams the prompt without awaiting `initialize`, and T3 Code sends its first `user` line that way. The relay keeps those lines only until that child's transcript exists. A replayed request the killed child had already answered gets a second response, and so does an answered request that gets the error; the SDK files each as unmatched. Every value-taking root flag has to be in `VALUE_TAKING_ROOT_FLAGS`, or a respawn drops its value as a positional (`--permission-prompt-tool stdio` loses `stdio` and the relaunched harness session cannot answer permission prompts); the `binary-bump-audit` skill audits the table on each binary bump. The relay decision reads the effective flag set after the persisted flags load, because a bare `claude --resume <sid>` replays a harness session's stream-json flags from `sessions/<sid>.json`.
- Every root subcommand of the binary, aliases and hidden ones included, has to be in `SUBCOMMANDS` in `src/entries/supervisor.ts`, or the supervisor runs it as a session: a one-shot read such as `claude plugins list` then waits on the pool lock to pick a seat and to exit, a move relaunches it with its positionals dropped, and the `--session-id` prefix hides it from the binary's early dispatchers (`daemon`, and a sole `--update` or `--upgrade`, which `SOLE_UPDATE_FLAGS` covers). Hidden commands register in several scopes; the `binary-bump-audit` skill audits the set on each binary bump.
- The supervisor watches its own seat every ten seconds while the child runs (`moveExhaustedSeat`: the account record plus the seat's tee through `teeObservation`, `usableAt` against `thresholdBars(cfg)`); at or over a bar it runs `evaluateAndMaybeSwap` with the seat passed explicitly (the supervisor's env names no store) and writes the respawn marker itself with `compact: true` and origin `seatwatch`, under the same `launchedAt` gate. This is the move that waits for no hook: a harness session has no turn boundary while a workflow or background agents burn the window between prompts, and a subagent StopFailure stamps the wall but returns `needs-respawn`. A turn in flight is cut at the bar. A decision that moves nothing is retried after a minute, a quiet check after ten seconds.
- The supervisor forwards SIGTERM to the real claude child and exits after it. The Agent SDK stops a session with SIGTERM on the process it spawned, which is the wrapper; without the forward the child survives as an orphan on the old seat while the harness relaunches the same session through a new supervisor, and the orphan's hooks write markers with the old launch stamp that the stale gate discards.
- A Claude session counts on one account in `presence()`: the account its `wait-queue.json` claim names while it moves or waits, else the account of its presence record. A move writes that claim in the critical section that picks the target, for twice `CLAUDE_COMPACT_KILL_MS`, and the relaunch releases it in the critical section that writes the new presence; a depleted decision writes its claim on the recovery target instead, and the depleted exit at the launch gate releases it, as does a marker the supervisor discards (a stale launch). Without the claim a burst of moves lands on one target, because a moving session's presence record names the child pid that the kill ends, and the relaunch waits on the compaction.
- A stream-json session (`--output-format stream-json`: the Agent SDK, T3 Code) has no TUI, so the statusLine command never runs and its stderr is a log nobody reads. Its seat's tee comes from the child's stdout instead: for a stream-json session with a seat, the supervisor pipes the child's stdout, forwards every chunk unchanged with backpressure, tees each `rate_limit_event` line's `rate_limit_info.unifiedWindows` (`five_hour` and `seven_day`, `utilization` a fraction, `resetsAt` in epoch seconds), and restamps the tee on each `assistant` line, because Claude Code emits the event on every one-point move of either window, so an API response with no event moved nothing. After the child exits, the supervisor waits for the pipe's end of file, or for one second with nothing read, before it writes a notice or relaunches, because a descendant that inherited the pipe holds it open. The supervisor's notices (compaction, move, depleted stop with its reset time, resume, and a fatal exit) therefore go to stdout there as `{"type":"system","subtype":"informational","level":"warning",...}` lines, the shape the binary emits for its own print-mode notices, with `content`, `uuid`, and the live `session_id` the supervisor is driving at that moment. The SDK passes unknown system subtypes through, but the line is not inert: the reader clears its last error text on every message that is not a `result`, so the supervisor writes only between the kill and the relaunch, except a notice that ends the session (the depleted-pool exit, a corrupt marker, the wrap-depth or wrapper-chain abort, a failed presence write, a binary-resolution failure). T3 Code renders `informational` only at level `warning` and `notification` only at priority `high` or `immediate`, dropping `notice`, and cuts the summary at 120 characters, so the operative clause goes first and the variable-length part (an account label, a failure reason) last. Every stdout line is a permanent chat row. The tee also follows each task the child starts (`task_started`) until a `task_notification` or a `task_updated` to `completed`, `failed`, or `killed`, and between the kill and the relaunch of a move the supervisor writes a `task_notification` with `status: "stopped"` and `reason: "worker_restart"` for each task still open, because T3 Code drops a live task only on those two edges, ignores the `background_tasks_changed` level line, and otherwise keeps the thread's background liveness at `working` until the session exits. The depleted stop writes no synthetic task and holds nothing open: the supervisor writes the stop notice and exits, so the harness ends the run instead of showing the session as working until the reset. In a stream-json session the stop also writes a `rate_limit_event` with `rate_limit_info: { status: "rejected", resetsAt }` (epoch seconds, no `rateLimitType`, `utilization`, or overage fields) and then a `result` with `subtype: "error_during_execution"`, `is_error: true`, `errors: [<notice>]`, `terminal_reason: "blocking_limit"`, and `num_turns: 0` (`depletedLines`). T3 Code Orchestrator V2 reads that pair as a `usage_limit` failure whose message is `errors[0]` and whose reset is the event's `resetsAt`; without the result it records its generic `Provider turn failed.` for the dead process. The result carries no `user_message_uuid`, because a uuid that is not the active turn's prompt drops the result as another turn's. The notice text never contains `interrupt` or `cancel`, which T3 Code reads as an interrupted or cancelled turn. A first launch writes the pair only after the relay reads the harness's first `user` line (`StdinRelay.firstUser`, which also settles when stdin ends), because T3 Code sets its active turn just before it sends that line, and a result written earlier is buffered as a wake frame or lost. Before that wait, the relay answers each control request the harness sent or sends later, `initialize` included, with an error `control_response` that carries the notice (`StdinRelay.refuse`), because no child exists to answer them and a client that awaits an answer before its first `user` line would otherwise wait on the wrapper forever. A stop after a move writes the pair at once and refuses nothing, because the turn the move cut is still the active one and the killed child already answered the cached setup requests. The hook-output `systemMessage` field cannot carry the wait: the supervisor kills the child within 150 ms of the marker. The mode is read from the effective flag set like the relay, never from the parent process, and a bare `--resume` or `--continue` first reads the saved flags for that session to pick the channel.
- The T3 Code capability probe is the one `--no-session-persistence` run the supervisor seats (`isCapabilitiesProbe` in `src/entries/supervisor.ts`: the stream-json flag set with `--strict-mcp-config`, `--setting-sources=user,project,local`, and `--settings {"disableAllHooks":true}`, plus the environment `ENABLE_CLAUDEAI_MCP_SERVERS=false`, `CLAUDE_CODE_AUTO_CONNECT_IDE=0`, and `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL=1`). It takes its seat from `pickSeat` under the pool lock, a depleted pick included, writes no presence record, no wait claim, and no session flags, and has no seat watch or respawn marker, because it sends no prompt and consumes no quota headroom as a session. Its `get_usage` control request is answered by the supervisor from the seat's sampled windows (`teeObservation`, then `sessionWindow`, `weeklyWindow`, and `limitWindows` at `liveUsed`) and never reaches the child, so the probe sends no usage read and no sampler claims one for it. The only stdin lines it forwards are an `initialize` control request, a `control_response`, and a `control_cancel_request`; any other line, a `user` prompt included, kills the child, so the seated run cannot become a session. A probe shape that stops matching fails closed to the unmanaged passthrough.
