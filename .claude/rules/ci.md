# CI and the publish job

The release procedure (shipping a merge, verifying a publish, recovering a failed one) is the `release` skill; `.memory/ci.md` holds the traps.

- The `publish` job in `ci.yml` runs on every push to main and nowhere else (a `workflow_dispatch` on another ref does nothing). When a packed file changed since the tag of the current version, it bumps the minor version, commits `chore: release <version>` to main, creates the GitHub release at that commit, publishes, and waits up to 60 minutes until the registry lists the version; otherwise it publishes nothing. The packed set is read from the merge commit's tree, so a PR that only deletes `README.md`, `DESIGN.md`, or `LICENSE` is outside the diff; touch `package.json` in that PR to release it. The packed set is whatever `npm pack --dry-run` lists, NOT the `files` array: `src`, `README.md`, `DESIGN.md`, plus `LICENSE` and `package.json`, which npm always includes even though `files` never names them. A change confined to `docs/`, `.memory/`, `.github/`, `.claude/`, or AGENTS.md publishes nothing; the docs site deploys from main on its own. A version set by hand in a PR is published as it is when the registry lacks it, which is how a major release happens.
- The release commit is the one push to main outside a PR; it comes from `GITHUB_TOKEN`, so it triggers no CI run. Publish jobs serialize on the `publish` concurrency group: a job whose release commit loses the push race fails without publishing, and the job queued behind it releases both merges as one version. A concurrency group holds at most one pending run, and the newest run checks out the newest merge, so the content of a cancelled run is released by the run that replaced it. A job that pushed its release commit and then failed to publish leaves main and the tag one version ahead of the registry; the next push to main, or `gh workflow run ci.yml --ref main`, publishes that version. A job whose wait times out has published; a run that starts before the registry lists that version fails on `E409` or `E403`, and the first run after the listing releases what merged since.
- Tool facts the job is written around: `npm pack --dry-run --json` prints an object keyed by package name on npm 12 and an array on npm 11, so the job reads `files` through a `..` recursion that accepts both, with `-e` to fail the step on none; on npm 12, `npm view <pkg> <field> --json` prints a one-element array, so read it as `.[0]` or read the `?write=true` document below with curl; the registry serves the package document that `npm view` reads through a CDN with `cache-control: public, max-age=300`, and that copy can omit a version for minutes after the registry holds it, so the version assignment and the wait read `https://registry.npmjs.org/tokenmaxxing?write=true`, which the CDN passes to the origin (`cf-cache-status: DYNAMIC`) and which answers only the full document (`406` for `application/vnd.npm.install-v1+json`); npm scans a publish before it lists the version, typically for about five minutes, at peak for 15 minutes or more, and at times for more than 25 minutes, and answers a second publish of it with `E409 Cannot publish over previously staged version` during the scan and `E403 You cannot publish over the previously published versions` after it; the pending state is readable only with a maintainer token (`GET /-/package/<name>/version/<version>/status`), and a trusted-publishing token can only publish, so the job waits for the listing and the job queued behind it reads a complete list; `npm version <bump> --no-git-tag-version` rewrites `package.json` only, and `bun.lock` carries no root version, so `--frozen-lockfile` keeps working; `git tag --contains` and `git diff <tag> HEAD` need `fetch-depth: 0`.
- The `test` job of `ci.yml` runs the install, the typecheck, and the pack check, the `nix` job builds the flake, and Vercel builds the docs site, on every pull request head and every push to main. This repository runs its CI on the owner's self-hosted runners on an arm64 machine while they are up, and on the GitHub-hosted `ubuntu-24.04` image while they are down: the repository variable `CI_RUNNER` selects them, `github` picks the hosted image, and the `ship` skill's runner switch sets it. The `test` job takes the `check` label and the `nix` job the `build` label. A self-hosted job has no Docker, a fresh user with a memory home, and the machine's own multi-user Nix with flakes, so the Nix installer and cache steps run only under `runner.environment == 'github-hosted'`, and the flake builds as an untrusted Nix user that ignores the flake's `extra-substituters`. The `publish` job stays on `ubuntu-24.04`, because npm trusted publishing supports only GitHub-hosted runners.
- npm trusted publishing is bound to the literal workflow filename `ci.yml`. Renaming it silently breaks publishing. It supports only GitHub-hosted runners (https://docs.npmjs.com/trusted-publishers).
